# Seven-area zero-risk calibration

Use this reference only to decide whether each later assessment area is genuinely assessable above zero. Do not allocate points or infer a grade.

The official form allocates 30 points across six four-point areas and a six-point program-execution area. It states that a zero in any area makes the total zero.

## 1 Difficulty of the programming task

Minimum assessability requires a thesis-level task and evidence of non-trivial student contribution. Relevant signals include knowledge beyond compulsory coursework, non-obvious algorithms, cross-component/platform integration, substantial data/persistence, or study of a larger system context. The three approved contributions and three exam-topic relationships must be technically genuine.

## 2 Structure, language, style, and appearance

Minimum assessability requires all compulsory parts, coherent sectioning, readable edited prose, usable contents/numbering/captions, legible balanced figures/tables, and proper citation/quotation. A technically strong system cannot compensate for an absent or unusable thesis document.

## 3 User documentation

Minimum assessability requires a defined audience, purpose, hardware/software prerequisites, installation/start guidance that matches reality, process-oriented function descriptions, runtime-message explanations, troubleshooting/security guidance, and enough visual help for the system type.

## 4 Software design or solution plan

Minimum assessability requires a design from which the main source structure could be implemented: architecture/layers, data design where applicable, module/class structure and important operations, and user/API/CLI interaction and navigation. The mandatory class diagram remains part of the checkpoint source.

## 5 Implementation or realization

Minimum assessability requires documented implementation decisions and source that corresponds to the plan, uses justified language/tool features, is readable and maintainable, handles errors/resources, and records limitations. Source listings alone are not implementation documentation.

## 6 Testing

Minimum assessability requires plans/cases, expected and observed results, coverage of key functions and integration, relevant high-volume/scalability/efficiency or correctness analysis, and lessons from testing. A test-framework dependency or screenshot of green tests alone is insufficient.

## 7 Program execution

Minimum assessability requires a runnable demonstrated system that is accurate against the promise, robust to realistic user errors and data, usable for its intended audience, and safe/interruptible where relevant. An ordinary ethical test crash blocks acceptance until repaired or convincingly bounded and handled.

## Cross-area rule

If one area is effectively absent, contradictory, or impossible to evaluate from the supplied artifacts, mark the corresponding checkpoint gate Fail or Unverified and return Insufficient. If it is merely weak but minimally assessable, preserve the checkpoint decision and state the weakness as a required correction only when another explicit checkpoint-5 gate is violated; otherwise list it as a grading-risk suggestion.
