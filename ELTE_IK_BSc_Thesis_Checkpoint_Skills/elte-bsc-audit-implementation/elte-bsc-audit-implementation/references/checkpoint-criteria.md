# Checkpoint 4 mandatory criteria

Apply every gate. A claim without direct evidence is Unverified.

## Completion calculation

Create a commitment ledger from the approved proposal and requirements:

| Commitment | Weight | Implemented | Integrated | Runnable | Demonstrated/tested | Credited fraction | Evidence |
| --- | ---: | --- | --- | --- | --- | ---: | --- |

Use approved importance/effort weights when documented. Otherwise use equal weights and say so. Credit requires implemented behavior integrated into the intended path and runnable/demonstrable evidence. Use a range when partial completion is uncertain. Generated code, boilerplate, inactive branches, stubs, mock-only screens, and unintegrated modules receive no completion credit.

The supported lower bound must be at least 60 percent.

## Mandatory gates

### C1 Stable approved baseline

The approved topic, exactly three contributions, requirements, design, and any supervisor-approved changes are available and mutually reconcilable. Without a baseline, completion is Unverified.

### C2 Evidence-supported 60 percent

The commitment ledger establishes a supported lower bound of at least 60 percent. A student estimate, issue count, commit count, or line count alone does not pass.

### C3 Runnable integrated slice

The student presents a coherent system that runs in the intended environment and completes representative end-to-end/core workflows. Static screenshots, isolated unit outputs, or disconnected components are insufficient.

### C4 Contribution progress

Progress is substantive across the three approved contributions, or the weighting explains why a different distribution still represents at least 60 percent of the approved thesis. No contribution may have silently disappeared.

### C5 Source and development evidence

The supervisor has access to the current repository: GitHub access for GregoryMorse or GitLab access for gregory.morse1@gmail.com, unless another method is approved. History shows demonstrable increments rather than a single opaque final dump. Identify the audited revision.

### C6 Correspondence to design

Implemented modules/classes, interfaces, data model, and main workflows correspond to the design. Deviations are documented with rationale and reflected back into the design plan.

### C7 Implementation quality

Representative core code is readable, structured, maintainable, and uses suitable modern language/tool features. Data representation, reuse mechanisms, identifiers, comments, module boundaries, and important non-obvious decisions are defensible.

### C8 Control, error, and resource handling

The demonstrated slice handles realistic invalid input and important failure conditions without an ordinary ethical test crashing the system. Exceptions/control paths and resource use such as time, memory, disk, connections, or user waiting are addressed proportionally to the implemented scope.

### C9 Reproducibility

Dependency/environment manifests, configuration guidance, setup/run commands, seed/sample data, and external-service assumptions are sufficient to reproduce the demonstrated slice in a safe environment.

### C10 Live debugging familiarity

The student can inspect and explain execution using tools appropriate to the stack: browser developer tools, IDE debugger, API inspector, database viewer, or console tracing. The exact mix is project-dependent. The evidence must show familiarity with their own code, not a rehearsed screen-only demo.

### C11 Proportional testing

Tests cover implemented core behavior and important edge/failure conditions, with test steps or inputs, expected results, and observed results. Include integration/end-to-end evidence where components are already integrated. Current testing need not equal the final ten-page chapter, but cannot be postponed entirely.

### C12 Implementation documentation

A substantive current draft records the environment/stack, repository structure, main implementation decisions, realized complex features, important snippets, design correspondence, debugging practice, and known shortcomings. It has a credible path to the final minimum ten pages without padding.

### C13 Final-exam topic discussion

Exactly three topics are selected or actively finalized from the official list, their subtopics have authentic relationships to the thesis, and implementation-heavy coverage is being documented. Forced topic labels or generic summaries do not pass.

### C14 AI-use record

When AI tools are used, the student maintains an accurate tool/purpose/location record and point-of-use disclosures. Substantial minimally modified generated code has inline attribution. If no AI was used and the student explicitly confirms this, mark AI-specific details N/A while still checking the current declaration requirement for final submission.

## Final-stage warnings

Report gaps in the final user documentation, ten-page implementation/testing targets, thirty-item bibliography, full advanced testing, AI declaration, and submission package as future risks unless they already prevent evidence of the 60-percent implementation.
