## FAILURE_DESCRIPTION
Failing case: graph_n=2, sequence_idx=0, operation="crash", error `name 'state' is not defined`. The crash happens during `init(graph)` — the very first call before any update — so no graph/update/expected-vs-actual result exists; the harness never got a state back.

Tracing `init`: it builds `adj`, `dist`, `parent`, `tree` as local variables, runs the initial BFS, then calls `_refresh_result(state)` and `return state`. But `state` is never created inside `init` — the function signature is `init(graph)` with no state parameter (correct per the interface), and no local `state = {...}` is ever assigned. Hence the `NameError` at the `_refresh_result(state)` line.

## ROOT_CAUSE
`init` never constructs the state dict. The last two lines of `init` are:

```python
    _refresh_result(state)
    return state
```

but `state` is undefined in that scope. The intended state dict (documented in the module docstring: keys `'n'`, `'dist'`, `'parent'`, `'tree'`, `'adj'`) is never assembled from the local variables `n`, `dist`, `parent`, `tree`, `adj`. This is a pure construction bug, not an algorithmic one — the BFS logic and the insert/delete logic were never even exercised.

## REPAIR_HINTS
Smallest fix: in `init`, before calling `_refresh_result`, build the state dict from the locals, e.g.:

```python
    state = {'n': n, 'dist': dist, 'parent': parent, 'tree': tree, 'adj': adj}
    _refresh_result(state)
    return state
```

That is the only change needed to clear this crash. Do not add a `state` parameter to `init` — the interface is `init(graph)` only.

After this fix, the candidate will actually run, so expect the next failure (if any) to come from the algorithmic logic rather than construction. Two things to watch when re-testing (not to change preemptively, but they are the likely next suspects):
1. `_bfs_from_frontier`'s `if dist[w] <= du: continue` guard treats "unreachable but closer" as settled — the comment itself flags this as suspect; verify it against a case where a vertex is unreachable (dist -1) but should be reached.
2. In `delete_edge`, the frontier is built as all vertices with `dist == old_dv - 1` AFTER the subtree's dists were set to -1; confirm no frontier vertex was itself in the detached subtree (the code claims tree edges always go d -> d+1, so this should hold, but verify).
