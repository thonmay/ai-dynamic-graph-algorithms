## FAILURE_DESCRIPTION
Case: 3-vertex directed graph, root 0. The case's `graph` field shows the final
graph of the sequence (edges 0→1 and 1→2), and `sequence_idx: 0` with
`operation: "insert (0, 1)"` is the FIRST update of that sequence. Expected
result: `distances {0:0, 1:1, 2:2}`, `parent {0:None, 1:0, 2:1}`.
Actual result: `distances {0:0, 1:1, 2:-1}`, `parent {0:None, 1:0, 2:None}`.
Flagged wrong vertex: 2 (expected distance 2, got -1).

## ROOT_CAUSE
The candidate's per-operation behavior is CORRECT; the mismatch is a
sequence-vs-single-operation expectation mismatch, not an algorithm bug.

Trace of `insert_edge(0,1)` on the state that exists at sequence_idx 0:
- Before the op, the only edge that can exist is (0,1) itself (it is being
  inserted), so the pre-op graph has no edges: `dist = {0:0, 1:-1, 2:-1}`,
  `tree = [[], [], []]`.
- `_sync` adds 1 to `adj[0]`.
- Guard `if dist[u] == -1 or (dist[v] != -1 and dist[u] + 1 >= dist[v])`:
  `dist[0]=0`, `dist[1]=-1` → not triggered.
- v=1 re-parented to 0: `dist[1]=1`, `tree[0]=[1]`.
- Cascade queue `[1]`: `tree[1]` is empty, loop ends.
- Result: `dist = {0:0, 1:1, 2:-1}` — exactly the candidate's output.

The expected snapshot `{2: dist 2, parent 1}` is only reachable if edge (1,2)
already exists, i.e. it is the state AFTER the full sequence (0→1 then 1→2),
not after op 0. The case's `graph` field is the final graph of the sequence,
which is why it looks like the candidate "missed" vertex 2 — but at op 0,
vertex 2 is genuinely unreachable, and the candidate's output is the correct
BFS state for the graph after applying only `insert (0,1)`.

Hypotheses ruled out:
- Cascade bug: the cascade only runs when a vertex's distance strictly
  improves; here it is a pure reachability expansion with an empty subtree,
  so no buggy code path is even executed.
- `_sync`/adjacency bug: `adj` is updated correctly before the guard.
- Guard bug: the guard correctly handles the `dist[v] == -1` (newly
  reachable) case by not returning early.

## REPAIR_HINTS
Do NOT "fix" the candidate's algorithm — it is correct for this operation.
The problem is in how the case's expected result is produced/compared:

1. The harness must apply the FULL update sequence to the initial (empty or
   given) graph and compare the candidate's state after EACH operation against
   the expected state after that same prefix of the sequence. The expected
   snapshot for `sequence_idx: 0` must be computed from the graph after only
   `insert (0,1)`, not from the final sequence graph.
2. Equivalently, the case's `graph` field should be the graph BEFORE the
   operation (or the harness should track per-step expected states), and the
   `expected` field should be the BFS state after applying exactly that one
   operation to the pre-op graph.
3. If the harness instead intends `graph` to be the pre-op graph and the
   expected to be post-op, then the case data is inconsistent: with pre-op
   graph = {0→1, 1→2} and op = insert(0,1), the edge (0,1) would already be
   present, making the "insert" illegal (it must flip exactly one entry).
   This confirms the `graph` field is the final graph and the expected is a
   full-sequence snapshot.

Approaches that will NOT work:
- Modifying `insert_edge` to somehow "see" vertex 2: at op 0 there is no edge
  into 2, so no correct algorithm can report dist[2]=2.
- Changing the cascade to scan all vertices: unnecessary and would still
  produce dist[2]=-1 since 2 has no in-edges at this step.
