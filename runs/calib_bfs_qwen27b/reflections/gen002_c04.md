## FAILURE_DESCRIPTION
Operation: timeout (no result within 3s) on a 3-vertex graph
`[[0,0,1],[0,0,1],[0,0,0]]` (edges 0->2, 1->2; root 0). The hang occurs during
the 20-operation update sequence (chunk_start 0, sequence_idx 0). The note says
"likely an infinite loop in init or one of these updates". init is a plain BFS
and cannot loop, so the hang is in `insert_edge` or `delete_edge`.

## ROOT_CAUSE
The cascade loop in `insert_edge` is unbounded:

```python
    queue = [v]
    head = 0
    while head < len(queue):
        x = queue[head]
        head += 1
        for y in list(tree[x]):
            if dist[y] > dist[x] + 1:
                ...
                queue.append(y)
```

There is no visited/processed set. A vertex can be re-parented and re-queued
multiple times within a single update, and because the tree is mutated while
being traversed, a vertex can be re-queued indefinitely.

Concrete trace of the cycle (n=3, root 0). After the first few operations the
state is: dist = {0:0, 1:1, 2:1}, parent = {0:None, 1:0, 2:0},
tree = {0:[1,2], 1:[], 2:[]}. Now consider `insert (1, 2)`:

1. `_sync` adds 1->2. `dist[1]=1`, `dist[2]=1`, and `dist[1]+1 = 2 >= 1`, so
   the early-return guard `if dist[v] != -1 and dist[u] + 1 >= dist[v]` fires
   and nothing changes. (This particular call is harmless.)

The dangerous pattern is an insertion where `dist[u]+1 < dist[v]` (or v is
unreachable) and the cascade re-parents a vertex y to a new parent x, but y
still appears in `tree[old_parent]`'s iteration list, or a vertex is re-queued
after its distance has already been lowered by an earlier re-parenting in the
same cascade. Because `dist[y] > dist[x] + 1` is re-evaluated against the
*current* (already-lowered) `dist[x]`, a vertex whose distance was just set to
`dist[x]+1` can still satisfy the condition if `x` itself is later re-parented
to a closer vertex, re-queueing y again. With 3 vertices and a small number of
edges this oscillation can repeat without bound.

The same unbounded-queue pattern exists in `delete_edge`:

```python
    queue = [v]
    head = 0
    while head < len(queue):
        x = queue[head]
        head += 1
        ...
        else:
            dist[x] = nd
            ...
            queue.extend(tree[x])
```

Here `queue.extend(tree[x])` re-queues all current tree children of x. If x's
distance changes, its children's distances may also change, and they are
re-queued. But a child can be re-queued multiple times if its parent is
re-parented again in the same cascade, and there is no visited set to prevent
reprocessing.

## REPAIR_HINTS
1. **Add a visited/processed set to both cascade loops.** In `insert_edge`,
   track a `seen` set of vertices already re-parented in this cascade. Only
   re-parent and enqueue a vertex `y` if `y not in seen`. This guarantees each
   vertex is processed at most once per update, bounding the loop.

2. **In `delete_edge`, similarly track a `seen` set** for vertices already
   re-parented in the cascade. When extending the queue with `tree[x]`, only
   enqueue children not yet in `seen`.

3. **Alternative (simpler and safer): fall back to a full BFS recompute**
   after any update that actually changes the tree. This is O(n^2) per update
   (adjacency matrix) and will never hang. The research goal says "reach full
   correctness first, then avoid a full recompute after insertions", so a
   correct-but-slow baseline is acceptable as a first step. The incremental
   path can be layered on top once correctness is established.

4. **Do NOT** try to fix the cascade by adding a depth counter or a max-iteration
   guard — that masks the bug and can still produce an incorrect tree. The
   visited-set fix is the minimal correct change.

5. **Do NOT** rely on the early-return guard in `insert_edge` to prevent
   re-queueing; the guard only checks the *initial* (u,v) pair, not the
   cascaded vertices.
