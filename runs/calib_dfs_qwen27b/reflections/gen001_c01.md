## FAILURE_DESCRIPTION

Case: n=2, initial graph is the all-zero 2×2 matrix. `init` yields
`parent=[None,None]`, `discover=[0,-1]`, `finish=[1,-1]` (only root 0 in the forest).
Update: `insert (0,1)` → graph becomes `[[0,1],[0,0]]`.

- Expected: `parent={0:None, 1:0}`, `discover={0:0, 1:1}`, `finish={1:2, 0:3}` (vertex 1 is now reachable and must be in the DFS forest).
- Actual: `{'parent': [None, None], 'discover': [0, -1], 'finish': [1, -1]}` — vertex 1 still absent from the forest.

## ROOT_CAUSE

`_is_valid` (lines 44–60) only verifies the *ordering* property (no forward-cross
edges among vertices already in the forest). It never verifies that the forest is
**spanning** — that every vertex reachable from the root in the current graph is
present in the forest.

The exact unhandled condition is in `_is_valid`:

```python
if discover[v] == -1:
    # edge to unreachable vertex: fine (v not in forest)
    continue
```

Trace on the failing case: after inserting (0,1), u=0, v=1: `row[1]=1` but
`discover[1]==-1`, so the `continue` branch is taken and no violation is reported.
`_is_valid` returns `True`, so `_maybe_recompute` keeps the stale state and
`insert_edge` returns a forest missing vertex 1.

The same flaw applies symmetrically to deletions: if deleting an edge makes some
previously-reachable vertex unreachable, `_is_valid` still returns `True` (the
stale parent pointers of the now-unreachable vertex are never checked), so the
stale forest is kept. The check is one-directional: it can only detect ordering
violations, never membership violations (vertices that should be in the forest
but aren't, or vice versa).

## REPAIR_HINTS

Smallest fix: make `_is_valid` also verify spanning-ness. After the edge-ordering
loop, compute the set of vertices reachable from 0 in the current graph (BFS/DFS
over `graph`, O(n²)) and require it to equal `{v : discover[v] != -1}`. If they
differ, return `False` so `_maybe_recompute` falls back to a full `_dfs`
recompute. This restores correctness for both insertions (newly reachable
vertices) and deletions (newly unreachable vertices) while keeping the fast path
for updates that don't change reachability or ordering.

Concretely, in `_is_valid`, after the existing double loop add:

```python
# spanning check: reachable set in graph must equal forest vertex set
seen = [False] * n
stack = [0]
seen[0] = True
while stack:
    u = stack.pop()
    for v in range(n):
        if graph[u][v] and not seen[v]:
            seen[v] = True
            stack.append(v)
for v in range(n):
    if seen[v] != (discover[v] != -1):
        return False
```

Approaches that will NOT work:
- Checking only the single updated edge (u,v) for ordering: the insertion case
  has `discover[v]==-1`, so any ordering check on that edge alone passes; the
  problem is membership, not ordering.
- Keeping the current `_is_valid` and special-casing insertions to always
  recompute: correct but abandons the fast path entirely for insertions, and
  still leaves the deletion-side membership bug (stale parent pointers for
  newly unreachable vertices) unless a symmetric fix is made.
- Relying on the verifier's "unreachable vertices are not checked" clause: the
  verifier does not check unreachable vertices, but it DOES check that every
  reachable vertex is in the forest (parent[v] must be a tree in-neighbor for
  every reachable v), so a missing reachable vertex is a hard failure.
