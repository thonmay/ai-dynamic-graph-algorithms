## FAILURE_DESCRIPTION
3-vertex directed graph, root 0. The state before the update was a valid DFS forest of the pre-update graph with parent=[None,0,1], discover=[0,1,2], finish=[5,4,3] (i.e. the pre-update graph contained 0->1, 1->2, and 0->2, so DFS went 0,1,2). The update is `delete (1,2)`, leaving the graph with edges 0->1 and 0->2 only.

- Expected (any valid DFS of the new graph): parent[2]=0, e.g. discover=[0,1,3], finish=[5,2,4] (0->1 first, then 0->2).
- Actual returned: the unchanged old state parent=[None,0,1], discover=[0,1,2], finish=[5,4,3].

The verifier rejects it because parent[2]=1 but edge 1->2 no longer exists, so parent[2] is not a tree in-neighbor of 2 in the current graph.

## ROOT_CAUSE
`_is_valid_dfs` (the fast-path check used by both `insert_edge` and `delete_edge`) never verifies that each parent edge actually exists in the current graph. It only checks:
1. no forward-cross edge among current graph edges, and
2. interval consistency of parent/child (`discover[p] < discover[v]` and `finish[v] < finish[p]`).

After deleting 1->2, the old forest passes both checks: the remaining edges 0->1 and 0->2 are both tree edges (descendants), and parent[2]=1 is interval-consistent with discover/finish. But the parent pointer 1->2 is a dangling edge — it was a tree edge of the old graph and is not present in the new one. The check therefore returns True, `delete_edge` keeps the stale state, and the returned parent array references a non-existent edge.

The missing condition: for every reachable v with parent[v]=p, the matrix entry graph[p][v] must be 1.

## REPAIR_HINTS
Smallest fix: in `_is_valid_dfs`, inside the parent-consistency loop (the `for v in range(n)` block), after the `p is None` handling, add:

```python
if not graph[p][v]:
    return False
```

before the interval checks. This makes the fast path reject any state whose parent pointers reference edges that were just deleted, forcing the `_make_state(graph)` recompute fallback.

Notes:
- Do not try to "repair" the forest locally in `delete_edge` by reassigning parent[2]=0 — that alone does not fix discover/finish (2's interval must be re-nested under 0's remaining children), and the recompute fallback is already correct; the goal is just to make the validity check sound.
- The forward-cross check itself is fine; the bug is purely the missing parent-edge-existence test.
- After this fix, the fast path remains a genuine optimization (it still skips recompute when the old forest is a valid DFS forest of the new graph), so the "avoid full recompute" research goal is unaffected.
