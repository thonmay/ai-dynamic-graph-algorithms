## FAILURE_DESCRIPTION
Case: n=2, graph initially empty (both rows all zeros). After `init`, state is
`parent=[None, None]`, `discover=[0, -1]`, `finish=[1, -1]` (vertex 0 reachable,
vertex 1 not). Operation: `insert_edge(graph, (0, 1), state)` — the matrix entry
`graph[0][1]` is already set to 1 in the passed graph.

Expected result: vertex 1 becomes reachable from root 0, e.g.
`parent={0: None, 1: 0}`, `discover={0: 0, 1: 1}`, `finish={1: 2, 0: 3}`.
Actual result returned: `{'parent': [None, None], 'discover': [0, -1], 'finish': [1, -1]}`
— the state is returned completely unchanged; vertex 1 is still marked
unreachable.

## ROOT_CAUSE
In `insert_edge`, the very first guard bails out whenever the target `v` is
currently unreachable:

```python
    # v unreachable: no effect
    if discover[v] == -1:
        return state
```

This is wrong for insertions. Inserting edge `u -> v` with `v` unreachable and
`u` reachable makes `v` (and everything reachable from `v`) newly reachable,
so the forest must be extended. The guard is only valid for *deletions* (where
an unreachable target is genuinely unaffected). In the failing case,
`discover[1] == -1`, so `insert_edge` returns the old state without ever
searching from `v`, and the verifier sees vertex 1 as unreachable even though
`graph[0][1] == 1`.

Note the second guard (`discover[u] < discover[v] and finish[v] < finish[u]`)
is also vacuously true when `discover[v] == -1` (since `finish[v] == -1 <
finish[u]`), so even removing the first guard would still misclassify the
unreachable case as "v is a descendant of u". The unreachable case must be
handled explicitly and first.

## REPAIR_HINTS
In `insert_edge`, replace the `if discover[v] == -1: return state` guard with
an explicit branch:

- If `discover[v] == -1` and `discover[u] == -1`: no effect (u unreachable, so
  v stays unreachable) — return state.
- If `discover[v] == -1` and `discover[u] != -1`: the new edge makes `v`
  reachable. Run `_dfs_from(v, graph, n, start_time, allowed)` where
  `start_time = finish[u]` (or simply the current max finish + 1, i.e. the
  next free counter value) and `allowed = {w for w in range(n) if
  discover[w] == -1}` (only previously-unreachable vertices may be newly
  discovered; already-reachable vertices keep their times). Set
  `parent[v] = u` and merge the returned parent/discover/finish into the
  state lists. Do NOT renumber existing vertices — appending after the last
  finish time keeps all existing intervals valid.

Also make sure the "v is a descendant of u" guard is only evaluated when
`discover[v] != -1` (or add `discover[v] != -1 and` to its condition), since
with `discover[v] == -1` the descendant test `finish[v] < finish[u]` is
vacuously true and would wrongly short-circuit.

Approaches that will NOT work:
- Simply deleting the `discover[v] == -1` guard: the descendant check
  `discover[u] < discover[v] and finish[v] < finish[u]` evaluates to
  `0 < -1 and ...` = False here, but for other orderings (e.g. u discovered
  later) it can misfire; more importantly, the forward-cross re-search branch
  uses `allowed = {w : discover[w] >= discover[u]}`, which excludes
  unreachable vertices entirely, so v would still never be discovered.
- Reusing the existing forward-cross re-search (re-DFS from u over
  `discover >= discover[u]`) for the unreachable-v case: `allowed` excludes
  v, so the new edge is never traversed.

The deletion path's `discover[v] == -1` guard is correct as-is and should be
left alone.
