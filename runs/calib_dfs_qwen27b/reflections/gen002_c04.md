## FAILURE_DESCRIPTION
Failing case: `{"graph_n": 2, "sequence_idx": 0, "operation": "crash", "error": "0"}`.
The harness crashed with error code "0" (an uncaught Python exception) at the very first operation of the sequence (index 0), on a 2-vertex graph. No expected-vs-actual result was produced; the candidate raised an exception instead of returning a state dict.

## ROOT_CAUSE
The crash is in `insert_edge`, in the "v unreachable, u reachable" branch:

```python
start_time = max(finish) + 1
```

`finish` is the full length-n list of finish times, and every unreachable vertex has `finish[w] == -1`. `max(finish)` therefore returns `-1` whenever ANY vertex is unreachable — which is exactly the precondition of this branch (`discover[v] == -1`). So `start_time = 0`, and the extension DFS from `v` is started at time 0, colliding with the root's existing `discover[0] = 0`.

Tracing the minimal failing instance (n=2, graph `[[0,0],[0,0]]`, insert edge `(0,1)`):
- `init` gives `parent=[None,None]`, `discover=[0,-1]`, `finish=[2,-1]`.
- `insert_edge((0,1))`: `discover[1] == -1`, `discover[0] == 0` → extension branch.
- `start_time = max([2,-1]) + 1 = 0`.
- `_dfs_from(1, graph, 2, 0, {1})` returns `discover={1:0}`, `finish={1:1}`.
- Merge: `discover[1]=0`, `finish[1]=1`, then `parent[1]=0`.
- `_renumber`: `reachable = [0,1]` sorted by discover → `[0,1]` (stable tie). `new_disc={0:0,1:1}`. Post-order: `new_fin[1]=1`, `new_fin[0]=2`.
- Result: `parent=[None,0]`, `discover=[0,1]`, `finish=[2,1]`.

This state is invalid: `finish[1] (1) < finish[0] (2)` while `parent[1]=0` (1 is a tree child of 0), and `discover[1] (1) < finish[1] (1)` is false — the child's finish is not after its own discover. The verifier's stricter replay check (applied because 'finish' is present) then fails, and the harness reports the failure as a crash with error "0".

The same latent bug exists in `delete_edge`'s renumber path only indirectly: `_renumber` itself is fine, but any state that reaches it with a corrupted finish ordering (as produced above) stays corrupted. The primary defect is the `max(finish)` line.

## REPAIR_HINTS
1. In `insert_edge`, replace
   ```python
   start_time = max(finish) + 1
   ```
   with a max over reachable vertices only:
   ```python
   start_time = max(f for f in finish if f != -1) + 1
   ```
   (or equivalently `max(finish[w] for w in range(n) if discover[w] != -1) + 1`). This makes the extension start strictly after the last existing finish time, so the new discover/finish times do not collide with the old ones and the subsequent `_renumber` sees a consistent ordering.

2. Note that after this fix the extension branch is actually redundant with the renumber: since `_renumber` renumbers the whole reachable set from scratch (preserving parent pointers and discover order), the `start_time` value only needs to be large enough that the new vertices sort after the old ones in `_renumber`'s `reachable.sort(key=lambda v: discover[v])`. Any value greater than the max old discover time works; `max(finish of reachable) + 1` is the natural choice.

3. Do NOT "fix" this by dropping the renumber or by special-casing n=2; the collision is structural (unreachable vertices' -1 finish times poison `max(finish)`), and it will recur on any graph with an unreachable vertex plus an insertion that makes it reachable.

4. Also double-check the forward-cross insertion branch: it claims "the vertex set is unchanged, so the numbering stays contiguous" and skips renumbering. That is only true if the re-search from `u` over `allowed = {w : discover[w] >= discover[u]}` visits exactly the old suffix set. Adding an edge cannot make a previously-reachable vertex unreachable, so the set is indeed unchanged — this branch is fine as-is, but it is worth a test case (e.g., n=3, edges 0->1, 0->2, then insert 1->2) to confirm the merged state passes the verifier.

5. The `delete_edge` branch's renumber is correct in isolation; no change needed there beyond what fix #1 implies (it never calls `max(finish)`).
