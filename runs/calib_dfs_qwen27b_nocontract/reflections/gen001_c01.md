## FAILURE_DESCRIPTION

Failing case: n=2, graph [[0,1],[1,0]] (edges 0->1 and 1->0), 20-operation
sequence alternating insert/delete of (0,1) and (1,0). The verifier reported a
timeout: no result within 3s, i.e. an infinite loop in `init` or one of the
updates.

Tracing the sequence:
- init: DFS from 0 gives parent=[-1,0], disc=[1,2], fin=[4,3], time=4.
- op 0 `delete (0,1)`: parent[1]==0, so the deletion path runs.
  `_affected_set(1, ...)`: `_subtree(1)` = {1}; BFS from 1 follows the
  **still-present** edge 1->0 (the matrix is only flipped by the harness
  *after* `delete_edge` returns), so affected = {1, 0}.
  `entries = [w for w in affected if graph[u][w] == 1]` with u=0:
  graph[0][1] is still 1 (not yet flipped), so entries = [1].
  Both vertices are cleared (disc=0, parent=-1), then
  `_dfs_from(1, graph, state, affected)` is called with parent[1]=0 preset.
  Inside `_dfs_from`, the first line after the stack setup is
  `parent[start] = -1`, which overwrites the preset parent[1]=0.
  The DFS from 1 visits 1 (disc=5), then 0 via edge 1->0 (disc=6,
  parent[0]=1), then finishes. Result: parent=[1, -1], disc=[6,5],
  fin=[8,7], time=8.

  **The state is now corrupt**: vertex 0 (the root) has parent 1, and vertex 1
  has parent -1. The forest no longer spans the reachable set from root 0.

- op 1 `insert (0,1)`: disc[1]=5 > 0, so it returns immediately. The corrupt
  state persists.
- op 2 `delete (0,1)`: parent[1] == -1 != 0, so it returns immediately.
- op 3 `insert (0,1)`: disc[1] > 0, no-op.
- op 4 `delete (1,0)`: parent[0] == 1, so the deletion path runs with u=1,
  v=0. `_affected_set(0)`: `_subtree(0)` = {0, 1} (parent[1] == -1? no —
  parent[1] = -1, so `_subtree(0)` = {0} only... wait, parent[1] = -1, so
  1 is NOT a child of 0. `_subtree(0)` = {0}. BFS from 0: graph[0][1] is 1
  (edge 0->1 was re-inserted at op 3), disc[1] > 0, so affected = {0, 1}.
  entries = [w for w in affected if graph[1][w] == 1]: graph[1][0] is still 1
  (not yet flipped), so entries = [0].
  Both cleared, then `_dfs_from(0, graph, state, affected)` with parent[0]=1
  preset, immediately overwritten to parent[0]=-1.
  DFS from 0: visits 0 (disc=9), then 1 via 0->1 (disc=10, parent[1]=0),
  then 1's edge 1->0: 0 is in affected but disc[0] > 0 already, so it's
  skipped (the `i in allowed` check passes but disc[i] is already set —
  actually the code does NOT check disc[i] == 0 before visiting! It checks
  `graph[v][i] and i in allowed` only).

  **This is the infinite loop**: in `_dfs_from`, when processing vertex 1,
  it finds edge 1->0, and 0 is in `allowed` (affected = {0,1}), so it
  "discovers" 0 again: disc[0] = 11, parent[0] = 1, pushes (0, 0) onto the
  stack. Then from 0 it finds edge 0->1, 1 is in allowed, "discovers" 1
  again: disc[1] = 12, parent[1] = 0, pushes (1, 0). This cycles forever:
  0 -> 1 -> 0 -> 1 -> ... with the clock incrementing each time. The stack
  grows unboundedly and the loop never terminates.

Expected: the algorithm should complete all 20 operations and maintain a valid
DFS forest. Actual: infinite loop at op 4 (`delete (1,0)`), hanging forever.

## ROOT_CAUSE

Two compounding bugs:

1. **`_dfs_from` does not check whether a vertex is already discovered
   before visiting it.** The inner loop condition is
   `if graph[v][i] and i in allowed:` — it never checks `disc[i] == 0`.
   In a normal DFS this is fine because `allowed` is restricted to
   undiscovered vertices (insertion case) or the affected set is cleared
   before re-DFS (deletion case). But in the deletion case, the affected
   set can contain vertices that are *re-discovered* during the re-DFS
   (e.g., vertex 0 is in affected, gets discovered first, then reached
   again via a back edge from 1). The code re-discovers already-discovered
   vertices, creating a cycle in the DFS stack: 0 -> 1 -> 0 -> 1 -> ...
   forever.

   The responsible lines in `_dfs_from`:
   ```python
   while i < n:
       if graph[v][i] and i in allowed:   # <-- missing: and disc[i] == 0
           stack[-1] = (v, i + 1)
           disc[i] = t + 1
           t += 1
           parent[i] = v
           stack.append((i, 0))
   ```

2. **`_affected_set` includes vertices reachable from the old subtree via
   edges that are still present in the graph at the time of the call.**
   Since the harness flips the matrix entry *after* `delete_edge` returns,
   the deleted edge (u, v) is still in the graph when `_affected_set` runs.
   This means the affected set can include the parent u (via a back edge
   from the subtree to u), which is wrong: u is still reachable from the
   root via the tree path and should not be cleared. In the failing case,
   `_affected_set(1)` includes vertex 0 because edge 1->0 is still present,
   so vertex 0 gets cleared and re-discovered with parent 1, corrupting the
   root.

   The responsible lines in `_affected_set`:
   ```python
   for y in range(n):
       if row[y] and disc[y] > 0 and y not in affected:
           affected.add(y)
           queue.append(y)
   ```
   This follows ALL edges from the subtree, including edges to ancestors
   (back edges) and the still-present deleted edge. It should only follow
   edges to vertices that are NOT ancestors of the subtree root (i.e., not
   on the path from root to the subtree root), or equivalently, it should
   exclude the parent u and all its ancestors from the affected set.

The combination: bug 2 causes the root (or an ancestor) to be included in
the affected set and cleared. Bug 1 then causes the re-DFS to re-discover
the already-discovered ancestor via a back edge, creating an infinite
cycle in the DFS stack.

## REPAIR_HINTS

**Fix 1 (critical, stops the infinite loop):** In `_dfs_from`, add a check
that the target vertex is not already discovered before visiting it:
```python
if graph[v][i] and i in allowed and disc[i] == 0:
```
This is the standard DFS "gray/white" check. Without it, any back edge or
forward edge to an already-discovered vertex in `allowed` causes re-discovery
and potential infinite cycling. This alone fixes the hang.

**Fix 2 (correctness, prevents corrupting the root/ancestors):** In
`_affected_set`, exclude the parent u and all its ancestors from the
affected set. The affected set should only contain vertices that may lose
reachability, which are the subtree of v and vertices reachable from that
subtree via edges to *non-ancestor* discovered vertices. Concretely, before
the BFS, compute the set of ancestors of v (walk parent pointers from v up
to the root) and skip any y that is an ancestor:
```python
ancestors = set()
a = v
while a != -1:
    ancestors.add(a)
    a = parent[a]
# in the BFS loop:
if row[y] and disc[y] > 0 and y not in affected and y not in ancestors:
```
This prevents the root and its ancestors from being cleared and
re-discovered with wrong parents.

**Fix 3 (correctness, entry-point logic):** The `entries` computation
`[w for w in affected if graph[u][w] == 1]` is also flawed: it includes
vertices that are reachable from u via *any* edge, not just tree edges.
After the fix in Fix 2, the affected set won't include u's ancestors, but
it can still include vertices that u reaches via non-tree edges. The
correct approach is to re-run DFS from u's *other* children (in old
discovery order) that are in the affected set, plus any vertex in the
affected set that is reachable from u via a non-tree edge. A simpler and
correct approach: after clearing the affected set, re-run DFS from u
itself (with u's disc/fin preserved or recomputed) over the affected set
plus u, so that u's adjacency scan naturally discovers the correct
children. Alternatively, re-run DFS from each of u's children (in old
discovery order) that are in the affected set, and also from any affected
vertex w where graph[u][w] == 1 and w is not a child of u (non-tree edge
from u).

**Approaches that will NOT work:**
- Simply checking `disc[i] == 0` in `_dfs_from` (Fix 1) without Fix 2:
  this stops the infinite loop but the state is still corrupt (root has
  wrong parent, some vertices are undiscovered but should be reachable).
  The verifier will reject the forest.
- Recomputing the entire DFS from scratch on every update: this is correct
  but defeats the purpose of the dynamic algorithm and will likely time out
  on larger graphs.
- Excluding only the direct parent u from the affected set (without
  excluding all ancestors): a back edge from the subtree to a grandparent
  would still cause the grandparent to be cleared and re-discovered.
