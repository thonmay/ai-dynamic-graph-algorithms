## FAILURE_DESCRIPTION
Failing case is the very first operation, `init`, on a 2-vertex directed graph
with adjacency matrix `[[0, 0], [1, 0]]` (only edge 1→0; vertex 1 is
unreachable from root 0).

- Expected (verifier): `parent = {0: None, 1: None}`, `discover = {0: 0}`,
  `finish = {0: 1}` — i.e. only vertex 0 is discovered; vertex 1 is
  undiscovered and must be absent from the discover/finish maps.
- Actual (candidate): `result = [[-1, -1], [0, 0], [1, 0], [0]]`, i.e.
  `parent = [-1, -1]`, `disc = [0, 0]`, `fin = [1, 0]`, `order = [0]`.
  The verifier reads `disc[1] = 0` and `fin[1] = 0` as "vertex 1 discovered
  at time 0, finished at time 0" — a bogus second vertex in the forest,
  which also collides with vertex 0's discovery time.

## ROOT_CAUSE
The state uses `disc[v] = 0` as the sentinel for "undiscovered" (see the
docstring: "disc[v]: 0-based discovery time (index in `order`), 0 if
undiscovered"), but vertex 0 — the root — is legitimately discovered at
time 0. The sentinel is therefore ambiguous: after `init`, `disc = [0, 0]`
and the verifier cannot distinguish "vertex 1 undiscovered" from "vertex 1
discovered at time 0".

The divergence happens in `init` → `_dfs_from(graph, 0, ...)`:
```python
disc[start] = len(order)   # disc[0] = 0, indistinguishable from the sentinel
```
and the initialisation
```python
disc = [0] * n
```
leaves `disc[1] = 0` for the unreachable vertex 1. The candidate's own
internal logic is self-consistent (it only ever checks `parent[v] != -1`
for reachability, so it never misreads its own state), but the *encoded*
state is not decodable by the verifier: any graph where the root is
discovered at time 0 (i.e. every non-empty graph) makes the sentinel
collide. This is a state-encoding bug, not a search-order bug — the DFS
itself (order `[0]`, `fin[0] = 1`) is correct.

## REPAIR_HINTS
Smallest fix: change the sentinel so it cannot collide with a real
discovery time.

1. Use `disc[v] = -1` (and `fin[v] = -1`) for undiscovered vertices:
   - in `init`: `disc = [-1] * n`, `fin = [-1] * n`;
   - in `_clear_subtree`: set `disc[v] = -1; fin[v] = -1` instead of `0`.
   Everything else stays the same: `_is_ancestor` comparisons still work
   (only called on discovered vertices), and `parent[v] == -1` remains the
   reachability test.
2. Alternatively, keep 0-based times but make the verifier-facing encoding
   explicit: store `disc[v] = -1` for undiscovered and only emit
   `disc[v] + 1` / `fin[v] + 1` in the returned state. Option 1 is simpler
   and touches fewer lines.

Do NOT try to "fix" this by special-casing vertex 0 or by reordering the
search — the DFS order is already correct; the problem is purely that the
undiscovered sentinel equals a valid discovery time.

Note for later updates (not the failing case, but the same encoding issue
applies): after the sentinel fix, re-check `_clear_subtree` and
`_dfs_from` — they already treat `parent == -1` as the reachability
predicate, so they are compatible with either sentinel choice.
