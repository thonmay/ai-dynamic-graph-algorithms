## FAILURE_DESCRIPTION

Operation: `init` on a 3-vertex graph (sequence_idx 0, no prior updates).
Expected ordering: `[0, 1, 2]` (the only valid LexBFS ordering for this graph).
Actual ordering: `[2, 0, 0]` — not even a permutation (vertex 0 appears twice,
vertex 1 is missing). The state is corrupt before any dynamic update runs.

The expected ordering `[0,1,2]` is the unique valid LexBFS ordering for the
path 0-1-2 (edges {01, 12}). In that graph, vertex 2 has exactly one
neighbor (1), so it cannot be the start of a LexBFS ordering (a start vertex
must have a non-neighbor to split the initial buckets). Hence the graph is
the path 0-1-2, and the static `_lexbfs` produced garbage on it.

## ROOT_CAUSE

The bug is in `_lexbfs`'s "pick next vertex" rule, which is not the
Habib-McConnell-Paul-Viennot rule. The code picks:

```python
chosen = None
for bi, b in enumerate(buckets):
    if len(b) > 1:
        chosen = b[0]
        break
if chosen is None:
    for b in buckets:
        if b:
            chosen = b[0]
            break
```

i.e. "first bucket with >1 vertices, else first non-empty bucket". The
correct rule is: pick the first bucket (in bucket order) that contains a
vertex with at least one non-neighbor among the not-yet-ordered vertices
(the "frontier" rule; equivalently, the first bucket whose vertices are not
all adjacent to every already-ordered vertex).

Trace on the path 0-1-2 (adj: 01, 12):
- s=0: buckets [[0],[1],[2]] (0 adjacent to 1, not 2). The buggy rule picks
  the first bucket with >1 vertices — none exists — so it falls back to the
  first non-empty bucket and picks 0. Correct.
- s=1: split by adjacency to 1: [1],[2],[0] (1 adj 0,2; 2 adj 1 not 0; 0
  adj 1 not 2). Buggy rule: no bucket has >1, picks first non-empty = 1.
  Correct.
- s=2: split by adjacency to 2: [2],[0],[1] (2 adj 1 not 0; 0 not adj 2; 1
  adj 2). Buggy rule: no bucket has >1, picks first non-empty = 2.
  **Wrong**: 2 is adjacent to every already-ordered vertex {0,1}, so it has
  no non-neighbor left to split; the correct rule skips it and picks 0.

Picking 2 as the last vertex leaves `pos[2]` at its stale value 0 from the
s=1 recompute (the "remove chosen" bookkeeping only decrements positions of
vertices *after* the chosen one, so pos[2]=0 is never updated). At the end:

```python
ordering = [0] * n
for v in range(n):
    ordering[pos[v]] = v
```

gives pos = [1, 2, 0] → ordering[1]=0, ordering[2]=0, ordering[0]=2 →
`[2, 0, 0]`, exactly the observed result.

So the root cause is the wrong vertex-selection rule in `_lexbfs`; the
duplicate/missing entry in the output is a downstream symptom of the stale
`pos` left behind when a vertex is chosen out of bucket order.

## REPAIR_HINTS

Fix the selection rule in `_lexbfs` (the `chosen = None` block). Replace it
with the standard LexBFS rule: scan buckets in order and pick the first
vertex v in the first bucket that has at least one non-neighbor among the
not-yet-ordered vertices (i.e. some w not yet ordered with `w not in
nbrs[v]`). Concretely, maintain the set of not-yet-ordered vertices and
test `any(w not in nbrs[v] for w in unvisited)` for each bucket in order.
This makes the algorithm a faithful partition-refinement LexBFS and yields
[0,1,2] on the failing case.

Do NOT try to "fix" the symptom by rebuilding `pos` from the buckets at the
end of the loop instead of trusting the incremental bookkeeping — the
bookkeeping is fine; the selection rule is what's wrong.

Also note for the repair role: the incremental `insert_edge`/`delete_edge`
logic (`_is_violation` / `_is_essential` + move-to-front / recompute) is a
separate, unverified claim and will likely fail on its own cases; but the
immediate blocker is `init`, so fix `_lexbfs` first. A safe fallback for the
dynamic ops is to recompute `_lexbfs` on every update (correctness first,
efficiency later), which removes the risk of the unproven incremental
invariants while the static routine is being fixed.
