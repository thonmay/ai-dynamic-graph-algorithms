## FAILURE_DESCRIPTION

Operation: `init` (sequence_idx 0) on a 3-vertex undirected graph.
The candidate returned ordering `[0, 2, 1]`; the expected (valid) ordering is `[0, 1, 2]`.
The verifier reports a (LB) 4-point violation with a=0, b=2, c=1 (pos_a=0, minD=1e9, i.e. no witness d exists).

Reconstructing the graph from the violation: for the triple (a=0, b=2, c=1) at positions 0<2<1... note the verifier's a<b<c are *positions*, so pos_a=0, and b, c are later positions. The violation means: A[0][2]=0 (ab not in E), A[0][1]=1 (ac in E), and no d before position 0 exists (trivially, since a is first). For `[0,1,2]` to be valid, the same triple (a=0, b=1, c=2) must be fine: either A[0][1]=1 (ab in E, no constraint) — consistent. So the graph is the path 1-0-2: A[0][1]=1, A[0][2]=0, A[1][2]=0 (edges {0-1, 0-2} would make 0-2 an edge; the violation requires A[0][2]=0, so edges are {0-1} only, or {0-1, 1-2}... either way 0 is not adjacent to 2).

In the returned order `[0, 2, 1]`: a=0 (pos 0), b=2 (pos 1), c=1 (pos 2). A[0][2]=0 and A[0][1]=1, and there is no d before position 0 → violation. So `[0,2,1]` is NOT a valid LexBFS ordering of this graph, yet `init` returned it.

## ROOT_CAUSE

The bug is in `_lexbfs`: the label comparison is wrong for LexBFS.

```python
labels = [() for _ in range(n)]
...
for v in remaining:
    if best is None or labels[v] < labels[best]:
        best = v
```

LexBFS requires choosing the vertex whose label is lexicographically **smallest**, where labels are compared as sequences of *positions of already-ordered neighbors*, and the **empty label is the largest** (a vertex with no ordered neighbors is last in the ordering, not first). Standard LexBFS initializes all labels to a sentinel that sorts *after* any non-empty label (e.g. a tuple containing a value larger than any position, or equivalently compares "fewer neighbors = larger").

Here, all labels start as `()`, and Python compares `() < ((0,0),)` as True, so the empty tuple sorts **first**. On the first iteration all labels are `()` and the tie is broken by iteration order of `remaining` (a `set`), picking vertex 0 first — fine. After ordering 0, vertex 1 (adjacent to 0) gets label `((0,0),)` and vertex 2 (not adjacent) keeps `()`. The next pick compares `() < ((0,0),)` → True, so vertex 2 is chosen before vertex 1, producing `[0, 2, 1]`.

That is exactly the wrong direction: LexBFS must pick the vertex with the *most informative* (lexicographically smallest in the "neighbor positions" sense) label, and a vertex with no neighbors yet must come **last** among ties, i.e. the empty label must compare as **larger** than any non-empty label. The code has the comparison inverted relative to LexBFS semantics.

Consequently `_lexbfs` returns an ordering that is not a LexBFS ordering. The self-check in `init` (`if not _is_valid_lexbfs(graph, order): order = _lexbfs(graph)`) is useless because it recomputes with the same broken function.

Note: `_is_valid_lexbfs` itself is correct (it correctly detects the violation), so the certification logic is fine — the defect is purely in the static construction.

## REPAIR_HINTS

Fix the label ordering in `_lexbfs` so that the empty label sorts **after** any non-empty label, and non-empty labels compare lexicographically by the positions of ordered neighbors (smaller position = earlier in the label = "better").

Concrete minimal change: represent labels so that "no ordered neighbors" is the maximum. Two clean options:

1. Initialize `labels = [(n,) for _ in range(n)]` (a sentinel tuple whose first element `n` is larger than any real position) and append `(pos, best)` as now; then `labels[v] < labels[best]` picks the lexicographically smallest, and the sentinel `(n,)` correctly sorts after any real label like `(0, 0)`. Note `(n,) < (n, x)` is False and `(0,0) < (n,)` is True, so this works.

2. Alternatively, keep `()` but invert the comparison: pick `best` where `labels[v] > labels[best]` is False... i.e. pick the lexicographically **largest** label with `()` as the smallest — but this inverts the neighbor-position comparison too, so option 1 is cleaner and less error-prone.

Also: the `init` self-check that recomputes with the same `_lexbfs` is a no-op; after fixing `_lexbfs` it can stay (harmless) or be removed. The `_local_repair`/fallback logic is sound *given* a correct `_lexbfs`, since it always falls back to `_lexbfs` and certifies with the correct `_is_valid_lexbfs`.

Approaches that will NOT work:
- Just changing the tie-break in the `set` iteration — the empty-label ordering is the fundamental error, not the tie-break.
- Relying on the `init` self-check to catch the bad ordering — it recomputes with the same broken `_lexbfs`, so it can never fix itself.
