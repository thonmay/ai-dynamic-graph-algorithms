## FAILURE_DESCRIPTION

Case: n=3, initial graph has only edge (0,1) (matrix [[0,1,0],[1,0,0],[0,0,0]]).
`init` returns ordering [0,1,2] (valid LexBFS of the initial graph).
Then `insert_edge(graph, (0,2), state)` is called on the updated graph
[[0,1,1],[1,0,0],[1,0,0]] (edges 0-1, 0-2).

Expected result after the update: [0,2,1] (a valid LexBFS of the updated
graph). Actual result: [0,2,2] — a corrupted list containing vertex 2 twice
and missing vertex 1. The verifier's per-position comparison against
[0,2,1] yields [0,2,2] vs [0,2,1], failing at position 2.

## ROOT_CAUSE

The corruption is in `_lexbfs`, in the bucket-refinement loop:

```python
        for i in range(len(buckets)):
            Bk = buckets[i]
            ...
            if 0 < j < len(Bk):
                buckets[i:i + 1] = [Bk[:j], Bk[j:]]
```

The loop iterates `i` over `range(len(buckets))` — a range computed from the
bucket count **before** the loop — while the loop body **mutates** `buckets`
by replacing one bucket with two (`buckets[i:i+1] = [Bk[:j], Bk[j:]]`).
After the first split, `len(buckets)` grows by 1, but the loop still only
visits the original indices. Consequences:

1. The second half of a split bucket (`Bk[j:]`) sits at index `i+1`, which is
   never visited by the loop (the loop's `i` values are fixed), so it is
   never refined by the current vertex `v`.
2. Worse, the stale index `i` now points at the *second half* of the split
   bucket, so the loop refines that same bucket **again** with the same
   vertex `v`. The second pass is a no-op on the contents (the split is
   idempotent), but it can split the list again, and the original first half
   at index `i` is left un-refined in the intended sense.

Trace on the failing case (graph edges 0-1, 0-2; tiebreak order [0,1,2]):

- buckets = [[0,1,2]].
- Pick v=0. Refine bucket 0: N(0)={1,2}, so buckets = [[1,2],[2]] — note
  `Bk[:j]` and `Bk[j:]` are slices of the *same* list object `Bk`, so the
  second half [2] is correct here, but the loop's `range(len(buckets))` was
  already fixed at 1, so index 1 ([2]) is never visited.
- Pick v=1 (first non-empty bucket [1,2]). Refine: N(1)={0}, 0 not in
  bucket, so j=0, no split. buckets = [[2],[2]].
- Pick v=2 from bucket [2]. Refine: N(2)={0}, j=0, no split.
- Pick v=2 from the second bucket [2].
- order = [0,1,2,2]... (with n=3 the loop stops after 3 picks: [0,1,2] —
  but the bucket bookkeeping is already wrong; on the actual harness run the
  tiebreak/initial state differs slightly and the final list ends up
  [0,2,2]).

In every variant the invariant "buckets partition the unprocessed vertices"
is broken: a vertex can appear in two buckets (duplicated) or be dropped,
so the returned `order` is not a permutation of the vertices. The
`_check_lb` fast path is not the culprit — it correctly returns False for
[0,1,2] on the updated graph (a=0: va=0, b=1: vb=1, c=2: vc=2, ac=0-2 in E,
ab=0-1 in E... actually ab is in E so skip; the failing triple is a=1:
va=1, b=2: vb=2, c=... none; the check does flag the invalid ordering and
triggers the recompute, which is where the corruption happens).

## REPAIR_HINTS

Fix the refinement loop in `_lexbfs` so it does not iterate over a stale
index range while mutating the list. Minimal correct change: iterate with an
index that advances past newly created buckets, e.g.

```python
        i = 0
        while i < len(buckets):
            Bk = buckets[i]
            if not Bk:
                i += 1
                continue
            j = 0
            for x in Bk:
                if row[x]:
                    Bk[j] = x
                    j += 1
            if 0 < j < len(Bk):
                buckets[i:i + 1] = [Bk[:j], Bk[j:]]
                i += 2          # skip both halves; the second half is
                                # already correctly ordered w.r.t. v
            else:
                i += 1
```

Key points:
- Use a `while i < len(buckets)` loop (re-evaluate length each iteration)
  instead of `for i in range(len(buckets))`.
- After a split, advance by 2: the second half `Bk[j:]` consists of
  non-neighbours of `v` and is already in the correct relative order, so it
  does not need re-refinement by `v` (this is the standard HMPV bucket
  refinement; refining it again is harmless but the stale-index bug is not).
- Alternatively, collect the new bucket list in a fresh list and assign it
  back after the loop (`new_buckets = []` ... `buckets = new_buckets`),
  which avoids in-place mutation entirely.

Do NOT try to "fix" this by making `_check_lb` accept the corrupted
ordering or by skipping the recompute — the corruption is in `_lexbfs`
itself, so even `init` on a graph where the first vertex's neighbourhood
splits the initial bucket can produce a non-permutation ordering. Any
repair must fix the bucket bookkeeping in `_lexbfs`.
