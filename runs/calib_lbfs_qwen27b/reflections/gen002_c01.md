## FAILURE_DESCRIPTION
Case: n=3, operation `insert (0,2)` at sequence_idx 0. The graph after the update is the path 0–1–2 (edges {0,1},{1,2}); the expected valid LexBFS is [0,2,1]. The candidate returned [0,1,2], which violates the (LB) 4-point property at (a=0, b=1, c=2): ac=(0,2)∈E, ab=(0,1)∉E, and no d<a exists (minD stayed at the sentinel 1e9).

Note: the failure is NOT in the dynamic part. `insert_edge`/`delete_edge` simply call `_lexbfs(graph)` on the current matrix, so the bug is entirely in the static routine `_lexbfs`.

## ROOT_CAUSE
The "frontier" vertex-selection rule in `_lexbfs` is wrong. The code:

```python
for b in buckets:
    for v in b:
        has_nonnbr = False
        for w in unvisited:
            if w not in nbrs[v]:
                has_nonnbr = True
                break
        if has_nonnbr:
            chosen = v
            break
```

picks the first vertex (in bucket order) that has at least one non-neighbor among the not-yet-ordered vertices. In LexBFS the next vertex must be the one whose label (the sequence of 0/1 adjacency bits to previously ordered vertices, in order) is lexicographically maximal — equivalently, the first vertex in the current bucket order, where the buckets are the refinement classes. The "has a non-neighbor" test is a completely different (and wrong) criterion.

Concrete trace on path 0–1–2 (`nbrs = [{1}, {0,2}, {1}]`, initial buckets `[[0],[1],[2]]`):
- s=0: split → `[[1],[0],[2]]`. Frontier rule: bucket [1], v=1 has non-neighbor 2 → chosen=1. ordered=[1].
- s=1: split → `[[0],[2],[1]]`. Frontier rule: bucket [0], v=0 has non-neighbor 2 → chosen=0. ordered=[1,0].
- s=2: split → `[[0],[2],[1]]`. Frontier rule: bucket [0], v=0 has non-neighbor 2 → chosen=0 again. ordered=[1,0,0].

So the routine returns [1,0,0] (a duplicate, missing 2) — it is not even a permutation. The verifier's reported [0,1,2] is the same class of bug (an ordering that is not a valid LexBFS of the graph); the selection rule is the single point of divergence. The fallback `if chosen is None: chosen = b[0]` is also unreachable in practice and masks nothing.

## REPAIR_HINTS
Replace the frontier scan with the correct LexBFS rule: after splitting all buckets by adjacency to the newly ordered vertex s (the split code is already correct — neighbors first, then non-neighbors, preserving order), the next vertex is simply the first vertex of the first non-empty bucket:

```python
chosen = None
for b in buckets:
    if b:
        chosen = b[0]
        break
```

This is the standard partition-refinement LexBFS (Habib–McConnell–Paul–Viennot): the bucket order IS the lexicographic label order, so the head of the first non-empty bucket is the lexicographically maximal label. Then remove `chosen` from its bucket as before.

Verification on path 0–1–2: s=0 → buckets `[[1],[0],[2]]` → pick 1; s=1 → `[[0],[2],[1]]` → pick 0; s=2 → `[[2],[1]]` → pick 2. Ordering [1,0,2], which is a valid LexBFS (labels: 1→"1", 0→"10", 2→"100"; 0 and 2 tie and either order is legal).

Do NOT try to "fix" the dynamic updates to avoid recomputation — the recompute-from-scratch strategy is fine for correctness; the only defect is the static selection rule. Also do not keep the `has_nonnbr` test in any form; it is not a LexBFS criterion.
