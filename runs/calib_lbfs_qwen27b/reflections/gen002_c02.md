## FAILURE_DESCRIPTION

Failing case: n=4, operation `insert (3, 2)` at sequence_idx 0. The candidate returned ordering `[0, 1, 2, 3]`, but the verifier reports a (LB) 4-point violation with `a=1, b=2, c=3, pos_a=1, minD=1000000000` (i.e. no witness d exists). The expected valid ordering was `[0, 1, 3, 2]`.

Reconstructing the graph: the violation requires, in the returned order `[0,1,2,3]`, that A[1][2]=0, A[1][3]=1, and no d in {0} satisfies A[d][2]=1 and A[d][3]=0 — so A[0][2]=0. The expected order `[0,1,3,2]` is valid, which forces A[0][1]=1, A[0][3]=1, A[1][3]=1, A[0][2]=0, A[1][2]=0. The inserted edge is (3,2), so before the update A[3][2]=0 and after A[3][2]=1. The post-update graph is:

```
A = [[0,1,0,1],
     [1,0,0,1],
     [0,0,0,1],
     [1,1,1,0]]
```

i.e. triangle {0,1,3} plus vertex 2 attached only to 3.

## ROOT_CAUSE

The bug is in the static fallback `_lexbfs_valid` (lines ~50-75), which is the function that must guarantee correctness when `_local_repair` returns None (which it does here: the current order is invalid, and none of the swap/adjacent-move candidates are valid).

`_lexbfs_valid` builds the initial buckets as:

```python
buckets = [[start]] + [[v] for v in range(n) if v != start]
```

This makes the initial partition **n singleton buckets** (start first, then every other vertex in id order). In a correct partition-refinement LexBFS, the initial partition is a **single bucket containing all remaining vertices** (all labels are the empty label, so all vertices are tied and the first vertex of that bucket is taken). With singleton buckets, the algorithm never breaks ties by adjacency: at each step it simply pops the first vertex of the first bucket, and the refinement of the other singleton buckets is a no-op (a singleton splits into at most one non-empty part). The result is therefore just `[start, start+1, ..., n-1, 0, ..., start-1]` — a rotation of the id order — regardless of the graph.

Tracing start=0 on the graph above: buckets `[[0],[1],[2],[3]]` → order `[0,1,2,3]`. This is exactly the invalid ordering returned. The same rotation is produced for every start (start=1 → `[1,2,3,0]`, start=2 → `[2,3,0,1]`, start=3 → `[3,0,1,2]`), and **none of them is a valid LexBFS ordering of this graph** (the only valid orderings are `[0,1,3,2]` and `[1,0,3,2]`). So the multi-start "defensive net" never finds a valid order, and the code falls through to the final line:

```python
return _lexbfs(A)
```

`_lexbfs` (the correct single-bucket implementation) would return `[0,1,3,2]` — a valid order — but the code never reaches it because the loop's `if _is_valid_lexbfs(A, order): return order` never fires. The returned `[0,1,2,3]` is the invalid start=0 rotation.

Note the contrast: `_lexbfs` (lines ~20-45) initializes `buckets = [list(range(n))]` (one bucket, correct) and is itself a valid LexBFS implementation. The bug is confined to `_lexbfs_valid`'s singleton-bucket initialization.

## REPAIR_HINTS

Smallest fix: in `_lexbfs_valid`, replace the singleton initialization

```python
buckets = [[start]] + [[v] for v in range(n) if v != start]
```

with a single bucket whose first element is `start`:

```python
rest = [v for v in range(n) if v != start]
buckets = [[start] + rest]
```

This makes each start's run a genuine partition-refinement LexBFS (start fixed as the first vertex, all other vertices tied in one bucket), and the multi-start loop then returns a valid order on the first iteration (start=0 → `[0,1,3,2]`).

Even simpler and sufficient: since `_lexbfs` is already a correct static LexBFS, `init` and the fallback in `insert_edge`/`delete_edge` can just call `_lexbfs(graph)` directly; `_lexbfs_valid` can be deleted. (Any valid LexBFS is acceptable per the state contract, so the multi-start search buys nothing once the construction is correct.)

Approaches that will NOT work:
- Keeping the singleton-bucket initialization and relying on the multi-start loop: as traced, every start yields a rotation of the id order, and for this graph no rotation is valid, so the loop always falls through to the final `return _lexbfs(A)` — the "defensive net" is dead code and the returned order is the invalid start=0 rotation.
- "Fixing" the problem by making `_local_repair` try more permutations: the repair is only ever consulted before the fallback, and the fallback itself is broken; the returned state comes from `_lexbfs_valid`, not from the repair.
