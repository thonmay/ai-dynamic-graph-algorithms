## FAILURE_DESCRIPTION

Case: n=3. After `init` on the initial graph, `insert_edge(graph, (0,2), state)`
is called on the updated graph. The verifier reports:

- expected: [0, 2, 1]
- actual:   [0, 2, 2]

The actual ordering is not even a permutation of {0,1,2}: vertex 2 appears
twice and vertex 1 is missing. So the returned state is invalid on its face.

The updated graph must contain edge (0,2) (just inserted) and, for the
expected answer [0,2,1] to be the canonical LexBFS, edge (0,1) must NOT be
present (otherwise 1 would precede 2 in any LexBFS starting at 0). The
initial graph is therefore most plausibly the empty 3-vertex graph
([[0,0,0],[0,0,0],[0,0,0]]), with `init` returning [0,1,2] (the default
rank order), and the update producing the single-edge graph 0-2.

## ROOT_CAUSE

The bug is in the bucket-refinement loop of `_lexbfs` (the recompute path
taken when `_check_lb` fails). The responsible lines:

```python
            j = 0
            for x in Bk:
                if row[x]:
                    Bk[j] = x
                    j += 1
            if 0 < j < len(Bk):
                buckets[i:i + 1] = [Bk[:j], Bk[j:]]
```

The in-place compaction `Bk[j] = x` writes into the very list it is
iterating over. This is only safe when the write pointer never lags behind
the read pointer, i.e. when the first element of the bucket is a neighbor
of v. When the first element is NOT a neighbor, the write lags and
clobbers not-yet-read elements, destroying the invariant "buckets form a
partition of the unprocessed vertices". Downstream picks then operate on a
corrupted multiset, so the final `order` is not a permutation (here:
[0,2,2]).

Exact trace on the failing case (initial graph empty; after insert, graph
has only edge 0-2; `_check_lb` rejects the old order [0,1,2] because
a=0 (v=0), b=1 (v=1), c=2 (v=2): 0-2 in E, 0-1 not in E, no d < 0):

`_lexbfs(graph, 3, tiebreak=[0,1,2])`, rank 0<1<2, buckets = [[0,1,2]]:

1. Pick v=0 (B=[0,1,2] -> [1,2]). Refine [1,2] with row of 0 = [0,0,1]:
   - x=1, row[1]=0: no write, j=0.
   - x=2, row[2]=1: **Bk[0] = 2** (clobber: overwrites the 1 that was
     already read, but the damage is that the list is now [2,2]). j=1.
   - 0 < j=1 < len=2: split into [Bk[:1], Bk[1:]] = [[2], [2]].
   - buckets = [[2], [2]] — vertex 1 is lost, vertex 2 duplicated.
2. Pick v=2 from first bucket; refine [2] with row of 2 = [1,0,0]:
   x=2, row[2]=0, j=0, no split.
3. Pick v=2 from second bucket; refine [] — nothing.

Final order = [0, 2, 2]. Matches the verifier's actual result exactly.

## REPAIR_HINTS

Smallest fix, in `_lexbfs`: replace the in-place compaction with a
non-destructive partition that preserves rank order in both halves:

```python
            neigh = [x for x in Bk if row[x]]
            non   = [x for x in Bk if not row[x]]
            if neigh and non:
                buckets[i:i + 1] = [neigh, non]
                i += 2
            else:
                i += 1
```

(Equivalently: build `Bk = neigh + non` into a fresh list before any
split.) This keeps the partition invariant intact for all cases, including
buckets whose first element is a non-neighbor.

Notes:
- Do NOT "fix" this by only compacting when `Bk[0]` is a neighbor of v:
  the clobbering corrupts the tail that feeds the `Bk[j:]` half of a split
  (as the trace shows: the stale 2 at index 1 became the second bucket),
  so any conditional in-place compaction is still unsafe.
- `_check_lb` is correct (it properly rejected [0,1,2] on the updated
  graph); the failure is purely in the recompute routine `_lexbfs`.
- After the fix, verify on this case: init on the empty 3-graph gives
  [0,1,2]; insert (0,2) must yield a valid permutation satisfying (LB),
  e.g. [0,2,1].
- The check-then-recompute strategy in `insert_edge`/`delete_edge` is
  sound in principle (any valid LexBFS ordering satisfies (LB), and a
  correct LexBFS recompute always produces a valid ordering), so no change
  to those functions is needed once `_lexbfs` is fixed.
