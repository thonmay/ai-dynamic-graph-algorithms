## FAILURE_DESCRIPTION
Operation `insert (3, 2)` on a 4-vertex graph. The candidate returned ordering `[0, 1, 2, 3]`, which the verifier rejected with the (LB) 4-point violation at positions a=1, b=2, c=3 (pos_a=1, minD=1000000000 = "no witness d found"). The expected valid ordering was `[0, 1, 3, 2]`.

Reconstructing the graph from the violation: in the returned order, a=1, b=2, c=3, so the violated triple requires A[1][2]=0, A[1][3]=1, and no d in {0} with A[d][2]=1 and A[d][3]=0 (i.e. A[0][2]=0 or A[0][3]=1). The only edge change was (3,2), so before the insert A[3][2]=0 and after A[3][2]=1. A concrete pre-update graph consistent with everything is:
- A[0][1]=1, A[0][2]=0, A[0][3]=1
- A[1][2]=0, A[1][3]=1
- A[2][3]=0
On this graph the pre-update ordering [0,1,2,3] is a valid LexBFS (verified by hand: the only candidate triple is a=1,b=2,c=3 and d=0 witnesses it since A[0][2]=0, A[0][3]=1). After inserting (3,2), the same triple a=1,b=2,c=3 now has A[1][2]=0, A[1][3]=1, but d=0 fails (A[0][2]=0) and there is no other d, so [0,1,2,3] is invalid; [0,1,3,2] is valid.

## ROOT_CAUSE
The failure is in `_local_repair` (lines ~110-145). After the insert, the current order [0,1,2,3] is invalid, so the repair tries a fixed, tiny set of candidates:
1. swap u,v -> [0,1,3,2]  (this IS valid)
2. move u one step left/right
3. move v one step left/right

The swap candidate is checked with `_is_valid_lexbfs(A, cand)`, and if that check returned True the repair would have succeeded. Since the returned result is the un-repaired [0,1,2,3], the only consistent explanation is that `_is_valid_lexbfs` returned False for the valid ordering [0,1,3,2] (and for every other candidate), so `_local_repair` returned None and the fallback `_lexbfs_valid` was invoked. The fallback then also returned [0,1,2,3], which means `_lexbfs_valid`'s per-start validation loop also rejected every candidate it generated (including the correct one) and fell through to the final unvalidated `return _lexbfs(A)`.

So the root cause is a bug in `_is_valid_lexbfs` (lines ~75-95): it is rejecting valid LexBFS orderings. Both the local repair and the multi-start fallback gate on this predicate, so a single false-negative in it defeats the entire "defensive net" design — the fallback is not a guarantee, it inherits the same broken checker.

Tracing the predicate on the valid order [0,1,3,2] with the reconstructed graph: the only triple with a<b<c, ac in E, ab not in E is a=1 (pos 1), b=2 (pos 3), c=3 (pos 2)? No — b must be after a and c after b, so the triple is a=1 (pos1), b=2 (pos3), c=3 (pos2) is impossible since c must be after b. The actual triple is a=1 (pos1), b=3 (pos2), c=2 (pos3): A[1][3]=1 (ab in E) -> skipped. And a=1, b=2, c=3 requires c after b: positions 1,3,2 -> not a<b<c. So for [0,1,3,2] the predicate should find no violating triple and return True — yet the observed behavior implies it returned False. This means the predicate's logic (or the A it sees) is wrong in a way not fully pinned down by the single failing case; the trace is conclusive that `_is_valid_lexbfs` produced a false negative, but the exact line is not identifiable without the full graph matrix.

## REPAIR_HINTS
1. Do not trust `_is_valid_lexbfs` as a gate. The fallback `return _lexbfs(A)` in `_lexbfs_valid` is unvalidated and is what actually produced the wrong answer — remove the "defensive multi-start" pattern entirely: `_lexbfs_valid` should just return `_lexbfs(A)` (or `_lexbfs(A, 0)`), and `init`/fallbacks should use it directly.
2. Fix `_is_valid_lexbfs` itself. Audit it against the (LB) property definition: for all positions i<j<k with A[order[i]][order[k]]==1 and A[order[i]][order[j]]==0, require some t<i with A[order[t]][order[j]]==1 and A[order[t]][order[k]]==0. Write a brute-force reference (e.g. check the ordering against an independent LexBFS label simulation, or enumerate all LexBFS orderings for small n) and fuzz-compare on random 4-6 vertex graphs to find the exact false-negative/false-positive.
3. In `_local_repair`, the candidate set is too small (only single swaps of u/v or their neighbors). Even with a correct validator, many updates need moving u or v by more than one position, or reordering other vertices whose labels changed. If keeping the local-repair idea, at minimum try all positions for u and v (O(n) candidates each), and validate each with the fixed predicate.
4. Approaches that will NOT work: keeping the multi-start "defensive net" in `_lexbfs_valid` — it amplifies the checker bug instead of masking it. Also, relying on the local repair alone without a validated full-recompute fallback is unsound.
5. The simplest correct fix: make the fallback a plain, known-correct static LexBFS (the partition-refinement `_lexbfs` is standard and correct), and use `_is_valid_lexbfs` only as a test oracle in development, not as a runtime gate. If the static `_lexbfs` is correct, then `init` and the fallback are correct regardless of the repair heuristic, and the only remaining question is whether the repair can return an invalid order — which it cannot if it validates with a correct predicate, but the safest design is to validate the repaired order and fall back to the static recompute on any doubt.
