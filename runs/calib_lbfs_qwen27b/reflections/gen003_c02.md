## FAILURE_DESCRIPTION
After `init` on a 4-vertex graph, the operation `insert (3, 2)` was applied. The returned ordering was `[0, 1, 2, 3]`, but the expected (valid) ordering is `[0, 1, 3, 2]`. The verifier reports a (LB) 4-point violation at positions a=1, b=2, c=3 (pos_a=1, minD=1e9 meaning no witness d was found).

## ROOT_CAUSE
The bug is in `_lexbfs` (the static partition-refinement routine). The bucket-sorting line:

```python
new_buckets.sort(key=lambda b: b[0][0])
```

sorts each bucket by the label of its **first** element only. This is only correct if all elements within a bucket share the same label. However, the initial bucket (when `start` is given) is:

```python
buckets = [[((), start)] + [((), v) for v in rest]]
```

All elements start with label `()`, so the first sort is fine. But after the first refinement step, the `b0` bucket (the remainder of the first bucket after popping `start`) is carried over **unrefined** into `new_buckets`. Its elements still have label `()`, while other buckets have been split into `nb` (label extended with `best`) and `nn` (label unchanged). The sort key `b[0][0]` for the carried-over `b0` bucket is `()`, which is lexicographically smaller than any label that has been extended. This is actually correct behavior for the carried-over bucket.

Wait — let me re-trace more carefully. The real issue: when `start=None`, the initial bucket is `[((), 0), ((), 1), ((), 2), ((), 3)]`. First iteration: pop vertex 0, `b0 = [((), 1), ((), 2), ((), 3)]`. No other buckets to refine. `new_buckets = [b0]`. Sort is trivial. Second iteration: pop vertex 1 from `b0`, `b0 = [((), 2), ((), 3)]`. Again no other buckets. This continues — the algorithm degenerates to just popping vertices in order 0,1,2,3 because there's only ever one bucket and it's never refined.

**The actual bug**: when there is only one bucket, the refinement loop `for b in buckets[1:]` iterates over an empty list, so no refinement ever happens. The algorithm just pops vertices in their initial order (0, 1, 2, ..., n-1) without ever splitting by adjacency. This means `_lexbfs(A, start=None)` returns `[0, 1, 2, ..., n-1]` regardless of the graph structure.

When `start` is given, the same issue occurs: after the first pop, `b0` contains all remaining vertices with label `()`, and since it's the only bucket, it's never refined. The result is `[start, 0, 1, ..., n-1]` (excluding start) — again independent of the graph.

The multi-start `_lexbfs_valid` then checks each of these degenerate orderings with `_is_valid_lexbfs`. For the failing case, after inserting edge (3,2), the graph has edges that make `[0,1,2,3]` invalid (violation at a=1,b=2,c=3). The multi-start loop tries starts 0,1,2,3, producing orderings `[0,1,2,3]`, `[1,0,2,3]`, `[2,0,1,3]`, `[3,0,1,2]` — all of which are also invalid for this graph (or at least the first one tried, start=0, gives `[0,1,2,3]` which fails). If none pass, it falls back to `_lexbfs(A)` (start=None) which gives `[0,1,2,3]` again.

The root cause is that **the partition-refinement loop never refines the bucket that the current vertex was taken from** (it only refines `buckets[1:]`). In the standard LexBFS algorithm, after selecting a vertex from the first bucket, you must refine ALL other buckets — but the "other buckets" should be the remaining buckets after removing the first one. The code does this correctly in principle, but the issue is that when there's only one bucket, there are no "other" buckets to refine, so the algorithm never splits. The correct behavior is: the first bucket's remaining elements should also be refined by the selected vertex's adjacency.

## REPAIR_HINTS
The fix is in `_lexbfs`: after popping the best vertex from `b0`, the remaining elements of `b0` must ALSO be refined by adjacency to `best`, just like all other buckets. Currently:

```python
new_buckets = []
if b0:
    new_buckets.append(b0)  # BUG: b0 is carried over unrefined
for b in buckets[1:]:
    nb = [(lbl + (best,), x) for lbl, x in b if A[x][best]]
    nn = [(lbl, x) for lbl, x in b if not A[x][best]]
    ...
```

The fix: refine `b0` the same way as other buckets:

```python
new_buckets = []
# Refine b0 (remaining elements of the first bucket)
if b0:
    nb = [(lbl + (best,), x) for lbl, x in b0 if A[x][best]]
    nn = [(lbl, x) for lbl, x in b0 if not A[x][best]]
    if nb:
        new_buckets.append(nb)
    if nn:
        new_buckets.append(nn)
# Refine all other buckets
for b in buckets[1:]:
    nb = [(lbl + (best,), x) for lbl, x in b if A[x][best]]
    nn = [(lbl, x) for lbl, x in b if not A[x][best]]
    if nb:
        new_buckets.append(nb)
    if nn:
        new_buckets.append(nn)
```

This ensures the partition is properly refined at every step, which is the core invariant of the LexBFS partition-refinement algorithm. Without this, the algorithm degenerates to a trivial ordering and the multi-start fallback cannot recover a valid LexBFS ordering for arbitrary graphs.

Note: the `_local_repair` and fallback logic are fine in principle — the bug is entirely in the static `_lexbfs` routine that is supposed to produce a valid ordering from scratch.
