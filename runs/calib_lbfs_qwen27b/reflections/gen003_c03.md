## FAILURE_DESCRIPTION

n=3. Pre-update graph is the triangle (edges 0-1, 1-2, 0-2); `init` produced ordering [0,1,2]. Operation: `delete (2,1)`. Post-update graph is the path 0-1-2 (edges 0-1, 0-2 only).

Expected: any valid LexBFS ordering of the path, e.g. [0,1,2] is NOT valid; a valid one is [1,0,2] or [2,0,1] (start at an endpoint). The verifier reports result [1,2,0] (a rotation of the kept order) with violation a=1, b=2, c=0, pos_a=0, minD=1000000000 (no witness d found).

The candidate returned the old order [0,1,2] unchanged because `_is_valid_lexbfs([0,1,2], adj)` returned True on the post-update graph.

## ROOT_CAUSE

`_is_valid_lexbfs` checks only the (LB) 4-point property, which is **necessary but not sufficient** for LexBFS validity. The missing condition is the **LBFS prefix property**: for every position i, N(order[i]) ∩ {order[0..i-1]} must be a *prefix* of the ordering (i.e. if a vertex at position p < i is adjacent to order[i], then every vertex at position q < p must also be adjacent to order[i]).

Trace on the failing case, order [0,1,2], graph with edges {0-1, 0-2}:
- bi=1: b=1, Nb={0}, S = {0} (vertex 0 is before 1 and adjacent).
- ci=2: c=2, Nc={0}. `diff = S & ~Nc = {0} & ~{0} = 0` → `continue`.
- No violation found → returns True.

But the prefix property is violated at position 2: N(2)∩{0,1} = {0}, and 0 is at position 0 while 1 (position 1) is NOT in N(2). So {0} is not a prefix of [0,1,2]. The (LB) 4-point property cannot catch this because it only quantifies over triples with c~b; here c=2 is not adjacent to b=1 (that edge was just deleted), so the triple is vacuous. The verifier's minD=1000000000 confirms no (LB) witness exists — the verifier is checking the prefix property, not (LB).

The responsible lines are the entire body of `_is_valid_lexbfs` (the `for bi in range(1, n-1)` loop), which never checks whether S_b is a prefix of the ordering.

## REPAIR_HINTS

Add the prefix-property check to `_is_valid_lexbfs` (or replace the (LB) check with it, since the prefix property is the actual certificate of LexBFS validity). For each position bi, compute S_b = {a : pos[a] < bi, a~b}. Then check that S_b is a prefix: if S_b is non-empty, let m = max position in S_b; require that every vertex at position p ≤ m is in S_b. In bitset terms: `S == (S | (1 << m)) & ((1 << (m+1)) - 1)` is not quite right; the correct check is `S & ~((1 << (m+1)) - 1) == 0` (no S element beyond m, trivially true) AND `((1 << (m+1)) - 1) & ~S == 0` (no gap: every position ≤ m is in S). Equivalently: `S == (1 << (m+1)) - 1` restricted to positions < bi, i.e. `S == ((1 << bi) - 1) & ((1 << (m+1)) - 1)` — but the simplest is: `S` must equal `(1 << (m+1)) - 1` masked to positions < bi, which reduces to checking `S & ~((1 << (m+1)) - 1) == 0` (always true) and `((1 << (m+1)) - 1) & ~S & ((1 << bi) - 1) == 0` (no gaps).

Concretely, after computing `S` in the `for bi` loop, add:
```python
if S:
    m = S.bit_length() - 1  # max position in S_b
    # every position 0..m must be in S_b
    if S & ((1 << (m + 1)) - 1) != (1 << (m + 1)) - 1:
        return False
```
This is O(n) per b, O(n²) total, and is the correct certificate. The (LB) 4-point check can be kept as an additional check or removed entirely — the prefix property alone is sufficient and necessary for LexBFS validity.

Note: `_rederive`'s prefix-validity check has the same bug (it only checks (LB) triples, not the prefix property), so it would also incorrectly accept invalid prefixes. Fix it the same way: a prefix of length k is a valid LexBFS prefix iff for every position i < k, N(order[i]) ∩ {order[0..i-1]} is a prefix of the ordering.

Approaches that will NOT work:
- Keeping only the (LB) 4-point check: it is strictly weaker than the prefix property and misses exactly the cases where an edge deletion breaks the prefix condition without creating an (LB) violation.
- Checking (LB) + "for each b, S_b is non-empty implies S_b contains position 0": insufficient; the gap can be at any position, not just 0.
