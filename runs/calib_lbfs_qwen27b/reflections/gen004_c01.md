## FAILURE_DESCRIPTION
Operation: `init` on a 3-vertex graph (sequence_idx 0, so no prior updates).
Result: `[0, 1, 2]`. Expected (a valid LexBFS ordering): `[0, 2, 1]`.
The verifier reports an (LB) 4-point violation with a=0, b=1, c=2, pos_a=0,
minD=1000000000 (sentinel = "no witness d exists").

Reconstructing the graph from the violation: in the returned order
[0,1,2], positions a=0<b=1<c=2 mean vertices 0,1,2 in that order, with
0-2 in E, 0-1 not in E, and no earlier vertex d (pos_a=0, so none exists)
with d-1 in E and d-2 not in E. So the graph has edge {0,2} and no edge
{0,1}. The expected valid order [0,2,1] is consistent with the graph
E = {{0,2}, {1,2}} (a path 0-2-1): in [0,2,1] the only triple is
a=0,b=2,c=1 with a-b in E, so no constraint; valid.

So `init` returned an ordering that is NOT a valid LexBFS ordering of the
input graph. The static routine `_lexbfs` itself is broken.

## ROOT_CAUSE
The bug is in `_lexbfs`'s bucket refinement, specifically the label update
for the non-neighbor part:

```python
for b in buckets[1:]:
    nb = [(lbl + (best,), x) for lbl, x in b if A[x][best]]
    nn = [(lbl, x) for lbl, x in b if not A[x][best]]
```

In LexBFS, a vertex's label is the **bit vector over all already-ordered
vertices** (1 = adjacent, 0 = not adjacent). When `best` is ordered, every
remaining vertex's label must be extended by one bit: neighbors get a 1,
**non-neighbors get a 0**. The code appends `best` to the neighbor labels
but leaves the non-neighbor labels **unchanged** (no 0 appended).

Consequence: labels of different lengths are compared lexicographically as
tuples, and a non-neighbor's label is a strict prefix of what it should be.
Trace on E = {{0,2},{1,2}}:
- Initial: one bucket [((),0),((),1),((),2)].
- Order 0. Refine: 1 is a non-neighbor of 0 -> label stays `()`; 2 is a
  neighbor -> label `(0,)`. Buckets: [[((),1)], [( (0,),2)]].
- Sort by label: `()` < `(0,)`, so bucket [1] comes first.
- Order 1, then 2. Result [0,1,2] — exactly the failing output.

Correctly, 1's label should be `(0,)` (0-bit for vertex 0), tying with 2's
label `(0,)`; the tie-break by vertex id then yields [0,2,1].

The same bug also corrupts the `start` branch: `buckets = [[((), start)] +
[((), v) for v in rest]]` puts the start vertex in the same bucket as the
rest, so it is not actually forced first (though `start` is never used by
the current call sites, so the live bug is the label update).

Note the local-repair path is not implicated: `init` calls
`_lexbfs_valid` -> `_lexbfs` directly, and the failure is at sequence_idx 0.

## REPAIR_HINTS
Smallest fix, in `_lexbfs`:
1. Append a 0-bit to non-neighbor labels:
   `nn = [(lbl + (0,), x) for lbl, x in b if not A[x][best]]`
   (and keep `nb = [(lbl + (1,), x) ...]` — using the literal 0/1 bits is
   cleaner than appending `best`, since the label is a bit vector, not a
   list of vertex ids; either works if consistent, but 0/1 is the standard
   formulation and sorts correctly).
2. Fix the `start` branch so the start vertex is ordered first: e.g.
   `order = [start]`, initialize buckets from `rest` only, and run the
   loop for `n-1` steps (or equivalently pre-populate `order` and skip the
   first iteration).

After the fix, verify with the (LB) 4-point checker `_is_valid_lexbfs` on
the failing graph: [0,2,1] must pass and [0,1,2] must fail.

Approaches that will NOT work:
- Sorting buckets by `b[0][0]` is fine once labels are uniform-length bit
  vectors (all remaining vertices share the same label length at each
  step), so do not "fix" this by changing the sort key — the sort is not
  the bug.
- Do not rely on `_is_valid_lexbfs` as a runtime gate to mask the bug;
  the static routine must produce a valid ordering on its own.
- The local-repair heuristics (swap u/v, adjacent moves) are only a
  performance concern and are irrelevant to this init failure; do not
  spend effort there for this case.
