## FAILURE_DESCRIPTION
n=3. Initial graph: only edge (0,1) (path 2-0-1). `init` returns [0,1,2] (valid: 0,1 adjacent; 2 isolated, last).
Update: insert edge (0,2). New graph: edges (0,1),(0,2) — a star centered at 0.
Expected: [0,2,1] (the only valid LexBFS orderings are [0,1,2] and [0,2,1] with 0 first; the verifier's checker rejects [0,1,2]).
Actual: [0,1,2] — the old ordering was kept unchanged.
Violation reported: a=0 (pos 0), b=1 (pos 1), c=2 (pos 2), minD=1e9 (no witness d exists).

## ROOT_CAUSE
The certificate check `_is_valid_lexbfs` is WRONG: it implements a different (stronger) property than the (LB) 4-point property, so it rejects valid LexBFS orderings.

The (LB) property (Corneil–Krueger) is: for all positions a < b < c with ac in E and ab not in E, there exists d < a with db in E and dc not in E. The witness d must be strictly BEFORE a.

The code instead does (in `_is_valid_lexbfs`, and identically in the prefix loop of `_rederive`):
```
# find a: pos < bi, a in Nc, a not in Nb
a0 = None
for ai in range(bi):
    ...
    a0 = ai
    break
...
# need d < a0 with d in Nb and d not in Nc
for di in range(a0):
```
i.e. it picks the FIRST (earliest) a in A = {a < b : a~c, a not~ b} and requires a witness d strictly before that earliest a. The correct property requires a witness d before SOME a in A — equivalently, before the LATEST a in A (max position in A). Requiring d < min(A) is strictly stronger and fails on valid orderings.

## REPAIR_HINTS
Two distinct bugs, both must be fixed:

1. `_is_valid_lexbfs` (and the identical loop in `_rederive`'s prefix scan) implements the wrong (LB) property. It picks the EARLIEST a in A (`a0 = ai; break` on first hit) and requires d < a0. The correct property requires: for the triple to be a violation, NO a in A has a witness d < a. Equivalently, let a_max = the LATEST position in A; the triple is satisfied iff there exists d < a_max with d~b and d not~ c. Fix: iterate `for ai in range(bi)` WITHOUT breaking (or track the max), and check `for di in range(a_max)`. This makes the certificate check correct (it will then accept [0,2,1] and reject [0,1,2] in the failing case, so `_update` would... still need re-derivation since [0,1,2] is genuinely invalid — good).

2. The prefix-extension strategy in `_rederive` is unsound: "longest prefix satisfying local (LB) condition" is not the same as "longest prefix that is a genuine LexBFS prefix (consistent with the partition-refinement trajectory)". A prefix can pass the local (LB) test yet be non-extendable (as [0,1] is in the failing case), and extending a non-genuine prefix yields an invalid ordering. The correct test for "prefix P is a valid LexBFS prefix" is: simulate the partition refinement on the full vertex set following P (refine by each prefix vertex in order, always taking the first non-empty bucket and requiring it to equal the next prefix vertex), and check that P is exactly the trajectory the refinement produces (with the candidate's tie-break, or with SOME tie-break if any is allowed). If the prefix is not consistent with the refinement, truncate to the longest consistent prefix, then continue the refinement from there.

Simplest correct repair (sacrifices the "avoid full recompute" goal but restores correctness): in `_update`, if `_is_valid_lexbfs` (fixed per #1) returns False, just call `_lexbfs_static(graph)` and return it. This is always correct. The prefix-reuse optimization can be re-attempted later with the corrected prefix-consistency test (#2).

Approaches that will NOT work:
- Keeping the "local (LB) on prefix" test as the prefix-validity criterion — it is strictly weaker than refinement-consistency and will keep producing invalid orderings.
- Re-checking `_is_valid_lexbfs` on `_rederive`'s output and falling back to static only if invalid — this would mask the bug but the re-derive path would still do wasted work; more importantly it papers over bug #2 rather than fixing it, and any future "optimization" built on the prefix idea inherits the unsoundness.
- Only fixing bug #1 without #2: in the failing case, fixed `_is_valid_lexbfs([0,1,2])` correctly returns False, `_rederive` runs, its (still buggy) prefix scan accepts [0,1], seeds buckets [{2},{1}], continuation appends 2 → returns [0,1,2] again → still invalid. So #2 must be fixed too (or the re-derive path replaced by a full static recompute).
