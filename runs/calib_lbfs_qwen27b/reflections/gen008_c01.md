## FAILURE_DESCRIPTION
n=3. Initial graph: only edge (0,1) (path 0-1-2). init() returns [0,1,2] (valid).
Operation: insert_edge (0,2). New graph: edges (0,1),(0,2),(1,2) = triangle K3.
Expected: [0,2,1] (the only valid LexBFS orderings of K3 are [0,1,2] and [0,2,1]).
Actual: [0,1,2] — the old ordering was kept.
Verifier's violation report: a=0, b=1, c=2, pos_a=0, minD=1000000000 (sentinel = "no witness d found").

## ROOT_CAUSE
The certificate check `_is_valid_lexbfs` is a FALSE certificate: it returns True for orderings that violate the (LB) property. The bug is in the bitset encoding of the "a0" test.

The (LB) property is stated over POSITIONS in the ordering: for positions a < b < c with ac in E and ab not in E, there must exist a position d < a with db in E and dc not in E. The code's own docstring says "a0 = min pos in (S_b \ N(c))" and "mask<a0: bits 0..a0-1" — i.e. a0 is meant to be a POSITION index.

But the code computes it as a VERTEX ID:

```python
diff = S & ~Nc
a0 = (diff & (-diff)).bit_length() - 1   # lowest set bit of diff = vertex id
mask = (1 << a0) - 1
if (S & mask & ~Nc) == 0:
    return False
```

`S` and `Nc` are bitsets indexed by vertex id, so `a0` is the vertex id of the smallest-id neighbor of b that is not a neighbor of c, and `mask` covers vertex ids 0..a0-1 — not positions 0..a0-1. The two coincide only when vertex id == position, which is not guaranteed.

Trace on the failing case (order [0,1,2], K3): bi=1, b=1, S={0}, c=2, Nc={0,1}. diff = S & ~Nc = 0, so the `if diff == 0: continue` branch skips the pair and the function returns True. The code's own stated condition ("a0 = min pos in (S_b \ N(c)) exists") is NOT satisfied here — S_b \ N(c) is empty — so the code is not even implementing its own documented condition. The real (LB) violation for this ordering is: positions a=0 (v0), b=1 (v1), c=2 (v2): ac in E (0~2), ab not in E (0 not~1), and no d < 0 exists. The certificate must flag this, but it does not.

Consequence in `_update`: step 1 `if _is_valid_lexbfs(order, graph): return {'ordering': order}` keeps the stale ordering [0,1,2] on the triangle. The safety net in step 3 never fires because it uses the same broken certificate.

## REPAIR_HINTS
1. Rewrite `_is_valid_lexbfs` as a direct, position-based check of the (LB) property. The simplest correct version is O(n^4) (or O(n^3) with per-b bitsets over positions): for each position b in 1..n-2, for each position c in b+1..n-1 with c~b, for each position a in 0..b-1 with a~c and not a~b, check whether some position d in 0..a-1 has d~b and not d~c; if none, return False. This is exactly the property in the brief and matches the verifier's violation format (a, b, c, minD sentinel when no d).
2. If keeping the bitset speedup: build bitsets indexed by POSITION (bit i set iff the vertex at position i is in the set), e.g. `S_b = { i < bi : order[i] ~ b }` as position bits, and `Nc_pos = { i : order[i] ~ c }` as position bits. Then `a0 = lowest set bit of (S_b & ~Nc_pos)` is a position, `mask = (1 << a0) - 1` covers positions < a0, and the test `S_b & mask & ~Nc_pos == 0` is the correct "all b-neighbors before position a0 are also c-neighbors" condition. Note the current code's `diff == 0: continue` is fine only under this position-bitset encoding; with vertex-id bits it silently skips real violations (as in the failing case).
3. Do NOT rely on the `_rederive` prefix logic or the safety net to mask this: both consume the same broken certificate, so the safety net can never catch an ordering the certificate wrongly accepts. Fix the certificate first; only then is the "keep old ordering / keep prefix" fast path sound.
4. Approaches that will not work: (a) patching only the `diff == 0` branch — the vertex-id vs position mismatch corrupts the mask test even when diff != 0; (b) adding a tie-break or start-vertex constraint — the problem allows any valid LexBFS, the issue is purely the false certificate; (c) trusting `_rederive`'s "longest valid prefix" — its incremental prefix check is position-based and correct, but it is unreachable in this failure because step 1 already returns early.
