## FAILURE_DESCRIPTION
Case: n=2, root 0, initial graph [[0,0],[0,0]] (no edges). Operation: insert (0,1).
Expected after the update: parent = {0: None, 1: 0}, distances = {0: 0, 1: 1}.
Actual: parent[1] = None, distances[1] = -1 (vertex 1 left unreachable).
The verifier reports vertex 1 wrong: expected_distance 1, your_distance -1, your_parent null.

## ROOT_CAUSE
In `insert_edge`, the update branch is guarded by:

    if dist[u] >= 0 and dist[u] + 1 < dist[v]:

This condition conflates two cases. It is correct for the "shorten an already-reachable vertex" case (dist[v] >= 0 and dist[u]+1 < dist[v]), but it is wrong for the "make an unreachable vertex reachable" case. When v is unreachable, dist[v] == -1, so `dist[u] + 1 < dist[v]` becomes `dist[u] + 1 < -1`, which is false for every reachable u (dist[u] >= 0). The branch is therefore never entered for a newly-reachable vertex, and the code falls through to return the unchanged state: parent[v] stays None, dist[v] stays -1.

Trace on the failing case:
1. init on [[0,0],[0,0]]: parent = [None, None], dist = [0, -1].
2. insert_edge((0,1)): in_edges[1] becomes [0], out_edges[0] becomes [1].
3. Guard check: dist[0] = 0 >= 0 (true), but dist[0] + 1 = 1 < dist[1] = -1 (false). Branch skipped.
4. State returned unchanged -> vertex 1 never gets parent 0 / distance 1.

The docstring even states the intent ("If v is unreachable and u is reachable, v becomes reachable") but the code never implements it.

## REPAIR_HINTS
Smallest fix: split the guard in `insert_edge` into the two cases, e.g.

    if dist[u] >= 0 and (dist[v] < 0 or dist[u] + 1 < dist[v]):

Inside the branch, the existing code already handles both cases correctly:
- `parent[v] = u; dist[v] = dist[u] + 1` works for the newly-reachable case (v was unreachable, so `_subtree(parent, v)` is just {v} and the descendant loop does nothing).
- For the reachable-shortening case, the descendant re-parenting loop is unchanged.

Do NOT "fix" this by special-casing only the unreachable case with a separate early return that sets parent[v]/dist[v] and skips the descendant loop — that would still be correct for the failing case but the unified guard above is the minimal change and keeps one code path.

Approaches that will not work / are not the issue here:
- Rebuilding in_edges/out_edges from the graph: they are already updated correctly before the guard; the bug is purely the guard condition.
- Changing `_subtree` or `_reparent_subtree`: they are not reached in this failing case at all.

Note (out of scope for this failing case, but worth flagging to the repair role): the descendant loop in `insert_edge` recomputes each w's distance as min over ALL in-neighbors using the partially-updated `dist` array, which can over-shorten descendants (e.g. a descendant w of v may get dist[u2]+1 where u2 is a non-descendant in-neighbor, breaking the BFS invariant that parent[w] is one level closer). The current failing case does not exercise that, so fix the guard first; if a later case fails on descendant distances after an insertion, that loop is the suspect.
