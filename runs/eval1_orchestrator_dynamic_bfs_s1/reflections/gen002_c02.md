## FAILURE_DESCRIPTION
Operation: `delete (0,1)` on a 4-vertex directed graph (post-update graph: 0→2; 1→0,1→2,1→3; 2→0,2→3; 3→1; root 0).
Expected after the update: parent = {0:None, 2:0, 3:2, 1:3}, distances = {0:0, 2:1, 3:2, 1:3}.
Actual reported: parent = [None, None, 0, None], distances = [0, -1, 1, -1] — vertices 1 and 3 wrongly marked unreachable.

## ROOT_CAUSE
**The trace is inconclusive — the reported result cannot be reproduced by the candidate as written on the given input.** I traced the code step by step:

- Initial BFS on the pre-update graph (which must have been the post-update graph plus edge 0→1, since a legal delete flips one entry) gives dist = [0, 3, 1, 2], parent = [None, 3, 0, 2] (1 is reached via 3→1 at distance 3).
- In `delete_edge`, `u=0, v=1`. The guard `if parent[v] != u:` evaluates `parent[1] = 3 != 0` → True, so the function takes the early-return path and returns the state **unchanged**: parent = [None, 3, 0, 2], dist = [0, 3, 1, 2]. That is a *valid* BFS tree for the post-update graph (0→2→3→1), so this candidate would actually PASS this case as written.
- The reported result `[None, None, 0, None]` requires `parent[1] == 0` at entry (so the deletion is treated as a parent-edge deletion) AND vertex 3 also pruned. Neither holds for the state I reconstructed. Even the alternative hypothesis (pre-update graph contained 0→1, so parent[1]=0, dist[1]=1) only yields `[None, None, 0, 2]` after `_reparent_subtree` prunes just {1} — 3 is not in the affected subtree of 1, so it survives.

Hypotheses ruled out:
1. "Early-return path is wrong" — ruled out: the early return here is correct (deleted edge 0→1 was not a tree edge).
2. "Pre-update graph had 0→1, parent[1]=0" — ruled out as the exact cause: it would prune only {1}, not {3}.

**Hypotheses still open (most likely):**
- The failing run used an *earlier revision* of this candidate whose deletion logic pruned more aggressively (e.g. recomputed reachability of the whole affected region, or pruned descendants of the pruned vertex in the *graph* rather than the *tree*).
- The state entering the operation was corrupted by a prior operation in the same sequence (sequence_idx is 0, but the harness may have applied an unseen init/insertion).

## REPAIR_HINTS
Because the exact divergence point is unconfirmed, do NOT "fix" the early-return guard — it is correct for this case. Instead, harden the deletion path so that *any* plausible prior state yields a valid tree:

1. **In `_reparent_subtree`, when a vertex v is pruned, do not prune its affected descendants unconditionally.** A descendant w of v may still be reachable via a non-tree in-neighbor outside the affected set (e.g. via a vertex at distance ≤ dist[w]-1 that is not in the subtree). Current code:
   ```python
   pruned.add(v)
   for w in desc_map.get(v, ()):
       pruned.add(w)
   ```
   This blanket pruning is the most likely source of the "3 wrongly unreachable" symptom if the affected set had ever contained 3. Fix: after marking v unreachable, continue the loop and let each descendant w be evaluated on its own in_edges (the `if v in pruned: continue` check must be changed so that a descendant of a pruned vertex is still *evaluated*, not skipped — only skip if w itself was already pruned).

2. **When re-parenting v, consider in-neighbors u with `new_dist[u] + 1 <= new_dist[v]` (allow equal), not just `<`.** Current code picks `best_d` from all in-neighbors with `new_dist[u] >= 0` and takes the minimum `new_dist[u]+1`, which is actually fine for distance, but the *cycle guard* `if u in desc_map.get(v, ())` only excludes descendants *within the affected set*. If u is a descendant of v in the *global* tree but not in `affected`, a cycle could form. Use the global parent pointers to exclude all true descendants of v, not just affected ones.

3. **Safest fallback (if incremental repair keeps failing):** in `delete_edge`, after the incremental repair, run a *verification pass*: check every v with parent[v] != None that `graph[parent[v]][v] == 1` and `dist[parent[v]] + 1 == dist[v]`; if any check fails, fall back to `_bfs_full`. This guarantees correctness at the cost of occasional full recomputation, and will pass the verifier regardless of which prior state produced the failure.

Approaches that will NOT work:
- Changing the `if parent[v] != u: return` guard — it is correct; the deleted edge not being a tree edge means the tree is valid as-is.
- Only fixing the insertion path — the failure is on a deletion.
