## FAILURE_DESCRIPTION

Graph: n=2, adjacency all zeros (no edges), root 0. Operation: `delete_edge(graph, (0,1), state)` (sequence_idx 0, i.e. the first update on the initial state).

Expected state: `parent = [None, None]`, `distances = [0, -1]` (vertex 1 unreachable).
Actual state: `parent = [None, 0]`, `distances = [0, -1]`.

The verifier flags vertex 1: `your_parent = 0` while `expected_distance = -1`. The distance is right, but the parent is a stale, dangling pointer to a vertex that is not (and never was) a valid BFS parent of 1.

## ROOT_CAUSE

The bug is in `delete_edge`. It removes the edge from `adj`, `in_adj`, `out_adj`, `in_adj_sets` and then does:

```python
if parent[v] != u:
    return state
```

For this case `parent[1]` is `None` (vertex 1 was unreachable from the start), so `None != 0` and the function returns immediately — **without ever clearing `parent[v]`**. The stale parent survives.

The deeper issue: the `parent[v] != u` early-exit is only sound when `parent[v]` is guaranteed to be a *currently existing* edge. That guarantee holds only if the state invariant "parent[v] is a true in-neighbor" was maintained at all prior steps. It is not: `_fix_subtree`'s parent reassignment loop can leave a dangling parent:

```python
for x in sub:
    if x == v:
        continue
    new_d = new_dist[x]
    if new_d == INF:
        parent[x] = None
    else:
        found = None
        for y in in_adj_sets[x]:
            if dist[y] == new_d - 1:
                found = y
                break
        parent[x] = found
```

If `new_d != INF` but no in-neighbor at distance `new_d - 1` is found (e.g. the only such in-neighbor was the deleted edge, or a distance committed earlier in the same loop made the search miss), `found` stays `None` and `parent[x] = None` — that part is fine — but the *symmetric* failure mode is when the search finds a `y` whose edge was just removed from `in_adj_sets` ordering, or when `dist[y]` was read after a partial commit. More concretely, the commit loop sets `dist[x]` for all `x in sub` *before* the parent loop, so a parent search for a later vertex can match an in-neighbor `y` inside the subtree whose *old* distance was `new_d-1` but whose *new* committed distance is different — no, it reads the new `dist`, so that's consistent. The real dangling-parent path is: a vertex `x` with `new_d != INF` whose only in-neighbor at distance `new_d-1` is `v` itself, but `v`'s parent was set by the caller to a value that is not actually an edge (e.g. `insert_edge` sets `parent[v]=u` before `_fix_subtree`, which is fine, but on the delete path the caller passes `new_parent=None` and never sets `parent[v]` at all — so `parent[v]` keeps its old value, which is exactly the deleted edge's tail `u`).

So the two concrete defects are:

1. **`delete_edge` never sets `parent[v] = None` before calling `_fix_subtree(state, v, None)`**, and `_fix_subtree` explicitly skips `x == v` in the parent loop ("whose parent was already set by the caller" — but on the delete path the caller set nothing). Hence `parent[v]` retains the stale value `u` even when `v` becomes unreachable.
2. **The `parent[v] != u` early-exit in `delete_edge` assumes `parent[v]` is a live edge.** If any prior update left a dangling parent (defect 1 in an earlier call, or the `found=None` case in `_fix_subtree` for a vertex that later got a finite `new_d`), the early-exit can skip a needed repair, or (as here) the stale parent simply persists because the "repair" path was never entered.

In this specific failing case, defect 1 is the direct cause: the initial state has `parent[1]=None`, so the early-exit fires and nothing is touched — wait, that means `parent[1]` was already `None` at init. Re-tracing: init on the all-zero graph gives `parent=[None,None]`, `dist=[0,-1]`. Then `delete_edge((0,1))`: `parent[1]` is `None`, `None != 0` → early return. `parent[1]` should still be `None`... but the reported actual is `parent[1]=0`.

This means the state that reached `delete_edge` was **not** the init state — the harness must have applied an `insert_edge((0,1))` first (or the sequence includes a prior op not shown in this single failing record). After `insert_edge((0,1))`: `parent[1]=0`, `dist[1]=1`. Then `delete_edge((0,1))`: `parent[1]==0==u`, so it proceeds to `_fix_subtree(state, 1, None)`. In `_fix_subtree`: `sub=[1]`, `best_out[1]=INF` (no other in-neighbors), `new_dist[1]=INF`, commit sets `dist[1]=-1`, parent loop skips `x==v` (x==1==v). **`parent[1]` is never reset to `None`** — it stays `0`. That is exactly the reported wrong state.

So the root cause is defect 1, confirmed by trace: on the delete path the caller contract ("parent was already set by the caller") is violated because `delete_edge` never sets `parent[v]=None`.

## REPAIR_HINTS

Smallest fix, in `delete_edge`, before calling `_fix_subtree`:

```python
if parent[v] != u:
    return state
parent[v] = None          # <-- add this line
return _fix_subtree(state, v, None)
```

This makes the caller contract of `_fix_subtree` ("subtree root's parent already set") true on the delete path: the root's parent is `None` (unreachable) or, if `_fix_subtree` later finds a finite `new_dist[v]`, the parent loop still skips `v` — so also handle the case where `v` regains reachability: after the distance commit in `_fix_subtree`, if `new_dist[v] != INF`, assign `parent[v]` to an in-neighbor at distance `new_dist[v]-1` (the same search used for other subtree vertices). Concretely, in `_fix_subtree`, change the parent loop to also process `x == v` when `new_parent is None` and `new_dist[v] != INF`:

```python
for x in sub:
    if x == v and new_parent is not None:
        continue   # caller already set parent[v]
    ...
```

(pass `new_parent` through; it already is a parameter).

Also harden the `delete_edge` early-exit against dangling parents: replace `if parent[v] != u: return state` with a check that the edge is actually a tree edge *and exists*: `if parent[v] != u or not adj[u][v]: return state` — though after the fix above, `parent[v]` can no longer dangle, so the original check is fine.

Approaches that will NOT work:
- Only fixing `insert_edge` — the bug is purely on the delete path.
- Recomputing the full BFS in `delete_edge` — correct but defeats the research goal (avoid full recompute); the targeted fix above is O(subtree + in-neighbor scans).
- Setting `parent[v]=None` inside `_fix_subtree` unconditionally at the top — wrong for the insert path, where the caller has already set `parent[v]=u` to the new (valid) parent; use the `new_parent is None` guard instead.
