## FAILURE_DESCRIPTION
4-vertex directed graph, root 0. Pre-update graph has edges 0→1, 0→2, 1→0, 1→2, 1→3, 2→0, 2→3, 3→1. The pre-update BFS tree is parent=[None, 0, 0, 1], dist=[0, 1, 1, 2] (vertex 3 is a tree child of 1, since 1 is dequeued before 2 and 1→3 exists).

Update: delete edge (0,1). Post-update graph (the one in the case) has 1's only in-neighbor as 3, and 3's only in-neighbor as 2. True BFS after deletion: dist=[0, 3, 1, 2], parent=[None, 3, 0, 2] (path 0→2→3→1).

Expected: parent[1]=3, dist[1]=3.
Actual: parent[1]=None, dist[1]=-1 (vertex 1 reported unreachable).
Vertices 0, 2, 3 are correct in the output; only vertex 1 is wrong.

## ROOT_CAUSE
In `_reparent_subtree`, the affected set is {1, 3} (the old tree subtree of 1). Processing order is by *old* distance: v=1 (old dist 1) first, then v=3 (old dist 2).

When processing v=1, the only in-neighbor is u=3. The guard

```python
if u in desc_map.get(v, ()):
    continue
```

skips u=3 because 3 is a descendant of 1 in the *old* tree (desc_map[1] = {3}). So 1 gets no candidate parent, is marked unreachable (new_dist[1] = -1). Then v=3 is re-parented to 2 (new_parent[3]=2, new_dist[3]=2), which is fine on its own.

The flaw: the cycle-avoidance check uses the old tree's descendant relation, but 3 is *itself being re-parented* to 2 (outside the affected subtree). In the new tree, 3 is no longer a descendant of 1, so the edge 3→1 is a perfectly valid parent edge (it would give dist[1]=3, which is the true answer). The guard is overly conservative: it forbids re-parenting v to a descendant u even when u will be (or is) re-parented outside v's subtree.

Compounding this, the processing order (sorted by old distance) means v=1 is decided *before* v=3's new parent is known, so even a "check u's new parent" fix would need 3 to be settled first. Note that 3's *new* distance (2) is less than the candidate distance it would give 1 (3), so a distance-ordered fix is feasible: a vertex v may only be re-parented to u if u's final new distance is already settled and new_dist[u] + 1 < current best, and u is not a descendant of v in the *new* tree.

`_verify` does not catch this because it only checks local consistency (dist[v] == dist[parent[v]] + 1 and the parent edge exists) plus the unreachable convention; it never checks that distances are minimal or that a vertex marked unreachable is actually unreachable. So the fallback to `_bfs_full` never triggers.

## REPAIR_HINTS
The smallest fix that restores correctness: in `_reparent_subtree`, do not reject a candidate parent u merely because u is an old-tree descendant of v. Instead, reject u only if u would still be a descendant of v in the *new* tree — i.e., if u's new parent chain (using new_parent as it is being built) leads back to v. Concretely:

1. When considering candidate u for v, walk u's new parent chain (new_parent[u], new_parent[new_parent[u]], ...) and reject u only if v appears on that chain (true cycle). Since new_parent for vertices outside `affected` is unchanged and for affected vertices is set in processing order, this requires that u's new parent be already settled when v is processed.
2. To guarantee that, process affected vertices in order of *candidate new distance*, not old distance. A safe approach: iterate in rounds. In each round, for each unsettled affected vertex v, compute the best candidate u among in-neighbors whose new distance is already finalized (either outside `affected`, or an affected vertex settled in an earlier round) and whose new parent chain does not pass through v. Settle v if a candidate exists. Repeat until no progress. Vertices never settled become unreachable.
   - In the failing case: round 1 settles 3 (candidate 2, outside affected, chain 2→0 does not hit 3). Round 2 settles 1 (candidate 3, now finalized with new_parent[3]=2, chain 3→2→0 does not hit 1) → parent[1]=3, dist[1]=3. Correct.
3. Alternatively (simpler, still incremental): after the current single-pass repair, run a *targeted* BFS restricted to the affected set plus their in-neighbors to recompute exact distances for affected vertices, using the finalized distances of non-affected vertices as sources. This is a small local BFS, not a full recompute.
4. Also strengthen `_verify` to catch this class of bug: for every vertex with dist[v] != -1, verify dist[v] equals the true shortest-path distance (e.g., by a full BFS comparison, or at minimum check that no in-neighbor u has dist[u] + 1 < dist[v]). This makes the fallback trigger on under-estimated distances, not just structural inconsistencies.

Approaches that will NOT work:
- Keeping the old `desc_map` guard but processing in old-distance order: the failing case shows the descendant's new parent is decided after the ancestor's, so the guard always fires too early.
- Simply removing the cycle guard: it can create genuine parent cycles (v→u and u→v both as parent edges) when u is re-parented to v's new subtree, so the guard must be replaced, not deleted.
- Relying on `_verify` as-is: it cannot detect a vertex wrongly marked unreachable (the invariant it checks is satisfied by the wrong answer).
