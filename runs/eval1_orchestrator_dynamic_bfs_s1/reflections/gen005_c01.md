## FAILURE_DESCRIPTION

Case: 3-vertex directed graph, root 0. Post-update graph (after `delete (0,2)`, sequence_idx 1):
- Edges: 0→1, 1→2, 2→0, 2→1.
- Expected: parent = [None, 0, 1], distances = [0, 1, 2].
- Actual: parent = [None, 0, None], distances = [0, 1, -1].
- Wrong vertex: 2 (expected distance 2, got -1 / parent None).

This is the *second* operation in the sequence (index 1). The current operation, `delete (0,2)`, is a no-op on the BFS tree: `parent[2] == 1 != 0`, so `delete_edge` hits the early-return guard `if parent[v] != u: return state` and returns the state **unchanged**. The state was already wrong *before* this operation — vertex 2 was already (incorrectly) marked unreachable. The invariant check after this op therefore reports the stale corruption. The bug is in the *previous* operation (index 0), which wrongly cut vertex 2 off; this case merely exposes it because the no-op deletion never repairs anything.

## ROOT_CAUSE

The failing op itself is not the bug — it correctly does nothing. The corruption was introduced by the prior update, which must have been a deletion of a *tree* edge (parent[v] == u) whose subtree repair in `delete_edge` failed to re-root a vertex that is actually still reachable.

The subtree-repair logic in `delete_edge` has a concrete defect that can cause exactly this: after cutting the subtree (setting `dist[x] = -1` for all `x in subtree`), the re-rooting BFS only seeds from **boundary vertices** `w` with `in_sub[w] == False` and `dist[w] == d-1`, scanning `for w in range(n)`. This is correct for reaching subtree vertices from *outside*. However, the subsequent "propagation" phase:

```python
for x in subtree:
    if dist[x] != -1:
        for y in adj[x]:
            if dist[y] == -1 or dist[x] + 1 < dist[y]:
                dist[y] = dist[x] + 1
                parent[y] = x
                q.append(y)
```

iterates `for x in subtree` in **arbitrary (DFS-stack) order**, not in nondecreasing-distance order. If a subtree vertex `x` is processed before another subtree vertex `x'` that should be its parent (i.e., `dist[x'] + 1 < dist[x]`), the condition `dist[x] + 1 < dist[y]` may assign a *suboptimal* (too-large) distance to a downstream vertex, or — worse — the `dist[y] == -1` branch may assign a distance from a non-minimal source before the true minimal source is processed. Because the loop is a plain `for` over `subtree` (not a BFS queue in distance order), the "settled at true minimum distance" invariant the docstring claims is **not actually maintained** in this phase. A vertex can be assigned a distance from a farther boundary path before the nearer path is considered, and since the assignment only fires on `dist[y] == -1 or dist[x]+1 < dist[y]`, a *later* nearer source would still fix it — BUT only if that nearer source is also in `subtree` and also gets processed. If the nearer source is a *boundary* vertex (outside subtree), it was already handled in the level loop, so this is fine. The real failure mode: a subtree vertex that is reachable only via a *chain of subtree vertices* where the chain's entry point was missed by the boundary scan because the boundary vertex's distance was not exactly `d-1` at the time the level loop ran (the level loop only checks `dist[w] == d-1` for fixed `d`, and `d` increments by 1 each iteration; if the true re-rooting distance of a subtree vertex is larger than the number of boundary levels scanned, the loop `break`s early via `if not any(dist[x] == d for x in subtree): break` before reaching it).

Concretely, the `break` condition is the most likely culprit: the level loop stops as soon as *no* subtree vertex was reached at the current level `d`. But a subtree vertex could be reachable at level `d+1` via a subtree vertex reached at level `d` — the loop does handle that (it continues while any subtree vertex was reached at level `d`). However, it only propagates *one* subtree level per iteration via the boundary scan; it does NOT expand subtree-vertex-to-subtree-vertex edges within the level loop. The expansion of subtree-internal edges is deferred to the post-loop propagation phase, which runs in arbitrary order. So if the re-rooting requires a path boundary → subtree_a → subtree_b where subtree_b is only reachable through subtree_a, the level loop reaches subtree_a at level d, then the `break` check passes (subtree_a has dist d), d increments, the next boundary scan finds no boundary vertex at level d pointing into the subtree (only subtree_a does), so `any(dist[x] == d+1 for x in subtree)` is False and the loop **breaks**, leaving subtree_b at -1. The post-loop propagation then processes `subtree` in arbitrary order: if subtree_a is processed, it will set subtree_b correctly. So this specific sub-case is actually saved by the propagation phase.

Given the trace is inconclusive about *which* prior operation corrupted the state (the case only shows op index 1), the root cause is: **the prior deletion's subtree repair left a reachable vertex at distance -1**, and the current no-op deletion's early-return guard (`if parent[v] != u: return state`) correctly does nothing, so the stale corruption persists and is reported. The defect is in the subtree-repair logic of `delete_edge`, most likely the interaction between the level-loop `break` condition and the arbitrary-order post-loop propagation, which can fail to re-root a subtree vertex whose only re-entry path goes through another subtree vertex at a level the loop broke past.

## REPAIR_HINTS

1. **The early-return guard is fine** — a non-tree-edge deletion genuinely cannot break the BFS tree. Do not "fix" the guard; the bug is upstream.

2. **Replace the two-phase (level-loop + arbitrary-order propagation) re-rooting with a single, correct multi-source BFS.** After cutting the subtree, collect all boundary edges (w, x) where `in_sub[w] == False` and `in_sub[x] == True` and `dist[w] != -1`, seed a queue with each such `x` at distance `dist[w] + 1` (taking the minimum if multiple boundary vertices reach the same `x`), and run a standard BFS *restricted to subtree vertices* (only expand `x` if `in_sub[x]`). This guarantees every subtree vertex is settled at its true minimum distance in one pass, in correct distance order, with no arbitrary-order phase.

3. **Do not** try to fix the arbitrary-order propagation loop by sorting `subtree` by distance — the distances are not final at that point, so sorting is circular. The only correct fix is to do the BFS in proper queue order from the start.

4. **Do not** add a full-recompute fallback as the "fix" — the research goal is to avoid full recomputation. A correct local multi-source BFS over the subtree is O(subtree_size + boundary_edges) and is the intended approach.

5. The `insert_edge` function is not implicated in this failure; leave it as-is unless a separate case shows otherwise.
