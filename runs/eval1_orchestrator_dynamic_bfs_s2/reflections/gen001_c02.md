## FAILURE_DESCRIPTION
Graph (3x3): edges 0->1, 1->2. Root 0. Operation: `insert (0, 1)` (edge already present; a legal update may flip an entry that is already 1, i.e. a no-op insertion). Expected state after the update: parent {0: None, 1: 0, 2: 1}, distances {0: 0, 1: 1, 2: 2}. Actual returned state: parent {0: None, 1: None, 2: None}, distances {0: 0, 1: -1, 2: -1}. Vertices 1 and 2 are wrongly marked unreachable.

## ROOT_CAUSE
The failure is in `insert_edge`. The guard that is supposed to make a no-op insertion a no-op is wrong:

```python
newd = dist[u] + 1
if dist[v] != -1 and newd >= dist[v]:
    return state
```

This guard only fires when `dist[v] != -1`. When `v` is currently unreachable (`dist[v] == -1`) but the edge (u,v) already exists in the graph (so the insertion is a no-op), the guard is skipped and the code falls through to the re-parenting block:

```python
oldp = parent[v]
if oldp is not None:
    children[oldp].discard(v)
parent[v] = u
children[u].add(v)
dist[v] = newd
```

Tracing the failing case: after `init`, dist = [0, 1, 2], parent = [None, 0, 1], children = {0: {1}, 1: {2}}. Inserting (0,1): u=0, v=1, dist[u]=0, newd=1, dist[v]=1, so `newd >= dist[v]` is True and the guard returns — that path is fine. The failing trace instead shows the state where `dist[v] == -1` at the moment of the call: the harness's pre-state for this case has v=1 unreachable (dist[1] = -1, parent[1] = None) while the matrix already contains edge 0->1. Then `dist[v] != -1` is False, the guard is skipped, and the code re-parents v=1 to u=0 and sets dist[1] = 1 — but the subsequent subtree walk

```python
q = deque([v])
while q:
    x = q.popleft()
    for c in children[x]:
        dist[c] = dist[x] + 1
        changed.add(c)
        q.append(c)
```

only propagates through `children[x]`. Since v=1 was unreachable, `children[1]` is empty, so vertex 2 (which in the true graph is reachable via 1->2) is never discovered. Worse, the observed actual output has dist[1] = -1 as well, meaning the re-parented state was not even the one returned — the returned state is the pre-update state with 1 and 2 unreachable, i.e. the candidate's `init`/pre-state for this case already had 1 unreachable despite edge 0->1 being in the matrix. Either way the invariant "spans exactly the vertices reachable from r" is violated: vertex 1 (and transitively 2) is reachable in the graph but marked unreachable.

The core defect: `insert_edge` treats "v unreachable" as "v must be re-parented to u", without checking whether the edge (u,v) is actually new. When the edge already exists and v is unreachable, the correct behavior is a no-op (the state was already wrong, or the state is consistent and nothing changes); when the edge is genuinely new and v is unreachable, the correct behavior is to re-parent v AND run a BFS from v to discover v's newly-reachable descendants (the current code only walks the existing tree children, which is empty for an unreachable v).

## REPAIR_HINTS
1. In `insert_edge`, before re-parenting, check whether the edge (u,v) was already present: `was_new = v not in adj[u]` (capture BEFORE `adj[u].add(v)`). If `not was_new`, return state immediately (no-op insertion). This fixes the failing case directly.
2. If the edge IS new and `dist[v] == -1` (v was unreachable), re-parenting v to u is correct, but the descendant update must be a real BFS from v over `adj` (not just a walk of `children`), because v's old tree children set is empty and v may have out-edges to other previously-unreachable vertices. Replace the `q = deque([v])` children-walk with a BFS that discovers all vertices reachable from v that are currently `dist == -1`, assigning `dist` and `parent` as it goes.
3. Do NOT fix this by making the guard `if newd >= dist[v]` unconditional (i.e. dropping the `dist[v] != -1` condition) — that would break the legitimate case where v is unreachable and the new edge genuinely makes v reachable at distance newd.
4. The `rad`/`_fix_radii_after_insert` machinery is not the cause of this failure; leave it alone for now.
