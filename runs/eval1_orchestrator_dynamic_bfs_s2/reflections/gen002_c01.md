## FAILURE_DESCRIPTION

Failing case: 4-vertex directed graph (root 0), operation `delete (0, 2)`.

Graph at the time of the check (0/1 adjacency matrix):
- 0→3
- 1→2
- 2→0, 2→3
- 3→1, 3→2

True BFS from 0 on this graph: dist = [0, 2, 2, 1], e.g. parent = {0:None, 3:0, 1:3, 2:3}.
Expected state: distances [0, 2, 2, 1], parent[2]=3.
Actual state returned: parent = [None, 3, 1, 0], i.e. parent[2]=1, and distances with dist[2]=3 (vertex 2 reported distance 3, parent 1).

Key observation: the state *before* the delete already had parent[2]=1, dist[2]=3. That is a BFS tree of the graph **without** the edge 3→2 (path 0→3→1→2). But the graph shown does contain 3→2, so the pre-delete state was already invalid for the current graph. The delete itself is a no-op in the code: `delete_edge` checks `if parent[v] != u: return state`, and since parent[2]=1 ≠ 0, it returns the (already corrupted) state unchanged. The delete did not cause the divergence; it merely exposed a corruption introduced by an **earlier** operation in the sequence (the harness applies a prefix of updates before this check; `sequence_idx: 0` refers to the recorded failing operation, not necessarily the first update applied).

## ROOT_CAUSE

The corruption was introduced by an earlier update (most plausibly an insertion or deletion) that left `dist[2]=3, parent[2]=1` even though the edge 3→2 was present, making dist[2] one too large. The `delete (0,2)` operation is a red herring: `delete_edge` correctly treats it as a non-tree-edge deletion (`parent[v] != u` → early return), which is the right behavior *if the state were valid*. The bug is that some earlier operation failed to keep the BFS invariant (parent of v one distance closer, distances equal to true BFS distances).

The most likely culprit, based on the code, is `insert_edge`. Its fast path assumes that when a vertex v is re-parented to a closer u, **all of v's descendants keep their tree edges and their distances simply drop by the same delta** (the `if oldp is not None:` branch: `dist[c] = dist[x] + 1` down the subtree). This is only valid if no descendant of v has an alternative in-tree or non-tree edge that would make its *true* distance drop by a different amount, or if a descendant's old parent edge was the only reason it was at that distance. More concretely, the branch never checks whether a descendant w of v has an in-neighbor x (outside v's subtree) with `dist[x]+1 < dist[w]` after the shift — if such an x exists, w's true distance is smaller than `dist[v]+depth(w)`, and the uniform-shift update leaves w's distance too large and its parent wrong. This exactly matches the observed symptom (a vertex whose distance is one too large, parented along the old chain).

A secondary suspect is the deletion re-BFS: it seeds the queue with *all* still-reachable vertices and only assigns vertices in `in_sub`. If a non-cut vertex's distance should have *increased* (because its only shortest path went through the cut subtree — impossible for a BFS tree edge deletion, but possible if the state was already inconsistent), it would not be fixed. But the primary, demonstrable defect is the insertion uniform-shift assumption.

## REPAIR_HINTS

1. In `insert_edge`, the `oldp is not None` branch must not blindly shift the whole subtree by the delta. After re-parenting v to u, run a proper BFS **restricted to the affected region**: start from v (and any vertex whose distance may have decreased), and for each popped x, for each out-neighbor y, if `dist[x]+1 < dist[y]`, re-parent y to x and update `dist[y]`; if `dist[x]+1 == dist[y]` and y is in v's old subtree, y may keep its parent but its distance must be re-verified. Vertices whose distance does not decrease keep their state. This is the standard Frigioni-style "affected region" BFS and is still bounded (only vertices whose distance actually decreases are touched).

2. Do NOT try to fix this by only adjusting radii (`_fix_radii_after_insert`): radii are derived from distances; if distances are wrong, radii propagation cannot repair the parent/distance invariant.

3. Do NOT make `delete_edge` recompute the whole BFS as a workaround for this case: the delete here is a correct no-op, and full recompute on every delete defeats the research goal. The fix belongs in the insertion path (and in any other path that mutates distances without a local BFS).

4. After fixing insertion, re-verify that `delete_edge`'s seeded BFS is correct for the case where a cut vertex is re-discovered at a *larger* distance than before (it is, since only cut vertices are reassigned and non-cut distances are unchanged by a tree-edge deletion — but this relies on the state being valid on entry, which the insertion fix restores).

5. Concrete minimal change: replace the `if oldp is not None:` subtree-shift loop in `insert_edge` with a BFS over `adj` seeded at v that only relaxes edges where `dist[x]+1 < dist[y]` (re-parenting and updating on strict improvement), collecting `changed` for the radius fix-up. Keep the `oldp is None` branch as is (it is already a correct local BFS).
