## FAILURE_DESCRIPTION
4-vertex directed graph (0-based), root 0:
- edges: 0->3, 1->2, 2->0, 2->3, 3->1, 3->2
- initial BFS: dist = [0, 2, 2, 1]; parent = [None, 3, 3, 0]; tree children: 0:{3}, 3:{1,2}, 1:{}, 2:{}
- update: delete_edge (0, 2)
- expected after update: dist = [0, 2, 2, 1], parent = [None, 3, 3, 0] (edge (0,2) is not a tree edge; nothing should change)
- actual: dist = [0, 3, 1, 0], parent[2] = 1 (vertex 2 wrong: expected distance 2, got 3; expected parent 3, got 1)

## ROOT_CAUSE
`delete_edge` assumes that if the deleted edge is not the tree edge of its head, the BFS tree is unaffected. That is false for directed graphs: a non-tree edge can be the *only* in-edge of a vertex at its BFS level, so deleting it forces that vertex (and possibly its subtree) to a larger distance.

Trace: before the update, vertex 2's in-edges are {0, 3}; its tree edge is (3,2), so `parent[2] == 3 != 0` and the code hits the early return:

```python
    if parent[v] != u:
        return state
```

After deleting (0,2), vertex 2's only in-edge is (3,2), so its true distance becomes 3 (0->3->2), and vertex 1 (whose only in-edge is (3,1)) becomes distance 4. The early return skips all of this, leaving the stale tree.

The same flaw exists in `insert_edge`:

```python
    if not was_new or dist[u] == -1:
        return state
    newd = dist[u] + 1
    if dist[v] != -1 and newd >= dist[v]:
        return state
```

The second guard is also wrong: an edge (u,v) with `dist[u]+1 == dist[v]` is a *same-level* edge. It never improves v's distance, but it can be the only in-edge of v at level `dist[v]`; deleting it later (or the fact that it exists now) matters for v's future distance. The insertion code never records such edges, so the deletion code cannot know that v's distance depends on them.

## REPAIR_HINTS
1. In `delete_edge`, remove the `if parent[v] != u: return state` early exit. After `adj[u].discard(v)`, check whether v still has any in-neighbor w with `dist[w] == dist[v] - 1` (scan the columns of `adj`, or keep a maintained `in_adj` list of sets in state). If yes, the tree is still valid and you can return. If no, v's distance must increase: cut v's tree subtree (as the code already does for the tree-edge case), then re-discover the cut region with a BFS seeded from all still-reachable vertices — but the re-discovery must allow *increasing* distances of cut vertices, not just assigning -1 vertices. The current re-discovery loop (`if y in in_sub and dist[y] == -1`) is fine for that purpose since cut vertices are reset to -1 first; the bug is purely that the early return prevents reaching it.
2. In `insert_edge`, the `newd >= dist[v]` early return is safe for the *current* distances (a same-level or worse edge cannot decrease any distance), so it can stay — but only if the deletion side is fixed as in (1), because the deletion side must recompute from scratch rather than relying on bookkeeping of which edges were "useful".
3. Do NOT try to fix this by tracking, per vertex, the count of in-edges from the previous level at insertion time: the count changes on every update and the current state has no such field; maintaining it correctly is the same amount of work as the column scan. A column scan (O(n) per deletion) is the smallest correct change.
4. The radius propagation code after re-discovery is fine and does not need changes.
