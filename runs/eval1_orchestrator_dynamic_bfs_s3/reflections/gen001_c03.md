## FAILURE_DESCRIPTION
Case: n=2, root 0, initial graph empty (both rows all zeros). Operation at sequence_idx 0: `insert (0, 1)`.
Expected after the update: distances = [0, 1], parent = [None, 0].
Actual: distances = [0, -1], parent = [None, None] (result `[None, None]`).
Vertex 1 is reachable from root 0 via the newly inserted edge (0,1) but the state still reports it as unreachable.

## ROOT_CAUSE
The bug is in `insert_edge`. The "v becomes reachable" branch is:

```python
elif distances[u] != -1 and distances[v] == -1:
    # v becomes reachable
    new_dist, new_parent = _bfs_from(v, adj, distances, parent)
    _apply_patch(state, new_parent)
```

It calls `_bfs_from(v, ...)` with `start = v`, but `distances[v] == -1` at that moment. Inside `_bfs_from`:

```python
d0 = dist[start]          # d0 = -1
new_dist[start] = d0      # new_dist[v] = -1   <-- wrong: v should get dist[u]+1 = 1
new_parent[start] = parent[start]   # new_parent[v] = None  <-- wrong: should be u
```

So the patch sets `distances[v] = -1` and `parent[v] = None` — i.e. it leaves v unreachable. The BFS then explores v's out-neighbors with `du = -1`, so any neighbor w with `dist[w] == -1` gets `new_dist[w] = 0` (should be 2) and parent v — also wrong.

The root cause: `_bfs_from` assumes `dist[start]` is already the correct new distance of `start`. That holds for the "shorten" branch (where the caller could/should set `distances[v] = distances[u]+1` first) and for the deletion branch, but the "becomes reachable" branch never establishes `distances[v] = distances[u] + 1` before calling it. The new edge (u,v) is the very reason v is now reachable, and the code never uses `u` to seed v's distance/parent.

## REPAIR_HINTS
Smallest fix, in `insert_edge`, in the `distances[v] == -1` branch: seed v with the new edge before calling `_bfs_from`:

```python
elif distances[u] != -1 and distances[v] == -1:
    distances[v] = distances[u] + 1
    parent[v] = u
    new_dist, new_parent = _bfs_from(v, adj, distances, parent)
    _apply_patch(state, new_dist, new_parent)
```

After this, `_bfs_from` starts with `d0 = distances[u]+1`, correctly sets `new_dist[v] = d0`, `new_parent[v] = u`, and propagates to v's out-neighbors (which all have old dist -1, so the `dist[w] <= du+1` skip does not fire for them).

Also audit the "shorten" branch (`distances[u] + 1 < distances[v]`): it has the same latent bug — `_bfs_from(v, ...)` reads the OLD `distances[v]` as `d0`, so `new_dist[v]` and `new_parent[v]` are set to the old values, and the patch does not actually shorten v (nor re-parent it to u). Fix it the same way: set `distances[v] = distances[u] + 1; parent[v] = u` before calling `_bfs_from`. (Note: `_bfs_from`'s skip condition `dist[w] <= du + 1` then uses the updated dist[v] for v's neighbors, which is the correct behavior for a BFS from v at its new distance.)

Approaches that will NOT work:
- Calling `_bfs_from(u, ...)` instead: it would skip v because `dist[v] == -1` is not `< d0`... actually it would visit v, but the "settled" skip `dist[w] < d0` and the `dist[w] <= du+1` logic are written around the assumption that `start` already has its final distance; running from u with old distances would re-derive the whole reachable region and is not the intended local patch.
- Changing `_bfs_from` to accept an explicit `start_dist`/`start_parent` parameter is a valid alternative fix (pass `distances[u]+1` and `u`), but the two-line seed in the caller is the minimal change and keeps `_bfs_from`'s contract ("start already has its new distance") intact.
