## FAILURE_DESCRIPTION
Operation: timeout (no result within 3s) on a 3-vertex graph.
Initial graph: only edge (0,1). The 20-operation sequence hangs at sequence_idx 1, i.e. during the 2nd operation, "insert (2, 0)".

State entering that op (after op 1 "insert (1,2)"):
- adj: 0->{1}, 1->{2}, 2->{}
- dist = [0, 1, 2], parent = [None, 0, 1]

Expected after "insert (2,0)": dist = [0, 1, 2] (edge 2->0 does not shorten anything; 0 is the root at dist 0). Actual: the process never returns — infinite loop.

## ROOT_CAUSE
The infinite loop is in `_recompute_region`, triggered by `insert_edge` when the new edge's target is the root.

In `insert_edge`, the guard is:
```python
if dist[u] != -1 and (dist[v] == -1 or dist[u] + 1 < dist[v]):
    dist[v] = dist[u] + 1
    parent[v] = u
    parent, dist = _recompute_region(adj, in_adj, n, parent, dist, [v])
```
For u=2, v=0: dist[2]=2, dist[0]=0, so 2+1 < 0 is False and the branch is NOT taken — this particular op is actually a no-op. So the hang is NOT at op 2's insert itself; the divergence must have already corrupted state at op 1, or the hang is at a later op. Re-tracing op 1 "insert (1,2)": dist[1]=1, dist[2]=-1, so 1+1 < -1 is False but dist[2]==-1 is True, so the branch IS taken: dist[2]=2, parent[2]=1, then `_recompute_region(..., [2])` with min_sd = dist[2] = 2.

Inside `_recompute_region` the relaxation loop is:
```python
while q:
    u = q.popleft()
    du = new_dist[u]
    for v in adj[u]:
        if dist[v] != -1 and dist[v] < min_sd:
            continue  # unaffected, cannot change
        cand = du + 1
        if v not in new_dist or cand < new_dist[v]:
            new_dist[v] = cand
            new_parent[v] = u
            q.append(v)
```
The termination argument for this loop is that `new_dist[v]` strictly decreases each time v is re-enqueued, and distances are bounded below by 0. That holds only if the seed distances are already the TRUE (final) distances. Here the seed is v=2 with dist[2]=2, which is correct, so op 1 terminates fine.

The real problem: the loop's "unaffected" test `dist[v] < min_sd` uses the OLD `dist` array, but the loop can also re-enqueue a vertex with a LARGER distance than before in the delete path. In `delete_edge`'s `best != -1` branch, the seed v is given `dist[v] = best` where `best` can be LARGER than v's old distance (the tree edge was cut and the replacement parent is farther). Then in `_recompute_region`, `min_sd = best` (larger), and the relaxation loop can assign `new_dist[v] = cand` where cand > old dist[v] — i.e. distances can INCREASE. The condition `cand < new_dist[v]` still bounds each vertex's new_dist from above by its first assignment, so the loop still terminates... but the "unaffected" skip `dist[v] < min_sd` is then WRONG: a vertex w with old dist[w] < min_sd but whose true new distance is >= min_sd (because its only short path went through the cut subtree) is skipped as "unaffected" and keeps a stale, too-small distance. That is a correctness bug, not a hang.

Given the reported symptom is a hang (timeout), the only unbounded loop in the code is the `while q` in `_recompute_region`. For it to be infinite, `cand < new_dist[v]` must hold forever, which requires `du` to keep decreasing — impossible with integer distances bounded below by 0 — UNLESS a vertex is enqueued with a distance that is later re-read from the mutated `dist` list. Note that `insert_edge` mutates `dist[v]` BEFORE calling `_recompute_region`, and `_recompute_region` reads `dist[s]` for seeds and `dist[u]` for the unaffected test on the SAME list it later overwrites in the apply phase. Within a single call this is consistent. However, in the delete `best == -1` branch, the code sets `dist[x] = -1` for all affected vertices, then seeds some of them with `dist[x] = dist[u2] + 1`, then calls `_recompute_region` with `min_sd = min(dist[s] for s in seeds)`. If a seed s has dist[s] = -1 (possible if the seed loop's `break` left some affected vertex at -1 and it was still added... no, seeds are only added when dist is set).

I cannot conclusively pin the exact op that loops from static analysis alone; the trace above shows op 1 and op 2 both terminate. The hang is most plausibly at a later op in the 20-op sequence where the delete `best != -1` path seeds `_recompute_region` with a vertex whose `dist` was set to a value, and the relaxation loop re-enqueues vertices with strictly decreasing `new_dist` values that are re-derived from the mutated shared `dist` list — the apply phase writes `dist[v] = new_dist[v]` for ALL v with old dist >= min_sd, including vertices that were never in the queue, setting them to -1, which can make a subsequent seed's `dist[s]` read -1 and `min_sd = -1`, after which the unaffected test `dist[v] < -1` is never true and the loop relaxes over the whole graph repeatedly... but still bounded.

Honest conclusion: I ruled out `_bfs_full` (provably terminates), the descendant-collection loop (tree, terminates), and the seed-collection loops (bounded by n). The only candidate for an infinite loop is the `while q` relaxation in `_recompute_region`, and the mechanism requires the shared `dist` list to be mutated between the seed-distance read and the loop in a way that lets `cand < new_dist[v]` hold unboundedly. I could not reproduce the exact op statically; the reflection below states the structural defects that must be fixed regardless.

## REPAIR_HINTS
1. Do not mutate `dist`/`parent` in place before calling `_recompute_region`, and do not let `_recompute_region` read the old `dist` for its "unaffected" test while also overwriting it. Make `_recompute_region` take the pre-update distances as a separate snapshot (or compute min_sd from the seed values passed in, not from the live list).
2. The "unaffected" predicate `dist[v] < min_sd` is unsound for deletions where the seed's new distance is LARGER than its old one: vertices with old dist < min_sd can still lose their short path through the cut subtree. The region-recompute approach as written only handles distance DECREASES (inserts). For the delete `best != -1` branch, either (a) fall back to `_bfs_full` (simplest, correct), or (b) properly identify the affected set as {v} ∪ {descendants of v in the tree} and recompute distances for exactly that set using a Dijkstra/BFS restricted to it, with boundary vertices (in-neighbors outside the set) as sources.
3. The delete `best == -1` branch already ends with a full `_bfs_full` "for safety", which makes all the preceding region work dead code — remove it or remove the full BFS, but keep the full BFS to guarantee termination and correctness.
4. Simplest correct repair that keeps the code small: in `delete_edge`, whenever `parent[v] == u` (tree edge deleted), just run `_bfs_full(adj, n)` and return. In `insert_edge`, keep the current shortcut (it is correct for decreases) or also fall back to `_bfs_full`. This eliminates `_recompute_region` entirely, removes the hang, and satisfies the invariant; the "avoid full recompute" goal can be pursued in a later generation with a properly bounded affected-set recompute.
5. Approaches that will NOT work: patching only the `cand < new_dist[v]` condition, or adding a visit counter to the relaxation loop — the loop's termination is not the fundamental issue; the unsound unaffected-set predicate and the in-place mutation of the shared `dist` list are. Any fix that keeps the `dist[v] < min_sd` skip for the delete path will remain incorrect on cases where a non-seed vertex's distance must increase.
