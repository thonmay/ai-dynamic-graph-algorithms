## FAILURE_DESCRIPTION

3-vertex directed graph (0/1 adjacency matrix):

```
0 -> 1
1 -> 0
2 -> 0, 2 -> 1
```

Root = 0. After `init`, the BFS state is: dist = [0, 1, -1], parent = [None, 0, None], rad = [0, 1, 0].

Failing update: `delete_edge(graph, (0, 2), state)` — i.e. delete the edge 0->2.

Expected after the update: dist = [0, 1, -1], parent = [None, 0, None] (vertex 2 is unreachable; the graph in the case is the post-deletion graph, which has no 0->2 edge).

Actual: `result = [None, 0, 0]` — the verifier reports vertex 2 with distance 1 and parent 0, i.e. the state still claims 2 is reachable at distance 1 via parent 0, even though the edge 0->2 no longer exists.

## ROOT_CAUSE

The bug is in `delete_edge`. The deleted edge (0, 2) is NOT the BFS parent edge of its head: `parent[2]` is `None` (vertex 2 is unreachable), so the early-exit test

```python
if parent[v] != u:
    # Deleted edge is not v's BFS parent. ... nothing changes.
    return state
```

fires and the function returns immediately. That early exit is only safe when the head `v` is reachable (its parent chain still provides a shortest path, and deletion cannot shorten distances). Here `v = 2` is unreachable, so the deleted edge 0->2 is a *forward* edge from a reachable vertex (0, dist 0) to an unreachable vertex (2, dist -1). Removing it can make `v` (and everything reachable only through `v`) lose reachability, but the code does no reachability propagation at all.

Concretely, the state before the delete must have had `dist[2] = 1, parent[2] = 0` (the edge 0->2 was present and made 2 reachable). After `adj[0].discard(2)` and `rad[2] -= 1`, the early exit leaves `dist[2] = 1` and `parent[2] = 0` stale: parent 0 no longer has an edge to 2, so the invariant "parent[v] is a true in-neighbor" is violated, and the true distance of 2 is -1.

The same latent bug exists in the `need_fix` path: the local repair only recomputes distances for vertices in the BFS-tree subtree of `v`, and the multi-source BFS seeds only from in-neighbors *outside* the subtree. If a subtree vertex's only remaining in-neighbor is a vertex that is itself unreachable (dist -1), it is never seeded and stays at its stale distance. The repair must also handle vertices whose only support comes from reachable outside-subtree vertices, and it must mark vertices unreachable when no such support exists — which it does for the subtree, but the early exit skips even that.

## REPAIR_HINTS

Smallest concrete fix in `delete_edge` (before the `parent[v] != u` early exit):

1. Handle the case where the head `v` is unreachable (`dist[v] == -1`) but the tail `u` is reachable (`dist[u] >= 0`). Deleting `u -> v` may make `v` and its descendants unreachable. Do a local reachability repair:
   - Collect the set `S` of vertices that are currently reachable and whose reachability might be affected: start from `v` and take all descendants in the current BFS tree (same `children`/`subtree` collection already in the code), but restricted to vertices with `dist >= 0`.
   - For each `x` in `S`, recompute whether it has any in-neighbor `a` with `dist[a] >= 0` and `x in adj[a]` (and `a` not in `S`, or `a` in `S` still supported). Vertices with no such in-neighbor become unreachable (`dist = -1`, `parent = None`), and their descendants in `S` must be re-checked (iterate to a fixpoint, or run a BFS from the still-supported vertices).
   - Update `rad` for affected vertices.

2. Alternatively (simpler and still local): after any deletion where `dist[v] == -1` and `dist[u] >= 0`, run a BFS from the root restricted to vertices whose reachability is in question (the subtree of `v` in the BFS tree, plus `v` itself), using the current `adj`. Any vertex in that set not reached by this BFS becomes unreachable. This is O(size of affected subtree) and preserves the "no full recompute" goal.

3. Also fix the `need_fix` path's seeding: when seeding the multi-source BFS for the subtree, include in-neighbors `a` with `dist[a] >= 0` (reachable) outside the subtree — the current code does this, but it should also verify that vertices in the subtree with no reachable in-neighbor at all (including from within the subtree after propagation) are marked unreachable. The current `nd[x] == INF` check does this, but only for vertices in the subtree; ensure the subtree collection includes all descendants, not just those with `rad == 0`.

Approaches that will NOT work:
- Simply checking `rad[v] == 0` before the early exit: `rad[v]` counts in-neighbors at `dist[v]-1`, which for unreachable `v` (dist -1) is meaningless (no vertex has dist -2). The reachability of `v` depends on whether it has ANY in-neighbor with `dist >= 0`, not just at `dist[v]-1`.
- Recomputing the full BFS on every deletion: correct but violates the "avoid full recompute" research goal.
