## FAILURE_DESCRIPTION

Failing operation: `delete (0, 2)` on a 4-vertex directed graph (sequence_idx 2, i.e. the 3rd op).

Graph (0/1 adjacency):
- 0 -> 3
- 1 -> 2
- 2 -> 0, 1, 3
- 3 -> 1

Expected final state: parent = {0:None, 3:0, 1:3, 2:1}, distances = {0:0, 3:1, 1:2, 2:3}.
Actual state: distances = [0, 2, -1, 1], parent[2] = None. Vertex 2 is reported unreachable (dist -1) but the true BFS distance is 3 (0->3->1->2).

CRITICAL OBSERVATION: the failing op itself is a NO-OP. Edge (0,2) is not present in the graph (graph[0][2]=0), and parent[2]=1 != 0, so `delete_edge` takes the early-return branch and mutates nothing. Therefore the state was ALREADY corrupted before this operation — vertex 2 was already at dist -1 when entering op 2. The bug is in an earlier update (op 0 or 1), which I cannot see in the task payload. The delete path is not the direct cause.

## ROOT_CAUSE

The corruption pattern (one reachable vertex wiped to -1 while 0,1,3 keep correct distances) is the signature of the "Apply" loop in `_recompute_region` (used by `insert_edge`):

```python
for v in range(n):
    if dist[v] != -1 and dist[v] < min_sd:
        continue  # unaffected
    if v in new_dist:
        dist[v] = new_dist[v]
        parent[v] = new_parent[v]
    else:
        dist[v] = -1
        parent[v] = None
```

This marks EVERY vertex with `dist[v] >= min_sd` (or already -1) as unreachable unless it was discovered by the restricted BFS. The restricted BFS is seeded only with (a) the improved vertex `v` and (b) affected vertices that have an in-neighbor with `dist < min_sd`, and it only relaxes edges out of vertices it has enqueued.

The soundness argument for "only v's descendants can change on an insertion" is FALSE in general. When an insertion improves v to distance d (min_sd = d), a vertex w at distance >= d that is reachable but whose shortest path does NOT go through v, and whose in-neighbors are all at distance >= d (so w is not enqueued by the scan) and which is not reachable from the seeds via the restricted relaxation, is never added to `new_dist` and is therefore wiped to -1. The restricted BFS does not guarantee it reaches every vertex that was reachable at distance >= min_sd; it only reaches the closure of the seeds plus the scan-enqueued boundary. Any reachable vertex outside that closure is destroyed.

I traced the delete path and ruled it out as the direct cause (it early-returns here). I could not conclusively reconstruct which of op 0/1 triggered the wipe because those operations are not in the payload, but the wipe-to--1 of a single reachable vertex with the rest intact is exactly what this Apply loop produces.

## REPAIR_HINTS

The smallest correct fix: do NOT let `_recompute_region` decide reachability for the whole "affected" region by absence from `new_dist`. Two viable options:

1. (Recommended, simplest) On an insertion that improves v, the only distances that can change are DECREASES, and a vertex's distance can only decrease if it is reachable from v in the new graph. So restrict the "wipe" to vertices that are actually descendants of v in the OLD tree AND are not re-reachable. Concretely: after the restricted BFS, only set dist[x] = -1 for x that (a) was in v's old subtree and (b) is not in new_dist. Vertices outside v's old subtree must keep their old (still-valid) distance/parent untouched. This restores the invariant because an insertion cannot increase any distance, so non-descendants are provably unaffected.

2. (Safest, still local) After the restricted BFS, for any vertex x with dist[x] >= min_sd that is not in new_dist, verify reachability by checking whether x has an in-neighbor y with a valid (already-correct) distance dist[y] != -1 and dist[y]+1 == dist[x]; if so keep x reachable (re-parent to y), else mark -1. This avoids the blanket wipe.

Do NOT "fix" this by making the restricted BFS a full BFS over all vertices with dist >= min_sd — that still relies on the same flawed closure and is O(m) per update, defeating the goal. Do NOT change the delete early-return; it is correct for this case. The real defect is the over-broad `else: dist[v] = -1` in `_recompute_region`'s Apply loop, which must be scoped to v's old subtree (option 1) or guarded by an explicit reachability check (option 2).
