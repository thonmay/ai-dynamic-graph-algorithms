- 0 -> 3
- 1 -> 2
- 2 -> 0, 2 -> 1, 2 -> 3
- 3 -> 1

Failing update: `delete_edge(graph, (0,2), state)` at sequence index 2.

## ROOT_CAUSE
The bug is in `_repair_after_tree_edge_delete`. The repair assumes that after deleting the tree edge of `v`, every subtree vertex's new distance is determined by (a) an in-neighbor OUTSIDE the subtree, or (b) its old-tree parent inside the subtree. That assumption is false: a subtree vertex can be re-parented to a NON-tree in-neighbor that is ALSO inside the subtree (a cross/back edge within the subtree), and that path can be the vertex's only remaining route to the root.

Concrete trace. Before the delete, the maintained tree was 0 -> 3 -> 1 -> 2 (parent[2]=1, parent[1]=3, parent[3]=0; dist = [0,2,3,1]). Edge (0,2) is a non-tree edge, so `delete_edge` takes the early-return branch `if parent[v] != u: return ...` with u=0, v=2 (parent[2]==1 != 0). The tree is still valid and distances [0,2,3,1] are correct for the pre-delete graph — so far so good.

But the failing case's expected state corresponds to the graph AFTER (0,2) is gone, and the verifier's "expected" tree is 0->3->1->2 with dist[2]=3 — which is exactly what the candidate's state already holds. The actual reported result is distances [0,2,-1,1] with parent[2]=None, i.e. vertex 2 was dropped. That means the delete that actually triggered the repair was the tree edge of 2, i.e. the sequence must have had parent[2]==0 at the moment of `delete (0,2)` (the tree was 0->2->1->3 or 0->2->3->1, with 0->2 as a tree edge). In that case `_repair_after_tree_edge_delete(adj, in_adj, n, parent, dist, v=2)` runs with subtree = {2, 1, 3} (all of 2's old descendants: 1 and 3, since 2->1 and 2->3 were tree edges, and 3->1).

Inside the repair, `sub_set = {2,1,3}`. For each subtree vertex the code only looks at in-neighbors with `if u in sub_set: continue` — i.e. it DISCARDS every in-neighbor that is inside the subtree. For vertex 2: in_adj[2] = {1} (edge 1->2). 1 is in sub_set, so it is skipped; in_sub[2] = None. For vertex 1: in_adj[1] = {2,3}; both in sub_set, skipped; in_sub[1] = None. For vertex 3: in_adj[3] = {0,2}; 0 is outside, dist[0]=0, so in_sub[3] = 1.

Then processing: new_dist[2] = -1 (in_sub[2] is None). new_dist[3] = 1 (parent 0). For child 1 of 3: best = in_sub[1] = None; cand = new_dist[3]+1 = 2, so new_dist[1] = 2, parent 3. For child 2 of 1: best = in_sub[2] = None; cand = new_dist[1]+1 = 3, so new_dist[2] = 3, parent 1.

Wait — that trace gives dist[2]=3, which is correct. Let me re-examine: the reported actual is [0,2,-1,1], i.e. dist[2]=-1, dist[1]=2, dist[3]=1. That matches a repair where 2 was NOT reached from 1. That happens if 1 was NOT a child of 3 in the old tree, i.e. the old tree was 0->2->1 and 0->2->3 with 1 and 3 as siblings under 2 (parent[1]=2, parent[3]=2). Then subtree = {2,1,3}, and the child loop from y=2 processes w=1 and w=3:

- w=3: in_sub[3]=1 (via 0); new_dist[3]=1, parent 0.

Hmm, dist[1]=2 in the actual. That means 1 WAS reached at distance 2. The only way: 1 got new_dist 2 from a parent at distance 1. In the child loop, w=1 gets cand = dy+1 where dy = new_dist[2]. If new_dist[2] were 1, cand=2. But new_dist[2] = in_sub[2] = None -> -1. Unless... the old tree was 0->2->3->1 (parent[3]=2, parent[1]=3). Child 1 of 3: in_sub[1]=None (in-neighbors 2,3 in sub_set); cand = new_dist[3]+1 = 2 -> new_dist[1]=2, parent 3. Result: dist=[0,2,-1,1], parent[2]=None. THIS MATCHES the reported actual exactly.

So the pre-delete tree was 0->2->3->1 (dist=[0,3,1,2]... wait dist[2]=1, dist[3]=2, dist[1]=3). After deleting tree edge (0,2): vertex 2's only in-neighbor is 1 (edge 1->2), which is INSIDE the subtree. The true new BFS: 0->3 (dist 1), 3->1 (dist 2), 1->2 (dist 3). So 2 should be reachable at distance 3 via the in-subtree edge 1->2. But the repair's `in_sub` computation skips all in-neighbors inside `sub_set`, so it never considers 1->2 as a way to reach 2, and since 2 is the subtree root (no old-tree parent to fall back on), it concludes new_dist[2] = -1.

The responsible lines:
```python

    for x in subtree:
        best = None
        for u in in_adj[x]:
            if u in sub_set:

```
and the subtree-root handling:
```python

        new_parent[v] = None
```
The root `v` of the subtree has no old-tree parent to fall back on, so if its only remaining in-neighbor is inside the subtree (a back/cross edge from a descendant), the repair wrongly marks it unreachable.

## REPAIR_HINTS
The repair must allow subtree vertices to be re-parented to in-neighbors that are ALSO inside the subtree, not just outside it. The current "only outside-subtree in-neighbors + old-tree parent" model is incomplete: a vertex's new shortest path can enter the subtree at one vertex and then travel through in-subtree edges to reach others.

Smallest correct fix: after computing the initial "entry" distances for subtree vertices from outside-subtree in-neighbors (the current `in_sub`), run a proper BFS/Dijkstra INSIDE the subtree using the actual graph edges, seeded with those entry distances. Concretely:
1. For each x in subtree, entry[x] = min{ dist[u]+1 : u in in_adj[x], u not in sub_set, dist[u] != -1 } (or +inf).
2. Run a BFS (all edges unit weight, so a simple queue in increasing-distance order, or a Dijkstra with a heap) over the subgraph induced by the subtree, starting from all vertices with finite entry, relaxing along edges (y->w) where both y and w are in the subtree. The resulting distances are the true new distances for subtree vertices; parent is the predecessor on the shortest path.
3. Vertices with no finite distance become unreachable (dist -1, parent None).

This handles the failing case: entry[3]=1 (via 0), entry[1]=inf, entry[2]=inf; internal BFS: 3->1 gives dist[1]=2, 1->2 gives dist[2]=3. Correct.

Do NOT try to fix this by only special-casing the subtree root `v` (e.g. "if v has an in-subtree in-neighbor, keep it reachable") — the same bug applies to any subtree vertex whose best new parent is an in-subtree non-tree edge, not just the root. The internal-BFS fix is the minimal change that restores the invariant for all subtree vertices.

Note: the non-tree-edge early return in `delete_edge` (`if parent[v] != u: return ...`) is correct and not the source of this failure; do not change it.
