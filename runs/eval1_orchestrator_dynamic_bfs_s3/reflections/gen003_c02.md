## ROOT_CAUSE
In `delete_edge`, the in-neighbor scan for a replacement parent does not verify that the candidate parent is reachable without going through v. When the old BFS tree has v as an ancestor of the candidate in-neighbor (i.e., the in-neighbor is in v's subtree), using it as a "new parent" creates a cycle and an invalid distance.

Specifically, the lines:
```python
for w in in_adj[v]:
    dw = distances[w]
    if dw != -1 and (best_d == -1 or dw < best_d):
        best_d = dw
        best_p = w
```
pick w=2 (dist 2) as the new parent of v=1, but 2's only path from root goes through 1 (parent[2]=1). This creates the cycle 1→2→1 and assigns dist[1]=3, dist[2]=2, which is inconsistent.

## REPAIR_HINTS
The in-neighbor scan in `delete_edge` must exclude in-neighbors that are in v's old BFS subtree (i.e., vertices whose path from root goes through v). The simplest fix: before scanning in_adj[v], collect the set of vertices in v's old subtree (walk parent pointers downward from v), and skip any in-neighbor w that is in that set.

Concretely, in `delete_edge`, after confirming `parent[v] == u and v != 0`:
1. Build `subtree = {v}` by walking all descendants of v in the current BFS tree (BFS/DFS following parent pointers in reverse, i.e., for each x, if parent[x] is in subtree, add x).
2. In the in-neighbor scan, skip any w where w is in `subtree`.
3. If no valid in-neighbor remains, call `_mark_unreachable(v, ...)` as before.

Alternatively, a simpler but less efficient fix: after computing best_p, verify that best_p is not a descendant of v in the current tree (walk parent pointers from best_p up to root; if you hit v, reject). If rejected, fall through to `_mark_unreachable`.

The `_mark_unreachable` function itself also has a latent bug: the "rescue" loop checks `if dist[w] == -1` but at that point dist still holds the OLD distances (the patch hasn't been applied yet), so the condition is almost never true for vertices that were just marked. The rescue logic should check whether w has an in-neighbor outside the marked set with a valid old distance, not whether w's old distance is -1. However, fixing the subtree-exclusion in `delete_edge` is the minimal fix for this failing case.
