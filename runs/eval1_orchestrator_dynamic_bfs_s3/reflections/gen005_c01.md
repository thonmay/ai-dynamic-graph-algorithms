4-vertex directed graph (post-state, 0/1 adjacency matrix):
- 0 -> 3
- 1 -> 2
- 2 -> 0, 2 -> 3
- 3 -> 1, 3 -> 2

Operation: `delete_edge(graph, (0, 2), state)` at `sequence_idx: 0` (first update after init).

Expected result (BFS from root 0 on the post graph):
- dist = [0, 2, 2, 1], parent = [None, 3, 3, 0] (paths 0->3->1, 0->3->2).

Actual result returned:
- dist[2] = 3, parent[2] = 1 (reported as "your_distance: 3, your_parent: 1").
- The parent chain 2 <- 1 <- 3 <- 0 is a valid path of length 3, but the true BFS distance of 2 is 2 (via 0->3->2). The invariant "parent sits one BFS distance closer" is violated: dist[2] = 3 but dist[parent[2]] = dist[1] = 2, so dist[2] should be 3 only if no shorter path exists — but 0->3->2 gives distance 2.

## ROOT_CAUSE
The trace is **inconclusive** from the given information alone. I traced two possible pre-states and neither reproduces the wrong output:

**Hypothesis A: pre-graph had edge 0->2 (the delete is a real deletion).**
- init on pre-graph: dist = [0, 2, 1, 1], parent = [None, 3, 0, 0].
- `delete_edge(0, 2)`: `parent[2] == 0 == u`, so the recompute path is taken.
- `_recompute_region_increase(adj, in_adj, 4, parent, dist, v=2)`:
  - Region = {2} (no vertex has parent == 2 in the old tree).
  - Seeds: in_adj[2] after delete = {3} (3->2 remains). dist[3] = 1 (outside region). new_dist[2] = 2, new_parent[2] = 3.
  - BFS from 2: adj[2] = {0, 3}, both outside region. No further discoveries.
  - Result: dist = [0, 2, 2, 1], parent = [None, 3, 3, 0]. **CORRECT.**

**Hypothesis B: pre-graph did NOT have edge 0->2 (the delete is a no-op).**
- init on the shown graph: dist = [0, 2, 2, 1], parent = [None, 3, 3, 0].
- `delete_edge(0, 2)`: `adj[0].discard(2)` is a no-op. `parent[2] = 3 != 0 = u`, so early exit.
- Returns unchanged state: dist = [0, 2, 2, 1], parent = [None, 3, 3, 0]. **CORRECT.**

Neither hypothesis produces the wrong output (dist[2]=3, parent[2]=1). The wrong output corresponds to a BFS tree computed on a graph **without edge 3->2** (path 0->3->1->2 gives dist[2]=3). This means the internal `adj[3]` in the state did not contain 2 at the time of the delete.

**Most likely root cause:** The test harness called `init` on a pre-state graph that lacked edge 3->2 (and possibly also lacked 0->2), making the "delete (0,2)" a no-op. The early-exit in `delete_edge` then returned the init state, which was computed on the pre-graph (without 3->2), not the post-graph. The candidate's code is correct for a single update from a consistent state; the failure is a **state/graph mismatch** — the state's internal `adj` does not reflect the post-update graph.

The responsible code is the early-exit in `delete_edge`:
```python
    if parent[v] != u:
        return {
            'parent': parent,
            'distances': dist,
            'adj': adj,
            'in_adj': in_adj,
            'n': n,
        }
```
This returns the state unchanged, assuming the tree is still valid. If the state was initialized on a graph different from the post-update graph, this assumption is false.

## REPAIR_HINTS
1. **The candidate's incremental logic is sound for a single update from a consistent state.** The bug is likely a harness/state mismatch, not a logic error in the BFS recompute. Verify that `init` is called on the correct pre-state graph (the graph BEFORE the update, with the edge to be deleted/inserted present/absent accordingly).

2. **Defensive fix in `delete_edge`:** After the early-exit condition `parent[v] != u`, add a sanity check that the tree is still consistent with the current `adj`. Specifically, verify that for every vertex w with `parent[w] != None`, the edge `parent[w] -> w` exists in `adj`. If not, fall back to a full BFS recompute:
   ```python
   if parent[v] != u:
       # Sanity check: verify tree edges are still real edges
       valid = True
       for w in range(n):
           if parent[w] is not None and w not in adj[parent[w]]:
               valid = False
               break
       if valid:
           return { ... }  # early exit
       # else: fall through to full recompute
   ```

3. **Alternative robust fix:** In `delete_edge`, if the deleted edge is not the tree edge of v, still verify that v's parent is a true in-neighbor in the updated `in_adj`. If `parent[v]` is not in `in_adj[v]` after the delete, the tree is broken and a recompute is needed.

4. **Approaches that will NOT work:** Simply re-running `_recompute_region_increase` when `parent[v] != u` does not help, because the region is defined by the old tree edges and the tree is already inconsistent. A full BFS recompute (`_bfs_full`) is the safe fallback when the tree's consistency cannot be verified incrementally.

5. **If the harness is correct and init is called on the right pre-graph:** The candidate should pass. Re-examine the test setup to confirm the pre-state graph matches the operation (for a delete, the pre-graph must contain the edge being deleted).
