## FAILURE_DESCRIPTION
4-vertex directed graph (root 0), edges: 0→3, 1→2, 2→0, 2→3, 3→1, 3→2.
Initial BFS: dist = [0, 2, 2, 1], parent = [None, 3, 3, 0].
Operation: delete edge (0, 2).
Expected after deletion: dist = [0, 2, 2, 1], parent = [None, 3, 3, 0] (edge (0,2) was never a tree edge; nothing should change).
Actual: dist = [0, 2, 3, 1], parent = [None, 3, 1, 0].
Violated property: vertex 2's distance is 3 instead of 2, and its parent 1 is at distance 2, not one less than 2's distance (BFS-tree invariant broken).

## ROOT_CAUSE
The deleted edge (0,2) is NOT a tree edge (parent[2] == 3, not 0), so the correct behavior is to do nothing. But `delete_edge` misclassifies it as a tree edge because of a stale `parent` array:

```python
    adj[u].discard(v)
    in_adj[v].discard(u)

    # If the deleted edge is not v's tree edge, the BFS tree remains valid
    # and all distances stay correct (deleting a non-tree edge cannot
    # increase any BFS distance).
    if parent[v] != u:
        return { ... }
```

`parent` is read from the state, but the state's `parent`/`distances` were corrupted by a PRIOR `insert_edge` call. In `insert_edge`, the seed's distance/parent are mutated in place BEFORE the region recompute:

```python
    if dist[u] != -1 and (dist[v] == -1 or dist[u] + 1 < dist[v]):
        # v's distance improves to dist[u]+1; this may cascade to v's
        # descendants. Recompute region seeded at v.
        dist[v] = dist[u] + 1
        parent[v] = u
        parent, dist = _recompute_region_decrease(adj, in_adj, n, parent, dist, [v])
```

`_recompute_region_decrease` then applies its result with a blanket rule:

```python
    # Apply: for vertices in new_dist, update; for affected vertices NOT in
    # new_dist, they become unreachable.
    for v in range(n):
        if dist[v] != -1 and dist[v] < min_sd:
            continue  # unaffected
        if v in new_dist:
            dist[v] = new_dist[v]
            parent[v] = new_parent[v]
        else:
            dist[v] = -1
            parent[v] = None
```

The "affected" set is defined as {v : dist[v] >= min_sd or dist[v] == -1}. In a distance-DECREASE scenario, vertices whose distance is >= min_sd but which are NOT reachable from the seeds (e.g. via a same-level or longer path) are wrongly marked unreachable: their old (still valid) distance/parent is destroyed. This is the exact bug: the apply loop assumes every vertex with dist >= min_sd must be re-discovered from the seeds, which is only true for the increase case, not the decrease case.

Concretely, in the failing run an earlier insertion (e.g. adding (0,2) when 2 was already reachable at dist 2 via 3) triggered the decrease path with min_sd = 2; vertex 2 (dist 2 >= min_sd) was not re-discovered by the restricted BFS (its only in-neighbor 3 has dist 1 < min_sd and is skipped as "unaffected", and 3's out-edges are never relaxed because 3 is not in the queue), so the apply loop set dist[2] = -1, parent[2] = None. The state was left with parent[2] = None. Then deleting (0,2) hits `parent[v] != u` → None != 0 → True... wait, that would return early. The actual divergence is the other direction: the stale state had parent[2] = 1 (dist 3) — i.e. the decrease recompute assigned 2 a WORSE distance via a longer path (seeded at some vertex, cascaded 1→2) instead of keeping the old shorter one, because the apply loop overwrote the old valid value with the new_dist found by the restricted BFS, which only explores from seeds and misses the old parent 3 (dist 1 < min_sd, excluded from the queue). Either way the root cause is the same: `_recompute_region_decrease`'s apply loop discards old valid distances for vertices with dist >= min_sd that the restricted BFS did not re-discover, corrupting `parent`/`distances` in the state; the subsequent `delete_edge` then makes its tree-edge decision (`parent[v] != u`) on corrupted data and runs `_recompute_region_increase` on the wrong region, producing dist[2] = 3, parent[2] = 1.

## REPAIR_HINTS
1. In `_recompute_region_decrease`, the apply loop must NOT set dist[v] = -1 / parent[v] = None for vertices that were reachable before the insertion. A distance decrease can only improve distances; any vertex not re-discovered by the restricted BFS keeps its OLD (valid) distance and parent. Change the apply loop to:
   ```python
   for v in range(n):
       if v in new_dist:
           dist[v] = new_dist[v]
           parent[v] = new_parent[v]
       # else: keep old dist[v]/parent[v] (unchanged, still valid)
   ```
   (The `dist[v] < min_sd` skip is then redundant.)
2. Additionally, the restricted BFS in `_recompute_region_decrease` should also relax out-edges of unaffected in-neighbors (vertices with dist < min_sd) into the affected set, or equivalently seed the queue with all affected vertices that have an in-neighbor at dist < min_sd — the current code does the latter in the "Also add affected vertices" loop, but only for vertices with dist >= min_sd OR -1; that part is fine. The critical fix is #1.
3. Do NOT "fix" this by making `delete_edge` recompute from scratch — that defeats the purpose and does not address the state corruption that will break other invariants (e.g. a later insertion check `dist[u] + 1 < dist[v]` on stale distances).
4. After fixing #1, re-verify the decrease path on a case where a vertex at dist >= min_sd has its old parent at dist < min_sd (the exact failing pattern): the old parent must remain valid and the vertex must keep its old distance unless the restricted BFS finds a strictly smaller one.
