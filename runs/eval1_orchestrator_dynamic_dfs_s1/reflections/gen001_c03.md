## FAILURE_DESCRIPTION
Graph: 2x2 all-zero adjacency matrix, root 0. After `init`, state is
parent=[None,None], discover=[0,-1], finish=[1,-1] (vertex 1 unreachable).
Operation: `insert_edge(graph, (0,1), state)` — the matrix now has
graph[0][1]=1, so vertex 1 is reachable from the root.

Expected: parent[1]=0, discover[0]=0, discover[1]=1, finish[1]=2, finish[0]=3
(vertex 1 must be in the DFS forest).
Actual: state returned unchanged — parent=[None,None], discover=[0,-1],
finish=[1,-1]. Vertex 1 is still marked unreachable (discover=-1), so the
verifier's reachability check fails: 1 is reachable from 0 in the current
graph but has no parent/discover/finish.

## ROOT_CAUSE
In `insert_edge`, the first guard is:

```python
    # Edge to an unreachable vertex: no effect on the forest.
    if d[v] == -1:
        return state
```

This is wrong. Inserting u->v where v is currently unreachable can make v
(and every vertex reachable from v) newly reachable from the root, so the
DFS forest must be extended to include them. The comment's premise ("no
effect") only holds if u itself is unreachable AND v is unreachable, or if
u is reachable but v is not — in the latter case the new edge is exactly
what makes v reachable. In the failing case u=0 is reachable (d[0]=0) and
v=1 is not (d[1]=-1), so the early return skips the necessary re-search.

A second latent bug in the same function: if u is unreachable (d[u]==-1)
but v is reachable, the code falls through to the forward-cross branch with
lo=d[u]=-1, hi=f[u]=-1; `_reset_interval(state, -1, -1)` resets nothing and
`_dfs_from(graph, u, state, -1)` starts a search from an unreachable vertex
with a negative counter, corrupting discover/finish times. (Not the cause of
this failure, but the same "unreachable vertex" handling is broken.)

## REPAIR_HINTS
In `insert_edge`, replace the `if d[v] == -1: return state` guard with logic
that distinguishes the cases:

1. If `d[u] == -1` (u unreachable): the new edge cannot make anything
   reachable from the root (u itself is not), so return state unchanged.
   This also fixes the latent negative-counter bug, since the forward-cross
   branch is only reached when u is reachable.
2. If `d[v] == -1` and `d[u] != -1` (u reachable, v not): the new edge makes
   v and its reachable closure newly reachable. Re-search from v (or from u
   over the affected region) to extend the forest: set the new vertices'
   discover/finish/parent via `_dfs_from(graph, v, state, counter)` using a
   counter that continues after the current maximum finish time (e.g.
   counter = max(finish)+1, or simply re-run the search from the root if
   simplicity is preferred at this stage). The new subtree's times must be
   consistent with the existing ones (all new discover times greater than
   existing ones is a valid DFS order, since v was not previously reachable
   and no existing edge points into the new region except the new u->v edge,
   which is a tree edge in the new forest).
3. Keep the existing `d[v] < d[u]` (back edge) and `_is_descendant` (forward
   edge) early returns for the both-reachable case.

Minimal change: change the guard to `if d[u] == -1: return state`, and add a
branch for `d[v] == -1` that runs `_dfs_from(graph, v, state, max(finish)+1)`
to absorb the newly reachable vertices. Note: simply deleting the
`d[v] == -1` guard without handling it is not enough — the forward-cross
branch would then call `_dfs_from(graph, u, ...)` which would not discover v
as a child of u in the required way (it would re-search u's subtree and
retime it, but v's times would be assigned inside u's interval, which is
actually fine for correctness, but the `_retime` call with hi=f[u] would
then retime vertices that were just discovered, breaking the invariant).
The cleanest fix is the explicit new-reachability branch in point 2.
