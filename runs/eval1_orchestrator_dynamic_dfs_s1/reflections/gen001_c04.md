## FAILURE_DESCRIPTION
n=3 directed graph. Old graph (before the update) had edges 0→1, 1→2, 0→2; init produced the DFS chain 0→1→2:
parent=[None,0,1], discover=[0,1,2], finish=[5,4,3].

Update: `delete (1,2)`. New graph has edges 0→1, 0→2.

Expected (any valid DFS of the new graph, e.g. the one the verifier showed): parent={0:None,1:0,2:0}, discover={0:0,1:1,2:3}, finish={1:2,2:4,0:5} — i.e. 2 must be re-parented to 0.

Actual: the candidate returned the OLD state unchanged: parent=[None,0,1], discover=[0,1,2], finish=[5,4,3].

Property violated: the state contract requires "for every vertex reachable from the root, parent[v] is a tree in-neighbor discovered before v". After the deletion, edge 1→2 no longer exists, so parent[2]=1 is not an in-neighbor of 2 in the current graph. The forest is no longer a spanning tree of the current graph.

## ROOT_CAUSE
The deletion branch of `_is_valid_dfs` (the `inserted == False` path) only checks reachability closure:

```python
    # deletion: the old forest was valid for the old graph.  Deleting an edge
    # cannot create a forward-cross edge, so the only way validity can break
    # is if some vertex becomes unreachable.  Check reachability closure.
    reach = [False] * n
    ...
    for w in range(n):
        if reach[w] != (discover[w] != -1):
            return False
    return True
```

The comment's premise is wrong. Deleting an edge cannot create a *forward-cross edge* (true), but it can destroy the **tree** itself: if the deleted edge (u,v) is a tree edge (parent[v] == u), the parent pointer of v (and of every vertex in v's subtree) now points across a non-existent edge, so the maintained structure is no longer a spanning search tree of the current graph at all — Lemma 1's "no forward-cross edges" condition is only a characterization *given* that the structure is still a spanning tree. In this case all vertices remain reachable (0→2 still exists), so the reachability check passes and the stale state is kept, with parent[2]=1 dangling.

The insertion branch has the same class of bug in the opposite direction: when an inserted edge (u,v) has discover[u] != -1 and discover[v] == -1, the code only returns False if *some* vertex reachable from v was previously unreachable — but it never actually re-parents v (or the newly reachable set) into the tree, so even when it does detect the problem and recomputes, that is fine; however when it returns True it keeps a forest that does not span the newly reachable vertices. (In this failing case only the deletion branch is exercised.)

## REPAIR_HINTS
Smallest fix: in the deletion branch of `_is_valid_dfs`, before (or instead of) the reachability check, detect whether the deleted edge is a tree edge:

```python
    if parent[v] == u:
        return False   # tree edge deleted -> subtree rooted at v must be re-searched
```

Returning False triggers the existing full `_dfs(graph)` recompute, which is correct. This single condition fixes the failing case (parent[2]==1==u, so recompute yields parent[2]=0).

For a proper (non-recomputing) repair, the standard Yang et al. deletion procedure is: if (u,v) is a tree edge, let S be the subtree of v in the old forest (all w with discover[v] <= discover[w] < finish[v]); re-search from the boundary — for each vertex x in S, look for an incoming edge from a vertex outside S (or from an ancestor of v) in the new graph, and re-attach the affected sub-subtrees in discovery order, updating discover/finish for the re-searched portion. But the minimal correctness fix is the `parent[v] == u` check above.

Also fix the insertion branch symmetrically: if discover[u] != -1 and discover[v] == -1, the old forest does not span the new reachable set, so return False (recompute) — the current code only returns False if a BFS from v finds a previously-unreachable vertex, which is actually equivalent here (v itself is such a vertex, so it does return False in that case); verify this path is kept, but note the BFS is redundant since v itself has discover[v] == -1 and is reachable from v.

Approaches that will NOT work:
- Relying on the reachability-closure check alone for deletions (the current code): it cannot detect a dangling parent pointer when the subtree stays reachable via another path.
- Checking only "no forward-cross edges" after a deletion: the stale state in this case actually passes the interval test for all existing edges (0→1: 0<1<4<5, 0→2: 0<2<3<5), so the forward-cross check alone would also wrongly accept it. The tree-edge check is essential.
