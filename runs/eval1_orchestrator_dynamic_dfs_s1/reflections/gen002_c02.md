## FAILURE_DESCRIPTION
Failing case: n=2, initial graph is the empty 2x2 matrix (no edges). `init`
produces state `parent=[None, None]`, `discover=[0, -1]`, `finish=[1, -1]`
(vertex 0 is the root, discover 0 / finish 1; vertex 1 is unreachable).
Operation: `insert_edge(graph, (0, 1), state)` on the graph with
`graph[0][1] = 1`.

- Expected (a valid DFS forest of the new graph): `parent={0: None, 1: 0}`,
  `discover={0: 0, 1: 1}`, `finish={1: 2, 0: 3}` (i.e. 1 nested inside 0's
  interval: 0 < 1 < 2 < 3).
- Actual returned: `parent=[None, 0]`, `discover=[0, 1]`, `finish=[2, 3]`.

The parent pointer is correct, but the finish times are swapped: the result
has `finish[0]=2 < finish[1]=3`, so vertex 1 is NOT a descendant of 0. The
verifier's contract requires `discover[u] < discover[v] < finish[v] <
finish[u]` for the tree edge 0->1, which is violated.

## ROOT_CAUSE
The bug is in the `d[v] == -1` branch of `insert_edge` (the "v newly
reachable" case). The code does:

```python
counter = max(f) + 1
_dfs_from(graph, v, state, counter)
state['parent'][v] = u
_retime(state, d[u], max(f) + 1)
```

Tracing on the failing case: `f = [1, -1]`, so `max(f) + 1 = 2`.
`_dfs_from(graph, 1, state, 2)` sets `discover[1]=2`, `finish[1]=3`
(vertex 1 has no outgoing edges, so it finishes immediately). Then
`_retime(state, d[u]=0, hi=2)` is called.

`_retime` selects `verts = [v for v in range(n) if lo <= discover[v] < hi]`
= `[v for v in range(2) if 0 <= discover[v] < 2]`. With
`discover = [0, 2]`, only vertex 0 qualifies (vertex 1 has discover 2, which
is NOT `< hi=2`). So `_retime` just reassigns `discover[0]=0`,
`finish[0]=2` — it never touches vertex 1. The intended "absorb v's subtree
into u's interval" never happens: vertex 1 keeps its times (2, 3) which lie
OUTSIDE u's interval [0, 2), producing the invalid order
`finish[0]=2 < finish[1]=3`.

The root cause is that the re-time window is computed as `max(f) + 1` using
the finish array BEFORE the new search, so it equals the old
`finish[u]` (2) and excludes the freshly discovered vertices whose discover
times start at exactly that value. The comment says "re-time u's interval to
absorb them", but the `hi` bound is off by the size of the newly added
subtree.

## REPAIR_HINTS
Smallest fix: in the `d[v] == -1` branch of `insert_edge`, compute the
re-time window AFTER the new search, using the updated finish array:

```python
counter = max(f) + 1
_dfs_from(graph, v, state, counter)
state['parent'][v] = u
_retime(state, d[u], max(f) + 1)   # max(f) now includes the new subtree
```

i.e. move the `max(f) + 1` evaluation to after `_dfs_from` (e.g.
`hi = max(state['finish']) + 1` after the search, then
`_retime(state, d[u], hi)`). On the failing case this gives
`hi = max([1, 3]) + 1 = 4`, so `_retime(state, 0, 4)` reassigns
`discover[0]=0, discover[1]=1, finish[1]=2, finish[0]=3` — exactly the
expected valid order.

Caveat for the repair role: `max(f)` over the whole array is O(n) and is
only correct because the new subtree is the last-discovered block; a cleaner
formulation is to track the counter returned by `_dfs_from` and re-time
`[d[u], counter_after)` — but note that `counter_after` from `_dfs_from`
counts both discover and finish stamps, so the window must be expressed in
discover-time units (the new vertices' discover times span
`[old_max_finish+1, old_max_finish+1+k)` for k new vertices, and their
finishes span the next k slots). The simplest correct change is the
post-search `max(f) + 1` bound above.

Approaches that will NOT work:
- Re-timing with the pre-search `max(f) + 1` bound (the current code) —
  provably excludes the new vertices, as traced above.
- Simply setting `finish[u] = max(f)` after the search without re-timing —
  leaves `discover[1]` outside u's discover interval and breaks the
  contiguous-counter invariant the verifier relies on.
- Re-running a full DFS from the root would be correct but defeats the
  research goal of avoiding full recomputation; use it only as a fallback
  sanity check, not as the fix.
