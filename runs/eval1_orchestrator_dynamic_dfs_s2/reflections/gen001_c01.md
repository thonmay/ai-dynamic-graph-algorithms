## FAILURE_DESCRIPTION

Graph (3x3, directed), initial state after `init`:
- parent = [None, 0, 0], discover = [0, 1, 2], finish = [3, 2, 3]
- i.e. DFS tree 0 -> 1, 0 -> 2 (edge 0->1 explored first, then 0->2).

Update: `delete_edge(graph, (0, 2), state)` — removes tree edge 0->2.
After the update the only edge is 0->1, so the correct DFS is:
- parent = [None, 0, None], discover = [0, 1], finish = [3, 2]
- vertex 2 must be UNREACHABLE (no discover/finish entry, or -1).

Actual result returned:
- parent = [None, None, None], discover = [0, 1, 3], finish = [2, 2, 4]

Violations:
1. parent[1] is None, but 1 is reachable from 0 (edge 0->1 exists) — the
   verifier requires parent[1] = 0.
2. Vertex 2 is reported as reachable (discover[2]=3, finish[2]=4) although
   it is unreachable in the current graph.

## ROOT_CAUSE

The bug is in `_reattach` (called from `delete_edge` when the deleted edge is
a tree edge). The "fixed vertex" fast-forwarding logic is fundamentally
incompatible with the renumbering it performs:

```python
# fixed = finished, not ancestor of v
fixed = [False] * n
for w in range(n):
    if w not in anc and old_fin[w] != -1:
        fixed[w] = True
```

In this case v = 2, anc = {2, 0}, so vertex 1 (old disc 1, fin 2) is marked
fixed and pre-marked `visited[1] = True` with old numbers disc=1, fin=2.

Then the re-DFS from root 0 runs:
- discover 0 at new clock 0; clock=1; `advance_clock()` sees
  `fixed_disc_map = {1: 2}` and jumps clock to 2.
- Scanning 0's adjacency: w=1 is `visited` (fixed), so it is SKIPPED —
  `new_parent[1]` is never set (stays None). w=2 is not in adj[0] anymore.
- 0 finishes at clock 2.
- The "unreachable" tail loop then visits 2: disc=3, fin=4.

So the renumbered DFS (root gets new number 0) collides with the fixed
vertex's OLD number (1), and `advance_clock` skips over it, causing the
re-DFS to never discover vertex 1. The invariant "fixed vertices keep their
old numbers while the rest are renumbered from a single counter" is
unsound: a fixed vertex's old interval [old_disc, old_fin) can lie inside
the region being renumbered (here 1's interval [1,2) is inside 0's new
interval), so the counter cannot both "jump over" it and keep the DFS
nesting valid.

The responsible lines:
- `fixed[w] = True` for every finished non-ancestor vertex (marks 1 fixed),
- `visited[w] = True` for fixed vertices (makes 1 undiscoverable),
- `advance_clock()` jumping the clock past `fixed_disc_map` entries
  (skips number 1, which is where the re-DFS would have discovered 1).

## REPAIR_HINTS

Smallest concrete fix: in `_reattach`, do NOT fast-forward fixed vertices.
After deleting a tree edge u->v, simply re-run a full DFS from root 0 over
the current `adj` (equivalently, call `_recompute`-style logic but without
rebuilding adj, since `delete_edge` already did `state['adj'][u].discard(v)`).
Concretely, replace the body of `_reattach` with a plain iterative DFS from
root 0 over `state['adj']` that assigns fresh parent/discover/finish to all
reachable vertices and leaves unreachable vertices with discover/finish = -1
and parent = None (matching `_dfs_full`'s convention, but without the
multi-source loop — only root 0 starts a search; other components stay
unvisited).

Key details for the fix:
- Unreachable vertices must get discover = finish = -1 (or be omitted), NOT
  fresh numbers from the tail loop; the current tail loop
  (`for w in range(n): if not visited[w]: new_disc[w] = clock[0] ...`)
  wrongly makes them look reachable and must be removed.
- The `fixed`/`fixed_disc_map`/`advance_clock` machinery should be deleted
  entirely; it is the source of the divergence.

Approaches that will NOT work:
- Keeping the fixed-vertex fast-forward but only fixing `advance_clock`
  (e.g., not jumping): the fixed vertex 1 would keep old numbers (disc 1,
  fin 2) while the re-DFS renumbers 0 to disc 0, fin 2 — producing
  finish[1] == finish[0] and breaking the nesting invariant
  (discover[u] < discover[v] < finish[v] < finish[u]) for edge 0->1.
  The old numbers of fixed vertices are simply not compatible with a
  renumbered ancestor region.
- Marking fixed vertices visited but still setting their parent during the
  re-DFS: a fixed vertex's old parent may be an ancestor of v whose
  renumbered interval no longer contains it, so the parent/interval
  consistency would still break.

The full-recompute fallback (as `insert_edge` already does via `_recompute`)
is correct and acceptable for this calibration run; the research goal of
avoiding full recompute can be addressed later with a proper Yang et al.
candidate-interval re-search that renumbers the whole affected region
consistently rather than mixing old and new numbers.
