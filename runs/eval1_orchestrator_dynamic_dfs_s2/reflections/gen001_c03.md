## FAILURE_DESCRIPTION
Graph: 2 vertices, 0/1 adjacency matrix, initially empty (no edges). Root = 0.
Operation: `insert (0, 1)` (sequence index 0, i.e. the first update after `init`).

- Expected after the insert: vertex 1 becomes reachable from 0. A valid DFS is
  `parent = {0: None, 1: 0}`, `discover = {0: 0, 1: 1}`, `finish = {1: 2, 0: 3}`.
- Actual returned state: `{'parent': [None, None], 'discover': [0, -1], 'finish': [1, -1]}`
  — vertex 1 is still marked unreachable (`discover[1] = -1`), so the verifier
  sees a forest that does not span the reachable set of the current graph.

## ROOT_CAUSE
In `insert_edge`, the very first guard treats an unreachable target as a
no-op:

```python
    # If either endpoint unreachable, no change to the reachable forest
    if discover[u] == -1 or discover[v] == -1:
        return state
```

This is wrong for the case where the *source* `u` is reachable and the
*target* `v` is not. Inserting `u -> v` then makes `v` (and everything
reachable from `v`) newly reachable, so the DFS forest must change. In the
failing case, after `init` on the empty graph the state is
`discover = [0, -1]`, `finish = [1, -1]`. On `insert (0, 1)`, `u = 0` has
`discover[0] = 0` (reachable) but `v = 1` has `discover[1] = -1`, so the guard
fires and the stale state is returned unchanged. The first divergence is
exactly this early return: the new edge 0->1 is never reflected in
`parent`/`discover`/`finish`.

The same guard also wrongly no-ops when `u` is unreachable and `v` is
reachable (harmless for reachability, but it silently skips any case where the
caller's state might need attention); the real bug is the `discover[v] == -1`
half of the condition.

## REPAIR_HINTS
Smallest fix in `insert_edge`: split the guard so that only an unreachable
*source* is a no-op, and an unreachable *target* with a reachable source
triggers a re-search.

```python
    if discover[u] == -1:
        return state                      # source unreachable: nothing new reachable
    if discover[v] == -1:
        # v becomes (partially) reachable via u: recompute (or do a
        # targeted DFS from v with parent[v] = u, then continue from v's
        # subtree, reusing the old timestamps for untouched vertices)
        parent, discover, finish = _dfs_full(graph)
        return {'parent': parent, 'discover': discover, 'finish': finish}
```

Notes:
- A full `_dfs_full` recompute is the safe minimal change and restores
  correctness immediately; the research goal of avoiding full recomputes can
  be addressed later by re-searching only from `v` (set `parent[v] = u`,
  DFS the newly reachable region, and keep the old `discover`/`finish` values
  for vertices outside it — but be careful that the shared-counter invariant
  `discover[u] < discover[v] < finish[v] < finish[u]` for ancestor pairs is
  preserved, which is easiest if the new region is searched in a way that
  keeps it inside `u`'s interval or by renumbering).
- Do NOT keep the combined `discover[u] == -1 or discover[v] == -1` guard:
  it is the direct cause of this failure.
- The rest of the logic (back/forward/cross classification for the
  both-reachable case, and the tree-edge check in `delete_edge`) is not
  implicated by this failing case; leave it as is for the minimal repair.
