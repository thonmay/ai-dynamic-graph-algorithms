## FAILURE_DESCRIPTION
Graph: 2 vertices, empty adjacency matrix (no edges). After `init`, state is
`parent=[None, None]`, `discover=[0, -1]`, `finish=[1, -1]` (vertex 1 unreachable).
Operation: `insert_edge(graph, (0, 1), state)` — the matrix now has `graph[0][1] = 1`.
Expected: vertex 1 becomes reachable, e.g. `parent={0: None, 1: 0}`,
`discover={0: 0, 1: 1}`, `finish={1: 2, 0: 3}`.
Actual: state returned unchanged: `parent=[None, None]`, `discover=[0, -1]`,
`finish=[1, -1]`. Vertex 1 is still marked unreachable even though edge 0->1
now exists from the root.

## ROOT_CAUSE
In `insert_edge`, the first guard bails out whenever the target is currently
unreachable:

```python
    if discover[v] == -1:
        # v unreachable: no effect on the forest
        return state
```

This is wrong. An inserted edge `u -> v` with `discover[v] == -1` makes `v`
(and everything reachable from `v`) newly reachable whenever `u` itself is
reachable (`discover[u] != -1`). The forest must then be extended: `v` gets a
parent, a discover time, and a finish time. The code instead treats the
insertion as a no-op, so the state no longer matches the graph.

The same bug pattern exists in `delete_edge`:

```python
    if parent[v] != u:
        # not a tree edge: forest stays valid
        return state
```

If the deleted edge was the *only* incoming edge to `v` from the reachable
part of the graph (e.g. `parent[v] == u` is false because `v` was reached via
another edge that is now gone, or more simply: `v` was reachable only through
`u` but via a non-tree path), the subtree that becomes unreachable is never
detached. In the minimal failing case only the insert path is exercised, but
the delete guard has the same "no effect" assumption and will fail on any
case where a deletion disconnects a vertex that was not a direct tree child.

## REPAIR_HINTS
1. **`insert_edge`**: remove the early `return state` for `discover[v] == -1`.
   When `discover[u] != -1` and `discover[v] == -1`, the new edge makes `v`
   reachable. The correct action is to re-search the subtree rooted at `u`
   (call `_resubtree(u, ...)`), which will discover `v` and all vertices
   reachable from `v` through the new edge. Note that `_resubtree` currently
   assumes the set of reachable vertices is unchanged (it renumbers a fixed
   interval); it must be extended to handle the case where the re-search
   discovers *new* vertices (the interval grows). Specifically:
   - Before resetting, record `base = discover[u]` and the old interval end.
   - After `_dfs_from(u, ...)` completes, the new interval may be longer than
     the old one. Renumber the *entire* interval `[base, new_finish[u])`
     contiguously, and shift the discover/finish times of all vertices
     *after* the old interval (i.e., vertices with `discover >= old_finish[u]`
     that are not in the re-searched set) by the amount the interval grew.
   - If `discover[u] == -1` (u itself unreachable), the insertion truly has
     no effect; keep the early return only for that sub-case.

2. **`delete_edge`**: the guard `if parent[v] != u: return state` is
   insufficient. Even if the deleted edge is not a tree edge, it may be the
   only edge that keeps some vertex reachable (e.g., a forward/cross edge
   that was the sole path into a vertex). The safe fix: after removing the
   edge, re-search the subtree of `u` and check whether any vertex that was
   previously reachable is now unreachable. If so, detach those vertices
   (set `discover = finish = -1`, `parent = None`) and renumber the remaining
   interval. A simpler (but less efficient) correct approach: re-run DFS
   from `u` and compare the reachable set; vertices that drop out must be
   marked unreachable and the interval renumbered.

3. **`_resubtree`** must be generalized to handle both interval growth
   (insertion making new vertices reachable) and interval shrinkage (deletion
   making vertices unreachable). The current code assumes the vertex set is
   invariant, which is false in both cases.

Approaches that will NOT work:
- Simply setting `parent[v] = u` and assigning fresh times to `v` on
  insertion without renumbering the rest of the interval will break the
  contiguity invariant (discover/finish must be a single shared counter).
- Calling `_resubtree` as-is on an insertion where `v` was unreachable will
  crash or produce wrong times because `sub` (collected via `_is_ancestor`)
  does not include `v` or its newly-reachable descendants, and the
  renumbering loop assumes the set is unchanged.
