## FAILURE_DESCRIPTION
Crash on the very first operation (sequence_idx 0) of a 2-vertex graph:
`ValueError: too many values to unpack (expected 2) at line 162: order, counter = _full_search(adj, n)` inside `insert_edge`. The candidate never produced a state for this case; the harness aborted.

## ROOT_CAUSE
`_full_search` returns a 5-tuple `(parent, disc, fin, order, counter)` (see its `return parent, disc, fin, order, counter`), but every call site in `insert_edge` unpacks it as a 2-tuple:

```python
order, counter = _full_search(adj, n)
state['parent'] = parent
state['disc'] = disc
state['fin'] = fin
```

This happens in both fallback branches of `insert_edge` (the "forward-cross edge" branch when `disc[v] is not None` and `disc[u] >= disc[v]`, and the "u unreachable" branch). The crash fires on the first update that takes either branch — for a 2-vertex graph, inserting an edge with `disc[u] > disc[v]` (e.g. 1->0 when 0->1 exists, or any edge into the root) hits the first branch immediately.

Two compounding bugs are on these same lines:
1. The unpack arity mismatch (the actual crash).
2. Even after fixing the arity, the code assigns the *old* `parent`/`disc`/`fin` local variables back into `state` instead of the fresh lists returned by `_full_search`. The locals were captured from `state` before the call, so the state would keep the stale DFS numbering while `order`/`counter` come from the new search — an inconsistent state that would fail the verifier's interval checks.

Note the contrast: `init` unpacks the 5-tuple correctly, and `_re_search_from` (used by `delete_edge` and the "v unreachable" insert branch) genuinely returns `(order, counter)` and mutates `parent`/`disc`/`fin` in place, so those 2-tuple unpacks are correct. Only the `_full_search` call sites are broken.

## REPAIR_HINTS
In `insert_edge`, replace each of the two broken blocks:

```python
order, counter = _full_search(adj, n)
state['parent'] = parent
state['disc'] = disc
state['fin'] = fin
state['order'] = order
state['counter'] = counter
```

with a proper 5-way unpack that stores the *returned* lists:

```python
parent, disc, fin, order, counter = _full_search(adj, n)
state['parent'] = parent
state['disc'] = disc
state['fin'] = fin
state['order'] = order
state['counter'] = counter
```

(Rebinding the local names is fine since `_state_fields(state)` reads from `state`.)

Do NOT "fix" this by making `_full_search` return only `(order, counter)` and mutating the passed-in lists: `_full_search` builds fresh lists internally and never receives the old ones, so that would require a larger refactor and would still leave the stale-list assignment bug unless the call sites are changed anyway.

After this fix, also sanity-check the "v already reachable" branch logic: the comment claims `disc[u] < disc[v]` implies the new edge is harmless, but a new edge u->v with disc[u] < disc[v] where v is NOT a descendant of u is exactly a forward-cross edge and invalidates the forest (e.g. graph 0->1, 0->2, 1->3, 2->4, insert 1->4: disc[1]<disc[4] but 4 is not under 1). The current code only re-searches when `disc[u] >= disc[v]`, so it will miss this case. The correct no-op condition is: `disc[u] < disc[v] < fin[v] < fin[u]` (v is a descendant of u) OR `disc[v] < disc[u]` (back edge); otherwise re-search. Fixing the crash is the immediate priority, but this is the next correctness failure the verifier will hit.
