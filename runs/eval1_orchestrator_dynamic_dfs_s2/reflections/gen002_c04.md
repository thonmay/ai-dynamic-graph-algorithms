## FAILURE_DESCRIPTION
Case: n=2, empty graph, single operation `insert (0,1)`.
Expected after the insert: `parent=[None,0]`, `discover=[0,1]`, `finish=[3,2]` (root 0 discovered at 0, child 1 at 1, 1 finishes at 2, 0 at 3).
Actual returned: `parent=[None,0]`, `discover=[0,0]`, `finish=[3,1]`.
Violations: `discover[0]==discover[1]` (two vertices share a discovery time), and the descendant-interval property fails: edge 0→1 has `discover[0] < discover[1]` false (0 < 0), and `finish[1]=1 < finish[0]=3` but `discover[1]` is not inside (0, 3) as a proper descendant time.

## ROOT_CAUSE
In `_resubtree`, after re-running `_dfs_from(u, ...)`, the renumbering step builds the new subtree set with:

```python
new_sub = [v for v in range(n) if discover[v] != -1 and _is_ancestor(u, v, discover, finish)]
```

`_is_ancestor(u, v, ...)` is `discover[u] < discover[v] and finish[v] < finish[u]`, which is **strictly false for v == u** (`discover[u] < discover[u]` is False). So the re-searched root `u` itself is excluded from `new_sub`. In the failing trace, after `_dfs_from(0,...)` we have `discover=[0,1]`, `finish=[3,2]`, and `new_sub` becomes `[1]` only. The renumbering loop then does:

```python
ordered = sorted(new_sub, key=lambda v: discover[v])   # [1]
for i, v in enumerate(ordered):
    discover[v] = base + i                              # discover[1] = 0 + 0 = 0
```

colliding with `discover[0]=0`, and the finish loop sets `finish[1]=1`. The root's own times are left untouched, so the interval is no longer contiguous and the root/child times are inconsistent.

Note the same latent bug exists in the `sub` collection line at the top of `_resubtree` (`_is_ancestor(u, v, ...)` also excludes `u`), but there it is harmless because `u` is immediately re-discovered at `base` right after the reset loop. It only becomes destructive in the renumbering phase, where `u` must be included in the renumbered set.

## REPAIR_HINTS
Smallest fix: include `u` in the renumbered set. In `_resubtree`, change the `new_sub` construction to treat `u` as part of its own subtree, e.g.:

```python
new_sub = [v for v in range(n) if discover[v] != -1 and (v == u or _is_ancestor(u, v, discover, finish))]
```

(or equivalently use a non-strict interval test `discover[u] <= discover[v] and finish[v] <= finish[u]`). With `u` included, `ordered` becomes `[0,1]`, giving `discover=[0,1]`, and `ordered_f=[1,0]` giving `finish=[3,2]` — the correct contiguous interval.

Also apply the same `v == u` guard to the initial `sub` collection for consistency (currently harmless, but it makes the reset loop's intent explicit and avoids a future regression if the re-discovery of `u` is moved).

Approaches that will NOT work:
- Renumbering only the non-root vertices and leaving `u`'s times as-is is exactly the current bug; the interval must be renumbered as a whole including `u`.
- Relying on `_dfs_from`'s raw counter values without the renumbering pass is also wrong in general, because the counter starts at `base+1` but the old interval may have contained vertices that are no longer reachable (deletion case), leaving gaps; the renumbering pass is needed, it just must include `u`.
- The `delta` shift loop (`discover[v] >= old_end and v not in new_sub`) is fine once `new_sub` is correct; do not change its condition.
