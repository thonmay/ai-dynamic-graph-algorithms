## FAILURE_DESCRIPTION

3-vertex directed graph, root 0. Before the update the DFS forest is
`parent = [None, 0, 1]`, `discover = [0, 1, 2]`, `finish = [5, 3, 4]`
(tree 0->1->2, so (1,2) is a tree edge). The update is
`delete_edge(graph, (1, 2), state)` on the graph with edges 0->1 and 0->2
(the 1->2 entry already cleared in the matrix).

Expected: vertex 2 reattached under 0, e.g. `parent = [None, 0, 0]`,
`discover = [0, 1, 3]`, `finish = [5, 2, 4]`.
Actual: `parent = [None, None, None]`, `discover = [0, 1, -1]`,
`finish = [5, 2, -1]` — vertex 2 is reported unreachable even though 0->2
still exists, and vertex 1 lost its parent pointer.

## ROOT_CAUSE

Two independent bugs, both in `_resubtree` / `delete_edge`.

**Bug 1 (corrupts the state): `_resubtree` resets `u` itself to
`discover = -1` before re-searching.**

```python
sub = [v for v in range(n) if discover[v] != -1 and (v == u or _is_ancestor(u, v, discover, finish))]
for v in sub:
    discover[v] = -1
    finish[v] = -1
    parent[v] = None
```

`_dfs_from` treats `discover[ci] == -1` as "unvisited" and makes such a
vertex a child of the current stack top. In the failing case `u = 1`,
`sub = [1, 2]`, so `discover[1]` is reset to -1. When the re-searched DFS
from 1 scans 1's adjacency list it finds the still-present edge 1->0 with
`discover[0] == -1` (0 was never reset) and executes

```python
if graph[x][ci] and discover[ci] == -1:
    parent[ci] = x
    discover[ci] = counter[0]
```

with `x = 1, ci = 0` — overwriting `parent[0] = 1` and `discover[0] = 2`.
The DFS then finishes 0 (finish[0]=3) and 1 (finish[1]=4), leaving
`parent = [1, None, None]`, `discover = [2, 1, -1]`, `finish = [3, 4, -1]`.
The root's own parent/discover/finish are destroyed, and the verifier's
tree-edge check on 0->1 fails (`discover[0]=2 > discover[1]=1`, so 1 is not
a descendant of 0). The harness's reported result is this corrupted state.

The invariant violated: `_dfs_from` assumes every vertex outside the
re-searched interval is already discovered, so it never re-visits them.
Resetting `u` breaks that assumption for `u`'s ancestors — any edge from a
reset vertex to an ancestor (a back edge, e.g. 1->0) is misread as a tree
edge.

**Bug 2 (wrong re-search region): `delete_edge` re-searches only the
subtree of `u`, but the detached subtree of `v` may be reattachable only
through an ancestor of `u`.**

```python
def delete_edge(graph, edge, state):
    u, v = edge
    ...
    if parent[v] != u:
        return state
    _resubtree(u, graph, parent, discover, finish)
```

After deleting tree edge (1,2), vertex 2 is not reachable from 1 (the only
remaining in-edge is 0->2), so re-searching from 1 can never reattach 2.
The correct dynamic-DFS behavior is to re-search from the lowest ancestor
of `u` that has an edge into the detached set (here, 0), or from 0 as a
safe fallback.

## REPAIR_HINTS

1. **Fix Bug 1 (minimal change in `_resubtree`):** exclude `u` from the
   reset loop — keep `discover[u] = base` and `parent[u]` intact, and reset
   only the proper descendants (`v != u and _is_ancestor(u, v, ...)`). Then
   `_dfs_from(u, ...)` starts with `u` already discovered, so its
   adjacency scan can never re-visit an ancestor. This is correct for both
   the deletion case (subtree shrinks) and the insertion case (subtree
   grows), because in both cases the re-searched region is exactly the
   subtree rooted at `u` and `u`'s discovery time is fixed by the
   surrounding forest. (Alternative: keep the reset of `u` but pass a
   "protected" set of already-discovered outside vertices into `_dfs_from`
   and skip them in the `discover[ci] == -1` test — more invasive.)

2. **Fix Bug 2 (in `delete_edge`):** after deleting tree edge (u, v),
   re-search from the lowest ancestor `a` of `u` (walking parent pointers
   up to 0) such that some vertex in the old subtree of `v` is reachable
   from `a` via an edge not going through `u`; if none exists, re-search
   from 0 (or simply always re-search from 0's subtree when the detached
   set is not reachable from `u` alone). A safe minimal variant: call
   `_resubtree(u, ...)` first; then for every vertex `w` in the old
   subtree of `v` with `discover[w] == -1`, walk ancestors of `u` up to 0
   and re-search from the first ancestor `a` with an edge `a->w`. If no
   such ancestor exists, `w` stays unreachable.

3. The renumbering/shift logic at the end of `_resubtree` is fine once the
   above are fixed: the raw DFS assigns the new subtree the contiguous
   block `[base, new_end)`, so `shift = base - raw_base` is 0 in the fixed
   version and `delta = new_end - old_end` correctly shifts the tail.

Approaches that will NOT work:
- Just resetting the subtree and re-searching from `u` (the current code):
  corrupts ancestors via back edges (Bug 1) and misses reattachments
  through ancestors (Bug 2).
- Re-running a full DFS from 0 on every update: correct but violates the
  "avoid full recompute" goal (acceptable only as a calibration fallback).
