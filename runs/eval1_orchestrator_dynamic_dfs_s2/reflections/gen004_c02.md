## FAILURE_DESCRIPTION
Case: n=2, initial graph all zeros (only vertex 0 reachable, discover=[0,-1], finish=[1,-1]).
Operation: insert_edge((0,1)).
Expected (any valid DFS of graph with edge 0->1): parent=[None,0], discover=[0,1], finish=[3,2] (e.g. expected dict {0:3, 1:2}).
Actual returned: parent=[None,0], discover=[0,1], finish=[2,1].
Violated property: for the tree edge 0->1, finish[1] (1) is NOT greater than discover[1] (1); the root's finish (2) is not the maximum time. The verifier requires finish[v] > discover[v] for every reachable vertex and finish[u] > finish[v] for tree edges.

## ROOT_CAUSE
The bug is in `_resubtree`, in the "renumber" block. After `_dfs_from` runs, the raw counter values are a perfectly valid DFS numbering of the new subtree (contiguous, correct nesting). The code then "normalizes" them by re-sorting:

```python
ordered = sorted(new_sub, key=lambda v: discover[v])
for i, v in enumerate(ordered):
    discover[v] = base + i
ordered_f = sorted(new_sub, key=lambda v: finish[v])
for i, v in enumerate(ordered_f):
    finish[v] = base + i + 1
```

This assigns finish times by sorting vertices by their finish time and giving them base+1, base+2, ... in that order. That is NOT a valid finish-time assignment: it ignores the nesting structure. In a DFS, finish times must satisfy finish[v] > discover[v] for every vertex and finish[child] < finish[parent] for tree edges. Sorting by finish and renumbering 1..k can (and here does) give a vertex a finish time smaller than or equal to its own discover time.

Trace on the failing case:
- base = discover[0] = 0, old_end = finish[0] = 1.
- sub = [0] (only 0 was reachable). Reset: discover=[-1,-1], finish=[-1,-1].
- discover[0]=0, counter=[1]. _dfs_from(0): discovers 1 at counter 1 (discover[1]=1, parent[1]=0), finishes 1 at counter 2 (finish[1]=2), finishes 0 at counter 3 (finish[0]=3). Raw state: discover=[0,1], finish=[3,2] — already valid.
- new_sub = [0,1].
- discover renumbering: ordered by discover = [0,1] -> discover=[0,1]. Fine.
- finish renumbering: ordered_f = sorted([0,1], key=finish) = [1,2] -> [1,0] (finish[1]=2 < finish[0]=3). So finish[1]=base+1=1, finish[0]=base+2=2. Result: finish=[2,1].
- Now finish[1]=1 == discover[1]=1, and finish[1] < discover[1]+1: the invariant finish[v] > discover[v] is broken. Also finish[1] (1) < finish[0] (2) is fine, but finish[1] must be > discover[1].

The comment in the code claims "Renumbering preserves the relative order of discover times and of finish times, so the DFS invariants ... are maintained." That is false: independently renumbering discover (by discover order) and finish (by finish order) does NOT preserve the interleaving that makes (discover, finish) pairs valid DFS intervals. The raw counter values from `_dfs_from` are already contiguous and valid; the renumbering is both unnecessary and destructive.

## REPAIR_HINTS
The smallest fix: delete the renumbering block entirely. The raw values from `_dfs_from` are already a contiguous, valid DFS numbering of the new subtree (discover starts at base, counter increments by 1 per event, so all times in the subtree are exactly [base, base+2*|new_sub|)). No re-sorting is needed.

Concretely, in `_resubtree`, remove:
```python
    new_sub = [v for v in range(n) if discover[v] != -1 and (v == u or _is_ancestor(u, v, discover, finish))]
    ordered = sorted(new_sub, key=lambda v: discover[v])
    for i, v in enumerate(ordered):
        discover[v] = base + i
    ordered_f = sorted(new_sub, key=lambda v: finish[v])
    for i, v in enumerate(ordered_f):
        finish[v] = base + i + 1
```
Keep only:
```python
    new_end = finish[u]
    delta = new_end - old_end
    if delta != 0:
        for v in range(n):
            if discover[v] != -1 and discover[v] >= old_end and v not in new_sub:
                discover[v] += delta
                finish[v] += delta
```
But note: `new_sub` is still needed for the shift loop (to exclude re-searched vertices). So keep the `new_sub = [...]` line, but drop the two renumbering loops.

After this fix, on the failing case: raw discover=[0,1], finish=[3,2], new_end=3, old_end=1, delta=2. No vertices outside new_sub have discover >= 1, so no shift. Final: discover=[0,1], finish=[3,2], parent=[None,0]. Valid.

Approaches that will NOT work:
- Keeping the renumbering but fixing only the finish loop (e.g., assigning finish by reverse-discover order or by tree depth) — this is fragile and still not guaranteed to produce valid DFS intervals for arbitrary subtree shapes. The raw counter values are already correct; any renumbering risks breaking the interleaving.
- Renumbering discover and finish independently by their respective sorted orders — this is exactly the current bug and cannot be made correct in general, because DFS validity depends on the specific interleaving of discover and finish events, not on their separate orders.
