## FAILURE_DESCRIPTION

Failing case: `delete (1, 2)` on a 3-vertex directed graph.

- Pre-update state (valid DFS of the pre-deletion graph): `parent = [None, 0, 1]`, `discover = [0, 1, 2]`, `finish = [5, 4, 3]`. This is a consistent DFS of a graph containing tree edges 0->1 and 1->2 (plus whatever else).
- Post-deletion graph: tree edge 1->2 removed. Vertex 2 is still reachable from the root (the expected result shows `parent[2] = 0`, i.e. a direct edge 0->2 exists in the post-deletion graph).
- Expected (one valid DFS of the post-deletion graph): `parent = {0: None, 1: 0, 2: 0}`, `discover = {0: 0, 1: 1, 2: 3}`, `finish = {1: 2, 2: 4, 0: 5}`.
- Actual returned: `parent = [None, 0, 1]`, `discover = [0, 1, 2]`, `finish = [5, 4, 3]` — the **stale pre-deletion state, returned unchanged**.

The verifier rejects it because the returned parent pointer `parent[2] = 1` references an edge (1->2) that no longer exists in the graph: the tree edge was deleted but the forest was not updated.

## ROOT_CAUSE

The bug is in `delete_edge`. The "no change" fast path is guarded by a check that is **too weak**:

```python
    for x in range(n):
        if not in_sub[x]:
            continue
        has_outside_in = False
        row = graph[x]
        for y in range(n):
            if row[y] and not in_sub[y]:
                has_outside_in = True
                break
        if not has_outside_in:
            return _re_search_after_tree_delete(graph, state, v, in_sub)

    # All subtree vertices still reachable from outside: no change.
    return state
```

The condition `has_outside_in` only asks whether vertex `x` has **any** incoming edge from a vertex outside the deleted subtree. It does **not** check that the outside source is actually *reachable from the root*. In the failing case, vertex 2 has an incoming edge from 0 (outside the subtree of 2), so `has_outside_in` is True for every subtree vertex and the function returns the old state. But the old state still contains `parent[2] = 1`, i.e. the deleted tree edge, so the returned forest is not a spanning tree of the current graph.

The correct invariant for the "no change" fast path is: every vertex in the deleted subtree must still be reachable from the root **via a path that does not use the deleted tree edge** (equivalently, via an incoming edge from a vertex that is reachable from the root outside the subtree). The current check drops the "reachable from the root" requirement on the outside source, so it can declare "no change" while the subtree is actually only reachable through the deleted edge (or, as here, while the kept parent pointers still reference the deleted edge).

Note the same latent flaw exists in the re-search branch: `_re_search_after_tree_delete` currently just calls `_dfs_full(graph)` (the partial re-search is abandoned in a comment), so that branch is correct but defeats the optimization goal. The immediate correctness failure, however, is the fast path returning stale state.

## REPAIR_HINTS

Smallest concrete fix, in `delete_edge`:

1. Replace the per-vertex `has_outside_in` check with a reachability check from the root in the post-deletion graph restricted to the subtree:
   - Run a BFS/DFS from the root over the current (post-deletion) graph, but only "enter" the subtree through edges from outside the subtree (i.e., when scanning an edge `y -> x` with `x in in_sub`, require `y` to be reachable and not in the subtree).
   - If every vertex in the subtree is reached this way, the subtree stays reachable without the deleted tree edge.
2. Even when the subtree stays reachable, you **cannot** simply return the old state: the old `parent` pointers inside the subtree may still reference the deleted tree edge (as in this case, `parent[2] = 1`). The kept forest must be a spanning tree of the *current* graph. So the "no change" fast path is only valid if the deleted edge was not the parent edge of any kept vertex — which it always is, since we only reach this code when `parent[v] == u`. Therefore, whenever `parent[v] == u`, you must re-derive at least the parent pointers (and consistent discover/finish times) for the affected interval; returning the untouched state is never correct for a tree-edge deletion.
   - Simplest correct approach: on any tree-edge deletion, recompute (a full `_dfs_full` is acceptable for correctness first; a partial re-search of the interval `[discover[v], finish[v])` with the prefix pre-marked visited is the optimization to add later).
3. Do not attempt to "patch" the old discover/finish values of the prefix onto a re-searched suffix (the abandoned code in `_re_search_after_tree_delete` shows why: prefix finish times must be recomputed to enclose any new descendants, and renumbering the suffix breaks the old prefix finish values). If you keep the partial re-search, renumber the *entire* order consistently (prefix keeps relative order, suffix gets fresh times, and prefix finish times are recomputed as the max over their descendants' new finishes).

Approaches that will not work:
- Keeping the `has_outside_in` check as the "no change" condition: it ignores root-reachability of the outside source and, more fundamentally, cannot justify keeping the old parent pointers after a tree edge is removed.
- Returning the old state unchanged for any tree-edge deletion: the deleted edge is by definition a parent edge, so the old forest is never a spanning tree of the new graph.
