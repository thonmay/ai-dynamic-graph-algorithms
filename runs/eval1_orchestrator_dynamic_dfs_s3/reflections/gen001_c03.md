## FAILURE_DESCRIPTION

3-vertex directed graph, root 0. Failing operation: `insert (0, 1)` at sequence index 0.

- Result returned by the candidate: `{'parent': [None, 0, None], 'discover': [0, 1, -1], 'finish': [3, 2, -1]}`
- Expected (a valid DFS of the post-update graph): `{'parent': {0: None, 1: 0, 2: 1}, 'discover': {0: 0, 1: 1, 2: 2}, 'finish': {2: 3, 1: 4, 0: 5}}`

The expected result shows vertex 2 is reachable from the root (parent[2]=1, discover[2]=2), so the post-update graph must contain a path 0 -> 1 -> 2, i.e. edge (1,2) is present. The candidate's result leaves vertex 2 unreachable (discover[2] = -1), so the candidate's state was computed on a graph that does NOT contain (1,2) — i.e. it was computed on the pre-update graph.

## ROOT_CAUSE

The candidate's `insert_edge` never rebuilds when the inserted edge (u,v) is a **tree edge** (target already reachable, `discover[u] < discover[v]`, and v is a descendant of u). In that case it falls through to the "Otherwise the forest remains a valid DFS forest" branch and returns the old state unchanged:

```python
    # New edge is a forward-cross edge iff u discovered before v and v is
    # not a descendant of u.  That invalidates the DFS forest.
    if discover[u] < discover[v] and not _is_descendant(u, v, tin, tout):
        ...rebuild...

    # Otherwise the forest remains a valid DFS forest.
    return _make_state(n, adj, parent, discover, finish,
                       state['tree_children'], state['subtree'], tin, tout)
```

The premise "otherwise the forest remains valid" is wrong. A DFS forest is a *spanning* tree of the reachable set: every reachable vertex must be discovered, and the parent pointers must form a spanning tree of the reachable subgraph. When the inserted edge (u,v) is a tree edge (v is a descendant of u), the insertion can change the reachable set if v has outgoing edges to previously unreachable vertices. The candidate does not check this.

Concretely, in the failing case:
- The state was built by `init` on the pre-update graph, which had (0,1) but NOT (1,2). So vertex 1 is reachable (discover[1]=1, parent[1]=0), but vertex 2 is unreachable (discover[2]=-1).
- The update inserts (0,1). The candidate checks `discover[u] == -1` (false, u=0 is reachable), `discover[v] == -1` (false, v=1 is reachable), and `discover[u] < discover[v] and not _is_descendant(u, v)` (false, v=1 IS a descendant of u=0). So it takes the "forest remains valid" branch and returns the old state.
- But the post-update graph has (1,2), which makes vertex 2 reachable. The candidate's state still shows vertex 2 as unreachable, so the forest is not spanning.

The root cause: the candidate's "forest remains valid" branch is unsound. It assumes that if the inserted edge is not a forward-cross edge and the target is already reachable, the forest remains valid. But this is only true if the insertion does not change the reachable set. When the inserted edge is a tree edge (v is a descendant of u), the insertion can make new vertices reachable if v has outgoing edges to previously unreachable vertices. The candidate does not check this.

## REPAIR_HINTS

1. **Simplest fix**: In `insert_edge`, always call `_rebuild(n, adj)` and return the new state. This is O(n^2) per update but correct. The current "fast path" that skips the rebuild when the edge is a tree edge or a back edge is unsound because it assumes the state is consistent with the post-update graph, which is not guaranteed.

2. **Targeted fix**: The "forest remains valid" branch is only sound if the inserted edge does not change the reachable set. This is true when:
   - The source u is unreachable (already handled).
   - The target v is unreachable (already handled, triggers rebuild).
   - The target v is reachable and the edge is a back edge (discover[v] < discover[u]) — this cannot change reachability.
   - The target v is reachable and a descendant of u (tree edge or forward edge) — this CAN change reachability if v has outgoing edges to previously unreachable vertices. The candidate must check whether any vertex reachable from v in the post-update graph was unreachable in the pre-update state. If so, rebuild.

   The simplest way to implement this check: after the insert, do a BFS/DFS from v in the post-update graph and check if any vertex discovered was unreachable in the pre-update state. If yes, rebuild. If no, the forest remains valid.

3. **What will NOT work**: Keeping the current "forest remains valid" branch without any reachability check. The branch is unsound because it assumes the state is consistent with the post-update graph, which is not guaranteed when the inserted edge is a tree edge.

4. **Code location**: The fix should be in `insert_edge`, specifically in the final "Otherwise the forest remains a valid DFS forest" branch. Replace the unconditional return with a reachability check, or simply always rebuild.
