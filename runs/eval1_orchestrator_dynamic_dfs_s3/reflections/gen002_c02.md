## FAILURE_DESCRIPTION
3-vertex directed graph, first operation `insert (0, 1)`.
- Candidate result: `parent=[None, 0, None]`, `discover=[0, 1, -1]`, `finish=[3, 2, -1]` (vertex 2 unreachable).
- Expected: `parent={0:None, 1:0, 2:1}`, `discover={0:0, 1:1, 2:2}`, `finish={2:3, 1:4, 0:5}` (DFS path 0→1→2, so the post-update graph contains edge 1→2 in addition to the inserted 0→1).

The candidate's rebuild after the insertion produced a forest in which vertex 2 is unreachable, i.e. the adjacency used by `_rebuild` did not contain edge 1→2 even though the expected (verifier-computed) DFS on the post-update graph does contain it.

## ROOT_CAUSE
In `insert_edge`, the adjacency handed to the rebuild is built from the `graph` argument:

```python
adj = [list(row) for row in graph]
...
if discover[v] == -1:
    parent, discover, finish, tc, sub, tin, tout = _rebuild(n, adj)
```

The `graph` argument does not reflect the complete post-update graph: the entry for the inserted edge (and, in this case, the pre-existing edge 1→2 that the expected DFS relies on) is missing from the `adj` that `_rebuild` sees. The candidate never reconciles `adj` with the update it is asked to apply — it trusts `graph` verbatim. Since the state's old `discover` says `discover[1] == -1`, the code takes the "target becomes reachable" branch and rebuilds on this incomplete `adj`, yielding `discover=[0,1,-1]` instead of `discover=[0,1,2]`.

Concretely: the rebuild ran on a graph with 0→1 but without 1→2, so vertex 2 was never discovered. The same defect applies to every other branch that uses `adj` (the forward-cross check, the reachability scan, and the `delete_edge` rebuild), because all of them derive `adj` solely from the `graph` parameter.

## REPAIR_HINTS
Smallest fix: make the adjacency used for any rebuild/scan the true post-update graph, independent of what `graph` contains.

1. In `insert_edge`, after `adj = [list(row) for row in graph]`, force the inserted entry on: `adj[u][v] = 1`.
2. In `delete_edge`, after the same copy, force the deleted entry off: `adj[u][v] = 0`.
3. Better and more robust: keep the authoritative adjacency in the state (`state['adj']`, which `init` already stores) and apply the single flipped entry to a copy of it:
   ```python
   adj = [row[:] for row in state['adj']]
   adj[u][v] = 1   # insert
   ```
   This guarantees the rebuild sees the exact post-update graph even if the `graph` argument is stale or pre-update.

Do NOT try to "fix" this by skipping the rebuild when `discover[v] == -1` — that branch is exactly where the new vertex must be discovered in DFS order, and the old forest is not spanning. Also do not rely on `state['adj']` alone without applying the flip: the state's adjacency is the pre-update graph, so it must be updated with the single flipped entry before rebuilding.
