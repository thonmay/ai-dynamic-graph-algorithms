## FAILURE_DESCRIPTION

Case: n=3, operation `insert (0, 2)` at sequence index 1 (the second
operation in the sequence; index 0 was the first update after init).

State returned by the candidate after this operation:
  parent   = [None, 0, 0]
  discover = [0, 3, 1]
  finish   = [5, 4, 2]

Expected (one valid DFS forest of the post-update graph):
  parent   = {0: None, 1: 0, 2: 0}
  discover = {0: 0, 1: 1, 2: 3}
  finish   = {0: 5, 1: 2, 2: 4}

The returned state is NOT a valid DFS forest of the post-update graph.
With discover[2]=1 < discover[1]=3 and edge 0->1 present, the verifier
requires vertex 1 to be a descendant of vertex 2 (interval nesting
discover[2] < discover[1] < finish[1] < finish[2]). But finish[1]=4 >
finish[2]=2, so the nesting is violated — edge 0->1 is a forward-cross edge
relative to the reported times.

## ROOT_CAUSE

The state was already corrupted BEFORE this insert (0,2) call. The
corruption was introduced by the first operation (sequence_idx=0), which
was almost certainly an insert_edge that took the "v unreachable, u
reachable" splicing branch.

Evidence: the returned state has discover=[0,3,1], finish=[5,4,2]. This is
the init state (discover=[0,1,3], finish=[5,2,4]) with the times of
vertices 1 and 2 swapped. The splicing branch in insert_edge does:

```python
shift = local_counter[0]
du = discover[u]
fu = finish[u]

# Shift all proper descendants of u (discover in (du, fu)) by `shift`.
for w in range(n):
    if discover[w] != -1 and du < discover[w] < fu:
        discover[w] += shift
        finish[w] += shift

# u's finish time extends by `shift`.
finish[u] = fu + shift

# Assign the subtree's times: local time t maps to du + 1 + t.
for w in visited:
    discover[w] = du + 1 + local_discover[w]
    finish[w] = du + 1 + local_finish[w]
```

The bug: the shift loop shifts ALL vertices with discover in (du, fu),
which includes u's existing descendants. Then the assignment loop assigns
new times to the spliced subtree starting at du+1. But the spliced
subtree's times OVERLAP with the shifted descendants' times. Specifically,
if u has existing descendants with discover in (du, fu), they are shifted
to (du+shift, fu+shift). The spliced subtree gets times in (du+1,
du+1+shift). These two ranges overlap when shift > 1, causing a collision.

In the failing case, the first operation (sequence_idx=0) was likely
insert (0, 1) or insert (1, 2) or similar, which triggered the splicing
branch. The splicing corrupted the times of vertices 1 and 2, swapping
them. Then the second operation insert (0,2) took the "v already
reachable" fast path:

```python
if discover[v] != -1:
    if discover[u] != -1 and discover[u] < discover[v] and finish[v] < finish[u]:
        return state
    return _state(graph)
```

With the corrupted state (discover[2]=1, finish[2]=2, discover[0]=0,
finish[0]=5), the condition `discover[0]=0 < discover[2]=1 and finish[2]=2
< finish[0]=5` holds, so the code returns the corrupted state unchanged.

The root cause is the splicing logic in the "v unreachable, u reachable"
branch of insert_edge: it does not correctly handle the case where u has
existing descendants. The shift and assignment overlap, corrupting the
times.

## REPAIR_HINTS

1. The splicing branch in insert_edge (the "v unreachable, u reachable"
   case) is the source of the corruption. The shift loop and the assignment
   loop overlap when u has existing descendants. The fix is to either:
   a. Recompute from scratch whenever u has existing descendants (i.e.,
      when fu > du + 1). This is safe but O(n^2).
   b. Correctly splice the subtree by inserting it at the RIGHT position
      within u's interval, not at du+1. The spliced subtree should be
      inserted after u's last existing child, not before all of u's
      descendants. This requires tracking u's children and inserting the
      new subtree at the correct position.

2. The simplest and safest fix is to **remove the splicing logic entirely**
   and recompute from scratch in the "v unreachable, u reachable" branch:
   ```python
   if discover[u] == -1:
       return state
   return _state(graph)
   ```
   This is O(n^2) per update but guarantees correctness.

3. The "v already reachable" fast path is also fragile: it returns the
   state unchanged when the descendant check passes, but if the state is
   corrupted, the corruption is propagated. The safest fix is to remove
   this fast path as well and always recompute from scratch:
   ```python
   def insert_edge(graph, edge, state):
       return _state(graph)
   ```
   This is O(n^2) per update but eliminates all fast-path bugs.

4. Approaches that will NOT work:
   - Keeping the splicing logic but fixing only the shift loop: the
     assignment loop also needs to be fixed to insert at the correct
     position, which is complex and error-prone.
   - Adding a validation step before returning the state: this would
     detect the corruption but not fix it, and would still require a
     recompute, so it's equivalent to just recomputing from scratch.
