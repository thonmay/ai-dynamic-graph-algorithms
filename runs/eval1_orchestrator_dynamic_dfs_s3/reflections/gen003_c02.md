## FAILURE_DESCRIPTION

Case: n=3, operation `insert (0, 2)` at sequence index 1.

Pre-state (after init on the graph before the insert, which must have been
edges 0->1 and 0->2 only, since 2 was unreachable before the insert):
- parent = [None, 0, -1]
- discover = [0, 1, -1]
- finish = [3, 2, -1]

After `insert_edge(graph, (0,2), state)` the candidate returned:
- parent = [None, 0, 0]
- discover = [0, 3, 1]
- finish = [5, 4, 2]

A valid DFS order for the resulting graph (edges 0->1, 0->2) is e.g.
discover = [0, 1, 3], finish = [5, 2, 4] (or the symmetric one with 1 and 2
swapped). The verifier rejected the candidate's result.

## ROOT_CAUSE

The splice in `insert_edge` (the "v unreachable, u reachable" branch) is
inconsistent with the parent pointers it produces.

The code shifts u's existing descendants by `shift` and then places the new
subtree at the FRONT of u's interval:

```python
for w in range(n):
    if discover[w] != -1 and du < discover[w] < fu:
        discover[w] += shift
        finish[w] += shift
...
for w in visited:
    discover[w] = du + 1 + local_discover[w]
    ...
    if w == v:
        parent[w] = u
```

So the new child v gets discover = du+1 (the FIRST slot after u), while the
old child 1 keeps parent[1] = u but is pushed to discover = du+1+shift.
The resulting times (discover = [0, 3, 1], finish = [5, 4, 2]) are a
consistent DFS order for the tree 0 -> 2 -> 1 (2's interval [1,4] contains
1's interval [3,4]), but the parent array says 0 -> 1 and 0 -> 2. The
verifier checks that for every tree edge u->v, discover[u] < discover[v] <
finish[v] < finish[u]; for the tree edge 0->1 it finds discover[1]=3 >
finish[1]=4 is fine, but discover[2]=1 < discover[1]=3 with 1 not a
descendant of 2 in the parent tree — i.e. the parent tree and the
discover/finish intervals describe two different trees. The parent pointers
were never updated to match the new time order.

In short: the splice reorders the DFS (new child first) but keeps the old
parent pointers, so `parent` and `(discover, finish)` no longer describe the
same tree.

## REPAIR_HINTS

Smallest fix: make the splice consistent with the existing parent pointers
instead of reordering. Since the new edge u->v is added to the adjacency
matrix, a genuine DFS from u would explore v AFTER all of u's existing
children (v is the last neighbor). So:

1. Place the new subtree at the END of u's interval, not the front:
   - keep all existing descendants of u at their current times (no shift
     loop needed for them);
   - assign the new subtree times starting at `fu` (the old finish of u):
     `discover[w] = fu + local_discover[w]`, `finish[w] = fu + local_finish[w]`
     for w in visited (local times are 0-based with v at 0, so v gets
     discover = fu, which is correct since u's old interval was [du, fu));
   - set `finish[u] = fu + shift` and add `shift` to the finish of every
     ancestor of u (the existing ancestor loop is already correct).

This yields discover = [0, 1, 3], finish = [5, 2, 4], parent = [None, 0, 0],
which is a valid DFS order matching the parent tree.

Alternative (also correct, less code): in this branch, simply
`return _state(graph)` (full recompute). It restores correctness
immediately; the splice optimization can be added later.

Approaches that will NOT work:
- Keeping the "new subtree at front" placement and only fixing the times
  without also rewriting parent pointers for u's old children (they would
  need to be re-parented under v, which is not a valid DFS tree of the
  graph).
- Shifting only discover or only finish of the old descendants — the
  intervals must stay nested, so both must move together (the current code
  does move both, but to the wrong side of the new subtree).
