## FAILURE_DESCRIPTION

Case: n=3, directed. Sequence index 1, operation `insert (1, 2)`.

State before the update (from init, consistent with the expected result):
- parent = [None, 0, 1]
- discover = [0, 1, 2]
- finish = [5, 4, 3]

So the DFS tree is 0 -> 1 -> 2, and the graph at that point contains edges
0->1 and 1->2 (the expected result's finish times 3/4/5 confirm 2 is a leaf
finished first, then 1, then 0).

After inserting edge 1->2, the candidate returns:
- parent = [None, 0, 1]
- discover = [0, 2, 4]
- finish = [1, 3, 5]

Expected (any valid DFS order of the same graph, e.g. the unchanged one):
- parent = {0: None, 1: 0, 2: 1}
- discover = {0: 0, 1: 1, 2: 2}
- finish = {2: 3, 1: 4, 0: 5}

The returned state is invalid: discover[0]=0 < discover[1]=2, but
finish[1]=3 > finish[0]=1, so 1 is NOT a descendant of 0. Yet parent[1]=0
claims 1 is a child of 0. The verifier's contract "for every edge u->v
between reachable vertices with discover[u] < discover[v], v must be a
descendant of u" is violated by the tree edge 0->1.

## ROOT_CAUSE

`insert_edge` misclassified the inserted edge. With u=1, v=2 and
discover=[0,1,2], finish=[5,4,3], `_is_ancestor(discover, finish, u, v)`
returns True (1 is a proper ancestor of 2), so the code takes the
"forward edge, fine" branch and returns the state unchanged.

But the edge 1->2 is already a TREE edge (parent[2] == 1). A legal update
"flips exactly one matrix entry", so the pre-update graph did NOT contain
1->2; the DFS tree 0->1->2 was impossible without it. The pre-update tree
must have been 0->1 and 0->2 (e.g. discover=[0,1,2], finish=[5,3,4]), where
1 and 2 are siblings. Inserting 1->2 then creates a genuine forward-cross
edge (1 discovered before 2, 2 not a descendant of 1), and the correct
repair is to re-parent 2 under 1, yielding parent=[None,0,1],
discover=[0,1,2], finish=[5,4,3].

The responsible lines in `insert_edge`:

```python
if _is_ancestor(discover, finish, u, v):
    # v is a proper descendant of u: forward edge, fine.
    return state
```

The code assumes that if v is a descendant of u, the new edge u->v is a
non-tree (forward) edge. That assumption is false: the descendant relation
is derived from the CURRENT parent pointers, and the current parent pointers
can already encode the very edge being inserted (the state is stale with
respect to the graph). The same latent bug exists in the sibling branch
`if _is_ancestor(discover, finish, v, u): return state` (a back edge u->v
with v an ancestor of u is fine only if u->v is not the tree edge
parent[u]==v).

## REPAIR_HINTS

Smallest fix: in `insert_edge`, before the "fine" early returns, check
whether the inserted edge is already a tree edge of the maintained forest:

```python
if discover[v] != -1 and discover[u] != -1:
    if parent[v] == u:
        # The edge u->v is already a tree edge in the maintained forest,
        # i.e. the state is stale: the pre-update graph lacked u->v, so
        # the current parent/discover/finish do not describe a DFS of the
        # pre-update graph. The ancestor/descendant classification above
        # is unreliable. Recompute from scratch.
        return _state(graph)
    ...
```

Placing this check before the `_is_ancestor` branches covers both the
forward-edge case (parent[v]==u) and the back-edge case (parent[u]==v).
Recomputing from scratch is correct (the from-scratch DFS is verified
correct) and is the minimal safe repair; a fully local repair would need to
re-derive the true pre-update forest, which is not recoverable from the
stale state alone.

Approaches that will NOT work:
- Trusting the discover/finish ancestor test to classify the new edge: the
  test reads state that may already reflect the inserted edge, so it can
  never distinguish "new forward-cross edge" from "edge already in the
  tree".
- Only checking `parent[v] == u` in the descendant branch: the symmetric
  stale case (inserting the tree edge u->v where v is an ancestor of u,
  i.e. parent[u] == v) would still slip through the back-edge branch.
- Patching `_reparent_subtree` alone: it is never reached in this case
  because the early return fires first.
