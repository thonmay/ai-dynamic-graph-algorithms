## FAILURE_DESCRIPTION

n=3. Sequence: init on the triangle (all three edges present) yields order [0,1,2]; then `delete_edge(graph, (1,0), state)` removes edge (0,1). The resulting graph is the path 0-2-1 (edges (0,2) and (1,2)). The candidate returned [0,1,2], but the only valid LexBFS orderings of this graph are [0,2,1] and [1,2,0] (the middle position must be the degree-2 vertex 2). The verifier's (LB) 4-point check reports the violation at positions a=0, b=1, c=2 (vertices 0,1,2): a0=0 and a2=2 are adjacent, a0=0 and a1=1 are not, and no d < a exists (minD stayed at the sentinel 1e9).

## ROOT_CAUSE

The fallback `_lexbfs_full` is itself broken, so the "correctness-first" guarantee fails. In `_lexbfs_full` the buckets are initialized as `buckets = [[v] for v in range(n)]` — one singleton bucket per vertex. The refinement step then splits each bucket by adjacency to the picked vertex, but a singleton bucket can never split, so the bucket structure carries no information at all: the algorithm degenerates to "always take the first vertex of the first bucket", i.e. it returns [0,1,2,...,n-1] for every graph.

Tracing the failing case: after deleting (0,1), `_repair` correctly rejects the old order [0,1,2] (the 4-point check fails), rejects the transposition [1,0,2] (also invalid: 0-2 edge, 0-1 non-edge, no d<0), and rejects the move-to-front candidate [1,0,2] (same). It returns None, so `delete_edge` calls `_lexbfs_full`, which — because of the singleton-bucket bug — returns [0,1,2] again. That order is invalid, and it is exactly the result the verifier saw.

Note the code comment claims "Tie-breaking: within a bucket, vertices are ordered by vertex id", but no such ordering is ever applied; the initial per-vertex buckets are the only source of the id order, and it is meaningless.

## REPAIR_HINTS

Minimal fix in `_lexbfs_full`: start from a single bucket containing all vertices, `buckets = [list(range(n))]`. Then the standard LexBFS refinement works: pick the first vertex of the first bucket, order it, and split every remaining bucket into (adjacent-to-v part first, non-adjacent part second). With a single initial bucket, the first pick is vertex 0 (smallest id, deterministic start), and subsequent picks are the smallest-id vertex of the first bucket — a valid deterministic LexBFS.

Verification on the failing case: graph 0-2-1. Start bucket [0,1,2]; pick 0; refine by N(0)={2}: buckets [[2],[1]]. Pick 2; refine [1] by N(2)∩{1}={1}: buckets [[1]]. Pick 1. Result [0,2,1] — valid.

Do NOT try to "fix" the tie-break by sorting the singleton buckets or by reordering `buckets` after each refinement: with singleton buckets the refinement is a no-op, so no tie-break rule can recover correctness — the bucket structure must actually contain multiple vertices, which requires the single-initial-bucket change.

Also note (not the cause of this failure, but a latent weakness): `_repair`'s local moves (transpose of u,v; move the later of u,v to the earlier position) are not guaranteed to find a valid order even when one exists near the old one, so the fallback must be correct — which it currently is not.
