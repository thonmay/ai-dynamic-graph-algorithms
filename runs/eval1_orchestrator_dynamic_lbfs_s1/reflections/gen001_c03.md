## FAILURE_DESCRIPTION
Case: `init` on the 2-vertex graph with adjacency matrix
```
[[0, 1],
 [1, 0]]
```
(i.e. a single edge 0-1). Expected result `[0, 1]` (any valid LexBFS ordering
of the two vertices, e.g. `[0,1]` or `[1,0]`). Actual result: `[0]` — the
returned ordering contains only ONE vertex; vertex 1 is missing entirely.
The state contract requires `ordering` to be a list of ALL n vertices, so the
verifier rejects the state.

## ROOT_CAUSE
The bug is in `_lexbfs_full` (used directly by `init`), in the bucket
refinement loop:

```python
        # refine remaining buckets by adjacency to v
        Nv = bits[v]
        new_buckets = []
        for bb in buckets:
            nb = bb & Nv
            nb2 = bb & ~Nv
            if nb:
                new_buckets.append(nb)
            if nb2:
                new_buckets.append(nb2)
        buckets = new_buckets
```

`nb2 = bb & ~Nv` is computed with the UNMASKED complement `~Nv`. In Python,
`~Nv` is a negative integer with infinitely many 1-bits above the low word,
so `bb & ~Nv` is not "the vertices of bb not adjacent to v" — it is
`bb & (all bits except Nv's low bits)`, which for a 2-vertex graph with
`Nv = 0b10` gives `~Nv = ...11111101` and `bb & ~Nv` can drop or corrupt
bits depending on the mask width.

Trace on the failing case (n=2, edge 0-1, `bits[0]=0b10`, `bits[1]=0b01`):
1. `buckets = [0b11]`. Pop `b=0b11`, pick lowest set bit → `v=0`. `order=[0]`.
2. Refine remaining buckets: `buckets` is now `[]` (the only bucket was
   popped), so the loop body never executes. `buckets = []`.
3. Loop ends. `order = [0]` — vertex 1 was never emitted.

The deeper structural bug: the algorithm pops the ENTIRE first bucket and
emits only ONE vertex from it (`v = (b & -b).bit_length() - 1`), then discards
the rest of that bucket (`b` is never split back into the queue). In a correct
partition-refinement LexBFS, when a bucket is selected, you emit ONE vertex
from it, and the REMAINING vertices of that bucket must be re-inserted (as
their own bucket) so they are still processed later. Here the leftover
`b ^ (1 << v)` is simply lost, so any bucket with more than one vertex
silently drops all but its lowest-id member. For n=2 the initial bucket
`{0,1}` loses vertex 1 immediately.

The `~Nv` unmasked-complement issue is a second latent bug in the same loop
(it would corrupt refinement for n where `~Nv`'s high bits interact with
`bb`), but the vertex-dropping bug alone fully explains this failure.

## REPAIR_HINTS
Fix `_lexbfs_full` (the only place `init` and the fallback path depend on):

1. **Re-insert the remainder of the popped bucket.** After picking `v` from
   bucket `b`, compute `rest = b & ~(1 << v)` and, if `rest != 0`, append it
   back to `new_buckets` (at the front, to preserve the "first bucket"
   priority). Concretely, replace the loop with:
   ```python
   new_buckets = []
   rest = b & ~(1 << v)
   if rest:
       new_buckets.append(rest)   # keep the remainder of the chosen bucket
   for bb in buckets:
       nb = bb & Nv
       nb2 = bb & (~Nv) & ((1 << n) - 1)   # mask to n bits
       if nb:
           new_buckets.append(nb)
       if nb2:
           new_buckets.append(nb2)
   buckets = new_buckets
   ```
   (Ordering of `rest` vs. the refined buckets: `rest` should come first so
   that the next vertex is drawn from the same original bucket before
   neighbors/non-neighbors of `v` — this matches the standard LexBFS
   refinement where the selected bucket is split into {v} and rest, and rest
   stays at the front.)

2. **Mask the complement.** `~Nv` must be masked to n bits:
   `nb2 = bb & (~Nv) & ((1 << n) - 1)`, or equivalently
   `nb2 = bb & (full_mask ^ Nv)` with `full_mask = (1 << n) - 1`. Without
   this, `bb & ~Nv` uses Python's infinite-precision negative integers and
   the "non-neighbor" split is wrong.

3. **Do NOT** "fix" this by changing `init` to special-case small n or by
   post-filtering the ordering — the same `_lexbfs_full` is the fallback for
   every update, so it must be correct for all n.

4. The `_is_lexbfs` checker and `_try_repair` are not implicated in this
   failure (they are only reached on updates, and the checker's logic is
   consistent with the (LB) property); leave them alone unless a later case
   shows otherwise.
