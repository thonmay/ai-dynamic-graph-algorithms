## FAILURE_DESCRIPTION
n=3. Operation: `delete (1, 2)` at sequence_idx 0. The graph after the deletion has exactly one edge, (0,1) (edge (0,2) was already absent, since the expected valid ordering is [0,2,1] and the only valid LexBFS orderings of a graph with single edge {0,1} are [0,1,2] and [1,0,2]).

- Expected (valid): `[0, 2, 1]`
- Actual (returned): `[0, 1, 2]`
- Verifier violation: a=0, b=1, c=2 at positions 0,1,2 with minD = 1e9, i.e. for the triple (a=0, b=1, c=2): 0~2 in E, 0~1 not in E, and no d<0 exists. This is a genuine (LB) 4-point violation, so the returned ordering is not a valid LexBFS ordering of the post-deletion graph.

## ROOT_CAUSE
The static LexBFS routine is broken, and the "cheap repair" path returns an invalid ordering without ever checking it.

1. `_lexbfs_from` (and therefore `_lexbfs_full`) ignores its `start` argument entirely and always picks the lowest-index vertex of the first bucket:
   ```python
   v = (b & -b).bit_length() - 1  # lowest set bit
   ```
   So it is just "LexBFS with lowest-index tie-break", not a LexBFS seeded from `start`.

2. `_try_repair`'s step 5 trusts the output of `_lexbfs_from` without verifying it:
   ```python
   for start in (u, v):
       cand = _lexbfs_from(graph, start)
       if _is_lexbfs(cand, bits):
           return cand
   ```
   Because `_lexbfs_from` is not a correct LexBFS implementation (see 1), the candidate it produces can fail the (LB) property, and the `_is_lexbfs` guard is supposed to catch that. But the guard itself is buggy:

3. `_is_lexbfs` uses unmasked Python-int negation:
   ```python
   W = Nb & ~Nc
   A = Nc & ~Nb
   ```
   `~Nc` is a negative integer with infinitely many high bits set. `Nb & ~Nc` therefore equals `Nb & ~Nc & full_mask` only by accident of `Nb` being n-bit; that part is fine. The real bug is in the *loop structure*: for a fixed (b, c) it iterates `for ai in range(bi)` and checks `if (A >> a) & 1` where `a = order[ai]`. This is correct in intent, BUT the condition `W & prefix[ai] == 0` is checked for the *first* violating `a` it finds — and the code returns False immediately. That part is actually correct.

   Re-examining: the actual bug is simpler. In `_try_repair`, step 5 runs BEFORE the plain-candidate checks (steps 1–3). For the failing case, `_lexbfs_from(graph, 1)` (start=1, but start is ignored) produces `[0, 1, 2]` (lowest-index tie-break on the graph with edge {0,1}). Then `_is_lexbfs([0,1,2], bits)` is called. Let's trace it:
   - order = [0,1,2], bits: N(0)={1}, N(1)={0}, N(2)={}.
   - bi=0: b=0, Nb={1}. ci=1: c=1, Nc={0}. W = Nb & ~Nc = {1} & ~{0} = {1}. A = Nc & ~Nb = {0} & ~{1} = {0}. ai=0: a=order[0]=0. (A>>0)&1 = 1. W & prefix[0] = {1} & {} = 0 → return False.
   
   So `_is_lexbfs` correctly rejects [0,1,2]. Then `_lexbfs_from(graph, 2)` (start=2, ignored) also produces [0,1,2], also rejected.

   Then the plain candidates are checked:
   - Candidate 1: old ordering. The old ordering (before deletion) was a valid LexBFS of the graph with edges {0,1} and {1,2}, i.e. path 0-1-2. A valid LexBFS of path 0-1-2 is [0,1,2] or [2,1,0]. The old ordering was [0,1,2]. After deleting (1,2), [0,1,2] is invalid (as shown above). `_is_lexbfs` rejects it.
   - Candidate 2: front=[1,2], rest=[0] → [1,2,0]. Check: N(1)={0}, N(2)={}, N(0)={1}. bi=0: b=1, Nb={0}. ci=1: c=2, Nc={}. W={0}&~{}={0}. A={}&~{0}={}. No a in A. ci=2: c=0, Nc={1}. W={0}&~{1}={0}. A={1}&~{0}={1}. ai=0: a=1. (A>>1)&1=1. W&prefix[0]={0}&{}=0 → False. Rejected.
   - Candidate 3: front reversed=[2,1], rest=[0] → [2,1,0]. Check: N(2)={}, N(1)={0}, N(0)={1}. bi=0: b=2, Nb={}. W always 0. bi=1: b=1, Nb={0}. ci=2: c=0, Nc={1}. W={0}&~{1}={0}. A={1}&~{0}={1}. ai=0: a=2. (A>>2)&1=0. ai=1: a=1. (A>>1)&1=1. W&prefix[1]={0}&{2}=0 → False. Rejected.

   All candidates rejected → `_try_repair` returns None → fallback `_lexbfs_full(graph)` is called.

4. The fallback `_lexbfs_full` calls `_lexbfs_from(graph, 0)` which (ignoring start) produces [0,1,2] via lowest-index tie-break. This is returned WITHOUT any `_is_lexbfs` check:
   ```python
   def delete_edge(graph, edge, state):
       order = _try_repair(graph, edge, state)
       if order is None:
           order = _lexbfs_full(graph)   # <-- no validation
       return {'ordering': order}
   ```

So the root cause is: **`_lexbfs_full` / `_lexbfs_from` is not a correct LexBFS implementation** (it ignores `start` and uses lowest-index tie-break, which does not in general produce a valid LexBFS ordering — it produces a valid one only when the lowest-index tie-break happens to coincide with a valid LexBFS, which is not guaranteed). The fallback path returns its output without validation, so an invalid ordering is returned.

Wait — actually, the standard HMPV LexBFS with ANY consistent tie-break (including lowest-index) DOES produce a valid LexBFS ordering. Let me re-examine whether [0,1,2] is truly invalid for the graph with edge {0,1} only.

Graph: 3 vertices, edge (0,1) only. N(0)={1}, N(1)={0}, N(2)={}.
Ordering [0,1,2]: positions 0,1,2.

- a=0,b=1,c=2: adj(0,2)? No. Skip.
- a=0,b=2,c=... no c after 2.
- a=1,b=2,c=... no.
So [0,1,2] is actually VALID for the graph with only edge (0,1)!

This means the graph after deletion must have edge (0,2) present. Let me reconsider: the violation says a=0,b=1,c=2 with adj(a,c)=adj(0,2)=True and not adj(a,b)=not adj(0,1)=True. So the post-deletion graph has edge (0,2) but NOT edge (0,1). The deleted edge was (1,2). So the pre-deletion graph had edges (0,2) and (1,2), and possibly (0,1). After deleting (1,2), the graph has edge (0,2) and possibly (0,1).

Given the violation: adj(0,2)=True, adj(0,1)=False. So post-deletion graph has edge (0,2) only (among the relevant pairs). N(0)={2}, N(1)={}, N(2)={0}.

Now [0,1,2]: a=0,b=1,c=2. adj(0,2)=True, adj(0,1)=False. Need d<0: none. VIOLATION. Confirmed invalid.

Valid ordering [0,2,1]: a=0,b=2,c=1? No, positions: 0 at pos 0, 2 at pos 1, 1 at pos 2. a=0,b=2,c=1: adj(0,1)=False. Skip. a=0,b=1,c=2: positions 0,2,1 — not a<b<c in position order. a=2,b=1: pos 1,2. adj(2,1)=False. No violations. Valid.

Now re-trace `_lexbfs_from` on graph with N(0)={2}, N(1)={}, N(2)={0}:
- buckets=[{0,1,2}]. v=lowest=0. order=[0]. rest={1,2}. Nv=N(0)={2}.
- new_buckets: no buckets[1:]. rest={1,2} appended. buckets=[{1,2}].
- v=lowest in {1,2}=1. order=[0,1]. rest={2}. Nv=N(1)={}.
- new_buckets: rest={2}. buckets=[{2}].
- v=2. order=[0,1,2].

So `_lexbfs_full` returns [0,1,2], which is INVALID for this graph. This confirms the HMPV implementation is buggy.

The bug: when we take vertex v from the first bucket, the remaining vertices in that bucket (`rest`) should be refined by adjacency to v and placed in the correct position relative to the other refined buckets. The code appends `rest` at the END of `new_buckets`, but it should be split into `rest & Nv` and `rest & ~Nv` and interleaved with the other buckets' refinements in the correct order. In the standard HMPV algorithm, the first bucket is split: the neighbors of v (from rest) go before the non-neighbors, and this split bucket is placed at the front (since it was the first bucket). The code instead puts the unrefined `rest` at the end.

## REPAIR_HINTS
The core bug is in `_lexbfs_from` (and the duplicate `_lexbfs_full`): the `rest` (remaining vertices of the first bucket after removing v) is appended unrefined at the end of `new_buckets` instead of being split by adjacency to v and placed at the front.

Fix in `_lexbfs_from`:
```python
# After taking v from buckets[0]:
rest = b & ~(1 << v)
Nv = bits[v]
new_buckets = []
# rest was the first bucket, so its refined parts go first:
rest_nb = rest & Nv
rest_nb2 = rest & (~Nv) & full_mask
if rest_nb:
    new_buckets.append(rest_nb)
if rest_nb2:
    new_buckets.append(rest_nb2)
# then refine the other buckets
for bb in buckets[1:]:
    nb = bb & Nv
    nb2 = bb & (~Nv) & full_mask
    if nb:
        new_buckets.append(nb)
    if nb2:
        new_buckets.append(nb2)
buckets = new_buckets
```

Additionally, `_lexbfs_from` should actually use its `start` parameter: initialize `buckets` as `[(1 << start), full_mask & ~(1 << start)]` so that `start` is picked first.

Also, the fallback in `insert_edge`/`delete_edge` should validate the result of `_lexbfs_full` with `_is_lexbfs` before returning, as a safety net.

Approaches that will NOT work:
- Just adding `_is_lexbfs` validation to the fallback without fixing `_lexbfs_from`: it would catch the bug but then have no valid ordering to return (all candidates would fail), causing an infinite loop or crash.
- Relying on the "move u,v to front" heuristics: these are not guaranteed to produce a valid LexBFS ordering for arbitrary graphs.
