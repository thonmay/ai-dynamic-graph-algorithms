## FAILURE_DESCRIPTION
Operation: `init` on a 4-vertex undirected graph (sequence_idx 0, so no prior updates).
`init` returned ordering `[0, 1, 2, 3]`; the verifier expected `[0, 1, 3, 2]` (i.e. `[0,1,2,3]` is NOT a valid LexBFS ordering of the graph).

The verifier's violation report: a=1, b=2, c=3 with pos_a=1 and minD=1000000000 (sentinel = "no valid d found").
Interpreted as positions in the returned ordering: pos_a=1 → a=1, b=2, c=3. The violated (LB) 4-point condition is:
  a=1, b=2, c=3 with 1-3 in E and 1-2 not in E, and NO d < a (i.e. d=0) satisfies 0-2 in E and 0-3 not in E.

The exact adjacency matrix is not included in the failure record, so the graph edges are not fully known; however the violation itself pins down the constraints: 1-3 ∈ E, 1-2 ∉ E, and for d=0 either 0-2 ∉ E or 0-3 ∈ E.

## ROOT_CAUSE
The bug is in the static partition-refinement LexBFS, `_lexbfs` (lines ~44-77). The queue discipline is wrong: it is a FIFO queue, but LexBFS requires a **priority queue ordered by the lexicographic label of each class**.

Concretely, when a class is processed, its first vertex v is output and the remainder is split into `neigh` (adjacent to v) and `non` (not adjacent to v). The code inserts both new classes at `insert_pos = head` — i.e. immediately after the just-processed class, in the fixed order neigh-then-non. This is only correct if the new classes' labels are lexicographically smaller than every class already queued behind `head`. They are not, in general:

- A class already in the queue may have been split by an EARLIER vertex w, giving it a label like `1...` (adjacent to w) or `0...`.
- The new `non` class has label `0` (not adjacent to v), and the new `neigh` class has label `1`.
- If an already-queued class has label `0...` (e.g. a `non` class from an earlier split), the new `neigh` class (label `1`) must be processed AFTER it, but the FIFO insertion puts it BEFORE.

On the failing 4-vertex graph this mis-ordering causes vertex 2 to be output before vertex 3, producing `[0,1,2,3]` instead of the valid `[0,1,3,2]`. The (LB) certificate then fails at (a,b,c)=(1,2,3) as reported.

Note: `_check_lb` (the 4-point checker) is NOT the root cause — it is only invoked inside `_local_repair`, which is never called from `init`. `init` returns `_lexbfs`'s output directly with no validation.

## REPAIR_HINTS
1. **Fix `_lexbfs` to use a proper priority queue keyed by lexicographic label.** Each class must carry its label (the sequence of 0/1 adjacency decisions from the vertices that split it). When a class is split by vertex v, the `neigh` child inherits label + '1' and the `non` child inherits label + '0'. Always process the class with the lexicographically smallest label (ties broken by vertex id, which the initial ordering already provides). In Python, use `heapq` with the label as a tuple of ints (or a string of '0'/'1') as the sort key. This is the standard HMPV LexBFS and will produce a valid ordering for the failing graph.

2. **Do NOT rely on the FIFO insertion at `insert_pos = head`** — that is the specific broken line. The `q.insert(insert_pos, ...)` calls must be replaced with `heapq.heappush` using the label key.

3. **Optional safety net:** after `_lexbfs` returns, call `_check_lb` and assert (or fall back to a brute-force search over all n! orderings for tiny n) to catch any residual bug. This is cheap for n ≤ 8 and would have caught this failure at `init` time.

4. **Approaches that will NOT work:**
   - Simply swapping the insertion order to `non`-then-`neigh` does not fix it; the correct order depends on the full label, not just the last split.
   - Keeping the FIFO queue but re-sorting the queue after each split is equivalent to a priority queue but less clean; just use `heapq`.
   - The `_local_repair` path is irrelevant to this failure (init never calls it), so fixing only the repair logic will not help.
