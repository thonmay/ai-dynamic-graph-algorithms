## FAILURE_DESCRIPTION
Operation `insert (2,0)` on a 4-vertex graph (sequence_idx 0). The post-update graph G1 contains edges (0,2), (0,3), (1,3), (2,3) (the verifier's violation triple a=2, b=1, c=3 requires 2–3 in E). The candidate returned `[0, 2, 1, 3]`; the expected valid LexBFS ordering is `[0, 2, 3, 1]`. The verifier reports the (LB) violation at (a=2, b=1, c=3, pos_a=1): a<b<c, ac=2–3 in E, ab=2–1 not in E, and no d < a (only d=0) with d–b in E and d–c not in E (0–1 is not an edge).

## ROOT_CAUSE
The validity checker `_is_valid_lexbfs` implements the wrong (LB) condition, and because every other code path (repair candidates, `_ensure_valid`, `_brute_force_lexbfs`) is gated on it, the bug corrupts the whole pipeline.

The (LB) property requires: for a<b<c with ac in E and ab not in E, **exists d < a with d–b in E and d–c not in E**, i.e. `∃d ∈ P_a: d ∈ N_b ∧ d ∉ N_c`.

The code (in the inner c-loop) instead tests:

```python
if (Na & prefix & ~N[vc]) == 0:
    bad = True
```

i.e. `∃d ∈ P_a ∩ N_a: d ∉ N_c`. It substitutes `d ∈ N_a` for the required `d ∈ N_b`. The docstring even states the correct condition ("exists d < a with db in E and dc not in E") while the code checks adjacency to `a` rather than to `b`.

Trace on the failing case (order `[0,2,1,3]`, G1): a=1 (va=2), b=2 (vb=1), c=3 (vc=3). 2–3 in E, 2–1 not in E. True property: d must be in P_a={0} ∩ N_1={0,3} = ∅ → no witness → INVALID. Code: `Na & prefix & ~N[3]` = {0} & {0} & ~{0,1,3} = ∅ → `bad=True` → should return False. But `_try_repair` returned the old order, so the checker returned True — the only way that happens is that the checker's condition is the wrong one (it accepted on the spurious witness d=0, which is adjacent to a=2 but not to b=1).

The same bug poisons the fallback: `_lexbfs_full(G1)` actually produces the correct `[0,2,3,1]` (trace: pick 0 → buckets [1],[2],[3]; pick 2 → [1],[3]; pick 3 → [1]; pick 1). But `_ensure_valid` runs the buggy checker on it: a=1 (va=2), b=2 (vb=3), c=3 (vb=1): 2–1 not in E, 2–3 in E; code test `Na & prefix & ~N[1]` = {0} & {0} & ~{0,3} = ∅ → `bad=True` → False. So the correct order is rejected, `_brute_force_lexbfs` (same checker) finds no permutation, and `_ensure_valid` returns the invalid order as-is.

## REPAIR_HINTS
1. **Fix the witness test in `_is_valid_lexbfs`** (the inner c-loop). Replace
   `if (Na & prefix & ~N[vc]) == 0:` with
   `if (N[vb] & prefix & ~N[vc]) == 0:`
   i.e. test `∃d ∈ P_a ∩ N_b: d ∉ N_c`. This is the minimal change; it makes the checker match the (LB) property and the docstring.
2. After the fix, the existing architecture works: `_try_repair` will correctly reject the stale order on this case, `_lexbfs_full` will produce `[0,2,3,1]`, and `_ensure_valid` will accept it.
3. **Do not** try to "fix" this by making `_ensure_valid` trust `_lexbfs_full` unconditionally or by skipping the checker — the checker is the only certification, and `_brute_force_lexbfs` also depends on it.
4. **Do not** attempt to repair by changing `_lexbfs_full` or `_try_repair`; both are fine. The single defect is the `Na` vs `N[vb]` substitution in the checker.
5. Note the checker is O(n^3) per call and `_try_repair` calls it up to 8 times per update; that is acceptable for correctness-first, but keep the fix local to the one line so no other behavior changes.
