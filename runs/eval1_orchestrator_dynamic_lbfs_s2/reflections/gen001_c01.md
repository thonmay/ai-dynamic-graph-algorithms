## FAILURE_DESCRIPTION
3-vertex undirected graph. Initial graph (before the update) has only edge (0,1); init produced ordering [0, 1, 2]. The failing operation is `insert (0, 2)`, yielding the path 1-0-2 (edges (0,1) and (0,2)). The candidate returned ordering [0, 1, 2], but the only valid LexBFS orderings of this path are [1, 0, 2] and [2, 0, 1] (the middle vertex 0 must come second). The verifier reports the (LB) violation at a=0, b=1, c=2, pos_a=0: positions 0<1<2, ac=(0,2) in E, ab=(0,1) not in E, and no d < a exists (pos_a=0, minD=1e9 sentinel).

## ROOT_CAUSE
The certificate check `_certify` is wrong: it uses **vertex ids** as the position mask instead of **positions in the ordering**.

In `_certify`, for the triple (a at position i, b at position j, c at position k):
- `prefix = (1 << i) - 1` is intended to be "vertices d at position < i", but it is actually "vertices with id < i".
- `cands = na & ~((1 << (j + 1)) - 1)` is intended to be "c at position > j", but it is actually "c with id > j".
- The witness test `(nb & ~bs[cc] & prefix) == 0` then tests "d with id < i", not "d at position < i".

Tracing the failing case, order = [0, 1, 2], graph edges (0,1),(0,2):
- i=0, a=0, na={1,2}, prefix=(1<<0)-1=0.
- j=1, b=1: (na>>1)&1 = 1, so `continue` — the real violation (a=0,b=1,c=2) is skipped because 0~1 is an edge.
- j=2, b=2: (na>>2)&1 = 1, `continue`.
- i=1, a=1, na={0}: j=2, b=2, (na>>2)&1=0; cands = na & ~((1<<3)-1) = {0} & ~0b111 = 0, skip.
- i=2: no j. `_certify` returns True.

So the buggy check passes the invalid ordering [0,1,2], `insert_edge` keeps it, and the verifier finds the genuine violation (a=0,b=1,c=2, no d before position 0).

Note the check is also asymmetric: it only tests triples where b is a non-neighbor of a and c is a neighbor of a, but the (LB) property must hold for both orientations (ac in E / ab not in E AND ab in E / ac not in E). In this particular case that asymmetry is not the trigger (the real violation is in the tested orientation), but it is a second latent bug: e.g. order [1,0,2] on the path 1-0-2 would be wrongly rejected at (a=1,b=0,c=2) because the "ab in E, ac not in E" orientation is never checked.

## REPAIR_HINTS
1. Fix `_certify` to work in **position space**, not vertex-id space. Build `pos[v] = position of v in order` and, for each position p, a bitset `P[p]` of vertices at positions < p (or equivalently, precompute for each vertex v the bitset of vertices appearing before v in the ordering). Then:
   - `prefix` for a at position i = bitset of vertices at positions < i (i.e. `P[i]`), not `(1 << i) - 1`.
   - `cands` for b at position j = neighbors of a whose position is > j, i.e. `na & (positions_after[j])`, not `na & ~((1 << (j+1)) - 1)`.
   - witness test: `(nb & ~bs[cc] & P[i]) != 0`.
2. Make the check symmetric: for each pair of positions i < j with a=order[i], b=order[j], check both orientations — (a~b and a not~c for c after j) and (a not~b and a~c for c after j) — each requiring a witness d at position < i with db in E and dc not in E.
3. After fixing `_certify`, the overall strategy (certify-then-keep, else recompute) is sound: `_lexbfs` itself is a correct static partition-refinement LexBFS, so `_recompute` always yields a valid ordering. The only defect is the certificate.
4. Do NOT try to "fix" this by special-casing small n or by comparing against a reference LexBFS — the certificate must be a correct, self-contained validity test, since the whole keep-vs-recompute decision depends on it.
5. Performance note (not required for correctness): the O(n^3)-ish triple loop with bitsets is fine for small n; for larger n, precomputing the position-prefix bitsets once per call keeps the inner test O(1) per (a,b,c) triple.
