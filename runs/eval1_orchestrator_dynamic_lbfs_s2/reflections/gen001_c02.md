## FAILURE_DESCRIPTION
Failing case (sequence_idx 2, operation `insert (0, 3)` on a 4-vertex undirected graph).
The candidate returned the unchanged ordering `[0, 1, 2, 3]`; the verifier expected `[0, 1, 3, 2]` and reported a 4-point violation at positions `a=1, b=2, c=3` (pos_a=1, minD=1e9, i.e. no witness d exists).

Reconstructing the graph from the case:
- The pre-insertion graph must have been a path 0-1-2-3 (edges {0,1},{1,2},{2,3}). Its unique LexBFS ordering is `[0,1,2,3]`, which is what `init` produced and what the candidate kept.
- After inserting (0,3) the graph is the 4-cycle 0-1-2-3-0. In the ordering `[0,1,2,3]` the triple (a=1, b=2, c=3) has ac=13 in E, ab=12 not in E, and the only candidate witness d=0 fails because 03 is now in E (dc not in E is false). So `[0,1,2,3]` is no longer a valid LexBFS ordering; the valid one is `[0,1,3,2]`.

## ROOT_CAUSE
`insert_edge` only checks 4-point triples in which the newly inserted edge is the "ac" edge (the two cases `a=u,c=v` and `a=v,c=u`). It never checks triples in which the new edge is the "dc" edge, i.e. triples where the new edge *destroys an existing witness*.

In the failing case the new edge (0,3) is exactly the dc edge of the triple (a=1, b=2, c=3): before the insertion d=0 witnessed it (02 in E, 03 not in E); after the insertion 03 in E, so the witness is gone and the triple becomes a violation. The code's own docstring claim — "It cannot create new non-edges, so it cannot create new 'ab not in E' or 'dc not in E' conditions" — is wrong: adding an edge turns a previously-true "dc not in E" into false, which can invalidate a previously-satisfied 4-point condition.

Concretely, the missing check in `insert_edge` is: for the new edge (u,v), for every triple (a,b,c) with pos[b] < pos[a] < pos[c], ab not in E, ac in E, and {d,c} = {u,v} (d the other endpoint of the new edge, d < a), verify that some *other* d' < a still witnesses (d'b in E, d'c not in E). If none exists, the ordering is invalid and must be recomputed. The symmetric case (d=v, c=u) is needed too.

## REPAIR_HINTS
Smallest concrete fix: in `insert_edge`, after the existing two "ac = new edge" cases, add the two "dc = new edge" cases (mirror of `delete_edge`'s Case 2a/2b, but with the witness-existence test over the *updated* graph):

- Case 3a (d = u, c = v, pu < pv): for every a with pv < pos[a] < pu, if graph[a][v] == 0 (ab not in E) and for every c with pos[a] < pos[c] < pu and graph[a][c] == 1 (ac in E): require exists d' < a, d' != u, with graph[d'][v] == 1 and graph[d'][c] == 0. If not found, `return {'ordering': _recompute(graph)}`.
- Case 3b (d = v, c = u, pv < pu): symmetric with u and v swapped.

Note the position ranges: since d < a < c and {d,c} = {u,v}, a must lie strictly between pu and pv, and c must lie between a and the other endpoint's position.

Approaches that will NOT work:
- Relying on the existing "ac = new edge" checks only (the current code) — they miss witness-destroying insertions, as this case shows.
- Checking only whether the new edge itself participates as a/b — the new edge can also be the dc edge, which is the only role it plays here.
- A cheaper "local swap" repair (e.g. moving v before b) is not guaranteed to restore validity in general; recomputing via `_recompute(graph)` when the extended check fails is the safe fallback and is what the rest of the candidate already does.
