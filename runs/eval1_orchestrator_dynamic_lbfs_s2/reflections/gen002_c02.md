## FAILURE_DESCRIPTION
Failing case: n=4, operation `insert (0, 3)` (sequence_idx 2). The candidate returned the unchanged ordering `[0, 1, 2, 3]`; the verifier reports it is invalid with a 4-point violation at (a,b,c) = (1,2,3), pos_a = 1, minD = 10^9 (no witness d < a found). The expected valid ordering is `[0, 1, 3, 2]`.

Reconstructed post-update graph (consistent with every observable): edges {0-1, 0-2, 0-3, 1-2, 1-3}. In the returned ordering [0,1,2,3]: a=1, b=2, c=3; ac = 1-3 in E, ab = 1-2 in E... wait — the verifier's violation requires ab NOT in E, so the actual graph must have 1-2 absent. The exact pre-update edge set is not given in the task, so I cannot 100% pin down the matrix; however the violation record (a=1,b=2,c=3, no witness d<1) is fully consistent with the graph having edges {0-1, 0-2, 0-3, 1-3} (1-2 absent): then a=1,b=2,c=3 has ac=1-3 in E, ab=1-2 not in E, and the only candidate witness d=0 fails because 0-2 in E (dc must be not in E). The expected ordering [0,1,3,2] is a valid LexBFS of that graph, and the candidate's own `_recompute` would have produced it.

## ROOT_CAUSE
`insert_edge`'s incremental validity check is incomplete: it only inspects 4-point tuples in which the updated edge (u,v) participates as the ac pair (Cases 1/2) or as the dc pair (Cases 3a/3b). It never checks tuples where the updated edge participates as the **ab pair** — i.e., a = u, b = v (or a = v, b = u) with an arbitrary c > b.

In the failing case u=0, v=3, pu=0, pv=3. The new edge (0,3) makes ab = 0-3 an edge, which *activates* the 4-point condition for every c > 3 with 0-c in E and 3-c not in E, requiring a witness d < 0. Since pu = 0, no such d can exist, so the ordering is invalid. But the code's Case 1 loop is `for b in range(pu + 1, pv)` with the guard `if graph[u][vb]: continue` — it only looks at b strictly between u and v and skips b adjacent to u; the tuple (a=u, b=v, c=anything) is never examined. The check therefore concluded "still valid" and returned the stale state.

Note the asymmetry: `delete_edge` DOES handle the ab-pair case (its Case 1a/1b: a=u, b=v, c > pv), because deleting an edge creates new "ab not in E" conditions. The insert side is missing the mirror image: inserting an edge creates new "ab in E" conditions, which activate 4-point obligations for (a=u, b=v, c) and (a=v, b=u, c).

## REPAIR_HINTS
1. In `insert_edge`, add the missing ab-pair cases (mirror of delete_edge's Case 1a/1b):
   - If pu < pv: for every c in range(pv + 1, n) with graph[u][vc] == 1 and graph[v][vc] == 0, require exists d in range(pu) with graph[vd][v] == 1 and graph[vd][vc] == 0; otherwise recompute.
   - If pv < pu: symmetric with u and v swapped (c in range(pu + 1, n), graph[v][vc] == 1 and graph[u][vc] == 0, witness d < pv with graph[d][u] == 1 and graph[d][c] == 0).
   This is exactly the logic already present in `delete_edge` Cases 1a/1b, just with the "ab not in E" trigger replaced by "ab in E" (the new edge) and the witness condition db in E / dc not in E unchanged.
2. Do NOT rely on patching only this case: the same "only check tuples containing the updated edge" pattern is fragile in general (e.g., the dc-destroyed-witness cases 3a/3b restrict c to the interval between u and v, which is also suspicious). The robust minimal fix for full correctness is: after any update, run a full O(n^4) (or O(n^3)) 4-point property check over the returned ordering against the current graph, and recompute via `_recompute(graph)` if any violation is found. This guarantees correctness for all update shapes and can be layered with the incremental checks as a fast path.
3. Approaches that will not work: (a) keeping the current four-case structure and just widening the b-range in Case 1 — the missing case is a different tuple shape (b = v itself, c beyond v), not a range bug; (b) trusting the incremental check alone without a full-property fallback, since the case analysis is easy to get wrong (as this failure shows).
