## FAILURE_DESCRIPTION
Failing case: 4-vertex undirected graph, operation `insert (2, 0)` at sequence_idx 0.
The candidate returned ordering `[0, 2, 1, 3]`, but the expected (valid) ordering is `[0, 2, 3, 1]`.

The violation reported is the (LB) 4-point property:
- a = 2 (pos 1), b = 1 (pos 2), c = 3 (pos 3)
- ac in E (edge 2-3 exists), ab not in E (edge 2-1 does not exist)
- No d < a (i.e., d = 0) satisfies db in E and dc not in E.
  - d=0: 0-1 in E? Yes. 0-3 not in E? No (0-3 IS in E). So d=0 fails.
- minD = 1000000000 (sentinel meaning no valid d found).

So the returned ordering `[0, 2, 1, 3]` is NOT a valid LexBFS ordering of the post-insertion graph.

## ROOT_CAUSE
The bug is in `_is_valid_lexbfs`: it uses the **prefix-neighbor property** as its validity check, but this property is **not equivalent** to the (LB) 4-point property for LexBFS validity.

The prefix-neighbor property states: for every prefix P of the ordering, N(P) ∩ R must be a prefix of R. This is a necessary condition for LexBFS but is **not sufficient** to certify that the ordering is a valid LexBFS ordering. The (LB) 4-point property (Corneil-Krueger) is the correct certificate.

Tracing the failing case:
- Post-insertion graph edges: {0-1, 0-2, 0-3, 2-3} (edge 2-0 was inserted; 0-1, 0-3, 2-3 were pre-existing).
- Ordering `[0, 2, 1, 3]`:
  - Prefix P={0}: N(P)∩R = {1,2,3} (all neighbors of 0 in R={2,1,3}). Is {1,2,3} a prefix of R=[2,1,3]? R starts with 2, then 1, then 3. N={1,2,3}. Scanning R: 2∈N, 1∈N, 3∈N. All in N, so yes, it's a prefix (the whole R). ✓
  - Prefix P={0,2}: N(P)∩R = N({0,2})∩{1,3} = {1,3}∩{1,3} = {1,3}. Is {1,3} a prefix of R=[1,3]? Scanning: 1∈N, 3∈N. Yes. ✓
  - Prefix P={0,2,1}: N(P)∩R = N({0,2,1})∩{3} = {3}∩{3} = {3}. Is {3} a prefix of R=[3]? Yes. ✓
  - Prefix P={0,2,1,3}: R is empty. ✓

So `_is_valid_lexbfs` returns True for `[0, 2, 1, 3]`, and `insert_edge` keeps the old ordering. But the ordering is actually invalid per the (LB) 4-point property (as shown above). The prefix-neighbor check is **too weak** — it does not catch this violation.

The root cause: the prefix-neighbor property is a necessary but not sufficient condition for LexBFS validity. The code's comment claims "This is equivalent to the (LB) 4-point property of Corneil-Krueger" but it is NOT equivalent. The (LB) 4-point property is strictly stronger.

## REPAIR_HINTS
1. **Replace `_is_valid_lexbfs` with a direct check of the (LB) 4-point property.** For all triples of positions a < b < c in the ordering, if ac ∈ E and ab ∉ E, then there must exist d < a with db ∈ E and dc ∉ E. This is O(n^4) in the worst case but is correct. For n up to a few hundred this is fine.

   Pseudocode:
   ```
   for a in range(n):
       for b in range(a+1, n):
           for c in range(b+1, n):
               va, vb, vc = ordering[a], ordering[b], ordering[c]
               if adj[va][vc] and not adj[va][vb]:
                   found = False
                   for d in range(a):
                       vd = ordering[d]
                       if adj[vd][vb] and not adj[vd][vc]:
                           found = True
                           break
                   if not found:
                       return False
   return True
   ```

2. **Do NOT try to fix the prefix-neighbor check by adding more conditions.** The prefix-neighbor property is fundamentally insufficient; no amount of patching will make it equivalent to the (LB) property. The (LB) 4-point property is the correct and complete certificate.

3. The static `_lexbfs` function is correct (standard HMPV partition refinement). The bug is purely in the validity checker used by `insert_edge`.

4. For performance, the O(n^4) check can be optimized to O(n^3) by precomputing, for each pair (a,c) with ac∈E, the set of b's that are non-neighbors of a, and checking if any such b has no valid d. But correctness first.
