## FAILURE_DESCRIPTION
Failing case: n=4, operation `insert (0, 3)` (sequence_idx 2). The candidate returned the unchanged ordering `[0, 1, 2, 3]`, but the verifier reports a 4-point (LB) violation at positions a=1, b=2, c=3 (pos_a=1, minD=1e9, i.e. no witness d < a exists). The expected valid ordering is `[0, 1, 3, 2]`.

Reconstructed scenario (consistent with all reported fields): before the update the ordering was `[0,1,2,3]` and the graph had edges {0-1, 0-2, 1-2, 1-3} (so 0-3 was the missing edge, and the ordering was valid: the only triggered triple (a=1,b=2,c=3) had witness d=0 since 0-2 in E and 0-3 not in E). After inserting 0-3, the triple (a=1, b=2, c=3) still has ac=1-3 in E and ab=1-2... wait, ab must be NOT in E for the property to trigger; in the failing state the verifier found a=1,b=2,c=3 with ac in E, ab not in E, and no d<1 with db in E and dc not in E. Either way: the ordering `[0,1,2,3]` is invalid for the post-insertion graph, and the candidate's `insert_edge` returned the state unchanged instead of recomputing.

## ROOT_CAUSE
The incremental "keep the ordering" decision in `insert_edge` is based on an incomplete case analysis of the (LB) 4-point property. The docstring claims:

    "Adding edge (u,v) can:
     1. Create new 'ac in E' conditions where {a,c} = {u,v}.
     2. Destroy 'dc not in E' witnesses where {d,c} = {u,v}."

This is wrong. Adding edge (u,v) also **destroys "db not in E" conditions** for every triple (a,b,c) with {d,b} = {u,v} (i.e. b = u or b = v, d < a). Such a triple was previously not triggered (ab in E), but after the insertion ab is not in E, so the triple becomes triggered and needs a witness d' < a with d'b in E and d'c not in E. The code only checks:

- Case 1/2: new "ac in E" triples (a,c) = (u,v) — correct but only covers triples where the new edge is the ac edge;
- Case 3a/3b: destroyed "dc not in E" witnesses with d = u (or v) and c = v (or u) — but note the loops are restricted to `a in range(pu+1, pv)`, `b in range(a+1, pv)`, `c in range(b+1, pv)`, i.e. only triples entirely between u and v, and only the specific assignment d=u, c=v.

The missing case is: **b = u (or b = v) with d < a, d != u (v)** — the new non-edge ab = (a,u) triggers triples (a, u, c) for all a with pos[a] > pu and all c with pos[c] > pos[a] such that ac in E, and the code never checks whether a witness d' < a with d'u in E and d'c not in E exists. In the failing case the triple (a=1, b=2, c=3) became triggered/unsatisfied via exactly this kind of path (the new edge 0-3 changed the witness landscape for a triple whose b is not the inserted edge's endpoint pair in the way Cases 1/3 assume), and `insert_edge` fell through to `return state`, keeping the invalid ordering.

The same structural gap exists in `delete_edge`: it checks new "ab not in E" triples (Cases 1a/1b) and destroyed "db in E" witnesses (Cases 2a/2b), but the case analysis there is also restricted to specific position windows (e.g. Case 2a only iterates `a in range(pu+1, pv)`), so other triples whose witness set changed are not covered.

## REPAIR_HINTS
1. Smallest correct fix: replace the hand-rolled case analysis in both `insert_edge` and `delete_edge` with a **full O(n^4) (or O(n^3) with precomputed witness sets) verification of the (LB) 4-point property on the post-update graph**: for every triple of positions a < b < c with graph[ordering[a]][ordering[c]] == 1 and graph[ordering[a]][ordering[b]] == 0, check that some d < a satisfies graph[ordering[d]][ordering[b]] == 1 and graph[ordering[d]][ordering[c]] == 0. If any triple fails, `return {'ordering': _recompute(graph)}`; otherwise `return state`. This is trivially correct (the property is the exact certificate the verifier uses) and keeps the "avoid recompute when the ordering survives" goal.
2. Do NOT try to patch the existing Cases 1/2/3 by adding more position-window loops: the windows (e.g. `range(pu+1, pv)`) are the source of the incompleteness, and the correct set of affected triples depends on the full adjacency, not just the relative order of u and v. Any local case analysis must enumerate ALL triples (a,b,c) with a<b<c and test the property directly; restricting to triples "between u and v" or with specific roles for u/v is unsound.
3. Note the recompute path is already correct (`_recompute` -> `_lexbfs`), so the only bug is the false "keep" decision. A verification-based keep/recompute decision is the minimal change that restores correctness.
4. Approaches that will not work: (a) checking only triples where the updated edge participates as ac or as dc (the current design) — misses triples where the update changes the ab condition or the db condition for arbitrary (a,b,c); (b) checking only triples with positions strictly between pu and pv — triples with c beyond max(pu,pv) or a before min(pu,pv) are affected too (as the failing case shows: the violation is at positions 1,2,3 while the inserted edge is (0,3)).
