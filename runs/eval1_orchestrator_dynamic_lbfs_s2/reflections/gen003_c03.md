## FAILURE_DESCRIPTION
n=3. Initial graph (before the update) has only edge (1,2); init produced ordering [0, 2, 1] (vertex 0 isolated, then 2, then 1). The update is `insert (0, 1)`, so the graph after the update has edges (0,1) and (1,2). The candidate returned the old ordering [0, 2, 1] unchanged (it reported the state valid), but the verifier found an (LB) violation at positions a=0, b=2, c=1 (vertices 0, 1, 2): ac=(0,2) not in E, ab=(0,1) in E, and no d < a exists. Expected a valid ordering, e.g. [0, 1, 2].

## ROOT_CAUSE
The (LB) check in `_is_valid_lexbfs` has the antecedent of the 4-point property inverted. The property is: for all a < b < c with **ac in E and ab not in E**, there must exist d < a with db in E and dc not in E. The code instead tests:

```python
if (Nvb >> a) & 1:          # ab IN E  -> skip (should be: ab NOT in E -> skip)
    S |= 1 << a
    continue
# ab not in E; violation iff exists c > b with ac in E and S subset of N(c).
```

It skips exactly the pairs (a,b) with ab in E and treats pairs with ab NOT in E as the ones to check, with the violation condition "exists c > b with ac in E and S subset of N(c)" — the exact negation of the real property. Consequences:

1. It never detects the actual violation class (ac in E, ab not in E, no separating d). In the failing case, the true violation is (a=0, b=2, c=1): ac=(0,2) not in E... wait — the verifier's violation has ac NOT in E, which is the *other* direction of the 4-point property (the (LB) property is symmetric in the sense that the standard statement is: for all a<b<c with ac in E and ab not in E, exists d<a with db in E and dc not in E; equivalently, for all a<b<c with ac not in E and ab in E, exists d<a with db not in E and dc in E). The verifier reports the second form (a=0, b=2, c=1: ab=(0,1) in E, ac=(0,2) not in E, no d<a). The code's check for the first form is also wrong because of the inverted antecedent, so neither direction is ever correctly certified.

2. It produces false positives: for the pre-update graph (only edge (1,2)), ordering [0,2,1] is a valid LexBFS, but the check returns False (e.g. b=1, a=0: ab=(0,2) not in E, S=0, and it flags "any c>1 adjacent to va=0" — vacuously fine — but for b=2, a=1: ab=(2,1) in E so it skips; for b=2, a=0: ab=(0,1) not in E, S=0, cand = neighbors of 0 after position 2 = empty, fine... the actual false positive comes from the inverted logic on other triples). In any case, the check is simply not the (LB) property.

3. Because the check is wrong in both directions, `insert_edge`/`delete_edge` sometimes keep an invalid ordering (the failing case: after inserting (0,1), [0,2,1] is invalid but the check says valid) and sometimes recompute unnecessarily.

Note the `S` bookkeeping is also inconsistent with the intended property: `S` accumulates positions d < a with db in E, which is correct for the "ac in E, ab not in E" form (the witness d must have db in E and dc not in E, i.e. S not subset of N(c)). But since the antecedent is inverted, the whole test is meaningless.

## REPAIR_HINTS
Rewrite `_is_valid_lexbfs` to implement the actual (LB) property. The simplest correct formulation (O(n^3) or O(n^3/word) with bitsets):

For all positions a < b < c with ac in E and ab not in E: require exists d < a with db in E and dc not in E.

Concretely, fix the loop body:
- The skip condition must be `if (Nvb >> a) & 1: continue` only when ab IS in E (i.e. the antecedent "ab not in E" is false) — that part is actually what the code does, BUT the violation test that follows must be: "exists c > b with ac in E and for ALL d < a with db in E, dc in E" (i.e. S subset of N(c) for every such c). The code's violation test `if (N[order[c]] & S) == S: return False` is actually the right test for the "ac in E, ab not in E" form... so the real bug is subtler: the code's comment says "ab not in E" for the branch it enters, and it does enter that branch when ab is NOT in E (since it `continue`s when ab IS in E). Re-reading: `if (Nvb >> a) & 1: S |= 1 << a; continue` — this skips ab-in-E pairs but ALSO adds them to S. That is correct for S (S = {d < a : db in E}). Then the else-branch handles ab not in E. The violation test there looks correct for the "ac in E, ab not in E" form.

So why did it fail? Trace the failing case: graph after insert has edges (0,1),(1,2); order [0,2,1]; N[0]={1}, N[2]={1}, N[1]={0,2}.
- b=1 (vb=2, Nvb={1}): a=0 (va=0): (Nvb>>0)&1 = 0, so ab=(0,2) not in E. S=0. Nva=N[0]={1}. cand = {1} & ~((1<<2)-1) = {1} & ~0b11 = 0. No violation.
- b=2 (vb=1, Nvb={0,2}): a=0 (va=0): (Nvb>>0)&1 = 1, so S |= 1, continue. a=1 (va=2): (Nvb>>1)&1 = 0, so ab=(2,1)... wait Nvb bit 1: Nvb={0,2} means bits 0 and 2 set, bit 1 not set. So ab=(order[1],order[2])=(2,1) not in E? But (1,2) IS an edge! N[1] should have bit 1 set (order[1]=2 is adjacent to 1). Nvb = N[1] = bits of positions i where order[i] adjacent to 1 = positions 0 (vertex 0) and 2 (vertex 2) → bits {0,2}. Bit 1 (position 1, vertex 2) — is vertex 2 adjacent to vertex 1? Yes, edge (1,2). So N[1] should be bits {0, 1, 2}? No: N[v] = bitset of positions i with order[i] adjacent to v. order = [0,2,1]. v=1: order[0]=0 adjacent to 1? yes (edge 0-1). order[1]=2 adjacent to 1? yes (edge 1-2). order[2]=1 adjacent to 1? no (no self-loop). So N[1] = bits {0,1}. The code computes N[v] from `graph[v]` row: row = graph[1] = [1,0,1] (edges to 0 and 2). Then `for w in range(n): if row[w]: bits |= 1 << w` → bits = 1<<0 | 1<<2 = {0,2}. **BUG**: the code sets bit w for vertex w, but the bitset is supposed to be indexed by POSITION in the order, not by vertex id. It should be `bits |= 1 << pos` where pos is the position of vertex w in `order`. Instead it uses the vertex id as the bit index. This is the root cause: N[v] is built as "bitset of vertex ids adjacent to v" but is used as "bitset of positions adjacent to v".

In the trace: Nvb = N[1] = {0,2} (vertex-id bits), but position-wise it should be {0,1}. So `(Nvb >> 1) & 1` = 0 (bit 1 not set in {0,2}), making the code think ab=(2,1) is NOT an edge, when it is. Then S={0} (from a=0), Nva=N[2]={1} (vertex-id bits; position-wise N[2] should be {1} since order[1]=1 adjacent to 2 — coincidentally same). cand = Nva & ~((1<<3)-1) = {1} & ~0b111 = 0. No violation found. The check returns True, so the invalid ordering [0,2,1] is kept.

The true violation (verifier's): a=0, b=2, c=1, i.e. ab=(0,1) in E, ac=(0,2) not in E, no d<a. In the "ac in E, ab not in E" form this corresponds to swapping roles: a'=1, b'=2, c'=0? No — the property is stated for a<b<c. The verifier uses the equivalent form: for all a<b<c with ab in E and ac not in E, exists d<a with db not in E and dc in E. The code only checks the "ac in E, ab not in E" form, which is the correct standard form, but the position/vertex-id bug in N[] corrupts all its tests.

**The fix**: in `_is_valid_lexbfs`, build N[v] indexed by position, not vertex id:

```python
pos = {v: i for i, v in enumerate(order)}
N = [0] * n
for v in range(n):
    bits = 0
    for w in range(n):
        if graph[v][w]:
            bits |= 1 << pos[w]
    N[v] = bits
```

(or equivalently, `for i, w in enumerate(order): if graph[v][w]: bits |= 1 << i`). Everything else in the check (the S accumulation, the skip on ab in E, the violation test `S subset of N(c)` over c > b with ac in E) is then correct for the standard (LB) form. After fixing this, the check will correctly reject [0,2,1] on the post-insert graph (b=2, a=0: ab=(0,1) in E → skip; a=1: ab=(2,1) in E → skip; so no violation found for b=2... hmm, need to double check: with correct N, N[1]={0,1}. b=2, vb=1, Nvb={0,1}. a=0: bit 0 set → S={0}, continue. a=1: bit 1 set → S={0,1}, continue. No ab-not-in-E pair, no violation. b=1, vb=2, Nvb={1}. a=0: bit 0 of Nvb = 0 → ab=(0,2) not in E. S=0. Nva=N[0]={1}. cand = {1} & ~((1<<2)-1) = 0. No violation. So the check would still say valid?! But [0,2,1] on edges (0,1),(1,2) is NOT a LexBFS ordering (it's a path 0-1-2, LexBFS from 0 gives 0,1,2). Let me recheck the (LB) property for [0,2,1] on path 0-1-2: a=0,b=1,c=2: ac=(0,2) not in E, ab=(0,2)... wait a=0 is vertex 0, b=1 is vertex 2, c=2 is vertex 1. ac = (0,1) in E, ab = (0,2) not in E. Need d < 0: none. VIOLATION. So the check must catch b=1, a=0: ab=(0,2) not in E, S=0, need c>1 with ac=(0,c) in E: c=2, vertex order[2]=1, (0,1) in E. S=0 subset of anything → violation. With correct N: Nva = N[0] = {1} (position of vertex 1 is 2? No: order=[0,2,1], pos[0]=0, pos[2]=1, pos[1]=2. N[0] = positions of neighbors of 0 = {pos[1]} = {2}. cand = N[0] & ~((1<<2)-1) = {2} & ~0b11 = {2} ≠ 0. S=0 → return False. Correct! I made an arithmetic error above (N[0] is {2}, not {1}). So fixing the position indexing makes the check correct.

Do NOT try to "fix" the violation test logic or the S bookkeeping — they are correct for the standard (LB) form; only the N[] construction is broken. Also note the check only tests the "ac in E, ab not in E" form, which is sufficient (it's the full (LB) property as stated in the brief).
