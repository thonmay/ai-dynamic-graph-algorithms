## FAILURE_DESCRIPTION
Case: n=3, operation `insert (0, 2)` at sequence_idx 0. The pre-update graph is the empty graph on {0,1,2} (this is the first update), so `init` produced the ordering `[0, 1, 2]`. After the insertion the graph has exactly one edge, 0-2. The candidate returned `[0, 1, 2]` (kept the old ordering), but the only valid LexBFS orderings of this graph are `[0, 2, 1]` and `[2, 0, 1]` (the two endpoints of the edge must be adjacent in the ordering). The verifier reports a 4-point violation at positions a=0, b=1, c=2 (vertices 0,1,2): ac=0-2 is an edge, ab=0-1 is not, and no d < a exists (minD = 1000000000 sentinel).

## ROOT_CAUSE
The verifier `_is_valid_lexbfs` is unsound: it returns `True` for the invalid ordering `[0,1,2]` on the post-update graph (edge 0-2 only), so `insert_edge` keeps the stale ordering instead of recomputing.

Exact trace of `_is_valid_lexbfs(graph, [0,1,2])` on the post-insertion graph. Position masks (bit j = position j): N[0] = {2} (0 is adjacent to vertex 2 at position 2), N[1] = ∅, N[2] = ∅.

- a=0 (va=0, Na={2}): b=1 (vb=1). `Na & (1<<1)` = 0, so the "ab in E" skip is not taken.
  `cands = Na & ~N[vb] & ~((1 << (b+1)) - 1)` = {2} & ~∅ & ~{0,1} = {2}.
  Loop: c=2. Test `N[va] & N[ordering[c]] & ((1 << a) - 1)` = {2} & ∅ & 0 = 0 → falsy → `else: return False`.

So the function DOES return False here, and `insert_edge` should recompute. The static `_lexbfs` on the single-edge graph is correct: start 0, refine {1,2} into {2} (neighbor) before {1}, giving `[0, 2, 1]`. Therefore the code as written should have produced the expected result on this case.

This means the failing result `[0, 1, 2]` cannot be explained by the code path I traced above. The most likely explanation, consistent with the observed output, is that the verifier returned `True` on the post-update graph — i.e. the `cands` loop never reached c=2. That happens if `Na` did not contain bit 2, i.e. `graph[0][2]` was read as 0. The only way that occurs is if the `graph` matrix passed to `insert_edge` did not yet contain the inserted edge (the harness passes the pre-update matrix, or the candidate is expected to apply the flip itself). In that scenario the verifier sees the empty graph, where `[0,1,2]` is a valid LexBFS ordering, returns True, and the stale ordering is kept.

I cannot fully rule out an alternative: a subtle bug in the witness test (see below) that makes the verifier accept invalid orderings on other inputs. The witness line
```python
if N[va] & N[ordering[c]] & ((1 << a) - 1):
```
is wrong in two independent ways relative to the (LB) property (witness d < a with db in E and dc NOT in E): it uses `N[va]` (da in E) instead of `N[vb]` (db in E), and it uses `N[ordering[c]]` (dc in E) instead of `~N[ordering[c]]` (dc not in E). The docstring even states the correct form ("N[va] & ~N[vb] & ~N[vc] == 0"). This bug does not fire on the specific failing case (a=0 makes `(1<<a)-1 = 0`, so the test is 0 regardless), but it makes the verifier unsound in general and must be fixed.

## REPAIR_HINTS
Two changes, both required:

1. **Apply the update to the graph before verifying.** In `insert_edge` and `delete_edge`, flip the matrix entry for `edge` (set to 1 on insert, 0 on delete) on a copy of the passed graph before calling `_is_valid_lexbfs` and `_recompute`. If the harness already passes the post-update matrix, this is a no-op, but the observed failure (stale ordering kept on an insertion) is consistent with the candidate seeing the pre-update matrix. Verify which convention the harness uses; the safe fix is to ensure the matrix used for verification and recomputation reflects the post-update graph.

2. **Fix the witness test in `_is_valid_lexbfs`** (the `while cands:` loop). Replace
```python
if N[va] & N[ordering[c]] & ((1 << a) - 1):
```
with
```python
if N[vb] & ~N[ordering[c]] & ((1 << a) - 1):
```
i.e. the witness d < a must be adjacent to b (`N[vb]`) and non-adjacent to c (`~N[ordering[c]]`). `~N[ordering[c]]` is an infinite two's-complement mask in Python, but it is ANDed with the finite `(1 << a) - 1`, so it is safe. The `cands` prefilter `Na & ~N[vb] & ~((1 << (b+1)) - 1)` is correct as written (c must satisfy ac in E, bc not in E, c > b).

After both fixes, the failing case works: the post-update graph (edge 0-2) is verified, the (now correct) witness test finds no witness for (a=0,b=1,c=2) and returns False, `insert_edge` recomputes, and `_lexbfs` yields `[0, 2, 1]`.

Approaches that will not work:
- Fixing only the witness test without ensuring the graph reflects the update: if the harness passes the pre-update matrix, the verifier still sees the old graph and keeps the stale ordering.
- Fixing only the graph convention without fixing the witness test: the verifier remains unsound on other inputs (it can both keep invalid orderings and needlessly recompute valid ones).
- Patching only the missing `~` on `N[ordering[c]]` while keeping `N[va]`: the witness must be adjacent to b, not a; using `N[va]` still gives wrong answers.
