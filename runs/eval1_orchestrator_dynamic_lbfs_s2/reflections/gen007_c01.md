## FAILURE_DESCRIPTION

n=3. Initial graph (sequence_idx 0, operation "insert (0, 1)"): the pre-update
graph has only edge (1,2) (edge (0,1) is absent, since the update inserts it).
`init` produced ordering [0, 2, 1] (start 0, then 2, then 1 — valid for the
pre-update graph). After inserting (0,1), the graph is the path 0-1-2, whose
valid LexBFS orderings are [0,1,2] and [2,1,0]. The candidate returned
[0, 2, 1] (kept the old ordering), which is invalid: the verifier reports the
(LB) violation at positions a=0, b=2, c=1 (i.e. vertices 0, 2, 1):
ac = (0,1) in E, ab = (0,2) not in E, and no d < a exists (minD = 1e9).

## ROOT_CAUSE

`_is_valid_lexbfs` mis-implements the (LB) 4-point property, so it returns
True for the invalid ordering [0,2,1] on the path 0-1-2, and
`insert_edge` therefore keeps the stale ordering instead of recomputing.

The property (as stated in the brief and in the function's own docstring) is:
for all positions a < b < c with ac in E and ab not in E, there exists
**d < a** with db in E and dc not in E.

The code instead checks, for the failing triple (a=0, b=2, c=1):

```python
nb_pm = N[vb] & pm  # neighbours of b that are before a
...
c_mask = na & suffix_mask[b + 1]
while c_mask:
    lb = c_mask & (-c_mask)
    c = lb.bit_length() - 1
    vc = ordering[c]
    if nb_pm & ~N[vc] == 0:
        return False
```

Two distinct bugs, both visible on this case:

1. **Wrong witness set.** `pm = prefix_mask[a]` is the set of *positions*
   before a, but `N[vb]` is a bitset of *vertex ids*. The code ANDs a
   position mask with a vertex-id mask, so `nb_pm` is not "neighbours of b
   that appear before a in the ordering" at all. The correct witness set is
   `{ordering[d] : d < a and graph[vb][ordering[d]]}`, i.e.
   `N[vb] & vertex_set_of_positions_before_a`.

2. **Wrong quantifier over c.** The property requires a witness d for
   *every* c > b with ac in E. The code returns False as soon as it finds
   *one* c with `nb_pm & ~N[vc] == 0` (i.e. nb_pm ⊆ N[vc]), which is the
   opposite of the required condition. The correct failure condition is
   `exists c > b with ac in E and (N[vb] & ~N[vc]) & W == 0` where W is the
   set of vertices at positions < a.

Trace on the failing case (ordering [0,2,1], graph = path 0-1-2):
- a=0 (va=0, na={1}), b=2 (vb=1, ab=(0,1) in E → skipped), b=1 (vb=2,
  ab=(0,2) not in E).
- pm = prefix_mask[0] = 0, so nb_pm = 0.
- `na & suffix_mask[2]` = {1} & {1} = {1} ≠ 0 → the `nb_pm == 0` branch
  should return False here, but...
- Actually it does NOT reach that branch correctly: with pm=0, nb_pm=0, and
  `na & suffix_mask[b+1]` = na & suffix_mask[2] = {1} & {1} = {1} ≠ 0, so it
  *would* return False. Wait — re-check: b=1, so suffix_mask[b+1] =
  suffix_mask[2] = bit 1 only. na = {1}. So na & suffix_mask[2] = {1} ≠ 0,
  and the code returns False... 

Re-tracing more carefully: the loop is `for b in range(a+1, n)`, so b=1
first, then b=2.
- b=1: vb = ordering[1] = 2. na = N[0] = {1}. Is 2 in na? No. So ab not in
  E. nb_pm = N[2] & prefix_mask[0] = {1} & 0 = 0. `na & suffix_mask[2]` =
  {1} & {1} = {1} ≠ 0 → **returns False**.

So the code *does* return False for this case, meaning `insert_edge` *would*
recompute. But the observed result is [0,2,1] (not recomputed). This means
either (a) the graph passed to `insert_edge` is the pre-update graph (edge
(0,1) not yet flipped in the matrix), or (b) the initial ordering was
different.

Hypothesis (a): if `graph` at the time of `_is_valid_lexbfs` still lacks
edge (0,1), then na = N[0] = {} (vertex 0 is isolated pre-update). Then for
a=0, b=1 (vb=2): ab=(0,2) not in E, nb_pm = N[2] & 0 = 0, `na &
suffix_mask[2]` = 0 → continue. b=2 (vb=1): ab=(0,1) not in E (pre-update),
nb_pm = N[1] & 0 = 0, `na & suffix_mask[3]` = 0 → continue. No other (a,b).
Returns True → stale ordering kept. Then the verifier checks the
post-update graph and finds the violation.

This is the most consistent explanation: **the candidate's validity check
runs on a graph that does not yet reflect the update** (or equivalently, the
check is vacuously true on the pre-update graph because vertex 0 is
isolated), so the stale ordering is kept. The secondary bugs (wrong witness
set, wrong quantifier) are real but were not the trigger here.

## REPAIR_HINTS

1. **Primary fix — ensure the check sees the post-update graph.** In
   `insert_edge`/`delete_edge`, the `graph` argument must already contain the
   flipped entry when `_is_valid_lexbfs` is called. If the harness passes
   the pre-update matrix, the candidate must apply the flip itself before
   checking (and the flip is exactly `graph[u][v] = graph[v][u] = 1` for
   insert, `= 0` for delete). Verify which convention the harness uses; the
   observed failure is consistent with the check running on the pre-update
   graph.

2. **Fix the witness set in `_is_valid_lexbfs`.** Replace
   `nb_pm = N[vb] & pm` with a mask of *vertices* at positions < a:
   build `pos_before_a = {ordering[d] for d in range(a)}` as a bitset
   `W_a`, then `nb_W = N[vb] & W_a`. The current code ANDs a position-index
   mask with a vertex-id bitset, which is meaningless.

3. **Fix the quantifier over c.** The property fails iff there exists c > b
   with ac in E and `(N[vb] & ~N[vc]) & W_a == 0`. The current code returns
   False when it finds one c with `nb_pm & ~N[vc] == 0` (nb_pm ⊆ N[vc]),
   which is the wrong direction. Correct logic: for each c in
   `na & suffix_mask[b+1]`, if `(N[vb] & ~N[vc]) & W_a == 0`, return False.

4. **Approaches that will not work:** simply recomputing unconditionally
   after every update is correct but defeats the research goal (avoid full
   recompute). Patching only the quantifier without fixing the witness set
   (or vice versa) will still mis-validate orderings.
