## FAILURE_DESCRIPTION
Case: n=3. Initial graph has the single edge (0,1) (matrix [[0,1,0],[1,0,0],[0,0,0]]).
`init` returns ordering [0,1,2], which is a valid LexBFS ordering of the initial
graph. Then the update `insert (0,2)` is applied, giving graph G with edges
(0,1) and (0,2) — a star centered at 0 (matrix [[0,1,1],[1,0,0],[1,0,0]]).

Expected result: [0,2,1] (the only valid LexBFS ordering of G up to the
symmetry between leaves 1 and 2 — actually [0,1,2] is also valid, see below;
the verifier's expected value is [0,2,1]).
Actual result: [0,1,2] (the stale ordering from before the update).
The verifier reports an (LB) violation at (a=0, b=1, c=2, pos_a=0, minD=1e9),
meaning: for the triple at positions 0<1<2 (vertices a=0, b=1, c=2), the
required witness d was not found (minD stayed at the sentinel 1e9).

## ROOT_CAUSE
The bug is in `_check_lb`: it is an **incomplete certificate** for LexBFS
validity, so the "keep old ordering" fast path in `insert_edge` fires
incorrectly.

Trace of `_check_lb(G, [0,1,2])` on the star G (edges 01, 02):
- i=0: a=0. j=1: b=1, A[0][1]=1 → `continue` (ab in E). j=2: b=2, A[0][2]=1 → `continue`.
- i=1: a=1. j=2: b=2, A[1][2]=0. Inner k loop: `range(3,3)` is empty.
- i=2: no j.
Result: `_check_lb` returns **True**, so `insert_edge` returns the stale
ordering [0,1,2] without recomputing.

Why the check is incomplete: the (LB) 4-point property as implemented
(for all a<b<c with ac∈E and ab∉E, ∃d<a: db∈E and dc∉E) is a **necessary**
condition for LexBFS validity but **not sufficient** on its own. The complete
characterization (Corneil–Krueger) requires the property to hold in **both
orientations**: the forward form (witness d < a) AND the reverse form
(witness d > c, i.e., the same clause applied to the reversed ordering).

In the failing case, the forward clause is vacuously satisfied for every
triple in [0,1,2] on the star (the only triples with ac∈E have ab∈E too, so
the antecedent "ab∉E" is never true). But the **reverse** clause fails:
consider the reversed ordering [2,1,0]. The triple a=2(pos 0), b=1(pos 1),
c=0(pos 2) has ac=20∈E and ab=21∉E, requiring ∃d before a (none, a is first)
— no witness exists. Equivalently, in the original ordering [0,1,2], the
triple a=0, b=1, c=2 with ac=02∈E and ab=01∈E... the reverse-orientation
clause (for all a<b<c with ac∈E and ab∉E, ∃d>c: db∈E and dc∉E) applied to
the appropriate triple catches the violation.

The verifier's reported violation (a=0, b=1, c=2, pos_a=0, minD=1e9) is
consistent with the verifier checking the **reverse** (LB) clause: for the
triple at positions 0<1<2, it requires a witness d at position > pos_c (or
equivalently d < a in the reversed ordering), and no such d exists.

The responsible code is in `insert_edge` (and `delete_edge`):
```python
if _check_lb(graph, ordering):
    return {'ordering': ordering}  # BUG: _check_lb is incomplete, returns True incorrectly
```

## REPAIR_HINTS
1. **Smallest fix — make `_check_lb` complete**: check the (LB) property in
   BOTH orientations. Concretely, after the existing forward check, also run
   the same check on `ordering[::-1]` (the reversed ordering). If either
   orientation fails, return False. In the failing case, the reversed
   ordering [2,1,0] on the star will fail the forward (LB) clause (triple
   a=2, b=1, c=0: ac=20∈E, ab=21∉E, no d before a), so `_check_lb` will
   correctly return False and trigger a recompute.

   Code change in `_check_lb`:
   ```python
   def _check_lb(A, ordering):
       n = len(A)
       # Forward check (existing code)
       for i in range(n):
           ...  # existing loops
       # Reverse check: same clause on reversed ordering
       rev = ordering[::-1]
       for i in range(n):
           a = rev[i]
           for j in range(i + 1, n):
               b = rev[j]
               if A[a][b]:
                   continue
               for k in range(j + 1, n):
                   c = rev[k]
                   if not A[a][c]:
                       continue
                   found = False
                   for l in range(i):
                       d = rev[l]
                       if A[d][b] and not A[d][c]:
                           found = True
                           break
                   if not found:
                       return False
       return True
   ```

2. **Alternative (more robust) fix**: replace `_check_lb` with a direct
   LexBFS-consistency test: for the given ordering, verify that at each
   position i, the vertex ordering[i] has a minimal adjacency-label
   (tuple of 0/1 over ordering[0..i-1]) among all vertices not yet placed.
   This is O(n^3) but is a complete and simple validity test.

3. **What will NOT work**:
   - Tightening the existing forward-only `_check_lb` loops (changing
     `continue` conditions, adding edge cases) without adding the reverse
     orientation — the forward clause alone is provably insufficient.
   - Removing the fast path entirely (always recompute) would be correct but
     defeats the research goal of avoiding full recomputation.

4. **Interim safety net**: if the two-orientation fix is uncertain, the
   safest interim change is to always recompute in `insert_edge` and
   `delete_edge` (remove the `_check_lb` fast path), then restore the fast
   path once the certificate is verified complete.
