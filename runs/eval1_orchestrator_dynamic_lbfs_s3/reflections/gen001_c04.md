## FAILURE_DESCRIPTION

Failing case: `operation: init`, `sequence_idx: 0`, n = 3. The candidate's
`init` returned ordering `[0, 2, 1]` (result), while the expected valid
LexBFS ordering is `[0, 1, 2]`. The verifier reports a (LB) 4-point property
violation with `a=0, b=2, c=1, pos_a=0, minD=1000000000` (minD = sentinel
"no witness d found").

Reconstructing the graph from the violation: in the returned order
`[0, 2, 1]`, positions are 0->vertex 0, 1->vertex 2, 2->vertex 1. The
violation tuple (a=0, b=2, c=1) means:
- a = vertex 0 at position 0,
- b = vertex 2 at position 1,
- c = vertex 1 at position 2,
- precondition: A[0][1] = 1 (ac in E) and A[0][2] = 0 (ab not in E),
- required witness: some d at position < 0 with A[d][2]=1 and A[d][1]=0.
  No such d exists (position 0 is the first), hence minD = sentinel.

So the graph has edge (0,1) and no edge (0,2). The only LexBFS orderings of
this graph are `[0,1,2]` and `[1,0,2]` (vertex 2 is isolated, so it must
come after whichever of {0,1} is first; and 0 must precede 1 because 0 is
adjacent to 1 while 1 is not adjacent to 0). `[0,2,1]` is NOT a valid
LexBFS ordering of this graph.

## ROOT_CAUSE

The bug is in `_lexbfs` (the static LexBFS routine used by `init`). The
selection rule is:

```python
x = min(remaining, key=lambda v: labels[v])
```

This picks the vertex with the **lexicographically smallest** label tuple.
LexBFS requires the **lexicographically largest** label (1 > 0, since a 1
means "adjacent to an already-ordered vertex", which should be preferred).

Trace on the failing graph (A[0][1]=1, A[0][2]=0, A[1][2]=0):
- Start: all labels = (). `min` picks vertex 0 (smallest id). order=[0].
  Labels: 1 -> (1,) [adjacent to 0], 2 -> (0,) [not adjacent to 0].
- Next: `min(remaining, key=labels)` compares (1,) vs (0,). Since 0 < 1,
  it picks vertex 2 (label (0,)). order=[0,2].  **This is the divergence.**
  Correct LexBFS would pick vertex 1 (label (1,), the larger label).
- Next: vertex 1. order=[0,2,1].

The result `[0,2,1]` violates (LB) as reported. The `_is_valid_lexbfs`
checker is only ever called inside `_try_repair` (i.e., on updates), never
on the `init` output, so the invalid ordering is returned unchecked.

The responsible line is:
```python
x = min(remaining, key=lambda v: labels[v])
```
in `_lexbfs`. It should select the maximum label, not the minimum.

## REPAIR_HINTS

1. **Fix the selection in `_lexbfs`**: change
   ```python
   x = min(remaining, key=lambda v: labels[v])
   ```
   to
   ```python
   x = max(remaining, key=lambda v: labels[v])
   ```
   This makes the routine pick the vertex with the lexicographically largest
   label (1s preferred over 0s), which is the correct LexBFS rule. Ties are
   broken by vertex id (Python's `max` returns the first maximal element in
   iteration order; since `remaining` is a set, tie-breaking is arbitrary
   but any tie-break is legal for LexBFS).

2. **Add a self-check in `init`** (defensive): after computing the order,
   call `_is_valid_lexbfs(graph, order)` and if it fails, fall back to a
   brute-force search over all permutations (for small n) or a corrected
   recompute. This guards against any residual bug in the static routine.

3. **Do NOT** try to "fix" this by changing the label construction
   (appending 1 for non-neighbor, 0 for neighbor) — that would invert the
   meaning and still be wrong. The label construction is correct (1 =
   adjacent to already-ordered vertex); only the comparison direction is
   inverted.

4. The `_is_valid_lexbfs` checker itself appears correct (it implements the
   (LB) 4-point property faithfully). No change needed there.

5. The `_try_repair` logic is fine in principle (it validates candidates
   with `_is_valid_lexbfs` before returning), but it is moot for this
   failure since the bug is in `init`/`_lexbfs`, not in the repair path.
