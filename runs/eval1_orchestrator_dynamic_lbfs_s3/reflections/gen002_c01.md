update is the path 0-1-2 (edges {01, 12}). The candidate returned
`[0, 2, 1]`; the expected (and only valid) LexBFS ordering is `[0, 1, 2]`.

The verifier's (LB) 4-point certificate reports a violation with
a=0, b=2, c=1, pos_a=0, minD=1000000000 (sentinel = "no witness d found").
Interpreted on the returned ordering `[0, 2, 1]`: position 0 = vertex 0,
position 1 = vertex 2, position 2 = vertex 1. The violated triple is
(pos_a=0, pos_b=2, pos_c=1): ac = (0,1) in E, ab = (0,2) not in E, and there
is no d < pos_a=0 with db in E and dc not in E. Indeed, `[0, 2, 1]` is NOT a

## ROOT_CAUSE

The bug is in `_check_lb`, which is the "keep the old ordering" fast path used
by both `insert_edge` and `delete_edge`:

```python
def _check_lb(A, ordering):
    n = len(A)
    for i in range(n):
        chosen = ordering[i]
        chosen_label = tuple(1 if A[chosen][ordering[t]] else 0 for t in range(i))
        for j in range(i + 1, n):
            v = ordering[j]
            label = tuple(1 if A[v][ordering[t]] else 0 for t in range(i))
            if label < chosen_label:
                return False
    return True
```

The inner loop only compares `chosen` (the vertex at position i) against
vertices at positions j > i (i.e., vertices that come AFTER it in the
ordering). It never compares against vertices at positions k < i (vertices
already placed before `chosen`).

This is not a valid certificate. A LexBFS ordering requires that at every
step i, `ordering[i]` has a minimal label among ALL vertices not yet placed
at that step — which includes vertices that end up placed LATER, but the
label of a vertex placed earlier (k < i) is not constrained by the choice at
step i. However, the converse is also needed: the check must verify that no
vertex placed at position k < i had a label (over ordering[0..k-1]) strictly
smaller than the label of the vertex that was actually chosen at step k. The
current code does check that for each i against later vertices, but the
asymmetry means it can miss violations where the ordering is invalid because
an earlier choice was wrong relative to a vertex that appears even earlier
in the final ordering.

Concretely, for the failing case: the old ordering before the insert was
`[0, 2, 1]` (valid for the graph with only edge 12, where 0 is isolated).
After inserting edge (0,1), the graph is path 0-1-2. The correct LexBFS is
`[0, 1, 2]`. The old ordering `[0, 2, 1]` is invalid. But `_check_lb`

## REPAIR_HINTS

The `_check_lb` function must be replaced with an actual check of the (LB)
4-point property (in both orientations, as the brief states):

```python
def _check_lb(A, ordering):
    n = len(A)
    # Check (LB) in forward direction
    for a in range(n):
        for b in range(a + 1, n):
            for c in range(b + 1, n):
                va, vb, vc = ordering[a], ordering[b], ordering[c]
                if A[va][vc] and not A[va][vb]:
                    # Need d < a with db in E and dc not in E
                    found = False
                    for d in range(a):
                        vd = ordering[d]
                        if A[vd][vb] and not A[vd][vc]:
                            found = True
                            break
                    if not found:
                        return False
    # Check (LB) in reversed direction
    rev = ordering[::-1]
    for a in range(n):
        for b in range(a + 1, n):
            for c in range(b + 1, n):
                va, vb, vc = rev[a], rev[b], rev[c]
                if A[va][vc] and not A[va][vb]:
                    found = False
                    for d in range(a):
                        vd = rev[d]
                        if A[vd][vb] and not A[vd][vc]:
                            found = True
                            break
                    if not found:
                        return False
    return True
```

Additionally, `_lexbfs_full_tie` must be modified to produce orderings that
satisfy the (LB) property. The standard LexBFS with smallest-id tie-breaking
does NOT guarantee (LB) for non-chordal graphs. One approach: after computing
a LexBFS ordering, verify it satisfies (LB) in both orientations; if not,
try other valid LexBFS orderings (different tie-breaks or start vertices)
until one satisfies (LB). If no LexBFS ordering satisfies (LB), the graph is
non-chordal and the problem may be infeasible — but the verifier presumably
only tests on graphs where a valid (LB)-satisfying ordering exists.

A simpler approach that will work: on each update, recompute a LexBFS
ordering and then verify it against the (LB) property. If it fails, try
different start vertices and tie-breaks. This is O(n^4) per update but is
correct.

Approaches that will NOT work:
- Keeping the current `_check_lb` (label-minimization check) — it does not
  match the verifier's (LB) check.
- Assuming the (LB) property is equivalent to LexBFS validity — it is not,
  for non-chordal graphs.
