## FAILURE_DESCRIPTION
Operation `init` on a 3-vertex undirected graph. The candidate returned ordering `[0, 1, 2]`, but the verifier reports a (LB) 4-point violation at positions a=0, b=1, c=2 (pos_a=0, minD=1e9, i.e. no witness d exists). The expected valid ordering is `[0, 2, 1]`.

Reconstructing the graph from the two orderings:
- `[0, 1, 2]` is invalid with the violation (a=0, b=1, c=2): requires `01 ∉ E`, `02 ∈ E`, and no d before position 0 (vacuously impossible).
- `[0, 2, 1]` is valid: the only triple with a=0, b=2, c=1 needs `02 ∉ E` (false, since 02 ∈ E), so no violation.

So the graph has `02 ∈ E`, `01 ∉ E`, and (for `[0,2,1]` to be valid) `21 ∉ E`. The graph is the single edge {0,2}.

## ROOT_CAUSE
The static `_lexbfs_full` is not a correct LexBFS. It starts with `buckets = [[v] for v in range(n)]` — one singleton bucket per vertex — and picks "the first non-empty bucket" each round. With singleton buckets, the first non-empty bucket is always the leftmost remaining vertex, so the algorithm outputs vertices in index order `0, 1, 2, ...` regardless of the graph. The refinement step (splitting bucket j into adj/non-adj to v) is dead code: every bucket has size 1, so `adj` and `non` are always singletons or empty, and the bucket order never changes.

Concretely, on the failing graph (edge {0,2}):
- Round 1: buckets `[[0],[1],[2]]`, pick 0. Refine bucket [1]: 1 not adj to 0 → stays [1]. Bucket [2]: 2 adj to 0 → adj=[2], non=[] → bucket becomes [2] (inserted at same position). Order so far: [0].
- Round 2: first non-empty bucket is [1] (index 1), pick 1. Order: [0,1].
- Round 3: pick 2. Order: [0,1,2].

Correct LexBFS: after outputting 0, vertex 2 (adjacent to 0) must precede vertex 1 (not adjacent to 0), giving [0,2,1]. The algorithm never reorders buckets by adjacency to the chosen vertex because the initial partition is already into singletons.

The `init` function's verification block (`if not _is_valid_lexbfs(...)`) is a no-op: the loop body is `pass`, so an invalid ordering is returned as-is.

## REPAIR_HINTS
1. **Fix `_lexbfs_full` to use a proper initial partition.** The standard LexBFS starts with a single bucket containing all vertices: `buckets = [[v for v in range(n)]]`. Then the "pick first non-empty bucket, take its first vertex, refine all other buckets by adjacency" loop works correctly: after picking v, each other bucket splits into (adjacent-to-v first, non-adjacent second), and the bucket list order encodes the lexicographic labels. This is the minimal change: replace `buckets = [[v] for v in range(n)]` with `buckets = [list(range(n))]`.

2. **Make the `init` verification actually do something.** The current `pass` loop means an invalid ordering from `_lexbfs_full` is silently returned. After fixing the bucket initialization, `_lexbfs_full` should produce valid orderings, but as a safety net, if `_is_valid_lexbfs` fails, the code should recompute (e.g., try different tie-breaks or start vertices) rather than returning the invalid ordering.

3. **Approaches that will not work:**
   - Keeping singleton initial buckets and trying to "fix" the refinement: with singletons, no bucket ever has more than one vertex, so adjacency-based reordering is impossible. The partition must start coarse (one bucket) so that refinement can split it.
   - Relying on `_try_local_repair` in `init`: `init` never calls it, and even if it did, the repair strategies (move one vertex, swap, reverse suffix) are not guaranteed to find a valid LexBFS from an arbitrary invalid ordering.
