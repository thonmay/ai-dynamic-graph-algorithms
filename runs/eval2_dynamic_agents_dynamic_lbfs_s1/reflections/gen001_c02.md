## FAILURE_DESCRIPTION
n=3. The failing case is `sequence_idx: 0`, operation `insert (0, 2)`, result "[0, 1, 2]", expected "[0, 2, 1]", verifier violation at positions a=0, b=1, c=2 with minD=1000000000 (sentinel: no witness d found).

Reconstructing the graph at check time: the violation triple (a=0, b=1, c=2) requires the (LB) antecedent "ac in E and ab not in E" to hold, i.e. edge 02 in E and edge 01 NOT in E. Since the operation is `insert (0,2)`, the pre-update graph must have had NO edge 01 and NO edge 02 (the insertion adds 02). So the initial graph is the empty graph on 3 vertices. `init` returns [0,1,2] (valid for the empty graph). After `insert (0,2)`, the graph is the single edge {02}. The candidate returned the stale ordering [0,1,2], but the expected valid LexBFS is [0,2,1].

Indeed [0,1,2] on graph {02} violates (LB): positions a=0 (v0), b=1 (v1), c=2 (v2): ac = 02 in E, ab = 01 not in E, and there is no d < a=0 with db in E and dc not in E (no d < 0 exists). Hence minD sentinel. [0,2,1] is valid: its only triple (0,1,2) has ac = 01 not in E, so the antecedent never fires.

## ROOT_CAUSE
`_is_valid_lexbfs` does not implement the (LB) 4-point property; it implements a different quantification, so it returned True for the stale ordering [0,1,2] on graph {02}, and `insert_edge` therefore kept the invalid ordering instead of recomputing.

The code's own comment states what it checks:

    # The property: for all b < c with c in adj[b],
    #   for all a < b with a not in adj[b] and c in adj[a],
    #     exists d < a with d in N_b and d not in adj[c].

and the loops implement exactly that: outer `for b in range(n)`, then `for c in range(b+1, n)` guarded by `if c not in adj[b]: continue` (i.e. **bc in E** is required), then `for a in range(b)` with `a not in adj[b]` and `c in adj[a]`, then witness `for d in N_b: if d >= a: break; if d not in adj[c]: found`.

The actual (LB) property is: for all positions a < b < c with **ac in E and ab not in E**, there exists d < a with db in E and dc not in E. The code's antecedent is "bc in E" (with ac in E and ab not in E as inner filters), not "ac in E and ab not in E" as the outer condition. In the failing case, the violating triple (a=0, b=1, c=2) has bc = 12 NOT in E, so the code's outer guard `if c not in adj[b]: continue` skips it entirely; the code never examines this triple and returns True. The witness restriction to `N_b` (neighbors of b) is actually consistent with the real property (d < a < b and db in E), so the witness loop is fine — the bug is purely the wrong outer quantification/antecedent.

## REPAIR_HINTS
1. Rewrite `_is_valid_lexbfs` to implement the property exactly, with the outer loop over a:
   ```
   for a in range(n):
       for b in range(a+1, n):
           if adj[a][b]: continue          # ab in E -> antecedent false
           for c in range(b+1, n):
               if not adj[a][c]: continue  # ac not in E -> antecedent false
               # need exists d < a with adj[d][b] and not adj[d][c]
               if not any(adj[d][b] and not adj[d][c] for d in range(a)):
                   return False
   return True
   ```
   (adj here is the position-indexed adjacency built from `ordering`, as the code already does.)
2. Do NOT keep the current structure (outer loop over b with the `c in adj[b]` guard) — that guard is the bug; it excludes exactly the triples where bc is not an edge, which is where violations like the failing one live.
3. The witness set {d < a : db in E and dc not in E} depends on c, so the per-b `N_b` precomputation cannot be reused as-is; either drop it or keep it only as the candidate pool and still test `d not in adj[c]` per c (the current inner test already does this, so keeping N_b as a pool is harmless once the outer loops are fixed).
4. After fixing the checker, verify end-to-end on the failing case: init(empty 3-graph) -> [0,1,2]; insert (0,2) -> checker must now return False -> recompute via `_lexbfs` on {02}. Note `_lexbfs` on {02} with min tie-break gives [0,1,2] (start 0, then 1 and 2 both labeled {0}... actually 2 is adjacent to 0 and 1 is not, so refinement splits {1,2} into {2} then {1}, giving [0,2,1] — correct). So the static routine is fine; only the checker needs the fix.
5. Do not attempt incremental maintenance of the refinement for this repair — check-then-recompute is acceptable for reaching correctness first.
