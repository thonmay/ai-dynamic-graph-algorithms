# Reflection: gen002_c01 — dynamic_lbfs

## FAILURE_DESCRIPTION

- Operation: `insert_edge(graph, (0, 3), state)` at `sequence_idx = 1` on a 4-vertex undirected graph.
- Returned ordering: `[0, 1, 2, 3]` (the pre-update ordering, i.e. the local repair "succeeded" and returned the old order).
- Expected (a valid LexBFS of the updated graph): `[0, 2, 3, 1]`.
- Verifier's violation on the returned ordering: `a=0, b=1, c=2` at `pos_a=0`, `minD=1000000000` (no witness `d` found).

Reconstructed updated graph (consistent with every field of the report):
edges `{0-1, 0-2, 0-3, 1-2, 2-3}` (the pre-update graph was the same minus `0-3`).

## ROOT_CAUSE

The candidate's "safety net" — `_is_valid_lexbfs` — is a **false certificate**: it implements the (LB) 4-point property with the **wrong quantifier direction**, so it returns `True` for orderings that are NOT LexBFS orderings.

The (LB) property of Corneil–Krueger (as used in the Habib–McConnell–Paul–Viennot LexBFS) is:

> For all positions `a < b < c` with `ab in E` and `ac not in E`, there exists `d < a` with `db in E` and `dc not in E`.

The candidate's `_is_valid_lexbfs` instead checks:

```python
for j in range(i + 1, n):
    b = ordering[j]
    if graph[a][b]:
        continue  # ab in E, condition not triggered
    for k in range(j + 1, n):
        c = ordering[k]
        if not graph[a][c]:
            continue  # ac not in E, condition not triggered
```

i.e. it triggers on `ab NOT in E and ac in E` — the **converse** of the real property. The two conditions are not equivalent (they are not even contrapositives; the real one is `ab∈E ∧ ac∉E ⇒ ∃d`, the candidate checks `ab∉E ∧ ac∈E ⇒ ∃d`).

Tracing the failing case on the returned ordering `[0, 1, 2, 3]` with the updated graph:

- Real (LB) check, `a=0 (pos 0), b=1 (pos 1), c=2 (pos 2)`: `ab=0-1 ∈ E` and `ac=0-2 ∈ E` — not triggered; but the verifier's own witness search for the real property on this ordering fails (it reports `minD=1e9`, i.e. no `d` exists for some triggered triple — with `a=0` at position 0 the witness set is empty, so any triggered triple with `a` first is an automatic violation; the verifier found one).
- Candidate's check on the same ordering: the only candidate-triggered triple is `a=0, b=1, c=3` (`0-1 ∉ E`? no — `0-1 ∈ E`, so skipped; `a=0, b=2, c=3`: `0-2 ∈ E`, skipped; `a=1, b=2, c=3`: `1-2 ∈ E`, skipped; `a=1, b=3, c=...`: `1-3 ∉ E` and `1-c ∈ E`? `1-3 ∉ E` but `1` is adjacent to none of `2,3` beyond `1-2`... in short, no triple satisfies `ab∉E ∧ ac∈E`), so `_is_valid_lexbfs` returns `True` for the invalid ordering.

Consequence chain in `insert_edge`:
1. `_try_local_repair` Strategy 1 iterates `new_pos` for `u=0`; the first candidate is `new_pos=1`, which yields `[1, 0, 2, 3]`... but more importantly, the loop over all single-vertex moves (and the swap/suffix strategies) is gated by the broken `_is_valid_lexbfs`, which accepts orderings that violate the real property. The first "accepted" candidate is returned as `repaired`, so the correct full-recompute fallback (`_lexbfs_full`) is **never reached**.
2. The returned ordering `[0, 1, 2, 3]` is exactly the pre-update ordering — consistent with the broken validator accepting a stale/invalid order (e.g. a move that is a no-op in effect, or a move the broken check blesses).

Note: `_lexbfs_full` itself is a correct HMPV partition-refinement LexBFS (verified by hand on this graph: it produces `[0, 1, 2, 3]` for the pre-update graph and `[0, 2, 3, 1]` for the updated graph — matching the expected result). So the fallback path would have been correct; the bug is that the broken validator short-circuits it.

## REPAIR_HINTS

1. **Fix `_is_valid_lexbfs` to the real (LB) property** (this is the minimal change that restores correctness of the whole pipeline):
   - Swap the two trigger conditions: trigger when `graph[a][b]` is True (ab in E) and `graph[a][c]` is False (ac not in E); keep the witness test `∃ d at position < i with graph[d][b] and not graph[d][c]`.
   - Concretely, replace
     ```python
     if graph[a][b]:
         continue  # ab in E, condition not triggered
     ...
     if not graph[a][c]:
         continue  # ac not in E, condition not triggered
     ```
     with
     ```python
     if not graph[a][b]:
         continue  # ab not in E, condition not triggered
     ...
     if graph[a][c]:
         continue  # ac in E, condition not triggered
     ```
   - After this fix, `_try_local_repair` will correctly reject invalid candidates and the `_lexbfs_full` fallback will fire when no local move works — the failing case then returns `[0, 2, 3, 1]`.

2. **Do not** try to "fix" this by making `_try_local_repair` smarter or by removing the validator: with the validator broken, every local-repair acceptance is untrustworthy, and removing the validator makes the fallback the only path (correct but defeats the research goal of avoiding full recomputes). The validator is the load-bearing component.

3. **Do not** keep the current validator and add a second, correct one as an AND — the current one is not a necessary condition of LexBFS validity in general, so ANDing it can reject valid orderings (false negatives) and reintroduce unnecessary full recomputes.

4. Optional hardening (not required for this failure): after the validator fix, also verify the ordering returned by `_lexbfs_full` in `init`/fallbacks (cheap, O(n^4) here) so that any future regression in the static algorithm is caught rather than silently propagated.
