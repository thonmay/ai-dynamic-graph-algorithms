## FAILURE_DESCRIPTION

3-vertex graph, operation `insert (1, 2)` at sequence index 0. The candidate
returned ordering `[1, 0, 2]`; the verifier expected a valid LexBFS ordering
(e.g. `[0, 1, 2]`). The verifier reports a 4-point violation with
`a=1, b=0, c=2, pos_a=0, minD=1000000000` (sentinel = no witness found).

Reconstructing the graph: the pre-insertion graph must have been the path
`0-1-2` (edges (0,1),(1,2)); inserting (1,2) is a no-op flip, so the graph
after the update is still the path 0-1-2. In `[1, 0, 2]` the triple
(a,b,c) = (1,0,2) at positions (0,1,2) has ab=1-0 in E, ac=1-2 in E, and
there is no d before position 0, so the 4-point property fails.

## ROOT_CAUSE

The candidate's `_is_valid_lexbfs` implements the 4-point property with the
**wrong adjacency conditions**. It reads:

```python
if not graph[a][b]:
    continue  # ab not in E, condition not triggered
...
if graph[a][c]:
    continue  # ac in E, condition not triggered
```

i.e. it triggers the witness search when **ab in E and ac not in E**. The
correct (LB) property (as stated in the brief and in the task's violation
record) triggers when **ac in E and ab not in E** — the two conditions are
swapped. The comments in the code even contradict the code: the comment says
"ab not in E, condition not triggered" but the code skips when ab IS in E.

Consequences, traced on the failing case:

1. `init` on path 0-1-2: `_lexbfs_full` returns `[0, 1, 2]`. The buggy
   checker passes it (the swapped condition never fires on this ordering),
   so the state is fine.
2. `insert (1, 2)`: `_try_local_repair` is called. Strategy 1 moves `u=1`
   to position 1, producing `[1, 0, 2]`. The buggy `_is_valid_lexbfs`
   accepts it: the only triple (1,0,2) has ab=1-0 in E, so the buggy code
   skips it (`if not graph[a][b]: continue` is False → not skipped... wait,
   it is NOT skipped; then it checks `if graph[a][c]: continue` — ac=1-2 is
   in E, so it IS skipped). Either way no witness is demanded, so the
   invalid ordering `[1, 0, 2]` is returned as "repaired".
3. The verifier (which implements the correct property) rejects it.

So the divergence happens at the very first update: the local-repair
acceptance test is unsound because the certificate check is inverted. The
fallback `_lexbfs_full` is never reached because the buggy checker
"validates" a bad ordering.

Note the static `_lexbfs_full` itself is fine (standard partition
refinement, non-adjacent part first), and the fallback path would have
produced a valid ordering — the bug is purely in the verifier used to gate
the local repairs (and in `init`'s verification).

## REPAIR_HINTS

1. **Fix `_is_valid_lexbfs` to the correct (LB) property.** The trigger
   condition must be: for positions i < j < k with a=ordering[i],
   b=ordering[j], c=ordering[k], if **graph[a][c] and not graph[a][b]**,
   then require some d at position l < i with **graph[d][b] and not
   graph[d][c]**. Concretely, swap the two `continue` conditions:

   ```python
   if not graph[a][c]:
       continue  # ac not in E, condition not triggered
   if graph[a][b]:
       continue  # ab in E, condition not triggered
   ```

   Keep the witness loop as-is (it already checks `graph[d][b] and not
   graph[d][c]`, which matches the brief).

2. After fixing the checker, re-verify that `_lexbfs_full`'s output passes
   it on the initial graph (it should; the non-adjacent-first refinement
   convention is the one certified by this property). If it does not, the
   refinement convention in `_lexbfs_full` (adj vs non ordering) is the
   second suspect — but the trace above shows the static output `[0,1,2]`
   is valid under the correct property, so only the checker needs fixing.

3. Do **not** try to "fix" this by making the local-repair strategies
   smarter or by removing the verification gate: the gate is the only thing
   preventing invalid orderings from being returned, and with the inverted
   property it actively accepts invalid orderings. The strategies
   themselves (single-vertex moves, swaps, suffix reversal) are sound
   *given* a correct certificate check.

4. Mentioned approach that will not work: keeping the swapped condition but
   "compensating" by also checking the mirror condition — the (LB) property
   is one-directional; adding the mirror check would reject valid LexBFS
   orderings (it is not a biconditional).

5. Performance note (not the cause of this failure): with the checker
   fixed, strategies 5–8 (all transpositions, all single moves, all
   permutations) call `_is_valid_lexbfs` O(n^3) times each on an O(n^4)
   checker, which is catastrophic for n > ~10. Once correctness is
   restored, consider dropping strategies 5–8 (or bounding them by n) and
   relying on the `_lexbfs_full` fallback, which is O(n^3) with matrices.
