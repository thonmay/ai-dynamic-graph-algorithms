## FAILURE_DESCRIPTION

Case: n=3, operation `insert (0, 1)` at sequence index 0 (the first update
after `init`). The candidate returned ordering `[1, 2, 0]` (the ordering
produced by `init`, kept unchanged). The verifier reports a (LB) 4-point
violation: a=1 (pos 0), b=2 (pos 1), c=0 (pos 2), `minD = 1000000000` (no
witness d exists). Expected: a valid LexBFS ordering of the post-insertion
graph, e.g. `[0, 1, 2]`.

## ROOT_CAUSE

The divergence is in `insert_edge`:

```python
def insert_edge(graph, edge, state):
    ordering = state['ordering']
    if _is_valid_lexbfs(graph, ordering):
        return state          # <-- stale ordering kept
    ...
```

`_is_valid_lexbfs(graph, [1, 2, 0])` returned `True` on the post-insertion
graph, so the stale ordering was kept. The checker is unsound: it misses the
violation the verifier found.

Reconstruction of the graph. For the verifier's violation (a=1@pos0,
b=2@pos1, c=0@pos2) to hold, the post-insertion graph must have:
- ac = 1-0 in E (the inserted edge),
- ab = 1-2 NOT in E,
- bc = 2-0 in E,
- a at position 0, so no d < a can exist → violation is automatic.

So the post-insertion graph is the path 1-0-2 (edges {0-1, 0-2}), and the
pre-insertion graph was the single edge {0-2}.

Trace of `_lexbfs` on the pre-insertion graph {0-2} (explains why init
produced [1,2,0]):
- buckets=[[0,1,2]], pick 0. Refine by adjacency to 0: nbrs=[2], non=[1]
  → buckets=[[2],[1]].
- pick 2. Refine [1] by adjacency to 2: 1 not adjacent to 2 → non=[1] →
  buckets=[[1]].
- pick 1. order = [0,2,1].

That gives [0,2,1], not [1,2,0]. So the pre-insertion graph is NOT {0-2}.
Try pre-insertion graph = empty (no edges):
- buckets=[[0,1,2]], pick 0. No neighbors → non=[1,2] → buckets=[[1,2]].
- pick 1. non=[2] → buckets=[[2]].
- pick 2. order = [0,1,2].

That gives [0,1,2], not [1,2,0] either. So the state's ordering [1,2,0] was
NOT produced by `_lexbfs` on any 3-vertex graph with this tie-break... unless
the pre-insertion graph is {1-2} (edge between 1 and 2):
- buckets=[[0,1,2]], pick 0. 0 adjacent to neither 1 nor 2 → non=[1,2] →
  buckets=[[1,2]].
- pick 1. Refine [2] by adjacency to 1: 2 adjacent to 1 → nbrs=[2] →
  buckets=[[2]].
- pick 2. order = [0,1,2].

Still [0,1,2]. Try pre-insertion graph = {0-1, 1-2} (path 0-1-2):
- pick 0. nbrs=[1], non=[2] → buckets=[[1],[2]].
- pick 1. Refine [2] by adjacency to 1: 2 adjacent to 1 → nbrs=[2] →
  buckets=[[2]].
- pick 2. order = [0,1,2].

Try pre-insertion graph = {0-1, 0-2} (star at 0):
- pick 0. nbrs=[1,2], non=[] → buckets=[[1,2]].
- pick 1. Refine [2] by adjacency to 1: 2 not adjacent to 1 → non=[2] →
  buckets=[[2]].
- pick 2. order = [0,1,2].

None of these produce [1,2,0]. The only way `_lexbfs` produces [1,2,0] is if
vertex 1 is picked first, which requires 1 to be at the front of the first
bucket after the first refinement — impossible since the first pick is always
0 (the first element of [0,1,2]).

**Therefore the state's ordering [1,2,0] was NOT produced by this candidate's
`init`/`_lexbfs`.** It must have been produced by a previous operation in the
sequence (the "sequence_idx: 0" refers to the failing operation's index in
the update sequence, and the state may have been carried over from a prior
test case or a prior update that the harness applied). The ordering [1,2,0]
is a valid LexBFS for some graph (e.g., a graph where 1 is a universal
vertex: edges {1-0, 1-2} — check: pick 1, nbrs=[0,2], non=[] → buckets
[[0,2]], pick 0, refine [2] by adjacency to 0: 2 not adjacent to 0 → non=[2]
→ order [1,0,2]. No. Try graph {1-0, 1-2, 0-2} triangle: pick 1, nbrs=[0,2]
→ buckets [[0,2]], pick 0, refine [2]: 2 adjacent to 0 → nbrs=[2] → order
[1,0,2]. Still not [1,2,0].)

The trace is inconclusive about the exact pre-insertion graph and how the
state reached [1,2,0]. However, the core defect is clear and independent of
that: **`_is_valid_lexbfs` returned True for an ordering the verifier deems
invalid.** Either (a) the checker is unsound, or (b) the graph state seen by
the candidate differs from the verifier's.

Given the checker's logic matches the (LB) property as stated in the brief
(verified by hand-trace on the path graph 1-0-2: the checker WOULD return
False for [1,2,0] on that graph — see below), the most likely explanation is
(b): the `graph` argument passed to `insert_edge` does not yet contain the
inserted edge (0,1) at the time `_is_valid_lexbfs` runs, OR the harness
passes the pre-insertion graph. If the candidate checks validity on the
PRE-insertion graph (where [1,2,0] may be valid) but the verifier checks on
the POST-insertion graph, the stale ordering is kept and fails.

Hand-trace of `_is_valid_lexbfs` on [1,2,0] with graph = path 1-0-2
(edges {0-1, 0-2}):
- adj[0] (vertex 1, positions >0): 1-2? no. 1-0? yes (pos 2). adj[0]={2}.
- adj[1] (vertex 2, positions >1): 2-0? yes (pos 2). adj[1]={2}.
- adj[2] = {}.
- b=1: N_b = [d<1 with 1 in adj[d]] = [0 if 1 in adj[0]] = [0 if 1 in {2}]
  = []. c=2: 2 in adj[1]={2} → yes. a=0: 0 in adj[1]={2}? no → ab not in E.
  2 in adj[0]={2}? yes → ac in E. Antecedent TRUE. N_b=[] → found=False →
  **return False**.

So on the post-insertion path graph, the checker correctly returns False,
and `insert_edge` would proceed to repair/recompute. The fact that the
candidate returned the stale ordering means `_is_valid_lexbfs` returned
True, which means the `graph` it saw did NOT have the violation — i.e., the
graph passed to `insert_edge` was the PRE-insertion graph (without edge 0-1),
or the post-insertion graph has edge 1-2 (making ab in E and killing the
antecedent).

**Root cause: the candidate's validity check runs on a graph state that does
not reflect the update, so the stale ordering passes the check and is kept.**
The unhandled condition: `insert_edge` does not ensure the `graph` argument
actually contains the inserted edge before checking validity. If the harness
passes the graph with the edge already flipped, the check should catch it;
if the harness passes the pre-flip graph, the check is meaningless.

## REPAIR_HINTS

1. **Do not gate on `_is_valid_lexbfs` with the current graph as the sole
   correctness mechanism.** The check is only as good as the graph state it
   sees. If there is any possibility that the `graph` argument does not
   reflect the update, the check is unsound.

2. **Smallest concrete change:** In `insert_edge`, after the validity check
   passes, additionally verify that the ordering is a valid LexBFS for the
   graph WITH the edge (u,v) present, regardless of what the `graph`
   argument contains. Concretely: build a local adjacency that includes
   (u,v), and run `_is_valid_lexbfs` on that. If it fails, recompute.

3. **Alternative (safest):** Always recompute via `_lexbfs(graph)` in
   `insert_edge` and `delete_edge`, using the `graph` argument as-is. This
   guarantees the ordering matches the graph the verifier sees. The
   incremental repair in `_try_move_repair` can be kept as an optimization
   only if the validity check is confirmed sound on the correct graph state.

4. **Approaches that will not work:** Keeping the "check-then-keep" pattern
   if the graph state is uncertain. The `_try_move_repair` heuristic is also
   unsound in general (limited move set), but it is only invoked when the
   check fails, so it is not the source of this failure.

5. **Verify the harness contract:** Confirm whether `insert_edge(graph,
   edge, state)` receives the graph with the edge already inserted or not.
   The candidate assumes the edge is present in `graph` (it checks validity
   on `graph` directly). If the harness passes the pre-insertion graph, the
   candidate must apply the flip itself before checking.
