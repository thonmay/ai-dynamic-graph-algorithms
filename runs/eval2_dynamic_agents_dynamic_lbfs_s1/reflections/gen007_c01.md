## FAILURE_DESCRIPTION

n=3. Initial graph (before the update) has only edge (0,1); init produced
ordering [0, 1, 2] (valid for that graph). Operation: `insert (0, 2)`, so the
post-update graph is the path 1-0-2 (edges {01, 02}).

- Expected (any valid LexBFS of the path 1-0-2): [0, 2, 1] (or a symmetric
  variant like [1, 0, 2]).
- Actual returned: [0, 1, 2] — the stale pre-update ordering was kept.
- Verifier violation: (a, b, c) = (0, 1, 2) at positions (0, 1, 2):
  ac = (0,2) in E, ab = (0,1) in E... wait, ab IS in E, so the trigger
  "ab not in E" — the verifier's own reported triple is (a=0, b=1, c=2) with
  minD = 1e9 (no witness found). In the returned ordering [0,1,2] the
  relevant (LB) pair is (b, c) = (1, 2): 1 and 2 are non-adjacent, and
  a = 0 is adjacent to c = 2 but not to b = 1, so a witness d < pos(1) with
  d~1 and d not~ 2 is required; the only candidate is d = 0, which is
  adjacent to 2, so no witness exists. The ordering is invalid.

## ROOT_CAUSE

`_still_valid_after_flip` (candidates/gen007_c01.py) is unsound: it only
checks a subset of the (LB) pairs and returns True, so `insert_edge` keeps
the stale ordering instead of calling `_recompute`.

The (LB) condition for a pair (b, c) with positions i < j is:
  for every a < i with a~c and a not~ b, there exists d < a with d~b and
  d not~ c.
A flip of edge (u, v) changes the status of a pair (b, c) whenever u or v
appears in the quantified sets, i.e. whenever u or v is (1) the b or c of
the pair, or (2) an `a` in the violation set, or (3) a `d` in the witness
set. The candidate's docstring claims "All other pairs are unaffected by the
flip" — that is false. It handles:
  - the (p, q) pair itself (u or v is b or c),
  - pairs (u, c), (v, c) for c > q (u or v is b),
  - pairs (b, u), (b, v) for b < p (u or v is c).
It never handles the case where u or v is an `a` (a violator) or a `d`
(a witness) of some other pair (b, c) with b, c both distinct from u, v.

Trace on the failing case: ordering [0,1,2], u=0 (p=0), v=2 (q=2).
- Step 1: `_check_pair(graph, ordering, 0, 2)` — i=0, both `for d in range(0)`
  and `for a in range(0)` loops are empty, so it returns True vacuously.
- Step 2: `for ci in range(3, 3)` — empty.
- Step 3: `for bi in range(0)` — empty.
- Returns True → stale ordering kept.

The pair that actually breaks is (b, c) = (1, 2) (positions 1 < 2), where
the flipped vertex u = 0 is the violator `a` (a~c: 0~2 true after the
insert; a not~ b: 0 not~ 1 true). Its violation set gained u, and the
required witness d < 1 (only d = 0) is adjacent to c = 2, so the pair is
unsatisfied. The check never inspects this pair because u is neither its b
nor its c.

Note the same hole exists symmetrically for the witness role: deleting an
edge (u, v) can remove the only witness d = u (or v) for some pair (b, c),
which the check also never detects.

## REPAIR_HINTS

Smallest correct fix: make the validity test actually complete. The simplest
way is to replace `_still_valid_after_flip` with a full O(n^3) (or O(n^2)
with precomputed bitsets) check of the (LB) property over all pairs
(i, j), i < j, using the same logic as `_check_pair` (which itself is
correct: it finds the minimum witness position min_d and requires every
violator a to satisfy a > min_d). If the full check passes, keep the state;
otherwise `_recompute(graph)`. This restores correctness immediately; the
"targeted" optimization is what broke it.

If a targeted check is desired later, it must cover ALL pairs (b, c) for
which u or v can appear as b, c, a violator a, or a witness d:
  - b or c is u or v: the pairs already handled, plus (b, u)/(b, v) for
    b between p and q (currently missing: step 3 only loops b < p, but a
    pair (b, u) with p < pos[b] < q also has u as its c and its
    violation/witness sets involve v).
  - u or v is a violator a: for every pair (b, c) with pos[b] < pos[u] <
    pos[c] (and similarly for v), check whether u (resp. v) newly enters
    the violation set (a~c and a not~ b) and, if so, whether a witness
    d < pos[u] with d~b, d not~ c exists.
  - u or v is a witness d: for every pair (b, c) with pos[u] < pos[b] <
    pos[c] (and similarly for v), if u (resp. v) was the only witness
    (d~b and d not~ c) and the edge flip removed that property, the pair
    may now be unsatisfied.
Enumerating and checking all these cases is essentially as expensive as the
full check, so the full check is the pragmatic repair.

Approaches that will NOT work:
- Keeping the current three-case targeted check and just adding the missing
  (b, u)/(b, v) for p < b < q loop: the violator/witness cases (u or v as
  `a` or `d` of a pair of two other vertices) are still uncovered, as this
  failing case shows.
- "Fixing" `_check_pair` alone: it is not the bug; it is only ever called
  for the (p, q) pair, and the failing pair (1, 2) is never checked at all.
