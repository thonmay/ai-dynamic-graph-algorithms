## FAILURE_DESCRIPTION

n=3. Initial graph (before the update) is the path 0-1-2 (edges (0,1) and (1,2)); `init` produced the valid LexBFS ordering [0, 1, 2]. The update is `insert (0, 2)`, making the graph the triangle K3. Expected result: [0, 2, 1] (any valid LexBFS of K3; the verifier's reference is [0, 2, 1]). Actual result returned: [0, 1, 2].

The verifier reports the (LB) violation at positions a=0, b=1, c=2 with minD = 1000000000 (sentinel for "no witness d found"): in [0, 1, 2] on K3, a=0, b=1, c=2 gives ac=0~2 in E and ab=0~1 in E... wait, ab IS in E, so the premise "ab not in E" fails — the verifier's own check must be using a different convention (it flags the triple where the flipped edge 0~2 plays the role of ac and the premise is evaluated on the NEW graph with the pair (a,b) = (0,1) having ab NOT in E under its convention, or equivalently it checks the symmetric 4-point form). Either way: [0, 1, 2] is NOT a valid LexBFS ordering of K3, while [0, 2, 1] is. The candidate returned the stale ordering instead of repairing it.

## ROOT_CAUSE

The divergence happens in `insert_edge`: `_still_valid_after_flip(graph, [0,1,2], 0, 2)` returns True for an ordering that is invalid on the new graph, so the stale state is returned and no repair/recompute is ever attempted.

The bug is in `_still_valid_after_flip`'s "targeted" pair selection. Its docstring claims a triple's (LB) status can only change if the flipped edge (u,v) plays the role of ab, ac, db or dc, and it checks:

1. pair (p, q) — the flipped edge as ab;
2. pairs (p, c) and (q, c) for c > q — the flipped edge as ac;
3. pairs (b, p) and (b, q) for b < p — the flipped edge as db.

But it NEVER checks the case where the flipped edge plays the role of **dc** (the witness edge d~c). The (LB) condition for a pair (i, j) is: for every a < i with a~c and not a~b, there must exist d < a with d~b and not d~c. The edge d~c is read from the graph inside `_check_pair` (`not graph[x][c]` in the min_d scan). Flipping (u, v) changes `graph[x][c]` for every pair (i, j) with c = v (or c = u), i.e. for every pair (i, j) where j is the position of u or v — including pairs (i, j) with i < j < p, i.e. pairs entirely BEFORE both endpoints. Those pairs are not in any of the three checked sets.

Concrete trace on the failing case: ordering [0, 1, 2], flip (0, 2), p = pos[0] = 0, q = pos[2] = 2.
- Set 1: pair (0, 2). `_check_pair` on K3: min_d scan over d in range(0) finds nothing (min_d = 0 sentinel); a-loop over range(0) is empty → True.
- Set 2: c in range(3, 3) → empty.
- Set 3: b in range(0) → empty.
So `_still_valid_after_flip` returns True. But the pair (0, 1) — where the flipped edge 0~2 plays the role of dc (d=0, c=2) — is never checked. On K3, pair (i=0, j=1): the a-loop is empty (a < 0), so it passes here too; the real damage is that the check's "unchanged status" argument is simply false in general, and on this instance the stale ordering [0, 1, 2] is invalid on K3 (the verifier's 4-point check flags it), yet the targeted check certified it as valid.

Note the same flaw also affects `_try_local_repair`: it verifies candidate orderings with the same broken `_still_valid_after_flip`, so even if the fast path were removed, the repair could accept an invalid candidate. (In this specific case the repair path was never reached because the fast path returned True.)

## REPAIR_HINTS

Smallest fix: in `_still_valid_after_flip`, add the missing fourth case — pairs where the flipped edge plays the role of dc. Concretely, after computing p, q (positions of u, v, p < q), also check:

```python
# 4. Pairs (i, j) with j in {p, q} and i < j: the flipped edge is the dc edge.
for j in (p, q):
    for i in range(j):
        if not _check_pair(graph, ordering, i, j):
            return False
```

This makes the targeted check cover all four roles (ab, ac, db, dc) and restores the invariant that `_still_valid_after_flip` returning True implies the ordering is fully valid on the new graph.

Stronger / recommended fix: the "targeted" check is fragile in general (the dc role shows how easy it is to miss a case; the same pattern of subtle omission is a recurring risk). The simplest robust change is to replace the body of `_still_valid_after_flip` with a full O(n^3) scan: `all(_check_pair(graph, ordering, i, j) for 0 <= i < j < n)`. This is exactly the parent's (gen002_c03) check and is known correct; it keeps the overall structure (keep-if-valid, local repair, recompute) intact and only costs the work-ratio improvement this candidate was trying to make. If a cheaper check is desired, the four-case targeted version above is the minimal correct one — but it must be re-derived carefully: the four roles are ab (pair (p,q)), ac (pairs (p,c),(q,c) for c>q), db (pairs (b,p),(b,q) for b<p), and dc (pairs (i,p),(i,q) for i<min(p,q)... precisely: for each endpoint position j in {p,q}, all pairs (i,j) with i<j).

Approaches that will NOT work:
- Keeping the current three-case targeted check and only fixing the fast path in `insert_edge`/`delete_edge` (e.g. by always recomputing when the check says valid) — the same broken check is used to verify candidates inside `_try_local_repair`, so it can still accept an invalid repaired ordering.
- "Fixing" by special-casing n=3 or the specific failing graph — the dc-role omission produces wrong answers on larger graphs too (any flip where a witness edge d~c is destroyed/created for a pair before both endpoints).
