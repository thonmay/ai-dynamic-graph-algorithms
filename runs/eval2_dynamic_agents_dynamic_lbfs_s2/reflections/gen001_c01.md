## FAILURE_DESCRIPTION
n=3. After `init` on the pre-update graph, the state held ordering `[0, 1, 2]`.
Operation: `insert_edge(graph, (2, 1), state)`. The post-update graph has
edges {0-1, 0-2, 1-2} (triangle). The candidate returned `[2, 0, 1]`, which
violates the (LB) 4-point property: a=2 (pos 0), b=0 (pos 1), c=1 (pos 2) —
ac=2-1 in E, ab=2-0 not in E, and no d < a exists (a is first), so the
property fails. Expected: any valid LexBFS ordering of the triangle, e.g.
`[0, 1, 2]`.

## ROOT_CAUSE
The bug is in `_try_local_repair`: it accepts the FIRST candidate ordering
that passes `_check_lb`, but `_check_lb` is NOT a sound certificate of
LexBFS validity.

`_check_lb` implements the (LB) 4-point property of Corneil–Krueger, which
characterizes LexBFS orderings of **chordal** graphs. On a non-chordal graph
it is only a necessary condition, not sufficient. The failing case is a
triangle (3-cycle), which is non-chordal, so `_check_lb` accepts orderings
that are not LexBFS.

Concrete trace: with the old order `[0, 1, 2]` and the new edge (2,1), the
first candidate tried is the swap of u=2 and v=1, giving `[0, 2, 1]`.
`_check_lb([0, 2, 1])` passes vacuously (the only non-edge among the
positions is 0-2, and no c after it is adjacent to 0 but not to 2). So the
repair "succeeds" and `[0, 2, 1]` is returned.

The returned result `[2, 0, 1]` is a permutation of the same multiset of
vertices, so the harness's reported result is consistent with the candidate
returning a `_check_lb`-accepted but non-LexBFS ordering (the exact
permutation depends on the harness's state handling; the root cause is the
same either way: `_check_lb` accepted an invalid ordering, so the full
recompute fallback — which would have produced a valid `[0, 1, 2]` — was
never triggered).

Note: `_lexbfs_full` itself is correct (standard partition-refinement
LexBFS); the failure is entirely in the local-repair path trusting
`_check_lb`.

## REPAIR_HINTS
1. **Do not use `_check_lb` as an acceptance test for the local repair.**
   It is unsound on non-chordal graphs. Replace it with a genuine LexBFS
   validity check: for each prefix of the ordering, verify that the
   ordering restricted to the prefix is a valid LexBFS of the induced
   subgraph (i.e., re-run the partition-refinement LexBFS on the prefix and
   compare, or check the standard LexBFS invariant: for every pair of
   consecutive vertices in the ordering, their neighbor sets among the
   remaining vertices are ordered lexicographically). This is O(n^3) but
   sound.
2. **Simplest correct fix:** remove `_try_local_repair` entirely and always
   call `_lexbfs_full` in `insert_edge`/`delete_edge`. This is correct but
   defeats the "avoid full recompute" research goal.
3. **If keeping local repair:** after a candidate passes the (LB) check,
   additionally verify it is a true LexBFS ordering (e.g., by checking that
   for every position i, the sequence of neighbor-sets of order[i] restricted
   to {order[i+1], ..., order[n-1]} is non-increasing in the lexicographic
   sense, which is the defining property of LexBFS). Only accept the
   candidate if both checks pass.
4. **Approaches that will NOT work:**
   - Relying on `_check_lb` alone (the current bug).
   - Checking only that the ordering is a permutation of all vertices
     (trivially true, no validity guarantee).
   - Assuming the (LB) property suffices for all graphs (it only suffices
     for chordal graphs).
