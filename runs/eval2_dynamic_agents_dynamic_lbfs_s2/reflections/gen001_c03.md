## FAILURE_DESCRIPTION
Operation `init` on a 3-vertex undirected graph. The candidate returned
ordering `[0, 2, 1]`; the expected valid ordering is `[0, 1, 2]`.

The verifier reports a (LB) 4-point violation with fields
`a=0, b=2, c=1, pos_a=0, minD=1000000000`. The `minD` sentinel (10^9)
indicates that no witness `d` was found for the violating triple, i.e. the
(LB) property is genuinely violated by the returned ordering.

The exact adjacency matrix is not included in the failing case, so the
precise graph cannot be reconstructed from the report alone. However, the
violation confirms that `[0, 2, 1]` is **not** a valid LexBFS ordering for
the input graph, while `[0, 1, 2]` is.

## ROOT_CAUSE
The failing code path is `init` → `_lexbfs_full(A)`. There is no other
code path in `init`; the local-repair machinery is only used in
`insert_edge`/`delete_edge`.

`_lexbfs_full` implements LexBFS via label refinement:

```python
best = min(unprocessed, key=lambda v: (labels[v], v))
order.append(best)
unprocessed.remove(best)
for u in unprocessed:
    labels[u].append(1 if A[best][u] else 0)
```

**The bug**: the label comparison `min(..., key=lambda v: (labels[v], v))`
uses Python's tuple ordering, which treats a shorter tuple as a prefix and
therefore *smaller* than a longer tuple that extends it. In LexBFS, the
correct comparison is: vertex x is preferred over vertex y if
`label[x] < label[y]` in the lexicographic order where **1 < 0** (i.e.
being adjacent to more already-processed vertices is *better* / *smaller*).

The code appends `1 if A[best][u] else 0`, so a `1` means "adjacent to the
processed vertex." In standard LexBFS, the vertex with the lexicographically
**smallest** label (where 0 < 1, i.e. fewer adjacencies is smaller) is
chosen next. But the code uses `min`, which picks the smallest tuple in
Python's natural order where `0 < 1`. This means it picks the vertex with
the **fewest** adjacencies to processed vertices, which is the **opposite**
of what LexBFS requires.

**Correct LexBFS**: at each step, pick the unprocessed vertex whose label
is lexicographically smallest when `1` is treated as *smaller* than `0`
(i.e. more adjacencies = smaller label = preferred). Equivalently, pick
the vertex with the lexicographically **largest** label in Python's natural
0<1 ordering, or flip the bits so that adjacency = 0 and non-adjacency = 1.

**Concrete trace on a path graph 1-0-2** (edges {0,1},{0,2}, no {1,2}):
- A = [[0,1,1],[1,0,0],[1,0,0]]
- Step 1: all labels empty, min picks 0 (id tie-break). order=[0].
  labels[1]=[1], labels[2]=[1].
- Step 2: min of ([1],1) vs ([1],2) → 1 (id tie-break). order=[0,1].
  labels[2]=[1,0].
- Step 3: 2. order=[0,1,2]. ✓

This trace gives the correct answer, so the path graph is not the failing
input. The failing graph must be one where the 0<1 vs 1<0 distinction
matters, i.e. a graph where at some step two unprocessed vertices have
labels of different lengths or different bit patterns such that the
"fewest adjacencies" choice differs from the "most adjacencies" choice.

Example: graph with edges {0,1} only (A=[[0,1,0],[1,0,0],[0,0,0]]).
- Step 1: all empty, pick 0. labels[1]=[1], labels[2]=[0].
- Step 2: min of ([1],1) vs ([0],2) → 2 (since [0]<[1]). order=[0,2].
  labels[1]=[1,0].
- Step 3: 1. order=[0,2,1].

But the correct LexBFS on this graph: 0 first, then 1 (adjacent to 0,
label [1]) before 2 (non-adjacent, label [0]). Correct order: [0,1,2].
The code produces [0,2,1] — **wrong**. This matches the failing output.

So the failing graph is (or is isomorphic to) the graph with a single edge
{0,1} and isolated vertex 2, or any graph where the "min picks fewest
adjacencies" bug manifests.

## REPAIR_HINTS
1. **Fix the label comparison in `_lexbfs_full`**: the vertex to pick next
   is the one with the lexicographically smallest label where adjacency
   bits are ordered 1 < 0 (more adjacencies = smaller = preferred). The
   simplest fix: change the append to store `0 if A[best][u] else 1`
   (flip the bits), so that Python's natural `min` with 0<1 correctly
   prefers vertices with more adjacencies. Alternatively, keep the bits as
   is and use `max` instead of `min` for the label comparison (but be
   careful with the id tie-break: use `max` on labels and `min` on id for
   ties, which requires a custom key).

   Concretely, change:
   ```python
   labels[u].append(1 if A[best][u] else 0)
   ```
   to:
   ```python
   labels[u].append(0 if A[best][u] else 1)
   ```
   and keep `min` with key `(labels[v], v)`.

2. **Add a self-check in `init`**: after computing `order`, call
   `_check_lb(A, order)`. If it returns False, fall back to a
   known-correct reference implementation (e.g. the bucket-queue LexBFS of
   Habib et al.). This guards against any residual bug.

3. **Do not** change `_check_lb` — it correctly implements the (LB)
   property and agrees with the verifier.

4. **Do not** rely on `_local_repair` for correctness — it is only a fast
   path in the update functions and has a full-recompute fallback. Fix the
   static routine first.

5. The `_local_repair` greedy per-vertex insertion is also potentially
   unsound (it may miss valid orderings), but since it falls back to
   `_lexbfs_full`, fixing `_lexbfs_full` also fixes the fallback. The
   repair path can remain as an optimization.
