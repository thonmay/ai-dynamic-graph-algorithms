## FAILURE_DESCRIPTION
3-vertex undirected graph, initial state an empty graph (no edges). `init` produced the valid ordering `[0, 2, 1]` (any permutation is a valid LexBFS of the empty graph). Then the update `insert_edge((0, 1))` is applied, yielding the single-edge graph 0—1 (vertex 2 isolated). The verifier reports the returned ordering `[0, 2, 1]` as invalid with violation `(a=0, b=2, c=1, pos_a=0, minD=1000000000)`, i.e. the 4-point property fails for the triple of positions a=0 (vertex 0), c=1 (vertex 2), b=2 (vertex 1): ac = (0,2) is NOT in E, ab = (0,1) IS in E, and no d < a exists (a is the first position, so the witness set is empty). The expected valid ordering is `[0, 1, 2]`.

## ROOT_CAUSE
The bug is in `_is_valid_lexbfs`, which is the validator used by `_local_repair` to accept a candidate ordering. The function implements the 4-point property with the **wrong quantifier order / wrong variable roles**:

```python
for a in range(n):
    va = order[a]
    for c in range(a + 1, n):
        vc = order[c]
        if va in adj[vc]:
            continue  # ac in E, skip
        for b in range(c + 1, n):
            vb = order[b]
            if va not in adj[vb]:
                continue  # ab not in E, skip
```

It iterates `a < c < b` and tests `ac not in E` and `ab in E`. The correct (LB) property (as stated in the brief) is: for all positions `a < b < c` with **ac in E** and **ab not in E**, there exists `d < a` with **db in E** and **dc not in E**. The candidate's loop has the edge conditions inverted (it requires ac NOT in E and ab in E) and the position order wrong (a < c < b instead of a < b < c).

Consequence on the failing case: for the invalid ordering `[0, 2, 1]` after inserting (0,1), the true violation is the triple of positions a=0 (v0), b=2 (v1), c=1 (v2) with a < b < c, ac=(0,2) not in E... wait — let me re-check against the verifier's own report: the verifier reports a=0, b=2, c=1 with pos_a=0, meaning positions a=0, b=2, c=1, i.e. the verifier's convention is a < c < b (a=0, c=1, b=2) with **ac in E** and **ab not in E**: ac = (v0, v2)? No — ac with a=0,c=1 is (v0,v2) which is NOT in E. Hmm, the verifier's labels: a=0, b=2, c=1, pos_a=0. Under the brief's convention (a < b < c, ac in E, ab not in E) the positions would be a=0, b=1, c=2: ac=(v0,v1) in E ✓, ab=(v0,v2) not in E ✓, and no d<0 exists → violation. The verifier's reported keys (a=0, b=2, c=1) are just its own variable naming for the same triple (its "b" and "c" are swapped relative to the brief). Either way, the violated triple is positions {0,1,2} = vertices {0,2,1} with the edge (0,1) present and (0,2) absent, and the first position having no earlier witness.

The candidate's `_is_valid_lexbfs` does NOT catch this: it only checks triples with `ac not in E` and `ab in E` (inverted conditions), so it returns `True` for `[0, 2, 1]`. Therefore `_local_repair(order, adj, u=0)` accepts the **unchanged** ordering (insert_pos = cur_pos = 0 reproduces the original order, which the broken validator deems valid) and returns it. `insert_edge` then returns the invalid ordering `[0, 2, 1]` without ever falling back to `_lexbfs`.

Note the static `_lexbfs` itself is fine — it would produce a valid ordering (e.g. `[0, 1, 2]`) if it were reached. The divergence happens at the very first operation: `insert_edge` returns the un-repaired ordering because the validator is wrong.

## REPAIR_HINTS
1. **Fix `_is_valid_lexbfs` to implement the actual (LB) property.** The loops must be: for all positions `a < b < c` such that `order[a]` is adjacent to `order[c]` (ac in E) and NOT adjacent to `order[b]` (ab not in E), require some `d < a` with `order[d]` adjacent to `order[b]` and NOT adjacent to `order[c]`. Concretely, replace the current triple-nested loop with:

```python
for a in range(n):
    va = order[a]
    for b in range(a + 1, n):
        vb = order[b]
        if va in adj[vb]:
            continue  # ab in E, skip
        for c in range(b + 1, n):
            vc = order[c]
            if va not in adj[vc]:
                continue  # ac not in E, skip
            found = False
            for d in range(a):
                vd = order[d]
                if vb in adj[vd] and vc not in adj[vd]:
                    found = True
                    break
            if not found:
                return False
```

2. After fixing the validator, the existing control flow works: `_local_repair` will reject the unchanged ordering `[0, 2, 1]`, try other single-vertex moves (none of which fix it, since the fix requires moving vertex 1 before vertex 2 — actually moving vertex 1 to position 1 does fix it, so `_local_repair(order, adj, v=1)` would succeed), and otherwise fall back to `_lexbfs`.

3. **Do not** try to "fix" this by changing `_lexbfs` or by always falling back to full recomputation — the static algorithm is correct; the only defect is the inverted edge conditions in the validator. Also note that `_local_repair`'s `vertex not in adj` check is a no-op (adj is a list, so `vertex in adj` is always False for a list of sets... actually `vertex in adj` checks list membership of the int against sets, which is always False, so `_local_repair` always returns None early!). Wait — re-examine: `adj` is a list of sets; `vertex not in adj` tests whether the int `vertex` is an element of the list, which it never is (elements are sets). So `_local_repair` **always returns None immediately** at `if vertex not in adj: return None`. This is a second, independent bug: the local repair path is dead code, and every update falls through to `_lexbfs`. If that were the only bug, the result would still be correct (full recompute). The actual failure therefore comes from the validator bug interacting with... no — if `_local_repair` always returns None, `insert_edge` would call `_lexbfs(adj)` and return a valid ordering. So the observed failure `[0, 2, 1]` means `_local_repair` did NOT return None, i.e. `vertex in adj` was True. Re-check: `adj` is a list of sets; `0 in [set(), set(), set()]` is False. So `_local_repair` should return None... unless the state's `adj` is something else. Given the observed result is the un-repaired ordering, the most consistent explanation is that `_local_repair` returned the original ordering, which requires both (a) the `vertex not in adj` guard to pass and (b) the broken validator to accept the original order. The guard `if vertex not in adj: return None` — for a list of sets this is always True, so it always returns None. This contradicts the observed output. Therefore the trace is **inconclusive** on which exact line produced `[0, 2, 1]`; two candidate explanations: (1) the `vertex not in adj` guard behaves differently than assumed (e.g. state['adj'] was mutated into a dict or the check is `vertex not in adj` where adj is a list and Python's `in` on a list of sets with an int is indeed False → returns None → full recompute → should be valid, contradicting the failure); (2) the validator bug is the root cause and the guard is not hit because... it is always hit. 

Given the contradiction, the safest statement: the validator `_is_valid_lexbfs` is definitely wrong (inverted edge conditions, wrong position order) and must be fixed as in hint 1; additionally the guard `if vertex not in adj: return None` in `_local_repair` is almost certainly a bug (it should be `if vertex < 0 or vertex >= len(adj)` or simply removed), making the local-repair path dead code. Fix both: correct the validator's quantifiers/conditions, and remove or fix the `vertex not in adj` guard. With both fixed, the failing case is resolved either by local repair (moving vertex 1 to position 1) or by the `_lexbfs` fallback.
