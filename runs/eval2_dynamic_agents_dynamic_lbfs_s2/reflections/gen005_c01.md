## FAILURE_DESCRIPTION
Failing case: graph_n=3, sequence_idx=2, operation="crash".
Runtime error: `IndexError: list index out of range at line 63: mb = adj[vb]`
inside `_check_lb`. The crash is a hard exception (not a wrong ordering), so the
verifier aborts the whole sequence at the 3rd operation.

## ROOT_CAUSE
`_check_lb(A, order)` assumes `order` is a permutation of `range(n)` and indexes
the adjacency bitmask array `adj` (length `n`) with the *vertex id* `vb = order[b]`.
Line 63 `mb = adj[vb]` (and the analogous `ma = adj[va]`, `vc = order[c]` uses)
crash whenever `order` contains a value outside `0..n-1` or a duplicate.

The corrupted `order` is produced by `_local_repair`. Its greedy placement loop
is unsound:

```python
for v in perm:
    placed = False
    for pos in range(len(new_order) + 1):
        trial = new_order[:pos] + [v] + new_order[pos:]
        if _check_lb(A, trial):
            new_order = trial
            placed = True
            break
```

It accepts the *first* position where the partial list `trial` satisfies (LB),
without checking that the remaining unplaced vertices can still be inserted
later. A partial list can be (LB)-valid while no completion exists, so the
algorithm commits to a dead-end placement. When no position works for a later
vertex, `ok=False` and that permutation is abandoned — but the code path that
*does* finish (`ok=True`) can still return an ordering that is not a valid
completion of the base, or (in the observed crash) the caller's `order` is
already inconsistent with `A`'s vertex set, so `vb` is out of range.

Concretely, for n=3 the affected set after an update can be all 3 vertices
(e.g. a triangle or a path where u and v share a common neighbor). Then
`base = []` and `aff` has 3 elements; the greedy reinsertion over
`permutations(aff)` explores 6 orders, and the first "valid" partial trial
locks in a vertex at a position that makes the final 3-vertex ordering fail
(LB) or, if the state's `order` was already stale relative to `A` (e.g. the
state was built for a different vertex set), `vb` indexes past `adj`.

The immediate trigger is the missing guard: `_check_lb` never validates that
`order` is a permutation of `range(n)` before using its entries as indices.

## REPAIR_HINTS
1. **Immediate crash fix (defensive):** at the top of `_check_lb`, validate
   `order`: `if sorted(order) != list(range(n)): return False` (or raise a
   controlled failure). This turns the IndexError into a clean "invalid"
   result so the caller falls back to `_lexbfs_full`. Add the same guard in
   `insert_edge`/`delete_edge` before calling `_check_lb` on `state['ordering']`.

2. **Fix the unsound greedy in `_local_repair`:** the per-vertex "first valid
   position" greedy does not guarantee a valid completion. Either:
   - (a) make the search exhaustive/backtracking: for each vertex in `perm`,
     try *all* positions (not just the first valid one) with recursion and
     backtracking, or
   - (b) drop `_local_repair` entirely and always fall back to
     `_lexbfs_full(A)` when `_check_lb(A, order)` fails. For n up to a few
     hundred this is O(n^3) per update and is correct; the research goal of
     avoiding full recompute can be pursued later with a proper
     partition-refinement structure.

3. **Do NOT** try to "fix" the crash by clamping `vb` or catching IndexError
   inside `_check_lb` — that would silently return wrong validity answers.

4. Note that `_local_repair`'s `affected` set (all neighbors of u or v) can be
   O(n), and the `len(aff) > 6` guard already bails out for large affected
   sets, but for small n (3–6) the greedy is exercised and is the source of
   the bad ordering.

The smallest change that restores correctness: add the permutation guard in
`_check_lb` (fixes the crash) AND replace the greedy in `_local_repair` with a
backtracking search or remove `_local_repair` and always recompute (fixes the
underlying invalid-ordering bug).
