## FAILURE_DESCRIPTION
Crash (not a wrong ordering): `IndexError: list index out of range at line 71: mb = adj[vb]` inside `_check_lb`, reached from `insert_edge`/`delete_edge` at sequence step 2 on a 3-vertex graph. The verifier never got a result for that update.

## ROOT_CAUSE
`_check_lb` assumes `order` is a permutation of `range(n)` (i.e. every entry is a valid vertex id in `[0, n)`), but it is called on **partial** orderings from `_local_repair`. In `_local_repair`, `new_order` starts as `list(base)` (length `n - len(aff)`) and vertices from `perm` are inserted one at a time; after inserting `k < len(aff)` vertices, `trial` has length `n - len(aff) + k < n`. The check then runs:

```python
n = len(order)          # n = len(trial) < true vertex count
...
for b in range(a + 1, n):
    vb = order[b]
    ...
    mb = adj[vb]        # line 71: adj has true-n entries, but vb can be >= len(trial)
```

`adj` is built with `for v in range(n)` where `n = len(order)`, so `adj` has only `len(trial)` entries. A vertex id `vb` in the partial ordering that is numerically `>= len(trial)` (e.g. vertex 2 in a 3-vertex graph while the partial ordering has only 2 entries) indexes out of range. The same latent bug also corrupts the bitmask logic: `prefix` and `adj` masks are built over the first `len(trial)` vertex ids, not over the ids actually present, so even when no crash occurs the `(mb & ~adj[vc] & prefix)` test is computed against the wrong universe of vertex ids.

Note the crash is triggered by the *partial* trial orderings, not by the final full ordering (a full permutation of `range(n)` is safe). The final `_check_lb(A, new_order)` after all insertions is fine; the crash happens on the intermediate `trial` checks.

## REPAIR_HINTS
Smallest fix: make `_check_lb` robust to partial orderings by sizing everything to the **true** vertex count, not `len(order)`:

1. In `_check_lb`, take `n = len(A)` (or add a `n` parameter) instead of `n = len(order)`. Build `adj` over `range(n)`.
2. The 4-point property is only meaningful for complete orderings; for a partial ordering the cleanest semantics is to check the property on the *relative* order of the vertices present, treating absent vertices as "not yet placed". Concretely, `prefix` should be the bitmask of vertices that appear **before position a in the partial ordering** (i.e. iterate over the partial order and accumulate `prefix |= 1 << va` as now, but with `adj` sized to the true n). The triple loops should iterate over positions in the partial ordering (`for a in range(len(order))` etc.), and the witness test `(mb & ~adj[vc] & prefix) != 0` then works over the full vertex-id universe.
3. Alternatively, skip the per-trial `_check_lb` calls in `_local_repair` entirely and only validate the final full ordering (cheaper and avoids the partial-ordering semantics question), accepting that the greedy insertion may pick a suboptimal position.

Approaches that will NOT work:
- Guarding with `if vb >= n: continue` — this silently skips triples and makes the certificate check unsound (a partial ordering could be accepted as valid when it isn't).
- Passing `len(A)` only to the `adj` build but keeping `n = len(order)` for the loops — the `prefix` mask would still be built over the wrong id universe if vertex ids are not a prefix of `range(n)`.

Also worth noting (not the crash, but a correctness risk for later): `_local_repair`'s greedy "insert at first position that passes the check" is not guaranteed to find a valid full ordering even when one exists (the check on a partial ordering is not a monotone property of the insertion position), so the fallback to `_lexbfs_full` is essential and should be kept.
