- Valid orderings: [0,2,1] or [2,0,1] or [1,0,2] etc.

  So [0,1,2] is NOT a valid LexBFS.

The `_lexbfs` function has a bug: in the first iteration, all labels are empty, so it picks
an arbitrary vertex (0 in this case due to set ordering). Then it appends adjacency to 0
to remaining vertices' labels. label[1]=[0], label[2]=[1]. It picks 1 (smallest label [0]).
But in LexBFS, after visiting 0, the next vertex should be a NEIGHBOR of 0 (label [1]),
not a non-neighbor (label [0]).

The issue: LexBFS labels should be such that neighbors come FIRST. The standard LexBFS
uses labels where 1 = adjacent, and picks the LEXICOGRAPHICALLY SMALLEST label. But
[0] < [1], so non-neighbors are picked first. This is BACKWARDS.

In standard LexBFS (Habib et al.), the label of a vertex is the sequence of 0/1 indicating
adjacency to already-ordered vertices, and you pick the lexicographically SMALLEST. But
the convention is: 0 = adjacent, 1 = not adjacent (or equivalently, you pick the one with
most 0s first). The code uses `1 if best in adj[v] else 0`, making neighbors have 1 and
non-neighbors have 0. Then picking smallest label picks non-neighbors first. This is WRONG.

The fix: either swap 0 and 1 in the label (use `0 if best in adj[v] else 1`), or pick the
lexicographically LARGEST label.

## REPAIR_HINTS
1. **Primary bug in `_lexbfs` (line 47)**: The label encoding is inverted. Change
   `labels[v].append(1 if best in adj[v] else 0)` to
   `labels[v].append(0 if best in adj[v] else 1)`.
   This makes neighbors (adjacent to ordered vertices) have 0s, which sort first,
   matching the standard LexBFS convention where you pick the vertex with the
   lexicographically smallest label (most 0s = most neighbors among ordered).

2. **Secondary concern in `_try_repair_insert`**: The repair logic only checks the
   case where the new edge (u,v) is the (a,c) pair. It does not check cases where
   the new edge affects other triples. However, since the fallback to `_lexbfs`
   exists, this is only a performance issue, not a correctness issue — AS LONG AS
   `_lexbfs` is correct. Once `_lexbfs` is fixed, the fallback will produce valid
   orderings.

3. **The `delete_edge` "deletion preserves validity" claim is WRONG**: Removing an
   edge can invalidate the (LB) property. Example: if the ordering was valid because
   a witness d existed due to edge (d,b), deleting (d,b) can break the property.
   However, this is not the cause of THIS failure (the failure is on an insertion).
   For full correctness, `delete_edge` should also verify or recompute.

4. **Approach that will NOT work**: Simply swapping the comparison in `_lexbfs`
   (picking largest instead of smallest) without fixing the label encoding would
   also work, but the label encoding fix is cleaner and matches the literature.
