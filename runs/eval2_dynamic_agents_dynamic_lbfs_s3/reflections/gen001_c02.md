## FAILURE_DESCRIPTION
Operation: `init` on a 3-vertex undirected graph (sequence_idx 0, so no prior updates).
The candidate returned ordering `[0, 1, 2]`; the expected (valid) ordering is `[0, 2, 1]`.
The verifier reports the (LB) 4-point violation at positions a=0, b=1, c=2 with `minD = 1000000000` (sentinel = "no witness d found").

Reconstructing the graph from the violation:
- pos_a=0 → vertex 0; pos_b=1 → vertex 1; pos_c=2 → vertex 2.
- The violation requires ac ∈ E and ab ∉ E, i.e. **0–2 is an edge** and **0–1 is not an edge**.
- `minD = 1e9` means the verifier found no d < a with db ∈ E and dc ∉ E. Since a=0, there is no d < 0 at all, so the witness set is empty by construction — the only way `[0,1,2]` can be invalid is if 0–2 ∈ E and 0–1 ∉ E.
- The expected valid ordering `[0,2,1]` is consistent with the graph **edges = {0–2, 1–2}** (a path 0–2–1). On that graph, `[0,1,2]` is invalid (0's only neighbor 2 comes after 1, so 0's label is [1,0,0] while 1's is [1,1,0], and 1 > 0 lexicographically, so 1 must precede 0's non-neighbor 1... concretely: 0's label [1,0,0] vs 1's label [1,1,0] → 1's label is larger, so 1 must come before 2? No — the rule is: when a vertex is output, its label must be the maximum among the remaining vertices. 1's label [1,1,0] > 0's label [1,0,0], so 1 cannot be output second while 0 was output first... the 4-point check is the formal statement of this).

So the failing graph is the path 0–2–1 (edges {0–2, 1–2}), and `init` produced the invalid ordering `[0,1,2]`.

## ROOT_CAUSE
The bug is in `_lexbfs` (the static partition-refinement routine), which is what `init` calls. The refinement step is **not a genuine LexBFS refinement**:

```python
# split into neighbors and non-neighbors of v, preserving order
# within each part, tie-broken by rank
neigh = []
non = []
for w in b:
    if (adj[v] >> w) & 1:
        neigh.append(w)
    else:
        non.append(w)
# sort each part by rank (stable refinement)
neigh.sort(key=lambda w: rank[w])
non.sort(key=lambda w: rank[w])
```

Two defects, either of which breaks correctness:

1. **Sorting by `rank` (the vertex id / order_hint position) instead of by the vertex's current label.** In LexBFS, after outputting vertex `v`, the remaining vertices in the same bucket must be ordered by their *current labels* (the sequence of 0/1 adjacency bits to already-output vertices), with the neighbor-of-v part first. The code instead re-sorts each part by the static `rank` array. On the failing graph:
   - Start: buckets `[[0],[1],[2]]`, rank = [0,1,2].
   - Output 0. Refine bucket [1,2] by adjacency to 0: 1 is a non-neighbor, 2 is a neighbor → neigh=[2], non=[1]. Sort by rank: neigh=[2], non=[1]. Buckets become `[[2],[1]]`.
   - Output 2. Refine bucket [1] (len 1, skipped).
   - Output 1.
   - Result: `[0, 2, 1]` — wait, that's actually correct.

   Let me re-trace more carefully. After outputting 0, the bucket that contained 0 was `buckets[0] = [0]`. After popping 0, `buckets[0]` is empty, so `del buckets[0]` and `continue` — **the refinement of the rest of the bucket never happens because the bucket had only one element**. The code only refines `buckets[bi]` (the bucket the chosen vertex came from), but at the start every bucket is a singleton, so the first vertex's output never refines anything. The buckets remain `[[1],[2]]` (after deleting the empty bucket 0), and the algorithm just outputs them in order: 1, then 2. Result: `[0, 1, 2]` — the invalid ordering.

   **The real root cause:** the initial partition is `[[v] for v in range(n)]` — one singleton bucket per vertex. In the standard HMPV LexBFS, the initial partition is a single bucket containing all vertices (or the algorithm refines the *entire remaining set* by adjacency to the first vertex). Here, because each bucket is a singleton, the first vertex's refinement is a no-op (the `if not buckets[bi]: del buckets[bi]; continue` branch fires), and the algorithm degenerates to "output vertices in bucket order" = vertex-id order, with no label-based ordering at all. Subsequent refinements only ever split the bucket the chosen vertex came from, which is also a singleton, so **no refinement ever happens** and the output is always `[0, 1, 2, ..., n-1]` regardless of the graph.

2. Even if the initial partition were a single bucket, sorting by `rank` (static vertex id) rather than by the current label would still be wrong in general — the neighbor/non-neighbor split by the *last* output vertex is correct, but the order *within* each part must be by the full current label, not by a static rank.

The `_is_lexbfs` checker and `_try_repair` are irrelevant to this failure because `init` never calls them; `init` just returns whatever `_lexbfs` produces.

## REPAIR_HINTS
The smallest fix that restores correctness:

1. **Fix the initial partition in `_lexbfs`:** replace
   ```python
   buckets = [[v] for v in range(n)]
   ```
   with a single bucket containing all vertices in label order:
   ```python
   buckets = [list(range(n))]   # or sorted by rank if using order_hint
   ```
   This way, when the first vertex is output, the remaining n−1 vertices in the same bucket get refined by adjacency to it, and the algorithm behaves like real LexBFS.

2. **Fix the within-part ordering:** after splitting a bucket into `neigh` and `non` by adjacency to the just-output vertex `v`, the order within each part should be by the vertex's **current label** (the bitstring of adjacencies to all already-output vertices, in output order), not by the static `rank` array. Concretely, maintain a label (e.g., a tuple or bitset) for each remaining vertex, updated each time a vertex is output, and sort `neigh` and `non` by that label (descending, since LexBFS picks the max label). The static `rank`/`order_hint` tie-break may be used only as a final tie-breaker for equal labels.

3. **Alternative (simpler, still correct):** since the research goal is "full correctness first," replace `_lexbfs` with a straightforward O(n²) label-based LexBFS: maintain a list of (label, vertex) for remaining vertices, repeatedly pick the vertex with the maximum label (tie-break by order_hint or vertex id), append it, and update all remaining labels by appending the adjacency bit to the picked vertex. This is the classic textbook LexBFS and is trivially correct. The partition-refinement structure can be added later for the dynamic part.

Approaches that will NOT work:
- Keeping the singleton initial partition and only fixing the sort key: the refinement still never fires because each bucket has one element.
- Using `_try_repair` in `init`: there is no prior ordering to repair; `init` must produce a valid ordering from scratch.
- Relying on the `order_hint` tie-break to fix the ordering: the hint only affects tie-breaks among equal labels; it cannot compensate for the missing refinement.
