## FAILURE_DESCRIPTION
n=3, operation `insert (0,2)` at sequence_idx 0. After the insert the graph has edge (0,2) and no edge (0,1) (edge (1,2) absent). The candidate returned ordering `[0,1,2]`, which violates the (LB) 4-point property at (a,b,c)=(0,1,2), positions (0,1,2): ac=0-2 ∈ E, ab=0-1 ∉ E, and there is no d < a (pos_a=0, so the witness set is empty; reported minD=1e9). A valid ordering for this graph is `[0,2,1]` (the only non-edge pair with a later neighbor is (0,1) at positions 0,2, and there is no c after b).

## ROOT_CAUSE
The dynamic check is NOT the bug. `_check_lb` correctly returns False for the stale ordering `[0,1,2]` on the updated graph (i=0: a=0; j=1: b=1, `graph[0][1]` is 0; k=2: c=2, `graph[0][2]` is 1; `for d in order[:0]` is an empty loop so `ok` stays False → `return False`). The code therefore falls through to the fallback `order = _recompute(graph)`.

The bug is in `_recompute` itself: it is not a correct LexBFS. It is a plain BFS that only refines buckets by adjacency to the *last* vertex, never by the full label (the set of ALL earlier neighbors). On the failing graph it traces as:
- buckets=[[0],[1],[2]]; pick 0 → order=[0]; refine by adjacency to 0: [1] non-neigh, [2] neigh → buckets=[[1],[2]]
- pick 1 → order=[0,1]; refine by adjacency to 1: [2] non-neigh → buckets=[[2]]
- pick 2 → order=[0,1,2]

Result `[0,1,2]` is exactly the invalid ordering. True LexBFS labels after 0,1 are: label(2)={0}, label(1)={0,1}; since {0} ⊂ {0,1}, vertex 2 must precede 1, giving `[0,2,1]`. The candidate's refinement discards the accumulated label history (it only splits by the newest vertex), so it cannot distinguish these labels.

Consequence: the "correctness-first" design (keep old order if valid, else recompute) is defeated because the recompute fallback can itself return an invalid ordering. Note also that `init` uses the same broken `_recompute`, so even the initial state can be invalid.

## REPAIR_HINTS
Fix `_recompute` to be a genuine LexBFS; the dynamic keep-or-recompute logic can stay as is.

Smallest concrete change: maintain the full label per vertex (the set of earlier neighbors) and, at each step, pick the vertex whose label is lexicographically smallest (e.g., compare labels as bitmasks/ints, or as sorted tuples of earlier-neighbor ids). For n up to a few hundred, bitmask labels are simplest:
- `label[v]` = bitmask of earlier neighbors; when vertex v is output, `label[x] |= (1 << v)` for every neighbor x of v.
- Pick the unvisited vertex with the minimum `label` value (tie-break by vertex id for determinism).
This is O(n^2) with bitmasks and produces a valid LexBFS for any tie-break.

Alternative: implement the proper Habib-McConnell-Paul-Viennot partition refinement where each bucket's label is the full set of earlier neighbors (refine by the *entire* label, not just the newest vertex), which is what the docstring claims but the code does not do.

Approaches that will NOT work:
- Keeping the current "refine only by the last vertex" scheme with any tie-break: it fundamentally loses label history, so it cannot order vertices with nested label sets correctly (exactly the failing case).
- Relying on `_check_lb` to catch the bad recompute: the candidate never re-checks after `_recompute`, so an invalid recompute is returned as-is. (A post-hoc `_check_lb` on the recomputed order would at least detect the bug, but it does not fix it.)
- Patching only `insert_edge`/`delete_edge`: `init` shares the same broken `_recompute`, so the initial state can already be invalid.
