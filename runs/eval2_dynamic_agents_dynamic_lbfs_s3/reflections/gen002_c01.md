## FAILURE_DESCRIPTION
4-vertex undirected graph. After two prior updates the maintained ordering is
`[0, 1, 2, 3]`. The failing operation is `insert (0, 3)` (sequence_idx 2).
The candidate returned the unchanged ordering `[0, 1, 2, 3]`, but the
verifier reports an (LB) violation at positions a=1, b=2, c=3 (vertices
a=1, b=2, c=3): edge (1,3) is in E, edge (1,2) is not in E, and no
d at position < 1 (only vertex 0) witnesses it — i.e. `graph[0][2] and not
graph[0][3]` is false in the post-insertion graph (minD stayed at the
sentinel 1e9). The expected valid ordering is `[0, 1, 3, 2]`.

## ROOT_CAUSE
`_try_repair_insert` (the local "repair" for insertions) is unsound. Its
docstring claims: "Inserting (u,v) can only create new (LB) violations where
the new edge plays the role of ac (the 'in E' pair)" and therefore it only
checks triples where the inserted edge is the ac pair (a=u, c=v or a=v, c=u).

That claim is false. Inserting (u,v) also creates new violations where the
new edge plays the role of **ab** (the "not in E" pair): for any triple
a < b < c with b = u or b = v, the condition `ab not in E` becomes true
after the insertion, so a new witness requirement `exists d < a with db in E
and dc not in E` is introduced. The code never checks these triples, so it
returns the old ordering as "still valid" and `insert_edge` skips the
recompute fallback.

Concrete trace on the failing case: after inserting (0,3), the triple
(a,b,c) = (1,2,3) has ab = (1,2) not in E and ac = (1,3) in E, so a witness
d < a (only d=0) with (0,2) in E and (0,3) not in E is required. Since
(0,3) is now in E, no witness exists and the ordering is invalid. The new
edge (0,3) is neither the ab pair nor the ac pair of this triple — it is the
**dc** pair (d=0, c=3). The insertion destroyed the witness condition
`dc not in E` for an existing triple, which is a third, entirely unhandled
way an insertion can break (LB). `_try_repair_insert` only handles the ac
case, so it returns the ordering unchanged and the invalid state is returned
to the verifier.

## REPAIR_HINTS
Smallest correct fix: make the insertion path as safe as the deletion path.
In `insert_edge`, replace the call to `_try_repair_insert` with a full
verification:

```python
def insert_edge(graph, edge, state):
    ordering = state['ordering']
    if not _check_lb_full(graph, ordering):
        state['ordering'] = _lexbfs(graph)
    return state
```

`_check_lb_full` is already correct (it is the same checker the deletion path
uses and the verifier's property), so this restores full correctness with no
other changes. `_try_repair_insert` can be deleted or kept unused.

If a fast path is still wanted, the local check must cover ALL three roles
the new edge can play in a violating triple: (1) as ac (already handled),
(2) as ab — for a < b < c with b in {u,v} and ab not in E and ac in E,
check a witness d < a exists, and (3) as dc — for a < b < c with
{d,c} = {u,v}, d < a, db in E, the insertion may have made dc in E, so the
witness is destroyed; this requires checking every triple whose witness set
contained u or v. That is essentially as expensive as `_check_lb_full`, so
the full check is the pragmatic repair.

Approaches that will NOT work:
- Keeping the current `_try_repair_insert` and only adding the "ab role"
  case: the "dc role" (witness destruction, the actual failing case) would
  still be missed.
- Any local check that only inspects triples containing u or v as a or c:
  the failing triple (1,2,3) contains neither 0 nor 3 as a or c; the
  affected vertex is the witness d=0 and the c-neighbor 3, so the check must
  scan triples where u or v appears as d or as the c-side of a witness.
