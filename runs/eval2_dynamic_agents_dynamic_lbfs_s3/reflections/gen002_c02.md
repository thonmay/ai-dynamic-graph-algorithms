## FAILURE_DESCRIPTION
Operation: `init` on a 4-vertex undirected graph (sequence_idx 0, so no prior state).
The candidate returned ordering `[0, 1, 2, 3]`; the expected valid LexBFS ordering is `[0, 1, 3, 2]`.
The verifier reports a (LB) 4-point violation at positions a=0, b=2, c=3 (minD=1):
- pos_a=0 -> vertex 0, pos_b=2 -> vertex 2, pos_c=3 -> vertex 3.
- Condition "ac in E and ab not in E" holds: 0-3 is an edge, 0-2 is not.
- Required: some d < a (i.e. d < 0) with db in E and dc not in E. There is no such d, so the property is violated.

The graph is consistent with: edges {0-1, 0-3, 1-2, 1-3, 2-3} (0-2 absent). In this graph the only valid LexBFS orderings are `[0,1,3,2]` and its reverse `[2,3,1,0]`; `[0,1,2,3]` is not a LexBFS ordering.

## ROOT_CAUSE
The bug is in `_lexbfs`'s tie-breaking, which is not a legal LexBFS tie-break.

Responsible lines:
```python
    if order_hint is None:
        rank = list(range(n))
    ...
        key = (labels[v], -rank[v])
        if best is None or key > best[0]:
            best = (key, v)
```

With `order_hint=None` (the `init` path), `rank[v] = v`, so the key is `(labels[v], -v)`. The comparison `key > best[0]` therefore prefers the LARGER vertex id on label ties (e.g. at step 1, vertices 2 and 3 both have label `0b10`; keys `(2,-2)` vs `(2,-3)` pick vertex 2).

LexBFS tie-breaking must be FIXED in advance (any fixed total order, e.g. vertex id ascending). The standard label formulation picks the remaining vertex with the lexicographically MAXIMUM label, breaking ties by the fixed order (smallest id). Picking the largest id on ties is not a valid LexBFS tie-break and produces orderings that violate the (LB) 4-point property, as seen here: step 1 wrongly picks 2 over 3, yielding `[0,1,2,3]`.

Note the asymmetry: with an `order_hint`, `rank = position in hint`, so `-rank` correctly prefers the EARLIER hint position (a fixed order) — that path is fine. Only the `order_hint=None` path is broken.

## REPAIR_HINTS
Smallest fix: in `_lexbfs`, when `order_hint is None`, set `rank = [n - 1 - v for v in range(n)]` (or equivalently change the tie-break to prefer smaller vertex id). Then `key = (labels[v], -rank[v])` prefers smaller ids on ties, which is a legal fixed tie-break and makes `init` produce a valid LexBFS (e.g. `[0,1,3,2]` on the failing graph).

Do NOT "fix" this by changing the label comparison direction (e.g. picking the minimum label) — that is not LexBFS either. The label-max formulation is correct; only the tie-break order is wrong.

Secondary (not the cause of this failure, but worth flagging for the repair role): `_is_lexbfs` is O(n^4) and `_try_repair` calls it O(n^3) times, so the "cheap repair" path is actually far more expensive than the O(n^2) full recompute it guards. If the goal is to avoid full recomputation, the repair search should be replaced with a cheaper validity check or a targeted local reordering; as written it will be a performance liability even though it is not what broke this case.
