## FAILURE_DESCRIPTION
3-vertex graph. Initial graph (before the update) has only edge (0,1):
adjacency `[[0,1,0],[1,0,0],[0,0,0]]`. `init` produced ordering `[0, 1, 2]`
(valid for that graph). Then `insert_edge(graph, (0,2), state)` is called on
the updated graph `[[0,1,1],[1,0,0],[1,0,0]]` (edges 0-1 and 0-2). Expected:
`[0, 2, 1]` (the valid LexBFS of the updated graph; `[0,1,2]` is NOT valid
there). Actual: `[0, 1, 2]` — the stale ordering was kept. Verifier violation
record: a=0 (pos 0), b=1 (pos 1), c=2 (pos 2), minD=1e9 (no witness d < a
exists; a is at position 0 so `order[:0]` is empty).

## ROOT_CAUSE
`_check_lb` implements the WRONG (LB) 4-point property, so it is unsound: it
returns True for orderings that are not valid LexBFS orderings, and
`insert_edge`/`delete_edge` keep the stale ordering instead of recomputing.

The candidate's docstring and code state the trigger as "a < b < c with
**ac in E and ab not in E**". The correct Corneil–Krueger (LB) property is:
for all positions a < b < c with **ab in E and ac not in E**, there exists
d < a with db in E and dc not in E. The candidate's trigger is the mirror
image (swapped a↔c in the edge conditions), which is not equivalent to
LexBFS validity.

Exact trace of the false acceptance, order `[0, 1, 2]`, updated graph edges
{0-1, 0-2}:
- i=0 (a=0): j=1 (b=1): `graph[0][1]=1` → `continue` (ab in E, skipped).
  j=2 (b=2): `graph[0][2]=1` → `continue`. No inner work.
- i=1 (a=1): j=2 (b=2): `graph[1][2]=0` → ab not in E, so the inner loop
  runs; but k ranges over `range(3, 3)` = empty, so no c is checked.
- i=2: no j.
`_check_lb` returns True, so `insert_edge` returns the stale `[0, 1, 2]`.

Why `[0, 1, 2]` is invalid for the updated graph: in any LexBFS, vertex 0 is
first; its neighbors 1 and 2 both get label {0} and are tied, so the id
tie-break must place 2 before 1, giving `[0, 2, 1]`. The verifier's (LB)
check flags the returned ordering with the violation record above.

The static `_recompute` (bitmask-label LexBFS with id tie-break) is correct;
the bug is entirely in the "is the old ordering still valid?" fast path.

## REPAIR_HINTS
1. Fix `_check_lb` to implement the CORRECT (LB) 4-point property: for all
   positions a < b < c with `graph[a][b] == 1` and `graph[a][c] == 0`, require
   some d at position < a with `graph[d][b] == 1` and `graph[d][c] == 0`.
   Concretely, swap the two trigger conditions in the current code: change
   `if graph[a][b]: continue` to `if not graph[a][b]: continue` and change
   `if not graph[a][c]: continue` to `if graph[a][c]: continue`.
   IMPORTANT: before trusting this, verify the corrected checker against
   `_recompute`'s output on many random graphs (both directions: the checker
   must accept every ordering `_recompute` produces, and must reject
   known-invalid orderings such as `[0,1,2]` on the updated graph above). If
   the corrected property still misclassifies, the safest fallback is to drop
   the fast path entirely and always `_recompute` in `insert_edge`/
   `delete_edge` (correctness first, per the research goal).
2. Do NOT try to "patch" the checker with extra special cases (e.g. handling
   a at position 0 separately) — the property itself is misstated, so any
   patch on top of the wrong trigger conditions will keep accepting invalid
   orderings.
3. The checker is O(n^4); acceptable for correctness-first, but if the fast
   path is kept, consider the standard O(n^2) (LB) check: for each b, the set
   of earlier neighbors of b must be a prefix of the set of earlier
   non-neighbors of b (i.e. there is no position p < b with p a non-neighbor
   of b and some q with p < q < b a neighbor of b). This formulation is
   easier to get right.
4. Approaches that will not work: keeping the current trigger conditions and
   only tightening the witness search; or comparing the old ordering to a
   fresh `_recompute` result for equality (LexBFS is not unique — different
   valid orderings exist, so equality is too strict and would force
   unnecessary recomputes, while the current checker is too weak).
