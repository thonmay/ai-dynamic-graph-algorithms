## FAILURE_DESCRIPTION
Operation: `init` on a 4-vertex undirected graph (sequence_idx 0, so no prior state).
The candidate returned ordering `[3, 1, 2, 0]`; the expected (valid) ordering is `[0, 3, 1, 2]`.
The verifier reports a (LB) 4-point violation at positions a=3, b=2, c=0 (pos_a=0, minD=1):
in the returned order, position 0 = vertex 3, position 2 = vertex 2, position 3 = vertex 0.
So the violated triple is (a=3, b=2, c=0) with a<b<c in position: 3-2 not in E, 3-0 in E,
and no d < a (i.e. no vertex before position 0 — vacuously none) with d-2 in E and d-0 not in E.
The graph is consistent with: E = {3-0, 3-1, 3-2, 1-2} (a 4-cycle 0-3-1-2-0 plus chord 3-2).
A valid LexBFS is `[0, 3, 1, 2]` (or `[2, 1, 3, 0]`); `[3, 1, 2, 0]` is NOT a valid LexBFS.

## ROOT_CAUSE
The bug is in `_lexbfs`: it implements a **greedy "max-label" selection** rather than the
correct LexBFS partition-refinement. The responsible lines:

```python
    for step in range(n):
        # pick max label, tie-break by rank (earlier in hint wins)
        best = None
        for v in remaining:
            key = (labels[v], -rank[v])
            if best is None or key > best[0]:
                best = (key, v)
        v = best[1]
```

Correct LexBFS (Habib–McConnell–Paul–Viennot) maintains a partition of the remaining
vertices into **blocks of equal label** and, at each step, picks the **first block**
(lexicographically smallest label, i.e. the block that was refined earliest / is at the
front of the queue), then refines every other block by the adjacency to the picked
vertex. The candidate instead picks the single vertex with the **maximum** label at
each step. "Max label" is the wrong direction: LexBFS is defined by the *smallest*
lexicographic label (equivalently, the first block in the refinement queue), and the
label comparison must be over the *output order* of already-picked vertices, which the
candidate does handle via `bit = 1 << step` — but the max-vs-min inversion alone breaks
validity.

Tracing on the failing graph (E = {3-0, 3-1, 3-2, 1-2}), no hint, rank = [3,2,1,0]:
- step 0: all labels 0; tie broken by -rank → vertex 3 (rank 3, -rank -3 is smallest…
  actually key = (0, -rank[v]); max key wins; -rank: v0→-3, v1→-2, v2→-1, v3→0; max is
  v3). Pick 3. Correct LexBFS would pick the first block = {0,1,2,3} and any vertex in
  it, e.g. 0 — but the max-label rule picks 3.
- step 1: labels: v0=1 (adj to 3), v1=1, v2=1, v3 removed. All equal; tie → v1 (rank 2).
- step 2: labels: v0=1, v2=1 (both adj to 1? v0 not adj to 1 → v0 stays 1; v2 adj to 1 → v2=1|2=3).
  Max label = v2 (3). Pick 2.
- step 3: pick 0.
Result: [3, 1, 2, 0] — exactly the failing output. The correct LexBFS [0, 3, 1, 2]
requires picking 0 first (smallest-label block, tie by vertex id), not 3.

The `_is_lexbfs` checker and `_try_repair` are irrelevant to this failure because
`init` calls `_lexbfs` directly and never validates its output.

## REPAIR_HINTS
Replace the greedy max-label selection in `_lexbfs` with the standard
partition-refinement LexBFS:

1. Maintain a list (queue) of blocks; each block is a list of remaining vertices that
   share the same label. Start with one block containing all vertices.
2. At each step, take the **first** block in the queue, pick its first vertex v (the
   tie-break within a block is by the hint position / vertex id), append v to the order.
3. Refine every other block by splitting it into (neighbors of v, non-neighbors of v),
   in that order, and append the non-empty sub-blocks to the end of the queue (in the
   order the blocks were visited). Remove v from its block; if the block becomes empty,
   drop it.
4. Repeat until all vertices are output.

This is O(n^2) with bitsets and is the textbook HMPV algorithm. The current
`labels`/`bit = 1 << step` machinery can be kept for the refinement step (a block's
label is the bitstring of adjacencies to already-output vertices in output order), but
the **selection rule must change from "max label over all remaining vertices" to
"first block in the refinement queue"**.

Do NOT try to fix this by changing the tie-break or by inverting the comparison to
"min label over all remaining vertices" — that is still wrong, because LexBFS is not
"pick the min-label vertex"; it is "pick from the first block of the partition
refinement". The block structure (which vertices have been refined together) is what
encodes the lexicographic order, and a flat min-label selection over all remaining
vertices does not reproduce it.

Also: `init` should validate its output with `_is_lexbfs` (or the repair path) as a
safety net, since the current code trusts `_lexbfs` blindly.
