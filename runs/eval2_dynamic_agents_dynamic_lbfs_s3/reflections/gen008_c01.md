## FAILURE_DESCRIPTION
n=3. Sequence step 0: `insert (0,1)`. The pre-insert graph (from `init`) was the path 0-2-1 (edges (0,2),(2,1)); `init` produced ordering `[0,2,1]`, which is a valid LexBFS of that graph. After inserting (0,1) the graph is the triangle K3 (edges (0,1),(0,2),(1,2)). The candidate kept `[0,2,1]` (its local (LB) check passed, so no recompute). The verifier reported a violation at triple (a=0, b=2, c=1) with `pos_a=0, minD=1000000000` and "expected" `[0,1,2]`.

## ROOT_CAUSE
The candidate's output is NOT actually wrong: `[0,2,1]` is a valid LexBFS of K3. In the (LB) property, the triple (a=0, b=2, c=1) has ac=(0,1)∈E but also **ab=(0,2)∈E**, so the precondition "ab not in E" is false and the triple imposes no constraint. The verifier's `minD=1000000000` (sentinel "no witness d found") is only meaningful when ab∉E; here it is a spurious report. Tracing the candidate's own `_check_lb_local` on K3 with ordering [0,2,1]: every (i,j) pair with j>i has j∈N[i] (complete graph), so all constraints are skipped and it correctly returns True. The candidate's logic and its full checker `_check_lb_full` agree: the ordering is valid. The divergence is in the **verifier's violation detection**, which appears to flag triples without correctly enforcing the "ab not in E" precondition (or to compare against a fixed expected ordering rather than checking validity). No line in the candidate is responsible for this failure.

## REPAIR_HINTS
Do NOT "fix" the candidate's ordering logic for this case — the output `[0,2,1]` is a legitimate LexBFS of the triangle, and any change aimed at producing `[0,1,2]` specifically would be chasing a non-unique "expected" value. The candidate's local-check restriction (only triples where a, b, or c is u or v) is sound for a single edge flip and is not the problem here.

The actionable item is on the verifier side: its (LB) violation check must (1) only consider triples with a<b<c, ac∈E, and **ab∉E**, and (2) treat the result as valid if no such triple lacks a witness d<a with db∈E and dc∉E. If the verifier instead compares against a hardcoded expected ordering, it must be replaced with a validity check, since LexBFS orderings are not unique (any start vertex, any tie-break is legal).

If the harness cannot be changed, the only (wasteful) workaround would be to recompute from scratch on every update, but that would still return a valid ordering like `[0,2,1]` or `[0,1,2]` depending on tie-breaks and would not guarantee matching a fixed "expected" — so it does not actually fix a verifier that demands a specific ordering.
