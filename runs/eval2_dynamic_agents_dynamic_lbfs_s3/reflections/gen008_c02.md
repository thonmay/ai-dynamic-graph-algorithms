## FAILURE_DESCRIPTION
3-vertex graph. After `init` the state holds ordering `[0, 1, 2]` (valid for the pre-update graph). The update is `insert (2, 0)` (edge (0,2) added). The candidate returned `[0, 1, 2]` unchanged; the verifier reports the (LB) violation with a=0, b=1, c=2 (pos_a=0, minD=1e9, i.e. no witness d exists). Expected: a recompute producing a valid ordering such as `[0, 2, 1]`.

## ROOT_CAUSE
The "optimization" in `_check_lb_affected` is unsound: it only checks triples in which the updated edge (x,y) is one of the four edges (ac, ab, db, dc), and its hand-derived case enumeration (A1, A2, C1, D2) is not exhaustive. The (LB) property is a universal statement over ALL triples a<b<c; a single edge update can invalidate a triple where the updated edge is the *witness* edge (db or dc) for that triple, and the code's case analysis silently drops such cases (e.g. "Case B: a = y ... impossible", "C2: ... impossible").

Concrete trace on the failing case. The pre-update graph must have had edge (1,2) only (so `[0,1,2]` was valid: the only triple a=0,b=1,c=2 has ac=(0,2) not in E, no constraint). After inserting (0,2): ac=(0,2) in E, ab=(0,1) not in E, and there is no d < a=0, so (LB) fails.

With x=0, y=2 (px=0, py=2), this triple is a=0=x, b=1, c=2=y, which is Case A2 ("a = x, c = y"). Tracing A2: `if graph[x][y]` is true; b=1 has pb=1 between px=0 and py=2; `graph[0][1]` is 0 so not skipped; the witness loop `for d in ordering: if pd >= px: break` breaks immediately at the first d (px=0), `found` stays False, and the function returns False — which WOULD trigger a recompute. So on this exact instance the A2 branch appears to catch the violation, yet the candidate returned the stale ordering. This means the actual pre-update graph differs from the (1,2)-only guess (the trace is inconclusive about which pre-update graph makes the check return True), but the structural defect is independent of the instance: the restricted check is a partial, hand-derived cover of "triples affected by edge (x,y)" and is not provably exhaustive. The failing case is a triple whose invalidation the enumeration does not reach — the updated edge acts as the witness (db or dc) for a triple whose a,b,c positions the case analysis did not cover.

## REPAIR_HINTS
Smallest correct fix: replace the restricted `_check_lb_affected` with a FULL verification of the (LB) property on the new graph after every update, and recompute via `_lexbfs` when it fails. Full check: for every triple of positions a<b<c with ac in E and ab not in E, assert some d<a with db in E and dc not in E (O(n^4), or O(n^3) with precomputed per-pair witness tables). This is trivially correct and restores the invariant; the "optimization" is what broke it.

Do NOT try to patch the case enumeration (adding more A/C/D subcases) — the hand-derived cover is the bug. Any partial enumeration of "triples affected by edge (x,y)" is fragile because the updated edge can act as the witness (db or dc) for triples whose a,b,c are arbitrary, and the position-ordering arguments in the comments (e.g. "impossible since pos[c] > py > px") do not cover all witness-side configurations. If performance matters later, maintain witness counts incrementally, but correctness first: full check + recompute.
