## FAILURE_DESCRIPTION
- Operation: `init` (sequence_idx 0), n = 3, undirected.
- The candidate returned ordering `[0, 1, 2]`; the verifier expected `[0, 2, 1]`.
- Violation reported: (a, b, c) = (0, 1, 2) at positions (0, 1, 2), with `minD = 1000000000` (sentinel = "no valid d found").
- Interpretation: in the returned order, vertex 0 is at position 0, vertex 1 at position 1, vertex 2 at position 2. The verifier found that 0–2 is an edge, 0–1 is NOT an edge, and there is no d < 0 (vacuously impossible) that is adjacent to 1 and non-adjacent to 2. So the (LB) 4-point property is violated.
- The only graph consistent with this: edges {0,2} and {1,2} (a path 0–2–1). The correct LexBFS orderings are `[0, 2, 1]` or `[1, 2, 0]`; `[0, 1, 2]` is not a valid LexBFS.

## ROOT_CAUSE
The bug is in `_lexbfs_full_simple` — the "simple O(n^2) LexBFS using bitset labels". It is NOT a correct LexBFS implementation.

The responsible lines:

```python
buckets = [[v] for v in range(n)]
...
v = buckets[0].pop(0)
order.append(v)
new_buckets = []
for bucket in buckets:
    if not bucket:
        continue
    inb = [x for x in bucket if (adjb[v] >> x) & 1]
    outb = [x for x in bucket if not ((adjb[v] >> x) & 1)]
    if inb and outb:
        new_buckets.append(inb)
        new_buckets.append(outb)
    else:
        new_buckets.append(bucket)

```

Two distinct defects:

1. **Wrong refinement rule.** Standard LexBFS (Habib–McConnell–Paul–Viennot) maintains a partition of the *unprocessed* vertices into buckets, each bucket holding vertices with the same label (the set of already-processed neighbours). When a vertex v is selected, each bucket is split into (bucket ∩ N(v), bucket \ N(v)) — the N(v) part goes FIRST. That is what this code does, so the split rule itself is actually the standard one.

2. **Wrong selection rule (the real bug).** LexBFS requires that the next vertex be chosen from the *front* bucket, and that the front bucket be the one with the lexicographically smallest label. In this implementation, all buckets start as singletons `[[0], [1], [2], ...]` and the code always picks `buckets[0].pop(0)`. After the first selection, the front bucket may contain multiple vertices, but the code never re-sorts buckets by label — it just keeps the insertion order of splits. This is NOT LexBFS; it is a greedy BFS-like ordering that happens to coincide with LexBFS only in special cases.

Trace on the failing graph (edges {0,2}, {1,2}):
- Initial buckets: `[[0], [1], [2]]`.
- Pick v=0. Split each bucket by N(0)={2}:
  - `[0]` → already consumed.
  - `[1]`: 1 ∉ N(0) → stays `[1]`.
  - `[2]`: 2 ∈ N(0) → stays `[2]`.
  - New buckets: `[[1], [2]]`.
- Pick v=1 (front of `[[1], [2]]`). Split by N(1)={2}:
  - `[2]`: 2 ∈ N(1) → stays `[2]`.
  - New buckets: `[[2]]`.
- Pick v=2.
- Result: `[0, 1, 2]`. ❌

A correct LexBFS with start 0 would, after picking 0, have buckets `[[1], [2]]` with labels: label(1) = ∅ (1 not adjacent to 0), label(2) = {0} (2 adjacent to 0). The lexicographically smaller label is ∅, so 1 should be picked next — wait, that gives `[0, 1, 2]` too. Let me re-check.

Actually, in LexBFS the label of a vertex is the set of *already-processed* vertices adjacent to it. After processing 0:
- label(1) = ∅ (1 not adjacent to 0)
- label(2) = {0} (2 adjacent to 0)

Lexicographic comparison: ∅ < {0}, so 1 is picked next. Then label(2) = {0, 1}. Order: `[0, 1, 2]`.

But the verifier says `[0, 1, 2]` is INVALID and `[0, 2, 1]` is valid. Let me re-check the 4-point property on `[0, 1, 2]` with edges {0,2}, {1,2}:
- a=0 (v=0), b=1 (v=1), c=2 (v=2): ac = 0-2 ∈ E ✓, ab = 0-1 ∉ E ✓. Need d < 0: none exist. → VIOLATION.

And on `[0, 2, 1]`:
- a=0 (v=0), b=1 (v=2), c=2 (v=1): ac = 0-1 ∉ E → skip.
- a=0 (v=0), b=2 (v=1): no c > b. → OK.
- a=1 (v=2), b=2 (v=1): ac = 2-1 ∈ E, ab = 2-1 ∈ E → skip (ab in E).
- Valid. ✓

So `[0, 2, 1]` is valid and `[0, 1, 2]` is not. But my LexBFS trace gave `[0, 1, 2]`. Let me re-examine: in LexBFS, the label comparison is lexicographic on the *sequence* of 0/1 (adjacent or not to each processed vertex in order). After processing 0:
- Vertex 1: not adjacent to 0 → label starts with 0.
- Vertex 2: adjacent to 0 → label starts with 1.

In LexBFS, the bucket with the *smaller* label (0 < 1) goes to the front. So vertex 1 (label 0) is in front, vertex 2 (label 1) is behind. We pick vertex 1 next. This gives `[0, 1, 2]`.

But `[0, 1, 2]` is NOT a valid LexBFS per the 4-point property! This means either:
(a) My understanding of LexBFS label comparison is inverted, or
(b) The 4-point property check in the verifier uses a different convention.

Re-reading the brief: "for all positions a < b < c with ac in E and ab not in E, there exists d < a with db in E and dc not in E."

In `[0, 1, 2]` with edges {0,2}, {1,2}: a=0, b=1, c=2. ac=0-2∈E, ab=0-1∉E. Need d<0: impossible. Violation confirmed.

The issue: in standard LexBFS, the label of a vertex is the sequence of 0/1 indicating adjacency to each *previously selected* vertex. The vertex with the lexicographically **smallest** label is selected next. "Smallest" means 0 < 1, so a vertex NOT adjacent to the previous vertex gets priority.

After selecting 0: vertex 1 has label [0] (not adj to 0), vertex 2 has label [1] (adj to 0). Smallest label is [0], so select 1. Order: [0, 1, 2].

But this violates the 4-point property! The resolution: the 4-point property as stated in the brief may use a different convention than what I'm assuming. OR, the standard LexBFS actually selects the vertex with the lexicographically **largest** label (i.e., adjacent vertices come first within a bucket).

Let me re-check: in the standard LexBFS (Cornéil & Krueger, 1985), the partition refinement works as follows: when vertex v is selected, each bucket is split into (B ∩ N(v), B \ N(v)), and the N(v) part is placed **before** the B\N(v) part. The next vertex is taken from the **front** of the partition. This means vertices adjacent to v come first.

So after selecting 0 (N(0)={2}):
- Bucket [1]: 1 ∉ N(0) → stays as [1] (the "out" part).
- Bucket [2]: 2 ∈ N(0) → stays as [2] (the "in" part).
- The "in" part should come BEFORE the "out" part. So the partition becomes [[2], [1]].
- Next vertex: 2. Order so far: [0, 2].
- After selecting 2 (N(2)={0,1}): bucket [1]: 1 ∈ N(2) → stays [1].
- Order: [0, 2, 1]. ✓

**THE BUG**: In `_lexbfs_full_simple`, when a bucket is split into `inb` and `outb`, the code does:
```python
new_buckets.append(inb)
new_buckets.append(outb)
```
This puts `inb` before `outb` WITHIN the same bucket's position. BUT the issue is that the split is done **per bucket independently**, and the relative order of different buckets is preserved from the previous iteration. The problem is more subtle: the code processes buckets in order and appends inb then outb for each. This is actually correct for the standard algorithm IF the initial ordering of buckets is correct.

Wait — let me re-trace more carefully. Initial: `buckets = [[0], [1], [2]]`.

Select v=0 (from buckets[0]). Remove 0 from its bucket (it was the only element, so bucket [0] becomes empty and is skipped). Now process remaining buckets [1] and [2]:
- Bucket [1]: inb = [] (1 ∉ N(0)), outb = [1]. Since inb is empty, just append [1].
- Bucket [2]: inb = [2] (2 ∈ N(0)), outb = []. Since outb is empty, just append [2].
- new_buckets = [[1], [2]].

Select v=1 (from buckets[0] = [1]). Process remaining bucket [2]:
- Bucket [2]: inb = [2] (2 ∈ N(1)), outb = []. Append [2].
- new_buckets = [[2]].

Select v=2. Order: [0, 1, 2]. ❌

The problem: after selecting 0, the partition should be [[2], [1]] (adjacent-to-0 vertices first), but the code produces [[1], [2]] because it processes buckets in their original order and the "in" part of bucket [2] is appended after the "out" part of bucket [1].

**The root cause is clear**: the code does NOT reorder buckets so that all "in" parts (vertices adjacent to the selected vertex) come before all "out" parts (vertices not adjacent). It only splits each bucket in place, preserving the original bucket order. The correct LexBFS requires that after each selection, the partition is reorganized so that the front bucket contains the vertices with the lexicographically smallest labels, which means the "in" parts must be gathered at the front.

The fix: after splitting all buckets, the new partition should be ordered by label. The simplest correct approach is to maintain the partition as a list of buckets sorted by their label (the set of processed neighbours). After each split, re-sort the buckets by their label. Alternatively, use the standard approach where you maintain a single ordered list and split it, keeping the "in" part at the front.

Since all vertices in a bucket share the same label, you can compute the label for each bucket and sort.

2. **Alternative (simpler and correct)**: Replace `_lexbfs_full_simple` with a straightforward O(n^2) LexBFS that maintains a list of unprocessed vertices and, at each step, computes the label of each unprocessed vertex (the sequence of 0/1 for adjacency to each already-processed vertex in order), then selects the unprocessed vertex with the lexicographically smallest label. This is O(n^3) total but clearly correct.
