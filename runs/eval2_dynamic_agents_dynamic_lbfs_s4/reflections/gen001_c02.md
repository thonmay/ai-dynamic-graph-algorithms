## FAILURE_DESCRIPTION
Failing case is at `init` (sequence_idx 0), so the bug is in the static `_lexbfs`, not the dynamic update path.

- Graph: n=3, undirected. The reported 4-point violation (a=0 at pos 0, b=1 at pos 1, c=2 at pos 2, minD left at the 1e9 sentinel) implies the graph has 0–1 as a NON-edge and 0–2 as an EDGE. A concrete matching graph is edges {0-2, 1-2} (adj[0]=[0,0,1], adj[1]=[0,0,1], adj[2]=[1,1,0]).
- Expected: any valid LexBFS, e.g. `[0, 2, 1]`.
- Actual: `[0, 1, 2]`.
- Violated property: the (LB) 4-point property. For a=0, b=1, c=2: ab∉E, ac∈E, and there is no d before a (a is at position 0), so the property fails.

## ROOT_CAUSE
The partition-refinement step in `_lexbfs` refines the WRONG buckets. After selecting vertex `v` from bucket `b`, the code does:

```python
        b = buckets[bi]
        v = b.pop(0)
        ordered.append(v)
        # refine all buckets by adjacency to v
        new_buckets = []
        for other in buckets:
            if not other:
                continue
            nb = [x for x in other if adj[v][x]]
            nnb = [x for x in other if not adj[v][x]]
            ...
```

The loop `for other in buckets` iterates over ALL buckets, including `b` itself (the bucket `v` was just popped from). In the trace above, after picking v=0 from bucket [0], that bucket is empty and skipped, so the bug is latent; but the algorithm's invariant is that only the buckets AFTER the selected one (i.e. `buckets[bi+1:]`) should be refined by adjacency to `v`. Refining buckets before/at the selected position is incorrect LexBFS: it lets a vertex that was already "behind" v in the queue be re-sorted by adjacency to v, which is not part of the algorithm.

Concretely, the correct HMPV refinement is: split every bucket in `buckets[bi+1:]` (the buckets that come after the one v was taken from) into its neighbors-of-v and non-neighbors-of-v parts, keeping the relative order of the other buckets. The current code instead splits every non-empty bucket in the whole list, which for this graph produces the invalid order [0,1,2] instead of [0,2,1].

Wait — let me re-trace more carefully. After v=0 is popped, buckets = [[], [1], [2]]. The loop skips the empty bucket, then refines [1] (0-1 non-edge → nnb=[1]) and [2] (0-2 edge → nb=[2]). Result: [[1],[2]]. This is actually the CORRECT refinement (only buckets after the selected one are non-empty here). Then v=1 is picked from [1], and [2] is refined by adjacency to 1: 1-2 is an edge → nb=[2]. Result: [[2]]. Then v=2. Order: [0,1,2].

So the refinement loop itself is not the bug in this trace. The real issue: after picking v=0, the bucket [1] (non-neighbor of 0) should come BEFORE [2] (neighbor of 0) in the queue? No — in LexBFS, neighbors of v come BEFORE non-neighbors. So [2] (neighbor) should come before [1] (non-neighbor). The code puts `nb` before `nnb` within each bucket, but the bucket [1] is at index 1 and [2] is at index 2 in the original list. After refinement, new_buckets = [[1], [2]] — [1] (non-neighbor) is still before [2] (neighbor). This is WRONG: the neighbor bucket should be moved to the front.

The correct HMPV algorithm: when refining by v, for each bucket after the selected one, split into nb and nnb, and the nb part should be placed BEFORE the nnb part in the global queue. But more importantly, the nb parts of ALL buckets should be collected and placed before the nnb parts. The current code preserves the original bucket order and just splits each bucket in place, which does NOT move neighbor-vertices ahead of non-neighbor-vertices across different original buckets.

In this trace: original buckets after v=0 are [1] (non-neighbor) and [2] (neighbor). Correct behavior: [2] should come before [1], giving queue [2, 1], so next pick is 2, then 1 → order [0,2,1]. The code gives [1, 2] → order [0,1,2].

The responsible lines:
```python
        new_buckets = []
        for other in buckets:
            if not other:
                continue
            nb = [x for x in other if adj[v][x]]
            nnb = [x for x in other if not adj[v][x]]
            if nb:
                new_buckets.append(nb)
            if nnb:
                new_buckets.append(nnb)
        buckets = new_buckets
```
This splits each bucket in place but does NOT reorder the nb parts to come before the nnb parts of other buckets. The fix is to collect all nb parts first (in bucket order), then all nnb parts (in bucket order), so that neighbors of v are globally ahead of non-neighbors.

## REPAIR_HINTS
In `_lexbfs`, replace the refinement loop so that neighbor parts are placed before non-neighbor parts globally:

```python
        new_buckets = []
        nb_parts = []
        nnb_parts = []
        for other in buckets:
            if not other:
                continue
            nb = [x for x in other if adj[v][x]]
            nnb = [x for x in other if not adj[v][x]]
            if nb:
                nb_parts.append(nb)
            if nnb:
                nnb_parts.append(nnb)
        buckets = nb_parts + nnb_parts
```

This ensures that after selecting v, all vertices adjacent to v (across all remaining buckets) are queued before all vertices not adjacent to v, which is the correct LexBFS refinement.

Approaches that will NOT work:
- Simply swapping nb/nnb within each bucket (already done) without reordering across buckets — this is the current bug.
- Refining only `buckets[bi+1:]` without the global nb-before-nnb reordering — still incorrect for the same reason.
- The dynamic update logic (`_try_reorder`, `insert_edge`, `delete_edge`) is not the cause of this failure; fixing `_lexbfs` is necessary first. The fallback to `_lexbfs` in the update functions will also be wrong until `_lexbfs` is fixed.
