## ROOT_CAUSE
The `_local_repair` function (lines 68-107) **always returns `None`** — it
contains only comments and a final `return None`. The intended local repair
logic was never implemented.

In `insert_edge` (lines 117-130) and `delete_edge` (lines 133-146), the code
does:
```python
new_order = _local_repair(A, state['ordering'], edge)
if new_order is None or not _is_valid_lexbfs(A, new_order):
    new_order = _lexbfs_full(A)
```

Since `_local_repair` always returns `None`, the fallback `_lexbfs_full(A)`
is always invoked. The bug is therefore in `_lexbfs_full`: it produces an
incorrect ordering for this graph.

Tracing `_lexbfs_full` on the graph with n=3, edges {(0,2)} (A[0][2]=A[2][0]=1,
all other off-diagonal entries 0):

- Initial: groups = [[0, 1, 2]]
- Step 1: u = 0, groups[0] = [1, 2], order = [0].
  Split groups[1:] (none, since groups[0] was the only group and is now [1,2]).
  Wait: groups = [[0,1,2]]. After picking u=0, groups[0] = [1,2].
  new_groups = [groups[0]] = [[1,2]]. No other groups to split.
  groups = [[1,2]].
- Step 2: u = 1, groups[0] = [2], order = [0, 1].
  new_groups = [[2]]. groups = [[2]].
- Step 3: u = 2, groups[0] = [], order = [0, 1, 2].

Result: [0, 1, 2]. But this is NOT a valid LexBFS ordering for the graph
with only edge (0,2).

The correct LexBFS: start at 0. Neighbors of 0: {2}. Non-neighbors: {1}.
So after outputting 0, the buckets are: [2] (adjacent to 0), [1] (not
adjacent to 0). Next pick from first bucket: 2. Then 1. Order: [0, 2, 1].

The bug in `_lexbfs_full`: when picking u=0 from group [0,1,2], the code
splits **other groups** by adjacency to u, but it does NOT split the
**remaining vertices in the same group** (groups[0] after removing u). In
standard LexBFS partition refinement, after outputting u, ALL remaining
vertices (including those in the same bucket as u) must be split by
adjacency to u. The code only splits `groups[1:]`, leaving `groups[0]`
(the rest of the original bucket) unsplit.

Specifically, lines 44-53:
```python
u = groups[0][0]
groups[0] = groups[0][1:]
order.append(u)

new_groups = [groups[0]]       # <-- groups[0] is NOT split by adjacency to u
for g in groups[1:]:
    g1 = [v for v in g if A[u][v]]
    g2 = [v for v in g if not A[u][v]]
    ...
```

`groups[0]` (the remaining vertices [1,2] after removing 0) is placed
directly into `new_groups` without being split by adjacency to u=0. It
should be split into [2] (adjacent to 0) and [1] (not adjacent to 0),
giving new_groups = [[2], [1]], which would then produce order [0, 2, 1].

## REPAIR_HINTS
1. **Fix `_lexbfs_full`**: After removing u from groups[0], also split
   groups[0] by adjacency to u, just like the other groups. Change:
   ```python
   new_groups = [groups[0]]
   for g in groups[1:]:
   ```
   to:
   ```python
   new_groups = []
   for g in groups:  # includes groups[0] (the remainder after removing u)
       g1 = [v for v in g if A[u][v]]
       g2 = [v for v in g if not A[u][v]]
       if g1:
           new_groups.append(g1)
       if g2:
           new_groups.append(g2)
   ```
   This ensures all remaining vertices are refined by adjacency to the
   just-output vertex, which is the correct LexBFS partition refinement.

2. **The `_local_repair` function** is a no-op (always returns None). This
   is not the cause of the correctness failure (the fallback recompute is
   used), but it means the "local repair" strategy is entirely absent. For
   correctness, fixing `_lexbfs_full` is sufficient. For the research goal
   of avoiding full recomputation, `_local_repair` would need actual
   implementation, but that is a separate concern from the current bug.

3. **Do NOT** try to "fix" this by adding a post-hoc validity check and
   retry with different start vertices — the root cause is the missing
   split of the current bucket, and any correct LexBFS implementation must
   refine all remaining vertices (not just those in later buckets) by
   adjacency to the output vertex.
