## FAILURE_DESCRIPTION
Operation: `init` on a 4-vertex undirected graph (sequence_idx 0, so no prior updates).
The candidate returned ordering `[0, 1, 2, 3]`; the expected (valid) ordering is `[0, 1, 3, 2]`.
The verifier reports an (LB) 4-point violation at positions a=0, b=2, c=3 (minD=1):
- a=0 -> vertex 0, b=2 -> vertex 2, c=3 -> vertex 3
- 0-2 is NOT an edge, 0-3 IS an edge, and the only candidate witness d < a is d=1 (vertex 1), which fails the witness condition (it is not adjacent to 2, i.e. 1-2 is not an edge).
So `[0,1,2,3]` is not a valid LexBFS ordering of the graph, yet `init` returned it without any fallback.

## ROOT_CAUSE
The bug is in `_lexbfs_full_simple` (the static partition-refinement LexBFS), specifically the bucket re-sorting line:

```python
new_buckets.sort(key=lambda b: label[b[0]], reverse=True)
```

Two defects, both in this line:

1. **Wrong sort key (the primary bug).** The key is the *current* label bitset of the first vertex of each bucket, i.e. the set of *already-processed* neighbours. But after processing vertex v, the correct LexBFS ordering of buckets is by the *refined* label: (bucket ∩ N(v)) first, then (bucket \ N(v)), with the old label as tie-break. The code splits each bucket into `inb`/`outb` but then throws the split information away and re-sorts by the old label only. The old label is identical for `inb` and `outb` (they came from the same bucket), so the sort is a no-op between the two halves — the split is never reflected in the bucket order. The correct key for a bucket is `label[b[0]] | (1 << v)` if the bucket is `inb`, else `label[b[0]]`.

2. **Python's `sort` is stable, so `reverse=True` is harmless here** (equal keys keep original relative order), but it is a red herring; the real problem is that the keys are equal where they should differ.

Trace on the failing graph (edges: 0-1, 0-3, 1-3, 2-3 — the only 4-vertex graph consistent with the violation: 0-2 non-edge, 0-3 edge, 1-2 non-edge, and `[0,1,3,2]` valid):
- Start: buckets [[0],[1],[2],[3]], all labels 0.
- Pick 0. Split: [1] in N(0), [2] out, [3] in. Correct order: [1],[3],[2]. Code sorts by old label (all 0) -> stable -> [1],[2],[3]. **Divergence here**: 2 (label {0}) is placed before 3 (label {0,1}).
- Pick 1. Correct next would be 3 (label {0,1}); code picks 2 (label {0}).
- Result: [0,1,2,3] — invalid, exactly the reported result.

The fallback `_verify_order` (which would have caught this and recomputed) is **never called in `init`** — `init` returns `_lexbfs_full_simple(adj)` directly. So the broken ordering is returned as-is.

## REPAIR_HINTS
Smallest fix: in `_lexbfs_full_simple`, sort buckets by the *refined* label, not the old one. Concretely, when building `new_buckets`, tag each half with its refined key and sort by that:

```python
new_buckets = []
for bucket in buckets:
    if not bucket:
        continue
    inb = [x for x in bucket if (adjb[v] >> x) & 1]
    outb = [x for x in bucket if not ((adjb[v] >> x) & 1)]
    if inb and outb:
        new_buckets.append((label[inb[0]] | (1 << v), inb))
        new_buckets.append((label[outb[0]], outb))
    else:
        b = inb or outb
        key = label[b[0]] | (1 << v) if inb else label[b[0]]
        new_buckets.append((key, b))
new_buckets.sort(key=lambda t: t[0], reverse=True)
buckets = [b for _, b in new_buckets]
```

(Within a bucket, any order is fine since all members share the same refined label.)

Additionally, as a safety net, make `init` run the same verification as the update paths:
```python
def init(graph):
    adj = _adj_sets(graph)
    order = _lexbfs_full_simple(adj)
    order = _verify_order(order, adj)
    return {'ordering': order, 'adj': adj}
```
This would have masked the bug even without the sort fix, but the sort fix is the real repair — `_verify_order` + full recompute is the same broken function, so it cannot fix itself.

Approaches that will NOT work:
- Relying on `_verify_order` alone: it calls `_lexbfs_full_simple` to recompute, which has the same bug, so it would "recompute" to the same invalid order and (since `_is_valid_lexbfs` would still fail) loop or return the invalid order.
- Changing only the tie-break or start vertex: the bug is in the bucket ordering after each refinement, not in tie-breaking.
- Keeping the split but sorting by `len(bucket)` or by vertex id: neither encodes the refined label.
