## FAILURE_DESCRIPTION
Operation: `init` on a 4-vertex undirected graph (sequence_idx 0, so no prior updates).
Candidate returned ordering `[0, 1, 2, 3]`; the expected (valid) ordering is `[0, 1, 3, 2]`.
The verifier reports a (LB) 4-point violation at positions a=0, b=2, c=3 (minD=1):
- va=0, vb=2, vc=3
- ab NOT in E (0-2 non-edge), ac in E (0-3 edge)
- no d < a exists (a=0, so the witness set is empty) → property fails.

The graph is consistent with: edges {0-1, 0-3, 1-2, 1-3} (0-2 and 2-3 non-edges).
In that graph, `[0,1,2,3]` is NOT a valid LexBFS ordering, yet the candidate returned it
from `init` without ever triggering a recompute.

## ROOT_CAUSE
The failure is in the static LexBFS itself, `_lexbfs_full_simple`, specifically the
bucket re-sorting line:

```python
new_buckets.sort(key=lambda t: t[0], reverse=True)
```

The buckets are sorted by the **integer value** of the label bitset, but LexBFS
requires ordering by the **lexicographic** order of the label strings, where the
string is read with the **earliest-processed vertex as the most significant
symbol** (1 before 0). The code stores the earliest-processed vertex in the
**lowest** bit (`label[x] |= 1 << v`), so integer comparison is the exact
**opposite** of the required lexicographic order.

Trace on the failing graph (edges 0-1, 0-3, 1-2, 1-3):
1. Pick 0. Labels: 1→{0}, 3→{0}, 2→∅. Buckets: [{1},{3},{2}].
2. Pick 1. Refine: 3→{0,1}, 2→{1}. Correct LexBFS order of buckets:
   {3} (label 11) before {2} (label 01), because at the first differing
   position (vertex 0) 1 > 0.
   Integer keys: 3→3 (0b11), 2→2 (0b10). `reverse=True` puts 2 (key 2)
   **before** 3 (key 3) — wrong.
3. So the algorithm picks 2 next, then 3 → order `[0, 1, 2, 3]`.

The correct order is `[0, 1, 3, 2]`.

Why the bug was not caught: `_verify_order` calls `_is_valid_lexbfs`, which
**correctly** implements the (LB) 4-point property and would have rejected
`[0,1,2,3]` (it fails at a=0,b=2,c=3 as above). But `_verify_order` only
recomputes with the **same buggy** `_lexbfs_full_simple`, so the recompute
produces the same invalid order and the check passes vacuously (the
recomputed order is re-verified and… wait, it should fail again).

Actually re-examining: `_verify_order` does `if not _is_valid_lexbfs(order, adj): return _lexbfs_full_simple(adj)`. If `_is_valid_lexbfs` correctly returns False for `[0,1,2,3]`, then `_verify_order` returns `_lexbfs_full_simple(adj)` — which produces the **same** `[0,1,2,3]` (same bug). The returned order is NOT re-verified. So the final answer is the buggy order. The verifier (external) then catches it.

So there are two compounding issues:
1. `_lexbfs_full_simple` sorts buckets by integer bitset value instead of
   lexicographic label order (earliest-processed = most significant).
2. `_verify_order` does not re-check the recomputed order, so a buggy
   recompute is returned as-is.

## REPAIR_HINTS
1. **Fix the bucket sort in `_lexbfs_full_simple`.** The label bitset has the
   earliest-processed vertex in the lowest bit. To sort lexicographically
   (earliest = most significant, 1 before 0), you must compare bitsets with
   the **lowest bit as most significant**. Options:
   - Reverse the bit order before comparing: build a key where bit i of the
     original becomes bit (n-1-i) of the key, then sort by integer value
     descending. E.g. `key = int(bin(label)[2:].zfill(n)[::-1], 2)`.
   - Or, equivalently, store the earliest-processed vertex in the **highest**
     bit (use `1 << (n-1-v)` or a shifting scheme) so that integer comparison
     naturally matches lexicographic order.
   - Or, use a proper lexicographic comparison function over the label
     bitsets (compare bit by bit from lowest to highest, 1 > 0).

2. **Make `_verify_order` actually verify the recomputed order.** After
   calling `_lexbfs_full_simple`, re-run `_is_valid_lexbfs` on the result.
   If it still fails (shouldn't happen with a correct LexBFS, but as a
   safety net), raise an error or try a different tie-break.

3. **Do NOT** try to "fix" the sort by just changing `reverse=True` to
   `reverse=False` — that would give the opposite (wrong) order in general.
   The issue is the bit-significance convention, not the sort direction.

4. The local repair path (`_try_local_repair`) is fine in principle (it
   exhaustively tries all single-vertex moves and checks with the correct
   `_is_valid_lexbfs`), but it is irrelevant to this failure since the bug
   is in `init` / the full recompute.
