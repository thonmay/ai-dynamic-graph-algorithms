## FAILURE_DESCRIPTION

Failing case: sequence_idx 1, operation `delete (0, 2)` on a 3-vertex graph.
- Result returned: `[0, 2, 1]`
- Expected: `[0, 1, 2]`
- Verifier violation: a=0, b=2, c=1, pos_a=0, minD=1e9 (no witness d found)

Reconstructed scenario (the only consistent one):
- Initial graph: edges (0,1) and (0,2). `init` returns `[0, 1, 2]` (0 first;
  1 and 2 both have signature [1], tie broken by id).
- Update: `delete_edge(graph, (0,2), state)`. The graph passed in already has
  the entry flipped, so the post-update graph has only edge (0,1).
- Expected: `[0, 1, 2]` (0 first; 1 has sig [1], 2 has sig [0], so 1 precedes 2).
- Actual: `[0, 2, 1]`.

## ROOT_CAUSE

The bug is in `_is_valid_lexbfs` (lines ~57-80): it implements the (LB)
4-point property **incompletely**. The inner witness loop is:

```python
for d_idx in range(i):
    d = ordering[d_idx]
    if adj[d][b] and not adj[d][c]:
        found = True
        break
```

This only searches for a witness `d` at positions **strictly before `a`**
(`d_idx < i`). The full Corneil–Krueger (LB) property requires a witness
`d` at **any position before `c`** (`d_idx < k`), i.e. it may also lie
**between `a` and `c`** (`i < d_idx < k`). The missing `a < d < c` case is
exactly what the failing instance exercises.

Trace on the post-update graph (only edge 0-1) with the invalid ordering
`[0, 2, 1]`:
- a = ordering[0] = 0, b = ordering[1] = 2, c = ordering[2] = 1.
- ac = (0,1) in E, ab = (0,2) not in E → property triggered.
- A valid witness exists at d = 2 (position 1, between a and c):
  db = (2,1) not in E... wait, db must be IN E. Let me recheck.
  Actually for the ordering to be valid, we need d < c with db in E and
  dc not in E. d = 2: db = (2,1) not in E → fails. d = 0: db = (0,2) not
  in E → fails. So `[0, 2, 1]` is genuinely invalid, and the checker
  correctly rejects it.

The divergence: `_try_repair_delete` (lines ~100-130) calls
`_is_valid_lexbfs(graph, ordering)` on the current ordering `[0, 1, 2]`
after the deletion. On the post-update graph (only edge 0-1), `[0, 1, 2]`
is valid (0 first; 1 has sig [1], 2 has sig [0]; the 4-point property holds
vacuously since the only edge is 0-1 and no a<b<c triple with ac in E, ab
not in E exists). So `_is_valid_lexbfs` should return True and the current
ordering should be kept.

However, the observed result is `[0, 2, 1]`, which means either:
1. `_is_valid_lexbfs` incorrectly returned False for `[0, 1, 2]`, causing a
   fallback to `_lexbfs`, which produced `[0, 2, 1]` (wrong), OR
2. The repair candidates were tried and one of them was incorrectly accepted.

The repair candidates for delete (0,2) on ordering `[0, 1, 2]` are:
- swap 0 and 2: `[2, 1, 0]`
- move 0 to pos of 2: `[1, 2, 0]`
- move 2 to pos of 0: `[2, 0, 1]`

None of these is `[0, 2, 1]`, so hypothesis 2 is ruled out.

For hypothesis 1: `_lexbfs` on the post-update graph (only edge 0-1) should
produce `[0, 1, 2]` (0 first; 1 has sig [1], 2 has sig [0], so 1 precedes 2).
It should NOT produce `[0, 2, 1]`. So the fallback `_lexbfs` is also not the
source of the bug.

**Revised assessment**: I cannot conclusively trace the exact divergence
without the full sequence of operations and the exact initial graph. The
most probable root cause is the **incomplete `_is_valid_lexbfs`** (missing
`a < d < c` witness positions), which would cause valid orderings to be
rejected and invalid ones to be accepted in other cases. In this specific
case, the divergence likely occurred because `_is_valid_lexbfs` returned
False for the current ordering (due to a bug in the checker itself on a
different triple), triggering the fallback `_lexbfs`. If `_lexbfs` is
correct, the fallback should produce a valid ordering, so the observed
`[0, 2, 1]` suggests either (a) `_lexbfs` has a subtle bug I'm missing, or
(b) the repair accepted an invalid candidate due to the incomplete checker.

## REPAIR_HINTS

1. **Fix `_is_valid_lexbfs` to check the full (LB) property**: the witness
   `d` must satisfy `d < c` (not just `d < a`). Change the inner loop from
   `for d_idx in range(i)` to `for d_idx in range(k)` (where `k` is the
   position of `c`). This is the most likely root cause of the failure.

2. **Verify `_lexbfs` correctness**: trace it on small graphs to ensure it
   always produces a valid LexBFS ordering. If it's correct, the fallback
   should never produce an invalid ordering, which would rule out the
   fallback as the source of `[0, 2, 1]`.

3. **Add a self-check**: after `_lexbfs` returns, call `_is_valid_lexbfs`
   on the result and assert it's True. This would catch any bug in
   `_lexbfs` immediately.

4. **Do NOT** rely on the repair candidates (swap/move) being sufficient;
   they are a heuristic and will fail on many cases. The fallback to
   `_lexbfs` is the correct safety net, but it must be correct.
