## FAILURE_DESCRIPTION
Graph: n=3, initially empty (no edges). Operation: insert edge (0,1), producing a graph with a single edge 0–1 and isolated vertex 2. Expected valid LexBFS ordering: [0,1,2]. Actual returned ordering: [0,2,1]. The (LB) 4-point property is violated at positions a=0, b=1, c=2 (vertices 0, 2, 1): ac = edge(0,1) ∈ E, ab = edge(0,2) ∉ E, but no d < 0 exists to witness the property.

## ROOT_CAUSE
The lexicographic label comparison in both `_lexbfs_full` and `_lexbfs_suffix` is **inverted**. The code uses:

```python
if best is None or labels[v] < best_label or (labels[v] == best_label and v < best):
```

This picks the lexicographically **smallest** label. However, in LexBFS the label of a vertex is the bit-vector of its adjacencies to already-ordered vertices (1 = adjacent). The correct greedy rule is to pick the vertex with the lexicographically **largest** label (i.e., the one most adjacent to earlier vertices), because a vertex that is adjacent to more prefix vertices should be ordered sooner.

Tracing `_lexbfs_full` on the post-insertion graph (edge 0–1 only):
1. All labels (0,0,0). Pick vertex 0 (tie-break). Update: label[1]=(1,0,0), label[2]=(0,0,0).
2. Compare: label[1]=(1,0,0) vs label[2]=(0,0,0). With `<`, (0,0,0) < (1,0,0), so vertex 2 is picked. **Wrong** — vertex 1 (adjacent to 0) should be picked.
3. Result: [0,2,1], which violates the 4-point property.

The `_verify_lexbfs` function correctly rejects [0,2,1], so `_try_local_repair` returns None. But the fallback `_lexbfs_full` has the same inverted comparison and also produces [0,2,1], so the invalid ordering is returned.

The same bug exists in `_lexbfs_suffix` (line: `if best is None or labels[v] < best_label or ...`), so the local repair path is also broken.

## REPAIR_HINTS
**Fix:** In both `_lexbfs_full` and `_lexbfs_suffix`, change the label comparison from `<` to `>` so that the lexicographically **largest** label is selected:

```python
# In _lexbfs_full (and identically in _lexbfs_suffix):
if best is None or labels[v] > best_label or (labels[v] == best_label and v < best):
```

This is the minimal change. The tie-break `v < best` on equal labels can stay (any tie-break is valid for LexBFS).

**Verification after fix:** On the failing case, step 2 becomes: label[1]=(1,0,0) > label[2]=(0,0,0), so vertex 1 is picked → ordering [0,1,2], which satisfies the 4-point property.

**What will NOT work:** Simply fixing `_lexbfs_full` without also fixing `_lexbfs_suffix` will leave the local-repair path broken (it will still produce invalid orderings that `_verify_lexbfs` rejects, forcing a full recompute every time — correct but slow, and the local repair will never succeed). Both functions must use the same (corrected) comparison.

**Note on the local-repair logic:** The prefix-fixing strategy in `_try_local_repair` (fix prefix up to `min(pos[u],pos[v])-1`, re-run on suffix) is sound *if* the suffix LexBFS is correct. Once the comparison is fixed, the local repair should work correctly and the `_verify_lexbfs` guard provides a safety net.
