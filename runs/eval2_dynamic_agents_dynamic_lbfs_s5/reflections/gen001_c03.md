## FAILURE_DESCRIPTION
Failing case: n=3, operation `insert (0, 2)` at sequence_idx 0. The candidate returned ordering `[0, 1, 2]` but the expected (valid) ordering is `[0, 2, 1]`. The verifier reports a 4-point (LB) violation with a=0, b=1, c=2, pos_a=0, minD=1000000000 (sentinel = no witness d found).

Reconstructing the graph: the violation is reported on the *post-update* graph. For the violation to hold with a=0 at position 0, we need:
- ab not in E: 0-1 is NOT an edge
- ac in E: 0-2 IS an edge (this is the inserted edge)
- no d < a: vacuously true since a is at position 0 (no earlier vertex)

So the post-update graph has edges {0-2, 1-2} (edge 1-2 must exist for 2 to be adjacent to 1, making the ordering [0,1,2] invalid). The pre-update graph had only edge {1-2}.

## ROOT_CAUSE
The `insert_edge` function (lines ~113-125) unconditionally keeps the old ordering, based on the **incorrect assumption** that "adding an edge cannot invalidate a LexBFS ordering." The comment states:

> "Adding an edge cannot invalidate a LexBFS ordering (the 4-point property is monotone under edge addition: any witness d that worked before still works, and new edges only add more potential witnesses)."

This is **false**. Adding an edge can create a *new* 4-point violation: the new edge (a,c) can trigger the antecedent "ac in E and ab not in E" for a triple (a,b,c) that was previously vacuously satisfied (because ac was not in E). If a is at position 0 (or more generally, if no earlier d witnesses the pair (b,c)), the property is violated.

In this specific case:
- Pre-update graph: only edge 1-2. Ordering [0,1,2] is valid (no 4-point violation since 0 has no edges).
- Post-update graph: edges {0-2, 1-2}. The new edge 0-2 creates the triple (a=0, b=1, c=2) where ac=0-2 ∈ E, ab=0-1 ∉ E, and no d < a exists. Violation.

The code at line ~120-125 simply returns the old ordering:
```python
return {
    'ordering': order,
    'n': state['n'],
}
```
without any verification or recomputation.

## REPAIR_HINTS
The fix is to **verify the 4-point property after edge insertion** (just as `delete_edge` already does) and recompute if it fails. The smallest concrete change:

In `insert_edge`, after the comment block, add the same verification logic used in `delete_edge`:
```python
def insert_edge(graph, edge, state):
    order = state['ordering']
    if _is_valid_lexbfs(graph, order):
        return {'ordering': order, 'n': state['n']}
    new_order = _lexbfs(graph)
    return {'ordering': new_order, 'n': state['n']}
```

This is O(n^2) per insertion (same as the existing delete path), which is acceptable for correctness. The `_is_valid_lexbfs` function already exists and is correct.

**Approaches that will NOT work:**
- Keeping the "monotonicity" assumption and only checking canonicality: the old ordering may be non-canonical AND invalid.
- Only checking if the inserted edge is "relevant" (e.g., only if it connects two vertices in a certain position relationship): the violation can arise from any new edge that creates a new (a,c) pair with an existing non-edge (a,b) and no witness d. A full 4-point check is the simplest correct approach.
- Using `_canonical_check` (which recomputes and compares): this would work but is O(n+m) and always recomputes, whereas `_is_valid_lexbfs` can short-circuit on the first violation.
