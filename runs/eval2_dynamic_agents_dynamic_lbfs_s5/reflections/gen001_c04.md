## FAILURE_DESCRIPTION

After `insert (2, 0)` on a 4-vertex graph, the candidate returned ordering `[0, 2, 1, 3]`.
The verifier's (LB) 4-point certificate rejects it: with a=2 (pos 1), b=1 (pos 2), c=3 (pos 3),
the edge ac=(2,3) is present, ab=(2,1) is absent, and no d < a (i.e. d=0) satisfies
db in E and dc not in E (violation reports `minD: 1000000000`, the "no witness" sentinel).
Expected (a valid) ordering was `[0, 2, 3, 1]`.

Reconstructing the post-update graph from the certificate: E = {(0,2), (2,3), (0,3)} — a
path 1–2–3–0 (edge (2,0) was just inserted; (2,1) is absent).

## ROOT_CAUSE

The bug is in `_lexbfs`: it is **not** the Habib–McConnell–Paul–Viennot partition-refinement
algorithm, despite the docstring. The code processes a bucket by taking its first vertex v,
splitting only the *remaining vertices of that same bucket* into B1/B2, and enqueuing B1, B2
at the **back** of the queue. This is a plain BFS with a FIFO queue, not LexBFS.

Concretely, on the failing graph (adj: 0–2, 2–3, 0–3):
- bucket [0,1,2,3], v=0, rest=[1,2,3] → B1=[2,3] (neighbors), B2=[1] (non-neighbor).
  Queue: [2,3], [1].
- bucket [2,3], v=2, rest=[3] → B1=[3]. Queue: [1], [3].
- bucket [1], v=1. Then bucket [3], v=3.
- Output: [0, 2, 1, 3].

The vertex 1 (a non-neighbor of 0) is output *before* 3 (a neighbor of 0), because the
B2 bucket was enqueued behind B1 and the queue is FIFO. In a correct LexBFS, the
refinement of a bucket must be processed **immediately** (the refined sub-buckets replace
the current bucket at the front of the queue, in B1-then-B2 order), so that 3 would be
output before 1, giving [0, 2, 3, 1].

The `labels` list is computed but never used for any ordering decision — it is dead code.
The comment "Two vertices are in the same bucket iff their labels are equal" is false in
this implementation: buckets are formed by successive splits, but the queue discipline
(FIFO, append-at-back) destroys the lexicographic property.

## REPAIR_HINTS

Replace the queue discipline in `_lexbfs` with the correct HMPV scheme:

1. Maintain a **list of buckets** (not a FIFO queue) and a pointer `i` to the current
   bucket. When processing bucket B at index i:
   - Output v = B[0].
   - Split B[1:] into B1 (neighbors of v) and B2 (non-neighbors of v).
   - **Replace** B in the bucket list with [B1, B2] (non-empty ones, B1 first), and
     advance `i` to point at B1 (or the next non-empty bucket). This makes the
     refinement of the current bucket the *next* thing processed — the key property
     that yields lexicographic order.
2. Drop the dead `labels` list entirely; it serves no purpose in the bucket-based
   formulation.
3. Do NOT try to "fix" the FIFO queue by reordering enqueues (e.g. B2 before B1, or
   inserting at the front) — the correct structure is a list with an index pointer,
   where the current bucket is *expanded in place*. Any FIFO-queue variant will fail
   on some graph because LexBFS requires depth-first refinement of the current bucket,
   not breadth-first queueing.
4. After fixing `_lexbfs`, the `init`/`insert_edge`/`delete_edge` wrappers are fine as-is
   (they recompute from scratch, which is correct but not the research goal).
