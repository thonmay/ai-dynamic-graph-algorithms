## FAILURE_DESCRIPTION
Operation: `insert (3, 2)` at sequence index 0 (the first update after `init`).
- Result returned by the candidate: `[3, 1, 0, 2]`
- Expected (a valid LexBFS of the post-insert graph): `[0, 1, 3, 2]`
- Reported (LB) violation: a=3 (pos 0), b=0 (pos 2), c=2 (pos 3), minD=1.

Reconstructed post-insert graph (4x4, undirected):
```
      0 1 2 3
0  [ 0 1 0 1 ]
1  [ 1 0 1 0 ]
2  [ 0 1 0 1 ]
3  [ 1 0 1 0 ]
```
i.e. edges {0-1, 0-3, 1-2, 2-3} — a 4-cycle 0-1-2-3-0. The inserted edge is (3,2), so the pre-insert graph was the path 0-1-2 plus edge 0-3 (a "V" 0-1-2 and 0-3).

The returned ordering `[3, 1, 0, 2]` is NOT a valid LexBFS of the 4-cycle:
- a=3 (pos 0), b=0 (pos 2): 3-0 is NOT an edge.
- c=2 (pos 3): 3-2 IS an edge (the just-inserted edge).
- The (LB) property demands some d before c with d-0 in E and d-2 not in E. The only candidates are d=3 (pos 0) and d=1 (pos 1): d=3 fails (3-0 not in E), d=1 fails (1-2 IS in E). No witness exists → violation.

## ROOT_CAUSE
The failure is in the local-repair path, specifically the first line of `_try_repair_insert`:

```python
def _try_repair_insert(graph, ordering, u, v):
    n = len(ordering)
    # First check if the current ordering is still valid
    if _is_valid_lexbfs(graph, ordering):
        return ordering
```

This early return is unsound. It assumes that an ordering which was a valid LexBFS before the update remains a valid LexBFS after an edge insertion. That is false: inserting an edge can create new (a, b, c) triples with ac in E and ab not in E that have no witness d, and the current ordering `[3, 1, 0, 2]` is exactly such a case (the new edge 3-2 creates the triple a=3, b=0, c=2).

The deeper reason the early return is so wrong here is that the pre-insert ordering `[3, 1, 0, 2]` is not a LexBFS of the pre-insert graph at all. Tracing `_lexbfs` on the pre-insert graph (edges 0-1, 1-2, 0-3):
- Step 1: all signatures empty, tie broken by smallest id → 0.
- Step 2: sigs 1=[1], 2=[0], 3=[1] → max is [1], tie between 1 and 3 broken by smallest id → 1.
- Step 3: sigs 2=[0,1], 3=[1,0] → max is [1,0] → 3.
- Step 4: 2.

So `_lexbfs` returns `[0, 1, 3, 2]`, not `[3, 1, 0, 2]`. The state entering `insert_edge` therefore already diverged from what `init`/`_lexbfs` would produce, which means the harness's `state` (or the candidate's own earlier bookkeeping) is not the canonical `_lexbfs` output. Regardless of how the state got there, the candidate's contract is to return a valid LexBFS of the current graph, and `_try_repair_insert` returned an invalid ordering because it trusted the (invalid) incoming ordering.

The same unsound early return exists in `_try_repair_delete` (deleting an edge can also break the (LB) property by removing a witness d for some triple).

Note the fallback `ordering = _lexbfs(graph)` in `insert_edge`/`delete_edge` is correct and would have produced `[0, 1, 3, 2]`; the bug is that the fallback is never reached because the early return fires first.

## REPAIR_HINTS
1. Remove the early `if _is_valid_lexbfs(graph, ordering): return ordering` from BOTH `_try_repair_insert` and `_try_repair_delete`. The current ordering must never be trusted after an update; it must be re-validated against the post-update graph, and even then "valid" is not guaranteed by the pre-update validity.

2. If a local repair is still desired for efficiency, the candidate list must be validated with `_is_valid_lexbfs` (which it already does), but the "keep current ordering" shortcut must be dropped. The swap/move candidates are fine to keep as long as each is checked.

3. The fallback `_lexbfs(graph)` is correct and should remain as the guaranteed-correct path. After removing the early return, the worst case is a full recompute, which is acceptable for correctness (the research goal is correctness first).

4. Do NOT try to "fix" the (LB) checker `_is_valid_lexbfs` — it is correct as written (the d range `range(k)` correctly covers all positions before c, and the a/b/c loops correctly enumerate the 4-point condition). The bug is purely in the repair logic's trust of the incoming ordering.

5. Approaches that will NOT work:
   - Keeping the early return but adding a "check that the inserted/deleted edge doesn't create a new violation" heuristic — this is essentially re-implementing the full (LB) check and is error-prone; just drop the shortcut.
   - Assuming the incoming state is always a valid LexBFS of the pre-update graph — the failing case shows it is not (the state `[3, 1, 0, 2]` is not a LexBFS of the pre-insert graph either).
   - Modifying `_lexbfs` — it is correct; the bug is entirely in the repair path.
