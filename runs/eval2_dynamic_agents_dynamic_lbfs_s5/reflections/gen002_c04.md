## FAILURE_DESCRIPTION
After `insert (2, 0)` on a 4-vertex graph, the candidate returned ordering `[0, 2, 1, 3]`, but the expected (valid) ordering is `[0, 2, 3, 1]`. The verifier reports a violation of the (LB) 4-point property with a=2, b=1, c=3 (pos_a=1, minD=1e9 meaning no witness d was found).

## ROOT_CAUSE
The static `_lexbfs` is not a correct LexBFS. It performs a **depth-first** refinement: after splitting the current bucket B into B1 (neighbors of v) and B2 (non-neighbors of v), it replaces B in place with `[B1, B2]` and immediately descends into B1, postponing B2 until B1 is fully exhausted. This is the wrong traversal order for LexBFS.

LexBFS requires **breadth-first** refinement: when a vertex v is output, the split of its *current* bucket must be processed before any other pending bucket, but the non-neighbor part B2 must be processed **before** the neighbor part B1 (B2 stays "closer to the front" of the queue). The correct HMPV invariant is:

- Maintain a queue of buckets.
- Pop the front bucket B, output its first vertex v.
- Split the rest of B into B1 (N(v)) and B2 (non-N(v)).
- Reinsert **B2 first, then B1** at the **front** of the queue (i.e., they are processed before any other pending bucket, and B2 before B1).

The candidate's code:
```python
new_buckets = []
if B1:
    new_buckets.append(B1)
if B2:
    new_buckets.append(B2)
buckets[i:i + 1] = new_buckets
```
does two things wrong: (1) it puts B1 before B2, and (2) it keeps them at the same position (depth-first descent into B1) rather than reinserting them at the front of the queue ahead of all other pending buckets.

Tracing the failing case: with the post-insert graph, the algorithm outputs 0, then 2, then descends into 2's neighbor bucket and outputs 1 before 3, yielding `[0, 2, 1, 3]`. The correct LexBFS (B2-before-B1, front-of-queue) yields `[0, 2, 3, 1]`. The returned ordering violates the 4-point property at (a=2, b=1, c=3): 2-3 is an edge, 2-1 is not, and no d < 2 witnesses the property.

## REPAIR_HINTS
Replace the bucket handling in `_lexbfs` with the standard HMPV **breadth-first** scheme:

```python
def _lexbfs(adj, n):
    buckets = [list(range(n))]   # queue of buckets
    order = []
    while buckets:
        B = buckets.pop(0)
        if not B:
            continue
        v = B[0]
        order.append(v)
        rest = B[1:]
        if not rest:
            continue
        B1 = [x for x in rest if adj[v][x]]
        B2 = [x for x in rest if not adj[v][x]]
        # reinsert at the FRONT, B2 before B1
        if B1:
            buckets.insert(0, B1)
        if B2:
            buckets.insert(0, B2)
    return order
```

Key points:
- `buckets.pop(0)` (front of queue), not an index pointer that descends in place.
- Reinsert the split parts at the **front** of the queue so they are processed before any other pending bucket.
- Insert **B2 before B1** so B2 ends up at the front (B2 processed first).

Do NOT keep the in-place `buckets[i:i+1] = new_buckets` depth-first scheme — that is the bug. Also do not try to "fix" it by only swapping B1/B2 while keeping the in-place descent; the front-of-queue reinsertion is essential for the lexicographic property.

Note: this is a correct-but-recomputing baseline; the dynamic (sub-recompute) part remains the open research question.
