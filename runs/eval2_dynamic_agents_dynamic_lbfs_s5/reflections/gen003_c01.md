## FAILURE_DESCRIPTION
After `insert (2, 0)` on a 4-vertex graph, the candidate returned ordering `[0, 2, 1, 3]`, but the expected (valid) ordering is `[0, 2, 3, 1]`. The verifier reports a 4-point (LB) property violation at (a, b, c) = (2, 1, 3), i.e. positions (pos_a, pos_b, pos_c) = (1, 2, 3) in the returned ordering:

- a = 2 (pos 1), b = 1 (pos 2), c = 3 (pos 3)
- ac in E: edge (2,3) exists
- ab not in E: edge (2,1) does not exist
- No d < a (i.e. no d among {0}) satisfies db in E and dc not in E (minD = 10^9 sentinel = none found)

So the returned ordering is NOT a valid LexBFS ordering of the current graph.

## ROOT_CAUSE
The candidate's `_lexbfs` is a **depth-first** partition refinement, not the standard **breadth-first** (FIFO) refinement of Habib–McConnell–Paul–Viennot. The bug is in the bucket queue handling:

```python
buckets[i:i + 1] = new_buckets
# i now points at B1 (or B2 if B1 empty), the next bucket to process
```

After splitting the current bucket B into [B1, B2], the code leaves `i` pointing at the *front* of the queue, so the next iteration immediately processes B1 (the neighbor sub-bucket) before B2 or any later buckets. This is DFS refinement.

LexBFS requires **BFS refinement**: when a vertex v is output, its split of the current bucket must be processed *after* all buckets that were already queued (i.e. the split sub-buckets are appended to the **end** of the queue, and `i` advances past the consumed bucket). The lexicographic property (and hence the (LB) 4-point certificate) is only guaranteed by the FIFO/queue discipline.

Concrete trace on the failing graph (edges after insert: (0,2), (2,3), (0,3) — the exact edge set is inferred from the violation; the key point is the queue discipline):

- Start: buckets = [[0,1,2,3]], i=0.
- Output 0. Split rest {1,2,3} by N(0): suppose B1=[2,3] (neighbors), B2=[1].
- **BFS (correct):** queue becomes [[2,3],[1]], i=1 → process [1] next (or [2,3] next, but the *relative* order of splits is what matters: splits are appended, not re-queued at the front).
- **DFS (candidate):** queue becomes [[2,3],[1]] but i stays 0 → process [2,3] next, output 2, split {3} → 3 is neighbor of 2, so B1=[3], B2=[] → queue [[3],[1]] → output 3, then 1. Order: 0,2,3,1.

Wait — that trace gives the *expected* order. The actual divergence depends on the exact adjacency, but the mechanism is the same: the candidate's DFS discipline produces a different (and here invalid) ordering than the FIFO discipline. The verifier's expected `[0,2,3,1]` is the FIFO result; the candidate's `[0,2,1,3]` is the DFS result, and the DFS result fails the (LB) certificate on this graph.

The responsible lines are the in-place replacement `buckets[i:i + 1] = new_buckets` combined with **not incrementing `i`** — this re-processes the split sub-buckets immediately (DFS) instead of appending them to the end of the queue (BFS).

## REPAIR_HINTS
The smallest fix: make the refinement **breadth-first** (FIFO queue discipline).

In `_lexbfs`, replace the in-place front replacement with:

```python
# consume the current bucket
i += 1
# append the split sub-buckets to the END of the queue
if B1:
    buckets.append(B1)
if B2:
    buckets.append(B2)
```

i.e. change:
```python
buckets[i:i + 1] = new_buckets
# (i unchanged)
```
to:
```python
i += 1
buckets.extend(new_buckets)
```

This is the standard HMPV FIFO refinement and guarantees a valid LexBFS ordering (any start vertex, any tie-break within a bucket).

**Approaches that will NOT work:**
- Keeping the DFS discipline and trying to "fix" the ordering post-hoc (e.g. re-sorting) — the DFS refinement does not produce a LexBFS ordering in general; no post-processing can restore the (LB) certificate.
- Changing only the tie-break (e.g. reversing B1/B2 order) — the problem is the queue discipline (front vs. back), not the sub-bucket order.
- Any "incremental" update that patches the old ordering after an edge flip — the research brief notes this is an open problem; the safe fix is to keep the full recompute but with the correct (BFS) static algorithm.
