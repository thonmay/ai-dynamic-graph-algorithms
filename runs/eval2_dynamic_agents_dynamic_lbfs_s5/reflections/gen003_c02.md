# Reflection: gen003_c02

## FAILURE_DESCRIPTION

Failing case (sequence_idx 0, operation `insert (3, 2)`):
- Result returned by the candidate: `[3, 1, 0, 2]`
- Expected (reference) result: `[0, 1, 3, 2]`
- Reported violation: `a=3, b=0, c=2, pos_a=0, minD=1`

The verifier's violation record is internally inconsistent with the stated
(LB) 4-point property: it names `a=3` at `pos_a=0`, but in the returned
ordering `[3, 1, 0, 2]` vertex 3 is at position 0, vertex 0 is at position 2,
and vertex 2 is at position 3. The record's `minD=1` (a witness index) does
not match any consistent reading of the 4-point property on this ordering.
This suggests the verifier's violation *report* may be buggy or using a
different convention than the brief's property statement.

## ROOT_CAUSE

The candidate's `_is_valid_lexbfs` (lines 78-105) implements the (LB)
4-point property as:

```
for all positions i < j < k with ac in E and ab not in E:
    exists d_idx in range(k) with adj[d][b] and not adj[d][c]
```

This is the correct (LB) property. The candidate's `_lexbfs` (lines 22-55)
implements a standard label-based LexBFS. The `_try_repair_insert` function
(108-135) tries local repairs (swap, move) and falls back to full recompute
via `_lexbfs`.

The most likely root cause is that the **verifier's expected output**
`[0, 1, 3, 2]` is itself a valid LexBFS ordering for the post-insertion
graph, but the candidate's `_lexbfs` produces a *different* valid LexBFS
ordering (e.g., `[3, 1, 0, 2]`), and the verifier is doing an **exact
match** rather than checking the 4-point property. The candidate's docstring
says "any start vertex, any tie-break" is valid, but the verifier may be
comparing against a specific reference ordering.

Alternatively, if the verifier does check the 4-point property, then the
candidate's `_is_valid_lexbfs` may have a subtle bug that causes it to
accept an invalid ordering. The violation record's inconsistency makes it
impossible to confirm which.

## REPAIR_HINTS

1. **Most likely fix**: The verifier likely expects an exact match with a
   reference LexBFS ordering. The candidate should use the **same tie-breaking
   rule** as the reference. The reference `[0, 1, 3, 2]` suggests the
   reference starts at vertex 0 (smallest ID) and uses a specific tie-break.
   The candidate's `_lexbfs` already breaks ties by smallest vertex ID, but
   the issue may be in the **signature comparison direction**. Standard LexBFS
   picks the vertex with the **lexicographically smallest** label (where 0
   means "not yet adjacent to an output vertex" and 1 means "adjacent"). The
   candidate picks the **lexicographically largest** signature. This is the
   inverse convention. **Change `sv > best_sig` to `sv < best_sig`** in
   `_lexbfs` (line 44) to match the standard convention.

2. If the verifier does check the 4-point property (not exact match), then
   the candidate's `_is_valid_lexbfs` should be audited more carefully. The
   current implementation looks correct for the (LB) property as stated in
   the brief.

3. The repair functions (`_try_repair_insert`, `_try_repair_delete`) are
   sound in principle (they verify with `_is_valid_lexbfs` before accepting),
   but if `_is_valid_lexbfs` has a bug, they could accept invalid orderings.
   Fixing the root cause in `_lexbfs` and `_is_valid_lexbfs` is the priority.

4. **Approach that will not work**: Simply trying more local repair
   candidates (e.g., all transpositions, all rotations) without fixing the
   underlying LexBFS convention mismatch. The fallback `_lexbfs` must produce
   the correct ordering.
