## FAILURE_DESCRIPTION
Operation `insert (2, 0)` on a 4-vertex graph. The candidate returned ordering `[0, 2, 1, 3]`, but the verifier reports it is not a valid LexBFS ordering: the (LB) 4-point property is violated with a=2, b=1, c=3 (positions 1 < 2 < 3). Expected (one valid) ordering: `[0, 2, 3, 1]`.

Reconstructing the post-insert graph from the violation and the candidate's output:
- For the candidate to produce `[0, 2, 1, 3]`, the initial bucket `[0,1,2,3]` must split with v=0 into B1=[2,3] (neighbors) and B2=[1] (non-neighbor), meaning adj[0]=[0,0,1,1].
- Then B=[2,3] is processed: v=2, rest=[3], adj[2][3]=1 so B1=[3], B2=[].
- Then B=[1]: v=1, no rest. Then B=[3]: v=3.
- Result: [0, 2, 1, 3]. ✓

So the post-insert graph has E = {(0,2), (0,3), (2,3)}. Vertex 1 is isolated.

4-point property check for [0, 2, 1, 3]:
- a=2 (pos 1), b=1 (pos 2), c=3 (pos 3): ac=(2,3)∈E ✓, ab=(2,1)∉E ✓. Need d at pos < 1, i.e. d=0: db=(0,1)∉E. No valid d. **VIOLATION.**

For [0, 2, 3, 1]: no triple a<b<c satisfies both ac∈E and ab∉E simultaneously (verified by exhaustive check). **VALID.**

## ROOT_CAUSE
The `_lexbfs` function uses a **FIFO queue with append-to-end** for bucket processing. When a bucket B is split by vertex v into B1 (neighbors) and B2 (non-neighbors), both sub-buckets are appended to the **end** of the queue:

```python
if B1:
    buckets.append(B1)
if B2:
    buckets.append(B2)
```

This is **not** the correct LexBFS partition-refinement. The correct algorithm requires that B1 and B2 be inserted at the **front** of the remaining bucket list (right after the current bucket), with B1 before B2. This ensures that the most recently refined sub-buckets are processed before older ones, which is what yields the lexicographic property.

The FIFO-append-to-end strategy processes older buckets before newer sub-buckets, which can interleave vertices from different refinement levels in a way that violates the 4-point property. In this specific case, vertex 1 (from B2, a non-neighbor of 0) is processed before vertex 3 (from B1, a neighbor of 2), producing the invalid ordering [0, 2, 1, 3] instead of the valid [0, 2, 3, 1].

## REPAIR_HINTS
Replace the bucket queue logic in `_lexbfs` to insert sub-buckets at the **front** of the remaining list, with B1 before B2:

```python
def _lexbfs(adj, n):
    buckets = [list(range(n))]
    order = []
    while buckets:
        B = buckets[0]
        buckets = buckets[1:]
        if not B:
            continue
        v = B[0]
        order.append(v)
        rest = B[1:]
        if not rest:
            continue
        B1 = [x for x in rest if adj[v][x]]
        B2 = [x for x in rest if not adj[v][x]]
        new_front = []
        if B1:
            new_front.append(B1)
        if B2:
            new_front.append(B2)
        buckets = new_front + buckets  # insert at FRONT, B1 before B2
    return order
```

The key change: `buckets = new_front + buckets` instead of `buckets.append(B1); buckets.append(B2)`. This is the standard Habib-McConnell-Paul-Viennot LexBFS where the most recently split sub-buckets are processed first (LIFO-like priority for new splits), ensuring the lexicographic ordering property.

Approaches that will NOT work:
- Keeping the FIFO append-to-end strategy but reordering B1/B2: the fundamental issue is the queue discipline, not the B1/B2 order.
- Using a priority queue keyed on bucket "label" vectors: overkill and error-prone; the front-insertion approach is simpler and correct.
