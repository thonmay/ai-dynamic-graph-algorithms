# Reflection: gen004_c02

## FAILURE_DESCRIPTION

- Operation: `insert (3, 2)` at `sequence_idx: 0` (first update after `init`).
- Returned ordering: `[3, 1, 0, 2]`.
- Expected (reference) ordering: `[0, 1, 3, 2]`.
- Verifier-reported violation: `a=3, b=0, c=2, pos_a=0, minD=1`.

Interpreting the violation: in the returned ordering, vertex `a=3` sits at position 0, vertex `b=0` at position 2, vertex `c=2` at position 3. The verifier found that the (LB) 4-point property is violated for this triple: `a=3` is adjacent to `c=2` (the just-inserted edge), `a=3` is NOT adjacent to `b=0`, and no earlier vertex `d` (with `minD=1`, i.e. the only candidate is position 0, which is `a` itself) witnesses `db in E and dc not in E`.

## ROOT_CAUSE

The static `_lexbfs` routine is **not a correct LexBFS**. It picks the unoutput vertex with the lexicographically **largest** signature (0/1 vector of adjacency to already-output vertices). Standard LexBFS (Habib–McConnell–Paul–Viennot) picks the vertex with the lexicographically **smallest** signature (equivalently, the vertex whose non-neighbourhood among the output set is lexicographically smallest, i.e. the vertex that is "most adjacent" to the output prefix). The candidate has the comparison inverted:

```python
if sv > best_sig:
    best = v
    best_sig = sv
elif sv == best_sig and v < best:
    ...
```

should be `sv < best_sig` (and the tie-break direction is also suspect). Because of this inversion, `init` already produces a non-LexBFS ordering on the initial graph, and the subsequent `insert (3,2)` repair path (which only tries the current ordering plus a swap / two single moves) cannot recover a valid ordering, so the returned `[3, 1, 0, 2]` fails the (LB) 4-point property.

The `gen004_c02` "repair" (widening the witness scan in `_is_valid_lexbfs` from `d < a` to `d < c`) does not address this: the validator itself is now consistent with the (LB) property, but the *generator* (`_lexbfs`) is producing orderings that no amount of local repair can fix because the base ordering is not a LexBFS to begin with.

## REPAIR_HINTS

1. **Fix `_lexbfs` to be a genuine LexBFS.** The minimal change is to invert the comparison:
   ```python
   if sv < best_sig:
       best = v; best_sig = sv
   elif sv == best_sig and v < best:
       best = v; best_sig = sv
   ```
   (Pick lexicographically **smallest** signature; break ties by smallest vertex id.) This is the standard "label-based" LexBFS: at each step, among unoutput vertices, choose the one whose 0/1 vector of adjacency to the output prefix is lexicographically smallest. Verify on a few small graphs (path, cycle, claw, complete bipartite) that the output satisfies the (LB) 4-point property as implemented in `_is_valid_lexbfs`.

2. **Do NOT try to "fix" the validator** to match the broken generator. The (LB) 4-point property as implemented in `_is_valid_lexbfs` (with `d < c` witness scan) is the correct certificate; keep it.

3. **Do NOT rely on the local repair heuristics** (`_try_repair_insert` / `_try_repair_delete`) for correctness. They are best-effort and only try a swap plus two single moves; they will miss valid orderings that require larger rearrangements. The fallback to `_lexbfs` is the only correctness guarantee, so once `_lexbfs` is correct, the fallback path is correct. The repair heuristics can stay as an optimisation but must be validated by `_is_valid_lexbfs` before being returned (which they already are).

4. **Approaches that will not work:**
   - Keeping the "largest signature" rule and trying to compensate with a different tie-break: the inversion is fundamental, not a tie-break issue.
   - Trying to make the repair heuristics exhaustive (e.g. trying all transpositions): the search space is O(n^2) and still does not guarantee finding a valid ordering if one exists; the recompute fallback is the right safety net.
   - Changing the (LB) property to a different certificate: the 4-point property is the standard one and is what the verifier checks.

5. **After fixing `_lexbfs`, re-run the failing case** (`insert (3,2)` at `sequence_idx: 0`) and confirm the returned ordering passes `_is_valid_lexbfs` on the post-insertion graph.
