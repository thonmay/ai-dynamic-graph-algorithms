# Reflection: gen008_c01

## FAILURE_DESCRIPTION
Failing case (sequence_idx 2, operation `insert (0, 3)` on a 4-vertex graph):
- Candidate returned ordering `[0, 1, 2, 3]` (kept the pre-update ordering).
- Expected (a valid LexBFS of the post-update graph): `[0, 1, 3, 2]`.
- Verifier's (LB) 4-point violation on the returned ordering:
  `a=1, b=2, c=3, pos_a=1, minD=1000000000` — i.e. at positions 1<2<3,
  `1-3 in E`, `1-2 not in E`, and NO vertex at position < 1 (only vertex 0)
  satisfies `d-2 in E and d-3 not in E`.

## ROOT_CAUSE
The incremental validity check `_fast_check` is unsound, and `insert_edge`
trusts it, so the invalid ordering is kept instead of being recomputed.

The (LB) property for a triple (a,b,c) depends on FOUR edges: `a-c` (must be
in E), `a-b` (must be not in E), and for the witness `d<a`: `d-b` (in E) and
`d-c` (not in E). A single edge flip (u,v) can therefore change the status of
a triple in up to FOUR roles:
1. `a-c` = flipped edge (covered by "Role 1" in the code),
2. `a-b` = flipped edge (covered by "Role 2"),
3. `d-b` = flipped edge — NOT covered,
4. `d-c` = flipped edge — NOT covered.

Roles 3 and 4 are exactly the ones that matter here. In the failing case,
the flipped edge (0,3) is the `d-c` edge of the violating triple
(a=1, b=2, c=3, d=0): before the insertion `0-3` was not an edge, so d=0
witnessed the triple (`0-2 in E`, `0-3 not in E`); after the insertion
`0-3 in E`, so d=0 no longer witnesses it and no other d exists. The
violation is NEW, but the flipped edge does not appear as `a-c` or `a-b` of
the triple, so `_fast_check` never examines this triple and returns True.

Responsible lines (in `_fast_check`): the docstring claim
"for a single edge flip, only triples where the flipped edge participates
can change their status. So this IS a complete check" is false — it only
enumerates the two roles where the flipped edge is `a-c` or `a-b`, and
omits the two roles where it is `d-b` or `d-c`. Consequently `insert_edge`
takes the `if _fast_check(...): return {'ordering': order, ...}` branch and
keeps the invalid ordering.

Note: the full checker `_is_valid_lexbfs` is correct (it would have caught
this violation), but it is dead code — never called from `init`,
`insert_edge`, or `delete_edge`.

## REPAIR_HINTS
Smallest change that restores correctness: in `insert_edge` and
`delete_edge`, replace the `_fast_check(graph, order, edge)` call with the
full `_is_valid_lexbfs(graph, order)` check (it is already implemented and
correct). If `_fast_check` returns True, keep the ordering; otherwise
recompute with `_lexbfs`. This is O(n^3) per update but fully correct, and
it satisfies the "full correctness first" research goal.

If a faster targeted check is desired later, it must enumerate ALL four
roles of the flipped edge in the (LB) property:
- Role 1 (a-c = flipped edge): for every b with pos(a)<pos(b)<pos(c),
  check the triple (a,b,c) — already done.
- Role 2 (a-b = flipped edge): for every c with pos(b)<pos(c), check
  (a,b,c) — already done.
- Role 3 (d-b = flipped edge): for every a with pos(d)<pos(a) and every
  c with pos(a)<pos(c), the triple (a,b,c) may have LOST a witness; it is
  violated iff no other d' < a witnesses it.
- Role 4 (d-c = flipped edge): for every a with pos(d)<pos(a) and every
  b with pos(a)<pos(b), the triple (a,b,c) may have LOST a witness; check
  the same way.
Roles 3 and 4 are the missing ones (this failure is a Role-4 case).

Approaches that will NOT work:
- Keeping the current two-role `_fast_check` and "fixing" it by also
  checking the flipped edge as `d-b`/`d-c` only for the specific triple
  where it appears — the witness-existence condition is global over all
  d<a, so any triple whose witness set changed must be re-verified in full.
- Trusting that an insertion can never invalidate a LexBFS ordering (it
  can, as this case shows).
- Relying on `_is_valid_lexbfs` being called implicitly — it is dead code
  and must be wired into both update functions explicitly.
