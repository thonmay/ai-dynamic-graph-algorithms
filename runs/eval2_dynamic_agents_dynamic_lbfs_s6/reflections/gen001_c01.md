## FAILURE_DESCRIPTION
Operation: `init` on a 2-vertex graph with adjacency matrix
```
[[0, 1],
 [1, 0]]
```
(i.e. a single edge 0-1). Expected ordering: `[0, 1]` (any valid LexBFS of a 2-vertex connected graph, e.g. `[0, 1]` or `[1, 0]`). Actual result: `[0]` — the returned ordering contains only one vertex; vertex 1 is missing entirely.

## ROOT_CAUSE
The bug is in `_lexbfs_full`. The queue `Q` is seeded with the *initial* bucket object:

```python
P = [list(range(n))]
Q = [P[0]]
```

but the main loop's guard rejects it:

```python
while head < len(Q):
    b = Q[head]
    head += 1
    if not b:
        continue
    if b not in P:
        continue
```

`b not in P` uses `list.__eq__` (value equality), not identity. After the first vertex is popped, the refinement step rebuilds `P` as `newP` from the *other* buckets only (the popped bucket `b` is kept as-is, but for n=2 the initial bucket becomes empty after `v = b.pop(0)`, and the only other bucket is the empty `Nc`/`N` split of the empty remainder — nothing is appended). So `P` ends up as `[]` (or contains only empty lists), and the remaining queued bucket (the original `P[0]`, now `[1]` before the pop... actually after the pop it is `[1]`) is no longer value-equal to any element of `P`, so `b not in P` is True and the loop `continue`s. The second vertex is never popped, and `order` is returned as `[0]`.

Concretely for n=2, graph = edge 0-1:
1. `P = [[0,1]]`, `Q = [[0,1]]`, `head=0`.
2. Pop `b = [0,1]` from Q. `b in P` → True (same object). `v = b.pop(0)` → `v=0`, `b` is now `[1]`, `order=[0]`.
3. Refine: iterate `P = [[0,1]]` (the list `P` still holds the object `b`, now `[1]`). For `b2 is b`: append `b` (`[1]`) to `newP`. No other buckets. `P = [[1]]`.
4. Loop: `head=1`, `len(Q)=1` → loop exits.

Wait — actually the loop exits because `head` (1) is no longer `< len(Q)` (1). The bucket `[1]` was never re-queued. In the standard HMPV algorithm, after refining, the *remaining* buckets (including the one that still holds `[1]`) must be enqueued so their first vertices get processed. Here only the *newly split* buckets `N` and `Nc` are appended to `Q`; the surviving bucket `b` itself (and any pre-existing non-split buckets) are never re-enqueued. So the loop terminates with `order = [0]`.

The `b not in P` guard is a secondary red herring (it would also misbehave on value-equal distinct lists), but the primary defect is: **the loop only processes buckets that were explicitly appended to `Q` as split products; the original bucket that still contains unprocessed vertices is never re-queued, so the while loop terminates prematurely.**

## REPAIR_HINTS
1. **Primary fix (in `_lexbfs_full`):** After the refinement step, re-enqueue every non-empty bucket in the new `P` that has not yet been fully consumed. The cleanest correct pattern is the standard HMPV one: maintain `Q` as a queue of *bucket references*, and after each refinement, enqueue the new sub-buckets `N` and `Nc` (as the code does), AND ensure the surviving bucket `b` (if still non-empty) is re-enqueued. Alternatively, restructure so that the loop invariant is "every non-empty bucket in `P` is in `Q` exactly once". A simple correct rewrite:

   ```python
   P = [list(range(n))]
   Q = deque(P)
   order = []
   while Q:
       b = Q.popleft()
       if not b:
           continue
       v = b.pop(0)
       order.append(v)
       newP = []
       for b2 in P:
           if b2 is b:
               if b:
                   newP.append(b)
                   Q.append(b)   # re-enqueue surviving bucket
               continue
           N  = [x for x in b2 if graph[v][x]]
           Nc = [x for x in b2 if not graph[v][x]]
           if N:
               newP.append(N); Q.append(N)
           if Nc:
               newP.append(Nc); Q.append(Nc)
       P = newP
   ```

   This guarantees every non-empty bucket is eventually popped and its first vertex emitted.

2. **Remove the `if b not in P: continue` guard.** It is both unnecessary (with the re-enqueue fix, every queued bucket is in `P`) and dangerous (value-equality on lists can cause spurious skips or, conversely, accept a stale bucket that was replaced by a value-equal new list). Use identity (`is`) if a guard is truly needed, but the re-enqueue fix makes it moot.

3. **Do not** try to "fix" this by special-casing n=2 or by appending all of `P` to `Q` unconditionally at the end of each iteration without deduplication — that would cause exponential blowup. The correct invariant is: each non-empty bucket appears in `Q` exactly once at any time.

4. The `_check_lb_property` and `_try_local_repair` functions are not implicated in this failure (the failure is at `init`, before any update). They can be left as-is for this fix, though `_check_lb_property` is O(n^4) and will be a performance bottleneck for larger n.
