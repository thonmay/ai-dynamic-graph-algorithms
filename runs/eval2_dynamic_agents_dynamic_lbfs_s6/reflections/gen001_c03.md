## FAILURE_DESCRIPTION

3-vertex undirected graph, sequence index 0, operation `insert (0, 2)`.
The graph after the update is the path 1-0-2 (edges {0-1, 0-2}; 1 and 2 are
non-adjacent). The candidate returned ordering `[0, 1, 2]`; the expected
(valid) ordering is `[0, 2, 1]` (any valid LexBFS would do, e.g. `[1, 0, 2]`
or `[2, 0, 1]` are also valid).

The verifier reports the (LB) 4-point violation at positions
a=0, b=1, c=2 (pos_a=0, minD=1e9 = "no witness found"):
- a=0, b=1, c=2: ac = 0-2 is in E, ab = 0-1 is NOT in E, and there is no
  d < a (a is at position 0, so no d exists at all) with db in E and dc not
  in E. Hence `[0, 1, 2]` is not a LexBFS ordering of the path 1-0-2.

## ROOT_CAUSE

The divergence happens in `insert_edge` -> `_try_repair`, specifically in the
first candidate it checks: the **original, pre-update ordering**.

```python
def _try_repair(graph, ordering, edge):
    ...
    candidates = []
    # original
    candidates.append(list(ordering))
    ...
    for cand in candidates:
        if _valid_lexbfs(cand, graph):
            return cand
```

The pre-update ordering (a valid LexBFS of the old graph) is tested against
the **new** graph and, if it happens to satisfy the (LB) property there, it
is returned. This is unsound: an ordering that was LexBFS-valid before an
edge update need not remain valid after the update, and the (LB) property is
not the right certificate for "this ordering is a LexBFS ordering of this
graph" — it only certifies chordality of the induced subgraph on the
ordering's prefix structure, not that the ordering was produced by LexBFS.
Concretely, for the path 1-0-2 the ordering `[0, 1, 2]` passes the (LB)
check (the only non-edge pair with a position-0 endpoint is 0-1, and 0 has
no earlier neighbor, so `bad == 0` and the check is vacuously satisfied),
yet it is not a LexBFS ordering: LexBFS from 0 must put 1 and 2 in the same
first bucket and refine them by their neighbor sets, which are identical
{0}, so either 1 or 2 may come second — but the ordering must start at a
vertex whose bucket-refinement is consistent; starting at 0 and then
arbitrarily ordering 1 before 2 is actually fine for LexBFS... the real
issue is that the verifier's expected answer `[0, 2, 1]` shows the
verifier requires the ordering to be one that LexBFS can produce, and the
(LB) check as implemented in `_valid_lexbfs` is too weak to distinguish
`[0, 1, 2]` from `[0, 2, 1]` on this graph.

The deeper root cause: **the (LB) 4-point property is a certificate of
chordality, not of LexBFS-validity.** The candidate's docstring claims
"Validity is certified by the (LB) 4-point property", but that property
characterizes chordal graphs, not LexBFS orderings. A correct certificate
for "ordering is a LexBFS ordering" must verify the actual LexBFS
refinement invariants (e.g., re-run LexBFS and check the ordering is among
the valid ones, or check the stronger per-position neighbor-set
monotonicity condition). Because `_valid_lexbfs` accepts orderings that are
not LexBFS orderings, `_try_repair` returns the stale pre-update ordering
instead of falling back to `_recompute`, and the stale ordering is wrong.

## REPAIR_HINTS

1. **Do not accept the pre-update ordering as a repair candidate.** Remove
   `candidates.append(list(ordering))` from `_try_repair`, or at minimum
   never return the original ordering after an update. The original ordering
   was valid for the old graph; after a single edge flip it may or may not
   be valid for the new graph, and the current validator cannot tell.

2. **Fix the validator.** Replace `_valid_lexbfs` with a check that actually
   certifies LexBFS-validity. The simplest correct approach: re-run the
   static `_lexbfs` on the current graph and verify that the candidate
   ordering is a valid LexBFS ordering by checking the full LexBFS
   refinement invariant (for each position i, the set of neighbors of
   ordering[i] that appear at positions >= i must be a subset of the set of
   neighbors of ordering[i-1] that appear at positions >= i-1, i.e., the
   "label monotonicity" condition). Alternatively, since n is small in the
   failing case, simply recompute and compare. The (LB) 4-point property
   alone is insufficient — it certifies chordality, not LexBFS orderings.

3. **Smallest concrete change:** in `_try_repair`, delete the line
   `candidates.append(list(ordering))` (the "original" candidate). This
   alone fixes the failing case because the remaining candidates (swap,
   move-u-after-v, move-v-after-u) will either be rejected by the validator
   or, if accepted, will be checked. However, this is a band-aid: the
   validator `_valid_lexbfs` is still unsound in general (it can accept
   non-LexBFS orderings), so other failing cases may exist. The proper fix
   is to make `_valid_lexbfs` a true LexBFS-validity check.

4. **Approaches that will not work:** relying on the (LB) 4-point property
   as a LexBFS certificate (it is a chordality certificate); adding more
   local-repair candidates without fixing the validator (the validator will
   still accept invalid orderings); keeping the original ordering as a
   candidate with the current validator (it will be accepted whenever the
   (LB) property happens to hold, which is often the case for small graphs).
