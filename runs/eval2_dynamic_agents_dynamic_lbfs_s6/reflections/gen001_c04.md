## FAILURE_DESCRIPTION
Operation: `init` on a 3-vertex undirected graph (sequence_idx 0, so no prior updates).
Result returned: `[0, 1, 2]`. Expected (a valid LexBFS ordering): `[0, 2, 1]`.

The verifier reports the (LB) 4-point violation with a=0, b=1, c=2 (pos_a=0, minD=1e9, i.e. no witness d exists). For this to be a violation we need:
- a=0 not adjacent to b=1 (ab ∉ E),
- a=0 adjacent to c=2 (ac ∈ E),
- no d before a (a is first, so vacuously none).

So the graph has edge (0,2) and no edge (0,1). The only LexBFS orderings of such a graph (with start 0) are `[0, 2, 1]` (if 2-1 non-edge) or `[0, 2, 1]`/`[0,1,2]`-invalid — in every case vertex 2 must come before vertex 1, because 2 is adjacent to the start 0 while 1 is not. The candidate's `_lexbfs_recompute` produced `[0, 1, 2]`, which is not a LexBFS ordering at all.

## ROOT_CAUSE
The bug is in `_lexbfs_recompute`'s bucket-refinement step. After visiting a vertex `v`, the code splits every bucket into "adjacent to v" and "not adjacent to v", but it **appends the `in_v` (adjacent) sub-bucket BEFORE the `not_v` sub-bucket**:

```python
if in_v:
    new_buckets.append([lbl | frozenset({v}), in_v])
if not_v:
    new_buckets.append([lbl, not_v])
```

LexBFS requires that, within the same label, the vertices adjacent to the just-visited vertex come **first** — but the global bucket order must also keep the *not-adjacent* bucket in its original relative position, with the *adjacent* bucket placed **immediately before** it (i.e., the adjacent part is a prefix of the original bucket's position, not a new bucket pushed ahead of the non-adjacent part in list order). More precisely, the standard partition-refinement LexBFS keeps buckets in a queue and, when refining a bucket, the "adjacent to v" part must be placed **before** the "not adjacent" part *at the same position in the queue*. The code does put `in_v` before `not_v` in the list, which is correct for a single bucket — but the real bug is subtler:

Tracing the failing case (edges: (0,2) only, i.e. adj[0]={2}, adj[1]={}, adj[2]={0}):
1. start=0, order=[0]. unvisited={1,2}.
2. Initial buckets: v=1 → label=∅ (1 not adj to 0); v=2 → label={0} (2 adj to 0).
   buckets = [[∅,[1]], [{0},[2]]].
3. Pick first non-empty bucket: idx=0, label=∅, verts=[1]. **v=1 is selected.**
   order=[0,1].
4. Refine with v=1: bucket [∅,[1]] is now empty; bucket [{0},[2]]: 2 not adj to 1 → not_v=[2], in_v=[]. new_buckets=[[{0},[2]]].
5. Pick bucket [{0},[2]]: v=2. order=[0,1,2].

The algorithm picked vertex 1 (label ∅) before vertex 2 (label {0}). **This is the core error: LexBFS must always pick the bucket with the LARGEST label (most visited neighbors), not the first bucket in list order.** The initial bucket list is ordered by vertex id (∅-bucket first), and the "pick first non-empty bucket" rule then selects the least-informed bucket. Correct LexBFS picks the bucket whose label is maximal (i.e., adjacent to the most recently visited vertices, in lexicographic order of the label sets).

The responsible lines:
```python
# Pick the first non-empty bucket
idx = -1
for i, (label, verts) in enumerate(buckets):
    if verts:
        idx = i
        break
```
This should instead select the bucket with the lexicographically maximal label (comparing labels as characteristic vectors over the visited set in visit order), which is the defining rule of LexBFS.

## REPAIR_HINTS
1. **Fix the bucket selection rule in `_lexbfs_recompute`**: replace "first non-empty bucket" with "non-empty bucket whose label is lexicographically maximal". Labels are sets of visited vertices; compare two labels by finding the most recently visited vertex that distinguishes them — the label containing that vertex is larger. Concretely, maintain the visit order and compare labels by: for the last-visited vertex v_k, if exactly one label contains v_k, that label wins; otherwise recurse to v_{k-1}, etc. Since labels are built incrementally (each refinement only adds the current v to the in_v sub-bucket), an efficient implementation keeps buckets in a list ordered by label (most-refined first) and, after each refinement, moves the `in_v` sub-bucket to the front of the list (it has the largest label because it contains the just-visited v). The `not_v` sub-bucket stays in place.

2. **Concrete minimal fix**: after building `new_buckets`, reorder so that buckets containing `v` in their label come first (in their original relative order), followed by the rest. Since only the `in_v` sub-buckets contain `v`, this means: `new_buckets = [b for b in new_buckets if v in b[0]] + [b for b in new_buckets if v not in b[0]]`. Then "pick first non-empty bucket" becomes correct.

3. **Do NOT** try to fix this by changing the initial bucket ordering or the tie-break within a bucket — the selection rule is the only issue. The within-bucket order (popping from the end of `verts`) is a valid tie-break.

4. Note that `_is_valid_lexbfs` and `_try_local_fix` are correct; the failure is entirely in the recompute path, which is also the path taken by `init`. Once `_lexbfs_recompute` is fixed, `init` and the fallback in `insert_edge`/`delete_edge` will all be correct.
