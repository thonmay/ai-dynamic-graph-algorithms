# Reflection: gen002_c02

## FAILURE_DESCRIPTION

- Graph: n=3, undirected. Initial graph (before the update) is the single edge (0,1):
  adjacency rows: 0: [0,1,0], 1: [1,0,0], 2: [0,0,0].
- Operation: `insert_edge(graph, (0,2), state)` (sequence_idx 0). After the flip,
  edges are (0,1) and (0,2).
- Expected result: `[0, 2, 1]` (a valid LexBFS ordering of the updated graph).
- Actual result: `[0, 1, 2]`.
- Violation reported by the verifier: (LB) 4-point property fails at
  a=0, b=1, c=2 (pos_a=0, minD=1e9 = "no witness d exists").
  In `[0,1,2]`: a=0, b=1, c=2; ac=(0,2) in E, ab=(0,1) in E — wait, ab IS in E,
  so the verifier's a/b/c are positions: pos_a=0 means a is at position 0.
  Reading the violation as positions a<b<c with ac in E and ab not in E:
  a=pos0 (vertex 0), b=pos1 (vertex 1), c=pos2 (vertex 2): ac=(0,2) in E,
  ab=(0,1) in E — that doesn't match either. The exact reading doesn't matter:
  the verifier found a genuine (LB) violation in `[0,1,2]` on the updated graph,
  and `[0,2,1]` is the valid ordering.

## ROOT_CAUSE

The divergence happens in `insert_edge` -> `_try_repair`. The repair path
returns a candidate ordering that is **not** a valid LexBFS, because the
validator `_is_lexbfs` is itself buggy and returns `True` for the invalid
ordering `[0,1,2]` on the updated graph.

Trace of `_is_lexbfs([0,1,2], updated_graph)`:
- pos = {0:0, 1:1, 2:2}; adj: 0->{1,2}, 1->{0}, 2->{0}.
- posset[0] = bits{1,2} = 0b110; posset[1] = bit{0} = 0b001; posset[2] = bit{0} = 0b001.
- j=0 (b=vertex 0): mask_lt_j = 0.
  - k=1 (c=vertex 1): adj[0]&1 -> bc in E, `continue`.
  - k=2 (c=vertex 2): adj[0]&1 -> bc in E, `continue`.
- j=1 (b=vertex 1): mask_lt_j = 0b001.
  - k=2 (c=vertex 2): adj[1]&1 -> bc not in E.
    bad = posset[2] & 0b001 = 0b001 != 0.
    T = posset[1] & ~posset[2] = 0b001 & ~0b001 = 0.
    -> `if T == 0: return False`.

So `_is_lexbfs` actually returns False here... which means `_try_repair`
returns None and `insert_edge` falls back to `_recompute(graph)`.

That means the bug is in the **fallback**: `_recompute` -> `_lexbfs`
(partition refinement) produced `[0,1,2]` for the updated graph
(edges (0,1),(0,2)), which is NOT a valid LexBFS. Trace of `_lexbfs`:
- buckets = [[0],[1],[2]], bidx = [0,1,2].
- label[0] = buckets containing neighbors of 0 = {1,2} = 0b110.
  label[1] = {0} = 0b001. label[2] = {0} = 0b001.
- i=0: B=[0], len 1 -> finalize 0, ordering=[0]. Refine remaining buckets by
  adjacency to 0: bucket [1] len 1 skip; bucket [2] len 1 skip.
  (The `if len(C) == 1: continue` skips refinement of singletons — fine here.)
- i=0: B=[1], len 1 -> finalize 1, ordering=[0,1]. Refine: bucket [2] len 1 skip.
- i=0: B=[2] -> finalize 2. ordering = [0,1,2].

The flaw: when a singleton bucket is finalized, the code refines the *other*
buckets by adjacency to x, but it does so **in place, in increasing index
order, without re-sorting the buckets by their new labels**. In this case the
refinement is a no-op (all singletons), so the real bug is subtler: the
algorithm never compares the *labels* of the two singleton buckets [1] and
[2] against the already-finalized vertex 0. Both 1 and 2 are adjacent to 0,
so their labels over finalized vertices are equal (both "1"), and either
order [0,1,2] or [0,2,1] should be acceptable... but the verifier says
[0,1,2] is invalid.

Re-examining: in the updated graph, is [0,1,2] really invalid? Labels over
positions: L(0)=011 (adj to pos1,pos2), L(1)=100 (adj to pos0), L(2)=100.
LexBFS requires labels non-increasing in lex order (1 > 0): L(0)=011 vs
L(1)=100: at position 0, L(0) has 0 and L(1) has 1 -> L(0) < L(1) lexicographically
(if 1>0). So [0,1,2] is indeed NOT a valid LexBFS ordering: vertex 1's label
(100) is lexicographically larger than vertex 0's label (011), yet 1 comes
after 0. The valid orderings are [0,2,1] or [1,0,2]-style variants where the
vertex with label 100 comes before the vertex with label 011... actually the
start vertex must have the smallest label among all; here 0 has label 011 and
1,2 have 100, so 0 cannot be first. The verifier's expected [0,2,1] suggests
the verifier uses the convention that the label bitstring is compared with
0 > 1 (i.e., "not adjacent" sorts first) — under that convention L(0)=011 >
L(1)=100 and [0,1,2] is valid... The verifier's own (LB) check is the
authority, and it flagged [0,1,2].

**Bottom line (honest):** I could not fully reconcile the verifier's expected
ordering with the standard LexBFS label convention in this trace, so the exact
convention mismatch is uncertain. What IS certain: `_try_repair`'s validator
`_is_lexbfs` and the static `_lexbfs` disagree with the verifier's (LB)
checker on this 3-vertex case, and the candidate's own `_valid_lexbfs`
(pairwise label comparison) would also need to be checked against the
verifier's convention. The candidate has **two different internal validity
checks** (`_valid_lexbfs` and `_is_lexbfs`) that are never cross-checked, and
neither is verified to match the verifier's (LB) formulation.

## REPAIR_HINTS

1. **Make the validator match the verifier exactly.** Implement the (LB)
   4-point property literally as stated in the brief: for all positions
   a < b < c with ac in E and ab not in E, exists d < a with db in E and
   dc not in E. The current `_is_lexbfs` rewrites this as a
   "min(T) < min(bad)" condition over j<k pairs; that rewrite is where the
   logic likely diverges from the verifier (note it only checks the *minimum*
   bad position and *minimum* T position, and its T is not restricted to
   positions < a as the property requires — `T = posset[b] & ~posset[c]`
   includes positions >= j, which the property forbids as witnesses d).
   Concretely: the witness d must satisfy d < a (position), so T must be
   masked with `(1 << j) - 1` as well. That missing mask is a concrete bug.
2. **Cross-check the static `_lexbfs` output with the validator in
   `_recompute`** (assert `_is_lexbfs(ordering, graph)` before returning).
   If the static algorithm and the validator disagree, the test harness will
   catch it immediately instead of silently returning a bad ordering.
3. **Unify the two validators.** `_valid_lexbfs` (pairwise label comparison)
   and `_is_lexbfs` (4-point) should agree on every input; run both in
   `_recompute` and `_try_repair` and require both to pass.
4. Approaches that will NOT work: relying on `_try_repair`'s three
   hand-crafted candidates (swap / move-after) — they are too narrow and
   their acceptance is only as good as the buggy validator. Fixing the
   validator is the prerequisite; the recompute fallback must also be
   validated.
