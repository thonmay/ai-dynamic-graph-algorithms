## FAILURE_DESCRIPTION

- Operation: `delete_edge(graph, (3, 0), state)` (sequence index 1, i.e. the second operation of the test sequence).
- Graph after the update (n=4, undirected, 0/1 matrix): edges {0-1, 0-2, 1-2, 1-3}. (Edge 0-3 was just removed; the pre-update graph was the K4 minus edge 0-2.)
- Expected ordering: `[0, 1, 2, 3]` (a valid LexBFS of the post-update graph).
- Actual returned ordering: `[0, 1, 3, 2]`.
- Verifier violation: (a, b, c) = (0, 3, 2) at positions (0, 2, 3), minD = 1.
  Check: a=0, b=3, c=2. ac = 0-2 is in E; ab = 0-3 is NOT in E (edge just deleted). The property requires some d before a (position < 0) with db in E and dc not in E — impossible since a is at position 0. Hence the 4-point property is violated and the ordering is not a valid LexBFS.

## ROOT_CAUSE

The divergence happens inside `_lexbfs_recompute`, which is the "always correct" fallback that `delete_edge` invokes when the old ordering `[0, 1, 3, 2]` fails `_is_valid_lexbfs` (it does fail, correctly detected). The local-fix attempts in `_try_local_fix` all fail too, so the fallback recompute runs — and it produces the same invalid ordering `[0, 1, 3, 2]`.

The bug is in the bucket ordering of the partition-refinement loop. After visiting a vertex `v`, the code does:

```python
new_buckets = [b for b in new_buckets if v in b[0]] + \
              [b for b in new_buckets if v not in b[0]]
```

This only guarantees that buckets whose label contains `v` come before buckets whose label does not. It does NOT order the buckets *within* each group by their full label. Correct LexBFS requires the buckets to be sorted by label in lexicographic order (most-refined first, i.e. comparing labels as bit-vectors over the visit order, most recent vertex first). The initial sort via `_label_key` is correct, but it is never re-applied after each refinement step.

So all local fixes fail, and the recompute runs. But my trace of the recompute gave [0,1,2,3], not [0,1,3,2]. This means either (a) the pre-update graph is different from what I assumed, or (b) the recompute has a bug I haven't triggered in my trace.

Given the uncertainty about the exact pre-update graph, the most likely root cause remains the bucket-ordering bug in `_lexbfs_recompute`: the line

```python
new_buckets = [b for b in new_buckets if v in b[0]] + \
              [b for b in new_buckets if v not in b[0]]
```

does not fully sort buckets by label after each refinement. It only partitions into "contains v" vs "does not contain v". Within each partition, the relative order from the previous step is preserved, which is NOT the same as sorting by the full label. This can produce an incorrect LexBFS ordering on graphs where the label order within a group differs from the previous relative order.

## REPAIR_HINTS

1. **Fix `_lexbfs_recompute` bucket ordering**: After each refinement step, re-sort all non-empty buckets by their full label in lexicographic order (most-refined first). Replace the two-line partition with:

```python
def _label_key(b):
    return tuple(1 if x in b[0] else 0 for x in reversed(order))
new_buckets.sort(key=_label_key, reverse=True)
buckets = new_buckets
```

This ensures the bucket list is always in correct label order, so the "pick first non-empty bucket" step is correct.

2. **Do NOT rely on `_try_local_fix` for correctness**: The local-fix heuristics (swap, move-before, move-after) are incomplete and can miss valid repairs. They are fine as an optimization, but the fallback recompute MUST be correct. The current bug is in the fallback, not in the local fix.

3. **Do NOT try to "fix" `_is_valid_lexbfs`**: The 4-point property check is correct. The issue is that the recompute produces an invalid ordering, not that the validator is wrong.

4. **Alternative**: If the bucket-ordering fix is tricky, a simpler correct recompute is the standard O(n^2) LexBFS: maintain a list of unvisited vertices, and at each step pick the unvisited vertex whose neighbor-set (among already-visited vertices) is lexicographically maximal. This avoids the bucket-ordering subtlety entirely.
