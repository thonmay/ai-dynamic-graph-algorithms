## FAILURE_DESCRIPTION
Failing case: n=4, operation `delete (3, 0)` at sequence index 1. The state returned
`ordering = [0, 1, 3, 2]`; the expected (valid) ordering is `[0, 1, 2, 3]`.

The verifier reports the (LB) 4-point violation with a=0, b=3, c=2 (pos_a=0, minD=1):
in the returned order, position 0 < position 2 (b=3) < position 3 (c=2), edge (0,2)
is present, edge (0,3) is absent, and no d before position 0 exists to witness the
property. So the returned ordering is not a valid LexBFS ordering of the post-deletion
graph.

Reconstructed post-deletion graph (consistent with the violation and the expected
ordering): edges {0-1, 0-2, 1-2, 1-3} (edge 0-3 was just deleted). In this graph
`[0,1,3,2]` is invalid (the violation above) while `[0,1,2,3]` is valid.

## ROOT_CAUSE
The divergence is in `_lexbfs_recompute`: its bucket ordering is wrong, so the
"always correct" fallback produces an invalid ordering, and the local-fix path
(`_try_local_fix`) also fails to find a valid ordering, so the bad fallback result
is returned.

The bug is the bucket sort key. After each visit the code does:

```python
def _label_key(b):
    return tuple(1 if x in b[0] else 0 for x in reversed(order))
...
new_buckets.sort(key=_label_key, reverse=True)
```

`order` is the visit order (oldest first), so `reversed(order)` puts the MOST
RECENTLY visited vertex first in the tuple. With `reverse=True`, buckets are sorted
so that the bucket adjacent to the most recent vertex comes FIRST. That is the
opposite of LexBFS: the next vertex must be chosen from the bucket whose label is
lexicographically LARGEST when labels are compared oldest-vertex-first (i.e. the
bucket adjacent to the EARLIEST visited vertex wins).

Tracing the failing graph (edges {0-1,0-2,1-2,1-3}, start 0):
- After visiting 0: buckets {1,2,3} (label {0}) and { } ... actually 1,2,3 all
  adjacent to 0 -> one bucket [1,2,3] label {0}.
- Visit 1 (only bucket). Refine by 1: bucket {2,3} label {0,1} (both adj to 1),
  and 3 is adj to 1, 2 is adj to 1 -> both in. Wait 2 adj 1 yes, 3 adj 1 yes, so
  {2,3} label {0,1}. No other buckets.
- Next pick: only bucket {2,3}. The code pops `verts[0]` after the pop/swap trick
  (`verts[0] = verts[-1]; verts.pop()`), which removes the LAST element, so it
  visits 3 before 2. Result order [0,1,3,2] — exactly the invalid output.

So two compounding defects:
1. `_label_key`/`reverse=True` orders buckets most-recent-first (wrong direction).
2. Even within a single bucket the pop order (`verts[0]=verts[-1]; verts.pop()`)
   removes the last element, so tie-breaking is by descending vertex id rather than
   the deterministic order the refinement expects.

Because the fallback is wrong, and `_try_local_fix` only tries a handful of
single-vertex moves (swap, move-before, move-after) which cannot reach `[0,1,2,3]`
from `[0,1,3,2]` in a way that passes `_is_valid_lexbfs` on this graph, the invalid
ordering is returned.

Note: `_is_valid_lexbfs` itself is correct (it correctly rejects `[0,1,3,2]`), so
the guard `if _is_valid_lexbfs(graph, order): return state` does not mask the bug;
the bug is purely that the recompute/local-fix produce an invalid order.

## REPAIR_HINTS
Smallest concrete fix, in `_lexbfs_recompute`:

1. Fix the bucket ordering direction. The next vertex must come from the bucket
   whose label is lexicographically largest when compared with the OLDEST visited
   vertex first. Change the key to iterate `order` (not `reversed(order)`) and keep
   `reverse=True`, OR iterate `reversed(order)` and use `reverse=False`. Concretely:
   ```python
   def _label_key(b):
       return tuple(1 if x in b[0] else 0 for x in order)   # oldest first
   ...
   new_buckets.sort(key=_label_key, reverse=True)
   ```
   This makes the bucket adjacent to the earliest visited vertex sort first, which
   is the correct LexBFS refinement order.

2. Fix the intra-bucket pop order so ties are broken consistently (ascending vertex
   id, matching the initial `sorted(unvisited)` seeding). Replace
   ```python
   v = verts[0]
   verts[0] = verts[-1]
   verts.pop()
   ```
   with a plain `v = verts.pop(0)` (or keep the list sorted and pop(0)). This
   guarantees deterministic, ascending tie-break within a bucket.

3. After fixing the recompute, the fallback is correct, so the overall
   insert/delete logic (validate -> local fix -> recompute) becomes correct. The
   local-fix heuristics can stay as an optimization; they are only used when the
   current order is already invalid, and any failure falls through to the now-correct
   recompute.

Approaches that will NOT work:
- Keeping `reversed(order)` with `reverse=True` (current code) — this is the
  most-recent-first ordering and is fundamentally the wrong direction for LexBFS.
- Relying on `_try_local_fix` alone — its limited move set (swap / move-before /
  move-after of u or v) does not span all valid reorderings, so it cannot be the
  correctness backstop.
- Changing `_is_valid_lexbfs` — it is already correct; the bug is in the
  construction, not the check.
