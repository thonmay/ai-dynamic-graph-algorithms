## FAILURE_DESCRIPTION
- Operation: `init` (sequence_idx 0) on a 3-vertex undirected graph.
- Candidate returned ordering `[0, 1, 2]`; the checker expected `[0, 2, 1]`.
- Violation reported: a=0, b=1, c=2 at pos_a=0, minD=1000000000 (sentinel = no witness d found).
- The only graph consistent with the violation and the expected ordering is the path 1-0-2, i.e.
  adjacency matrix `[[0,1,1],[1,0,0],[1,0,0]]` (edges {0,1}, {0,2}, no edge {1,2}).
  - For `[0,1,2]`: a=0 (pos 0), b=1 (pos 1), c=2 (pos 2). ab=01 in E? No (0-1 is an edge... wait, in this matrix 0-1 IS an edge). Let me re-check: with edges {0,1},{0,2}: ab=01 in E -> the triple would be skipped, no violation. So the matrix must instead be edges {0,2} only plus... Actually the violation requires ab NOT in E and ac in E: a=0,b=1,c=2 needs 0-1 not in E and 0-2 in E. Expected `[0,2,1]` is valid for the graph with edges {0,2} and {1,2} (path 0-2-1): check `[0,1,2]` on it: ab=01 not in E, ac=02 in E, no d before a -> violation. And `[0,2,1]`: only triple a=0,b=2,c=1: ab=02 in E -> skip. Valid. So the graph is the path 0-2-1: matrix `[[0,0,1],[0,0,1],[1,1,0]]`.
- So: graph = path 0-2-1. Correct LexBFS from 0 is `[0,2,1]` (0's only neighbor is 2, so 2 must come second). Candidate produced `[0,1,2]`, which violates (LB) at (a,b,c)=(0,1,2).

## ROOT_CAUSE
The bug is in the "HMPV partition-refinement" loop used by both `_lexbfs_full` and `_lexbfs_canonical` (identical code). The docstring claims the surviving bucket `b` is "re-inserted at the FRONT of P and re-enqueued first in Q", but the code does neither:

```python
        newP = []
        if b:
            newP.append(b)
            Q.append(b)  # re-enqueue surviving bucket
        for b2 in P:
            if b2 is b:
                continue
            N = [x for x in b2 if graph[v][x]]
            Nc = [x for x in b2 if not graph[v][x]]
            if N:
                newP.append(N)
                Q.append(N)
            if Nc:
                newP.append(Nc)
                Q.append(Nc)
        P = newP
```

Two distinct defects:

1. **Wrong queue discipline (FIFO instead of LIFO).** HMPV LexBFS requires the surviving bucket to be processed *next* (stack/LIFO semantics: the bucket that just yielded a vertex keeps priority). Here `Q.append(b)` puts the surviving bucket at the *back* of the queue, behind all buckets created by the current refinement. This is a plain BFS queue, not the LexBFS priority rule.

2. **Wrong bucket order in P.** The surviving bucket is appended to the *front* of `newP` (that part matches the docstring), but the split buckets N, Nc are appended in the order N (neighbors) before Nc (non-neighbors). In HMPV, after refining a bucket by v, the non-neighbor part must come *before* the neighbor part (non-neighbors get lexicographically smaller labels). The code has `N` before `Nc` — reversed.

Trace on the failing graph (path 0-2-1, edges {0,2},{1,2}):
- P=[[0,1,2]], Q=[[0,1,2]]. Pop b=[0,1,2], v=0. b becomes [1,2].
- newP=[b]; refine no other buckets. P=[[1,2]], Q=[[1,2],[1,2]] (b enqueued once at back).
- Pop b=[1,2], v=1. b becomes [2]. No other buckets. P=[[2]], Q=[[2],[2]].
- Pop b=[2], v=2. order=[0,1,2].

Correct HMPV would give: after v=0, the only bucket is [1,2]; next v=1? No — with correct HMPV on this graph: start 0; refine [1,2] by 0: N=[2] (0-2 edge), Nc=[1]; order Nc before N -> P=[[1],[2]] with [1] first (non-neighbor before neighbor). Next vertex = 1? That gives [0,1,2]... but the checker says [0,2,1] is the valid one and [0,1,2] violates (LB). Re-examining: for path 0-2-1, LexBFS from 0: 0's neighbors = {2}. In LexBFS, after picking 0, the next vertex must be a neighbor of 0 (BFS layering): only 2. So order [0,2,1]. The partition-refinement rule "non-neighbors before neighbors" applies to *label refinement*, but the *next vertex chosen* comes from the front bucket of P, and the front bucket after the first step must be the neighbor part... Actually in HMPV, the initial bucket is refined by the first vertex v: the neighbor part N(v) is placed FIRST (front), because the next vertex must be adjacent to v. The "non-neighbor before neighbor" ordering applies when refining a bucket by a vertex that is NOT the one that just left it. So the correct rule: when refining bucket b2 by v, if b2 is the bucket v came from, N before Nc; for other buckets, Nc before N. The candidate applies N-before-Nc uniformly, and more fatally uses FIFO queue order, so the surviving bucket (which should be processed immediately) is delayed.

The exact divergence point: step 2, where v=1 is chosen from bucket [1,2] instead of v=2. In correct LexBFS, after v=0 the front bucket must be [2] (the neighbor of 0), so v=2 is chosen second. The FIFO re-enqueue + uniform N/Nc ordering produced [1,2] as the sole bucket with 1 at the front, so 1 was picked second — the first divergence.

Note: `_try_local_repair` and the fallback are irrelevant here — the failure is at `init`, which calls `_lexbfs_canonical` directly. The local-repair path also cannot save a wrong initial ordering, and its candidate set (single-vertex moves/swaps of the two endpoints) is far too small to be a general repair anyway.

## REPAIR_HINTS
1. **Fix the queue discipline in `_lexbfs_canonical` (and `_lexbfs_full`):** the surviving bucket `b` must be processed *immediately next*, i.e. use LIFO (stack) semantics: `Q.insert(0, b)` / `Q.append(b)` with `Q.pop()` from the back, or simply make Q a stack and push `b` last so it is popped first. The current `Q.append(b)` + `head`-pointer FIFO is the core bug.
2. **Fix the split-bucket ordering:** when refining a bucket b2 by vertex v, the neighbor part N must come before the non-neighbor part Nc ONLY when b2 is the bucket v was taken from; for all other buckets, Nc must come before N. The current code always appends N before Nc.
3. Simplest robust fix: replace both `_lexbfs_full` and `_lexbfs_canonical` with a known-correct HMPV implementation (e.g. the standard one from the HMPV paper / networkx `lexicographical_bfs`), verified against `_check_lb_property` on random graphs before use.
4. Will NOT work: keeping the FIFO queue and only swapping N/Nc order (the queue discipline alone breaks LexBFS on this 3-vertex case); keeping the current loop and relying on `_try_local_repair` (init has no repair path, and the repair candidate set is not complete).
5. Secondary: `_lexbfs_full` and `_lexbfs_canonical` are byte-identical; consolidate into one correct implementation to avoid divergence.
