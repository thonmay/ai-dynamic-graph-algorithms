## FAILURE_DESCRIPTION
n=3. Initial graph: only edge (1,2) (path 1-2, vertex 0 isolated). init() returns a valid LexBFS (e.g. [0,1,2]). Then `insert_edge(graph, (0,2), state)` adds edge 0-2, making the graph the path 1-0-2. The candidate returned `[0, 1, 2]`; the expected (valid) ordering is `[0, 2, 1]`.

The returned ordering violates the (LB) 4-point property at positions a=0, b=1, c=2 (vertices 0,1,2): ac = 0-2 is in E, ab = 0-1 is not in E, but no d < a exists (a is the first position), so minD stays at the sentinel 1000000000. In a valid LexBFS of this graph, vertex 2 (adjacent to 0) must come before vertex 1 (not adjacent to 0) once 0 is first.

## ROOT_CAUSE
The divergence happens in `insert_edge` -> `_try_repair`. The old ordering `[0,1,2]` is invalid after the insertion, and `_try_repair` builds only three candidates:
1. swap u,v -> `[2,1,0]`
2. move u (0) to just after v (2) -> `[1,2,0]`
3. move v (2) to just after u (0) -> `[0,2,1]`

Candidate 3 is in fact the correct answer, but `_is_lexbfs([0,2,1], graph)` returns False, so `_try_repair` returns None and `_recompute` is called. `_recompute` then returns `_lexbfs(graph)` = `[0,1,2]` because `_is_lexbfs([0,1,2], graph)` also (wrongly) returns True.

The bug is in `_is_lexbfs` (the (LB) checker). Its loop is:

```python
for j in range(n):
    b = ordering[j]
    mask_lt_j = (1 << j) - 1
    for k in range(j + 1, n):
        c = ordering[k]
        if adj[b] >> c & 1:
            continue  # bc in E, no constraint
        bad = posset[c] & mask_lt_j
        ...
```

It iterates over pairs (j,k) with j<k and treats them as (b,c) = (ordering[j], ordering[k]), i.e. it only ever checks the case where the non-edge is between the EARLIER and MIDDLE positions (ab not in E with a<b<c). The (LB) property, however, requires the check for the case where the non-edge is between the MIDDLE and LAST positions: for all a < b < c with **bc not in E** and **ac in E**, there must exist d < a with db in E and dc not in E. The candidate's own comment block ("For positions j < k: b = ordering[j], c = ordering[k]. if bc not in E: ...") describes the correct (b,c) = (middle,last) formulation, but the code implements the wrong one.

Consequences, verified by hand on the failing case:
- For `[0,1,2]` on graph {0-2, 1-2}: the only (j,k) pair with a non-edge is (j=0,k=1) (0-1 not in E); there bad = posset[1] & mask_lt(0) = 0, so the check is vacuous and `_is_lexbfs` returns True for an INVALID ordering. The real violation (a=0,b=1,c=2: bc=1-2 in E, ac=0-2 in E, ab=0-1 not in E, no d<a) is never examined.
- For the valid ordering `[0,2,1]`: the real (LB) triple is a=0,b=2,c=1 (bc=2-1 in E, ac=0-1 not in E, ab=0-2 in E, no d<a) — this is a genuine violation of the property as stated in the brief, and the code's (j,k)=(0,1) check (b=0,c=2, bc in E -> skip) misses it, so the valid ordering is also rejected.

So the validator is wrong in both directions: it accepts invalid orderings and rejects valid ones. This breaks both the repair gate (rejects the correct `[0,2,1]`) and the `_recompute` fallback (accepts the invalid `[0,1,2]` from `_lexbfs` instead of falling back to `_lexbfs_simple`, which would have produced the correct `[0,2,1]`).

Note: the (LB) formulation in the brief ("for all a<b<c with ac in E and ab not in E, exists d<a with db in E and dc not in E") is itself suspect — on the failing graph it is violated by the expected answer `[0,2,1]` (triple a=0,b=2,c=1). The verifier's reported violation (a=0,b=1,c=2, minD=inf) matches the standard Corneil-Krueger (LB) property: for all a<b<c with **bc in E and ac not in E**, exists d<a with **dc in E and db not in E**. The candidate's `_is_lexbfs` implements neither correctly.

## REPAIR_HINTS
1. Rewrite `_is_lexbfs` to implement the standard (LB) property exactly as the verifier checks it: for all positions a < b < c with bc in E and ac not in E, require some d < a with dc in E and db not in E. In the existing bitset style, iterate (a,c) with a<c and ac not in E, let `bad = posset[c] & mask_lt(a)` (positions d<a with dc in E); if bad != 0, require `T = posset[a] & ~posset[c]` (positions d with da in E, dc not in E) to have min(T) < min(bad). The current code's variable naming (b=ordering[j], c=ordering[k]) and the `if adj[b] >> c & 1: continue` skip are the wrong pair orientation and must be replaced, not patched.
2. Before trusting any validator, cross-check it against `_lexbfs_simple` (the straightforward O(n^2) LexBFS, which is correct) on random small graphs: `_is_lexbfs(_lexbfs_simple(g), g)` must be True, and `_is_lexbfs` must reject known-bad permutations. The current validator fails both directions, so any "verified" repair or recompute result is untrustworthy until this is fixed.
3. Do NOT try to fix this by adding more candidates to `_try_repair` or by changing `_lexbfs`: the repair gate and the recompute fallback both route through the broken `_is_lexbfs`, so they will keep accepting invalid orderings (as happened here: `_recompute` returned the invalid `[0,1,2]` instead of falling back to `_lexbfs_simple`).
4. Also resolve the property-statement mismatch: the brief's (LB) wording (ac in E, ab not in E) contradicts the verifier's behavior on this case; implement the verifier's property (bc in E, ac not in E) and confirm with a brute-force checker that enumerates all triples and all d.
