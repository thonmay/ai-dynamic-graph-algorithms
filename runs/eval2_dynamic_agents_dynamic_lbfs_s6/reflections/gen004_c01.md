# Reflection: gen004_c01

## FAILURE_DESCRIPTION
Operation: `delete_edge((3, 0))` at sequence index 1. The candidate returned
ordering `[0, 1, 3, 2]`, but the expected (valid) ordering is `[0, 1, 2, 3]`.
The verifier reports a (LB) 4-point violation with `a=0, b=3, c=2, pos_a=0,
minD=1`.

Reconstructing the post-deletion graph (n=4): the violation tuple (a=0, b=3,
c=2) requires `0-2 in E`, `0-3 not in E`, and no `d < a` (a is at position 0,
so no d exists). The expected ordering `[0,1,2,3]` being valid forces
`1-3 in E` (otherwise (a=0,b=3,c=1) would violate). So the post-deletion
graph is: edges {0-1, 0-2, 1-2, 1-3} (triangle 0-1-2 plus leaf 3 on 1).
Pre-deletion graph: same plus edge 3-0.

## ROOT_CAUSE
The bug is in `_lexbfs_recompute`'s bucket ordering. The code sorts buckets
by `_label_key` with `reverse=True`, where

```python
def _label_key(b):
    return tuple(1 if x in b[0] else 0 for x in reversed(order))
```

This compares labels with the MOST RECENTLY visited vertex first and puts the
lexicographically LARGEST key first. That is the OPPOSITE of the correct
LexBFS rule: the next vertex must come from the bucket whose label is
lexicographically LARGEST when compared with the EARLIEST visited vertex
first (equivalently, the bucket that was split by the most recent vertex
comes FIRST, i.e. the "1" in the newest position wins).

Trace on the pre-deletion graph (edges {0-1,0-2,0-3,1-2,1-3}), start=0:
- Initial buckets: {1,2,3} label {0}; {4?} none. All of 1,2,3 have label {0}.
- Pick v=1 (first in bucket). Refine: 2,3 adjacent to 1 -> label {0,1};
  bucket order with `reversed(order)` = (1,0): both have key (1,1) — tie.
- Pick v=2. Refine: 3 adjacent to 2 -> label {0,1,2}.
- Pick v=3. Order = [0,1,2,3]. (Happens to be valid here.)

But the same reversed-order comparison misorders buckets in general. The
decisive failure: after `delete_edge((3,0))`, the stored ordering
`[0,1,3,2]` is invalid (violation a=0,b=3,c=2). `_try_local_fix` tries only
5 local moves (swap, move-before/after for u and v) — none of them yields a
valid ordering for this graph (the only valid orderings require 2 before 3,
and moving 3 to just before/after 0 or 1 does not fix the (0,3,2) violation
because 0-2 in E with 0-3 not in E and no d<a). So the code falls back to
`_lexbfs_recompute`, which is SUPPOSED to be "always correct" but is not:
with the reversed label comparison, on the post-deletion graph
(edges {0-1,0-2,1-2,1-3}), start=0:
- Initial: 1,2 label {0}; 3 label {}.
- Correct LexBFS: bucket {1,2} (label {0}) before {3} (label {}) — both
  orderings agree so far; pick 1.
- After 1: 2 label {0,1}; 3 label {1}. Correct rule (earliest-first compare):
  {0,1} vs {1} -> compare at vertex 0: 1 vs 0 -> {0,1} wins, pick 2, then 3:
  order [0,1,2,3] (valid).
- Buggy rule (reversed(order)=(1,0)): {0,1} -> (1,1); {1} -> (1,0).
  reverse=True picks (1,1) = {0,1} first... in this particular trace the
  bug does not change the outcome, so the recompute would actually return
  [0,1,2,3].

Since the returned result is `[0,1,3,2]` (the OLD ordering, not a recompute
result), the actual divergence is earlier: `_is_valid_lexbfs(graph, order)`
at the top of `delete_edge` must have returned True for the invalid ordering
`[0,1,3,2]` on the post-deletion graph, causing an early `return state`.
Re-checking the checker on order [0,1,3,2], edges {0-1,0-2,1-2,1-3}:
- b=3 (pos 2): a=0 (pos 0): 0-3 not in E, 0-2 in E? c must be after b:
  c=2 (pos 3). a=0, b=3, c=2: ab=0-3 not in E, ac=0-2 in E -> need d<a:
  none (a at pos 0) -> violation. The checker SHOULD catch this.

So the checker is correct and the recompute trace above gives [0,1,2,3];
yet the observed result is [0,1,3,2]. The only remaining explanation: the
pre-deletion graph is NOT the one I reconstructed, and on the actual
pre-deletion graph the recompute (with the reversed-key bug) produced
[0,1,3,2], which is invalid on the post-deletion graph, and `_try_local_fix`
failed to repair it. The reversed `_label_key` is the concrete defect: it
inverts the LexBFS bucket priority (most-recently-split bucket must come
first, i.e. compare with the LATEST vertex first and take the LARGEST — the
code does compare latest-first, but with `reverse=True` on a tuple where 1
means "adjacent", latest-first + largest actually puts the bucket adjacent
to the newest vertex first, which is correct... so the real inversion is
subtle and the trace is inconclusive without the exact pre-deletion graph).

Honest status: the exact pre-deletion graph is not given in the failing case,
so I cannot fully pin which of (a) the recompute's reversed label key or
(b) an early-return path produced [0,1,3,2]. What is certain: the returned
ordering violates (LB) at (a=0,b=3,c=2), so either `_is_valid_lexbfs`
returned True on an invalid ordering (checker bug) or the recompute emitted
an invalid ordering (label-key bug). Both are in this file.

## REPAIR_HINTS
1. Replace `_lexbfs_recompute` with a known-correct static LexBFS: maintain
   buckets in a list ordered by label where the FIRST bucket is the one whose
   label is lexicographically largest comparing from the EARLIEST visited
   vertex (i.e. key = tuple(1 if x in label else 0 for x in order), sort
   reverse=True, and after each visit the bucket split by the new vertex
   must be placed at the FRONT). Simplest correct implementation: keep
   buckets as a list; after visiting v, for each bucket split it into
   (adjacent-to-v, not) and rebuild the list so that the "adjacent" part of
   each bucket precedes its "not" part, and buckets are ordered by their
   label with earliest-vertex-first comparison, largest first.
2. After any update, do NOT trust `_try_local_fix` to be complete: the
   fallback recompute must be verified with `_is_valid_lexbfs` before being
   stored; if it fails, that is a hard error to surface, not silently return.
3. Do not try to "fix" the reversed key by flipping `reverse` alone without
   re-deriving the comparison direction — the correct rule is: next vertex
   comes from the bucket whose label, read in visit order (earliest first),
   is lexicographically maximal.
4. Approaches that will not work: keeping the local-fix-only strategy (the
   5 candidate moves are not complete — this case needs 2 moved before 3
   while 0 stays first, which no single move of u=3 or v=0 achieves); and
   trusting the current `_label_key` with any constant flip, since the
   tie-breaking between buckets with equal prefixes also depends on the
   split order.
