## ROOT_CAUSE
In `_lexbfs_canonical` (and `_lexbfs_full`, `_lexbfs_canonical2`), when a bucket `b2` in P is refined into `N` and `Nc`, new list objects are created and appended to Q, but the OLD list object `b2` (which may still be in Q from a prior enqueue) is NOT removed from Q. This violates the invariant that each non-empty bucket appears in Q exactly once.

Concretely, in the trace above:
- Iter 1: Nc_b=[2] is created and enqueued at Q[2].
- Iter 2: bucket [2] (at P[1]) is refined, creating a NEW list [2] enqueued at Q[3]. The old [2] at Q[2] is still in Q.
- Iter 3: Q[2] (old [2]) is processed, vertex 2 is extracted, old list is emptied.
- Iter 4: Q[3] (new [2]) is still non-empty, vertex 2 is extracted AGAIN.

This causes duplicate vertices in `order` and can lead to non-termination (the loop processes more than n vertices, and the partition P may not become empty in the expected way).

The responsible lines in `_lexbfs_canonical`:
```python
for b2 in P:
    if b2 is b:
        continue
    N = [x for x in b2 if graph[v][x]]
    Nc = [x for x in b2 if not graph[v][x]]
    if N:
        newP.append(N)
        Q.append(N)      # NEW list enqueued, but b2 (old list) may still be in Q
    if Nc:
        newP.append(Nc)
        Q.append(Nc)     # same problem
```

The fix requires either:
1. Mutating `b2` in place (clearing it and reusing it as N or Nc), so the Q reference remains valid.
2. Or tracking which Q entries are stale and skipping them (e.g., by checking if the bucket is still in P).

## REPAIR_HINTS
The partition-refinement LexBFS must maintain the invariant that each non-empty bucket in P has exactly one entry in Q. The current code breaks this by creating new list objects for refined buckets without invalidating the old Q entries.

**Smallest fix:** Instead of creating new lists N and Nc, mutate the existing bucket list in place. For each bucket b2 being refined:
1. Partition b2's contents into neighbor and non-neighbor lists.
2. Clear b2 and extend it with the neighbor portion (so b2 becomes N).
3. Create a new list for Nc and insert it into P right after b2's position.
4. Enqueue only the new Nc list in Q (b2 is already in Q).

Alternatively, use a "generation" or "version" counter: each bucket has a version number, and Q entries store (bucket, version). When a bucket is refined, its version is incremented, and stale Q entries (with old versions) are skipped.

**Approaches that will NOT work:**
- Simply checking `if not b: continue` at the top of the loop (already present) — this doesn't help because the duplicate bucket is non-empty when processed.
- Deduplicating Q before processing — Q can contain the same vertex in different list objects, so dedup by identity won't catch it.
- The local repair and fallback logic in `insert_edge`/`delete_edge` is fine; the bug is entirely in the static LexBFS recompute functions.

All three static LexBFS functions (`_lexbfs_full`, `_lexbfs_canonical`, `_lexbfs_canonical2`) have the same bug and need the same fix. Since `init` and the fallback both call `_lexbfs_canonical`, fixing that one function is sufficient to resolve the timeout.
