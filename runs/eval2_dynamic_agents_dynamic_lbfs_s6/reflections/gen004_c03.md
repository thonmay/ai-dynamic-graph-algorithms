## FAILURE_DESCRIPTION

3-vertex graph, operation `insert (0, 1)` at sequence index 0.
- Graph BEFORE the update: edge (0,1) absent, edge (0,2) present (the
  verifier's violation witness uses `ac in E` with a=0, c=1, i.e. 0-2 in E).
  So pre-update graph = {0-2} only.
- Graph AFTER the update: {0-1, 0-2} (a path 1-0-2).
- Expected valid LexBFS ordering: `[0, 1, 2]`.
- Actual returned ordering: `[0, 2, 1]`.
- Verifier's (LB) violation: a=0, b=2, c=1, pos_a=0, minD=1000000000
  (no witness d found). In the returned ordering, positions are
  pos(0)=0, pos(2)=1, pos(1)=2. The triple (a=0, b=2, c=1) has
  ac=0-2 in E, ab=0-1 in E... wait — the verifier reports this as a
  violation with no witness d, meaning in the verifier's reading
  `ab not in E` and `ac in E`. Either way, `[0, 2, 1]` is not a valid
  LexBFS ordering of {0-1, 0-2}: the only valid orderings are
  `[0, 1, 2]` and `[0, 2, 1]`? No — check: for `[0,2,1]`, labels are
  L(0)=11, L(2)=10, L(1)=10. At position 1, L(2)=10 vs L(1)=10 tie,
  but L(0)=11 > L(2)=10 at position 1 (bit 1: L(0) has 1, L(2) has 0),
  so 0's label is NOT <= 2's label lexicographically. Hence `[0,2,1]`
  is invalid; `[0,1,2]` (L(0)=11, L(1)=10, L(2)=10) is valid.

## ROOT_CAUSE

The candidate's "cheap local repair" path accepted an invalid ordering.
`insert_edge` calls `_try_repair(graph, ordering, edge)` and returns the
first candidate that passes BOTH `_is_lexbfs` and `_valid_lexbfs`. The
bug is that **both validators are wrong**, so the invalid candidate
`[0, 2, 1]` slips through.

1. `_valid_lexbfs` (the pairwise label check) is subtly broken. It
   computes `posset[x]` as a bitset over *positions* (bit p = 1 iff
   `ordering[p]` is adjacent to x) — that part is correct. But the
   lexicographic comparison of two labels must compare from position 0
   upward, and "smaller" means: at the first differing position, the
   smaller label has a **0** and the larger has a **1** (LexBFS picks
   the lexicographically smallest label, where labels are compared as
   bitstrings with 0 < 1). The code does:
   ```
   first = (diff & -diff).bit_length() - 1
   if not (li >> first & 1):
       return False
   ```
   i.e. it requires `li` (the EARLIER vertex's label) to have a 1 at the
   first differing position. That is the OPPOSITE of the correct
   condition: for a valid LexBFS ordering, the earlier vertex must have
   the SMALLER label, so at the first differing position `li` must have
   0 and `lj` must have 1. The check is inverted. For `[0,2,1]` on
   {0-1,0-2}: li=L(0)=11, lj=L(2)=10, first diff at bit 1, li has 1
   there → the (inverted) check passes, so `_valid_lexbfs` wrongly
   returns True.

2. `_is_lexbfs` (the (LB) 4-point check) is also wrong. The (LB)
   property is: for all positions a < b < c with ac in E and ab not in
   E, there exists d < a with db in E and dc not in E. The code iterates
   `j` (as b) and `k` (as c) and checks, when bc not in E, that
   `min(T) < min(bad)` where `bad` = positions i < j with ordering[i]
   adjacent to c, and T = positions d < j with ordering[d] in N_b \ N_c.
   This is a mangled restatement: it uses j (position of b) as the
   "a < b < c" middle index and conflates the roles of a, b, c. The
   correct check must, for each triple of positions a < b < c with
   ac in E and ab not in E, verify existence of d < a with db in E and
   dc not in E. The code's `min_T < min_bad` heuristic does not encode
   that. For the failing case it also returns True for `[0,2,1]`.

Because both validators are broken in the same direction (both accept
`[0,2,1]`), `_try_repair` returns the invalid swap/move candidate and
`insert_edge` never falls back to `_recompute` (which would have
produced the correct `[0,1,2]`).

Note: `_recompute` itself is fine — `_lexbfs_simple` is textbook-correct
and would return `[0,1,2]` for {0-1,0-2}. The failure is entirely in
the repair path's acceptance test.

## REPAIR_HINTS

Smallest fix: make the validators actually correct, so the repair path
can only accept genuinely valid orderings.

1. Fix `_valid_lexbfs`: invert the comparison. At the first differing
   position `first` between `li` (earlier vertex) and `lj` (later
   vertex), a valid LexBFS ordering requires `li` to have 0 and `lj` to
   have 1 (earlier = lexicographically smaller label, 0 < 1). Change
   ```
   if not (li >> first & 1):
       return False
   ```
   to
   ```
   if (li >> first & 1) or not (lj >> first & 1):
       return False
   ```
   (equivalently: `li` must be 0 and `lj` must be 1 at `first`).
   This single check, applied to all pairs i < j, is a complete
   certificate of LexBFS validity (the ordering is a LexBFS ordering
   iff every earlier vertex's label is lexicographically <= every later
   vertex's label).

2. Fix `_is_lexbfs` to implement the (LB) property literally: iterate
   positions a < b < c; if ac in E and ab not in E, require some
   d < a with db in E and dc not in E. The current `min_T < min_bad`
   formulation is not equivalent and should be replaced. (Alternatively,
   drop `_is_lexbfs` entirely and rely on the corrected
   `_valid_lexbfs` alone — the pairwise label check is a complete
   certificate, so one correct validator is sufficient.)

3. Do NOT try to "fix" `_try_repair`'s candidate generation (swap /
   move-to-adjacent) — its search space is fine; the problem is purely
   that the acceptance test accepts invalid orderings. Once the
   validator is correct, the repair will correctly return None for
   `[0,2,1]` and `insert_edge` will fall back to `_recompute`,
   producing `[0,1,2]`.

Approaches that will not work:
- Keeping the inverted `_valid_lexbfs` and adding more candidate
  permutations to `_try_repair`: the inverted check will keep accepting
  invalid orderings, so more candidates only increases the chance of
  returning a wrong one.
- Relying on `_is_lexbfs` alone without fixing it: its `min_T < min_bad`
  logic is not a correct (LB) check and will also accept invalid
  orderings.
