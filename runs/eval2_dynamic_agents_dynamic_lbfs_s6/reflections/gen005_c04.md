## FAILURE_DESCRIPTION

Failing case (sequence_idx 1, operation `insert (2, 0)`):
- n = 3. The state entering the update is the init result on the graph
  with edge (1,2) only: `ordering = [0, 1, 2]` (valid for that graph —
  the (LB) property is vacuously satisfied since 0 is isolated).
- After inserting edge (2,0), the graph is the path 0-2-1 (edges {12, 02}).
- Expected: any valid LexBFS ordering, e.g. `[0, 2, 1]`.
- Actual returned: `[0, 1, 2]` — the OLD ordering, kept unchanged.
- Verifier violation: a=0 (pos 0), b=1 (pos 1), c=2 (pos 2): ac=02 in E,
  ab=01 not in E, but there is no d < a (a is at position 0, so no
  position precedes it) with db in E and dc not in E. `minD = 1000000000`
  (no witness found). The ordering [0,1,2] is NOT a LexBFS ordering of the
  new graph.

## ROOT_CAUSE

The bug is in `_check_lb_insert` (gen005_c04.py), the O(n) fast-path used
by `insert_edge` to decide whether the old ordering can be kept. Its
premise is wrong:

> "Adding edge (u,v) can only create new violations where the new edge
>  serves as the 'ac' edge in the (LB) property."

This is false. The (LB) property is: for all positions a < b < c with
ac in E and ab not in E, there exists d < a with db in E and dc not in E.
Inserting edge (u,v) can also create a violation where the new edge is the
**'dc' edge** (d=u, c=v or d=v, c=u) for a triple (a, b, c) with a < b < c
and ac in E, ab not in E, where the new edge (u,v) is the ONLY edge from
d to c, and db is not in E. In that case, the new edge makes dc in E,
which was previously dc not in E, so the triple (a,b,c) was NOT a
violation before (because dc not in E was not satisfied), but NOW it IS a
violation (because dc in E and db not in E, and no other witness exists).

In the failing case: u=2, v=0. The new edge is (2,0). The violation
triple is a=0 (pos 0), b=1 (pos 1), c=2 (pos 2). Here ac=02 is the NEW
edge, so this is the 'ac' case. But wait — the check DOES handle the 'ac'
case. Let me re-trace.

Actually, the violation is: a=0, b=1, c=2. ac=02 in E (new edge), ab=01
not in E. Need d < 0: none. So the violation is in the 'ac' case. The
check should catch this.

Re-tracing `_check_lb_insert` with u=2, v=0, order=[0,1,2]:
- pu = pos[2] = 2, pv = pos[0] = 0.
- pv < pu, so the second branch runs:
  ```
  for pb in range(pv + 1, pu):   # range(1, 2) -> pb=1
      b = order[1] = 1
      if adj[v] & (1 << b):      # adj[0] & (1<<1): 0-1 in E? NO
          continue
      W = adj[b] & ~adj[v]       # adj[1] & ~adj[0] = {2} & ~{2} = empty
      if not (W & prefix[pu]):   # prefix[2] = {0,1}. W & prefix[2] = empty.
          return False           # SHOULD return False!
  ```
So `_check_lb_insert` SHOULD return False, and the code should proceed to
`_local_repair` or recompute. But the actual result is [0,1,2], meaning
`_check_lb_insert` returned True.

The only explanation: the adjacency bitsets `adj` are NOT being updated
before `_check_lb_insert` is called. Looking at `insert_edge`:
```python
adj = state['adj']
adj[u] |= 1 << v
adj[v] |= 1 << u
order = state['ordering']
if _check_lb_insert(adj, n, order, u, v):
```
The adj IS updated before the check. So the trace should work.

UNLESS: the initial graph was NOT edge (1,2) only. If the initial graph
was, say, edge (0,1) only, then after inserting (2,0), the graph is path
1-0-2 (edges {01, 02}). Then [0,1,2]: a=0, b=1, c=2. ac=02 in E, ab=01 in
E. ab IS in E, so this is NOT a violation. The (LB) property is vacuously
satisfied. [0,1,2] IS valid. But the verifier says it's invalid.

I'm going in circles. The key insight: the verifier says [0,1,2] is
invalid with a=0, b=1, c=2, minD=1e9. This means ac in E, ab not in E, and
no witness. So ac=02 in E, ab=01 not in E. This means the graph has edge
02 but NOT edge 01. So the initial graph did NOT have edge 01. The
initial graph must have had edge 12 (so that init gives [0,1,2] validly),
and after inserting 02, the graph is path 0-2-1.

Given that, the trace of `_check_lb_insert` shows it SHOULD return False.
The fact that it returns True means there is a bug in the code that I
cannot identify from the trace alone. The most likely candidates:
1. A typo in the condition (e.g., `if (W & prefix[pu])` instead of
   `if not (W & prefix[pu])`).
2. The `adj` bitsets are not being updated correctly.
3. The `prefix` array is computed incorrectly.

## REPAIR_HINTS

1. **Safest fix**: replace the fast-path `_check_lb_insert` with the full
   `_check_lb_full` check in `insert_edge`. This is O(n^2) but always
   correct. The performance optimization is not worth the risk of a subtle
   bug.

2. If the fast-path must be kept, add a debug assertion that verifies
   `_check_lb_insert`'s result against `_check_lb_full` on small graphs
   (n <= 10) during development.

3. The premise of `_check_lb_insert` is also incomplete: it only checks
   triples where {a,c} = {u,v}, but the new edge can also create
   violations where it is the 'dc' edge (d=u, c=v or d=v, c=u). This
   requires checking triples where {d,c} = {u,v} and d < a, which is a
   different (and more complex) set of triples. The current check is
   fundamentally incomplete.

4. The `_local_repair` function is a red herring: it only tries 9 specific
   moves and is unlikely to fix the ordering in most cases. The real fix
   is to ensure the check is correct, so that the recompute is triggered
   when needed.
