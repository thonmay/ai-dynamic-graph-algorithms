## FAILURE_DESCRIPTION
n=3. The failing operation is `delete (1, 2)` at sequence index 0, i.e. the very first update after `init`. The graph after the deletion is the single edge (0,1) (edges: 0-1 only; 0-2 and 1-2 absent). The candidate returned ordering `[2, 1, 0]`, but the only valid LexBFS orderings of this graph are `[0, 1, 2]` and `[1, 0, 2]` (the isolated vertex 2 must come last). The verifier reports the (LB) violation with a=2 (pos 0), b=1 (pos 1), c=0 (pos 2): ac=2-0 is NOT an edge, ab=2-1 is NOT an edge, and no witness d exists before a (minD = 10^9 sentinel).

## ROOT_CAUSE
The divergence is in `_check_lb_delete`. It is called from `delete_edge` with the **already-updated** adjacency bitsets (the edge (1,2) has been cleared from `adj` before the check runs), but the function's logic is written for the **pre-deletion** adjacency:

- It computes `S1 = adj[u] & ~adj[v]` and `S2 = adj[v] & ~adj[u]` using the post-deletion `adj`. With u=1, v=2 after the deletion: `adj[1] = {0}`, `adj[2] = {}`, so `S1 = {0}`, `S2 = {}`. The inner loop over `S2` never executes, and the function returns `True` — the old ordering `[2, 1, 0]` is kept.
- The intended affected set (per the docstring: "b adj u, c not adj u, b not adj v, c adj v") requires `c` to be adjacent to `v`, which is only true **before** the deletion. After the deletion, `c` is no longer adjacent to `v`, so the affected pairs are invisible to the check.
- The same post-deletion `adj` is then used for `A = prefix[pb] & ~adjb & adj[c]` and `W = adjb & ~adj[c] & ~(1<<u) & ~(1<<v)`, which is inconsistent with the pre-deletion reasoning in the comments.

Because the check wrongly returns `True`, `delete_edge` returns the stale ordering `[2, 1, 0]` without ever reaching `_local_repair` or the `_lexbfs` fallback. (Note: `_local_repair` would also have failed here — none of its 9 candidates is a valid ordering for this graph — but the fallback recompute would have produced a valid one, so the only real defect is the false-positive check.)

## REPAIR_HINTS
Smallest fix: in `delete_edge`, call `_check_lb_delete` **before** clearing the edge from `adj` (i.e. pass the pre-deletion adjacency), then clear the edge. Equivalently, inside `_check_lb_delete`, restore the edge first (`adj[u] |= 1 << v; adj[v] |= 1 << u`) at the top so that `S1`, `S2`, `A` and `W` are all computed with the pre-deletion adjacency, matching the docstring's reasoning. With the pre-deletion adjacency (edges 0-1, 1-2), the check correctly finds S1={0}, S2={0}, pair (b=0, c=0) has A empty, and — crucially — the pair where the deleted edge was the only witness is caught, so the check returns `False` and the fallback recompute runs.

Do NOT try to "fix" this by making `_check_lb_delete` more conservative (e.g. always return False) — that just turns every deletion into a recompute and defeats the purpose of the O(n) check. Do NOT rely on `_local_repair` as the safety net: its candidate set (swap/move u or v to front/back/next to the other) is not complete; in this very case no candidate is valid, so a false-positive check that skips the recompute is fatal. The check must be sound (never return True for an invalid ordering) — the cleanest way is to evaluate it on the pre-update graph state.
