## FAILURE_DESCRIPTION
n=3. After some prior updates the state held ordering [2, 0, 1] (valid for the
pre-deletion graph). Operation: `delete_edge(graph, (0, 2), state)`. The
post-deletion graph has only edge (0,1) (adj: 0~1, 2 isolated). The candidate
returned [2, 0, 1] unchanged. Expected: any valid LexBFS ordering, e.g.
[0, 1, 2]. The returned ordering violates (LB) at a=2 (pos 0), b=0 (pos 1),
c=1 (pos 2): ac=2-1 is NOT an edge, ab=2-0 is NOT an edge, and there is no
d < a (a is first) — the verifier reports minD = 1e9 (no witness).

## ROOT_CAUSE
`_check_lb_delete` (the O(n) deletion check) is unsound: it only re-checks
triples (a,b,c) whose witness set W = N(b)\N(c) could have lost u or v, i.e.
triples where b or c lies in N(u)\N(v) or N(v)\N(u), plus the b=u / b=v /
c=u / c=v cases (Cases 1-8). It never re-checks triples where the *deleted
edge itself* was the 'ac' edge, i.e. {a,c} = {u,v}.

In this case the deleted edge is (0,2) = (u,v). The violating triple is
a=2, b=0, c=1: here {a,c} = {2,1} does not contain u=0 or v=2 in the
(a,c) slot... wait, a=2 IS v. Let me restate precisely: the triple is
a=2 (pos 0), b=0 (pos 1), c=1 (pos 2). The deleted edge (0,2) connects
b=0 and a=2. Before deletion, edge a-b = 2-0 existed, so the triple was not
a (LB) candidate at all (requires ab not in E). After deletion, ab is no
longer an edge, so the triple becomes a candidate, and it needs a witness
d < a with db in E and dc not in E — but a is at position 0, so no witness
can exist.

The deletion check's premise ("removing edge (u,v) can only destroy
witnesss") is wrong: deleting an edge can also *create* new (a,b,c)
candidates by removing the 'ab' edge (or the 'dc' edge of a witness
condition, or the 'ac' edge — though removing ac only helps). Specifically,
when the deleted edge is the 'ab' edge of a triple, that triple was
previously exempt (ab in E) and becomes a new obligation with no guaranteed
witness. `_check_lb_delete` has no case for "deleted edge = ab", so it
returns True, `delete_edge` keeps the stale ordering, and the invalid
ordering is returned.

Responsible lines: the entire case enumeration in `_check_lb_delete`
(Cases 1-8) — none of them considers triples where the deleted edge is the
ab edge (b = u or b = v with a in N(u)\N(v) or N(v)\N(u), c arbitrary after
b). Note Cases 3/4/5/6/7/8 only cover b=u or b=v with c restricted to
S1/S2 or c=u/v; they do not cover b=u with arbitrary c (or b=v with
arbitrary c), which is exactly what is needed when the deleted edge is ab.

## REPAIR_HINTS
Smallest fix: in `delete_edge`, when `_check_lb_delete` returns False OR
more robustly, add the missing case to `_check_lb_delete`: for b = u (and
symmetrically b = v), iterate ALL c with pos[c] > pos[b] (not just c in
S1/S2 or c = the other endpoint), compute A = prefix[pb] & ~adj[b] & adj[c]
and W = adj[b] & ~adj[c] (with the deleted edge already removed from adj,
so W is correct), and require a witness in prefix[min_pos(A)]. This covers
triples where the deleted edge was the ab edge.

Even simpler and safer: make the deletion check conservative — if the
deleted edge (u,v) is the ab edge of any triple, just fall through to
`_local_repair` / full recompute. Concretely, in `delete_edge`, before
trusting `_check_lb_delete`, also run the insertion-style check with roles
swapped: after deletion, the new obligations are exactly the triples where
the deleted edge was ab (b=u or b=v, a on the other side, c after b) —
check those O(n) triples directly (same loop shape as `_check_lb_insert`
but with the edge removed). If any fails, go to repair/recompute.

Approaches that will NOT work:
- Relying on `_local_repair` alone: it only moves u or v, but here the
  invalid ordering [2,0,1] needs 2 moved after 0 (or 0/1 reordered); the
  repair candidates (swap 0/2, move 0 or 2 next to the other, to front/back)
  do include [0,2,1] and [2,1,0] etc. — actually some may pass, but the
  check never even calls repair because `_check_lb_delete` returns True.
  The bug is the check, not the repair.
- "Fixing" by always recomputing on deletion: correct but abandons the
  O(n) check goal; acceptable as a fallback but the targeted fix above is
  smaller.
- Symmetric argument for insertions: `_check_lb_insert` is sound (adding an
  edge only creates obligations where the new edge is ac, which it checks),
  so do not "fix" it by symmetry.
