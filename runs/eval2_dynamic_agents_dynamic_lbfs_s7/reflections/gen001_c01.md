## FAILURE_DESCRIPTION
Initial graph: 3 vertices, no edges (all-zero 3x3 matrix). `init` returns `[0, 1, 2]` (valid for the empty graph). Then `insert_edge(graph, (0, 2), state)` is called on the graph with edge 0-2 present. The candidate returns `[0, 1, 2]`, but the expected (and only valid) LexBFS ordering is `[0, 2, 1]`.

The verifier reports the (LB) 4-point property violation at positions a=0, b=1, c=2 (pos_a=0, minD=10^9 = sentinel meaning no witness d exists): in the returned ordering, vertex 0 (pos 0) is adjacent to vertex 2 (pos 2) but not to vertex 1 (pos 1), and there is no d < 0 that could witness the property. Indeed, in the graph with only edge 0-2, the only valid LexBFS orderings are `[0, 2, 1]` and `[2, 0, 1]` (start 0 forces 2 before 1; start 2 forces 0 before 1; start 1 is impossible since 1 is isolated and must come last).

## ROOT_CAUSE
The bug is in `_lexbfs`: the partition-refinement step refines **all** buckets, including the one the just-selected vertex `v` was taken from.

```python
        v = min(buckets[bi], key=lambda x: (rank[x], x))
        buckets[bi].remove(v)
        order.append(v)
        processed[v] = True

        # refine all buckets by adjacency to v
        new_buckets = []
        for b in buckets:
            ...
```

In the failing trace (graph = only edge 0-2, start=0, rank=[0,1,2]):
- Initial buckets: `[[1, 2]]`.
- Iteration 1: `v = 1` (min by (rank,id) in the single bucket). Refine by adjacency to 1: 1 is isolated, so `nb = []`, `nb2 = [2]` — no split, buckets stay `[[2]]`.
- Iteration 2: `v = 2`. Order = `[0, 1, 2]`.

The correct LexBFS behavior: after processing start vertex 0, the **remaining** vertices must be split by adjacency to 0 into N(0) = {2} and non-N(0) = {1}, with the neighbor bucket placed **first** in the queue. Then 2 is selected before 1, giving `[0, 2, 1]`. The candidate never performs this split because it only refines by the *last selected* vertex (1), which is isolated and causes no split.

In general, the algorithm is missing the fundamental LexBFS invariant: after selecting vertex v, every bucket in the queue (including the one v came from) must be split into N(v) and non-N(v), with the N(v) part moved to the **front** of the queue. The candidate (a) does not move the neighbor part to the front, and (b) in this case the split never happens at all because the refinement is keyed on the wrong vertex sequence — the start vertex's adjacency is never used to split the initial bucket.

## REPAIR_HINTS
Rewrite `_lexbfs` as the standard partition-refinement LexBFS (Habib–McConnell–Paul–Viennot):

1. Maintain a queue of buckets. Initialize with one bucket containing all vertices except `start`.
2. When selecting the next vertex `v` from the **front** bucket:
   - Remove `v` from its bucket.
   - Split **every** bucket in the queue (including the front bucket, now without `v`) into `N(v)` and non-`N(v)` parts, preserving the relative order of elements within each part.
   - **Move all non-empty `N(v)` parts to the front of the queue** (in their original queue order), followed by the non-`N(v)` parts.
3. Select the next vertex from the front non-empty bucket (tie-break within a bucket by (rank, id) is fine for determinism).

The two concrete defects to fix in the current code:
- The refinement loop must run over all buckets **after** `v` is removed, and the `nb` (neighbor) sub-bucket must be placed **before** `nb2` in the queue, with all neighbor sub-buckets collected at the front of the whole queue (not just in-place splits).
- The start vertex's adjacency must be used to split the initial bucket (this happens automatically once the loop structure is correct: after selecting `start`... actually `start` is selected before the loop, so the initial refinement by `start` must be done explicitly, or restructure so the loop processes `start` first).

Simplest correct structure: put `start` into the queue as a singleton "processed" step — i.e., after `order = [start]`, immediately refine all buckets by adjacency to `start` and move N(start) to the front. Then the loop for the remaining n-1 vertices does: pop front bucket, pick v, append to order, refine all buckets by v, move N(v) parts to front.

Approaches that will NOT work:
- Keeping the current "refine by last selected vertex only, in-place split" structure and just changing the tie-break — the queue ordering invariant (neighbors first) is the core of LexBFS and cannot be recovered by tie-breaking alone.
- Using the previous ordering as the start vertex hint is fine, but the rank-based tie-break within a bucket is only valid if the bucket structure is correct; it cannot compensate for a wrong queue order.
