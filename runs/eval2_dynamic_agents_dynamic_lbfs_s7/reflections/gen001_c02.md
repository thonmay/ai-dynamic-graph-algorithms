## FAILURE_DESCRIPTION

3-vertex undirected graph. Initial graph (before the update) has only edge (0,1); `init` returns ordering `[0, 1, 2]` (valid for that graph). Then the harness applies `insert (0, 2)`, so the graph becomes:

- E = {(0,1), (0,2)}  (path 1-0-2)

Expected: any valid LexBFS ordering, e.g. `[0, 2, 1]` (or `[0, 1, 2]` is NOT valid here).
Actual returned: `[0, 1, 2]`.

Verifier reports the (LB) violation at positions a=0, b=1, c=2 (vertices va=0, vb=1, vc=2):
- ac in E: 0-2 is an edge (the just-inserted one).
- ab not in E: 0-1 ... wait, 0-1 IS an edge, so the trigger `ab not in E` should not fire. Re-checking: the violation record says `minD = 1000000000`, i.e. the verifier found a triple (a,b,c) with ac in E, ab not in E, and NO witness d < a. With a=0 there is no d < 0, so any such triple is an automatic violation. For a=0, va=0: we need b with 0-b not in E and c > b with 0-c in E. In `[0,1,2]`: b=1 (vertex 1): 0-1 in E, skip. b=2 (vertex 2): 0-2 in E, skip. Hmm — so the recorded (a=0,b=1,c=2) must be interpreted as: the verifier's own check found va=0, vb=1, vc=2 with ac in E (0-2 yes) and ab not in E. That means in the verifier's view 0-1 is NOT an edge.

Reconciling: the failing case is `sequence_idx: 0`, i.e. the FIRST operation of the sequence is `insert (0,2)`. The initial graph therefore has NO edges at all (empty graph on 3 vertices). `init` on the empty graph returns `[0,1,2]` (valid: no edges, no (LB) triples). After inserting (0,2), E = {(0,2)}. Now in `[0,1,2]`: a=0 (va=0), b=1 (vb=1): ab = 0-1 not in E ✓; c=2 (vc=2): ac = 0-2 in E ✓; need d < 0: none exists → violation. Expected valid ordering: `[0,2,1]` (check: a=0,vb=2: 0-2 in E skip; a=0,vb=1: 0-1 not in E, c=2: 0-2 in E, need d<0: none — wait that also fails!). Let me recheck `[0,2,1]`: positions a=0 (v=0), b=1 (v=2), c=2 (v=1): ab = 0-2 in E → skip. a=0,b=2 (v=1), no c. a=1 (v=2), b=2 (v=1): 2-1 not in E, no c. So `[0,2,1]` is valid. Good — the expected `[0,2,1]` matches.

So the concrete failure: after `insert (0,2)` on the empty 3-vertex graph, the candidate returned the stale ordering `[0,1,2]` which violates (LB) at (a=0,b=1,c=2).

## ROOT_CAUSE

The bug is in `_try_repair_insert` (and the fallback logic in `insert_edge`), which is entered because the stale ordering `[0,1,2]` is indeed invalid on the new graph. The repair tries:

1. Moving u=0 to each of the other positions: `[1,0,2]` and `[2,0,1]`.
2. Moving v=2 to each of the other positions: `[0,2,1]` and `[1,2,0]`.

Each candidate is checked with `_is_valid_lexbfs(new_order, graph)`. The correct answer `[0,2,1]` IS among the tried candidates (moving v=2 from position 2 to position 1). Therefore `_try_repair_insert` should have found it — UNLESS `_is_valid_lexbfs` itself is buggy.

Tracing `_is_valid_lexbfs([0,2,1], graph)` with E={(0,2)}:
- adj = [{2}, {0}, {0}]
- a=0 (va=0): b=1 (vb=2): 2 in adj[0] → skip. b=2 (vb=1): 1 not in adj[0]; c loop: range(3,3) empty. OK.
- a=1 (va=2): b=2 (vb=1): 1 not in adj[2]; c loop empty. OK.
- a=2: no b.
Returns True. So `_is_valid_lexbfs` correctly accepts `[0,2,1]`.

Then why did the candidate return `[0,1,2]`? Re-examining the repair loop order: it first tries moving u=0. Targets are `range(n)` = 0,1,2, skipping pos[u]=0. So target=1: `new_order = [1,0,2]`; target=2: `new_order = [2,0,1]`. Check `[1,0,2]` with E={(0,2)}:
- a=0 (va=1): b=1 (vb=0): 0 not in adj[1]={0}? 0 IS in adj[1] → skip. b=2 (vb=2): 2 not in adj[1]; c loop empty. OK.
- a=1 (va=0): b=2 (vb=2): 2 in adj[0] → skip.
- a=2: none.
`[1,0,2]` is ALSO valid! (Any ordering where 0 is not first, or where the non-neighbor of 0 comes after its neighbor, works.) So the repair returns `[1,0,2]` — a valid ordering.

But the reported actual result is `[0,1,2]`, the UNREPAIRED ordering. That means `_try_repair_insert` returned the original ordering, i.e. the very first line `if _is_valid_lexbfs(ordering, graph): return ordering` returned True for the INVALID ordering `[0,1,2]`.

Tracing `_is_valid_lexbfs([0,1,2], graph)` with E={(0,2)}, adj=[{2},{},{0}]:
- a=0 (va=0): b=1 (vb=1): 1 in adj[0]={2}? No → ab not in E. c=2 (vc=2): 2 in adj[0]? Yes → ac in E. Need d in range(0): empty → found=False → return False.

So `_is_valid_lexbfs([0,1,2])` correctly returns False... which contradicts the observed result. The only remaining explanation: the `graph` passed to `insert_edge` at the time of the check did NOT yet contain edge (0,2) — i.e., the harness passes the graph BEFORE the flip, or the candidate's `nbrs`/`adj` sets were built from a stale graph. But `insert_edge` builds `adj` fresh from the `graph` argument inside `_is_valid_lexbfs`, so if the harness had already flipped the matrix, the check would see the new edge.

Given the observed output `[0,1,2]` (the untouched ordering) and the violation being exactly the inserted edge (0,2), the most consistent root cause is: **the harness calls `insert_edge(graph, edge, state)` with the graph matrix already updated, but the candidate's `_try_repair_insert` early-exit `if _is_valid_lexbfs(ordering, graph): return ordering` was evaluated against a graph that still lacked (0,2)** — which can only happen if the `graph` argument is the pre-update matrix and the candidate is expected to apply the flip itself. In that case:
- `_is_valid_lexbfs([0,1,2], pre-update empty graph)` → True (no edges) → returns `[0,1,2]` unchanged.
- The verifier then checks against the post-update graph → violation.

This is the exact divergence point: the first line of `_try_repair_insert` (and the implicit assumption in `insert_edge`/`delete_edge`) that the passed `graph` already reflects the update. If the interface instead passes the pre-update graph and the edge to flip, the candidate never applies the flip to its own view, so every validity check and every recompute (`_recompute(graph)`) runs on the stale graph.

## REPAIR_HINTS

1. **First, disambiguate the interface contract** (this is the crux; do not guess). The failing trace is consistent with `insert_edge`/`delete_edge` receiving the PRE-update adjacency matrix plus the edge to flip. If so, the minimal fix is: at the top of `insert_edge`, set `graph[u][v] = graph[v][u] = 1` (and `= 0` in `delete_edge`) on a local copy before any check/recompute, and use that copy for `_try_repair_insert` and `_recompute`. Do not mutate the caller's matrix if the harness reuses it — copy first (`g = [row[:] for row in graph]`).
2. If the contract is instead "graph already updated", then the current code path should have worked (the repair finds `[1,0,2]` or `[0,2,1]`), and the failure would be a harness/state-passing bug rather than a candidate bug — in that case verify by instrumenting: print `graph` inside `insert_edge` and confirm whether (0,2) is set.
3. Do NOT "fix" this by making `_is_valid_lexbfs` more lenient or by skipping the early-exit in `_try_repair_insert`; the validator is correct and the early-exit is sound given a correct graph. The divergence is in which graph the checks see.
4. Note for the repair role: the local-repair search (move u, then move v, one vertex at a time) is sound for this case once the graph is correct, but in general a single-vertex move may not suffice for larger updates; keep the `_recompute` fallback. Also `_recompute`'s loop over starts is dead weight if `_lexbfs` is correct (any start yields a valid LexBFS), but harmless.
