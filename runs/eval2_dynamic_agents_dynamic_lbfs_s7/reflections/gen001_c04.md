## FAILURE_DESCRIPTION
3-vertex graph. The initial graph (sequence_idx 0) contains edge 0–1 (and no other edges); `init` produced ordering `[0, 1, 2]`, which is a valid LexBFS for that graph. The update is `insert (0, 2)`, so the graph becomes a path 2–0–1. The candidate returned the stale ordering `[0, 1, 2]`; the verifier reports it invalid with violation `{a: 0, b: 1, c: 2, pos_a: 0, minD: 1000000000}`: in the ordering, a=0 (pos 0), b=1 (pos 1), c=2 (pos 2); ab = 0–1 is in E, ac = 0–2 is not in E, and there is no d < a (a is first, so the required set is empty — hence `minD` stays at the sentinel 1e9). Expected a valid ordering such as `[0, 2, 1]` (or `[2, 0, 1]`).

## ROOT_CAUSE
The static `_lexbfs` is correct, but the dynamic wrapper's validity check `_is_valid_lexbfs` implements the **dual** of the (LB) 4-point property, so `insert_edge` keeps the stale ordering instead of recomputing.

The (LB) property (Corneil–Krueger) is: for all positions a < b < c with **ab in E and ac not in E**, there exists d < a with **db not in E and dc in E**. The candidate's code checks the opposite edge pattern:

```python
if b in adj[a]:
    continue  # ab in E, no constraint
...
for l in range(j + 1, n):
    c = order[l]
    if c not in adj[a]:
        continue
    # ac in E, ab not in E, a < b < c.
    # Need: exists d in D with dc not in E.
```

with `D = {d < a : db in E}`. That is "ab not in E and ac in E ⇒ ∃ d < a: db in E and dc not in E" — the dual, not (LB).

Tracing the failing case through the buggy check: order `[0,1,2]`, edges {0–1, 0–2}.
- (a=0, b=1): `b in adj[a]` (0–1 in E) → `continue`, no constraint checked. But (LB) has a constraint here: c=2 > b, ac = 0–2 not in E, and no d < 0 exists → violation. The buggy check never looks at this triple because it only inspects triples where ab is a non-edge.
- (a=0, b=2): 0–2 in E → `continue`.
- (a=1, b=2): 1–2 not in E; D = {d < 1 : 2 in adj[d]} = ∅; no c > 2 → passes.
Result: `_is_valid_lexbfs` returns True, so `insert_edge` returns the stale state. The verifier's correct (LB) check then flags the violation (minD = 1e9 sentinel = "no d < a with db not in E and dc in E").

The dual property is not equivalent to (LB), so the keep-or-recompute decision in `insert_edge`/`delete_edge` is unsound in both directions (it can keep invalid orderings, as here, and in principle could also force unnecessary recomputes).

## REPAIR_HINTS
1. Fix `_is_valid_lexbfs` to the actual (LB) property: for all positions a < b < c with **ab in E and ac not in E**, require ∃ d < a with **db not in E and dc in E**. Concretely, swap the edge/non-edge tests: iterate pairs (a,b) with `b in adj[a]` (ab in E, do NOT continue), then for each c > b with `c not in adj[a]` (ac not in E), require some d < a with `b not in adj[d]` and `c in adj[d]`. The current `D` set must become `{d < a : b not in adj[d]}` and the per-c test must be `c in adj[d]`.
2. Do not keep the dual property as a certificate — it is not equivalent to (LB) and misclassifies orderings (this failure is the "keeps an invalid ordering" direction).
3. Simplest robust fallback while the checker is being fixed: always recompute `_lexbfs(graph)` in `insert_edge`/`delete_edge` (the static routine is correct). This guarantees correctness first; the keep-if-valid fast path can be re-enabled once the checker implements the true (LB) property.
4. The static `_lexbfs` tie-break (smallest label, then smallest vertex id) is fine — the verifier accepts any valid LexBFS, so no change needed there.
