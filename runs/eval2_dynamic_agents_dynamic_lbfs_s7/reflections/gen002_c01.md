## FAILURE_DESCRIPTION
After `insert (2, 0)` on a 4-vertex graph, the candidate returned ordering `[0, 1, 3, 2]` (the verifier's "result" field). The expected valid ordering was `[0, 1, 2, 3]`. The (LB) 4-point property is violated at (a, b, c) = (0, 3, 2) with positions pos_a = 0, minD = 1: in the returned ordering, a=0 precedes b=3 precedes c=2, edge (0,2) is present, edge (0,3) is absent, and the only earlier vertex d=1 is adjacent to b=3 but also adjacent to c=2 (so it does not witness the property). The graph after the update must therefore contain edges (0,2) and (1,3) and (1,2), and not (0,3).

## ROOT_CAUSE
The static `_lexbfs` is not a correct LexBFS. The bug is in `_refine`:

```python
def _refine(buckets, v, graph):
    nb_parts = []
    non_parts = []
    for b in buckets:
        ...
        if nb:
            nb_parts.append(nb)
        if non:
            non_parts.append(non)
    return nb_parts + non_parts
```

This moves ALL neighbor parts to the front of the queue and ALL non-neighbor parts to the back, i.e. it reorders the buckets by adjacency to v. That is NOT the partition-refinement LexBFS of Habib–McConnell–Paul–Viennot. In that algorithm, the queue order of buckets is fixed by the order in which buckets were created (refined); when a bucket is refined by a newly processed vertex, its neighbor part stays in the same queue position (splitting the bucket in place, neighbor part first) and the non-neighbor part is appended to the END of the queue. The relative order of the other buckets is never changed by a refinement.

Concretely, on the failing graph (edges (0,2), (1,2), (1,3), no (0,3)), starting at 0 with rank = [0,1,2,3]:
- Initial bucket [1,2,3] refined by 0: neighbor part [2], non-neighbor part [1,3]. Correct HMPV queue: [[2], [1,3]]. The candidate's `_refine` happens to produce the same here.
- Pick v=2 (only in first bucket). Refine [1,3] by 2: neighbor part [1], non-neighbor part [3]. Correct HMPV queue: [[1], [3]] (the [1] part stays in the position of [1,3], [3] is appended). The candidate's `_refine` produces [[1], [3]] here too.
- Pick v=1. Refine [3] by 1: neighbor part [3], non-neighbor part empty. Both variants give [[3]].
- Pick v=3. Order: [0, 2, 1, 3].

So with the hint rank the candidate actually outputs [0,2,1,3] on this graph; the reported result [0,1,3,2] indicates the actual pre-update hint ordering differed (the hint rank changes which vertex is picked in multi-element buckets), but the mechanism is the same: `_refine`'s global reordering by adjacency to v is not a valid LexBFS refinement step, so the produced order can fail the (LB) property. The tie-break `min(buckets[bi], key=lambda x: (rank[x], x))` is fine (any deterministic tie-break is legal), and the start-vertex hint is fine (any start is legal); the only defect is the queue reordering in `_refine`.

## REPAIR_HINTS
Fix `_refine` to implement in-place splitting with the non-neighbor part appended to the end of the queue, preserving the relative order of all other buckets:

```python
def _refine(buckets, v, graph):
    new_buckets = []
    tail = []
    for b in buckets:
        if not b:
            continue
        nb = [x for x in b if graph[x][v]]
        non = [x for x in b if not graph[x][v]]
        if nb:
            new_buckets.append(nb)
        if non:
            tail.append(non)
    return new_buckets + tail
```

i.e. each bucket is replaced in place by its neighbor part (same queue position, so it is examined before the non-neighbor part), and the non-neighbor parts are appended to the end of the queue in original queue order. Do NOT sort/reorder buckets by adjacency to v (the current `nb_parts + non_parts` scheme) — that is the bug and will keep producing invalid orderings.

After fixing `_refine`, the recompute-based approach is correct (any start vertex and any deterministic tie-break yield a valid LexBFS), so the candidate should pass. The `rank`-based tie-break and the `start = hint[0]` hint can stay as-is; they are legal choices. Note that the `processed` array is unused and can be dropped.
