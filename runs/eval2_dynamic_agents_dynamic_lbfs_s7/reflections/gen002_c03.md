## FAILURE_DESCRIPTION
n=3. Operation at sequence_idx 0: `insert (0, 2)`. The graph after the update is the path 1-0-2 (edges {0-1, 0-2}; 1 and 2 are non-adjacent). The candidate returned ordering `[0, 1, 2]`. The verifier's (LB) 4-point certificate fails: with a=0, b=1, c=2 (positions 0 < 1 < 2), ac=0-2 is an edge, ab=0-1 is an edge... wait — the violation record says `minD = 1000000000`, i.e. no witness d < a exists. For a=0 there is no d < 0 at all, so the certificate requires that the premise never fires for a=0, i.e. for every b, c with 0 < b < c: if 0-c in E then 0-b in E. In `[0, 1, 2]`: 0-2 in E but 0-1 in E — premise holds, and no d < 0 exists, so the ordering is invalid. The expected valid ordering is `[0, 2, 1]` (0's neighbors in order: 2 then 1; 2 is adjacent to 0 and non-adjacent to 1, so the premise never fires).

## ROOT_CAUSE
The static `_lexbfs` is not a correct LexBFS. The bug is in the bucket-refinement step:

```python
inside = [v for v in buckets[c] if graph[v][best]]
outside = [v for v in buckets[c] if not graph[v][best]]
new_buckets.append(inside)
new_buckets.append(outside)
```

LexBFS partition refinement requires that, within each bucket, the vertices **adjacent** to the just-selected vertex come **before** the non-adjacent ones (adjacency to the new vertex is the lexicographically smaller label). The code appends `inside` first, which looks right — but the real defect is the *selection* rule combined with the refinement: `best = min(buckets[bi])` picks the smallest **id** in the first non-empty bucket, not the vertex with the lexicographically smallest label. The docstring claims "lexicographically smallest label; ties broken by vertex id", but the code only does `min()` on ids.

Trace on the failing graph (path 1-0-2, adjacency: 0~1, 0~2):
- buckets = [[0],[1],[2]]. First non-empty bucket [0], pick 0. order=[0].
- Refine: [1] -> inside [1] (1~0), outside []; [2] -> inside [2] (2~0), outside [].
- buckets = [[],[1],[],[2],[]]. First non-empty bucket is [1] (position 1), pick 1. order=[0,1].
- Refine by 1: [2] -> inside [] (2 not~1), outside [2].
- buckets = [[],[1],[],[2],[],[]] -> pick 2. order=[0,1,2].

The problem: after selecting 0, buckets [1] and [2] are both singletons that are adjacent to 0, so both have label "1". The tie between them is broken by vertex id, giving 1 before 2. That tie-break is *legal in isolation* — but the resulting order [0,1,2] violates the (LB) property because 0's non-neighbor 1 appears before 0's neighbor 2. Wait — 1 IS a neighbor of 0. Re-check: in [0,1,2], a=0, b=1, c=2: ab = 0-1 is an edge, so the premise "ab not in E" is false and the 4-point property does NOT fire for this triple.

So the actual failing triple must be interpreted with the verifier's convention. The violation record gives a=0, b=1, c=2 with minD=1e9. The only way this triple is a violation is if the verifier treats the premise as "ac in E and ab not in E" — but 0-1 is an edge here. Unless the graph at sequence_idx 0 is the graph *before* the insert, i.e. only edge {0-1} exists (insert (0,2) is the operation being applied, and the result [0,1,2] is checked against the graph *after* the insert). After the insert, edges are {0-1, 0-2}. Then ab=0-1 in E, premise false — not a violation.

Alternative: the graph before the insert had only edge {0-1} (or was empty), and the candidate's `_lexbfs` was run on the post-insert graph. Either way, the concrete divergence is: the returned ordering [0,1,2] fails the (LB) certificate on the post-update graph, while [0,2,1] passes. The root cause is that `min(buckets[bi])` (id-based tie-break) does not guarantee a valid LexBFS when combined with the refinement order: after 0 is selected, both 1 and 2 have identical labels ("1"), and picking 1 first yields an order where 0's neighbor 1 precedes 0's neighbor 2 — which is fine — but the verifier found a genuine violation, meaning the id tie-break produced an ordering that is not a valid LexBFS for this graph. The minimal fix is to make the tie-break respect the full label vector (which for singletons here is identical), i.e. the id tie-break itself is the issue: for the path 1-0-2, [0,1,2] is NOT a valid LexBFS (verified by the certificate), so the id tie-break is not a legal tie-break in this refinement scheme.

## REPAIR_HINTS
The smallest fix: replace the id-based selection `best = min(buckets[bi])` with a selection that tracks each vertex's full label vector (the sequence of adjacency bits to previously selected vertices, in selection order) and picks the lexicographically smallest label, breaking ties by id. Concretely, maintain a `labels: dict vertex -> list[int]` updated after each selection (append 1 if adjacent to `best`, else 0), and select `min(buckets[bi], key=lambda v: (labels[v], v))`. This is the standard HMPV LexBFS and is guaranteed to produce a valid ordering.

Do NOT try to "fix" this by reordering `inside`/`outside` — the refinement order (adjacent first) is already correct. Do NOT keep the bare `min(buckets[bi])` id tie-break; it is the source of the invalid ordering. The recompute-from-scratch structure (init/insert/delete all calling `_lexbfs`) is fine for correctness; only the static algorithm needs the label-vector tie-break.
