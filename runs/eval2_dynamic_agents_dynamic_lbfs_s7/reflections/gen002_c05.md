# Reflection: gen002_c05

## FAILURE_DESCRIPTION
Failing case: `operation = "init"` on the 2-vertex graph with adjacency matrix
`[[0, 1], [1, 0]]` (single edge 0-1). Expected result `[0, 1]`, actual result
`[0, 0]`. The returned `state['ordering']` is `[0, 0]`: vertex 0 appears twice
and vertex 1 is missing entirely, so the ordering is not even a permutation of
the vertex set.

## ROOT_CAUSE
The bug is in `_lexbfs`, in the bucket bookkeeping. The buckets are indexed by
`label.bit_length() - 1` (the highest set bit of the label), but the selection
loop scans `for k in range(n): if buckets[k]: ... break`, i.e. it takes the
first non-empty bucket in ascending index order. That is the wrong order:
lexicographic comparison of labels (as bitsets of ordered neighbors) compares
from the LOWEST bit upward, so the lexicographically smallest label is the one
whose highest set bit is LARGEST (a label with no high bits is smaller than a
label with a high bit set). The code's own comment even states the intended
semantics ("the lexicographically smallest label is found by scanning k from 0
upward"), which is backwards.

Trace on the failing case (n=2, edge 0-1):
- Init: `buckets[0] = 0b11` (both labels empty).
- Iteration 1: scan finds `buckets[0]` non-empty, picks vertex 0. `order=[0]`.
  Neighbor 1 gains bit 0: `label[1] = 0b01`, moved from `buckets[0]` to
  `buckets[0.bit_length()-1] = buckets[0]`. So `buckets[0] = 0b10` (vertex 1).
- Iteration 2: scan finds `buckets[0]` non-empty, picks vertex 0 again
  (`(0b10 & -0b10).bit_length()-1 = 1`... actually it picks the lowest set bit
  of `buckets[0]`, which is bit 1 = vertex 1). Wait — re-tracing: `buckets[0]`
  holds vertex 1 (bit 1 set), so `best = 1`, `order = [0, 1]`.

Re-checking: the second iteration actually does pick vertex 1 correctly here,
so the trace above does not reproduce `[0, 0]` on this exact 2-vertex graph.
The trace is therefore INCONCLUSIVE for the literal 2x2 case as written; the
reported `[0, 0]` output (a duplicated vertex) cannot arise from the selection
loop alone, since each iteration removes `best` from `unvisited` and `nbrs` is
masked by `unvisited`. The only way to emit a duplicate is if `best` were
already in `order`, which the `unvisited` masking prevents.

Given the inconclusive trace, the hypotheses are:
1. (ruled out) The selection loop picks a vertex twice — prevented by
   `unvisited &= ~(1 << best)` and `nbrs = adj_bits[best] & unvisited`.
2. (ruled out) The `best < 0` fallback — `unvisited` is non-empty each
   iteration, so the fallback is unreachable.
3. (open) The reported failure may come from a different code path or a
   harness/serialization issue not visible in this file, OR the actual failing
   graph in the harness differs from the 2x2 matrix shown (e.g. the matrix
   `[[0,1],[1,0]]` was mis-transcribed and the real graph is larger, where the
   reversed bucket-scan bug DOES produce a wrong-but-permutation ordering).

The reversed bucket-scan bug is real and will produce incorrect (non-LexBFS)
orderings on larger graphs: e.g. on a path 0-1-2, after ordering 0, vertex 1
has label {0} (bucket 0) and vertex 2 has label {} (bucket 0) — both in bucket
0, tie broken by id, fine; but on graphs where one vertex's label is a strict
subset of another's (e.g. labels {0} vs {0,1}), the subset label (lexicographically
smaller) has a LOWER highest bit and thus a LOWER bucket index, so scanning
ascending k picks the LARGER label first — wrong.

## REPAIR_HINTS
1. Fix the bucket scan direction in `_lexbfs`: scan `k` from `n-1` DOWN to 0
   (highest set bit first) to find the lexicographically smallest label, since
   a label with a higher highest-set-bit is lexicographically LARGER. Change
   `for k in range(n):` to `for k in range(n - 1, -1, -1):`.
2. Alternatively (simpler and less error-prone): drop the bucket structure
   entirely and, each iteration, scan all unvisited vertices and pick the one
   with the lexicographically smallest `label` (compare as tuples of bits from
   low to high, or simply as integers if labels are compared by their binary
   value read from the LOW end — note: integer comparison of the bitsets is
   NOT lexicographic-from-low, so use an explicit low-to-high comparison or
   store labels as reversed bitsets). O(n^2) total, still fine.
3. Do NOT keep the current ascending scan with the "empty label in bucket 0"
   convention — it conflates the empty label (smallest) with labels whose
   highest bit is 0, and inverts the comparison for multi-bit labels.
4. Add a self-check in `_lexbfs`: assert `sorted(order) == list(range(n))`
   before returning, so a duplicate/missing vertex fails loudly instead of
   silently producing `[0, 0]`.
5. The `_is_valid_lexbfs` (LB) checker appears logically correct (C & N(D) == 0
   with N(D) = intersection over D, all-ones when D empty); no change needed
   there, but note it is only invoked on updates, not after `init`, so an
   `init` bug is never caught by the checker.
