## FAILURE_DESCRIPTION
After `insert_edge(graph, (2, 0), state)` on a 4-vertex graph, the candidate returned
`[0, 1, 3, 2]` where the verifier expected `[0, 1, 2, 3]`. The (LB) 4-point property is
violated at (a, b, c) = (0, 3, 2) with pos_a = 0 and minD = 1: in the returned ordering,
a=0 is at position 0, b=3 at position 2, c=2 at position 3, so a < b < c; edge (a, c) =
(0, 2) is in E (it is the edge just inserted), edge (a, b) = (0, 3) is not in E, and there
is no d < a (pos_a = 0, so no earlier vertex exists) with d adjacent to b and not to c.
The returned ordering is therefore not a valid LexBFS ordering of the updated graph.

## ROOT_CAUSE
The bug is in the static LexBFS itself, in `_refine` (lines 20-33). The function is
documented as "Split every bucket by adjacency to v. Each bucket is replaced in place by
its neighbor part (same queue position), and the non-neighbor parts are appended to the
end of the queue in original queue order." That is NOT the HMPV partition-refinement
LexBFS. In HMPV, when a bucket is split by the adjacency of the just-selected vertex v,
the non-neighbor part must be moved to the FRONT of the queue (before the bucket that
was split), because non-neighbors of v have lexicographically larger labels than
neighbors of v. The candidate instead appends the non-neighbor parts to the END
(`return new_buckets + tail`), which is the reverse of the correct rule.

Concretely, in the failing case the updated graph has edges (0,1), (0,2), (1,2) (the
inserted edge) and no edge (0,3). Starting from 0:
- `_refine` on the initial bucket [1,2,3] by 0 gives neighbor part [1,2] and non-neighbor
  part [3]. Correct HMPV queue: [[3], [1,2]] (non-neighbor part first). The candidate's
  queue: [[1,2], [3]] (non-neighbor part last).
- The candidate then picks from the first bucket [1,2] (vertex 1), refines by 1, and
  eventually picks 3 before 2, producing [0, 1, 3, 2]. With the correct HMPV queue the
  first bucket is [3], so 3 would be picked before 2 only if it were a neighbor of 0 —
  it is not, and the correct ordering is [0, 1, 2, 3].

The responsible lines are:
```python
        if nb:
            new_buckets.append(nb)
        if non:
            tail.append(non)
    return new_buckets + tail
```
The `tail` (non-neighbor parts) should be PREPENDED, not appended: the correct return is
`tail + new_buckets` (with the non-neighbor parts in original queue order, placed before
the neighbor parts).

## REPAIR_HINTS
The smallest concrete fix is in `_refine`: change the return from
`return new_buckets + tail` to `return tail + new_buckets`. This places the non-neighbor
parts at the front of the queue (in original queue order) and the neighbor parts in their
original positions, which is the HMPV rule.

After this one-line change, re-trace the failing case: starting from 0 with edges
(0,1),(0,2),(1,2), the queue after the first refine is [[3],[1,2]]; pick 3 (only vertex
in first bucket), refine by 3 (no edges to 3, so [1,2] stays as-is, no non-neighbor
part), queue becomes [[1,2]]; pick 1, refine by 1 (2 is a neighbor of 1, so [2] stays),
pick 2. Result: [0, 3, 1, 2]. This is a valid LexBFS (any valid LexBFS is accepted by
the verifier). The specific ordering [0,3,1,2] should pass the (LB) 4-point property
check.

Approaches that will NOT work:
- Keeping `new_buckets + tail` (current code) — this is the bug.
- Using a different tie-break or start vertex — the fundamental queue-ordering rule is
  wrong, so no tie-break can fix it.
- Recomputing with a different static LexBFS algorithm — the fix is a one-line change to
  the existing `_refine`.
