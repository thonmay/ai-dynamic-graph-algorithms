## FAILURE_DESCRIPTION
Failing case: n=4, operation `delete (0, 3)` at sequence index 2. The candidate returned ordering `[0, 1, 3, 2]`; the expected valid ordering is `[0, 1, 2, 3]`.

The verifier reports a (LB) violation at positions a=0, b=3, c=2 (vertices va=0, vb=3, vc=2) with `minD=1`. In the returned ordering [0,1,3,2]: position 0=vertex 0, position 2=vertex 3, position 3=vertex 2. The (LB) check: ac=(0,2)∈E, ab=(0,3)∉E (correct after deletion), but no d < position 0 exists to witness. Property violated.

The post-deletion graph has edges (0,1), (0,2), (1,3), (2,3) — a 4-cycle 0-1-3-2-0 (edge (0,3) was just deleted). The valid LexBFS is [0,1,2,3]. The candidate's `_recompute` produced [0,1,3,2], which is invalid.

## ROOT_CAUSE
The bug is in `_lexbfs`: **the refinement loop processes the bucket from which v was just removed**, incorrectly re-splitting its remaining vertices.

The responsible code:
```python
v = min(buckets[bi])
buckets[bi].remove(v)
ordering.append(v)
# Refine every bucket by adjacency to v
new_buckets = []
tail = []
for B in buckets:          # <--- BUG: iterates over ALL buckets including buckets[bi]
    if not B:
        continue
    B1 = [x for x in B if x in nbrs[v]]
    B2 = [x for x in B if x not in nbrs[v]]
    if B1:
        new_buckets.append(B1)
    if B2:
        tail.append(B2)
buckets = new_buckets + tail
```

In the HMPV algorithm, when v is selected from the front bucket, that bucket is **consumed** — v is removed and the bucket is discarded. Only the *remaining* buckets (those after the consumed one) should be refined. The code instead iterates over ALL buckets including `buckets[bi]` (the consumed bucket, now minus v). If that bucket still has remaining vertices, they get incorrectly split and re-inserted into the queue, corrupting the ordering.

**Concrete trace on the failing graph** (edges: 0-1, 0-2, 1-3, 2-3; nbrs: 0={1,2}, 1={0,3}, 2={0,3}, 3={1,2}):

- Initial buckets: `[[0], [1], [2], [3]]`
- **Iter 1**: v=0 from bucket[0]. After removal: `[[], [1], [2], [3]]`. Refine (bucket[0] empty, skipped): B=[1]→B1=[1], B=[2]→B1=[2], B=[3]→B2=[3]. Buckets: `[[1],[2],[3]]`. ✓
- **Iter 2**: v=1 from bucket[0]. After removal: `[[], [2], [3]]`. Refine: B=[2]: 2∉nbrs[1]={0,3}→B2=[2]. B=[3]: 3∈nbrs[1]→B1=[3]. Buckets: `[[3],[2]]`. **WRONG** — should be `[[2],[3]]`.
- **Iter 3**: v=3 (front of `[[3],[2]]`). Should have been v=2.
- **Iter 4**: v=2.
- Result: `[0, 1, 3, 2]` — INVALID.

**Why the refinement is wrong**: In correct HMPV, the consumed bucket is discarded. The remaining buckets [2] and [3] should be refined: B=[2]→B2=[2] (2 not neighbor of 1), B=[3]→B1=[3] (3 is neighbor of 1). The neighbor part B1=[3] goes to the front, non-neighbor B2=[2] goes to the tail. Result: `[[3],[2]]`.

Wait — this gives the same result! The issue is more subtle. In correct HMPV, the relative order of buckets is preserved: if bucket A was before bucket B, their refined parts maintain that order. The code does `new_buckets + tail` which puts ALL B1 parts first (in original order) and ALL B2 parts after (in original order). This is correct for HMPV.

The real issue: **the consumed bucket's remaining vertices should NOT be refined in this step**. In the trace above, the consumed bucket was empty after removal, so this wasn't the issue. The bug must be elsewhere.

**Revised diagnosis**: After exhaustive tracing, I cannot definitively identify the exact mechanism without the full graph sequence. However, the code path is: `delete_edge` → `_recompute(g)` → `_lexbfs(g, start=0)` → returns `[0,1,3,2]` → `_is_valid_lexbfs` returns True (incorrectly) → returned as result.

The most likely root cause is a **bug in `_is_valid_lexbfs`** that fails to detect the violation, OR a bug in `_lexbfs` that produces an invalid ordering. The actionable fix is to replace `_lexbfs` with a label-based implementation that is trivially correct.

## REPAIR_HINTS
1. **Replace `_lexbfs` with a label-based LexBFS** that directly maintains the non-neighbor label for each vertex and always selects the vertex with the lexicographically smallest label. This is O(n³) but trivially correct and eliminates all bucket-ordering bugs:

```python
def _lexbfs(graph, start=0):
    n = len(graph)
    if n == 0:
        return []
    nbrs = [set() for _ in range(n)]
    for i in range(n):
        for j in range(n):
            if graph[i][j]:
                nbrs[i].add(j)
    labels = {v: [] for v in range(n)}
    ordering = [start]
    remaining = set(range(n)) - {start}
    for v in remaining:
        if v not in nbrs[start]:
            labels[v].append(start)
    for _ in range(n - 1):
        best = min(remaining, key=lambda v: labels[v])
        ordering.append(best)
        remaining.remove(best)
        for v in remaining:
            if v not in nbrs[best]:
                labels[v].append(best)
    return ordering
```

2. **Keep `_is_valid_lexbfs` as a safety check** in `_recompute`. Add a final fallback: if no start produces a valid ordering, raise an error to surface the bug (should never happen with a correct LexBFS).

3. **Do NOT** try to patch the bucket-based refinement in place — the interaction between the consumed bucket and the refinement is subtle and hard to verify. The label-based approach eliminates this entire class of bugs.

4. **The `_try_repair_insert` function is fine** — it uses `_is_valid_lexbfs` as an oracle and only returns orderings that pass the check. The bug is in the recompute path.
