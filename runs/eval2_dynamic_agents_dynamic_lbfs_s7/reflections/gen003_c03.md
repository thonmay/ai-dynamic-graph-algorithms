## FAILURE_DESCRIPTION

Failing case: n=3, operation `insert (1, 2)` at sequence index 0. The graph
after the update is the path 0-1-2 (edges {01, 12}; 0-2 absent). The
candidate returned ordering `[2, 0, 1]`; the expected (and only valid)
LexBFS ordering is `[0, 1, 2]`.

The verifier reports the (LB) 4-point violation with a=2, b=0, c=1
(positions 0, 1, 2 in the returned order): ac = 2-1 is an edge, ab = 2-0 is
not an edge, and no d < a exists (a is at position 0, so the witness set is
empty; reported as `minD: 1000000000`).

## ROOT_CAUSE

The bug is in `_lexbfs`'s tie-breaking. The code iterates
`for v in sorted(unvisited, reverse=True)` and keeps the first vertex whose
label is strictly smaller (`if best is None or label[v] < best_label`).
Because the iteration is descending and the comparison is strict, when two
unvisited vertices have EQUAL labels the LARGER vertex id wins. The comment
claims this "matches the reference implementation used by the verifier",
but it does not: the verifier's reference breaks ties by the SMALLEST vertex
id (equivalently, iterate ascending with strict `<`).

Trace on the failing graph (path 0-1-2):
- Step 1: all labels are `[]` (tie). Descending scan 2,1,0 keeps 2 (first
  seen, later ties are not strictly smaller). Picks 2.
- Step 2: label[1]=[2], label[0]=[]. Smallest label is `[]` -> picks 0.
- Step 3: picks 1.
Result: `[2, 0, 1]`.

`[2, 0, 1]` is not a valid LexBFS ordering of the path: the (LB) property
fails exactly as the verifier reports (a=2 at position 0, b=0, c=1). The
correct tie-break (smallest id) gives `[0, 1, 2]`, which is valid.

Note: the candidate's `insert_edge`/`delete_edge` always recompute via
`_lexbfs`, so the failure is entirely in the static routine, not in the
dynamic logic. The (LB) property is in fact a certificate of LexBFS
validity (Corneil-Krueger), so the "always recompute because the check is
only necessary" comment is also wrong, but that is not what caused this
failure.

## REPAIR_HINTS

1. Fix the tie-break in `_lexbfs`: iterate `for v in sorted(unvisited)`
   (ascending) with the same strict `<` comparison, so that on equal labels
   the SMALLEST vertex id is picked. This is the minimal change and makes
   the static routine produce a valid LexBFS ordering for the failing case
   (`[0, 1, 2]`).

2. Do NOT rely on the (LB) check to "repair" a bad ordering: the check is
   a certificate, so any ordering it accepts is already valid; the problem
   is producing an ordering that fails it. Fix the generator, not the
   checker.

3. Optional (research goal, not required for correctness): once the static
   routine is correct, `insert_edge`/`delete_edge` can keep the previous
   ordering when `_is_valid_lexbfs(state['ordering'], graph)` returns True
   and only recompute on failure — the current "always recompute" is
   correct but misses the no-recompute goal.

Approaches that will not work: keeping the descending scan and switching to
`<=` (that would pick the smallest id only by accident of scan order and is
fragile); or trying to post-process the returned order to satisfy (LB)
without re-running LexBFS.
