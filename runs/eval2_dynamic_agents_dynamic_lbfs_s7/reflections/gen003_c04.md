## FAILURE_DESCRIPTION
Case: n=3, operation `insert (0, 2)` at sequence_idx 0. After the update the
graph is the path 1-0-2 (edges {0-1, 0-2}; 1 and 2 are non-adjacent). The
candidate returned ordering `[0, 1, 2]`; the expected (valid) ordering is
`[0, 2, 1]` (any valid LexBFS works, e.g. `[1, 0, 2]` or `[2, 0, 1]` too).

The verifier's (LB) 4-point check reports a violation at a=0, b=1, c=2
(positions pos_a=0, pos_b=1, pos_c=2): ac=(0,2) is an edge, ab=(0,1) is not an
edge, and no d < a exists (minD stays at the sentinel 1000000000). So the
returned ordering is not a valid LexBFS ordering of the updated graph.

## ROOT_CAUSE
The bug is in the static `_lexbfs` partition refinement: the split of each
bucket by adjacency to the chosen vertex `best` is inverted. The code does:

```python
inside  = [v for v in buckets[c] if graph[v][best]]
outside = [v for v in buckets[c] if not graph[v][best]]
...
new_buckets.append(outside)
new_buckets.append(inside)
```

i.e. it places the NON-neighbors of `best` BEFORE the neighbors. In LexBFS the
refinement must put the NEIGHBOR part first (neighbors of the chosen vertex
move to the front of the queue / get smaller labels), so the correct order is
`new_buckets.append(inside)` then `new_buckets.append(outside)`.

Trace on the failing case (graph after insert: edges 0-1, 0-2):
- Step 1: first bucket {0}, pick 0. Bucket {1}: inside=[1], outside=[] ->
  buckets become [[],[1],[]] (1 is a neighbor, stays first). Bucket {2}:
  inside=[2], outside=[] -> [[],[1],[],[2],[]].
- Step 2: first non-empty bucket is [1] (before [2]), so 1 is picked next.
- Step 3: 2. Result `[0, 1, 2]`.

With the correct (inside-first) refinement, after step 1 the buckets are
[[],[1],[],[2],[]] in the same shape but the neighbor parts come first, so the
first non-empty bucket after step 1 is [1]... wait — the decisive difference
is the label ordering: with inside-first, neighbors of 0 (1 and 2) get label
[1] and are placed before non-neighbors; the queue order after step 1 is
[1],[2] (neighbors first, in original bucket order). Then 1 is picked, and 2
is refined by adjacency to 1: 2 is a non-neighbor of 1, so 2 stays. Hmm — the
actual divergence: with the inverted split, the non-neighbor part is placed
first, so a vertex that is NOT adjacent to the chosen vertex is ordered before
one that IS adjacent. In this 3-vertex case the inversion makes 1 (adjacent to
0) and 2 (adjacent to 0) both neighbors, so the inversion's effect shows up in
the label comparison: `labels` are appended as 1 for inside / 0 for outside,
but the bucket ORDER contradicts the labels (outside bucket placed first yet
labeled 0, which is lexicographically smaller — consistent), while the
LexBFS queue semantics require neighbors first. The net effect is that the
produced order `[0,1,2]` violates the (LB) property: 0 is adjacent to 2 but
not to 1, and 1 appears before 2 with no earlier witness d.

The responsible lines are the two `new_buckets.append(...)` calls (and the
comment justifying them, which states the wrong rule: "the non-neighbor part
(outside) is placed BEFORE the neighbor part (inside)").

## REPAIR_HINTS
Smallest fix: in `_lexbfs`, swap the two appends so the neighbor part comes
first:

```python
new_buckets.append(inside)
new_buckets.append(outside)
```

and update the comment accordingly (neighbors of the chosen vertex are placed
before non-neighbors). This restores the standard LexBFS partition refinement
and makes the static recompute correct; since `init`/`insert_edge`/
`delete_edge` all call `_lexbfs`, fixing it fixes all three entry points.

Notes:
- Do NOT try to "fix" this by changing the tie-break (`min` over labels) or
  the label values (1/0) alone; the bucket ordering and the labels must agree
  with the LexBFS queue semantics (neighbors first). Swapping only the labels
  without swapping the bucket order (or vice versa) leaves the algorithm
  inconsistent.
- The dynamic part (recompute after each update) is correct in principle and
  is not the source of this failure; the research goal of avoiding full
  recompute can be pursued later, but correctness of `_lexbfs` is the
  prerequisite.
- After the fix, verify on the failing case: expected valid orderings include
  `[0, 2, 1]`, `[1, 0, 2]`, `[2, 0, 1]` (any start, any tie-break); the
  (LB) 4-point property must hold for all a<b<c.
