# Reflection: gen003_c05

## FAILURE_DESCRIPTION
Operation: `init` (sequence_idx 0, no prior updates). n = 4. The candidate
returned ordering `[0, 1, 2, 3]`, but the expected (valid) ordering is
`[0, 3, 2, 1]`. The verifier reports a (LB) 4-point violation at
`a=0, b=1, c=3, pos_a=0, minD=1000000000`.

Interpreting the violation: in the returned ordering, position 0 = vertex 0,
position 1 = vertex 1, position 3 = vertex 3. The (LB) property requires that
for a=0 < b=1 < c=3 with `ac in E` (edge 0-3 present) and `ab not in E`
(edge 0-1 absent), there exists `d < a` (i.e., d at a position before 0)
with `db in E` and `dc not in E`. Since `a` is at position 0, there is no
`d < a` — hence `minD` stays at the sentinel 1000000000 and the property
fails. The graph must therefore contain edge (0,3) and lack edge (0,1), with
vertex 1 adjacent to some earlier vertex d that is NOT adjacent to vertex 3.

## ROOT_CAUSE
The static `_lexbfs` routine is not a correct LexBFS implementation. The
divergence happens in the refinement loop:

```python
for x in range(n):
    bx = bidx[x]
    ...
```

The loop iterates over vertices in **fixed id order** (`x = 0, 1, 2, ...`),
not in the order in which they are *processed* by the algorithm (i.e., the
current front of the bucket list). In a correct partition-refinement LexBFS,
after refining with vertex `x`, the next vertex to process is the first
vertex of the first non-empty bucket (the "front" of the queue), which
depends on the graph structure. By processing in id order, the candidate
performs a sequence of refinements that does not correspond to any LexBFS
search, so the resulting ordering is not guaranteed to satisfy the (LB)
property.

Additionally, the tie-breaking within a bucket uses `sorted(B)` (original
vertex id order), which is a valid tie-break only if the bucket ordering
itself is correct. Since the bucket ordering is wrong, the final ordering is
invalid.

The `_recompute` fallback (trying all starts) cannot save this: every start
goes through the same flawed `_lexbfs` loop, so all 4 candidate orderings
are potentially invalid. In this specific case, none of the 4 starts
produced a valid ordering, so `_recompute` fell through to the final
`return _lexbfs(graph, start=0)` which is also invalid.

## REPAIR_HINTS
1. **Fix the processing order in `_lexbfs`.** Replace
   `for x in range(n):` with a loop that processes vertices in the order
   they appear in the bucket list (front-to-back). Concretely, maintain a
   pointer or use the fact that after each refinement the next vertex to
   process is the first element of the first bucket. A standard approach:
   keep a list `order` of vertices to process; initially `[start]` then the
   rest. After processing `x`, the next `x` is the first vertex in the
   first bucket that hasn't been processed yet. Alternatively, use the
   well-known formulation: process vertices in the order they are
   *discovered* (i.e., the order of the final ordering itself, built
   incrementally).

   A clean correct implementation:
   ```python
   def _lexbfs(graph, start=0):
       n = len(graph)
       # buckets as ordered list of sets/lists
       # Process: pick first vertex from first bucket, refine, repeat
       # The processing order IS the output ordering.
       unprocessed = list(range(n))  # or use buckets
       # Standard: maintain ordered partition; at each step take the
       # first vertex of the first bucket, remove it, refine all other
       # buckets by adjacency to it.
   ```

2. **Do NOT rely on `_recompute` trying all starts as a safety net.** If
   `_lexbfs` is correct for any start, one start suffices. The all-starts
   loop masks the bug and wastes time.

3. **The `_is_valid_lexbfs` checker appears correct** (it faithfully
   implements the (LB) 4-point property). Keep it as a self-check in
   `_recompute` to catch regressions.

4. **Approaches that will NOT work:**
   - Simply changing the tie-break within buckets (e.g., using insertion
     order instead of `sorted(B)`) does not fix the fundamental issue that
     the refinement sequence is wrong.
   - Adding more start vertices to try in `_recompute` does not help if
     the core refinement is structurally incorrect.
   - The `_try_repair` logic for dynamic updates is a separate concern and
     is not the cause of this failure (which occurs at `init`).
