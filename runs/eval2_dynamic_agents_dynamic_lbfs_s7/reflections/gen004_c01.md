# Reflection: gen004_c01

## FAILURE_DESCRIPTION
- Operation: `init` (sequence_idx 0), n = 4.
- Candidate returned ordering `[0, 1, 2, 3]`.
- Expected (one valid LexBFS): `[0, 3, 2, 1]`.
- Verifier violation: a=0, b=1, c=3 at pos_a=0, minD = 1e9 (no witness found).

## ROOT_CAUSE
The static `_lexbfs` is not a correct LexBFS. It refines **every** remaining
bucket by adjacency to the just-processed vertex x:

```python
        # refine every remaining bucket by adjacency to x
        new_buckets = []
        for B in buckets:
            B1 = [v for v in B if v in nbrs[x]]
            B2 = [v for v in B if v not in nbrs[x]]
```

In LexBFS, a vertex x only refines buckets that **contain a neighbor of x**
(the "front"); buckets with no neighbor of x must be left untouched. Refining
all buckets by x is a different (invalid) ordering scheme.

Concrete trace (the failing graph is the path 0-1-2-3, i.e. edges {01,12,23};
this is the unique 4-vertex graph for which the candidate's output `[0,1,2,3]`
violates (LB) exactly at (a,b,c)=(0,1,3) with no witness, and for which
`[0,3,2,1]` is valid):

- buckets = [[0],[1],[2],[3]]; process 0.
- Correct LexBFS: only bucket [1] contains a neighbor of 0, so it is split
  into [1] (N) + [] (non-N); buckets [2],[3] are untouched.
- Candidate: [2] is split into [] (N) + [2] (non-N) and [3] into [] + [3].
  The non-neighbor sub-buckets of [2] and [3] are now **lexicographically
  smaller** than [1] (their label gained a 0 from x=0, while [1]'s label
  gained a 1).
- Next, the candidate picks 1 (front [1]); correct LexBFS picks 3 (front [3]).
- Result: candidate outputs `[0,1,2,3]`, which is not a LexBFS of the path.

Why the bug was not caught by the candidate's own checks:
1. `_is_valid_lexbfs` implements the (LB) property **incorrectly**. It
   requires a witness d for every triple (a,b,c) with ab∉E and ac∈E, i.e. it
   treats the condition as `∀c ∃d`. The true (LB) property is
   `∃d ∀c`: there must exist a single d < a such that for **all** c > b with
   ac∈E, db∈E and dc∉E. The candidate's checker is strictly stronger than
   (LB), so it rejects valid orderings (e.g. `[0,3,2,1]` on the path: for
   (a,b,c)=(0,1,2) the only d=0 has d-c=0-2∉E, so the checker fails it even
   though (LB) is satisfied by d=0 for the c=3 triple).
2. `_recompute` therefore falls through all starts: `_lexbfs` produces the
   invalid `[0,1,2,3]` for every start, the over-strict checker rejects every
   candidate, and the final fallback `return _lexbfs(graph, start=0)` returns
   the invalid ordering anyway.

So the divergence happens at the very first refinement step of `_lexbfs`
(refining buckets with no neighbor of x), and the invalid result survives
because the validator is wrong in both directions (too strict to accept valid
orderings, and the fallback ignores its verdict).

## REPAIR_HINTS
1. **Fix `_lexbfs` (primary bug).** Refine only buckets that contain at least
   one neighbor of x:
   ```python
   new_buckets = []
   for B in buckets:
       B1 = [v for v in B if v in nbrs[x]]
       if B1:
           B2 = [v for v in B if v not in nbrs[x]]
           if B2:
               new_buckets.append(B1)
           new_buckets.append(B2)
       else:
           new_buckets.append(B)
   ```
   (Buckets with no neighbor of x are appended unchanged, preserving their
   relative order.) This is the standard Habib-McConnell-Paul-Viennot
   formulation and produces a valid LexBFS for any start.
2. **Fix `_is_valid_lexbfs` to the true (LB) property.** For each (a,b) with
   ab∉E, let C = {c > b : ac∈E}; if C is nonempty, require a single
   `d < a` with db∈E and dc∉E for **all** c in C (existential over d,
   universal over c). The current `∀c ∃d` loop must be restructured so the
   chosen d is checked against every c in C.
3. **Do not** rely on the "try all starts" loop in `_recompute` as a
   correctness net: with a correct `_lexbfs`, any single start yields a valid
   ordering, so the loop is unnecessary (keep it only as a sanity check with
   the fixed validator).
4. Approaches that will not work:
   - Keeping the "refine all buckets" scheme and patching the validator to
     accept its output — the output is not a LexBFS, no validator change can
     make it valid.
   - Trying to repair the ordering in `init` via `_try_repair` — there is no
     prior state at init; the static routine itself must be correct.
   - Note for later generations: the single-endpoint-move repair in
     `_try_repair` is also not guaranteed to find a valid ordering after an
     update even when one exists (a valid LexBFS of the new graph may differ
     from the old one in more than one position), so the full-recompute
     fallback must remain, and its correctness depends on fixes 1 and 2.
