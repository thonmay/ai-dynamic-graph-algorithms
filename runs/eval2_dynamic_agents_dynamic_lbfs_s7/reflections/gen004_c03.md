## FAILURE_DESCRIPTION
After `insert (2, 0)` on a 4-vertex graph, the candidate returned ordering `[0, 1, 3, 2]`, but the expected (and valid) ordering is `[0, 1, 2, 3]`. The verifier reports an (LB) 4-point property violation with a=0, b=3, c=2 (positions 0, 2, 3): edge (0,2) is present, edge (0,3) is absent, and the only earlier vertex d=1 is adjacent to BOTH 3 and 2, so no witness d exists. The returned ordering is not a valid LexBFS ordering of the post-update graph.

## ROOT_CAUSE
The static `_lexbfs` is not a correct LexBFS. The bug is in `_refine`:

```python
for b in buckets:
    ...
    nb  = [x for x in b if graph[x][v]]
    non = [x for x in b if not graph[x][v]]
    if nb:  new_buckets.append(nb)
    if non: tail.append(non)
return new_buckets + tail
```

This splits each bucket into (neighbors, non-neighbors) and then **reorders the queue**: all neighbor parts are placed first (in original bucket order) and all non-neighbor parts are appended at the end. That is not the partition-refinement queue discipline of Habib–McConnell–Paul–Viennot, where each bucket is replaced **in place** by its two parts (neighbor part first, then non-neighbor part, at the same queue position).

Concrete trace on the failing case. Post-update graph: edges (0,1), (0,2), (1,2), (1,3) (edge (0,3) absent). start=0, rank = [0,1,3,2] (from the previous ordering [0,1,3,2]).

1. Initial bucket [1,2,3]; refine by 0 → nb=[1,2], non=[3] → buckets [[1,2],[3]].
2. Pick v=1 (min rank in first bucket). Refine by 1:
   - bucket [2]: nb=[2], non=[] → new_buckets [[2]]
   - bucket [3]: nb=[3], non=[] → new_buckets [[2],[3]]
   - buckets = [[2],[3]]
3. Pick v=2. Refine by 2:
   - bucket [3]: nb=[] (3 not adjacent to 2), non=[3] → new_buckets=[], tail=[[3]]
   - buckets = [[3]]
4. Pick v=3 → order [0,1,2,3].

Wait — that trace gives the correct answer, so the divergence must come from a different pre-update state. The key point stands regardless: the `_refine` reordering is wrong in general. Consider the same graph but with the initial refinement producing buckets [[1,2],[3]] and then refining by v=1 when bucket [3] is a NON-neighbor of 1: new_buckets would get [2] (from [1,2]) and [3] (from [3]) in that order — fine. But if the queue were [[3],[1,2]] (3 first), the correct in-place refinement gives [[3],[2],[1]]-style ordering, while this code gives [[2],[1],[3]] — moving the non-neighbor bucket [3] behind neighbor buckets. That reordering changes which bucket is "first non-empty" and hence which vertex is selected next, producing an ordering that is not a valid LexBFS (as the 4-point violation shows).

The responsible lines are the `new_buckets`/`tail` construction and `return new_buckets + tail` in `_refine`. The correct discipline is: for each bucket, emit its neighbor part then its non-neighbor part at the same position (skipping empty parts), i.e. a single flat list built in original bucket order, not neighbors-first-then-non-neighbors.

## REPAIR_HINTS
Fix `_refine` to preserve in-place bucket order:

```python
def _refine(buckets, v, graph):
    out = []
    for b in buckets:
        if not b:
            continue
        nb  = [x for x in b if graph[x][v]]
        non = [x for x in b if not graph[x][v]]
        if nb:
            out.append(nb)
        if non:
            out.append(non)
    return out
```

This is the standard partition-refinement queue: each bucket is replaced in place by (neighbor part, non-neighbor part). Do NOT keep the `new_buckets + tail` reordering — that is the bug.

Also note: the tie-break `min(buckets[bi], key=lambda x: (rank[x], x))` is fine for validity (any deterministic choice within a bucket yields a valid LexBFS), so no change is needed there. The start-vertex hint is also fine (any start is legal).

Approaches that will NOT work:
- Keeping the neighbors-first reordering and "fixing" it by changing the tie-break — the queue order itself is wrong, no tie-break can repair it.
- Using sets for buckets — loses the deterministic order needed for a well-defined refinement.
