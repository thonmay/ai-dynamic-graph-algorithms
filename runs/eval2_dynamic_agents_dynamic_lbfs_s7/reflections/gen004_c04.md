## FAILURE_DESCRIPTION
3-vertex graph, initial state (before the update) has no edges, so `init` produced the ordering `[0, 1, 2]`. The update is `insert (0, 1)`, giving the single-edge graph E = {(0,1)}. The candidate returned `[0, 2, 1]` (it kept the old ordering), but the expected result is `[0, 1, 2]`. The verifier reports a (LB) violation with a=0, b=2, c=1 (pos_a=0, minD=1e9): in the returned order, a=0 at position 0, b=2 at position 1, c=1 at position 2; ac = (0,1) IS in E, ab = (0,2) is NOT in E, and there is no d < a (a is first) that could witness the property. Indeed `[0, 2, 1]` is not a valid LexBFS ordering of the graph with edge (0,1): a valid ordering must place 1 before 2 (e.g. `[0,1,2]` or `[1,0,2]`), because 1 is the only neighbor of 0 and must be picked before the non-neighbor 2.

## ROOT_CAUSE
The static `_lexbfs` is correct (it produces `[0,1,2]` on the updated graph), so the divergence is entirely in the "keep the old ordering if still valid" fast path. The bug is that `_is_valid_lexbfs` implements the (LB) 4-point property with the edge conditions SWAPPED relative to the correct statement.

Correct (LB) property (as stated in the brief): for all positions a < b < c with **ac in E and ab not in E**, there exists d < a with **db in E and dc not in E**.

What the code checks (lines in `_is_valid_lexbfs`):
```python
if b not in adj[a]:
    continue  # ab not in E, no constraint
# ab in E.
...
if c in adj[a]:
    continue
# ac not in E, ab in E, a < b < c.
# Need: exists d in D with dc in E
```
i.e. it triggers on **ab in E and ac not in E** and requires a witness d with **db not in E and dc in E** — the exact negation of the correct antecedent/consequent.

Tracing the failing case: order `[0,2,1]`, graph E={(0,1)}. The only triple with a<b<c is (a=0, b=2, c=1). The correct property's antecedent (ac=(0,1) in E, ab=(0,2) not in E) holds, so the property is violated (no d < a exists). But the code's antecedent (ab=(0,2) in E) is false, so it `continue`s and never inspects this triple; the function returns True, `insert_edge` keeps the stale ordering, and the invalid `[0,2,1]` is returned.

Note the swap is not a harmless symmetry: the property is not invariant under swapping the roles of b and c, so the swapped check is a genuinely different (and wrong) condition that can both miss real violations (as here) and, in principle, reject valid orderings.

## REPAIR_HINTS
Smallest fix: in `_is_valid_lexbfs`, swap the edge conditions to match the brief exactly:
- Trigger (antecedent) on `c in adj[a]` (ac in E) AND `b not in adj[a]` (ab not in E) — i.e. replace the `if b not in adj[a]: continue` guard with `if b in adj[a]: continue` and the `if c in adj[a]: continue` guard with `if c not in adj[a]: continue`.
- Define the witness set as `D = {d : pos[d] < pos[a], d in adj[b]}` (db in E, not "db not in E").
- Require `exists d in D with d not in adj[c]` (dc not in E, not "dc in E").

After this fix, the fast path correctly detects that `[0,2,1]` is invalid on the updated graph and falls through to `_lexbfs`, which returns the correct `[0,1,2]`.

Approaches that will NOT work:
- "Just recompute unconditionally in insert_edge/delete_edge" would be correct but abandons the keep-if-valid fast path the candidate is built around (and the research goal of avoiding full recomputation); the intended design is a correct validity check plus recompute-on-failure.
- Trying to "fix" the static `_lexbfs` is pointless — it is already correct on this case.
- Keeping the current (swapped) check but adding extra cases does not work; the antecedent/consequent must be exactly the (LB) property, not a superset of it.
