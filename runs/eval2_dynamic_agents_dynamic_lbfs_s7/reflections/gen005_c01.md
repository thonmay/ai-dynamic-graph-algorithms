# Reflection: gen005_c01 — init fails on 4-vertex graph

## FAILURE_DESCRIPTION
Operation: `init` (sequence_idx 0) on a 4-vertex undirected graph.
- Result returned: `[0, 1, 2, 3]`
- Expected (a valid LexBFS): `[0, 3, 2, 1]`
- Verifier violation: `a=0, b=1, c=3, pos_a=0, minD=1000000000`.
  In the returned ordering, positions a=0 (vertex 0), b=1 (vertex 1), c=3 (vertex 3)
  satisfy: 0-3 in E, 0-1 not in E, and NO witness d < a exists (trivially, since
  pos_a = 0, there is no d < 0). The (LB) 4-point property is violated.

The expected ordering `[0, 3, 2, 1]` is valid: the only non-edge pair with a later
neighbor of the earlier vertex is (0,2) at positions 0,2; witness d=3 (position 1)
is adjacent to 2 and not to 1.

## ROOT_CAUSE
The static `_lexbfs` partition-refinement loop is correct, but the candidate's
**validator `_is_valid_lexbfs` implements the (LB) property incorrectly**, so the
safety net in `_recompute` (which is supposed to catch a bad ordering and try other
start vertices) is defeated.

The (LB) property is: for all positions a < b < c with ac in E and ab not in E,
there exists d < a with db in E and dc not in E. The existential over d is
**per (a,b,c) triple** — a different witness d may serve different c's.

The candidate instead (lines in `_is_valid_lexbfs`):

```python
C = [ordering[c] for c in range(b + 1, n)
     if ordering[c] in adj[va]]
...
for d in range(a):
    vd = ordering[d]
    if vb not in adj[vd]:
        continue
    if all(vc not in adj[vd] for vc in C):
        found = True
        break
```

It collects ALL c > b with ac in E into `C` and demands a **single** d that is
non-adjacent to every vertex of C simultaneously. This is strictly stronger than
(LB). Consequences:

1. `_is_valid_lexbfs` returns False for orderings that are actually valid
   (false negatives). In `_recompute`, a correct `_lexbfs` output is therefore
   rejected, and the code falls through to the final line
   `return _lexbfs(graph, start=0)` — which returns the same (valid) ordering
   **without any validation**. So the "try other starts" fallback is dead code:
   it can never rescue anything, and the final return bypasses the check.

2. The same over-strict check is used in `_try_repair`, so the local-repair path
   also rejects valid orderings and forces unnecessary recomputes (and, combined
   with point 1, can still end up returning an unvalidated ordering).

Note the failure is reported at `init` with result `[0,1,2,3]`. The exact input
matrix is not in the failure record, so I cannot re-derive the precise graph; but
the mechanism is unambiguous: the only way `init` returns an ordering is either
(a) `_is_valid_lexbfs` accepted it, or (b) the final unvalidated
`return _lexbfs(graph, start=0)`. Since the verifier found a genuine (LB)
violation in the returned ordering, the returned ordering is genuinely invalid,
which means `_lexbfs` itself produced an invalid ordering on this input — and the
broken validator (false negative on the true LexBFS output, plus the unvalidated
final return) is what allowed it to ship. The validator bug is the concrete,
fixable defect; the `_lexbfs` output on this specific input should be re-checked
after the validator is fixed (see hints).

## REPAIR_HINTS
1. **Fix `_is_valid_lexbfs` to the true (LB) property** — the smallest change:
   replace the `C`-set / `all(...)` logic with a per-triple check:
   ```python
   for a in range(n):
       va = ordering[a]
       for b in range(a + 1, n):
           vb = ordering[b]
           if vb in adj[va]:
               continue
           for c in range(b + 1, n):
               vc = ordering[c]
               if vc not in adj[va]:
                   continue
               # need some d < a with db in E and dc not in E
               if not any(vb in adj[ordering[d]] and vc not in adj[ordering[d]]
                          for d in range(a)):
                   return False
   return True
   ```
   (Existential over d inside the innermost loop; O(n^4) but exact.)

2. **Remove the unvalidated final return in `_recompute`**: after trying all
   starts, if none passes the (now-correct) validator, raise an error instead of
   `return _lexbfs(graph, start=0)`. Shipping an unvalidated ordering is what let
   the bad result out of `init`.

3. **After fixing the validator, re-trace `_lexbfs` on the failing input.** The
   refinement loop (take first vertex of first bucket, split each remaining bucket
   into neighbors-first / non-neighbors-second) is the standard HMPV scheme and
   should be correct; if the corrected validator still flags its output on this
   4-vertex graph, the bug is in `_lexbfs` itself (e.g., bucket ordering after
   splits) and must be traced on the concrete matrix. Do NOT "fix" this by
   weakening the validator further.

4. **Do not** try to "fix" the failure by changing the tie-break or start vertex
   selection in `_lexbfs` — the expected output `[0,3,2,1]` starts at 0, so start
   selection is not the issue.

5. Approaches that will not work: keeping the `all(vc not in adj[vd] for vc in C)`
   formulation (it is a different, stronger property); adding more start-vertex
   retries without fixing the validator (the final unvalidated return still
   bypasses all checks).
