# Reflection: gen007_c01 — dynamic_lbfs

## FAILURE_DESCRIPTION

- n = 3, operation at sequence_idx 1: `delete_edge(graph, (2, 0), state)`.
- Ordering returned (kept from before the update): `[0, 2, 1]`.
- Expected (any valid LexBFS of the post-deletion graph): `[0, 1, 2]`.
- Verifier violation: a=0 (pos 0), b=2 (pos 1), c=1 (pos 2), `minD = 1000000000` — i.e. the (LB) 4-point property fails: with ac=01 in E and ab=02 not in E, no d < a exists (a is first in the order, so the witness set is empty).

Reconstructed scenario (consistent with all reported fields):
- Before the update the graph had edges {01, 02, 12} (triangle). `_lexbfs` from start 0 produced `[0, 2, 1]` (after refining by 0, bucket {1,2} is unsplit; tie-break by (rank,id) picks 2 first).
- `delete_edge(graph, (2, 0), state)` is called with the graph already flipped to {01, 12} (path 0-1-2).
- `_local_delete_ok` returned True, so the stale ordering `[0, 2, 1]` was returned unchanged.
- In the new graph, `[0, 2, 1]` is invalid: 0-1 in E, 0-2 not in E, and 0 is at position 0 so no witness d can exist. The only valid orderings are `[0, 1, 2]` (and its mirror `[2, 1, 0]`).

## ROOT_CAUSE

The local deletion check in `_local_delete_ok` is unsound. It only inspects triples in which the deleted edge (u, v) played the role of the **witness edge db** (cases "d=u, b=v" / "d=v, b=u"). But deleting an edge can also **create** new failing triples in which (u, v) plays the role of the **ab edge** (the edge that must NOT be in E): for any triple (a, b, c) with b=u, c=v (or b=v, c=u) and pos(a) < pos(b) < pos(c), the condition "ac in E and ab not in E" becomes true *after* the deletion, and a witness d < a is required.

In the failing case, the deleted edge (2, 0) plays the role of ab: a=0 (pos 0), b=2 (pos 1), c=1 (pos 2). After deletion, 0-1 in E and 0-2 not in E, so the triple is triggered; the witness set {d : pos(d) < 0} is empty, so the property fails. `_local_delete_ok` never examines this triple (it only loops `a_idx in range(j+1, i)` with b=u fixed and checks witnesses for triples where u was the witness), so it returns True and the stale ordering is kept.

The same class of bug exists in `_local_insert_ok`: it only checks triples where the inserted edge plays the role of **ac**. An insertion can also *destroy* witnesses: for any triple (a, b, c) with d=u, b=v (or d=v, b=u) where (u, v) was the witness edge db, inserting (u, v) makes dc... more precisely makes the witness condition `db in E and dc not in E` fail for the witness d=u (db=uv is now in E, but the witness also needs dc not in E — if dc is in E the witness was already invalid; the real danger is that the insertion of uv changes the trigger condition for triples where uv plays the role of ab, making them newly triggered). Concretely, insertion of (u, v) with b=u, c=v (pos(a) < pos(u) < pos(v)) newly triggers triples where ac in E and au not in E — these are not checked either.

So the "local check" is missing two of the four roles the flipped edge can play in the 4-point property (ab on deletion; ab on insertion), which is why the candidate is incorrect.

## REPAIR_HINTS

1. **Smallest correct fix (recommended): stop trusting the local check and always recompute.** In `insert_edge` and `delete_edge`, unconditionally call `_recompute(graph, state)` and return its result. The static `_lexbfs` + `_is_valid_lexbfs` machinery is already present and correct (the failure is in the local check, not in the recompute path). This sacrifices the "avoid full recompute" research goal but restores full correctness immediately.

2. If a local fast path is desired, it must check **all** roles the flipped edge can play in the (LB) property, not just one:
   - Deletion of (u, v): (a) triples where (u, v) was the witness db (already handled), AND (b) triples where (u, v) is the ab edge — i.e. for b=u, c=v with pos(a) < pos(u) < pos(v) (and the mirror), check that a witness d < a with d·v in E and d·c not in E exists.
   - Insertion of (u, v): (a) triples where (u, v) is the ac edge (already handled), AND (b) triples where (u, v) is the ab edge — newly triggered triples with b=u, c=v (or b=v, c=u) and pos(a) < pos(b) < pos(c) and ac in E need a witness d < a.
   - Even then, a safer design is: run the local check, and if it passes, **verify** with the full O(n^3) `_is_valid_lexbfs(order, graph, n)` before returning the state unchanged. `_is_valid_lexbfs` already exists in the file and is correct; using it as a final gate makes the local check a pure optimization that cannot cause incorrectness.

3. **Approaches that will not work:**
   - Keeping the current `_local_delete_ok` / `_local_insert_ok` as-is: they are structurally incomplete (missing the ab-role cases) and will keep failing on cases like this one.
   - "Fixing" only the deletion case: the insertion path has the symmetric gap and will fail on analogous insertion cases.
   - Relying on the recompute hint (start = previous first vertex, rank = previous positions) to produce a valid ordering: `_lexbfs` is a correct static LexBFS for any start/tie-break, so the hint is harmless, but it is not a substitute for actually triggering the recompute.
