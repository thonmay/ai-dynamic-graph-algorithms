## FAILURE_DESCRIPTION
Crash at `sequence_idx: 0` (the very first operation, before any update) on a graph with `graph_n: 3`. The harness reports `IndexError: list index out of range at line 23: if row[w]:`. Line 23 is inside `_lexbfs_full`'s adjacency-building loop:

```python
for v in range(n):
    row = graph[v]
    for w in range(v + 1, n):
        if row[w]:          # <-- line 23, IndexError
```

So `row` (i.e. `graph[v]`) is shorter than `n` — the adjacency matrix passed to `init` is ragged: some row has fewer than `n` entries. The same pattern `for w in range(v + 1, n): if row[w]:` is repeated verbatim in `_check_valid`, so it would crash identically there.

## ROOT_CAUSE
Both `_lexbfs_full` and `_check_valid` assume the input is a perfectly square n×n matrix and index `row[w]` for `w` up to `n-1`. The failing input violates that assumption (a row is shorter than `n`), so `row[w]` raises `IndexError`. The crash happens in `init` → `_lexbfs_full` on the first call, so no update logic is even reached; the bug is purely the unguarded matrix read.

Note: the repair functions' slice arithmetic (e.g. `order[:pu] + [v] + order[pu:pv] + order[pv+1:]` when `pu > pv`) is also suspicious and would produce wrong-length orders, but that is NOT the cause of this failure — the crash precedes any repair call.

## REPAIR_HINTS
1. Make the adjacency read tolerant of ragged/short rows in BOTH `_lexbfs_full` and `_check_valid`. Replace
   `if row[w]:`
   with a bounds-checked read, e.g.
   `if w < len(row) and row[w]:`
   (treat missing entries as 0 / non-edge). This is the minimal change that fixes the crash.
2. Do NOT "fix" this by asserting the matrix is square or by raising a clearer error — the harness feeds ragged matrices and expects a valid ordering back, so the code must handle them.
3. After fixing the crash, re-verify the repair slice expressions in `_try_repair_insert`/`_try_repair_delete` for the `pu > pv` case: several slices (e.g. `order[:pu] + [v] + order[pu:pv] + order[pv+1:]` with `pu > pv`) drop or duplicate elements and yield lists of length ≠ n, which would then either fail `_check_valid`'s `pos` indexing or silently corrupt the ordering. The fallback `_lexbfs_full` only saves the case when repair returns `None`; a wrong-length `new_order` that happens to pass `_check_valid` (or that crashes `_check_valid` on `pos[v]`) is a second latent bug to fix in the same pass.
4. Approaches that will not work: recomputing `n` from `len(graph)` only (rows can still be short); assuming symmetry to pad rows (the matrix may be ragged in a way that breaks symmetry too — just index defensively).
