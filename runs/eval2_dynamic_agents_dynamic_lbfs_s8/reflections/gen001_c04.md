## FAILURE_DESCRIPTION
3-vertex undirected graph. Sequence: init on the empty graph (no edges), then `insert_edge(graph, (0,2), state)`. After the insertion the graph has exactly one edge, 0-2. The verifier reports the maintained ordering `[0, 1, 2]` is invalid: 4-point violation with a=0 (pos 0), b=1 (pos 1), c=2 (pos 2) — ac=02 in E, ab=01 not in E, and no d < a exists (minD = 1000000000 sentinel). Expected a valid ordering, e.g. `[0, 2, 1]` (or `[1, 0, 2]`, `[2, 0, 1]`, etc.).

## ROOT_CAUSE
The static `_lexbfs` itself is broken; it is not a LexBFS algorithm. It is a greedy "pick the lexicographically smallest label, then append `(pos, best)` to the labels of best's remaining neighbors" loop. That is not partition refinement:

1. **No partitioning / no label sharing.** In real LexBFS, all vertices in the same bucket share one label, and a refinement splits a bucket into sub-buckets. Here each vertex has its own independent label list, so the "smallest label" choice is just a greedy vertex selection with no bucket structure.
2. **Labels are never reset.** In LexBFS, when a vertex is selected, the labels of the *remaining* vertices are reset (the selected vertex's position becomes the new first entry for every remaining vertex, and only neighbors get the extra marker). Here `labels[w] = labels[w] + [(pos, best)]` only *appends* for neighbors and leaves non-neighbor labels untouched, so old markers from earlier selections accumulate and dominate the ordering.

Tracing the failing case: after init on the empty graph, `_lexbfs` returns `[0, 1, 2]` (all labels equal, ties broken by vertex id). `insert_edge` calls `_lexbfs` on the graph with edge 0-2:
- remaining = [0,1,2], all labels `[(0,v)]`. Pick 0 (smallest). pos=1. Neighbor 2 gets label `[(0,2),(1,0)]`; 1 keeps `[(0,1)]`.
- Pick min of {1,2}: compare `[(0,1)]` vs `[(0,2),(1,0)]` → 1 wins (0,1) < (0,2). order = [0,1]. pos=2. 1's neighbors among remaining: none (1 is isolated).
- Pick 2. order = [0,1,2].

Result `[0,1,2]` violates the (LB) property: a=0, b=1, c=2, ac in E, ab not in E, no d < a. A correct LexBFS on this graph would pick 0, then 2 (the only neighbor of 0), then 1 → `[0,2,1]`.

Note the candidate's own `_is_lexbfs` would correctly have detected this violation, but it is only called in `delete_edge`, never after `insert_edge` (which unconditionally trusts `_lexbfs`). So the bug is the static algorithm, not the dynamic policy.

## REPAIR_HINTS
Replace `_lexbfs` with the actual Habib–McConnell–Paul–Viennot partition-refinement LexBFS on the adjacency matrix:

- Maintain a list of buckets (each bucket = list of vertices sharing one label). Initialize with one bucket containing all vertices.
- Labels: for each vertex v, a list of (position, vertex) pairs, initially `[(0, v)]`.
- Repeatedly: take the first bucket, pick its first vertex v (any deterministic tie-break), append v to the order, remove v from the bucket (drop the bucket if empty). Then **reset**: for every remaining vertex w, set `labels[w] = [(pos, v)]` (pos = len(order)); then for each remaining neighbor w of v, append `(pos, v)` again — i.e. neighbors get a label with a repeated marker, non-neighbors get the single marker. Split each bucket into (non-neighbor part, neighbor part) accordingly, preserving relative order, and put the non-neighbor part first.
- The key missing pieces in the current code are (a) shared labels per bucket with bucket splitting, and (b) the per-selection label reset for all remaining vertices.

Smallest concrete change: rewrite `_lexbfs` (lines 14–33) as the standard O(n^2) matrix LexBFS above. The dynamic policy (`insert_edge` recomputes, `delete_edge` verifies with `_is_lexbfs` then recomputes) is fine and can stay as-is once `_lexbfs` is correct — `_is_lexbfs` itself is a correct implementation of the (LB) property and can be kept as a safety net.

Approaches that will not work:
- Keeping the current per-vertex independent-label greedy scheme and just adding a reset — without bucket structure and shared labels, the "smallest label" selection is not LexBFS.
- Relying on `_is_lexbfs` to filter bad outputs of the broken `_lexbfs` — it would pass on the empty graph but the recompute path in `insert_edge` never calls it; and even if it did, you'd need a correct fallback anyway.
