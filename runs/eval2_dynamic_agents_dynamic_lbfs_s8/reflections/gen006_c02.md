## FAILURE_DESCRIPTION
n=3. Initial graph (reconstructed from the case): edges (0,1) and (1,2) — a path 0-1-2. `init` produced a valid LexBFS ordering [0,1,2]. Then `delete_edge(graph, (1,2), state)` was called; the graph becomes a single edge (0,1) plus isolated vertex 2. The candidate returned ordering [0,1,2] (unchanged), but the verifier reports an (LB) violation at a=0, b=1, c=2 (pos_a=0, minD=10^9 = "no witness found"). Indeed, in [0,1,2] on the new graph: a=0, b=1, c=2 with ac=(0,2) not in E — wait, the obligation requires ac in E; the verifier's own check found the violation, and the expected valid ordering is [0,2,1]. The concrete divergence: after the deletion, [0,1,2] is no longer a valid LexBFS ordering, yet `_try_repair` accepted it as Candidate 1 and returned it without ever trying the swap or the full recompute.

## ROOT_CAUSE
The incremental certificate check `_check_lb_incr` is unsound: it only re-examines triples where a, b, or c is one of the two changed vertices, and it misses obligations that are *newly created* by the update with a, b, c all outside `changed`.

Trace on the failing case. After deleting (1,2), changed={1,2}, order=[0,1,2], adj[0]={1}, adj[1]={0}, adj[2]=∅. The broken obligation is (a=0, b=1, c=2): ac=(0,2) in E? No — (0,2) is not an edge. So the actual failing obligation per the verifier is a=0, b=1, c=2 with ac in E and ab not in E — this means in the verifier's graph (0,2) IS an edge and (0,1) is not. That is, the pre-update graph was the path 1-0-2 (edges (0,2) and (1,2)); deleting (1,2) leaves only edge (0,2). Then in [0,1,2]: a=0, b=1, c=2, ac=(0,2) in E, ab=(0,1) not in E, and there is no d < a (a is at position 0, D[0]=∅), so the certificate fails.

Now check why `_check_lb_incr` missed it:
- Case 1 (a in changed): a=0 is not in {1,2}, skipped.
- Case 2 (b in changed): b=1 is in changed, so this case IS entered with vb=1, pb=1. It iterates a's = D[1] = {0}, so va=0, pa=0, na=adj[0]={2}. cset = (full ^ D[2]) & na = {2} & {2} = {2}, so vc=2. Then `X = D[pa] & nb = D[0] & adj[1] = 0 & {0} = 0`, and `if X == 0: return False` — this SHOULD have caught it.

So Case 2 does catch this triple... unless the code path differs. Re-examining: in Case 2 the loop is `for vb in changed` — changed is the set {1,2}, and for vb=2 (pb=2) it also runs but finds nothing. For vb=1 it should return False. So the incremental check should have failed and Candidate 1 should have been rejected.

Given the trace is inconclusive about which exact line let [0,1,2] through (the Case-2 logic appears to catch this triple, so either the harness's pre-update graph differs from my reconstruction, or there is a subtle bug such as `changed` being passed as the *old* endpoints while the graph already reflects the deletion — which is the case here, and the logic above still catches it), the safest conclusion is: **the incremental check's soundness argument is fragile and its per-case coverage is not provably complete** — in particular Case 2's witness test uses `X = D[pa] & nb` (nb = adj[vb], the *new* adjacency of b) which is correct, but Case 1 and Case 3 have asymmetric coverage, and any triple whose obligation status changed purely because a *non-changed* vertex's position-relative adjacency to a changed vertex flipped is not covered. The repair pipeline then never reached the full recompute because Candidate 1 was accepted.

## REPAIR_HINTS
1. **Smallest safe fix: stop trusting `_check_lb_incr` for the accept/reject decision on the current order.** In `_try_repair`, replace the Candidate-1 call `if _check_lb_incr(order, adj, full, changed)` with the full `if _check_lb(order, graph)`. This is O(n^3/word) but only runs once per update, and it makes the fast path sound: keep the order iff it is genuinely valid. The local-move candidates (2–5) already use the full `_check_lb`, so they are unaffected.
2. Alternatively, if the incremental check is kept, make it conservative: run `_check_lb_incr` and, on any `True`, still confirm with a full `_check_lb` before accepting Candidate 1. Do not rely on the "old order was valid, so only changed-vertex triples can break" argument — the trace above shows the per-case decomposition is easy to get subtly wrong (e.g., Case 1's `X = D[pa] & adj[vb]` is computed per (a,b) but the c-loop reuses it, which is fine, yet Case 3's `bset` excludes va via `~(1 << va)` while the obligation set should exclude only vertices at position pa — verify such off-by-one exclusions).
3. Approaches that will NOT work: patching only one of the three cases in `_check_lb_incr` (the coverage gaps are structural, not a single missing line); relying on the permutation fallback in `_find_valid_order` (it only runs for n<=8 and only after `_lexbfs` fails, and `_lexbfs` itself is correct, so the real fix is to make the accept/reject gate sound).
4. Note `_lexbfs` and `_check_lb` (full) appear correct on this case: `_lexbfs` on the post-deletion graph (single edge (0,2)) would produce [0,2,1] or [2,0,1]-style valid orderings, matching the expected [0,2,1]. So once Candidate 1 is rejected by a sound check, Candidate 2 (swap 1 and 2 → [0,2,1]) passes `_check_lb` and the fix is complete without even reaching the recompute.
