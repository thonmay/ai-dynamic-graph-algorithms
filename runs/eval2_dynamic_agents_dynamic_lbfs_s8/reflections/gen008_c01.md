## ROOT_CAUSE
The fast path in `insert_edge` trusts `_is_lexbfs(graph, order)` to detect the invalidation, but `_is_lexbfs` has a bug that makes it return `True` for this invalid ordering.

The witness test is:
```python
if not (P[i] & nb & Z[c]):
    return False
```
where `Z[c] = N[c] ^ ((1 << n) - 1)`. The flaw: `Z[c]` contains the bit for **c itself** (the diagonal is 0 in the adjacency matrix, so c is its own "non-neighbor"). The witness d must satisfy d < a (positions), i.e. d ∈ {order[t] : t < i} = the set of bits in `P[i]`. In the failing case, P[i] for i=1 (a=1) is N[0] = {1,2,3} (after the insertion). The true witness set is P[i] & N[b] & Z[c] = {1,2,3} & {0,3} & Z[3]. Z[3] = complement of N[3]={0,1} = {2,3}. Intersection = {3} — non-empty, so the check passes. But the only "witness" is d=c=3 itself, which is at position k > i, not d < a. The bit for c in Z[c] (and symmetrically, bits for a and b can leak in via N[b] containing b? no — N[b] never contains b, but Z[c] always contains c) lets the test be satisfied by an out-of-range vertex.

Concretely: `Z[c]` should be masked to exclude c (and ideally the test should intersect with the prefix set P[i], which it does, but P[i] can contain c's bit only if some earlier vertex is adjacent to c — here 0 is adjacent to 3, so bit 3 is in P[1]). The self-bit of c in Z[c] is what makes `P[i] & N[b] & Z[c]` non-zero spuriously.

Fix the mask: `Z[c]` must be `((1 << n) - 1) ^ N[c] ^ (1 << c)` (exclude c itself). With that, Z[3] = {2}, and P[1] & N[3] & Z[3] = {1,2,3} & {0,3} & {2} = ∅ → the check correctly returns False, triggering the recompute to `[0,1,3,2]`.

## REPAIR_HINTS
1. **Primary fix (the bug):** In `_is_lexbfs`, exclude c from its own non-neighbor set. Change
   ```python
   Z[v] = bits ^ ((1 << n) - 1)
   ```
   to
   ```python
   Z[v] = (bits ^ ((1 << n) - 1)) & ~(1 << v)
   ```
   This removes the self-bit so the witness test can no longer be satisfied by d=c. With this fix, the failing case's spurious witness disappears, `_is_lexbfs` returns False, and the recompute path produces a valid ordering.

2. **Defense in depth (optional but recommended):** Also mask out a and b from the witness intersection, since the property requires d distinct from a, b, c and d < a. The position constraint d < a is already enforced by intersecting with P[i] (vertices before position i), but only if the bitset correctly represents vertex ids of earlier positions — which it does. The self-bit of c is the only leak, because c's id can appear in P[i] (as a neighbor of an earlier vertex) while c itself is at position k > i. Masking a and b is unnecessary: a ∉ N[a]... actually a could be in P[i]? No, P[i] contains neighbors of order[t] for t < i; a = order[i] is not among those, but a's *id* could appear in P[i] if some earlier vertex is adjacent to a. Then d=a would need da ∈ E (self-loop, false) so it's already excluded by N[b]... no, d=a requires a ∈ N[b] (ba ∈ E, but we're in the ab ∉ E branch, so a ∉ N[b]). So a is already excluded. b: d=b requires b ∈ N[b] (self-loop, false). So only c leaks, via Z[c]'s self-bit. Fix #1 is sufficient.

3. **Do NOT** try to "fix" this by special-casing the insert/delete logic or by always recomputing — the recompute path (`_lexbfs`) is correct; the bug is purely in the verifier `_is_lexbfs` accepting an invalid ordering.

4. **Verification after fix:** On the failing case, after the fix, `_is_lexbfs` must return False for the stale ordering, triggering `_lexbfs` which produces a valid ordering (e.g. [0,1,3,2]). Also sanity-check that `_is_lexbfs` still returns True for genuinely valid orderings (the fix only removes a spurious witness, never a real one, since a real witness d < a has d ≠ c).
