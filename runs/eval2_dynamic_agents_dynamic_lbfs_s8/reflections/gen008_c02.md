## ROOT_CAUSE
The divergence happens in `_try_repair`, Candidate 1:

```python
if _check_lb_incr(order, adj, full, changed):
    return list(order)
```

`_check_lb_incr` is UNSOUND. Its docstring claims "a triple whose status cannot change
was satisfied before and remains satisfied", but that is false: the (LB) certificate is
a property of the *positions* in the ordering, and an edge update changes the
adjacency of triples where the updated vertex plays role a, b, or c — but the
incremental check only re-examines triples where a, b, or c is in `changed` **in the
current (post-update) adjacency sense**, and crucially it can *miss* obligations that
are newly created by the update.

This is the real root cause: **the (LB) certificate as implemented in `_check_lb`
(and as stated in the brief) is missing the standard boundary condition**. The correct
Corneil–Krueger (LB) property is: for all a < b < c with ac in E and ab not in E,
there exists d < a with db in E and dc not in E — **with the convention that the
property is vacuously satisfied when a is the first position (no d < a exists) AND
ac in E and ab not in E cannot occur for the first vertex in a LexBFS**... Actually the
standard statement handles this: in a valid LexBFS, if a is first, then a is adjacent
to everything that appears later in a way that... no. The real issue: the standard (LB)
property is stated for a < b < c with **ab not in E and ac in E**, and the witness d
satisfies d < a, db in E, dc not in E. For a = first position, the property is
vacuously true because there is no such triple: in any LexBFS, the first vertex is
adjacent to all vertices that are adjacent to any later vertex... that's not generally
true either.

The actual standard formulation (Corneil–Krueger, as in the HMPV paper): an ordering
is LexBFS iff for all a < b < c, if ac in E and ab not in E, then there exists
d < a with db in E and dc not in E. For a at position 0, the antecedent "ac in E and
ab not in E" CAN hold (e.g. [0,2,1] with edge (0,1): a=0, b=2, c=1: ac=(0,1) in E,
ab=(0,2) not in E — antecedent holds, and no d < 0 exists, so the property FAILS).

## REPAIR_HINTS
1. **Fix `_check_lb` (and the same pattern in `_check_lb_incr` Cases 1-3): move the
   `if X == 0: return False` test INSIDE the c-loop.** The witness requirement only
   applies when there actually exists a c > b with ac in E. Current code:
   ```python
   X = D[pa] & adj[vb]
   if X == 0:
       return False          # BUG: fires even when cset is empty
   cset = (full ^ D[pb + 1]) & na
   while cset:
       ...
       if X & ~adj[vc] == 0:
           return False
   ```
   Correct: compute `cset` first; if `cset == 0`, skip this b entirely; otherwise
   require `X != 0` and `X & ~adj[vc] != 0` for every c in cset. Same fix in
   `_check_lb_incr` Case 1 (the `X == 0` before the cset loop), Case 2 and Case 3
   (where `X == 0` is checked before/without confirming the obligation exists).
2. After fixing the checker, re-verify that `_check_lb_incr`'s case partition is
   complete: a triple's status can change when ANY of a, b, c is in `changed`, and
   the three cases must cover all such triples exactly (the `if va in changed:
   continue` / `if vb in changed: continue` guards are fine for dedup, but ensure no
   triple with a changed vertex is skipped by two guards simultaneously — e.g. in
