# Reflection: gen001_c01

## FAILURE_DESCRIPTION
Operation: `insert (0, 3)` at sequence index 2 on a 4-vertex graph.
- Resulting ordering returned: `[0, 1, 2, 3]`
- Expected (valid) ordering: `[0, 1, 3, 2]`
- Reported violation: a=1, b=2, c=3 (positions pos_a=1, minD=1e9, i.e. no witness d found).

The verifier's 4-point check found a triple (a,b,c) = (1,2,3) in the returned
ordering `[0,1,2,3]` such that:
- `a=1` is NOT adjacent to `b=2` (ab not in E),
- `a=1` IS adjacent to `c=3` (ac in E),
- no `d` before position 1 (only d=0) satisfies `d~b and not d~c`.

This means the returned ordering is NOT a valid LexBFS ordering.

## ROOT_CAUSE
The bug is in `_lexbfs_full`. The label-update loop runs AFTER the
frontier-expansion loop, but the expansion loop marks neighbors as
`visited[v] = True` immediately. So when the label loop checks
`if not visited[v]`, the just-discovered neighbors are already marked
visited and their labels are NEVER updated.

Specifically, in `_lexbfs_full`:
```python
nbrs = [v for v in range(n) if graph[best][v] and not visited[v]]
for v in nbrs:
    visited[v] = True          # <-- marks visited
    frontier.append(v)
for v in range(n):
    if not visited[v]:         # <-- these neighbors are now visited!
        if graph[best][v]:
            labels[v] = labels[v] | frozenset([best])
```

The label update should apply to the neighbors that were just discovered
(i.e., the `nbrs` list), not to vertices that are still unvisited. The
correct logic is: when vertex `best` is processed, every unvisited neighbor
gets `best` added to its label set. But since `visited` is set to True
before the label loop, the condition `not visited[v]` excludes exactly the
vertices that should receive the label.

This causes the algorithm to produce an ordering that is NOT a valid
LexBFS. The `_is_valid_lexbfs` check in `insert_edge`/`delete_edge` is
supposed to catch this and trigger a full recompute, but the recompute
calls the same buggy `_lexbfs_full`, so it produces the same invalid
ordering. The fallback is therefore useless.

## REPAIR_HINTS
1. **Fix `_lexbfs_full` label update**: The label update must apply to the
   neighbors that were just discovered (the `nbrs` list), not to all
   unvisited vertices. Change the label loop to:
   ```python
   for v in nbrs:
       labels[v] = labels[v] | frozenset([best])
   ```
   Remove the separate `for v in range(n): if not visited[v]: ...` loop
   entirely, or change it to iterate over `nbrs`.

2. **Alternative correct approach**: Use the standard partition-refinement
   LexBFS (Habib-McConnell-Paul-Viennot) which maintains a list of
   unvisited vertices partitioned by their adjacency to already-processed
   vertices. This avoids the label-tracking bug entirely.

3. **Do NOT** rely on the `_is_valid_lexbfs` fallback to mask a broken
   `_lexbfs_full` — the fallback calls the same broken function.

4. The `_try_repair` heuristic is fine as a fast path; the critical fix is
   making `_lexbfs_full` correct so the fallback actually works.
