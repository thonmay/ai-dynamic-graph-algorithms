## FAILURE_DESCRIPTION
n=3. Initial graph is the empty graph (no edges); `init` returns ordering `[0, 1, 2]` (valid for the empty graph). The update is `insert (0, 2)`, so the graph becomes a single edge {0,2}. The candidate returned `[0, 1, 2]` (it kept the old ordering because `_is_valid_lexbfs` returned True). The verifier reports a (LB) 4-point violation at positions a=0, b=1, c=2 (vertices 0, 1, 2): ac=(0,2) is in E, ab=(0,1) is not in E, and no d < a exists (minD = 1e9 sentinel). The expected valid ordering is `[0, 2, 1]` (or `[2, 0, 1]`).

## ROOT_CAUSE
The static `_lexbfs` is correct, but the cheap validity check `_is_valid_lexbfs` is wrong, so the "keep the old ordering" fast path is unsound.

The (LB) 4-point property is: for all positions a < b < c with ac in E and ab not in E, there exists d < a with db in E and dc not in E. The candidate's code handles the case W = {d < a : db in E} non-empty correctly, but the empty-W branch is inverted:

```python
W = [p2v[d] for d in range(a) if vb in adj[p2v[d]]]
if not W:
    # If any c > b with ac in E, violation
    for c in range(b + 1, n):
        if p2v[c] in adj[va]:
            return False
    continue
```

When W is empty, the property's existential ("there exists d < a ...") is vacuously false, so ANY c > b with ac in E is a violation. The code does flag that, but only for the single (a, b) pair currently being examined; it then `continue`s and never re-checks the same a against other b values. More importantly, the check is applied per (a,b) pair in isolation, which is fine for that pair, but the real bug is that the check as written is actually the correct per-pair test — the divergence happens because the check is being run on the OLD ordering `[0,1,2]` against the NEW graph and it should have caught a=0,b=1,c=2.

Tracing the failing case through `_is_valid_lexbfs(graph, [0,1,2])` with E={(0,2)}:
- a=0, va=0. b=1, vb=1. 1 not in adj[0] (ab not in E). W = [p2v[d] for d in range(0) ...] = [] (empty). Then the loop `for c in range(2, 3)`: c=2, vc=2, 2 in adj[0] → `return False`.

So the check SHOULD have returned False and triggered a recompute. The fact that the candidate returned `[0, 1, 2]` means the check returned True. The only way that happens is if the adjacency sets were built from a graph that does NOT contain edge (0,2).

The responsible lines are the adjacency construction in `_is_valid_lexbfs`:

```python
adj = [set() for _ in range(n)]
for i in range(n):
    row = graph[i]
    for j in range(i + 1, n):
        if row[j]:
            adj[i].add(j)
            adj[j].add(i)
```

This reads `graph[i][j]` for j > i only. If the harness passes the graph with the edge stored only in the upper triangle (graph[0][2]=1, graph[2][0]=0) — i.e., the matrix is not guaranteed symmetric at the moment of the call, or the update is applied to only one entry — then `adj` misses the edge and the check passes. The same construction pattern is used in `_lexbfs`, so a recompute would also produce a wrong ordering.

Given the failing case shows `result == expected` is false with result `[0,1,2]` (the pre-update ordering), the check returned True, which is only possible if the edge (0,2) was not visible to the adjacency construction. Root cause: the adjacency is built from the upper triangle only (`for j in range(i + 1, n)`), so a single-entry matrix flip (legal per the interface: "A legal update flips exactly one matrix entry") is missed when the flipped entry is in the lower triangle (graph[2][0]=1, graph[0][2]=0).

## REPAIR_HINTS
1. Build adjacency from BOTH triangles (or just read the full row): replace the `for j in range(i + 1, n)` loops in both `_lexbfs` and `_is_valid_lexbfs` with `for j in range(n): if i != j and row[j]: adj[i].add(j)`. This makes the code robust to non-symmetric input matrices where only one entry of an edge is set.
2. Alternatively, symmetrize the graph at the top of each function: `graph[i][j] = graph[j][i] = max(graph[i][j], graph[j][i])` before building adj.
3. Do NOT "fix" this by changing the (LB) property check logic — the per-pair check is actually correct; the bug is purely in how adjacency is read from the matrix.
4. The empty-W branch logic (`if not W: ... return False if any c>b with ac in E`) is correct and should be left as-is.
