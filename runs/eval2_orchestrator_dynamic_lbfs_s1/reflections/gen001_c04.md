## FAILURE_DESCRIPTION
Operation: `init` on a 4-vertex undirected graph (sequence_idx 0, so no prior state is involved).
`init` returned ordering `[0, 1, 2, 3]`; the verifier expected a valid LexBFS ordering, e.g. `[0, 1, 3, 2]`.
The returned ordering violates the (LB) 4-point property at (a, b, c) = (0, 2, 3) with pos_a = 0:
- a=0 at pos 0, b=2 at pos 2, c=3 at pos 3 (a < b < c)
- ac in E (0-3 is an edge), ab not in E (0-2 is not an edge)
- required: some d at position < 0 with db in E and dc not in E — impossible because a is at position 0, so no d exists.
The violation record's `minD: 1` is consistent: the earliest position at which a witness d could exist is 1, but the property demands d strictly before a (pos 0), so the certificate fails.

## ROOT_CAUSE
The bug is in the static `_lexbfs` partition refinement, not in the dynamic repair path (which never runs on `init`).

The candidate implements the "split all remaining buckets by N(u)" variant of LexBFS, but it does so incorrectly. After picking `u = B[0]`, it does:

```python
all_buckets = [B] + list(Q)
...
n_parts = []
nonn_parts = []
for bucket in all_buckets:
    n_part = [v for v in bucket if graph[u][v]]
    nonn_part = [v for v in bucket if not graph[u][v]]
    ...
for part in n_parts + nonn_parts:
    Q.append(part)
```

Two defects:

1. **The N(u) parts are not placed at the front of the queue.** The correct algorithm (Habib–McConnell–Paul–Viennot) requires that after processing u, the queue order is: the N(u)-part of the *current* bucket B first, then the N(u)-parts of the other buckets in their old relative order, then all the non-N(u) parts in their old relative order. Here the code appends `n_parts + nonn_parts`, which interleaves the N(u)-parts of *later* buckets ahead of the non-N(u)-part of the *current* bucket B. That reorders the queue incorrectly.

2. **The current bucket's own N(u)-part is not prioritized.** In the correct algorithm, the N(u)-part of the bucket from which u was taken must come first (it is the "front" of the queue). The code treats B's N(u)-part the same as any other bucket's N(u)-part.

Concretely, on the failing graph the refinement produces `[0, 1, 2, 3]` instead of `[0, 1, 3, 2]` because the queue ordering after processing vertex 0 (or 1) places the bucket containing 2 ahead of the bucket containing 3, when the correct LexBFS refinement would place 3's bucket first.

The `_is_valid_lexbfs` checker itself is correct (it faithfully implements the 4-point property), and `_try_local_repair` is sound *if* it is ever called with a valid starting ordering — but on `init` it is never called, so the flawed `_lexbfs` output is returned directly.

## REPAIR_HINTS
Fix `_lexbfs` to implement the correct HMPV partition-refinement queue discipline:

1. When processing bucket B (popping from the front of Q), take u = B[0], remove u, and split B into B_N = {v in B : uv in E} and B_nonN = {v in B : uv not in E}.
2. For every *other* bucket in Q (in order), split it into its N(u)-part and non-N(u)-part.
3. Rebuild the queue as:
   - B_N (if non-empty) — **first**,
   - then, for each other bucket in its original order, its N(u)-part (if non-empty),
   - then, for each bucket in its original order, its non-N(u)-part (if non-empty),
   - and B_nonN (if non-empty) goes in the "non-N(u) parts" section, at the position corresponding to B's original slot (i.e., first among the non-N(u) parts, since B was the front bucket).

The minimal concrete change: replace the `for part in n_parts + nonn_parts` loop with a loop that (a) emits B's N(u)-part first, (b) emits the N(u)-parts of the remaining buckets in order, (c) emits B's non-N(u)-part, then the non-N(u)-parts of the remaining buckets in order.

Do **not** try to "fix" this by adding a post-hoc `_is_valid_lexbfs` check in `init` and falling back to a different tie-break — the root cause is the queue discipline, and any correct HMPV implementation will produce a valid ordering without needing a fallback.

Also note: the local-repair path in `insert_edge`/`delete_edge` is only sound if the input `state['ordering']` is already a valid LexBFS ordering. Once `_lexbfs` is fixed, `init` will produce a valid ordering and the repair path's soundness argument holds.
