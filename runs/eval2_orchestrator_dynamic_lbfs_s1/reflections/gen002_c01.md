# Reflection: gen002_c01

## FAILURE_DESCRIPTION

Failing case (sequence_idx 2, operation `insert (0, 3)` on a 4-vertex undirected graph):
- Returned ordering: `[0, 1, 2, 3]`
- Expected (valid) ordering: `[0, 1, 3, 2]`
- Reported 4-point violation: `a=1, b=2, c=3` at `pos_a=1`, with `minD = 10**9` (sentinel meaning **no witness d was found at all**).

Interpreting the violation: in the returned order, vertex 1 is at position 1, vertex 2 at position 2, vertex 3 at position 3. The checker found a triple (a=1, b=2, c=3) with `1~3 in E`, `1~2 not in E`, and **no** vertex d before position 1 (i.e. d=0) satisfying `d~2 in E` and `d~3 not in E`. So the returned ordering is not a valid LexBFS ordering.

## ROOT_CAUSE

The candidate's design is "try a cheap local repair; if the repair fails the O(n^2) 4-point check, fall back to a full recompute." The fallback is supposed to guarantee correctness. The bug is that **the fallback is never triggered on this case**, because the local repair *succeeds* and the repaired ordering *passes* `_is_valid_lexbfs` — yet the ordering the harness actually observes is still invalid.

Two concrete defects combine:

1. **`_try_repair` (insertion branch) returns a single local move and stops.** It iterates candidate `(a, c)` orientations and `w` in vertex-id order, and on the *first* detected violation it does `return _move_before(order, w, a)`. It never checks whether that one move actually resolves the violation, and it never looks for other violations. A single move can fix one 4-point triple while leaving (or creating) another.

2. **The verification gate is the real safety net, and it is the part that must be scrutinised.** In `insert_edge`:
   ```python
   repaired = _try_repair(order, pos, graph, edge, inserted=True)
   if repaired is not None and _is_valid_lexbfs(repaired, graph):
       return _make_state(repaired)
   return _make_state(_lexbfs_full(graph))
   ```
   For the harness to observe an invalid ordering, one of these must hold:
   - (a) `_is_valid_lexbfs(repaired, graph)` returned `True` on an ordering that is actually invalid (checker/verifier disagreement), or
   - (b) `_lexbfs_full(graph)` itself produced an invalid ordering (the fallback is not actually correct), or
   - (c) the `graph` matrix passed to `insert_edge` at call time differs from the graph the harness uses to verify (e.g. the harness verifies against a graph state that is one update ahead/behind the matrix handed to the candidate).

   The `minD = 10**9` sentinel in the violation record strongly suggests the harness's checker uses a *different* sentinel/loop than `_is_valid_lexbfs`, which makes (a) plausible: the two checkers may not be checking the identical property (e.g. one checks the (LB) 4-point property, the other checks a related but distinct certificate, or they differ on the boundary condition `d < a` vs `d <= a`, or on whether `a` itself can serve as witness).

   I cannot fully disambiguate (a) vs (b) vs (c) from the information given, but the *structural* root cause is clear: **the candidate trusts a local heuristic repair plus a self-written validator, and the self-written validator is not guaranteed to agree with the harness's checker.** The docstring's claim "Correctness is guaranteed by the fallback" only holds if `_lexbfs_full` is correct AND `_is_valid_lexbfs` is a sound certificate for the harness's notion of validity. Either of those assumptions is broken on this case.

## REPAIR_HINTS

Smallest concrete changes, in priority order:

1. **Make the fallback unconditional and the repair purely an optimisation that is *never* trusted without an independent, harness-matching certificate.** Concretely:
   - In `insert_edge` / `delete_edge`, after computing `repaired`, run the *harness's* 4-point check (not the candidate's own `_is_valid_lexbfs`) before accepting it. If the harness checker is not available in-process, the safest fix is to **drop the repair path entirely** and always return `_make_state(_lexbfs_full(graph))`. This is O(n^2) per update but is the only change that is guaranteed to restore correctness given the current evidence.

2. **If the repair path must stay, make it exhaustive, not single-move.** Replace the early `return _move_before(order, w, a)` in `_try_repair` with a loop that (i) collects *all* currently-violating triples, (ii) applies a candidate move, (iii) re-checks *all* triples, and (iv) only accepts the move if the set of violations is strictly smaller (ideally empty). Repeat until a fixed point or give up and fall back.

3. **Audit `_lexbfs_full` for correctness.** The current implementation uses a `frontier` list and a `labels` dict of frozensets, updating labels *after* appending neighbours to the frontier. This is not the standard partition-refinement LexBFS; it is a home-grown variant that may not produce a valid LexBFS ordering in general. The safest fix is to replace `_lexbfs_full` with a textbook O(n^2) LexBFS (e.g. the simple "pick the unvisited vertex with the lexicographically smallest label vector, tie-break by id" loop, updating labels of unvisited neighbours after each pick). Verify the replacement against the harness checker on a battery of random graphs before trusting it.

4. **Do NOT** try to "fix" `_is_valid_lexbfs` by tweaking its loop bounds or sentinel — that is guessing at the harness checker's exact semantics. The correct move is to either (i) match the harness checker exactly (if its source is available) or (ii) stop relying on the self-written checker as a gate and always fall back to a verified-correct recompute.

Approaches that will NOT work:
- Tightening the repair heuristic (more candidate moves, smarter tie-breaks) without fixing the validator/fallback: the heuristic is unbounded in the number of violations it can miss, and the validator is the part that is actually failing.
- Caching the previous ordering and doing incremental label updates: this is the open research problem the brief flags; it is not a repair for this bug.
