## FAILURE_DESCRIPTION
The candidate crashed (operation "crash") on a 3-vertex graph during the very first update, `insert_edge` with `edge=(0, 2)` (sequence_idx 0). The verifier reported `RuntimeError: DEBUG-STOP at line 48: raise RuntimeError("DEBUG-STOP")`. No ordering was ever returned for that update, so the test failed with an exception rather than a wrong answer.

## ROOT_CAUSE
The failure is not an algorithmic bug in the LexBFS logic — it is a leftover debug trap embedded in the candidate. The function `_debug_dump` (lines 33–48) unconditionally writes diagnostics to stderr on every `insert_edge`/`delete_edge` call, and contains a hard-coded abort:

```python
    if n == 3 and tag.startswith("insert_edge edge=(0, 2)"):
        import traceback
        sys.stderr.write("TRACEBACK:\n" + traceback.format_stack()[-6:-1].__str__() + "\n")
        raise RuntimeError("DEBUG-STOP")
```

`insert_edge` calls `_debug_dump(f"insert_edge edge={edge} valid={valid}", graph, ordering)` on every invocation. For the failing case (n=3, edge=(0,2)) the tag is `"insert_edge edge=(0, 2) valid=..."`, which matches the condition, so the function raises `RuntimeError("DEBUG-STOP")` before `insert_edge` can return any state. The exception propagates out of `insert_edge` and the verifier records a crash.

Note the tag format: `edge` is a tuple, so `f"insert_edge edge={edge}"` renders as `insert_edge edge=(0, 2)` — exactly what the `startswith` check matches.

The actual LexBFS/check logic (`_lexbfs`, `_is_valid_lexbfs`, `_adjacency`) was never reached for this case; the crash happens before the validity decision.

## REPAIR_HINTS
1. **Delete the entire `_debug_dump` function and both of its call sites** (one in `insert_edge`, one in `delete_edge`). This is the minimal fix: the rest of the code path (`_is_valid_lexbfs` → keep or recompute via `_lexbfs`) is untouched and was presumably working.
2. Do NOT keep any `sys.stderr` writes or `traceback` imports in the final candidate — the verifier treats any exception as a crash.
3. After removing the debug code, re-verify the n=3 insert_edge(0,2) case end-to-end: the ordering from `init` should be checked by `_is_valid_lexbfs` against the post-insertion matrix, and either kept or recomputed.
4. Approaches that will not work: patching only the `raise` line but leaving the stderr dumps (harmless but noisy, and the `if n == 3 ...` branch is a landmine for any other 3-vertex test with edge (0,2)); or renaming the tag format to dodge the `startswith` match (fragile, and the debug code should simply not ship).
