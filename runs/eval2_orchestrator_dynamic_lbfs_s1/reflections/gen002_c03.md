- But the N-part of a later bucket goes AFTER the non-N-part of an earlier bucket IF and only IF the earlier bucket's label + × < later bucket's label + u.

This is complex. A simpler correct approach: just sort the new buckets by their labels. But labels can be long.

Alternatively, the simplest fix: after forming the new queue, verify it's in label order, and if not, sort it. But this defeats the purpose of HMPV.

The simplest correct fix for this candidate: replace the HMPV implementation with a straightforward LexBFS that explicitly maintains labels and picks the vertex with the smallest label at each step. This is O(n^2) but correct.

## REPAIR_HINTS
The bug is in `_lexbfs`: the queue discipline "all N(u)-parts first, then all ¬N(u)-parts" does NOT maintain label order. Counterexample: 4-cycle 0-1-2-3-0. After processing 0 and 1, the queue should be [[3], [2]] (labels "0×" and "×1" respectively, and "0×" < "×1"), but the code produces [[2], [3]].

The smallest fix: replace `_lexbfs` with a correct O(n²) LexBFS that explicitly maintains labels:

```python
def _lexbfs(graph):
    n = len(graph)
    if n == 0:
        return []
    unvisited = set(range(n))
    labels = {v: [] for v in range(n)}  # label as list of (vertex_id or -1 for ×)
    ordering = []
    while unvisited:
        # Pick vertex with smallest label (lexicographic, -1 = × is largest)
        u = min(unvisited, key=lambda v: labels[v])
        ordering.append(u)
        unvisited.remove(u)
        for v in unvisited:
            if graph[u][v]:
                labels[v].append(u)
            else:
                labels[v].append(-1)  # ×
    return ordering
```

This is O(n³) in the worst case (n steps × n vertices × label comparison O(n)) but is correct. For the dynamic setting, this can be the fallback.

Approaches that will NOT work:
- Keeping the "all N-parts first" queue discipline: it's fundamentally incorrect as shown by the 4-cycle counterexample.
- Just swapping the order to "all non-N-parts first": also incorrect by symmetry.
- The local repair in `_try_local_repair` is fine (it checks the (LB) certificate), but it's irrelevant here since the failure is in `init` → `_lexbfs`.
