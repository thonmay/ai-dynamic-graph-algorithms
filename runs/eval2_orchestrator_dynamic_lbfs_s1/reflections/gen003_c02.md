## FAILURE_DESCRIPTION
Failing case: n=4, operation `insert (0, 3)` at sequence index 2. The candidate returned ordering `[0, 1, 2, 3]`, but the expected (valid) ordering is `[0, 1, 3, 2]`. The verifier reports a 4-point violation at positions a=1, b=2, c=3 (vertices 1, 2, 3) with `minD = 1000000000` (no witness found).

## ROOT_CAUSE
The bug is in `_lexbfs_full`. The label comparison `key=lambda x: (len(labels[x]), labels[x])` is **not** the standard LexBFS rule. It picks the frontier vertex with the **fewest** visited neighbors first, rather than the vertex whose label (characteristic vector of adjacency to already-output vertices, in output order) is **lexicographically smallest**.

In standard LexBFS, each unvisited vertex's label is the tuple `(graph[order[0]][v], graph[order[1]][v], ..., graph[order[k-1]][v])` where `order[0..k-1]` are the already-output vertices. We pick the vertex with the lexicographically smallest such tuple. Using `len(labels[x])` as the primary key is wrong: it conflates "fewest neighbors" with "lexicographically smallest label."

For the graph after inserting (0,3), `_lexbfs_full` produces `[0, 1, 2, 3]` which violates the 4-point property at (a=1, b=2, c=3). The correct LexBFS should produce `[0, 1, 3, 2]` (or another valid ordering).

The `_try_repair` heuristic is also incomplete (it only checks violations where the new edge is the "ac" side, not where it affects the "ab not in E" condition or the "db" side), but this is secondary: the fallback to `_lexbfs_full` is supposed to guarantee correctness, and that fallback is broken.

## REPAIR_HINTS
1. **Fix `_lexbfs_full` (primary fix)**: Replace the label comparison with proper LexBFS. For each frontier vertex `x`, compute its label as a tuple of 0/1 values: `(graph[order[i]][x] for i in range(len(order)))`. Pick the frontier vertex with the lexicographically smallest such tuple. This is the standard LexBFS rule and will produce a valid ordering.

   Concretely, replace:
   ```python
   best = min(frontier, key=lambda x: (len(labels[x]), labels[x]))
   ```
   with:
   ```python
   best = min(frontier, key=lambda x: tuple(graph[order[i]][x] for i in range(len(order))))
   ```
   (The `labels` list and its maintenance can be removed entirely.)

2. **`_try_repair` can remain as a heuristic**: It is not required for correctness since the fallback handles it. However, if the repair produces an ordering that passes `_is_valid_lexbfs`, it is used; otherwise the (now-correct) `_lexbfs_full` is called. No changes needed here for correctness.

3. **Do NOT** try to "fix" `_try_repair` to handle all violation types — that is the open research problem. The correct approach is to ensure the fallback `_lexbfs_full` is a correct static LexBFS, which guarantees correctness for all updates.
