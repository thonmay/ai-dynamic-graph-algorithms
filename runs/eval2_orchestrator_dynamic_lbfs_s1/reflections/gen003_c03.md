## FAILURE_DESCRIPTION

Failing case: n=3, operation `insert (0,1)` at sequence_idx 0. The pre-update graph is the single edge 0-1; the post-update graph is the path 1-0-2 (edges 0-1 and 0-2).

- Candidate returned: `[0, 2, 1]`
- Expected (verifier): `[0, 1, 2]`
- Verifier violation: (LB) 4-point property, a=0, b=2, c=1, pos_a=0, minD=1e9 (no witness d exists). In the verifier's edge set, ac = 0-1 ∈ E but ab = 0-2 ∉ E, and since a is the first vertex there is no d < a, so the property fails.

The only valid LexBFS ordering of the path 1-0-2 is `[0,1,2]` (start 0; after step 1, vertices 1 and 2 both have label (1), and the vertex-id tie-break forces 1 before 2). The candidate's `[0,2,1]` violates the tie-break.

## ROOT_CAUSE

The candidate's validity checker `_is_lexbfs_ordering` (the loop in `def _is_lexbfs_ordering(ordering, adj)`) certifies an ordering by **label-minimality alone**:

```python
for k in range(n):
    v = ordering[k]
    best = None
    for w in remaining:
        key = tuple(labels[w])
        if best is None or key < best:
            best = key
    if tuple(labels[v]) != best:
        return False
```

This accepts `v` whenever its label equals the *minimum* label among the remaining vertices, with **no vertex-id tie-break**. So it accepts any ordering that is a LexBFS under *some* tie-breaking, not the canonical vertex-id tie-break that the verifier enforces.

Trace on the failing case:
1. Pre-update graph (edge 0-1 only): `_lexbfs` picks 0 (empty-label tie broken by id), then 2 (label (0) < (1)), then 1 → `init` returns `[0,2,1]`.
2. Post-update graph (path 1-0-2): `insert_edge` calls `_is_valid_lexbfs(graph, [0,2,1])`.
   - Step 1: v=0, all labels empty, 0 is minimal ✓. Update: label[2]=(1), label[1]=(1).
   - Step 2: v=2, best label among {1,2} is (1); label[2]=(1) == best → **passes** (but 1 and 2 are tied, and the id tie-break requires 1 first).
   - Step 3: v=1 ✓.
   - `_is_valid_lexbfs` returns True, so `insert_edge` keeps `[0,2,1]` and never recomputes.

The candidate's own docstring claims "This is exactly the definition of LexBFS with the vertex-id tie-break", but the code never applies that tie-break in the checker. The static `_lexbfs` does use the id tie-break (key = (tuple(labels[v]), v)), so a recompute would have produced the correct `[0,1,2]` — but the buggy checker prevents the recompute from ever being triggered.

## REPAIR_HINTS

Smallest fix: make `_is_lexbfs_ordering` enforce the **vertex-id tie-break** exactly as the verifier does. At each step k, the valid next vertex is the one with the lexicographically smallest `(label, vertex_id)` key among the remaining vertices. Change the check from

```python
if tuple(labels[v]) != best:
    return False
```

to comparing the full key:

```python
best_key = min((tuple(labels[w]), w) for w in remaining)
if (tuple(labels[v]), v) != best_key:
    return False
```

This makes the checker accept exactly the orderings that `_lexbfs` (which already uses `key = (tuple(labels[v]), v)`) would produce, so the "keep if still valid" fast path will correctly reject `[0,2,1]` on the path graph and trigger the recompute to `[0,1,2]`.

Approaches that will NOT work:
- Keeping the label-minimality-only check and hoping the 4-point property is equivalent to it: it is not, because the 4-point property (as the verifier applies it) pins down the tie-break, and label-minimality alone admits multiple orderings per graph.
- Adding a separate 4-point-property check on top of the label check: the 4-point property as stated in the brief ("for all positions a < b < c with ac in E and ab not in E, there exists d < a with db in E and dc not in E") is also not sufficient to pin the tie-break on its own for arbitrary graphs; the cleanest fix is to match the verifier's exact tie-break rule in the checker.
- Changing `_lexbfs` to not use the id tie-break: the verifier expects the id tie-break, so the static algorithm must keep it.
