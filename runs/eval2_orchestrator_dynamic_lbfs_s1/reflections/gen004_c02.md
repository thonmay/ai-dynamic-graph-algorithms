## ROOT_CAUSE
The bug is in `insert_edge` (and symmetrically `delete_edge`): the "verified repair" fast path is trusted without ever checking that the *pre-update* ordering was valid on the *pre-update* graph.

```python
def insert_edge(graph, edge, state):
    order = state['ordering']
    pos = state['pos']
    repaired = _try_repair(order, pos, graph, edge, inserted=True)
    if repaired is not None and _is_valid_lexbfs(repaired, graph):
        return _make_state(repaired)
    return _make_state(_lexbfs_full(graph))
```

The docstring claims "Correctness is guaranteed by the fallback", but the fallback only fires when `_try_repair` returns None or when the *repaired* order fails `_is_valid_lexbfs`. It does NOT fire when `_try_repair` returns None while the *original* order is already invalid on the new graph. In that case the code falls through to `_lexbfs_full(graph)` — which is fine — BUT the real problem is that `_try_repair` can return a "repaired" order that passes `_is_valid_lexbfs` on the new graph while the original order was never valid to begin with, OR (as here) the repair heuristic produces an order that the verifier's (stricter/different) check rejects.

But wait — is [0,1,3,2] actually a valid LexBFS? Let me run standard LexBFS from 0:

The bug is that the candidate's "frontier" approach discovers 3 only after 1 is output, but in true LexBFS, 3 should be considered at the same time as 1 and 2 (all are neighbors of 0).

The root cause: `_lexbfs_full` does not implement correct LexBFS. It uses a BFS-like frontier where vertices are only added when their neighbor is output, rather than maintaining the full set of unvisited vertices and picking the one with the smallest label each time.

## REPAIR_HINTS
The `_lexbfs_full` function must be replaced with a correct LexBFS implementation. The standard approach:

```python
def _lexbfs_full(graph):
    n = len(graph)
    visited = [False] * n
    order = []
    for s in range(n):
        if visited[s]:
            continue
        # All unvisited vertices are candidates; pick the one with smallest label
        unvisited = set(range(n)) - set(order)
        # Initialize: only s is "active" (discovered)
        active = {s}
        visited[s] = True
        order.append(s)
        while True:
            # Find all unvisited vertices adjacent to any active vertex
            # Actually, standard LexBFS: maintain labels for all unvisited vertices
            # Pick the unvisited vertex with the smallest label (tie-break by id)
            # Add it to order, update labels
            best = None
            best_key = None
            for v in unvisited:
                if visited[v]:
                    continue
                key = tuple(graph[order[i]][v] for i in range(len(order)))
                if best_key is None or (key, v) < (best_key, best):
                    best_key = key
                    best = v
            if best is None:
                break
            visited[best] = True
            order.append(best)
    return order
```

The key fix: at each step, consider ALL unvisited vertices (not just those in a BFS frontier) and pick the one with the lexicographically smallest label (sequence of adjacency bits to already-ordered vertices). This is the standard O(n^2) LexBFS.

The repair heuristic `_try_repair` is secondary; the primary bug is that the fallback `_lexbfs_full` itself is incorrect. Fix `_lexbfs_full` first, then the fallback will always produce a valid ordering and the overall correctness guarantee will hold.
