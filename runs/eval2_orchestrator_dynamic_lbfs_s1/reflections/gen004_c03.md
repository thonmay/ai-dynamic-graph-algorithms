## FAILURE_DESCRIPTION

3-vertex graph, operation `insert (0, 2)` at sequence index 0. The candidate
returned ordering `[0, 1, 2]`, but the verifier reports a (LB) 4-point
violation at positions a=0, b=1, c=2 (minD = 1e9, i.e. no witness d exists).
The expected valid ordering is `[0, 2, 1]`.

Reconstructing the graph from the violation: at positions a=0 (v=0), b=1
(v=1), c=2 (v=2), the violated triple requires `0-2 in E`, `0-1 not in E`,
and no d < 0 (vacuous, so the "W empty" branch fires). Since the operation
is `insert (0, 2)`, the post-update graph has edge {0,2} and no edge {0,1}.
The third edge {1,2} is irrelevant to the violation.

## ROOT_CAUSE

The bug is in `_symmetrize`, which uses OR of the two matrix entries:

```python
if sym[i][j] or sym[j][i]:
    sym[i][j] = 1
    sym[j][i] = 1
```

A legal update flips exactly one matrix entry, so the matrix handed to
`insert_edge`/`delete_edge` is momentarily non-symmetric. For an **insertion**
the flipped entry is 0→1, so OR is correct. But for a **deletion** the
flipped entry is 1→0 while the mirror entry is still 1, and OR resurrects
the deleted edge. The docstring even claims OR "recovers the intended
undirected graph for both insertions and deletions" — that is false for
deletions.

Consequence in this failing case: the graph the candidate actually reasons
about is not the true post-update graph. `_is_valid_lexbfs` and `_lexbfs`
both run on the OR-symmetrized matrix, so:
- the validity check can pass on a stale (pre-deletion) graph and keep an
  ordering that is invalid for the real graph, or
- the recomputed ordering is a LexBFS of the wrong graph.

Either way the returned ordering violates (LB) on the true graph, exactly as
the verifier reports.

## REPAIR_HINTS

Smallest fix: make symmetrization operation-aware.

- In `insert_edge`: keep OR (or simply set both entries to 1 for the given
  edge) — the flipped entry is 0→1.
- In `delete_edge`: use AND of the two entries (or set both entries to 0 for
  the given edge) — the flipped entry is 1→0, so the surviving 1 in the
  mirror triangle is stale and must be cleared.

Concretely, replace the single `_symmetrize` with a mode parameter
(`_symmetrize(graph, mode)` where mode is 'or' for insert, 'and' for delete),
or better, since the `edge` argument is already passed in, just copy the
matrix and set `sym[u][v] = sym[v][u] = 1` in `insert_edge` and `= 0` in
`delete_edge`. The latter is O(n) instead of O(n^2) and cannot go wrong.

Do NOT try to "fix" this by making `_is_valid_lexbfs` or `_lexbfs` tolerant
of non-symmetric input — the real problem is that the graph itself is wrong
for deletions; every downstream consumer inherits the stale edge.

Note: `_adjacency` already reads both triangles, so once the matrix is
correctly symmetrized per operation, no other change is needed.
