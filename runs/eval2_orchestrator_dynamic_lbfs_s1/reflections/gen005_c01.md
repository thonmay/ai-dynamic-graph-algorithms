## FAILURE_DESCRIPTION

Operation: `init` (sequence_idx 0) on a 4-vertex undirected graph. The candidate returned ordering `[0, 1, 2, 3]`; the expected (valid) ordering is `[0, 1, 3, 2]`. The verifier reports a (LB) 4-point violation with `a=0, b=2, c=3, pos_a=0, minD=1`: at positions 0 < 2 < 3 we have `ac in E` (0-3) and `ab not in E` (0-2), but no `d` before position 0 exists with `db in E` and `dc not in E` (minD=1 means the earliest such d would be at position 1, i.e. after a).

The graph is not included in the failing-case record, so the exact adjacency matrix cannot be quoted. However, the violation record pins down the relevant edges: 0-3 in E, 0-2 not in E, and (from minD=1) vertex 1 is adjacent to 2 but not to 3. The failure is in the static `_lexbfs` itself — the local-repair path is never reached at `init`.

## ROOT_CAUSE

The static partition-refinement `_lexbfs` uses the wrong queue order after refining by a selected vertex `u`. The code (lines ~44-60) appends buckets in this order:

```python
if b_n:
    Q.append(b_n)
for part in other_n:
    Q.append(part)
if b_nonn:
    Q.append(b_nonn)
for part in other_nonn:
    Q.append(other_nonn)   # (sic: other_nonn)
```

i.e. **all** N(u)-parts first (current bucket's N-part, then other buckets' N-parts), then **all** non-N(u)-parts. This is not the HMPV LexBFS queue discipline.

The correct HMPV rule is: after selecting `u` from the front bucket `B`, the queue becomes
1. `B ∩ N(u)` (the N-part of the *current* bucket, first),
2. the other buckets **in their old relative order**, each split into its N-part followed by its non-N-part (empty parts dropped),
3. `B \ N(u)` (the non-N-part of the current bucket, last).

The candidate's comment even states the intended order ("N(u)-part of the current bucket B (first), N(u)-parts of the other buckets, non-N(u)-part of B, then non-N(u)-parts of the other buckets"), but the code implements a different grouping (all N-parts, then all non-N-parts), which changes the selection order of vertices and produces an ordering that is not a valid LexBFS.

Concretely, on the failing graph this mis-ordering causes vertex 2 to be selected before vertex 3, yielding `[0, 1, 2, 3]` instead of the valid `[0, 1, 3, 2]`. The (LB) certificate then fails at the triple (a=0, b=2, c=3).

## REPAIR_HINTS

Fix the queue reconstruction in `_lexbfs` to match the HMPV rule. Replace the block that builds `other_n`/`other_nonn` and re-appends with:

```python
other_buckets = list(Q)
Q.clear()

b_n = [v for v in B if graph[u][v]]
b_nonn = [v for v in B if not graph[u][v]]

if b_n:
    Q.append(b_n)
for bucket in other_buckets:
    n_part = [v for v in bucket if graph[u][v]]
    nonn_part = [v for v in bucket if not graph[u][v]]
    if n_part:
        Q.append(n_part)
    if nonn_part:
        Q.append(nonn_part)
if b_nonn:
    Q.append(b_nonn)
```

Key points:
- The N-part of the current bucket `B` goes first.
- Each *other* bucket contributes its N-part immediately followed by its non-N-part, preserving the old relative order of buckets.
- The non-N-part of the current bucket `B` goes last.

Do NOT keep the "all N-parts then all non-N-parts" grouping — that is the bug.

After fixing `_lexbfs`, the local-repair and fallback paths in `insert_edge`/`delete_edge` will also benefit, since they call `_lexbfs` as a fallback. The `_is_valid_lexbfs` checker and `_try_local_repair` logic appear correct and need no changes.
