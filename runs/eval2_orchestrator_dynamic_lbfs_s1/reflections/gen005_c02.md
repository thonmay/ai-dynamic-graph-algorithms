## REPAIR_HINTS
The bug is in `_lexbfs_full`. The frontier management is incorrect. The code maintains a cumulative frontier (vertices are added when first discovered and stay until picked), but standard LexBFS uses a "current frontier" that is replaced at each step by the unvisited neighbors of the just-output vertex.

Fix: replace the frontier logic with:
```python
def _lexbfs_full(graph):
    n = len(graph)
    visited = [False] * n
    order = []
    for s in range(n):
        if visited[s]:
            continue
        visited[s] = True
        order.append(s)
        frontier = [v for v in range(n) if graph[s][v] and not visited[v]]
        while frontier:
            best = min(frontier,
                       key=lambda x: (tuple(graph[order[i]][x]
                                            for i in range(len(order))), x))
            visited[best] = True
            order.append(best)
            frontier = [v for v in range(n) if graph[best][v] and not visited[v]]
    return order
```

The key change: `frontier` is REPLACED (not accumulated) at each step with the unvisited neighbors of the just-output vertex. This is the correct LexBFS frontier semantics.

Additionally, the `_try_repair` heuristic's assumption that "the new edge can only create violations where the new edge serves as the 'ac in E' side" is incorrect (as shown by the failing case where the violation involves edges unrelated to the new edge). However, since the fallback `_lexbfs_full` is supposed to catch all cases, fixing `_lexbfs_full` is the critical repair. The repair heuristic can remain as a best-effort optimization.

Approaches that will NOT work:
- Just fixing the repair heuristic: the fallback `_lexbfs_full` is the correctness guarantee, and it's broken.
- Adding more cases to `_try_repair`: the fundamental issue is that the static recompute is wrong, so even when repair returns None, the fallback produces an invalid order.
