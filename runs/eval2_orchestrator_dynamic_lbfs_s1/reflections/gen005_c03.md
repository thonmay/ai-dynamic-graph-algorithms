## FAILURE_DESCRIPTION
3-vertex graph, operation `insert (0, 1)` at sequence index 0. The verifier
reports the returned ordering as `[0, 2, 1]` with a (LB) 4-point violation at
positions a=0, b=2, c=1 (i.e. vertices va=0, vb=1, vc=2): va–vc is an edge,
va–vb is not, and no d < a exists. The expected valid ordering was `[0, 1, 2]`.

## ROOT_CAUSE
The failure is in `insert_edge`, which recomputes via `_lexbfs(graph)`. The
static routine is correct for a symmetric matrix, but the interface allows a
**legal update that flips exactly one matrix entry** — so at call time the
matrix may be asymmetric (e.g. `graph[0][1] = 1` set, `graph[1][0]` still 0).

`_adjacency` builds directed adjacency sets:
```python
for i in range(n):
    row = graph[i]
    for j in range(n):
        if i != j and row[j]:
            adj[i].add(j)
```
With the asymmetric matrix, `adj[0] = {1}` but `adj[1] = {}`. In `_lexbfs`,
the label of vertex 1 after processing 0 is `[0]` (because `1 not in adj[0]`
is false but `0 not in adj[1]` — the label uses `w in adj[best]`, i.e.
`1 in adj[0]` = True... let me re-trace: after picking 0, for w=1:
`labels[1].append(1 if 1 in adj[0] else 0)` → 1; for w=2: `2 in adj[0]` → 0.
Then labels: 1→[1], 2→[0]; pick 2 (smaller). After 2: `1 in adj[2]` → 0.
Final order `[0, 2, 1]` — exactly the reported result. The directed
asymmetry makes the "LexBFS" run on a graph that is neither the pre-update
nor the post-update undirected graph, producing an ordering invalid for the
true (symmetric) post-update graph.

Note the candidate's own comment in `insert_edge` ("the cheap check would be
unsound if the matrix is not symmetric at call time") shows the author
recognized the asymmetry risk for the *check* but did not apply the same
fix to the *recomputation* path.

## REPAIR_HINTS
Make the adjacency construction symmetric so a single-entry flip is
interpreted as the intended undirected edge: in `_adjacency`, treat an edge
as present if `row[j]` OR `graph[j][i]` is set (i.e. `adj[i].add(j)` when
`graph[i][j] or graph[j][i]`). This fixes both `_lexbfs` and
`_is_valid_lexbfs` for asymmetric call-time matrices.

Do NOT try to "fix" this by assuming the matrix is symmetric at call time —
the interface explicitly permits one-entry flips, and the failing case
demonstrates the verifier's graph is the symmetric closure of the flipped
matrix.

Secondary (not the cause of this failure, but a latent bug worth fixing in
the same pass): `delete_edge` returns the old state unconditionally. Edge
deletion can invalidate the (LB) property (e.g. deleting the only edge from
a vertex to all earlier vertices can break the witness condition). The
correct cheap path is: run `_is_valid_lexbfs(graph, state['ordering'])` on
the (symmetrized) post-update graph and recompute only if it fails.
