## FAILURE_DESCRIPTION
Operation: `init` (sequence_idx 0) on a 4-vertex undirected graph.
`init` returned ordering `[0, 1, 2, 3]`, but the expected (valid) ordering is `[0, 1, 3, 2]`.
The verifier reports a (LB) 4-point violation with a=0 (pos 0), b=2 (pos 2), c=3 (pos 3), minD=1:
- ac in E (0-3 edge present), ab not in E (0-2 edge absent),
- no d at position < 0 exists (minD=1 means the witness search over d<a found nothing),
  so the certificate fails.

Since the failure is at `init`, the bug is in the static `_lexbfs` itself — the dynamic
repair/fallback logic is never reached.

## ROOT_CAUSE
The queue discipline in `_lexbfs` is wrong. The HMPV (Habib–McConnell–Paul–Viennot)
LexBFS rule is: when vertex u is selected from the front bucket B, split every remaining
bucket by N(u), and requeue in this order:

1. the N(u)-part of B (the rest of the front bucket),
2. the N(u)-parts of the other buckets, in their old order,
3. the non-N(u)-parts of the other buckets, in their old order.

Crucially, the non-N(u)-part of B (the front bucket) is NOT requeued at all — it is
discarded, because those vertices are non-neighbors of u and u was the front of the
queue, so they can never be selected before the N(u)-parts.

The candidate instead does:

```python
if B_n:
    Q.append(B_n)
for part in n_parts:
    Q.append(part)
if B_nonn:
    Q.append(B_nonn)      # <-- BUG: requeues the front bucket's non-N(u)-part
for part in nonn_parts:
    Q.append(nonn_parts)
```

It requeues `B_nonn` (the non-neighbor part of the front bucket) between the N(u)-parts
and the other non-N(u)-parts. This lets a non-neighbor of u be selected before some
N(u)-part of a later bucket, which is exactly what breaks the LexBFS invariant and
produces the invalid ordering `[0, 1, 2, 3]` (vertex 2, a non-neighbor of 0, is placed
before vertex 3, a neighbor of 0, in a way that violates the 4-point property).

## REPAIR_HINTS
In `_lexbfs`, remove the requeueing of `B_nonn`. The correct requeue order is:

```python
if B_n:
    Q.append(B_n)
for part in n_parts:
    Q.append(part)
for part in nonn_parts:
    Q.append(part)
```

i.e. delete the `if B_nonn: Q.append(B_nonn)` lines (and the `B_nonn` computation can
stay or go; it is simply discarded). Do NOT move `B_nonn` to the end of the queue —
it must be dropped entirely, not reordered.

Approaches that will NOT work:
- Moving `B_nonn` to the very end of the queue (after `nonn_parts`): still wrong, because
  HMPV discards it; keeping it anywhere in the queue can let a non-neighbor of the
  selected vertex be picked out of order.
- Only fixing the dynamic repair path: the failure is at `init`, so the static routine
  must be fixed first.
- Relying on `_is_valid_lexbfs` as a post-hoc filter in `init`: `init` has no fallback
  and returns `_lexbfs` output directly, so the static routine must itself be correct.
