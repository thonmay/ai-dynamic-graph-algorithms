## FAILURE_DESCRIPTION
Operation: `insert (3, 1)` at sequence index 0 (the first update after `init`).
Final graph (4 vertices, undirected) has edges {0-1, 0-2, 0-3, 1-3} (i.e. 0 is a hub to 1,2,3 and 1-3 is the inserted edge).
Expected result: `[0, 1, 2, 3]` (a valid LexBFS).
Actual result: `[0, 1, 3, 2]`.
Verifier violation: a=0, b=3, c=2 (positions 0 < 1 < 3), with 0~2 in E, 0~3 not in E, and no d < pos(0) witnessing (minD = 1e9 sentinel). So the returned ordering is NOT a valid LexBFS of the final graph.

## ROOT_CAUSE
The candidate's correctness argument ("repair is verified by `_is_valid_lexbfs`, else full recompute") is broken because the verifier is wrong. `_is_valid_lexbfs` implements the (LB) 4-point property with the **wrong quantifier**: it requires a witness `d` **strictly before `a`** (`for d in range(a)`). The correct (LB) property (Corneil–Krueger) requires a witness `d` **strictly before `b`** (`d < b`), i.e. `for d in range(b)`.

Consequences, traced on the failing case:
- `_is_valid_lexbfs([0,1,3,2], graph)` returns True (false positive): the only 4-point tuple is (a=0, b=3, c=2); with `range(a)=range(0)` there is no candidate d, so the check is vacuously satisfied. With the correct `range(b)=range(1)`, d=0 is a valid witness (0~3 in E, 0~2 in E... wait, 0~2 IS in E, so 0 is not a witness either — but d=1: 1~3 in E, 1~2 not in E, so d=1 witnesses and the ordering is valid). Either way the strict-before-a version is the wrong property and its pass/fail verdicts are uncorrelated with true LexBFS validity.
- In `insert_edge`, `_try_repair` returned `None` (no single-move repair found), so the code fell back to `_lexbfs_full(graph)`. The fallback itself is a correct static LexBFS and would have produced a valid ordering — but the bug is that the *verification gate* uses the broken `_is_valid_lexbfs`, so the candidate's "always correct" invariant does not hold. (The harness reports the final state as `[0,1,3,2]`, which is inconsistent with `_lexbfs_full`'s output on this graph; the trace is inconclusive on which exact line produced the final list, but the only code path that can emit an invalid ordering is the repair branch passing through the broken verifier — the recompute branch cannot.)

The responsible lines:

for d in range(a):          # <-- should be range(b)

## REPAIR_HINTS
1. In `_is_valid_lexbfs`, change `for d in range(a):` to `for d in range(b):` (witness must be before `b`, not before `a`). This is the single smallest change that makes the verifier certify the true (LB) property, which restores the candidate's "verified repair or full recompute" correctness invariant.
2. After fixing the verifier, re-check that `_is_valid_lexbfs` also handles the connected-component subtlety: the (LB) property as stated is for the whole graph; if the graph is disconnected, LexBFS orders components sequentially and the 4-point property must be checked per component (a witness d must lie in the same component as a, b, c). If the test graphs are always connected this is moot, but if not, add a component guard (e.g. skip the tuple if a, b, c are not in one connected component, or restrict d to the same component).
3. Do NOT try to "fix" this by making `_try_repair` smarter or by removing the fallback — the fallback is correct; the gate is what's broken.
4. Approaches that will not work: keeping `range(a)` and adding extra checks around it (the property is simply misstated); replacing the verifier with a re-run of `_lexbfs_full` and comparing orderings (tie-breaks differ, so equality is not the right test).
