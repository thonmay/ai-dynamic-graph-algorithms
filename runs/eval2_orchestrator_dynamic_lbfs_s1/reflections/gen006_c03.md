## FAILURE_DESCRIPTION
n=3. Initial graph: edge (0,1) only (matrix has 1 at [0][1] and/or [1][0]; the other entries 0). `init` returns ordering [0, 1, 2], which is a valid LexBFS of that graph.

Failing update: `insert_edge(graph, (0, 2), state)`. The matrix handed in has the single entry [0][2]=1 flipped (legal single-entry flip), so the raw matrix is asymmetric: 0~1 and 0~2 present, 1~2 absent.

- Expected result: [0, 2, 1] (a valid LexBFS of the undirected graph {01, 02}).
- Actual result: [0, 1, 2] (the stale ordering was kept).
- Verifier's violation: a=0, b=1, c=2 (positions 0,1,2): ac in E (0~2), ab not in E (1~2 not an edge), and no d < a exists (minD = 10^9 sentinel). Indeed [0,1,2] is NOT a LexBFS of {01, 02}: the label of 1 is (0,1) while the label of 2 is (1,0), and (0,1) > (1,0), so 2 must precede 1.

## ROOT_CAUSE
The candidate's `_symmetrize` (lines: `if graph[i][j] or graph[j][i]: sym[i][j] = 1; sym[j][i] = 1`) ORs the two triangles, i.e. it treats the matrix as "edge present if either entry is 1". But a legal update flips exactly ONE entry, so after `insert (0,2)` the raw matrix has [0][2]=1 and [2][0]=0. The correct undirected graph is {01, 02}, but `_symmetrize` produces {01, 02, 12} (a triangle), because [1][0]=1 (from the initial edge) ORs with [0][1] to keep 01, and — critically — the stale ordering [0,1,2] is then checked against the triangle, where it IS a valid LexBFS (any ordering of a triangle is valid). So `_is_valid_lexbfs` returns True and the stale ordering is kept.

The divergence happens at the very first operation: `insert_edge` builds `sym` via `_symmetrize`, which silently adds the spurious edge 1~2 (and would equally drop a real edge on a deletion that flips only one triangle entry, e.g. deleting (0,1) when only [0][1] is flipped would leave [1][0]=1 and keep the edge). The (LB) check is then run on the wrong graph, so it cannot detect the real violation.

Note the static `_lexbfs` itself is fine (it would produce [0,2,1] on the correct graph {01,02}); the bug is purely in how the asymmetric input matrix is interpreted.

## REPAIR_HINTS
Smallest fix: stop guessing the undirected graph from a possibly-asymmetric matrix. The interface hands you the exact update: `edge = (u, v)` and the operation name (insert vs delete). Maintain the undirected edge set explicitly in the state:

1. In `init`, build the edge set from the matrix (either triangle is fine for the initial symmetric matrix) and store it in state, e.g. `state['edges'] = set of frozenset({i,j})`.
2. In `insert_edge`, add `frozenset(edge)` to the stored edge set; in `delete_edge`, remove it. Use the stored edge set (not the raw matrix) for both `_is_valid_lexbfs` and `_lexbfs` — pass adjacency built from the edge set instead of calling `_adjacency`/`_symmetrize` on the matrix.
3. Delete `_symmetrize` entirely; do not OR the triangles (that is what fabricates edge 1~2 here) and do not AND them (that would drop the edge on a one-sided deletion).

Approaches that will NOT work:
- OR-ing or AND-ing the two triangles of the raw matrix: a single-entry flip makes the matrix asymmetric, so neither recovers the true undirected graph in general.
- Trusting `state['ordering']` to be valid without re-deriving the graph: the validity check is only as good as the graph it is checked against.
- Relying on the `edge` argument alone without persisting the edge set: you still need the full current edge set for the (LB) check and for recomputation, and the matrix cannot be trusted to provide it.
