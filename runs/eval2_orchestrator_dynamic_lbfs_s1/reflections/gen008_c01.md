## FAILURE_DESCRIPTION
`init` on a 4-vertex graph returns `[0, 1, 2, 3]`; the expected valid LexBFS is `[0, 1, 3, 2]`. The (LB) certificate is violated at (a=1, b=2, c=3) with positions 1<2<3: 1~3 ∈ E, 1~2 ∉ E, and no d before position 1 (only d=0) satisfies 0~2 ∈ E and 0~3 ∉ E (minD stayed at the sentinel 1e9).

Reconstructed graph (consistent with both the violation and the expected ordering): edges {0-1, 1-3} only (0~2, 0~3, 1~2, 2~3 all absent). On this graph `[0,1,2,3]` fails exactly at (1,2,3), and `[0,1,3,2]` passes all triples.

## ROOT_CAUSE
The failure is in `_lexbfs` (the static routine), not in the dynamic repair path — the failing operation is `init`, which calls `_lexbfs` directly.

The bug is the queue ordering after splitting the current bucket. The code does:

```python
new_q = []
if B_n:
    new_q.append(B_n)
if B_nonn:
    new_q.append(B_nonn)
new_q.extend(Q)
```

i.e. it puts the neighbor part `B_n` **before** the non-neighbor part `B_nonn`. The HMPV/LexBFS discipline requires the opposite: the non-neighbor part must be placed at the **front** of the queue (before `B_n` and before all other buckets), because in LexBFS the vertices NOT adjacent to the just-output vertex must be ordered before the vertices that are adjacent to it (labels: non-neighbors get a leading 0, neighbors a leading 1, and 0 < 1).

Trace on the failing graph (edges 0-1, 1-3):
- Q=[[0,1,2,3]], u=0, B=[1,2,3]. B_n=[1], B_nonn=[2,3]. Candidate: Q=[[1],[2,3]] (wrong). Correct: Q=[[2,3],[1]].
- Candidate: u=1 (B empty), then u=2, B=[3], B_n=[], B_nonn=[3], Q=[[3]], u=3 → ordering [0,1,2,3] → INVALID (violation at (1,2,3)).
- Correct: u=2, B=[3], B_n=[], B_nonn=[3], Q=[[3],[1]], u=3, then u=1 → ordering [0,2,3,1].

Note: with the swap, the algorithm produces a different (also valid) LexBFS such as [0,2,3,1] rather than [0,1,3,2]; the verifier accepts any valid ordering, so matching the expected string exactly is not required — only passing the (LB) certificate is.

## REPAIR_HINTS
Smallest fix, in `_lexbfs`: swap the two appends so the non-neighbor part is enqueued first:

```python
new_q = []
if B_nonn:
    new_q.append(B_nonn)
if B_n:
    new_q.append(B_n)
new_q.extend(Q)
```

This restores the HMPV invariant (B_nonn at the front of the queue), which is what makes the lazy single-bucket refinement correct.

Approaches that will NOT work:
- Keeping B_n first and "fixing" the output by post-processing: the queue order is the whole mechanism; any local reordering of the final list is unsound.
- Relying on `_is_valid_lexbfs` as a filter inside `init`: `init` never calls it, and the local-repair path is only used by insert/delete, so an invalid `_lexbfs` output from `init` is returned as-is.
- Changing the tie-break (e.g. picking a different start vertex) instead of the queue order: the bug is the relative order of B_n vs B_nonn, which is wrong for every start vertex.

After the fix, verify `_lexbfs` output against `_is_valid_lexbfs` on the failing graph (edges {0-1, 1-3}) — the produced ordering must pass the (LB) certificate.
