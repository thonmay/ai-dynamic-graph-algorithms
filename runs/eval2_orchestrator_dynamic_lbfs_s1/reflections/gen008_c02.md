## FAILURE_DESCRIPTION
n=4, operation `insert (3, 1)` at sequence_idx 0. The candidate returned ordering `[0, 1, 3, 2]`; the expected (valid) ordering is `[0, 1, 2, 3]`. The verifier reports a 4-point (LB) violation at positions a=0, b=3, c=2 (pos_a=0, minD=1e9): i.e., va=order[0]=0, vb=order[3]=3, vc=order[2]=2 with ac (0-2) in E and ab (0-3) not in E, and no d < a exists to witness (a is the first position, so the witness set is empty). This is a hard violation: any valid LexBFS ordering must place 2 before 3 here.

## ROOT_CAUSE
The "always correct" fallback `_lexbfs_full` is itself a buggy LexBFS, and its output is never validated.

Two compounding defects:

1. **Wrong comparison direction in `_lexbfs_full`.** The selection key is
   ```python
   best = min(frontier,
              key=lambda x: (tuple(graph[order[i]][x] for i in range(len(order))), x))
   ```
   The LexBFS label of a frontier vertex is its adjacency vector to the already-ordered prefix, and LexBFS must pick the lexicographically **largest** label (1s first — vertices adjacent to earlier vertices come first). `min` picks the lexicographically **smallest** label (0s first), the exact opposite. Concrete trace on the post-insert graph with edges {0-1, 0-2, 1-3}: after ordering [0,1], frontier = {2,3}; label(2) = (1,0) (adjacent to 0, not 1), label(3) = (0,1). `min` picks 3 (0s first), yielding [0,1,3,2]. The correct choice is 2 (1s first), giving [0,1,2,3]. The produced [0,1,3,2] is precisely the failing result, and its violation has the exact reported signature: a=0 (first position, so no possible witness d), b=3, c=2.

2. **Fallback result is never checked.** In `insert_edge`/`delete_edge`:
   ```python
   repaired = _try_repair(...)
   if repaired is not None and _is_valid_lexbfs(repaired, graph):
       return _make_state(repaired)
   return _make_state(_lexbfs_full(graph))
   ```
   `_is_valid_lexbfs` is applied only to the repaired candidate. The fallback `_lexbfs_full(graph)` is returned unconditionally, so the buggy static ordering sails through. In this failing case `_try_repair` returned `None` (for orientation (a=1,c=3) no w satisfies pos[1] < pos[w] < pos[3]; for (a=3,c=1) pos[3] >= pos[1]), so the unvalidated buggy fallback output was returned.

Note the docstring claim "Correctness is guaranteed by the fallback" is false: the guarantee only holds if `_lexbfs_full` is a correct LexBFS, which it is not.

## REPAIR_HINTS
Smallest fix, in `_lexbfs_full`: change the selection from `min` to `max` over the label tuple (keep the vertex-id tie-break, which then becomes the largest-id tie-break — or negate it if you want lowest-id ties; any tie-break is legal for validity):
```python
best = max(frontier,
           key=lambda x: (tuple(graph[order[i]][x] for i in range(len(order))), -x))
```
This makes the static routine a genuine LexBFS (largest label first), which restores the fallback's correctness.

Defensive second fix (recommended, cheap): validate the fallback too, so no future static bug can ship an invalid ordering:
```python
full = _lexbfs_full(graph)
if not _is_valid_lexbfs(full, graph):
    raise RuntimeError("static LexBFS produced invalid ordering")
return _make_state(full)
```
(or fall back to a brute-force search over orderings for tiny n as a last resort).

Approaches that will NOT work:
- Improving `_try_repair` alone: the repair heuristic is not the failure point here; it correctly returned None and the bug is in the fallback it hands off to.
- Keeping `min` and "fixing" the 4-point checker: `_is_valid_lexbfs` is correct; the checker is not the problem.
- Relying on the tie-break `x` to compensate for the wrong direction: the tie-break only breaks exact label ties and cannot fix the systematic 0s-first vs 1s-first inversion.
