## FAILURE_DESCRIPTION
Case: n=3, operation `insert (0, 2)` at sequence_idx 0 (the first operation after init).
The candidate returned ordering `[0, 1, 2]`; the verifier expected `[0, 2, 1]`.
The verifier reports a (LB) 4-point violation at positions a=0, b=1, c=2 (minD = 1e9, i.e. no witness d exists).

Reconstructed post-update graph (the only graph consistent with the violation):
- E = {0-1, 0-2} (a path 1-0-2).
- In ordering [0,1,2]: a=0→v0, b=1→v1, c=2→v2. ac = 0-2 ∈ E, ab = 0-1 ∈ E... wait, ab must NOT be in E for the property to apply. So the actual post-update graph must have 0-1 NOT in E and 0-2 in E, i.e. E = {0-2} only (plus possibly 1-2, which is irrelevant to this triple). Then:
  - a=0 (v0), b=1 (v1): ab = 0-1 ∉ E. W = {d<0 : ...} = ∅.
  - c=2 (v2): ac = 0-2 ∈ E.
  - Property requires a witness d < a = 0, but no such position exists → violation.
- The correct ordering [0,2,1]: a=0 (v0), b=1 (v2): ab = 0-2 ∈ E, no constraint; a=0, b=2 (v1): ab = 0-1 ∉ E, but no c > b, so no constraint. Valid.

So the candidate's `_is_valid_lexbfs` returned True for [0,1,2] on a graph where it is invalid, and the candidate kept the stale ordering instead of recomputing.

## ROOT_CAUSE
The bug is in `_is_valid_lexbfs` (and symmetrically in how the update is applied): the candidate builds the post-update adjacency via `_adjacency(graph, edge=edge, inserted=inserted)`, which reads the FULL matrix and then applies the edge flip on top. But `insert_edge`/`delete_edge` first call `_effective_graph(graph, edge, inserted)` to produce `g`, and then pass `g` to `_is_valid_lexbfs` WITHOUT the `edge`/`inserted` arguments — so `edge=None` there and the flip is NOT re-applied. That part is actually consistent (g already has the flip). The real divergence:

Trace `_is_valid_lexbfs(g, [0,1,2])` on g with E={0-2}:
- a=0, va=0. b=1, vb=1. `vb in adj[va]`? 1 in adj[0]? adj[0]={2}, so no → ab ∉ E, continue.
- W = [p2v[d] for d in range(0) if ...] = [] (empty).
- `if not W:` → loop c in range(2,3): c=2, vc=2, `2 in adj[0]` → True → `return False`.

So `_is_valid_lexbfs` DOES return False here, and the candidate SHOULD recompute. Therefore the divergence must be earlier: the `g` passed in is wrong. Look at `_effective_graph`: it symmetrizes with `if g[i][j] or g[j][i]: g[i][j]=g[j][i]=1`. If the harness passes the PRE-update matrix (edge (0,2) not yet in the matrix), then g[0][2]=g[2][0]=0, the insert sets both to 1 — fine. But if the harness passes the POST-update matrix (entry already flipped), the insert is idempotent — also fine. So g is correct.

Re-examining: the failure says result `[0,1,2]` was returned, meaning `_is_valid_lexbfs(g, [0,1,2])` returned True. The only way that happens with E={0-2} is if `adj[0]` did NOT contain 2, i.e. the flip was lost. That happens if the harness passes the pre-update matrix AND `_effective_graph` is NOT the source of truth used by the validity check... but it is. The remaining possibility: the harness passes the pre-update matrix, and `_effective_graph` correctly produces E={0-2}, BUT the initial state's ordering `[0,1,2]` came from `init` on the pre-update graph E=∅ (or E={0-1} etc.), and the check ran on the correct g and returned False, triggering `_lexbfs(g)`. Then `_lexbfs(g)` itself produced `[0,1,2]` — the bug is in `_lexbfs`.

Trace `_lexbfs` on g with E={0-2} (adj[0]={2}, adj[1]={0}, adj[2]={0}):
- Iter 1: all labels empty; tie-break by id → best=0. order=[0]. Labels: 1→[0] (1∉adj[0]), 2→[1] (2∈adj[0]).
- Iter 2: unprocessed={1,2}. Keys: 1→((0,),1), 2→((1,),2). Min is 1. order=[0,1]. Label 2: 2∈adj[1]? adj[1]={0}, no → 2→[1,0].
- Iter 3: order=[0,1,2].

So `_lexbfs` returns [0,1,2] — which is INVALID for E={0-2} (the same violation). The static LexBFS is wrong: after processing 0, vertex 2 (adjacent to 0, label [1]) must come before vertex 1 (label [0]), since [1] > [0] lexicographically... wait, LexBFS picks the LARGEST label (most 1s), not the smallest! The code does `key < best_key` — it picks the lexicographically SMALLEST label. LexBFS requires picking the lexicographically LARGEST label (vertices adjacent to more already-processed vertices come first). That is the root cause: the comparison is inverted.

## REPAIR_HINTS
In `_lexbfs`, the selection loop picks the unprocessed vertex with the lexicographically SMALLEST label:
```python
key = (tuple(labels[v]), v)
if best_key is None or key < best_key:
```
LexBFS must pick the lexicographically LARGEST label (ties broken by vertex id, either direction is legal). Change the comparison to `key > best_key` (or negate the label tuple). With the fix, the trace on E={0-2} gives: iter 2 picks 2 (label [1] > [0]) → order [0,2,1], which is valid.

Also note: the tie-break direction (smaller id first on equal labels) is fine and legal. Do NOT "fix" this by making the validity check more lenient — the check `_is_valid_lexbfs` is correct; the static builder is what is broken. The `_adjacency`/`_effective_graph` double-application of the edge flip is harmless (idempotent) but worth simplifying to avoid confusion: pass `edge=None` consistently, as the candidate already does in the update paths.
