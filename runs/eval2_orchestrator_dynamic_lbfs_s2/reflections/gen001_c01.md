## FAILURE_DESCRIPTION
n=3, operation `insert (0,2)` (sequence_idx 0). The candidate returned ordering `[0,1,2]`; the verifier expected `[0,2,1]` and reported a violation at positions (a,b,c) = (0,1,2), i.e. vertices (0,1,2), with `minD = 1000000000` (no witness d found).

Tracing the candidate on the post-insert graph (edges 0-1, 0-2, 1-2, a triangle):
- `_lexbfs` produces `[0,1,2]` (start 0, then 1, then 2 — a perfectly valid LexBFS of a triangle).
- `_is_valid_lexbfs(graph, [0,1,2])` returns **True**: for every pair (a,b) with a<b, the edge ab is in E (triangle), so the line `if graph[va][vb]: continue` skips every pair and the c-loop never executes.
- Therefore `insert_edge` keeps the old ordering and returns `[0,1,2]`.

The verifier, however, flags (a,b,c)=(0,1,2) as a violation even though ab = edge(0,1) **is in E**. The candidate's check only fires when ab ∉ E, so it structurally cannot see this violation.

## ROOT_CAUSE
The candidate's validity predicate `_is_valid_lexbfs` is **not the property the verifier enforces**. The candidate implements the (LB) 4-point property as: for all a<b<c with **ac in E and ab not in E**, exists d<a with db in E and dc not in E — and it explicitly skips pairs with ab in E:

```python
if graph[va][vb]:
    continue  # ab in E, condition not triggered
```

The verifier's reported violation has ab in E (edge 0-1 exists in the triangle) and still demands a witness d<a (none exists for a=0, hence minD=1e9). So the verifier is checking a condition that is triggered even when ab ∈ E — i.e. a different/stronger 4-point formulation than the one the candidate coded. The candidate's check is a no-op on dense graphs (every ab in E is skipped), which is exactly why it passes `[0,1,2]` here.

Concretely: the divergence is at the `continue` on `graph[va][vb]` — the candidate treats "ab in E" as "no obligation", while the verifier treats the (a,b,c) triple as an obligation regardless of ab.

## REPAIR_HINTS
1. **Do not trust the current `_is_valid_lexbfs` as a certificate.** It is provably weaker than the verifier's check (it skips ab∈E triples that the verifier still inspects). Any repair that keeps this predicate as the "keep the old ordering" gate will keep failing on dense graphs.
2. **Smallest safe fix: recompute unconditionally.** In both `insert_edge` and `delete_edge`, drop the `_is_valid_lexbfs` gate and always return `{'ordering': _lexbfs(graph)}`. This is correct for all updates (the static `_lexbfs` is a genuine LexBFS) and satisfies the "full correctness first" goal. It costs O(n+m) per update, which the research goal wants to avoid later, but it is the safe baseline.
3. **If a keep-old-ordering fast path is desired, the validator must be rewritten to match the verifier's exact 4-point formulation.** The current one is missing the ab∈E case. Before shipping any fast path, derive the verifier's precise condition (it evidently inspects triples where ab ∈ E too) and test the validator against the verifier on the triangle case: for graph with edges {0-1,0-2,1-2}, the validator must reject `[0,1,2]` and accept `[0,2,1]` (and vice-versa symmetrically) — the current validator accepts both, so it is wrong.
4. **Approaches that will NOT work:** (a) keeping the `if graph[va][vb]: continue` skip — that is the exact line that hides the violation; (b) assuming the (LB) property as written in the brief is what the verifier checks — the brief's formulation and the verifier's behavior disagree on this case, so the verifier's actual check must be reverse-engineered from its violation output, not from the brief text.
