## FAILURE_DESCRIPTION
Case: n=3, sequence_idx=0, operation `insert (0, 2)`.

- Pre-insertion graph: single edge (0,1) (matrix rows [0,1,0], [1,0,0], [0,0,0]).
- `init` produced ordering `[0, 1, 2]`, which is a valid LexBFS of that graph.
- `insert_edge` returned the state unchanged, so the reported result is `[0, 1, 2]`.
- Post-insertion graph: edges (0,1) and (0,2).
- Expected: `[0, 2, 1]` (any valid LexBFS of the new graph).
- Verifier violation: a=0, b=1, c=2, pos_a=0, minD=1e9 (no witness d < a exists).

## ROOT_CAUSE
The algorithm diverges at the `insert_edge` call, which is a no-op:

```python
def insert_edge(graph, edge, state):
    """Handle edge insertion.  The new edge can only help satisfy the
    (LB) property, so the ordering remains valid.  Return state unchanged."""
    return state
```

The docstring's premise is false: the (LB) 4-point property is **not monotone
under edge insertion**. Tracing the failing case:

- Ordering `[0, 1, 2]`, positions pos[0]=0, pos[1]=1, pos[2]=2.
- After inserting (0,2), consider the triple a=0, b=1, c=2:
  - pos[a]=0 < pos[b]=1 < pos[c]=2 ✓
  - a~c: edge (0,2) now exists ✓ (this is the NEW edge)
  - a!~b: the verifier's check flags this triple, so in the verifier's
    post-insertion graph (0,1) is absent — i.e. the pre-insertion graph was
    the single edge (0,2) or the edge set differs from my assumption.
    Either way the mechanism is identical:
  - No d < a=0 exists, so minD = 1e9 → property violated.

The inserted edge (0,2) **creates** a new violating triple: it makes a~c
true where previously a!~c, so the triple was vacuously satisfied before and
is now unsatisfied. Additionally, an inserted edge (d,c) can **destroy**
existing witnesses for other triples (a witness requires d!~c). So insertion
can both create new obligations and remove existing witnesses. The candidate's
`delete_edge` path (check certificate, recompute if invalid) is sound;
`insert_edge` has no such check at all.

## REPAIR_HINTS
Smallest concrete fix: make `insert_edge` symmetric with `delete_edge` —
run the same certificate check and recompute if it fails:

```python
def insert_edge(graph, edge, state):
    ordering = state['ordering']
    if _is_valid_lexbfs(graph, ordering):
        return state
    ordering = _lexbfs(graph)
    return {'ordering': ordering, 'n': state['n']}
```

This restores correctness immediately (both update types now verify the (LB)
property against the *current* graph before trusting the stored ordering).
It does not yet meet the "avoid full recompute" research goal, but it is the
minimal correct change.

Notes for later optimization (not required for correctness):
- A cheaper local check is possible: an insertion (u,v) can only affect
  triples where the new edge (u,v) is the a~c edge (making a~c newly true)
  or where it destroys a witness (the inserted edge is (d,c) for some
  witness d). Restrict the O(n^3) scan to those triples.
- Do NOT try to "repair" the ordering by local swaps after an insertion;
  the (LB) property is global and a local fix can break other triples.
  Recomputation (or a proven local refinement) is the safe route.
- The `_lexbfs` and `_is_valid_lexbfs` implementations themselves are not
  implicated in this failure; the trace shows the stored ordering was valid
  for the pre-insertion graph and the no-op `insert_edge` is the sole
  divergence point.
