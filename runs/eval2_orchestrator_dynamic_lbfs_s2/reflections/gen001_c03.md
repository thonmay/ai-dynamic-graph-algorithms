## FAILURE_DESCRIPTION

3-vertex graph, operation `insert (0, 2)` at sequence index 0. The pre-insert
graph is the single edge (0,1) (vertex 2 isolated). `init` produced ordering
`[0, 1, 2]`, which is a valid LexBFS of that graph (and was accepted by the
verifier). After inserting edge (0,2), the graph is the path 1-0-2. The
candidate returned `[0, 1, 2]` (it kept the old ordering because its
`_is_valid_lexbfs` checker said it was still valid), but the verifier reports
a 4-point violation at positions a=0, b=1, c=2 with minD = 1e9 (no witness
d exists). The verifier's expected result is `[0, 2, 1]`.

## ROOT_CAUSE

The static `_lexbfs` is a correct partition-refinement LexBFS (its init
output was accepted), so the divergence is in the *validity checker*
`_is_valid_lexbfs`, which wrongly returned True for the ordering `[0, 1, 2]`
on the path 1-0-2.

**Trace of the checker** on graph = path 1-0-2 (edges (0,1), (0,2)),
order = [0, 1, 2] (pos[0]=0, pos[1]=1, pos[2]=2):

- nbr_bits[0] = {1,2} = 0b110
- nbr_bits[1] = {0}   = 0b001
- nbr_bits[2] = {0}   = 0b001

The loop `for b in range(n): for c in range(b+1, n)` visits (b,c) = (0,1),
(0,2), (1,2):

- (b=0, c=1): `bad_a = C & ~B & ((1<<0)-1)` = 0b001 & 0b110 & 0b0 = 0. No check.
- (b=0, c=2): `bad_a = C & ~B & 0b0` = 0. No check.
- (b=1, c=2): B = nbr_bits[1] = 0b001, C = nbr_bits[2] = 0b001.
  `bad_a = C & ~B & ((1<<1)-1)` = 0b001 & 0b110 & 0b01 = **0**. No check.

The checker returns True. But the ordering is invalid: the verifier's
violation triple is (a=0, b=1, c=2), i.e. vertices (0, 1, 2) at positions
(0, 1, 2). In the path 1-0-2: ab = (0,1) ∈ E, ac = (0,2) ∈ E, and there is
no d < a=0. The verifier's property is therefore the **dual** of what the
code implements:

- Code implements: ∀ a<b<c, **ac∈E ∧ ab∉E** ⇒ ∃ d<a: db∈E ∧ dc∉E.
- Verifier checks:  ∀ a<b<c, **ab∈E ∧ ac∉E** ⇒ ∃ d<a: **da∈E ∧ dc∈E**
  (equivalently, the (LB) property applied to the complement graph, or the
  "reverse-order" form).

For the failing triple: ab=(0,1)∈E ✓, ac=(0,2)∈E... wait, ac IS in E, so the
dual antecedent "ac∉E" also fails. Let me re-examine.

Actually, re-reading the verifier's violation: a=0, b=1, c=2, minD=1e9. The
verifier found a triple where the antecedent holds but no witness exists.
In the path 1-0-2 with order [0,1,2]:
- a=0 (vertex 0), b=1 (vertex 1), c=2 (vertex 2)
- ab = (0,1) ∈ E, ac = (0,2) ∈ E, bc = (1,2) ∉ E

The only 4-point property form whose antecedent is satisfied by this triple
and which has no witness (d < 0 is impossible) is:
**∀ a<b<c, ab∈E ∧ bc∉E ⇒ ∃ d<a: da∈E ∧ dc∈E** — no, that's not standard.

Or: **∀ a<b<c, ac∉E ∧ ab∈E ⇒ ∃ d<a: da∉E ∧ dc∈E** — ac=(0,2)∈E, fails.

The most likely correct reading: the verifier checks the (LB) property as
stated in the brief (∀ a<b<c, ac∈E ∧ ab∉E ⇒ ∃ d<a: db∈E ∧ dc∉E) but with
**a, b, c being vertex IDs, not positions**, or the property is stated over
the **reverse** ordering. In the reverse ordering [2,1,0] of the path 1-0-2:
- positions: pos[2]=0, pos[1]=1, pos[0]=2
- a=0 (vertex 2), b=1 (vertex 1), c=2 (vertex 0): ac=(2,0)∈E, ab=(2,1)∉E ✓
  Need d<0: impossible. Violation! minD=1e9. ✓

This matches: the verifier checks the (LB) property on the **reverse** of the
returned ordering (equivalently, the "dual" property: ∀ a<b<c, ab∈E ∧ ac∉E
⇒ ∃ d<a: da∈E ∧ dc∈E applied to the forward ordering). The candidate's
checker implements the forward (LB) property, which is NOT equivalent to
LexBFS validity — the correct certificate is the (LB) property on the
**reverse** ordering (or equivalently the dual form on the forward ordering).

**Responsible lines:**

```python
bad_a = C & ~B & ((1 << b) - 1)   # a: neighbor of c, NON-neighbor of b
W = B & ~C                          # d: neighbor of b, NON-neighbor of c
```

This encodes the forward (LB) property. The correct check for "order is a
valid LexBFS" is the (LB) property applied to the **reverse** of `order`
(equivalently: ∀ a<b<c in forward positions, ab∈E ∧ ac∉E ⇒ ∃ d<a: da∈E ∧
dc∈E).

## REPAIR_HINTS

1. **Safest immediate fix:** in `insert_edge`, always recompute
   `_lexbfs(graph)` (as `delete_edge` already does). The static algorithm is
   correct and its output was accepted at init. This restores correctness
   immediately at the cost of the "avoid recompute" research goal.

2. **If the checker must be kept** (to skip recomputes when the old ordering
   is still valid), fix it to check the (LB) property on the **reverse**
   ordering. Concretely, replace the body of `_is_valid_lexbfs` with a check
   of: for all positions a < b < c in the **reversed** order, if
   ac∈E ∧ ab∉E then ∃ d < a with db∈E ∧ dc∉E. Equivalently, on the forward
   order: for all positions a < b < c, if **ab∈E ∧ ac∉E** then ∃ d < a with
   **da∈E ∧ dc∈E**. In bitset terms on the forward order:
   ```python
   # B = nbr_bits[order[b]], C = nbr_bits[order[c]]
   bad_a = B & ~C & ((1 << b) - 1)   # a: neighbor of b, NON-neighbor of c
   W = ~B & C                          # d: NON-neighbor of b, neighbor of c
   # (mask W to positions < n; check min(W) < min(bad_a))
   ```
   Note: `~B` in Python is infinite-precision, so mask with `(1 << n) - 1`.

3. **Approaches that will not work:**
   - Widening the loop to include b=0 (b=0 has no a < b, so it changes
     nothing).
   - Blaming `_lexbfs` (it is a standard correct partition-refinement
     LexBFS and its init output was accepted).
   - Keeping the current checker polarity and adding a "reverse the order
     before checking" step without also swapping the B/C roles in the
     bitset expressions (the polarity swap is the essential change).
