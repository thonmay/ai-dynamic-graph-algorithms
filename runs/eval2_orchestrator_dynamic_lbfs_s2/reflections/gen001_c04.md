## FAILURE_DESCRIPTION
n=3. After init the state holds ordering [0, 2, 1] (a valid LexBFS of the
initial graph). The failing update is `delete (2, 0)` at sequence_idx 1. The
candidate returned the unchanged ordering [0, 2, 1], but the verifier reports
a (LB) 4-point violation with a=0, b=2, c=1 (pos_a=0, minD=1e9, i.e. no
witness d exists). Expected result [0, 1, 2].

## ROOT_CAUSE
`_certify_delete` is unsound: it only checks triples in which the deleted
edge acts as the *witness* edge db (Case 1: d=u, b=v; Case 2: d=v, b=u).
It never checks triples in which the deleted edge is the *ac* edge of the
property. Deleting an edge can create a new violation by making a previously
satisfied triple (a, b, c) with ac in E lose its ac edge... more precisely,
the property is "for all a<b<c with ac in E and ab not in E, exists d<a with
db in E and dc not in E". Removing edge (u,v) can only *create* violations
when the removed edge was the ac edge of a triple that now has ac NOT in E —
wait, that removes the antecedent, so that cannot create a violation. The real
danger is the opposite: the removed edge (u,v) was the *ab* edge of a triple
(a=u, b=v, c) or (a=v, b=u, c) with a<b<c. Before deletion ab in E, so the
triple was not required to have a witness; after deletion ab not in E, so
the triple (a, b, c) with ac in E now REQUIRES a witness d<a with db in E
and dc not in E, and that witness may not exist.

In the failing case: ordering [0, 2, 1], delete (2,0). Take a=0 (pos 0),
b=2 (pos 1), c=1 (pos 2). After deletion, ab=(0,2) not in E, ac=(0,1) in E,
and there is no d<0, so the property is violated. Before deletion (0,2) was
in E, so this triple was exempt. `_certify_delete` has no case for "deleted
edge is the ab edge", so it returns True and keeps the invalid ordering.

The same gap exists symmetrically for (a=v, b=u, c) when pos(v)<pos(u).

## REPAIR_HINTS
Add a third case to `_certify_delete` (and note the same class of bug is
worth re-auditing in `_certify_insert`, where the new edge can become the ab
edge of a triple (a=u, b=v, c) or (a=v, b=u, c) with c after both — the
current insert certifier only handles the new edge as the ac edge):

For delete (u,v) with pu<pos(v) (i.e. u before v in the ordering):
  For each c with pos(c) > pos(v): if graph[u][c] (ac in E, a=u, b=v) and
  graph[u][v] was in E (it was, since we're deleting it), then after deletion
  ab not in E, so we need a witness d with pos(d) < pos(u), d != v, with
  graph[d][v] and not graph[d][c]. If none exists, return False.
Symmetric case when v is before u: a=v, b=u, c after u, need d<pos(v) with
d != u, graph[d][u] and not graph[d][c].

Simplest robust fix given the open-problem context: make the certifiers
conservative — on any update, recompute `_lexbfs` unless a *complete*
re-check of the (LB) property over all triples (a,b,c) passes (O(n^4) or
O(n^3) with precomputed adjacency). A full post-update (LB) check is the
minimal change that restores correctness; the local cases are only an
optimization and must be proven to cover every way the update can affect the
property (ac edge, ab edge, and witness edge db).

Approaches that will not work: keeping the current two-case delete
certifier (it misses the ab-edge case, as shown); relying on the fact that
removing an edge "only removes witnesses" (it also removes ab edges, which
activates new obligations).
