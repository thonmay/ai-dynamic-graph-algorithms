## FAILURE_DESCRIPTION

Operation: `insert (2, 0)` at sequence index 0 (first update after `init`).
Post-update graph (4 vertices, undirected, 0/1 adjacency matrix):

```
    0 1 2 3
0: [0 0 1 0]
1: [0 0 0 1]
2: [1 0 0 1]
3: [0 1 1 0]
```

Edges: {0-2, 1-3, 2-3}.

- Expected (a valid LexBFS ordering): `[0, 2, 3, 1]`
- Actual returned: `[0, 2, 1, 3]`
- Reported violation: a=2, b=1, c=3, pos_a=1, minD=1000000000 (no witness).

The actual ordering is genuinely invalid on the post-insertion graph:
positions pos[0]=0, pos[2]=1, pos[1]=2, pos[3]=3. Triple a=2 (pos 1), b=1
(pos 2), c=3 (pos 3): a~c (2-3 in E), a!~b (2-1 not in E). A witness d must
have pos[d] < 1, i.e. d=0, with d~b (0-1 in E) and d!~c (0-3 not in E). But
0-1 is not an edge, so no witness exists.

## ROOT_CAUSE

The bug is in the static `_lexbfs` partition-refinement routine. The dynamic
checker `_is_valid_lexbfs` is actually correct here: it rejected the stale
pre-insertion ordering (the verifier's minD=1000000000 is the verifier's own
sentinel, not the candidate's INF=5, so it tells us nothing about the
candidate's internals), which forced the recompute path. The recompute then
called `_lexbfs(graph)` on the post-insertion graph, and `_lexbfs` itself
produced the invalid ordering `[0, 2, 1, 3]`.

Trace of `_lexbfs` on the post-insertion graph (edges {0-2, 1-3, 2-3}):

1. buckets=[[0,1,2,3]]. Pop v=0 from bucket 0.
   adj of 0 in [1,2,3] = [2] (0-2 edge); nonadj = [1,3].
   buckets=[[2],[1,3]]. order=[0].
2. Pop v=2 from bucket 0 (now [2]→[]).
   adj of 2 in [] = []; nonadj = []. buckets=[[],[1,3]]. order=[0,2].
3. Pop v=1 from bucket 1 ([1,3]→[3]).
   adj of 1 in [3] = [3] (1-3 edge); nonadj = [].
   buckets=[[],[3]]. order=[0,2,1].
4. Pop v=3. order=[0,2,1,3].

Result `[0,2,1,3]` — exactly the failing output.

Why this is wrong: the standard partition-refinement LexBFS (Habib–McConnell–
Paul–Viennot) refines EVERY bucket by adjacency to the chosen vertex v, not
just the bucket v was taken from. In step 2, when v=2 is chosen, the other
bucket [1,3] must be split by adjacency to 2: 2~3 (edge) and 2!~1, so it
becomes [3] (adj, front) then [1] (nonadj). The correct queue after step 2 is
[[3],[1]] (plus the emptied bucket 0), giving order [0,2,3,1] — the expected
answer. The candidate's code only splits `buckets[i]` (the bucket v came from):

```python
# Split the rest of bucket i into adj and nonadj.
adj = [w for w in buckets[i] if graph[v][w]]
nonadj = [w for w in buckets[i] if not graph[v][w]]
```

All other buckets are left untouched, so vertex 1 (non-neighbor of 2) is never
pushed behind 3 (neighbor of 2), and 1 is ordered before 3 — violating the
LexBFS label-refinement rule and hence the (LB) 4-point property.

## REPAIR_HINTS

1. Fix `_lexbfs` to refine ALL buckets by adjacency to v, not just v's own
   bucket. After popping v from bucket i, for every bucket j (including i,
   which now holds v's remaining siblings) split it into adj_v (front) and
   nonadj_v (behind), preserving the global FIFO order of buckets. Concretely,
   replace the single-bucket split with a loop over all buckets:

   ```python
   new_buckets = []
   for bk in buckets:
       a = [w for w in bk if graph[v][w]]
       na = [w for w in bk if not graph[v][w]]
       if a: new_buckets.append(a)
       if na: new_buckets.append(na)
   buckets = new_buckets
   ```

   (Drop empty buckets; the "first non-empty bucket, first vertex" selection
   already handles empties, but dropping them keeps the queue clean.)

2. After fixing, verify `_lexbfs` output on the post-insertion graph yields
   `[0,2,3,1]` and passes `_is_valid_lexbfs`. Also spot-check on a few small
   graphs (path P4, cycle C4, two disjoint edges) that the output satisfies
   the (LB) property.

3. The `_is_valid_lexbfs` checker is fine as-is for this failure (it correctly
   forced the recompute). Do not "fix" it based on this case. If you want a
   faster validator, note the current O(n^3) min_pos_W test is a necessary
   condition that is sound for validating arbitrary orderings only if you keep
   the `min_pos_W[b][c] >= pa` comparison — which the code already does — so
   leave it alone unless a separate bug is found.

Approaches that will NOT work:
- Only adjusting the dynamic update logic (insert_edge/delete_edge): the
  recompute path is already taken and correct; the defect is entirely in the
  static `_lexbfs`.
- Keeping the single-bucket split and adding a post-hoc sort/repair of the
  ordering: LexBFS validity is not restorable by local reordering; the
  refinement must be done correctly during the scan.
