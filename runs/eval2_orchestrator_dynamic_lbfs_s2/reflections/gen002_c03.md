## FAILURE_DESCRIPTION

Failing case: n=3, operation `insert (0, 2)` at sequence_idx 0. The graph
after the update is the path 1-0-2 (edges {0-1, 0-2}; vertex 1 and 2 are
non-adjacent). The candidate returned `[0, 1, 2]`; the expected valid LexBFS
ordering is `[0, 2, 1]` (any valid ordering is accepted, but `[0, 1, 2]` is
not one).

The verifier reports a 4-point violation at positions a=0, b=1, c=2
(pos_a=0, minD=10^9 = "no witness found"). Interpreting the verifier's
property in the forward order (the brief's form): for a<b<c with
ab in E and ac not in E, there must exist d < a with da in E and dc not in E.
For order [0,1,2]: a=0 (v=0), b=1 (v=1), c=2 (v=2): 0-1 in E, 0-2 not in E
in the verifier's view, and no d < 0 exists, so the property fails.

Note the asymmetry: the candidate's own `_is_valid_lexbfs` checks the (LB)
property on the REVERSE of the order, while the verifier evidently checks the
brief's forward form. For a 3-vertex path these two forms are not equivalent
for arbitrary orderings: [0,1,2] fails the forward form but passes the
reverse form (and vice versa for [0,2,1]).

## ROOT_CAUSE

The static `_lexbfs` is a correct partition-refinement LexBFS (verified by
hand on this case: it produces [0,1,2] for the path 1-0-2, which is a valid
LexBFS in the standard "non-neighbors before neighbors" convention). The
divergence is a convention mismatch between the candidate and the verifier:

- The candidate's docstring and `_is_valid_lexbfs`/`_is_valid_lexbfs_brute`
  all check the (LB) 4-point property on `reversed(order)`:
  "for all positions a < b < c in the reversed order, if ac in E and ab not
  in E, then exists d < a with db in E and dc not in E."
- The verifier (per the failing case) checks the brief's forward form on the
  returned order: "for all a < b < c with ab in E and ac not in E, exists
  d < a with da in E and dc not in E."

These are dual forms. The candidate's ordering [0,1,2] satisfies the reverse
form (its own checker would return True) but violates the forward form, so
the verifier rejects it. The bug is not in the partition refinement itself
and not in the update logic (insert/delete just recompute from scratch,
which is always consistent with init); it is that the produced ordering is
in the opposite orientation to what the verifier certifies.

## REPAIR_HINTS

Smallest fix: return the reverse of the static LexBFS output, i.e. in
`init`, `insert_edge`, and `delete_edge` return
`{'ordering': list(reversed(_lexbfs(graph)))}`. Equivalently, keep the
forward output and change the static algorithm's refinement so that the
neighbor part of a split bucket is placed BEFORE the non-neighbor part
(currently `new_buckets.append(nnb); new_buckets.append(nb)` — swap to
`new_buckets.append(nb); new_buckets.append(nnb)`). Either change makes the
returned order satisfy the verifier's forward 4-point form.

Verification of the fix on the failing case: reversing [0,1,2] gives
[2,1,0]; forward check: a=0 (v=2), b=1 (v=1), c=2 (v=0): ab=2-1 not in E,
so the antecedent is false — no violation. Valid.

Do NOT "fix" this by changing the verifier's property or by special-casing
small n; the mismatch is a global orientation convention. Also note the
candidate's `_is_valid_lexbfs` bitset check is itself correct for the
reverse form (the min(W) < min(bad_a) reduction is valid because the witness
set W is position-independent of a), so no change is needed there once the
orientation is fixed — but the dead code (`_is_valid_lexbfs`,
`_is_valid_lexbfs_brute`, and the state parameter) can be removed since
insert/delete currently just recompute.
