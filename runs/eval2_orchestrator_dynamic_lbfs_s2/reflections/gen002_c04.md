## FAILURE_DESCRIPTION

Failing case (sequence_idx 0, i.e. the very first update after `init`):
- Operation: `insert (2, 0)` on a 4-vertex undirected graph.
- The candidate returned the pre-insertion ordering `[0, 1, 3, 2]` unchanged
  (local certification passed), but the post-insertion graph requires
  `[0, 1, 2, 3]`.
- The verifier reports the (LB) 4-point violation with a=0, b=3, c=2
  (pos_a=0, minD=1): in the returned ordering, a=0 is at position 0, b=3 at
  position 2, c=2 at position 3, so a < b < c holds; after the insertion
  ac = (0,2) is an edge, ab = (0,3) is not an edge, and no witness
  d < a exists (a is the first vertex, so the witness set is empty).

Reconstructed pre-insertion graph (consistent with everything below):
edges (0,1), (1,2), (1,3). Static LexBFS with the candidate's tie-break
(smallest label set, then smallest id) gives [0, 1, 3, 2]:
- pick 0; labels: 1->{0}, 2->{}, 3->{}
- pick 1 (label {0}); labels: 2->{0,1}, 3->{0,1}
- pick 3 (tie, smaller id); labels: 2->{0,1,3}
- pick 2.
After inserting (0,2), the correct LexBFS is [0, 1, 2, 3]:
- pick 0; labels: 1->{0}, 2->{0}, 3->{}
- pick 1; labels: 2->{0,1}, 3->{0,1}
- pick 2 (tie, smaller id); labels: 3->{0,1,2}
- pick 3.

## ROOT_CAUSE

`_certify_insert` (candidates/gen002_c04.py) is unsound: it only checks the
triples in which the *new edge* is the `ac` edge, and it does so with the
wrong witness condition. Two independent defects:

1. **Wrong witness condition.** The (LB) property requires, for a triple
   (a, b, c) with a < b < c, ac in E, ab not in E, a witness d < a with
   **db in E and dc not in E** (witness edges go to b and c). The code
   instead checks:

   ```python
   for d_idx in range(pu):
       d = ordering[d_idx]
       if graph[d][b] and not graph[d][v]:
   ```

   i.e. `db in E and dv not in E` — it tests the witness against the
   endpoint v of the new edge rather than against c. In this case the new
   edge is (u,v) = (0,2) with pu=0, so the loop `range(pu)` is empty and
   the function returns True without checking anything.

2. **Missing triple families.** Inserting edge (u,v) also makes `ab not in E`
   false for triples where the new edge is the **ab edge**: (a=u, b=v, c)
   and (a=v, b=u, c) for every c after both. Those triples previously had
   no obligation (ab was an edge) and now require a witness d < a with
   db in E and dc not in E. `_certify_insert` never checks these. In the
   failing case this is exactly the violated triple: a=0=u, b=3, c=2=v,
   with ac=(0,2) in E (the new edge), ab=(0,3) not in E, and no d < 0.

   (The symmetric "new edge as the dc edge" family, (a, b=u, c=v) /
   (a, b=v, c=u), is also not checked, but the two defects above are
   sufficient to explain this failure.)

Because the certification returned True, `insert_edge` kept the stale
ordering `[0, 1, 3, 2]` instead of falling through to the `_lexbfs`
recompute, which would have produced the correct `[0, 1, 2, 3]`.

## REPAIR_HINTS

Smallest correct fix: make `_certify_insert` check **all** triple families
whose status can change when edge (u,v) is added, with the correct witness
condition (db in E and dc not in E, d < a):

- Family A (new edge = ac): (a=u, b, c=v) and (a=v, b, c=u) for b strictly
  between a and c in position, with ab not in E. Witness: d < a with
  `graph[d][b] and not graph[d][c]` (note: c, not v).
- Family B (new edge = ab): (a=u, b=v, c) and (a=v, b=u, c) for c after
  both, with ac in E. Witness: d < a with `graph[d][b] and not graph[d][c]`.
- Family C (new edge = dc): (a, b=u, c=v) and (a, b=v, c=u) for a before
  both, with ac in E and ab not in E. Witness: d < a, d != the other
  endpoint, with `graph[d][b] and not graph[d][c]`.

If any such triple lacks a witness, return False so `insert_edge`
recomputes via `_lexbfs`.

Approaches that will not work:
- Keeping the current "only family A" structure and merely fixing the
  witness variable (v -> c) is still incomplete: family B (new edge as ab)
  is exactly what this failing case exercises, and it is not covered.
- A "cheap" certification that only looks at b between the two endpoints
  cannot be sound for insertions, because the new edge can create
  obligations for triples where one endpoint is b and the other endpoint is
  anywhere after it.
- Note the same audit should be applied to `_certify_delete`: its
  "witness edge" cases (Case 1/Case 2) correctly use `graph[d][v] and not
  graph[d][c]`-style conditions, but the "ab edge" cases (3a/3b) should be
  re-verified against the same property statement before trusting them.
  The safest interim measure, if a full audit is not feasible, is to make
  both `_certify_insert` and `_certify_delete` return False (force
  recompute) until the certification logic is proven correct — the
  recompute path is already correct.
