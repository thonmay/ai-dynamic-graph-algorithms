## FAILURE_DESCRIPTION
n=3. Operation at sequence_idx 0: `insert (0,1)`. The post-update graph is the triangle K3 (edges (0,1), (0,2), (1,2)). The candidate returned ordering `[0, 2, 1]`; the expected (and only valid) LexBFS ordering of K3 is `[0, 1, 2]`. The verifier reports a 4-point violation at positions a=0, b=2, c=1 (minD = 1e9, i.e. no witness d found).

## ROOT_CAUSE
The candidate's "keep the ordering" path is unsound. In `_check_and_maybe_recompute`:

```python
if _fast_filter(graph, order) and _is_valid_lexbfs(graph, order):
    return state
```

it keeps the stale ordering whenever the (LB) 4-point property holds. But the 4-point property is a certificate of **chordality**, not of "this ordering is a LexBFS ordering." It is necessary but not sufficient.

Trace on the failing case:
1. `_fast_filter` passes: order[0]=0 is universal in K3, and consecutive pairs (0,2), (2,1) are edges.
2. `_is_valid_lexbfs` passes vacuously: in K3 every pair is an edge, so the trigger condition `ab not in E` never holds and the function returns True without checking anything.

So the stale ordering `[0,2,1]` (carried over from the pre-insert graph) is kept. But `[0,2,1]` is NOT a LexBFS ordering of K3: in a complete graph every vertex is adjacent to every previously selected vertex, so all buckets remain merged throughout the refinement and the tie-break `v = min(buckets[bi])` in `_lexbfs` forces the ordering to be `[0,1,2]`. Selecting 2 before 1 is impossible in any LexBFS run on K3.

The docstring's soundness claim — "we never keep an invalid ordering" because "the 4-point property is the exact certificate" — is the false premise. The 4-point property characterizes chordal graphs (and, for a chordal graph, the set of LexBFS orderings is a subset of all orderings satisfying it); it does not certify that an arbitrary ordering is a LexBFS ordering.

## REPAIR_HINTS
The smallest correct fix: **remove the keep path entirely** — always recompute after an update:

```python
def _check_and_maybe_recompute(graph, state):
    return {'ordering': _lexbfs(graph)}
```

This restores full correctness (the static `_lexbfs` is correct; the failing case is purely a false-keep, not a bug in `_lexbfs` itself). It does cost a full O(n^2) recompute per update, which the research goal wants to avoid later, but correctness first.

What will NOT work:
- Strengthening `_fast_filter` (e.g. adding more necessary conditions) cannot fix this: the problem is that the 4-point check is not sufficient, and no cheap necessary-condition filter can distinguish `[0,2,1]` from `[0,1,2]` on K3 without essentially re-running the refinement.
- "Fixing" `_is_valid_lexbfs` to be a true certificate of LexBFS-ness is not feasible as a cheap check: verifying that an ordering is a LexBFS ordering requires simulating the partition refinement (or an equivalent O(n^2)-ish check), at which point you may as well recompute the ordering directly.

For a future (non-correctness) optimization: a legitimate cheap keep-test would be to re-run the static refinement on the current ordering's bucket structure and check that the same ordering is reproduced (i.e., verify the ordering is a fixed point of the refinement with the min tie-break). That is O(n^2) and equivalent in cost to recomputing, so the real open-problem work is in maintaining the refinement incrementally.
