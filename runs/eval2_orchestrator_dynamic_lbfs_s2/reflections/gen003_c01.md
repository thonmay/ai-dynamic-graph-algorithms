## FAILURE_DESCRIPTION

Failing case (sequence_idx 0, operation `insert (2, 0)` on a 4-vertex
graph): the candidate returned the stale ordering `[0, 1, 3, 2]` instead
of the expected valid LexBFS ordering `[0, 1, 2, 3]`.

The verifier reports the (LB) 4-point property violated at
`a=0, b=3, c=2` (pos_a=0, minD=1). In the returned ordering
`[0, 1, 3, 2]`: pos(0)=0, pos(1)=1, pos(3)=2, pos(2)=3. The triple
(a=0@pos0, b=3@pos2, c=2@pos3) has ac=(0,2) in E (the just-inserted
edge) and ab=(0,3) not in E, so a witness d < a is required. Since a is
at position 0, no such d exists, and the ordering is invalid.

## ROOT_CAUSE

The local certification in `_certify_insert` is unsound: it only checks
triples whose *obligation* (the ac-in-E / ab-not-in-E condition) can
change when the new edge is added, and misses triples whose obligation
was already present before the update but whose *witness set* is
destroyed by it.

Concretely, consider a triple (a, b, c) with a < b < c that was already
obligated before the insert (ac in E, ab not in E). Its witness d < a
satisfies db in E and dc not in E. If the inserted edge is (d, c), then
after the insert dc is in E, so d is no longer a valid witness. If d was
the *only* witness, the triple now lacks a witness and the ordering is
invalid — but the certification never looks at this triple, because the
new edge is neither ac nor ab of any triple it enumerates.

In the failing case: the stale ordering `[0, 1, 3, 2]` was valid before
the insert. The triple (a=0, b=3, c=2) was already obligated (0-2 in E,
0-3 not in E) and its only witness was d=1 (1-3 in E, 1-2 not in E).
The inserted edge (2, 0) makes 0-2 in E, which is the ac edge of the
triple (a=0, b=3, c=2). This is Family A in the certification.

Tracing `_certify_insert` with edge (2,0): u=2, v=0. pos(2)=3, pos(0)=0.
Since pu=3 > pv=0, swap: u=0, v=2, pu=0, pv=3.

Family A: new edge = ac, a=u=0, c=v=2, b strictly between pu=0 and pv=3.
b_idx in range(1, 3): b_idx=1 → b=ordering[1]=1; b_idx=2 → b=ordering[2]=3.

- b=1: if graph[0][1]=1, skip. If graph[0][1]=0, check witness for
  (a=0, b=1, c=2): d_idx in range(0) → empty → False → return False.
- b=3: if graph[0][3]=1, skip. If graph[0][3]=0, check witness for
  (a=0, b=3, c=2): d_idx in range(0) → empty → False → return False.

The violation says ab=(0,3) is NOT in E, so graph[0][3]=0, and Family A
should catch b=3 and return False, triggering recompute. But the
candidate returned the stale ordering, meaning `_certify_insert` returned
True. This is a contradiction unless the graph state at certification
time differs from the post-update graph.

The most likely explanation: the `graph` parameter in `insert_edge` is
the graph BEFORE the edge is inserted (the caller flips the entry after
the call). In that case, graph[0][2]=0 at certification time, and the
triple (a=0, b=3, c=2) is NOT yet obligated (ac=(0,2) not in E), so
Family A's check `if graph[u][b]: continue` for b=3 sees graph[0][3]=0
and proceeds to `_witness_exists(graph, ordering, 0, 3, 2)`. But since
ac is not in E, this triple is not actually obligated, and the witness
check is vacuous — the certification incorrectly treats it as if the
obligation exists.

Alternatively, if the graph IS post-update, then Family A should catch
the violation, and the bug is elsewhere (e.g., a logic error in the
swap or the family enumeration). Without the exact pre-update graph, I
cannot fully disambiguate, but the root cause is clear: the
certification does not correctly handle the case where the new edge
destroys the witness set of an already-obligated triple.

## REPAIR_HINTS

1. **Verify the graph state convention**: Confirm whether `graph` in
   `insert_edge`/`delete_edge` is the pre-update or post-update graph.
   The certification logic in `_certify_insert` assumes post-update (the
   new edge is present in `graph`). If the convention is pre-update, all
   family conditions need to be adjusted. This is the most likely root
   cause of the failure.

2. **Implement Family C for insert**: The docstring of `_certify_insert`
   describes Family C ("new edge = dc: (a, b=u, c=v) and (a, b=v, c=u)
   for a before both, with ac in E and ab not in E"), but the code only
   implements Families A and B. Add the Family C loop to
   `_certify_insert`:
   ```python
   # Family C: new edge is dc. a before both, b = u, c = v.
   for a_idx in range(pu):
       a = ordering[a_idx]
       if not graph[a][v]:
           continue
       if graph[a][u]:
           continue
       if not _witness_exists(graph, ordering, a_idx, u, v, exclude=(v,)):
           return False
   ```
   This mirrors the Family C loop already present in `_certify_delete`.

3. **Make the certification conservative**: If any family is uncertain
   or the graph state convention is unclear, return False to trigger a
   recompute. The recompute path (`_lexbfs`) is correct, so a
   conservative certification is safe.

4. **Approaches that will not work**: Simply adding the missing Family C
   loop without verifying the graph state convention may still fail if
   the graph is pre-update. Always test with the actual graph state
   convention used by the verifier.
