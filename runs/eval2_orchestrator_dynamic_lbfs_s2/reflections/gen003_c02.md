## FAILURE_DESCRIPTION

Operation: `insert (2, 0)` at sequence index 0 (i.e. the first update after `init`).
The state's ordering before the update was `[0, 1, 3, 2]` (a valid LexBFS of the
pre-insertion graph). After inserting edge (2,0), the candidate returned the
**unchanged** ordering `[0, 1, 3, 2]` (actual result), but the expected valid
ordering is `[0, 1, 2, 3]`.

The returned ordering violates the (LB) 4-point property on the post-insertion
graph:
- a = 0 (pos 0), b = 3 (pos 2), c = 2 (pos 3)
- ac = (0,2) is in E (this is exactly the edge just inserted)
- ab = (0,3) is NOT in E
- required: some d < pos(a)=0 with db in E and dc not in E — impossible, since
  no vertex precedes position 0. The verifier reports `minD: 1` (no witness).

So the ordering `[0, 1, 3, 2]` is not a valid LexBFS of the post-insertion
graph, and the candidate failed to detect this.

## ROOT_CAUSE

The local certification `_certify_insert` is **unsound**: it only checks the
triples in which the newly inserted edge plays the role of the *ac* edge
(a=u, b, c=v with pu < pos(b) < pv), and returns True if all of those have a
witness. It never checks triples in which the new edge plays the role of the
*ab* edge.

Trace on the failing case. After the swap, u=0 (pu=0), v=2 (pv=3). The loop
`for idx in range(pu + 1, pv)` covers positions 1 and 2, i.e. b=1 and b=3:
- b=1: `graph[0][1]` is 1 (edge (0,1) exists), so `continue` — no check.
- b=3: `graph[0][3]` is 0, so it searches for a witness d in
  `range(pu)` = `range(0)` — an **empty** range — finds none, and should return
  False.

Wait — that would return False and trigger a recompute. Let me re-check: the
violation triple is (a=0, b=3, c=2), where the new edge (0,2) is the **ac**
edge, b=3 is between pu=0 and pv=3, and ub=(0,3) is not in E. The certification
loop does cover b=3 at idx=2, and `range(pu)` = `range(0)` is empty, so
`found` stays False and the function should return False...

Re-examining: the loop is `for idx in range(pu + 1, pv)` = `range(1, 3)` =
{1, 2}. At idx=2, b = ordering[2] = 3. `graph[u][b]` = `graph[0][3]` = 0, so
we enter the witness search over `range(pu)` = `range(0)` — empty — `found`
remains False, and `_certify_insert` returns False. That would force a

Given the actual result equals the pre-update ordering, the recompute path was
NOT taken, which means `_certify_insert` returned True. The only way that
happens is if `graph[0][3]` was 1 at the time of the check (i.e. the loop
`continue`d at b=3) — but then the violation triple (a=0,b=3,c=2) would not
exist either, since ab would be in E. This is contradictory, so the trace is
**inconclusive** from the reported fields alone: I cannot determine from the
violation record which matrix entries the pre-update graph had beyond
(0,2) inserted and (0,3) absent in the post-update graph.

What IS certain, independent of the exact trace, is the **structural flaw** in
`_certify_insert`: it only certifies triples where the new edge is the ac edge.
An insertion of (u,v) can also create a violation where the new edge is the
**ab** edge: triple (a=u, b=v, c) with pos(c) > pv and uc in E. Before the
insertion, ab=(u,v) was not in E, so the triple (u, v, c) was not subject to
the witness obligation (the property only applies when ab is NOT in E — wait,
the property requires a witness when ab is NOT in E, so before insertion the
obligation already existed and was satisfied; after insertion ab IS in E, so
the obligation is *removed* — this direction cannot create a violation).

Correctly: an insertion can only *create* a violation by adding an ac edge
(activating a new obligation) — which is what the code checks — or by adding a
witness edge (which only helps). So the ac-edge case is the only dangerous one,
and the code's case analysis is actually the right one. The remaining suspect
is the **witness search range**: for triple (a=u, b, c=v), the witness d must
satisfy d < a = u, i.e. d in positions [0, pu). The code uses
`range(pu)` — correct. But it requires `graph[d][b] and not graph[d][v]`.
That is also correct per the property.

Since the trace is inconclusive from the given data, the hypotheses are:
1. (ruled out by logic) the certification's case analysis is wrong — it is not;
   insertion only creates obligations via the ac edge.
2. (open) the pre-update ordering `[0,1,3,2]` was itself invalid for the
   pre-update graph (a bug in `_lexbfs` or in `init`), and the verifier's
   expected/actual comparison is masking that; the reported violation is on
   the post-update graph but the true first divergence may be earlier.
3. (open) `_lexbfs`'s tie-breaking (`tl > tb` on sorted label lists) is not a
   valid LexBFS comparison — LexBFS compares labels lexicographically as
   sequences of 0/1 over the *ordering so far*, not as sorted sets of
   neighbor ids. Comparing `sorted(lv) > sorted(best_label)` compares the
   neighbor-id sets in ascending id order, which is NOT the LexBFS label
   order (labels must be compared in the order vertices were output). This is
   a concrete, likely bug: `_lexbfs` may produce orderings that are not valid
   LexBFS orderings at all, so `init` can return an invalid ordering, and the
   "expected" `[0,1,2,3]` vs "actual" `[0,1,3,2]` may reflect that the
   candidate's static routine is wrong.

## REPAIR_HINTS

1. **Fix `_lexbfs` first (highest priority).** The label comparison
   `tl = sorted(lv); tb = sorted(best_label); if tl > tb` compares labels as
   sorted lists of *vertex ids*, but LexBFS labels are bit-vectors indexed by
   *output position* and must be compared lexicographically in output order
   (earlier output positions are more significant). Replace the label
   representation with a list/tuple indexed by output position (e.g.
   `labels[v]` = tuple of 0/1 of length = current output length, appended as
   each vertex is output), and compare tuples directly (Python tuple
   comparison is lexicographic). This is the smallest change that restores
   static correctness; without it, no amount of dynamic certification can
   save the candidate.
2. **Do not** try to "fix" `_certify_insert` by adding the ab-edge case —
   that case cannot create a violation on insertion (adding ab removes the
   obligation), so it is a no-op and will not fix this failure.
3. After fixing `_lexbfs`, re-run the failing sequence; if the failure
   persists, the certification logic should be re-audited with the corrected
   pre-update ordering, since the current trace is inconclusive because the
   pre-update ordering may itself have been invalid.
4. A robust fallback while debugging: make `insert_edge`/`delete_edge` always
   recompute via the (fixed) `_lexbfs`; this guarantees correctness and
   isolates whether the certification functions are the remaining issue.
