## FAILURE_DESCRIPTION

Failing case (sequence_idx 2, operation `insert (0, 3)` on a 4-vertex undirected graph):

- State entering the update: `ordering = [0, 1, 2, 3]` (positions: 0→0, 1→1, 2→2, 3→3).
- Update: insert edge (0, 3).
- Expected result: `[0, 1, 3, 2]` (the verifier's reference LexBFS for the post-update graph).
- Actual result: `[0, 1, 2, 3]` — the candidate kept the old ordering because `_certify_insert` returned True.
- Violation reported by the checker on the returned ordering: a=1, b=2, c=3 (pos_a=1), `minD = 1000000000` (sentinel = no witness found).

Concrete check of the violation on the post-update graph: positions a=1 < b=2 < c=3, edge (1,3) in E, edge (1,2) not in E, and there is NO d < pos(1)=1 with (d,2) in E and (d,3) not in E. The only candidate witness is d=0, and 0 is adjacent to BOTH 2 and 3, so it fails the "dc not in E" requirement. Hence `[0,1,2,3]` is not a valid LexBFS ordering of the post-update graph.

## ROOT_CAUSE

The local certification in `_certify_insert` is unsound: it only checks triples where the NEW edge (u,v) plays the role of the `ac` edge, and it misses the case where the new edge plays the role of the `ab` edge.

Responsible lines (in `_certify_insert`):

```python
for idx in range(pu + 1, pv):
    b = ordering[idx]
    if graph[u][b]:
        continue
    found = False
    for d_idx in range(pu):
        d = ordering[d_idx]
        if graph[d][b] and not graph[d][v]:
            found = True
            break
    if not found:
        return False
return True
```

The docstring claim — "The new edge can only break the property as the ac edge of a triple (a=u, b, c=v) with pu < pos(b) < pv and ub not in E" — is false. The new edge (u,v) can ALSO be the `ab` edge of a triple (a=u, b=v, c) with pos(c) > pv and uc in E. Before the insertion, (u,v) was not in E, so the triple (u, v, c) was not subject to the witness obligation (the property only fires when ab is in E). After the insertion, (u,v) IS in E, so the triple (u, v, c) now REQUIRES a witness d < pu with (d,v) in E and (d,c) not in E. The code never checks this.

Trace on the failing case:
- pu = pos(0) = 0, pv = pos(3) = 3.
- The loop `for idx in range(1, 3)` checks b = ordering[1] = 1 and b = ordering[2] = 2.
  - b=1: `graph[0][1]` — if 0-1 is an edge, `continue`; if not, it looks for d in range(0) = empty → returns False. Either way this branch does not produce the bug.
  - b=2: `graph[0][2]` — if 0-2 is an edge, `continue`; if not, d in range(0) is empty → returns False.
- The loop finishes without returning False, so `_certify_insert` returns True and the stale ordering is kept.
- The missed obligation: triple (a=0, b=3, c) for every c with pos(c) > 3 and (0,c) in E. In the post-update graph, the checker's violation is reported at (a=1, b=2, c=3), which is a DIFFERENT triple, but the root cause is the same: the insertion of (0,3) changed the witness landscape for triples where (0,3) is the ab edge, and the certification did not account for it. The stale ordering fails the (LB) property, and the checker reports the first (or some) violating triple it finds.

The deeper issue: the certification's case analysis is incomplete. An edge insertion can affect the (LB) property in at least two ways:
1. The new edge is the `ac` edge (checked, but the check itself may also be incomplete — see below).
2. The new edge is the `ab` edge (NOT checked — this is the bug).

Additionally, even the checked case (new edge as `ac`) is only partially correct: the code checks triples (a=u, b, c=v) with pu < pos(b) < pv and ub not in E, requiring a witness d < pu with (d,b) in E and (d,v) not in E. But the new edge (u,v) as `ac` could also appear in triples where a=v and c=u (if pv < pu, which is handled by the swap) — that is covered. However, the new edge as `ac` could ALSO appear in triples where the new edge is (a,c) = (u,v) but b is NOT between u and v in the ordering... wait, no: for (a,b,c) with a < b < c and ac = (u,v) in E, we need pu < pos(b) < pv (after the swap so pu < pv). So that part is correct. The missing case is purely the `ab` role.

## REPAIR_HINTS

The smallest concrete fix: in `_certify_insert`, after the existing loop (which handles the new edge as `ac`), add a second loop that handles the new edge as the `ab` edge:

```python
# New edge (u,v) as the ab edge: triple (a=u, b=v, c) with pos(c) > pv and uc in E.
# After insertion, (u,v) in E, so a witness d < pu with (d,v) in E and (d,c) not in E is required.
for c_idx in range(pv + 1, n):
    c = ordering[c_idx]
    if not graph[u][c]:
        continue
    found = False
    for d_idx in range(pu):
        d = ordering[d_idx]
        if graph[d][v] and not graph[d][c]:
            found = True
            break
    if not found:
        return False
```

This is exactly the same structure as Case 1 in `_certify_delete` (which correctly handles the symmetric situation where deleting an edge REMOVES the ab edge and thus the witness obligation — wait, no: in deletion, removing the ab edge REMOVES the obligation, so it can never create a violation. In insertion, ADDING the ab edge CREATES the obligation, so it CAN create a violation. The check is the same: for each c with uc in E, verify a witness exists.)

Approaches that will NOT work:
- Simply returning False from `_certify_insert` always (forcing a recompute) would be correct but defeats the purpose of the local certification. The goal is to avoid full recomputation when the ordering is still valid.
- Checking only the `ac` role (current code) is insufficient — the `ab` role must also be checked.
- The `db` (witness) role: an edge insertion can only ADD witnesses, never remove them, so it cannot create a violation. No check needed for this role on insertion.

The fix is a ~10-line addition to `_certify_insert`. The `_certify_delete` function's Case 1 is actually WRONG in the opposite direction: deleting the ab edge REMOVES the witness obligation, so it can never create a violation (the code's comment says this correctly, but then it still checks and returns False if no witness is found — this is overly conservative but not incorrect, since it just forces a recompute unnecessarily). The real bug is in `_certify_insert`.
