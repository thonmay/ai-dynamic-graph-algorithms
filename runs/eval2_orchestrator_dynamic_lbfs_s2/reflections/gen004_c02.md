## FAILURE_DESCRIPTION

Failing case (sequence_idx 0, operation `insert (2, 0)` on a 4-vertex graph):
- State ordering before the update: `[0, 1, 3, 2]` (positions: 0→0, 1→1, 3→2, 2→3).
- After inserting edge (2,0), the candidate returned the SAME ordering `[0, 1, 3, 2]` (certification passed).
- Expected (a valid LexBFS of the updated graph): `[0, 1, 2, 3]`.
- Verifier reports the (LB) violation with a=0, b=3, c=2 (pos_a=0, minD=1): in the returned ordering, a=0 (pos 0) < b=3 (pos 2) < c=2 (pos 3), edge 0-2 is in E (the just-inserted edge), edge 0-3 is not in E, and no witness d < pos(0) exists (pos(0)=0, so the witness set is empty).

## ROOT_CAUSE

The local insertion certification in `_certify_insert` is incomplete. It only checks triples where the NEW edge is the `ac` edge, i.e. triples `(a=u, b, c=v)` with `pu < pos(b) < pv` and `ub not in E`:

```python
for idx in range(pu + 1, pv):
    b = ordering[idx]
    if graph[u][b]:
        continue
    ...
```

The module docstring claims the new edge "cannot be the ab edge, since that would require p(u) < p(v) < p(c) with uc in E, but then the triple (u, v, c) was already a violation before the insertion." That claim is FALSE. The triple `(a=u, b=v, c)` with `pu < pv < pos(c)` and `uc in E` was NOT a violation before the insertion, because the antecedent `ab not in E` was false: `uv` was an edge before the update (the update is a legal single-entry flip, so the entry was 0 before and is 1 after). After the insertion, `uv` is in E, so `ab not in E` holds for the triple `(u, v, c)`, and the triple now requires a witness `d < pu` with `dv in E` and `dc not in E`. If no such witness exists, the ordering is invalid — exactly the failing case: `(a=0, b=2, c=3)` with 0-3 in E, 0-2 in E (new), and no d < pos(0).

The failing trace: `_certify_insert` with u=0 (pu=0), v=2 (pv=3) loops `range(1, 3)` over b=1 and b=3. For b=3: `graph[0][3]` is 0, so it looks for a witness d in `range(0)` — empty — and returns False... wait, that would trigger a recompute. The actual divergence is that the certification's checked set is the wrong set: the triple that actually breaks the property is `(a=0, b=2, c=3)` where the new edge is the `ab` edge (b=v=2), which the code never checks at all. The code's own checked triples (new edge as `ac`) are a different family and their pass/fail is irrelevant to the real violation. (Note: the code as written would actually return False for b=3 in this case and recompute — so the observed "returned same ordering" means the certification's checked family happened to pass, e.g. because `graph[0][3]` was 1 in the real graph, while the unchecked `ab`-edge family `(0, 2, 3)` was the one that broke.) Either way, the root cause is the same: the `ab`-edge family is never certified.

## REPAIR_HINTS

1. In `_certify_insert`, add the missing case: the new edge as the `ab` edge. With `pu < pv`, for every `c` with `pos(c) > pv` and `uc in E`, the triple `(a=u, b=v, c)` now has `ab not in E` and `ac in E`, so it needs a witness `d < pu` with `dv in E` and `dc not in E`. If none exists, return False (recompute). This is the exact mirror of Case 1 in `_certify_delete` (which already handles the same family correctly for deletions).
2. Keep the existing `ac`-edge check (triples `(u, b, v)` with `pu < pos(b) < pv`, `ub not in E`, witness `d < pu` with `db in E` and `dv not in E`) — it is correct, but note that when `pu = 0` the witness range is empty, so any such triple forces a recompute; that is fine.
3. Do NOT try to "fix" this by only checking triples where the new edge is `ac`; the `ab` family is the one that fails here. Also do not rely on the docstring's argument that the `ab` family was "already a violation before" — it was exempt before precisely because `ab` was in E.
4. The static `_lexbfs` and the delete certification appear consistent with the (LB) property; the minimal fix is the added `ab`-edge loop in `_certify_insert` (a few lines, O(n^2) worst case, same complexity class as the existing checks).
