## FAILURE_DESCRIPTION
Operation: `insert (0, 3)` at sequence index 2 on a 4-vertex graph. The
candidate kept the old ordering `[0, 1, 2, 3]` (returned the state unchanged
because `_certify_insert` returned True), but the verifier reports the
ordering is invalid: violation triple a=1, b=2, c=3 (positions 1 < 2 < 3)
with ac=13 in E, ab=12 not in E, and no witness d < a (minD = sentinel
10^9, i.e. none exists). The only valid ordering the verifier accepts is
`[0, 1, 3, 2]`.

Reconstructed post-insertion graph (consistent with every check below):
edges {01, 02, 03, 13}; non-edges {12, 23}.

## ROOT_CAUSE
`_certify_insert` is unsound: it only checks triples in which the inserted
edge (u,v) plays the role of the `ac` edge (Case 1) or the `ab` edge
(Case 2), and asserts in the module docstring that "The new edge as the
witness edge db can only add witnesses, never remove them, so it cannot
create a violation." That claim is false.

Inserting (u,v) also changes the witness predicate for every triple
(a,b,c) with b = u or b = v: a witness d must satisfy db in E AND dc not
in E. When b = u, the new edge (u,v) makes dc not in E fail for every
c = v, so the insertion can *remove* witnesses d that were valid before
the update. The code never checks this case.

Trace on the failing case, ordering [0,1,2,3], insert (0,3), so u=0 (pu=0),
v=3 (pv=3):
- Case 1: b in {1,2}; graph[0][1]=1 and graph[0][2]=1, both skipped. Pass.
- Case 2: c in {} (pv+1 = n). Pass.
- `_certify_insert` returns True, state kept.

But the triple (a=1, b=2, c=3) is a genuine violation: ac=13 in E, ab=12
not in E, and the only candidate witness d < a is d=0, which fails because
dc = 03 is now in E (the inserted edge). Before the insertion, d=0 was a
valid witness (02 in E, 03 not in E); the insertion of (0,3) destroyed it.
This is exactly the "new edge as dc" case the code never checks.

## REPAIR_HINTS
Add a third case to `_certify_insert` (and re-audit `_certify_delete` for
the symmetric "insertion of the non-edge dc" effect, i.e. deletion of (u,v)
making dc not in E hold for c = v, which can *create* new witnesses —
that direction is safe, but the deletion code's Case 3 only covers the
case where the deleted edge is the witness edge db; verify it also covers
the case where the deleted edge is the dc non-edge, which can only add
witnesses and is therefore safe — so deletion is likely fine, but the
insertion is definitely broken).

Concrete fix in `_certify_insert`, after the existing Case 2 loop:

```python
# Case 3 (dc non-edge): triple (a, b, c) with b == u, c == v,
# pos(a) < pu, av in E, ab not in E.  The inserted edge (u,v) makes
# dc not in E fail for every witness d, so a witness d < a with
# du in E and dv not in E must still exist.
for a_idx in range(pu):
    a = ordering[a_idx]
    if not graph[a][v] or graph[a][u]:
        continue
    found = False
    for d_idx in range(a_idx):
        d = ordering[d_idx]
        if graph[d][u] and not graph[d][v]:
            found = True
            break
    if not found:
        return False
```

Note the witness condition here is `du in E and dv not in E` (b = u, c = v),
which is different from the existing cases' `dv in E and dc not in E`.

Do NOT try to "fix" this by swapping u/v and re-running the existing two
cases: the missing case is structural (the new edge as the dc non-edge),
not a symmetry issue. Also do not rely on the docstring's claim that the
new edge as a witness edge only adds witnesses — the dangerous role is the
new edge as the *dc non-edge*, which removes witnesses.

If a local certification keeps proving fragile, the safe fallback is to
always recompute `_lexbfs` on update (correctness first, per the research
goal); the local check is only an optimization and must be a sound
certificate (i.e. it must check every triple whose witness set or
obligation status changed).
