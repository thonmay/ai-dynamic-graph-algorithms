## FAILURE_DESCRIPTION
Operation: `insert (2, 0)` at sequence index 0 (immediately after `init`).
The candidate returned ordering `[0, 1, 3, 2]`, which the verifier rejected.
The (LB) 4-point property is violated at (a, b, c) = (0, 3, 2) with
pos_a=0, pos_b=2, pos_c=3:
- ac in E: 0-2 is an edge (the edge just inserted),
- ab not in E: 0-3 is not an edge,
- no witness d < a exists (a is at position 0, so the witness set is empty).
Expected result was `[0, 1, 2, 3]` (a valid LexBFS ordering of the same graph).

## ROOT_CAUSE
`_certify_insert` (lines 74-95) is unsound: it only checks triples where the
inserted edge plays the role of `ac` (a=u, c=v, b strictly between them in
position). It never checks triples where the inserted edge plays the role of
`ab`.

Concretely, after inserting (u,v) with pu < pv, a triple (a, b, c) with
a < b < c, ac in E, and ab = (u,v) not in E (i.e. a = u, b = v, and
pos(c) > pv) was exempt before the insertion (ab was in E) but now requires a
witness d < a with db in E and dc not in E. `_certify_insert` has no loop for
this case, so it returns True and `insert_edge` keeps the stale ordering.

Trace on the failing case: the pre-update ordering was `[0, 1, 2, 3]`
(valid for the pre-update graph, where 0-2 was not an edge). Inserting (2,0)
gives u=0, v=2, pu=0, pv=2. The only loop in `_certify_insert` iterates
`idx in range(1, 2)` -> b = ordering[1] = 1; since 0-1 is an edge,
`graph[u][b]` is truthy and it `continue`s. The function returns True, so the
ordering `[0, 1, 2, 3]` is kept. The verifier reports the result as
`[0, 1, 3, 2]` (a different but equally invalid ordering of the same graph);
the violation triple (a=0, b=3, c=2) at positions 0 < 2 < 3 has ac=0-2 in E,
ab=0-3 not in E, and no d < 0. This triple is exactly the "inserted edge as
ab" case (a=u=0, b=v=2, c=3) that `_certify_insert` never examines.

## REPAIR_HINTS
1. In `_certify_insert`, after the existing loop, add the missing case:
   for each c with pos(c) > pv (i.e. `for c_idx in range(pv + 1, n)`),
   if `graph[u][c]` (ac in E), require a witness d with pos(d) < pu such that
   `graph[d][v]` and not `graph[d][c]`. If none exists, return False.
   This mirrors sub-case 3a of `_certify_delete` (which already implements
   exactly this check for the deletion direction).
2. Do NOT "fix" this by making `_certify_insert` always return False (that
   would be correct but defeats the purpose of the local certification and
   the research goal of avoiding full recomputation).
3. The symmetric gap in `_certify_delete` is not a problem: when deleting
   (u,v), the deleted edge can be the `ac` edge of a triple (a=u, b, c=v)
   with pu < pos(b) < pv and ab not in E. Before deletion ac was in E (the
   triple required a witness, which existed); after deletion ac is not in E
   (the triple is exempt). Deletion of an ac edge cannot create a violation,
   so this direction is safe. The current `_certify_delete` cases (1, 2, 3a,
   3b) appear to cover the ways deletion can break the property. The bug is
   isolated to `_certify_insert` missing the "inserted edge as ab" case.
