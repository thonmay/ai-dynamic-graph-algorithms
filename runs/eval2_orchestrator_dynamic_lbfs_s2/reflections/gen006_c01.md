Failing case (sequence_idx 2, operation `insert (0, 3)` on n=4):
- Ordering returned by `insert_edge`: `[0, 1, 2, 3]` (the pre-insertion ordering, kept because `_certify_insert` returned True).
- Expected: `[0, 1, 3, 2]` (a valid LexBFS ordering of the post-insertion graph).
- Verifier violation: (a, b, c) = (1, 2, 3) at positions (1, 2, 3), i.e. a=1, b=2, c=3 with a<b<c, edge (a,c)=(1,3) in E, edge (a,b)=(1,2) not in E, and no witness d < pos(a)=1 with (d,b) in E and (d,c) not in E. The only candidate d is vertex 0, and (0,2) is in E, so 0 fails to witness.

Reconstructed post-insertion graph (consistent with the violation and with the expected ordering being valid):

- Pre-insertion graph: E \ {(0,3)} = {(0,1), (0,2), (1,3)}.
- Pre-insertion ordering [0,1,2,3] is a valid LexBFS of the pre-insertion graph (labels: 0:ε, 1:1, 2:1, 3:10 → 0, then 1, then 2, then 3).

## ROOT_CAUSE

`_certify_insert` (candidates/gen006_c01.py) is unsound: it only checks triples in which the inserted edge (u,v) plays the role of the `ac` edge (Case A) or the `ab` edge (Case B), and it assumes "the new edge as the witness edge db can only ADD witnesses, never remove them, so it cannot create a violation."

That assumption is false. The (LB) property requires, for every triple a<b<c with ac in E and ab not in E, a witness d < a with db in E and dc not in E. Inserting edge (u,v) can *destroy* an existing witness: if u was the witness d for some triple (a, b, c) — i.e. u < a, (u,b) in E, (u,c) not in E — and v = c, then after the insertion (u,c) is in E, so u no longer satisfies "dc not in E". If u was the *only* witness, the triple becomes a violation even though the inserted edge is neither the ac edge nor the ab edge of that triple.

Trace on the failing case, insert (0,3), ordering [0,1,2,3], pu=0, pv=3:
- Case A: b in {1,2} with (0,b) not in E → none (0 is adjacent to both 1 and 2). Passes.
- Case B: c in {} (nothing after position 3). Passes.
- `_certify_insert` returns True, so the old ordering is kept.
- But the pre-insertion triple (a=1, b=2, c=3): (1,3) in E, (1,2) not in E, witness d=0 (0<1, (0,2) in E, (0,3) not in E pre-insertion). After inserting (0,3), (0,3) is in E, so 0 is no longer a witness and no other d exists → violation. The inserted edge (0,3) is the *witness-destroying* edge (u=0 is the witness, v=3 is the c of the triple), a role the certification never checks.

The same flaw exists in `_certify_delete`: its Case 3 only covers triples with pu < pos(a) < pv (i.e. a between u and v). A deletion of (u,v) can also destroy a witness for a triple with a > pv (u before a, v = c, u the witness): after deletion (u,c) is not in E, so u stops witnessing. That case is not checked either.

## REPAIR_HINTS

1. Add the missing "witness destruction" case to `_certify_insert`. After swapping so pu < pv, for every triple (a, b, c) with pu < pos(a) < pos(b) < pos(c) and (a,c) in E and (a,b) not in E, check that some d < pos(a), d != u, satisfies (d,b) in E and (d,c) not in E. If none exists, return False (recompute). This is the exact mirror of the existing Case 3 in `_certify_delete`, generalized to the insertion direction.
2. Add the symmetric missing case to `_certify_delete`: for every triple (a, b, c) with pu < pos(a) < pos(b) < pos(c) and (a,c) in E and (a,b) not in E, check that some d < pos(a), d != u, satisfies (d,b) in E and (d,c) not in E (the graph passed in is post-deletion, so (u,c) is already 0 and u is simply excluded). If none exists, return False.
3. Simplest correct alternative: make both `_certify_insert` and `_certify_delete` run a full O(n^4) check of the (LB) 4-point property over the post-update graph (for all a<b<c with (a,c) in E and (a,b) not in E, verify a witness d<a exists). This is guaranteed sound and only costs the same asymptotic class as the recompute fallback, while still avoiding the O(n^3) `_lexbfs` when the old ordering survives.
4. What will NOT work: keeping the current two-case (insertion) / three-case (deletion) structure and only tightening the existing loops — the missing role of the updated edge as a *witness* (db) is a distinct case that must be added explicitly; no amount of fixing Case A/B/1/2/3 as written covers it. Also note the static `_lexbfs` itself is fine (it produced the correct expected ordering [0,1,3,2] for the post-insertion graph), so do not modify it.
