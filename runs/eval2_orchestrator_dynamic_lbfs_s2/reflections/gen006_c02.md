## FAILURE_DESCRIPTION

Failing case (sequence_idx 0, i.e. the very first update after init):
- n = 4, operation: `insert (2, 0)`.
- The ordering returned (kept from init, because `_certify_insert` returned True) is `[0, 1, 3, 2]`.
- Expected (a valid LexBFS of the post-insertion graph) is `[0, 1, 2, 3]`.
- The verifier reports the (LB) 4-point violation with a=0, b=3, c=2 (pos_a=0, minD=1): in the returned ordering, positions a=0 < b=2 < c=3 hold (vertex 0 at pos 0, vertex 3 at pos 2, vertex 2 at pos 3), edge (0,2) is in E, edge (0,3) is not in E, and no witness d < pos(0) exists (pos_a=0, so the witness set is empty).

Reconstructed post-insertion graph (consistent with the violation and the expected answer):
- E = {(0,1), (0,2), (1,2), (1,3)}.
- Pre-insertion graph: E \ {(0,2)} = {(0,1), (1,2), (1,3)}.
- Pre-insertion LexBFS (the candidate's tie-break: lexicographically larger label set wins, then smaller vertex id): 0 first (only vertex with a nonempty label set {1}); then 1 (label {0}); then 3 (label {1} > {0}); then 2. So init returns `[0, 1, 3, 2]`.
- Post-insertion LexBFS: 0 first; then 1 (label {0}); then 2 (label {0,1} > {1}); then 3. So the valid answer is `[0, 1, 2, 3]`.

## ROOT_CAUSE

The algorithm diverges at the single `insert (2, 0)` call: `_certify_insert` returns True, so `insert_edge` keeps the stale ordering `[0, 1, 3, 2]` instead of recomputing.

The responsible code is `_certify_insert`:

```python
for idx in range(pu + 1, pv):
    b = ordering[idx]
    if graph[u][b]:
        continue
    found = False
    for d_idx in range(pu):
        d = ordering[d_idx]
        if graph[d][b] and not graph[d][v]:
            found = True
            break
    if not found:
        return False
return True
```

with the docstring claim: "The new edge can only break the property as the ac edge of a triple (a=u, b, c=v) with p(u) < p(b) < p(v) and ub not in E."

That claim is false. The new edge (u,v) can also break the property as the **witness edge db** of a triple (a, b, c) with d = u, b = v (or d = v, b = u). Concretely, in the failing case with u=0, v=2 (pu=0, pv=3):

- The new edge (0,2) is the witness edge db of the triple (a=1, b=3, c=2): positions 1 < 2 < 3, ac=(1,2) in E, ab=(1,3) not in E, and the only witness before a=1 is d=0 with 0-3 in E and 0-2 not in E.
- Before the insertion, (0,2) was not in E, so this triple was exempt (ab=(1,3) not in E but ac=(1,2) in E... wait, actually the triple (a=1,b=3,c=2) requires ac=(1,2) in E and ab=(1,3) not in E — both true before the insertion too, so the triple existed before and was witnessed by d=0 via edge (0,3) and non-edge (0,2)). After the insertion, (0,2) becomes an edge, so d=0 no longer satisfies "dc not in E" — the witness is destroyed. No other d < pos(1) exists, so the triple is now violated.

The certification loop only checks triples where the new edge is the **ac** edge (a=u, c=v, b between). It never checks triples where the new edge is the **db** witness edge (d=u, b=v, or d=v, b=u). Hence it returns True on a graph where the ordering is invalid.

Note the asymmetry with `_certify_delete`, which *does* handle the "deleted edge is the witness edge db" case (its Case 1 and Case 2 loops). The insert certification is missing the exact dual of those cases.

## REPAIR_HINTS

The smallest concrete fix is to add the missing witness-removal checks to `_certify_insert`, mirroring the structure of `_certify_delete`'s Case 1 / Case 2:

After the existing ac-edge loop in `_certify_insert` (with u, v swapped so pu < pv), add:

1. **New edge as witness db with d = u, b = v** (u is before v): for each a with pu < pos(a) < pv, and each c with pos(a) < pos(c): if ac in E and av not in E, then the triple (a, b=v, c) needs a witness d' < a with d'v in E and d'c not in E. If no such d' exists, return False. (This is exactly `_certify_delete`'s Case 1 loop, with the roles of "deleted" and "inserted" reversed: here the inserted edge (u,v) *removes* the witness d=u because it makes dc=(u,c) an edge whenever c is adjacent to u... more precisely, the inserted edge (u,v) makes d=u fail the "dc not in E" condition for every c adjacent to u, so any triple that relied on d=u as witness and has c adjacent to u is now broken.)

   Concretely: for a in ordering[pu+1:pv], if graph[a][v] is 0 (av not in E), for c in ordering[pos(a)+1:], if graph[a][c] is 1 (ac in E), check whether there exists d in ordering[:pos(a)] with d != u, graph[d][v] == 1, and graph[d][c] == 0. If not, return False.

2. **New edge as witness db with d = v, b = u** (v is after u, so d=v is after b=u — this case only applies when the witness d is *before* a, i.e. pv < pos(a) < pu, which is impossible since pu < pv after the swap). So with the pu < pv normalization, only case 1 is needed. (If the code did not swap, both cases would be needed, as in `_certify_delete`.)

Alternatively — and more robustly — replace the local certification with a full O(n^3) (or O(n^2)) check of the (LB) 4-point property on the post-update graph. This is simpler, obviously correct, and still avoids the O(n^3) LexBFS recompute (the 4-point check is O(n^3) in the worst case but with a much smaller constant, and can be optimized to O(n^2) with bitsets). Given that the local certification has already produced a correctness bug, the full 4-point check is the safer repair.

Approaches that will NOT work:
- Keeping the current `_certify_insert` and only fixing the ac-edge loop: the bug is the *missing* witness-removal case, not a bug in the ac-edge logic.
- Assuming that edge insertions can only add witnesses and never remove them (the docstring's claim): this is false. Inserting (u,v) makes d=u fail the "dc not in E" condition for every c adjacent to u, thereby *removing* u as a witness for triples (a, b=v, c) where c is adjacent to u.
