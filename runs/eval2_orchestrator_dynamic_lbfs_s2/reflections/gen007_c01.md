## FAILURE_DESCRIPTION
n=3. After some sequence of updates, the state held ordering [0, 2, 1] (pos: 0→0, 2→1, 1→2). The operation `delete (2, 0)` was applied. The candidate returned the unchanged ordering [0, 2, 1], but the correct LexBFS ordering for the resulting graph is [0, 1, 2]. The verifier reports a (LB) 4-point violation at a=0, b=2, c=1 (pos_a=0, minD=1e9, i.e. no witness d < a exists).

Reconstructing the graph: the deleted edge (2,0) was present before the update, and the violation triple (a=0, b=2, c=1) requires 0-1 ∈ E and 0-2 ∉ E after the update. The only graph consistent with all of this is:
- before: edges {0-1, 0-2, 1-2} (triangle) — LexBFS [0,2,1] is valid (no a<b<c with ac∈E, ab∉E).
- after deleting (2,0): edges {0-1, 1-2} (path 0-1-2).
- In [0,2,1]: a=0, b=2, c=1: ac=0-1 ∈ E, ab=0-2 ∉ E, and d < a is impossible (a is first) → violation. Correct LexBFS is [0,1,2].

## ROOT_CAUSE
`_certify_delete` returned True (so `delete_edge` kept the stale ordering) because it only checks triples where the deleted edge plays the role of the **witness edge db** (or dc) with `pu < pos(a) < pv`. It never checks triples where the deleted edge is the **ac edge** with `pos(a) < pu < pos(c)`.

In this case the deleted edge (2,0) is the ac edge of the violating triple: a=0 (pos 0), b=2 (pos 1), c=1 (pos 2), with pu=pos(2)=1, pv=pos(0)=0. After the swap `pu=0, pv=1`, the triple has pos(a)=0 = pu, so `a` is NOT in `range(pu+1, pv)` — every case loop in `_certify_delete` skips it.

The code's own docstring claims this is safe:
```
# Case 1 (ac edge): triple (a=u, b, c=v) with pu < pos(b) < pv,
# av in E and ub not in E.  The ac edge is gone, so the obligation is
# removed; this case can never create a violation.  No check needed.
```
That reasoning is wrong. Deleting the ac edge does not merely "remove an obligation": it **changes the adjacency of the vertex c** (the later endpoint of the deleted edge). For every triple (a, b, c) with `pos(a) < pu < pos(c)` and `ab ∉ E`, the edge `ac` flips from 1 to 0. If `ac` was 1 before, the triple previously needed a witness d < a with `db ∈ E` and `dc ∉ E`; after deletion `dc` becomes 1, so **every such witness is destroyed** (dc ∉ E can no longer hold for any d). The triple then needs a witness with `dc ∉ E` in the new graph, and none of the old witnesses qualify. This is exactly what happened: before deletion, triple (0,2,1) had ac=0-2 ∈ E and witness d=2 (2-1 ∈ E, 2-0 ∉ E); after deletion dc=2-0 ∈ E, so d=2 no longer witnesses, and no d < 0 exists.

The same flaw exists in `_certify_insert`: it only checks triples where the new edge is the ac edge (Case A) or the ab edge (Case B), and asserts "the new edge as the witness edge db can only ADD witnesses, never remove them". That is false: inserting (u,v) also flips `dc` from 0 to 1 for every triple (a, b, c) with `pos(a) < pu < pos(c)` and `ab ∉ E`, destroying witnesses d < a that satisfied `dc ∉ E`. So the insert certification is unsound in the same way (not triggered by this failing case, but the same class of bug).

## REPAIR_HINTS
1. **Immediate fix (correctness first):** make both `insert_edge` and `delete_edge` recompute unconditionally:
   ```python
   def insert_edge(graph, edge, state):
       return {'ordering': _lexbfs(graph), 'n': state['n']}
   def delete_edge(graph, edge, state):
       return {'ordering': _lexbfs(graph), 'n': state['n']}
   ```
   This restores full correctness; the static `_lexbfs` is already correct (the failure is purely in the local certification, not in the recompute path).

2. **If a local certification is still desired (performance goal):** the certification must also handle the "deleted/inserted edge is the ac edge" role, i.e. triples (a, b, c) with `pos(a) < pu < pos(c)` and `ab ∉ E`:
   - For deletion: for each such triple where `ac` was 1 before the update (i.e. `graph[a][c] == 1` in the pre-update graph — note the `graph` passed in is post-update, so `ac` is 0 now; you must check the pre-update value, e.g. via `graph[a][c] or (a == u and c == v) or (a == v and c == u)`), verify a witness d < a with `db ∈ E` and `dc ∉ E` in the **post-update** graph.
   - For insertion: symmetric — for each triple (a, b, c) with `pos(a) < pu < pos(c)`, `ab ∉ E`, and `ac` was 0 before (now 1), verify a witness d < a with `db ∈ E` and `dc ∉ E` in the post-update graph.
   Note the current `_certify_delete` also has a structural smell: its 13 near-identical case loops all test `graph[d][v]` (the adjacency to the later endpoint v) as the witness condition, which is only correct for the specific role assignments they were written for; a cleaner formulation is to enumerate the affected triples by the role of the updated edge (ac / ab / db / dc) and check the witness condition `db ∈ E ∧ dc ∉ E` directly against the post-update graph.

3. **Approaches that will not work:**
   - Keeping the current "Case 1 needs no check" reasoning — it is the direct cause of this failure.
   - Only fixing the delete side — the insert side has the identical unsound "witness edge can only add witnesses" claim and will fail on a symmetric case.
   - Patching individual case loops in `_certify_delete` without adding the missing ac-role check — the missing role is the whole class of unhandled triples, not a bug in an existing loop.
