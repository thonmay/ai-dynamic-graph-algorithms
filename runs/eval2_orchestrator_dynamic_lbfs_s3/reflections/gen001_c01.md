## FAILURE_DESCRIPTION

Operation: `insert (3, 2)` on a 4-vertex undirected graph (sequence_idx 0, i.e. the first update after init).
The candidate returned ordering `[0, 1, 2, 3]`; the verifier reports it is NOT a valid LexBFS ordering.
The (LB) 4-point violation is at positions a=1, b=2, c=3 (vertices va=1, vb=2, vc=3):
- ab not in E: 1-2 is a non-edge,
- ac in E: 1-3 is an edge,
- no d < a (only d=0, vertex 0) satisfies db in E and dc not in E (minD = 1e9 = not found).
The verifier's expected ordering for this graph is `[0, 1, 3, 2]`.

## ROOT_CAUSE

The static partition-refinement LexBFS in `_lexbfs` uses the WRONG refinement direction. In the
HMPV formulation, when a vertex v is selected, each other bucket is split so that the NEIGHBORS of v
come FIRST (the neighbor part is the "smaller" label), then the non-neighbors. The candidate does the
opposite:

```python
# split into non-neighbors (first) and neighbors (second)
non = []
neigh = []
for x in b:
    if adj[v][x]:
        neigh.append(x)
    else:
        non.append(x)
if neigh:
    # replace bucket j with [non, neigh]
    if non:
        buckets[j] = non
        buckets.insert(j + 1, neigh)
```

The docstring even states the wrong rule: "vertices NOT adjacent to v come before those adjacent to v
(the non-neighbor part is the 'smaller' label, so it sorts first)". This is backwards: in LexBFS the
label of a vertex is the sequence of 0/1 bits (1 = adjacent to an already-ordered vertex), and the
lexicographically SMALLER label has a 0 earlier, i.e. the neighbor part (bit 1) is the smaller label and
must be placed first.

Tracing the failing case (graph after inserting 3-2; edges: 0-1, 0-3, 1-3, 2-3):
- Start: bucket [0,1,2,3]. Pick 0. Refine: neighbors of 0 = {1,3}, non-neighbors = {2}.
  Correct (neighbors first): [1,3] then [2] -> buckets [[1,3],[2]].
  Candidate (non-neighbors first): [2] then [1,3] -> buckets [[2],[1,3]].
- Candidate picks 2 next (wrong; correct picks 1). Then 3, then 1 -> order [0,2,3,1]... (the exact
  order depends on the tie-break, but the point is 2 is ordered before 1, which is impossible in any
  valid LexBFS of this graph because 1 is adjacent to 0 and 2 is not).
- The produced order [0,1,2,3] (or similar) violates the 4-point property at (1,2,3) as reported.

The same wrong-direction bug is duplicated in the fallback loop inside `_lexbfs_verified` (the
"try each start vertex" branch), so the fallback also produces invalid orderings.

## REPAIR_HINTS

1. In `_lexbfs` (and the duplicated loop in `_lexbfs_verified`), swap the refinement direction:
   place the NEIGHBOR part of each bucket FIRST, then the non-neighbor part. Concretely, replace the
   split block with:
   ```python
   non = []
   neigh = []
   for x in b:
       if adj[v][x]:
           neigh.append(x)
       else:
           non.append(x)
   if non:
       if neigh:
           buckets[j] = neigh
           buckets.insert(j + 1, non)
           j += 2
       else:
           buckets[j] = non
           j += 1
   else:
       # all neighbors, no split needed
       j += 1
   ```
   (i.e. the "no split needed" case is when `non` is empty, not when `neigh` is empty.)
   Also fix the docstring to say neighbors come first.

2. After fixing the direction, the `_verify_lexbfs` + all-starts fallback in `_lexbfs_verified` is
   unnecessary for correctness (a correct HMPV LexBFS is always valid), but it is harmless to keep as a
   safety net. Note the fallback's inline loop must get the same direction fix.

3. Do NOT try to "fix" this by changing the verifier or by trying all start vertices with the wrong
   direction — the wrong direction produces invalid orderings for every start, so the fallback will
   exhaust all starts and fall through to the "last resort: return the natural order" line, which is
   also invalid. The only correct fix is the refinement direction.

4. The recompute-on-every-update strategy is fine for correctness (it is the stated baseline); the
   dynamic-maintenance optimization is a separate, later concern.
