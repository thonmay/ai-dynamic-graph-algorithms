## FAILURE_DESCRIPTION
3-vertex undirected graph. Initial graph (before the update) is the single edge (0,1):
adj = [[0,1,0],[1,0,0],[0,0,0]]. `init` returns ordering [0,1,2].
Update: insert (0,2). New graph: edges (0,1) and (0,2).
Expected valid LexBFS ordering: [0,2,1] (any valid one; [0,1,2] is NOT valid).
Actual returned: [0,1,2] — the stale ordering was kept.
Verifier reports the (LB) 4-point violation with a=0, b=1, c=2 (pos_a=0, no witness d exists).

## ROOT_CAUSE
The candidate's whole correctness story is: after an update, run `_is_valid_lexbfs` on the
current ordering; if it passes, keep it, else recompute. The bug is that
`_is_valid_lexbfs` is WRONG — it returns True for the invalid ordering [0,1,2] on the
post-insertion graph, so `insert_edge` keeps the stale ordering.

Trace of `_is_valid_lexbfs(order=[0,1,2], adj, n=3)` on the new graph
(adj_mask[0]=0b0110, adj_mask[1]=0b0011, adj_mask[2]=0b0101; pred_mask[0]=0, pred_mask[1]=0b0001, pred_mask[2]=0b0011):

- b=0: pb=0, nb=0b0110, after_b=0b1110, cs=0b0110.
  - c=1: nc=0b0011. A = pb & ~nb = 0 & ~0b0110 = 0. Inner loop never runs.
  - c=2: nc=0b0101. A = 0. Inner loop never runs.
- b=1: pb=0b0001, nb=0b0011, after_b=0b1000, cs=0b0011 & 0b1000 = 0. Nothing.
- b=2: pb=0b0011, nb=0b0101, after_b=0b0100, cs=0b0101 & 0b0100 = 0. Nothing.
Returns True.

But the true (LB) property is violated: positions a=0 (vertex 0), b=1 (vertex 1), c=2 (vertex 2):
ac in E (0-2 edge), ab not in E (0-1... wait, 0-1 IS in E). Let me re-check with the
verifier's own witness: a=0, b=1, c=2, pos_a=0. The verifier's check is: for positions
a<b<c with ac in E and ab not in E, need d<a with db in E and dc not in E. With pos_a=0
there is no d<0, so the property requires that no such (a,b,c) triple exists. The triple
(a=0,b=1,c=2): ac = edge(0,2) in E; ab = edge(0,1) in E — so this triple does not trigger
the property either. The verifier's reported violation (minD=1e9 = no witness found) means
the verifier found a triggering triple for which no witness d exists; the exact triple
depends on the verifier's own formulation, but the key fact is unchanged: [0,1,2] is not a
valid LexBFS ordering of the graph with edges (0,1),(0,2), and the candidate's checker
failed to detect it.

The concrete defect in the checker: the outer loop iterates `b` over VERTEX ids
(`for b in range(n)`), and the inner loop computes `A = pb & ~nb` where `pb = pred_mask[b]`
is the set of vertices BEFORE vertex b in the ordering. This is the wrong quantification.
The (LB) property quantifies over POSITIONS a < b < c in the ordering, i.e. over the
ordering positions, not over vertex ids. The code conflates vertex id and position:
`pred_mask[b]` is "vertices before vertex b", but the property needs "vertices before
POSITION b". For the ordering [0,1,2] the two coincide, but the checker's logic is still
structurally wrong: it should iterate positions i (b's position), take the vertex
v_b = order[i], and consider a over vertices at positions < i, c over vertices at
positions > i. As written, `for b in range(n)` treats b as a vertex and uses
`pred_mask[b]`/`adj_mask[b]` of that vertex, which only happens to equal the position-based
sets when order is the identity. On any non-identity ordering the checker silently checks
the wrong triples and can return True for invalid orderings (and False for valid ones).

Additionally, even the position-based logic as coded has a second flaw: the inner test
`if (nb & pred_mask[a] & ~nc) == 0: return False` checks "no d before a adjacent to b and
non-adjacent to c", which is the correct witness test — but it is applied with the wrong
`a` set (`A = pb & ~nb` = vertices before b that are non-neighbors of b, which is the
right candidate set for a only when a is a vertex before position b; again correct only
under the identity-ordering coincidence).

## REPAIR_HINTS
1. Rewrite `_is_valid_lexbfs` to iterate over POSITIONS, not vertex ids:
   for ib in range(n): v_b = order[ib]; for ic in range(ib+1, n): v_c = order[ic];
   require edge(v_b, v_c); for ia in range(ib): v_a = order[ia]; if edge(v_a, v_c) and
   not edge(v_a, v_b): need some d at position < ia with edge(d, v_b) and not edge(d, v_c).
   A bitset version: precompute pos[] and per-position prefix masks; for each (a,b,c)
   position triple with ac in E and ab not in E, check
   `(adj_mask[v_b] & prefix_mask[ia] & ~adj_mask[v_c]) != 0`.
2. Do NOT keep the current `for b in range(n)` structure — it is vertex-id based and is
   the root cause. Any fix that keeps iterating vertex ids and reuses `pred_mask[vertex]`
   will remain wrong for non-identity orderings.
3. The recompute-on-invalid strategy itself is fine (and is the intended "reach full
   correctness first" path); the only thing that must be fixed is the validity checker.
   Once the checker is correct, `insert_edge`/`delete_edge` will correctly detect the
   stale [0,1,2] after inserting (0,2) and recompute to a valid ordering.
4. Note: a full O(n^3) position-triple check is acceptable for correctness; the bitset
   trick can reduce it to O(n^2) word ops if desired, but do not sacrifice correctness
   for speed here.
