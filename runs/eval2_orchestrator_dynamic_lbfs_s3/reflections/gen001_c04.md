## FAILURE_DESCRIPTION
3-vertex undirected graph. After `init` the state held ordering `[0, 1, 2]` (valid for the pre-update graph). The update is `insert (0, 2)`; the graph passed to `insert_edge` already contains edge (0,2) (matrix has 1 at [0][2] and [2][0]). Expected result: `[0, 2, 1]` (the only valid LexBFS of the resulting path 1-0-2). Actual result: `[0, 1, 2]` — the stale ordering was kept.

The verifier reports the (LB) violation on the returned ordering: a=0, b=1, c=2 (positions 0<1<2), ac=02 in E, ab=01 not in E, and no d<a (none exists, a is first) with db in E and dc not in E.

## ROOT_CAUSE
The candidate's incremental strategy is: after an update, run `_is_valid_lexbfs(graph, ordering)` on the *current* (post-update) graph and keep the old ordering if it passes. That check is sound for **deletions** (removing edges cannot destroy the 4-point property) but **unsound for insertions**: adding an edge can create new (a,c) adjacency pairs that violate the property, and the old ordering may still pass the check on the new graph while not being a LexBFS of it.

Trace on the failing case:
- Post-insert graph: edges {0-2, 1-2} (path 1-0-2).
- `_is_valid_lexbfs` on ordering [0,1,2]:
  - b=1 (pos 1), c=2 (pos 2): 2 not in adj[1]? adj[1]={2}, so 2 IS adjacent to 1 → `continue` (vacuous).
  - b=0 (pos 0): no c with b<c and b not adj c that triggers a check with a before b (a must be before b=0, impossible).
  - No violation found → returns True → `insert_edge` keeps the stale `[0,1,2]`.
- But `[0,1,2]` is NOT a LexBFS of the path 1-0-2: the only valid orderings are [0,2,1] and [2,0,1] (start 0: 0's neighbor 2 must come before non-neighbor 1; start 2: 2's neighbor 1 before non-neighbor 0). The verifier's 4-point check (which correctly uses the *current* graph) finds the violation a=0,b=1,c=2.

So the divergence happens at the `insert_edge` decision point: the "keep if still valid" test is the wrong test for insertions. The responsible lines:

```python
def insert_edge(graph, edge, state):
    ordering = state['ordering']
    if _is_valid_lexbfs(graph, ordering):   # <-- unsound for insertions
        return state
    ordering = _lexbfs(graph)
    return {'ordering': ordering}
```

Note the check is not even a correct *certification* of "ordering is a LexBFS of this graph" in general — it only certifies the (LB) 4-point property, which is necessary but the candidate apparently assumed sufficient for keeping the ordering after an insertion. In this concrete case the 4-point check passed while the ordering was still invalid, so the check itself (as implemented) also fails to catch the violation the verifier catches. Either way, the keep-on-insert branch is the bug.

## REPAIR_HINTS
Smallest concrete fix: in `insert_edge`, do NOT keep the old ordering based on the 4-point check. Either:
1. Always recompute: `ordering = _lexbfs(graph); return {'ordering': ordering}`. This restores correctness immediately (recomputation is allowed; the research goal is to avoid it later, but correctness first).
2. If keeping the old ordering on insert is desired, the keep-condition must be a *sufficient* condition for the old ordering to be a LexBFS of the new graph, e.g. verify the ordering against the actual LexBFS label-refinement process on the new graph (recompute labels and check the ordering is consistent with them), not just the 4-point property.

Also fix `_is_valid_lexbfs` if it is to be used at all: as written it misses the violation the verifier reports on this exact case (it `continue`s when b and c are adjacent, but the violation here has b=1, c=2 which ARE adjacent — the verifier's check evidently uses a different/stronger formulation, e.g. checking all triples a<b<c with ac in E and ab not in E regardless of bc). Re-derive the (LB) property check carefully from Corneil-Krueger: the condition is for all a<b<c with ac in E and ab not in E, exists d<a with db in E and dc not in E — note it does NOT require bc not in E, so the `if c in adj[b]: continue` line is wrong and must be removed.

Approaches that will not work:
- Keeping the "check 4-point property on new graph, keep if passes" logic for insertions — it is unsound (this failure).
- Relying on the current `_is_valid_lexbfs` as a general validity certificate — its `continue` on bc in E makes it too weak.
