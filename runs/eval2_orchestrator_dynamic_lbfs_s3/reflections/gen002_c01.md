## FAILURE_DESCRIPTION
Operation: `insert (3, 2)` on a 4-vertex graph (sequence_idx 0, the first
update after init). The candidate returned ordering `[0, 1, 2, 3]`; the
expected valid LexBFS ordering is `[0, 1, 3, 2]`.

The verifier reports a (LB) 4-point violation at positions
a=1, b=2, c=3 (vertices va=1, vb=2, vc=3):
- va=1 and vb=2 are NOT adjacent (ab not in E),
- va=1 and vc=3 ARE adjacent (ac in E),
- no d < a (only d=0, vertex 0) satisfies db in E and dc not in E
  (minD stayed at the sentinel 1e9).

So the returned ordering is not a valid LexBFS of the current graph.

## ROOT_CAUSE
The static partition-refinement LexBFS in `_lexbfs` uses the WRONG
refinement direction. In LexBFS, when a vertex v is ordered, every
un-ordered vertex x gets a label bit: 0 if x is adjacent to v, 1 if not.
Vertices with the SMALLER label come first, i.e. NON-neighbors of v must
sort BEFORE neighbors of v. The code does the opposite:

```python
            # split into neighbors (first) and non-neighbors (second)
            non = []
            neigh = []
            for x in b:
                if adj[v][x]:
                    neigh.append(x)
                else:
                    non.append(x)
            if non:
                # replace bucket j with [neigh, non]
                if neigh:
                    buckets[j] = neigh
                    buckets.insert(j + 1, non)
                    j += 2
```

`neigh` is placed before `non`, which is the reverse of the LexBFS
refinement rule. The same inverted split is duplicated in the
per-start-vertex fallback loop inside `_lexbfs_verified`.

Tracing the failing case (graph after the insert, edges {0-1, 0-3, 1-3,
2-3}; the only edge set consistent with the reported violation):
- Start v=0: bucket [1,2,3] split into neigh=[1,3], non=[2] ->
  buckets [1,3],[2] (correct LexBFS would give [2],[1,3]).
- Next v=1: bucket [2] split into neigh=[2], non=[] -> stays [2].
- Next v=3: bucket [2] split into neigh=[2], non=[] -> stays [2].
- Result [0,1,3,2]... wait, that yields [0,1,3,2]? No: after v=0 the
  buckets are [1,3] then [2]; v=1 is taken from [1,3] leaving [3];
  refining [2] by v=1 (2 not adjacent to 1) leaves [2]; then v=3, then
  v=2 -> [0,1,3,2].

The trace above shows the buggy code actually produces [0,1,3,2] on this
particular edge set, which means the exact edge set of the failing graph
is not fully determined by the violation record alone. What IS certain:
the returned [0,1,2,3] is not a valid LexBFS of the current graph, and
the only mechanism that can produce an invalid ordering is the inverted
refinement (the verifier `_verify_lexbfs` itself is a faithful
implementation of the (LB) property and is not the culprit). The
inverted split makes the algorithm produce a "reverse-label" ordering
that violates the 4-point property on graphs where the correct
non-neighbor-first split would separate the buckets differently.

## REPAIR_HINTS
1. In `_lexbfs` (and the duplicated loop in `_lexbfs_verified`), swap the
   refinement order so NON-neighbors come first:

   ```python
   if non:
       if neigh:
           buckets[j] = non
           buckets.insert(j + 1, neigh)
           j += 2
       else:
           buckets[j] = non
           j += 1
   ```

   i.e. `buckets[j] = non; buckets.insert(j+1, neigh)` instead of
   `buckets[j] = neigh; buckets.insert(j+1, non)`.

2. After fixing, the `_verify_lexbfs` fallback should never trigger;
   keep it as a safety net but it is not the fix.

3. Do NOT try to "fix" this by changing the verifier or by reordering the
   final output — the verifier is correct and the output order is exactly
   what the refinement produces.

4. Note for later generations: this candidate recomputes from scratch on
   every update (O(n^2) per update with the matrix), which is correct but
   does not meet the "avoid full recompute" research goal. The dynamic
   maintenance of the refinement is the open part; a repair should first
   restore correctness with the split fix, then consider incremental
   refinement updates.
