## FAILURE_DESCRIPTION
n=3. Initial graph is the empty graph; `init` returns ordering `[0, 1, 2]` (valid for the empty graph). Operation `insert (0, 2)` is then applied, so the updated graph has exactly one edge, (0,2). The candidate kept the old ordering `[0, 1, 2]` because its fast validity check `_is_valid_lexbfs` returned `True`, but the verifier reports it invalid: with a=0, b=1, c=2 at positions 0,1,2, ac=(0,2)∈E and ab=(0,1)∉E, and no d<0 exists to witness. The only valid LexBFS orderings of this graph are `[0,2,1]` and `[2,0,1]`; expected `[0, 2, 1]`, actual `[0, 1, 2]`.

## ROOT_CAUSE
The bitset check `_is_valid_lexbfs` is not equivalent to the (LB) 4-point property; it silently skips a whole class of violating triples. The outer loop iterates over `ib` and builds the candidate set for `c` as:

```python
cs = nb & ~prefix_mask[ib + 1]
```

i.e. it only considers `c` that are **adjacent to b**. But the (LB) property must be checked for every triple `ia < ib < ic` with `ac ∈ E` and `ab ∉ E` — there is no requirement that `bc ∈ E`. In the failing case the violating triple is (a=0, b=1, c=2): c=2 is NOT adjacent to b=1, so at ib=1 we have `cs = adj_mask[1] & ~prefix_mask[2] = 0 & ... = 0`, the inner loops never run, and the triple (a=0,b=1,c=2) is never examined. The check therefore only tests triples with `bc ∈ E`, missing exactly the violations where `bc ∉ E`.

Cross-check: the brute-force reference `_is_valid_lexbfs_brute` in the same file correctly returns `False` for this case (ia=0, ib=1, ic=2: adj[0][1]=0, adj[0][2]=1, no d in range(0) → False), confirming the bitset version is a wrong optimization, not a different property.

## REPAIR_HINTS
The smallest fix: make `_is_valid_lexbfs` actually test the (LB) property as stated. Two options:

1. **Simplest and safest:** replace the body of `_is_valid_lexbfs` with the logic of `_is_valid_lexbfs_brute` (the O(n^4) scalar version already present in the file and verified correct on this case). This restores full correctness; the bitset speedup can be re-attempted later.

2. **If keeping bitsets:** restructure so the outer loop is over `ia` (or over the triple directly) and the candidate set for `a` is `prefix_mask[ib] & ~nb` (vertices before b NOT adjacent to b), intersected with `nc` (adjacent to c) — i.e. `A = prefix_mask[ib] & nc & ~nb` — and for each such `a` check the witness `(nb & prefix_mask[pos[a]] & ~nc) != 0`. Do NOT gate `c` on adjacency to `b` (drop the `cs = nb & ...` restriction); `c` should range over all positions after `ib` adjacent to `a`.

Approaches that will NOT work:
- Keeping the current `cs = nb & ~prefix_mask[ib+1]` (c adjacent to b) restriction — it excludes exactly the triples where the violation occurs with `bc ∉ E`.
- Any fix that still iterates `c` from `nb` (neighbors of b) — the property's quantification over `c` is independent of `bc`.

The core invariant to restore: for EVERY `ia < ib < ic` with `ac ∈ E` and `ab ∉ E`, the witness test must run. The current code only runs it for a strict subset (those with `bc ∈ E`).
