## FAILURE_DESCRIPTION
3-vertex graph, operation `insert (0, 2)` at sequence index 0. The candidate returned ordering `[0, 1, 2]`, but the verifier reports an (LB) 4-point violation with a=0, b=1, c=2 (pos_a=0, minD=1e9, i.e. no witness d exists). Expected a valid ordering such as `[0, 2, 1]`.

## ROOT_CAUSE
The static LexBFS routine `_lexbfs_ordering` uses the WRONG refinement rule. Its code says:

```python
nb = [x for x in bk if adj[u][x]]
nnb = [x for x in bk if not adj[u][x]]
if nnb:
    new_buckets.append(nnb)   # non-neighbors FIRST
if nb:
    new_buckets.append(nb)    # neighbors AFTER
```

In standard LexBFS (Habib-McConnell-Paul-Viennot), the NON-neighbor part carries the SMALLER label and is processed (output) FIRST. The candidate does the opposite: it outputs non-neighbors before neighbors, which is the reverse of LexBFS. This produces an ordering that violates the (LB) 4-point property on the post-insertion graph.

Tracing on the failing case: the post-insertion graph has edges (0,1) and (0,2) (a star centered at 0). The candidate's `_lexbfs_ordering` starts with buckets [[0],[1],[2]], picks 0, then refines bucket [1,2]. Since both 1 and 2 are adjacent to 0, nb=[1,2] and nnb=[], so the order is [0,1,2]. However, the verifier's (LB) check flags a=0, b=1, c=2 as a violation because pos_a=0 means there is no d < a to serve as a witness. The candidate's own `_is_valid_lexbfs_direct` check fails to catch this because it requires `not adj[va][vb]` (a non-edge between a and b) to trigger the 4-point test; in this case adj[0][1]=1, so the triple is not triggered and the check passes vacuously. The core defect is the inverted refinement rule in `_lexbfs_ordering`, which produces an ordering that is not a valid LexBFS order.

## REPAIR_HINTS
1. In `_lexbfs_ordering`, swap the order of appending: put `nb` (neighbors) BEFORE `nnb` (non-neighbors) in `new_buckets`, so that neighbors are processed (output) first. This matches the standard LexBFS partition-refinement where the neighbor part carries the smaller label.
2. Do NOT rely on `_is_valid_lexbfs_direct` alone to catch the bug; it may pass vacuously on small graphs where no triggering triple exists. Add a cross-check against a known-correct reference implementation during development.
3. The `_is_valid_lexbfs_lex` and `_lexbfs_signature` functions are unused and based on a false premise (two valid LexBFS orderings do NOT necessarily have the same "signature" as defined); remove them to avoid confusion.
