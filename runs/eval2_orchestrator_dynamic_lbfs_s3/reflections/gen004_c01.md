## FAILURE_DESCRIPTION
Operation `insert (3, 2)` on a 4-vertex graph. The candidate returned ordering `[0, 1, 2, 3]`, but the expected (valid) ordering is `[0, 1, 3, 2]`. The verifier reports an (LB) 4-point violation at positions a=1, b=2, c=3 (vertices 1, 2, 3): edge (1,3) is present, edge (1,2) is absent, and no d < a (i.e. no d in {0}) satisfies "d adjacent to 2 and d not adjacent to 3". So the returned ordering is not a valid LexBFS ordering of the post-insertion graph.

## ROOT_CAUSE
The static `_lexbfs` refinement rule is inverted. In the partition-refinement formulation, when a vertex v is selected, each other bucket is split so that the **neighbors of v come first** (they receive the smaller label bit 0), and non-neighbors come after (bit 1). The code does the opposite:

```python
# split into non-neighbors (first) and neighbors (second)
non = []
neigh = []
for x in b:
    if adj[v][x]:
        neigh.append(x)
    else:
        non.append(x)
if non:
    # replace bucket j with [non, neigh]
    if neigh:
        buckets[j] = non
        buckets.insert(j + 1, neigh)
```

This produces a "reverse-lexicographic" ordering that is not a valid LexBFS. The same inverted logic is duplicated in the fallback loop inside `_lexbfs_verified`.

Why the fallback did not save it: `_lexbfs_verified` tries each vertex as the forced first vertex, but the refinement rule is still inverted in every run, so no permutation of the initial bucket can fix the label ordering. The final "last resort" `return list(range(n))` is also not guaranteed valid.

## REPAIR_HINTS
1. **Fix the refinement order in `_lexbfs`**: swap so that `neigh` is placed before `non` in the bucket list. Concretely, replace the split block with:
   ```python
   if neigh:
       if non:
           buckets[j] = neigh
           buckets.insert(j + 1, non)
           j += 2
       else:
           buckets[j] = neigh
           j += 1
   else:
       # all non-neighbors, no split needed
       j += 1
   ```
2. **Apply the same fix to the duplicated loop in `_lexbfs_verified`** (the fallback that tries each start vertex).
3. **Do not** rely on the `_verify_lexbfs` fallback to mask an incorrect refinement — it cannot compensate for a systematically inverted label rule. Once the refinement is correct, the first `_lexbfs` call should pass verification and the fallback becomes dead code (but keep it as a safety net with the corrected rule).
4. The "last resort" `return list(range(n))` should be removed or replaced with a raise, since returning an arbitrary order that may violate the 4-point property is worse than failing loudly.
