## FAILURE_DESCRIPTION

Failing case: `init` on a 3-vertex undirected graph. The candidate returned
ordering `[0, 1, 2]`; the expected (valid) ordering is `[0, 2, 1]`.

The verifier reports the (LB) 4-point violation at positions
`a=0, b=1, c=2` (vertices `va=0, vb=1, vc=2`): `ac in E` (0-2 is an edge),
`ab not in E` (0-1 is not an edge), and `minD = 1000000000` means NO vertex
`d < a` exists with `db in E and dc not in E` (vacuously impossible since
`a=0` has no earlier vertices).

Reconstructing the graph from the violation: edges are 0-2 and 1-2 (a path
0-2-1); 0-1 is absent. The true LexBFS from start 0 is `[0, 2, 1]`: after
visiting 0, vertex 2 (adjacent to 0) must precede vertex 1 (not adjacent to 0).
The candidate's `[0, 1, 2]` puts the non-neighbor 1 before neighbor 2 — invalid.

## ROOT_CAUSE

The bug is in `_lexbfs` (the static partition-refinement routine), which is
called directly by `init` — so the failure is at `init`, before any dynamic
repair logic runs.

The algorithm's invariant is: `labels[v]` = the set of **already-ordered**
vertices adjacent to `v`. The selection rule "smallest label, tie-break
smallest vertex id" is only correct if labels are compared **lexicographically
as bitsets ordered by position in the ordering** (most significant = earliest
in the ordering). The code instead compares labels as plain integers:

```python
if best_label is None or lab < best_label or (lab == best_label and v < best_v):
```

and refines with raw vertex-id bits:

```python
if nb & low:
    labels[v] |= low
```

For the failing graph (edges 0-2, 1-2), trace:
- order=[0]; labels[1]=0, labels[2]=0.
- Both unvisited labels are 0 → tie → smallest id wins → **1 is picked**.
- Refine: 1's neighbor 2 gets `labels[2] |= (1<<1)` → labels[2]=2.
- order=[0,1,2].

But the correct LexBFS tie-break is by **position in the ordering**, not by
vertex id. Here both labels are empty, so the tie-break is arbitrary — picking
1 (a non-neighbor of 0) before 2 (a neighbor of 0) is not a valid LexBFS
choice: in any valid LexBFS, a vertex adjacent to an earlier vertex must come
before a vertex not adjacent to it (that is exactly the (LB) property with
`a=0`). The integer comparison `lab < best_label` also misorders non-empty
labels in general: e.g. label {position 3} (bit 3, value 8) compares as
"smaller" than label {positions 0,1} (bits 0,1, value 3), even though
lexicographically {0,1} < {3}.

So the root cause: **labels are keyed by vertex id and compared as integers,
but LexBFS requires labels keyed by ordering position and compared
lexicographically (earliest position = most significant).**

## REPAIR_HINTS

Fix `_lexbfs` so labels are maintained in **ordering-position space** and
compared lexicographically:

1. Keep a `pos[v]` map (position of each vertex in `order` once placed).
2. When a vertex `x` is placed at position `p`, refine: for each unvisited
   neighbor `v` of `x`, set `labels[v] |= (1 << p)` — i.e. OR in the bit at
   the *position* of `x`, not the bit at vertex id `x`.
3. Compare labels lexicographically with position 0 as the most significant
   bit. Since labels only ever contain bits at positions `< current length of
   order`, and all labels have the same bit-length (positions 0..k-1), the
   lexicographic order "earlier position = more significant" is exactly the
   **integer** order of the position-keyed bitmasks. So after change (2), the
   existing `lab < best_label` integer comparison becomes correct.
4. Tie-break: when labels are equal, any unvisited vertex may be chosen
   (LexBFS allows arbitrary tie-breaking), so keep `v < best_v` or use
   smallest position-agnostic id — either is fine.

Concretely, the minimal edit in `_lexbfs`:
- Add `pos = {}`; set `pos[start] = 0` after `order.append(start)`.
- In the main loop, after `order.append(best_v)`, set `pos[best_v] = len(order) - 1`.
- Replace the refine step `labels[v] |= low` with `labels[v] |= (1 << pos[best_v])`
  (i.e. OR in the single bit for `best_v`'s position, for each unvisited
  neighbor `v`).
- `labels[start]` should be `1 << 0` (position 0), which it already is
  coincidentally (start=0), but should be written as `1 << pos[start]` for
  clarity.

Approaches that will NOT work:
- Keeping vertex-id bits and only changing the tie-break: the integer
  comparison of id-keyed labels is still wrong for non-empty labels
  (e.g. {id 3} vs {ids 0,1}).
- Sorting labels as Python sets of ids: same id-vs-position confusion.
- Relying on `_try_repair` to fix `init`'s output: `init` never calls
  `_try_repair`, and the repair candidates (swap/move endpoints of one edge)
  are not guaranteed to reach a valid ordering anyway.

Note: `_is_lexbfs` (the certificate checker) is correct as written and can be
used to validate the repaired `_lexbfs` on the failing case: it must accept
`[0, 2, 1]` and reject `[0, 1, 2]` for the path 0-2-1.
