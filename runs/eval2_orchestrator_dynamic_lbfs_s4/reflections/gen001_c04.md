## FAILURE_DESCRIPTION

Failing case: `insert_edge` of edge (0, 2) on a 3-vertex undirected graph.
The candidate returned the unchanged ordering `[0, 1, 2]`; the expected
(valid) ordering is `[0, 2, 1]`.

The verifier reports the (LB) 4-point violation at positions
`a=0, b=1, c=2` (vertices `va=0, vb=1, vc=2`): `ac in E` (0-2 is an edge),
`ab not in E` (0-1 is not an edge), and `minD = 1000000000` means NO vertex
`d < a` exists with `db in E and dc not in E` (vacuously impossible since
`a=0` has no earlier vertices).

Reconstructing the graph from the violation: after the insert, edges are
0-2 and 1-2 (a path 0-2-1); 0-1 is absent. The true LexBFS from start 0 is
`[0, 2, 1]`: after visiting 0, vertex 2 (adjacent to 0) must precede vertex
1 (not adjacent to 0). The candidate's `[0, 1, 2]` puts the non-neighbor 1
before neighbor 2 — invalid.

## ROOT_CAUSE

The bug is in `_insert_ok`, which is called by `insert_edge` and incorrectly
returns `True`, so `insert_edge` keeps the stale ordering instead of
recomputing.

The check is:

```python
for w in range(n):
    if w == u or w == v:
        continue
    if pos[w] < pos[u] and not graph[u][w] and graph[v][w]:
        return False
return True
```

It only inspects vertices `w` with `pos[w] < pos[u]` (strictly before the
earlier endpoint `u`). In the failing case, `u=0` is at position 0, so the
loop body never executes and the function returns `True` unconditionally.
The ordering is kept, but it is invalid.

The check is missing the `a = u` case of the (LB) property. After adding
edge (u, v) with `u` earlier than `v`, the new edge itself can create a
violation with `a = u`, `c = v`, and any `b` with `pos[u] < pos[b] < pos[v]`
such that `u-b` is not an edge. The (LB) property then requires a witness
`d < u` with `d~b` and not `d~v`. The current code never checks this.

Concretely for the failing case: `u=0`, `v=2`, `b=1`. `pos[0] < pos[1] <
pos[2]`, `0-1` is not an edge, and there is no `d < 0`. So the new edge
(0,2) creates a violation at `(a,b,c) = (0,1,2)`, but `_insert_ok` returns
`True` because it only looks at `w` before `u=0` (none exist).

The docstring of `_insert_ok` also misstates the condition: it claims the
ordering stays valid iff `N(u) \ {v} ⊆ N(v) \ {u}`, which is not the correct
criterion for the (LB) property. The correct criterion must also consider
the `a = u` case described above.

## REPAIR_HINTS

Fix `_insert_ok` to also check the `a = u` case. After adding edge (u, v)
with `u` earlier than `v`, the ordering stays valid iff for every `b` with
`pos[u] < pos[b] < pos[v]` and `not graph[u][b]`, there exists a witness
`d` with `pos[d] < pos[u]`, `graph[d][b]`, and `not graph[d][v]`.

Concretely, add this loop to `_insert_ok` (after the existing loop, or
replacing it if the existing loop is also incorrect):

```python
for b in range(n):
    if b == u or b == v:
        continue
    if pos[u] < pos[b] < pos[v] and not graph[u][b]:
        # need witness d < u with d~b and not d~v
        found = False
        for d in range(n):
            if d == u or d == v or d == b:
                continue
            if pos[d] < pos[u] and graph[d][b] and not graph[d][v]:
                found = True
                break
        if not found:
            return False
return True
```

This is O(n^2) in the worst case, but correct. For the failing case, `b=1`
has `pos[0] < pos[1] < pos[2]` and `not graph[0][1]`, and no `d < 0` exists,
so the function returns `False` and `insert_edge` recomputes, yielding the
valid ordering `[0, 2, 1]`.

Approaches that will NOT work:
- Keeping the current `_insert_ok` and only fixing the tie-break in
  `_lexbfs`: the incremental check is still wrong and will keep invalid
  orderings after inserts.
- Checking only `w` with `pos[w] < pos[u]` (the current code): misses the
  `a = u` case entirely.
- Checking only `w` with `pos[w] > pos[v]`: misses the `a = u` case and
  other potential violations.

Note: `_delete_ok` may also be incorrect, but the failing case is an insert,
so the immediate fix is in `_insert_ok`. After fixing `_insert_ok`, re-run
the test suite to check if `_delete_ok` also needs repair.
