## FAILURE_DESCRIPTION
Operation: `init` on a 3-vertex undirected graph (sequence_idx 0, so no prior updates).
- Expected ordering: `[0, 1, 2]`
- Actual ordering: `[0, 2, 1]`
- Reported (LB) violation: a=0, b=2, c=1 (positions pos_a=0, pos_b=2, pos_c=1), minD = 1e9 (no witness found).

The verifier's violation record is internally inconsistent: it lists b=2 and c=1 with pos_b=2 > pos_c=1, but the (LB) 4-point property only quantifies over positions a < b < c. So the recorded tuple cannot itself be a genuine (a<b<c) violation of the property as stated. The concrete, verifiable fact is: the static `_lexbfs` produced `[0, 2, 1]` where the expected valid ordering is `[0, 1, 2]`.

## ROOT_CAUSE
The failure is in `init` -> `_recompute` -> `_lexbfs`, i.e. the static partition-refinement routine, not in any dynamic update logic (no update has happened at sequence_idx 0).

The bug is in the bucket-refinement step of `_lexbfs`:

```python
        new_buckets = []
        for C in buckets:
            if not C:
                continue
            Cn = set()
            Cy = set()
            for w in C:
                if graph[v][w]:
                    Cy.add(w)
                else:
                    Cn.add(w)
            if Cn:
                new_buckets.append(Cn)
            if Cy:
                new_buckets.append(Cy)
        buckets = new_buckets
```

The non-neighbor part `Cn` is appended BEFORE the neighbor part `Cy`. In LexBFS, when a bucket is split by adjacency to the just-selected vertex v, the sub-bucket of vertices ADJACENT to v must come FIRST (they are lexicographically smaller: their label has a 1 in the new coordinate), and the non-adjacent sub-bucket comes second. This code has the order reversed, so the algorithm is effectively running a "reverse-lexicographic" refinement and can emit orderings that are not valid LexBFS orderings (e.g. `[0, 2, 1]` where `[0, 1, 2]` is the valid one).

Note the selection rule `v = min(B)` (smallest vertex in the first non-empty bucket) is a legal tie-break and is not the problem; the problem is purely the Cn/Cy ordering inside the refinement.

## REPAIR_HINTS
Smallest concrete fix, in `_lexbfs`: swap the two appends so the neighbor sub-bucket precedes the non-neighbor sub-bucket:

```python
            if Cy:
                new_buckets.append(Cy)
            if Cn:
                new_buckets.append(Cn)
```

After this change, re-run the failing init case and confirm the output is a valid LexBFS ordering (the verifier's (LB) check should pass).

Approaches that will NOT work:
- Do not "fix" this by adding a post-hoc `_is_lexbfs` validation + `_try_repair`/recompute loop inside `init`. The repair candidates in `_try_repair` are a fixed set of single-vertex moves and are not guaranteed to find a valid ordering; relying on them masks the real bug and can still fail on larger graphs.
- Do not change the `min(B)` tie-break; it is a valid LexBFS tie-break and is not the cause of this failure.
- The dynamic checks `_insert_ok` / `_delete_ok` are not implicated by this failing case (it is an init failure), so do not spend effort on them for this bug; however, note that `insert_edge`/`delete_edge` already call `_is_lexbfs` as a safety net, which will catch any residual invalidity from a fixed `_lexbfs` — keep that.
