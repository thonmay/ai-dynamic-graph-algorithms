## FAILURE_DESCRIPTION

Operation: `init` on a 3-vertex undirected graph (sequence_idx 0, no prior updates).
`init` returned ordering `[0, 2, 1]`; the verifier reports it invalid and expects
`[0, 1, 2]`.

Reported (LB) violation: positions a=0, b=2, c=1, i.e. vertices va=0, vb=1, vc=2 in
the returned ordering, with:
- ac in E: adj[0][2] = 1
- ab not in E: adj[0][1] = 0
- no witness d < a (a is position 0, so the d-range is empty; `minD: 1000000000`
  is the "no witness" sentinel)

Reconstructing the graph: the violation requires adj[0][2]=1 and adj[0][1]=0. For
`[0,1,2]` to be valid, the only remaining edge is adj[1][2]=1 (if it were 0, then in
[0,1,2] the triple a=0,b=1,c=2 would violate (ac in E, ab not in E, no d<a)). So the
graph is the path 0-2-1: edges {0-2, 1-2}, non-edge {0-1}.

Tracing `_lexbfs` on this graph:
- start = 0, order = [0].
- Seed: neighbors of 0 are {2}, so labels[2] = 1 (bit 0), labels[1] = 0.
- Selection over unvisited {1, 2}: integer labels are labels[1]=0, labels[2]=1.
  The code picks the smallest integer label → vertex 1.
- order = [0, 1], then vertex 2 → order = [0, 1, 2].

Wait — that trace gives [0,1,2], which is valid. So the integer-comparison
hypothesis alone does not reproduce the failure on this graph. Re-examining: the
returned result was [0,2,1], meaning the code picked vertex 2 (label 1) BEFORE
vertex 1 (label 0). That is the OPPOSITE of `lab < best_label` on integers.

Re-reading the selection loop:
```python
if best_label is None or lab < best_label or (lab == best_label and v < best_v):
```
Iterating unvisited bits low-to-high: v=1 first (lab=0) sets best=(0,1); then v=2
(lab=1): `1 < 0` is False, `1 == 0` False → not replaced. Result: vertex 1. So the
code as written should return [0,1,2] on this graph, contradicting the observed
[0,2,1].

Therefore the trace is INCONCLUSIVE from the report alone: either (a) the actual
graph differs from my reconstruction (e.g. adj[1][2]=0 and the "expected" [0,1,2]
is valid for a different reason, or the graph has a self-loop/extra structure), or
(b) the candidate file I read differs from the one that was executed. I cannot
reproduce [0,2,1] from `_lexbfs` on the reconstructed path graph.

What IS certain: `init` returned an ordering that fails the (LB) certificate, so the
static `_lexbfs` (the only code path in `init`) produced an invalid ordering. The
repair path is never involved.

## ROOT_CAUSE

The static `_lexbfs` returned an invalid ordering. The most suspicious defect,
independently of the exact failing graph, is the label-comparison encoding:

The comment claims "Lexicographic comparison with position 0 as the most significant
bit is exactly integer comparison of these masks." This is FALSE for the encoding
used: bit p is set for ordering position p, so bit 0 (position 0) is the LEAST
significant bit. Integer comparison therefore prioritizes differences at LATE
positions over EARLY ones, i.e. it implements lexicographic order read from position
n-1 down to 0 — the reverse of the LexBFS rule (which compares from position 0
upward).

Responsible lines:
```python
if best_label is None or lab < best_label or (lab == best_label and v < best_v):
```
together with the encoding `bit = 1 << (len(order) - 1)` (position = bit index) and
the seed `labels[v] |= 1` (position 0 = bit 0).

Caveat: on the specific reconstructed 3-vertex path, this reversed comparison
happens to give the same answer as the correct one (the two labels differ only in
bit 0, and the reversed rule picks the vertex with bit 0 = 0, which is also the
lexicographically-smallest-from-position-0 choice). So the reversed comparison is a
real latent bug but may not be the trigger for THIS case. The exact trigger for this
case could not be pinned down from the report; hypotheses ruled out: (1) the repair
path (never called in init); (2) the `_is_lexbfs` checker (it correctly implements
the (LB) property as stated).

## REPAIR_HINTS

1. Fix the label comparison so it implements lexicographic order from position 0
   upward. Two equivalent options:
   a. Flip the bit assignment so position 0 is the MOST significant bit: seed the
      start's neighbors with `1 << (n-1)` and refine with `bit = 1 << (n - len(order))`
      (position p gets bit n-1-p). Then plain integer `lab < best_label` is correct.
   b. Keep the encoding (position p = bit p) and replace the integer comparison with
      a per-bit scan from bit 0 upward (0 < 1 at each position). O(n) per comparison,
      still O(n^2) overall.

2. After fixing, verify `_lexbfs` against `_is_lexbfs` on the failing 3-vertex case
   AND on random small graphs (n up to ~8, all edge subsets) — the reversed-comparison
   bug only manifests when labels differ at multiple positions, which needs n >= 4
   or a specific 3-vertex configuration, so the single failing case may not catch it.

3. Do NOT rely on `_try_repair` to mask the bug: `init` never calls it, and its
   candidate set (swap / move-to-ends) is not complete anyway.

4. If the repaired `_lexbfs` still fails the reported case, the discrepancy suggests
   the executed candidate differed from the file read here; in that case re-run the
   failing case against the current file before further changes.
