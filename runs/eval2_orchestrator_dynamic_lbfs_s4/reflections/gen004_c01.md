## FAILURE_DESCRIPTION
Operation: `init` on a 3-vertex undirected graph (sequence_idx 0, so no prior updates).
The candidate returned ordering `[0, 1, 2]`; the expected (valid) ordering is `[0, 2, 1]`.
The verifier reports an (LB) 4-point violation at positions a=0, b=1, c=2 (vertices 0, 1, 2):
`ac in E` (edge 0-2 present), `ab not in E` (edge 0-1 absent), and no `d < a` exists
(a is position 0, so the witness set is empty; reported as `minD = 1000000000`, i.e. "no witness found").
So the graph must be the path 1-0-2 (edges {0-2, 0-1? no} — precisely: 0-2 in E, 0-1 not in E, and 1-2 in E so that 1's label is nonempty). The only valid LexBFS orderings from start 0 are `[0, 2, 1]` (and its mirror `[0, 1, 2]` is NOT valid, as the violation shows).

## ROOT_CAUSE
The bug is in `_lexbfs` (the static partition-refinement routine), in the label-comparison direction. Labels are position-keyed bitmasks where position 0 is the MOST significant bit (bit `1 << (len(order)-1)` is OR'd in when a vertex is placed at that position). LexBFS must pick the lexicographically LARGEST label (the vertex adjacent to the earliest-possible positions). But the code picks the SMALLEST integer:

```python
if best_label is None or lab < best_label or (lab == best_label and v < best_v):
```

The comment even states the wrong conclusion ("'smallest label' ... is the SMALLEST integer").

Trace on the failing graph (edges 0-2, 1-2; start=0):
- order=[0]; labels=[0,0,0]; unvisited={1,2}.
- Both labels are 0, tie broken by smallest id -> picks 1. order=[0,1].
- Refine: 1's neighbors = {2}; bit for position 1 = 2; labels[2] |= 2 -> labels[2]=2.
- Next: labels[1]=0, labels[2]=2. The code picks the smallest integer -> picks 1's successor 2? No: it picks the vertex with the smallest label, which is... labels[1] is irrelevant (1 already visited); among unvisited {2}, only 2 remains -> order=[0,1,2].

Wait — the real divergence is at the FIRST selection: after placing 0, both 1 and 2 have label 0 (neither is adjacent to 0? No: 2 IS adjacent to 0). Let me re-trace with edges {0-2, 1-2}:
- masks: masks[0]={2}, masks[1]={2}, masks[2]={0,1}.
- order=[0]; refine: neighbors of 0 = {2}; bit for position 0 = 1; labels[2] |= 1 -> labels[2]=1.
- Unvisited {1,2}: labels[1]=0, labels[2]=1. LexBFS must pick the LARGEST label -> 2 (correct, giving [0,2,1]). The code picks the SMALLEST -> 1 (wrong, giving [0,1,2]).

So the first selection already diverges: `lab < best_label` selects vertex 1 (label 0) over vertex 2 (label 1), producing the invalid ordering `[0, 1, 2]`.

Note: `_is_lexbfs` is only used by `_try_repair` (updates), never by `init`, so the wrong ordering is returned unchecked.

## REPAIR_HINTS
1. In `_lexbfs`, flip the comparison to select the lexicographically LARGEST label: change
   `if best_label is None or lab < best_label or (lab == best_label and v < best_v):`
   to
   `if best_label is None or lab > best_label or (lab == best_label and v < best_v):`
   (the tie-break by smallest id is fine and arbitrary). Also fix the misleading comments that claim "smallest label ... is the SMALLEST integer".
2. Defense in depth: have `init` (and the update fallbacks) verify the produced ordering with `_is_lexbfs` and, if it fails, recompute with a corrected routine. This would have caught the bug at init time.
3. Do NOT "fix" this by changing the bit assignment (e.g., making position 0 the least significant bit) while keeping `lab < best_label` — that would make integer comparison the reverse of lexicographic order for multi-bit labels and is wrong in general. The clean fix is the comparison direction in step 1.
4. The `_try_repair` local-repair heuristic is sound in principle (it validates every candidate with `_is_lexbfs` before accepting), so once `_lexbfs` is correct the fallback path is safe; no change needed there for this failure.
