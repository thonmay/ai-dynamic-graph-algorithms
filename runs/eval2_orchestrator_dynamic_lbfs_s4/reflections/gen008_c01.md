## FAILURE_DESCRIPTION

4-vertex undirected graph, `sequence_idx = 2`, operation `insert (0, 3)`.
The candidate returned the pre-update ordering `[0, 1, 2, 3]` unchanged; the
verifier reports it is NOT a valid LexBFS ordering of the post-insert graph and
gives a valid alternative `[0, 1, 3, 2]`.

Reported (LB) violation: positions `a=1, b=2, c=3` (vertices `va=1, vb=2, vc=3`),
`minD = 1000000000` (no witness found). So in the post-insert graph:
- `ac in E`: edge (1,3) present;
- `ab not in E`: edge (1,2) absent;
- no `d` at position `< 1` (i.e. no `d = 0`) with `db in E` and `dc not in E`.

Reconstructing the post-insert graph from these constraints:
- (0,3) in E (the inserted edge), (1,3) in E, (1,2) not in E.
- For `[0,1,3,2]` to be valid, (0,1) must be in E (otherwise the triple
  a=0,b=1,c=3 would violate: ac=(0,3) in E, ab=(0,1) not in E, no d<0).
- (0,2) must be in E: in `[0,1,3,2]` the triple a=0,b=1,c=2 has ac=(0,2) in E,
  ab=(0,1) in E — no constraint; but in the returned `[0,1,2,3]` the triple
  a=0,b=1,c=2 would need ac=(0,2) in E and ab=(0,1) not in E to be a violation,
  and ab IS in E, so no constraint either way. The minimal consistent graph is
  edges {(0,1), (0,2), (0,3), (1,3)} (a 4-cycle 1-0-2 plus the chord 0-3...
  precisely: 0 adjacent to 1,2,3; 1 adjacent to 0,3; 2 adjacent to 0; 3
  adjacent to 0,1).

So the bug is a FALSE NEGATIVE in the fast verifier `_is_valid_lexbfs`: it
certified the invalid ordering `[0,1,2,3]` as valid, so `insert_edge` kept the
stale ordering and never recomputed.

## ROOT_CAUSE

The verifier's witness set is wrong. In `_is_valid_lexbfs`:

```python
    # P[a] = bitmask of all vertices adjacent to at least one vertex
    # at position < a.
    P = [0] * n
    running = 0
    for a in range(n):
        P[a] = running
        running |= adj_mask[ordering[a]]
    ...
            # S = {d < a : dc not in E}
            S = P[a] & ~adj_vc
```

`P[a]` is the **union of the adjacency masks** of the vertices at positions
`< a` — i.e. the set of vertices that are adjacent to *at least one* earlier
vertex. But the (LB) property requires the witness `d` to be a vertex at
position `< a` (a vertex, not a neighbor of one). The correct prefix set is the
**position mask** `Q[a] = { ordering[0], ..., ordering[a-1] }`, and the witness
set is `S = Q[a] & ~adj_vc`.

The two sets coincide only when the graph is complete (every vertex is adjacent
to every earlier vertex). On the failing case, with ordering `[0,1,2,3]` and
post-insert adj masks `adj[0]={1,2,3}`, `adj[1]={0,3}`, `adj[2]={0}`,
`adj[3]={0,1}`:

- `P[1] = adj[0] = {1,2,3}` (bitmask 0b1110).
- Correct `Q[1] = {0}` (bitmask 0b0001).

For the violating triple (a=1, b=2, c=3): `vc=3`, `adj_vc={0,1}`.
- Buggy: `S = P[1] & ~adj_vc = {1,2,3} & {2,3} = {2,3}`. Then
  `adj[vb=2] & S = {0} & {2,3} = 0` — this particular b is caught, but the
  buggy S also *falsely passes* other triples: e.g. any b whose neighbor set
  happens to contain 2 or 3 gets a witness that is not at position `< a`.
- Correct: `S = Q[1] & ~adj_vc = {0} & {2,3} = 0`, so the `S == 0` branch
  fires: `va=1` must be adjacent to every vertex at positions 2..2, i.e. to
  `vb=2`. `adj[1] & {2} = 0` → `return False`. The verifier rejects the
  ordering and `insert_edge` recomputes.

The concrete divergence: at the triple (a=1, b=2, c=3) the buggy verifier
computes a non-empty witness set `S={2,3}` containing vertices that are NOT at
position `< a`, so the existential clause "exists d < a with db in E and dc not
in E" is evaluated over the wrong universe. (In this exact triple the buggy
code happens to still return False via `adj[vb] & S == 0`; the false negative
arises from the same wrong S on the other triples the verifier scans — e.g.
triples where `adj[vb]` contains 2 or 3 — which the buggy code accepts while
the correct S would be empty and the `S == 0` branch would reject. The
verifier's overall verdict on `[0,1,2,3]` is `True`, which is why the stale
ordering was kept.)

Note the `S == 0` branch itself is correct in this candidate (it returns False
when `va` is non-adjacent to some middle `vb`), so the only defect is the
definition of `P`/`S`.

## REPAIR_HINTS

1. In `_is_valid_lexbfs`, replace the prefix-adjacency mask with a prefix
   **position** mask. Concretely, change:

   ```python
   P = [0] * n
   running = 0
   for a in range(n):
       P[a] = running
       running |= adj_mask[ordering[a]]
   ```

   to:

   ```python
   P = [0] * n
   running = 0
   for a in range(n):
       P[a] = running
       running |= (1 << ordering[a])
   ```

   (bit `ordering[a]` = the vertex id at position `a`). The rest of the
   function — `S = P[a] & ~adj_vc`, the `S == 0` branch, and the
   `(adj_mask[vb] & S) == 0` test — is then correct as written, because
   `P[a]` now enumerates exactly the vertices at positions `< a`.

2. Keep the `~adj_vc` as is: Python's infinite sign extension is harmless here
   because `P[a]` only has bits in the n-bit range, so `P[a] & ~adj_vc` is
   well-defined. (Optionally mask with `(1 << n) - 1` for clarity.)

3. Do NOT try to "fix" this by special-casing the failing triple or by
   intersecting `P[a]` with `adj_mask[va]` or similar — the witness `d` is
   required to be at position `< a`, full stop; the position mask is the only
   correct universe.

4. After the fix, sanity-check the verifier against the static `_lexbfs` on
   random small graphs (n up to ~8, all edge subsets): `_is_valid_lexbfs` must
   accept every ordering `_lexbfs` produces and reject at least one
   permutation of each non-complete graph. Also re-run this failing case
   (insert (0,3) on the 4-vertex graph) end-to-end: the verifier must now
   return False for `[0,1,2,3]`, forcing the `_lexbfs` recompute that yields a
   valid ordering such as `[0,1,3,2]`.

5. The static `_lexbfs` (bucket refinement with neighbor sub-bucket first,
   `min(B)` tie-break) is correct and was already fixed in an earlier
   generation; do not touch it. The recompute fallback is therefore safe once
   the verifier is fixed.
