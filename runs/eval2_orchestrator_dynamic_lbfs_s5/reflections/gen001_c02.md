## FAILURE_DESCRIPTION
Case: n=3. After `init` on the triangle (edges (0,1),(1,2),(0,2)) the state holds a valid ordering (e.g. [0,1,2]). Then `delete_edge(graph, (0,2), state)` is called on the graph with edge (0,2) already removed, i.e. the remaining graph is the path 0-1-2 (adj[0][1]=adj[1][0]=1, adj[1][2]=adj[2][1]=1, adj[0][2]=0).

Expected: any valid LexBFS ordering of the path, e.g. [0,1,2] (or [2,1,0]).
Actual returned: [0,2,1].

The verifier reports the (LB) violation with a=0, b=2, c=1 (vertex ids), pos_a=0, minD=1000000000 (sentinel = no certifier found). In ordering [0,2,1]: pos(0)=0, pos(2)=1, pos(1)=2. So a=0 (pos 0), b=2 (pos 1), c=1 (pos 2): ac = (0,1) in E, ab = (0,2) not in E, and there is no d before position 0, so the 4-point property is violated.

## ROOT_CAUSE
The bug is in `_try_local_repair` (and its caller): it is invoked on the OLD ordering BEFORE the update is applied, and it validates candidates against the NEW adjacency matrix.

In `delete_edge`:
```python
ordering = state['ordering']          # ordering of the OLD graph (triangle)
repaired = _try_local_repair(ordering, graph, n, edge)   # graph is already the NEW graph
if repaired is not None:
    return {'ordering': repaired, 'n': n}
```
`_try_local_repair` builds candidates by moving/swapping u and v in the old ordering and accepts the first candidate for which `_check_lb_property(cand, adj, n)` holds on the NEW graph. It does NOT require the candidate to be a genuine LexBFS ordering of the new graph — the (LB) 4-point property is a necessary but not sufficient condition for a LexBFS ordering (it characterizes chordal graphs, not LexBFS orderings of arbitrary graphs).

Trace on the failing case: old ordering [0,1,2], new graph = path 0-1-2. Candidate "move v=2 to position 0" gives [2,0,1]. `_check_lb_property([2,0,1], path)` returns True (the only non-edge pair is (2,0); for a=2,b=0 there is no c>b with ac in E, so vacuously satisfied). So `_try_local_repair` returns [2,0,1]... but the reported result is [0,2,1]. Either way the mechanism is the same: a candidate that satisfies the (LB) property on the new graph but is not a valid LexBFS ordering of it is accepted, and the fallback recompute is never reached. (For [0,2,1] the check fails, so the exact accepted candidate depends on candidate ordering, but the class of bug is identical: the (LB) check is used as a proxy for "valid LexBFS ordering", which is unsound.)

The deeper issue: the (LB) 4-point property is NOT a certificate that an ordering is a LexBFS ordering of the given graph. It is a certificate that the graph is chordal (when the ordering is a LexBFS ordering). Checking it on an arbitrary ordering of a non-chordal graph can pass for orderings that no LexBFS run would ever produce.

## REPAIR_HINTS
1. Smallest correct fix: in `insert_edge`/`delete_edge`, do NOT trust `_try_local_repair`'s acceptance criterion. Either (a) remove the local-repair path entirely and always recompute with `_lexbfs_ordering(graph, n)` (correct, but gives up the "avoid full recompute" goal), or (b) keep local repair but validate each candidate by actually running the static LexBFS partition-refinement and checking that the candidate equals the produced ordering (or at least that the candidate is a valid LexBFS ordering via a proper certificate, e.g. re-running the HMPV algorithm and comparing). Option (b) with full recompute-comparison defeats the purpose; a real fix needs a sound local certificate.
2. Do NOT fix this by "checking the (LB) property more carefully" — the property check itself is fine; the error is using it as a validity certificate for LexBFS orderings of arbitrary graphs.
3. Note the secondary issue: `_try_local_repair` is called with the pre-update ordering and post-update graph; even if the acceptance test were sound, the candidate generation (single-vertex moves of u and v) is not guaranteed to contain a valid LexBFS ordering of the new graph, so the fallback must remain.
4. The static `_lexbfs_ordering` itself is correct (standard label-based LexBFS with vertex-id tie-break); the fallback path produces valid orderings. The failure is solely that the local-repair fast path returns an unsound result.
