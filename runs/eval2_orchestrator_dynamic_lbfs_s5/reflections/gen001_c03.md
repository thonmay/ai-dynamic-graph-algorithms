## FAILURE_DESCRIPTION
Failing case: `init` on a 2-vertex graph (n=2, 0/1 adjacency matrix). Expected result `[0, 1]` (any valid LexBFS ordering of all 2 vertices), actual result `[]` — the returned `state['ordering']` is an empty list. The verifier reads `state['ordering']` and found no vertices in it.

## ROOT_CAUSE
The static `_lexbfs` routine is broken: it never records the vertices it *selects*. Trace on n=2:

1. `buckets = [[0], [1]]`, `bucket_of = [0, 1]`, `idx_in = [0, 0]`.
2. Loop iteration `s = 0`:
   - Refinement: each singleton bucket splits into `nb`/`rest` by adjacency to 0. For a singleton `[v]`, exactly one of `nb`, `rest` is non-empty, so `new_buckets` is again `[[0], [1]]` (or `[[1], [0]]` if 1 is adjacent to 0).
   - `s = buckets[0][0]` (say 0), then the removal block pops 0 from its bucket. Since the bucket had length 1, `b.pop()` empties it and `buckets.pop(bucket_of[s])` removes it.
   - **The selected vertex 0 is discarded — it is not appended to any output list.**
3. Loop iteration `s = 1`: same thing — vertex 1 is selected and discarded.
4. After the loop, `buckets` is empty, so `order = []`.

The responsible lines are the removal block inside the `for s in range(n)` loop:

```python
        # pick next vertex: first bucket, first vertex
        s = buckets[0][0]
        # remove s from its bucket
        b = buckets[bucket_of[s]]
        i = idx_in[s]
        if i + 1 < len(b):
            ...
        else:
            b.pop()
            if not b:
                buckets.pop(bucket_of[s])
```

and the final flatten:

```python
    order = []
    for b in buckets:
        order.extend(b)
    return order
```

The algorithm conflates "the queue of unprocessed vertices" with "the output ordering". In a correct LexBFS, the vertex removed from the front of the queue at step i *is* the i-th element of the output ordering. Here the removed vertex is simply thrown away, and the final `order` is built from the *remaining* (unprocessed) buckets, which is empty after n iterations. Hence `[]` for any n ≥ 1.

Note the failure is in `init` itself (sequence_idx 0), so the dynamic update logic (`insert_edge`/`delete_edge`) is never even reached; the (LB) checker `_is_lexbfs` is not implicated in this particular failure (it would actually accept `[]` as vacuously valid, which is a secondary latent bug worth fixing too — see hints).

## REPAIR_HINTS
Smallest concrete fix in `_lexbfs`:

1. Add an output list, e.g. `order = []` before the loop.
2. In the removal block, after `s = buckets[0][0]`, append the selected vertex: `order.append(s)` (do this before removing it from its bucket).
3. Return `order` directly instead of flattening the leftover buckets (the leftover buckets are empty by construction after n selections).

This is the standard queue-based LexBFS: the selection order *is* the output.

Secondary fixes to consider (not the cause of this failure, but they will bite later):

- `_is_lexbfs` returns `True` for an empty or partial ordering vacuously; guard with `if sorted(order) != list(range(n)): return False` so a corrupted state can never pass the "keep current ordering" fast path in `insert_edge`.
- The (LB) check as written is O(n^4) (a, b, c, d loops) despite the docstring claiming O(n^3); fine for small n, but if the fast path is meant to be cheap, consider the standard O(n^2) certificate check (for each b, track the set of "witness" candidates).
- The refinement step rebuilds all bookkeeping in O(n) per iteration, making `_lexbfs` O(n^2) rather than O(n+m); acceptable for correctness-first, but the brief favours the HMPV O(n+m) structure if performance matters later.

Approaches that will NOT work:
- Returning the flattened leftover buckets (current code) — by construction they are empty after n selections.
- "Fixing" the failure by special-casing n=2 — the bug discards every selected vertex for all n ≥ 1.
