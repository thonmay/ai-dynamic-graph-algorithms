# Reflection: gen001_c04

## FAILURE_DESCRIPTION
Operation: `init` on a 3-vertex graph (n=3). The candidate returned
`ordering = [2, 1, 0]`, but the verifier reports it is NOT a valid LexBFS
ordering. The reported violation is a 4-point witness with
`a=2, b=1, c=0, pos_a=0, minD=1000000000`.

Interpreting the violation fields as *positions* in the returned ordering
(a=2, b=1, c=0, pos_a=0): the verifier found a triple of positions
`pos_a < b < c` (i.e. `0 < 1 < 2`) such that the vertex at position `pos_a`
is adjacent to the vertex at position `c` but NOT adjacent to the vertex at
position `b`, and no earlier position `d < pos_a` witnesses the (LB)
property. Since `pos_a = 0`, there is no `d < 0`, so the property fails
unconditionally. `minD=1000000000` is the sentinel for "no witness d found".

The expected ordering `[0, 2, 1]` is a valid LexBFS ordering of the same
graph. So the static `_lexbfs` routine produced an ordering that does not
satisfy the (LB) 4-point property.

## ROOT_CAUSE
The bug is in `_lexbfs` (the static partition-refinement routine). The
algorithm is structurally wrong: it does not implement the standard
LexBFS bucket refinement.

Specifically, the loop `for x in range(n):` iterates over vertex IDs in
numeric order, NOT over vertices in the current LexBFS order. In a correct
LexBFS, at each step you must pick the *first* vertex of the *first* bucket
in the current bucket order. Here `x` is just `0, 1, 2, ...` regardless of
where those vertices sit in the bucket list. This means the refinement is
applied in the wrong sequence, producing an ordering that is not a valid
LexBFS.

Additionally, the bucket-refinement logic itself is incorrect:

1. **Wrong refinement target.** In standard LexBFS, when vertex `x` is
   selected, you refine *every other bucket* by splitting it into
   `N(x) ∩ B` and `N(x)^c ∩ B`. The code does this, but it also
   re-inserts `x`'s own bucket as `[x], N(x)∩Bx, N(x)^c∩Bx` at the *front*
   of the bucket list. In correct LexBFS, `x` is simply removed from its
   bucket and the remaining vertices in that bucket stay in place (they are
   not re-sorted relative to other buckets). Placing `[x]` at the front
   distorts the order.

2. **Bucket order is reset every iteration.** After each refinement, the
   code sets `order = list(range(len(buckets)))`, which just enumerates
   buckets by their index in the `new_buckets` list. This is fine *if*
   `new_buckets` is built in the correct relative order, but because the
   refinement is applied to buckets in the order they appear in `order`
   (which is just `0..k-1`), and `x`'s own bucket is always inserted at
   position 0, the relative ordering of buckets is not maintained
   correctly across iterations.

3. **The `for x in range(n)` loop is the fundamental error.** Even if the
   bucket logic were correct, iterating by vertex ID rather than by the
   current first vertex of the first bucket means the algorithm does not
   follow the LexBFS selection rule.

The `_is_lexbfs` checker and `_try_repair` are only invoked on updates, not
on `init`, so the broken `_lexbfs` output is returned directly from `init`
without any validation.

## REPAIR_HINTS
The smallest fix is to **replace `_lexbfs` with a correct static LexBFS
implementation**. The current bucket-refinement code is too broken to patch
in place. A correct implementation:

1. Maintain a list of buckets (each a list of vertices), initially one
   bucket per vertex: `[[0], [1], ..., [n-1]]`.
2. Maintain a pointer/queue of "active" buckets. At each step, take the
   first vertex `x` from the first non-empty bucket (this is the LexBFS
   selection rule: always pick the earliest vertex in the current order).
3. Remove `x` from its bucket. If the bucket becomes empty, remove it.
4. For every *other* bucket `B`, split it into `B ∩ N(x)` (placed before
   `B ∩ N(x)^c`). This is the partition refinement step.
5. Append `x` to the output ordering.
6. Repeat until all vertices are placed.

A simpler and more reliable approach for correctness-first: implement
LexBFS via the **label-based** formulation. Each vertex `v` carries a
label (a list of 0s and 1s of length equal to the number of vertices
already placed). Initially all labels are empty. At each step, pick the
vertex with the lexicographically smallest label (tie-break by vertex ID).
Append that vertex to the order, and for every remaining vertex `w`,
append `1` to `w`'s label if `w` is adjacent to the just-placed vertex,
else append `0`. This is O(n^3) but trivially correct and easy to verify.

**Do NOT** try to fix the bucket logic in place — the iteration order
(`for x in range(n)`) is fundamentally wrong and the bucket re-insertion
logic is also incorrect. A clean rewrite of `_lexbfs` is the right fix.

**Also note:** `init` does not call `_is_lexbfs` to validate its output.
Adding a self-check in `init` (and in the update fallback) would catch
this class of bug immediately.
