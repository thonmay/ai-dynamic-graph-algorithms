## FAILURE_DESCRIPTION
3-vertex undirected graph. After `init` (graph had edges (0,1) and (0,2), i.e. a star centered at 0), the state held ordering `[0, 1, 2]`. The failing update is `delete_edge(graph, (0, 2), state)` at sequence index 1, leaving only edge (0,1). The candidate returned `[0, 2, 1]`, but the expected (and only valid) ordering is `[0, 1, 2]`.

The verifier reports the (LB) 4-point violation with a=0 (pos 0), b=2 (pos 1), c=1 (pos 2): a~c (0-1 is an edge), a not~ b (0-2 is not an edge), and no witness d < a exists (minD = 10^9 sentinel). Indeed, in `[0, 2, 1]` the non-neighbor 2 of 0 is placed before the neighbor 1, which no LexBFS of this graph can do.

## ROOT_CAUSE
The bug is in the static fallback `_lexbfs`, specifically the label-sorting line:

```python
new_buckets.sort(key=lambda b: b[0])
```

Labels are lists of vertex ids (the splitting neighbors in order of appearance), and the code sorts them **lexicographically by vertex id**. But LexBFS requires buckets to be ordered by **reverse lexicographic** comparison of labels: the most recently added label element (the first element of the list, since the code prepends with `new_label = [v] + blabel`) must dominate the comparison.

Tracing the failing case (adj after deletion: 0~1 only):
- Start: buckets = `[[[], [0,1,2]]]`. Pick v=0. Refine: 1 is adjacent to 0, 2 is not.
  - adj part: label `[0]`, verts `[1]`
  - nonadj part: label `[]`, verts `[2]`
- `new_buckets.sort(key=lambda b: b[0])` compares `[]` vs `[0]` and puts `[]` first (shorter list sorts before longer). So buckets = `[[[], [2]], [[0], [1]]]`.
- Next pick: first bucket is `[2]` -> order becomes `[0, 2, ...]`, then `[1]` -> `[0, 2, 1]`.

Correct LexBFS: after 0, the neighbor 1 (label `[0]`) must come before the non-neighbor 2 (label `[]`), giving `[0, 1, 2]`.

Because `_try_repair` correctly rejected the old ordering `[0, 1, 2]`? No — actually `_validate([0,1,2], adj)` passes, so repair should have returned it. The real divergence is that the *initial* ordering from `init` was already wrong: with the star graph (edges 0-1, 0-2), the same sort bug produced `[0, 2, 1]` (non-neighbor 2 before neighbor 1) at init time. That invalid ordering was stored in state; after the deletion, `_try_repair` tried the old order `[0, 2, 1]` (invalid), the swap `[0, 1, 2]`... wait, the swap of u=0 and v=2 in `[0,2,1]` gives `[2,0,1]` (invalid), and the move candidates also failed validation, so it fell back to `_lexbfs`, which reproduced the same wrong `[0, 2, 1]`. Either way, the single root cause is the lexicographic (instead of reverse-lexicographic) bucket sort in `_lexbfs`.

## REPAIR_HINTS
Smallest fix: in `_lexbfs`, change the sort to reverse-lexicographic order over the label lists. Since labels are stored with the newest element first (`[v] + blabel`), reverse-lexicographic comparison is exactly the comparison of the lists **reversed** in normal lexicographic order:

```python
new_buckets.sort(key=lambda b: list(reversed(b[0])))
```

Equivalently, append instead of prepend (`blabel + [v]`) and keep `sort(key=lambda b: b[0])` — both give the same bucket order. Verify with the failing trace: labels `[]` (verts [2]) vs `[0]` (verts [1]) -> reversed keys `[]` vs `[0]` -> `[0]` first -> order `[0, 1, 2]`, which `_validate` accepts.

Do NOT try to "fix" this by improving `_try_repair` or by adding more local move candidates: the fallback `_lexbfs` is the correctness backstop and it is itself broken, so every repair failure lands on an invalid ordering. Fix the sort first; the repair layer can stay as-is.

Also note: `_validate` itself is correct (it matches the (LB) property), so no change is needed there.
