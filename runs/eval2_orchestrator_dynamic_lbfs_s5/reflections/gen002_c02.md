## FAILURE_DESCRIPTION

Failing case (sequence_idx 0, operation `insert (0, 1)` on a 3-vertex graph):
- Result returned by the candidate: `[0, 2, 1]`
- Expected (any valid LexBFS ordering, e.g. `[0, 1, 2]`)
- Verifier violation: (LB) 4-point property broken at positions a=0, b=2, c=1
  (i.e. ordering positions 0 < 2 < 1 are the vertices at those slots:
  ordering[0]=0, ordering[2]=1, ordering[1]=2).

Tracing the code on this case:

1. `init` produced some ordering of the pre-update graph (whatever it was,
   the state carried into `insert_edge` is `state['ordering']`).
2. `insert_edge` calls `_try_local_repair(ordering, graph, n, (0,1))`.
3. `_try_local_repair` builds a candidate list: the unchanged ordering,
   the swap of u and v, local moves of u/v near each other, and then
   **all single-vertex moves of u and v to every position** (the last loop
   `for x in (u, v): for target in range(n): ...`).
4. It then accepts the **first** candidate for which
   `_is_lexbfs_ordering(cand, adj, n)` returns True.
5. The accepted candidate was `[0, 2, 1]`, which the verifier rejects.

So the divergence is not in `_lexbfs_ordering` (the fallback recompute is
correct) but in the acceptance test `_is_lexbfs_ordering`, which returned
True for the invalid ordering `[0, 2, 1]`.

## ROOT_CAUSE

`_is_lexbfs_ordering` is unsound: it checks the wrong extremum.

LexBFS selects, at each step, the remaining vertex whose label (the
adjacency pattern to the already-output prefix, read in output order) is
lexicographically **MINIMAL**. The candidate's own generator
`_lexbfs_ordering` implements this correctly:

```python
if best is None or labels[v] < best_label or (labels[v] == best_label and v < best):
```

But the certificate inverts the comparison. In `_is_lexbfs_ordering`:

```python
for i in range(n):
    x = ordering[i]
    # x must have a lexicographically maximal label among remaining
    # vertices (positions i..n-1).
    for j in range(i + 1, n):
        y = ordering[j]
        # if label[y] > label[x], x is not maximal -> invalid
        if not label_less(y, x):
            return False
```

This accepts an ordering iff every chosen vertex has a lexicographically
**MAXIMAL** label among the remaining vertices — i.e. it certifies
"reverse-label LexBFS", not LexBFS. (Equivalently, it is the certificate
for the ordering reversed.)

Concrete trace on the accepted-but-invalid candidate `[0, 2, 1]`
(positions: pos[0]=0, pos[2]=1, pos[1]=2):

- i=0, x=0: remaining y=2 (label (1,)), y=1 (label (1,)).
  `label_less(2,0)`: m=0 -> returns 1<0 = False -> `not False` = True ->
  return False. So the check fails at i=0.

This shows the check is inconsistent even with the candidate's own
debug trace (`_debug_trace` asserts `[0,1,2]` should pass, but the same
code path rejects it). The point stands regardless of the exact pre-update
graph: the acceptance test is the wrong predicate, so `_try_local_repair`
can accept orderings that no LexBFS run produces (and reject valid ones),
and the fallback recompute is never reached.

Note the docstring of `_is_lexbfs_ordering` even says "lexicographically
maximal" — the author believed the maximal-label variant was the correct
invariant. It is not; HMPV LexBFS picks the minimal label.

## REPAIR_HINTS

Smallest concrete fix, in `_is_lexbfs_ordering`:

1. Flip the extremum: the chosen vertex `x = ordering[i]` must have a
   lexicographically **MINIMAL** label among the remaining vertices
   (positions i..n-1). Replace the inner test

   ```python
   if not label_less(y, x):
       return False
   ```

   with

   ```python
   if label_less(x, y):
       return False
   ```

   i.e. reject as soon as some remaining `y` has a strictly smaller label
   than `x`. (`label_less` itself is correct: it compares the two
   adjacency-pattern prefixes and, on a tie, the shorter label is smaller,
   which matches the generator's tuple comparison.)

2. Update the docstring/comments that say "maximal" to "minimal".

3. Sanity-check the fixed certificate against the generator: for a batch
   of random graphs, `_is_lexbfs_ordering(_lexbfs_ordering(adj, n), adj, n)`
   must be True, and `_is_lexbfs_ordering(reversed(_lexbfs_ordering(adj, n)),
   adj, n)` must be False on non-trivial graphs (the old code accepted the
   reversed ordering, which is a quick regression test for this bug).

Approaches that will NOT work:

- Keeping the maximal-label test and instead reversing the ordering before
  checking: the certificate must match the direction in which the ordering
  is actually produced; patching the call sites is more error-prone than
  fixing the predicate.
- Using `_check_lb_property` as the acceptance test: as the candidate's own
  comments note, the (LB) 4-point property is necessary but not sufficient
  for a LexBFS ordering of an arbitrary graph, so it would still accept
  invalid orderings.
- Relying on the fallback recompute: it is correct, but it is only reached
  when `_try_local_repair` returns None; with an unsound certificate the
  fast path accepts garbage first, so the fallback never runs.
