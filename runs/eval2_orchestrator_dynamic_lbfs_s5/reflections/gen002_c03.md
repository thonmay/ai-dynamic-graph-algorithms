## FAILURE_DESCRIPTION
n=3, single operation `insert (0,2)` at sequence_idx 0. Initial graph has only edge (1,2); after the insert the graph has edges (0,2) and (1,2). Expected a valid LexBFS ordering `[0,2,1]`; the candidate returned `[0,1,2]`. The verifier's (LB) check fails at positions a=0, b=1, c=2 (vertices 0,1,2): 0–2 ∈ E, 0–1 ∉ E, and there is no d < 0 to witness the property (minD = 1e9).

## ROOT_CAUSE
The bug is in the static `_lexbfs` routine, not in the dynamic logic. The `insert_edge` path works correctly: `_is_lexbfs(graph, [0,1,2])` correctly returns False (a=0, b=1, c=2, the d-loop over `range(0)` is empty so `ok` stays False), and the code falls through to `order = _lexbfs(graph)`. But `_lexbfs` itself is wrong and returns the invalid `[0,1,2]`.

The responsible line is the next-vertex selection:

```python
# pick next vertex: first bucket, first vertex
s = buckets[0][0]
```

In LexBFS the next vertex must be chosen from the **frontier** — the bucket of vertices *adjacent* to the most recently selected vertex (the "nb" part of the last split), not from the first bucket overall. Tracing on the final graph (edges 0–2, 1–2):

1. s=0. Refine by adjacency to 0: bucket [2] splits into nb=[2], rest=∅; buckets [0],[1] unchanged → buckets = [[0],[1],[2]]. Pick s=0, order=[0], remove 0 → buckets = [[1],[2]].
2. s=1. Refine by adjacency to 1: bucket [2] splits into nb=[2] → buckets = [[1],[2]]. Pick s=1, order=[0,1], remove 1 → buckets = [[2]].
3. s=2, order=[0,1,2].

After selecting 0, the frontier is {2} (adjacent to 0), but `buckets[0]` is [1] (non-adjacent to 0), so the code picks 1 instead of 2. The correct ordering is [0,2,1].

Note the same bug makes `init` and `delete_edge` wrong on any graph where, after a split, the first bucket is the non-adjacent remainder (e.g., any graph where the start vertex has a neighbor with a larger id than some non-neighbor). The "check-then-recompute" strategy in `insert_edge` is sound; the fallback recompute is what produces the invalid result.

## REPAIR_HINTS
Fix the next-vertex selection in `_lexbfs` to pick from the frontier (the bucket of vertices adjacent to the last selected vertex), not from `buckets[0]`. Concretely:

1. After refining by adjacency to the current vertex `s`, record which bucket is the "nb" part (the vertices adjacent to `s`). The next vertex to select is the first vertex of that nb bucket.
2. A clean way: after the refinement loop, the bucket containing the neighbors of `s` is the one that was split off as `nb` from the bucket that contained `s`'s neighbors. Track this: when you split the bucket containing the current frontier, the `nb` sub-bucket is the new frontier. Pick `s = nb[0]` (or the first vertex of the nb bucket) as the next vertex.
3. Alternatively, restructure to the standard HMPV formulation: maintain a single ordered list of buckets where the first bucket is always the frontier (vertices adjacent to the last selected vertex). After selecting a vertex, refine all buckets by adjacency to it, and the first bucket of the refined list is the new frontier.

Approaches that will NOT work:
- Keeping `s = buckets[0][0]` and just reordering buckets after each split does not fix the fundamental issue: the first bucket after a split is the non-adjacent remainder, not the frontier. You must explicitly track which bucket is the frontier (adjacent to the last selected vertex).
- The dynamic logic in `insert_edge` (check-then-recompute) and `delete_edge` (always recompute) is fine; do not change them. The fix is entirely in `_lexbfs`.
