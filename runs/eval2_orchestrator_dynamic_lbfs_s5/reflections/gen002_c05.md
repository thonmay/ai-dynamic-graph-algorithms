## FAILURE_DESCRIPTION
n=4. Operation: `delete (1, 0)` (sequence_idx 0, i.e. the first update after init).
Returned ordering: `[0, 1, 2, 3]`. Expected (one valid LexBFS): `[0, 2, 1, 3]`.
The verifier reports a (LB) 4-point violation at positions a=0, b=1, c=2 (vertices
va=0, vb=1, vc=2): va–vc is an edge, va–vb is not an edge, and no d < a exists
(a is the first position, so the witness set is empty). The graph after the
deletion must therefore contain edge (0,2) and not (0,1); the pre-deletion graph
contained (0,1) (the deleted edge) and (0,2).

## ROOT_CAUSE
The static algorithm `_lexbfs` is simply wrong, and the fallback path in
`insert_edge`/`delete_edge` uses it unverified:

```python
    new_order = _try_repair(order, adj, n, edge, False)
    if new_order is None:
        new_order = _lexbfs(adj, n)          # <-- unverified result returned
```

`_try_repair` correctly refuses to return an invalid ordering (every candidate is
checked with `_is_lexbfs`), so it returned `None` here. The fallback then returned
the raw output of `_lexbfs`, which is not a valid LexBFS ordering for this graph.

Why `_lexbfs` is wrong: it is not the Habib–McConnell–Paul–Viennot algorithm.
The HMPV rule is: when vertex x is selected, x's own bucket is split into
({x}, N(x)∩B, N(x)^c∩B) and the two non-singleton parts are reinserted at the
END of the bucket list (they are the "last" buckets, i.e. the least-preferred
vertices), while every other bucket is split in place into (N(x), N(x)^c).
The candidate instead does:

```python
        new_buckets.insert(0, [x])
        if N:
            new_buckets.insert(1, N)
        if Nn:
            new_buckets.insert(2 if N else 1, Nn)
```

i.e. it puts x's neighbours immediately AFTER x at the FRONT of the list. This
is a different (non-LexBFS) ordering rule. Concretely, on the post-deletion graph
(edges {0,2}, {1,3}, {2,3} — the only 4-vertex graph consistent with the
violation data and the expected answer), the algorithm produces:
- iter 1: x=0, buckets [[0],[2],[1],[3]]
- iter 2: x=2, buckets [[2],[3],[0],[1]]
- iter 3: x=3, buckets [[3],[1],[2],[0]]
- iter 4: x=1, buckets [[1],[3],[2],[0]]
- flatten: [1,3,2,0]

which also fails `_is_lexbfs` (positions a=0,b=1,c=2: 1–2 non-edge, 1–3 edge,
no d<a). So the static routine is broken on this very instance.

Why the bug was never caught at init: `init` uses `_lexbfs_verify`, which falls
back to a brute-force permutation search when `_lexbfs`'s output fails
`_is_lexbfs` (n<=8). The pre-deletion graph (edges {0,1},{0,2},{1,3},{2,3}) is
chordal, so some permutation passes the check and init returned a valid
ordering. The update path, however, calls bare `_lexbfs` with no verification,
so the broken static routine's output went straight to the verifier.

Note the returned `[0,1,2,3]` is not even the raw `_lexbfs` output for the
reconstructed graph (that would be `[1,3,2,0]`), so the exact pre-deletion graph
may differ slightly from my reconstruction — but the mechanism is the same in
all cases: `_try_repair` returned None and the unverified `_lexbfs` fallback
produced an ordering that violates the (LB) property.

## REPAIR_HINTS
1. Minimal fix (restores correctness immediately): in `insert_edge` and
   `delete_edge`, replace the fallback
   `new_order = _lexbfs(adj, n)` with `new_order = _lexbfs_verify(adj, n)`.
   This guarantees the returned ordering always satisfies the (LB) property.
   (For n>8 the brute-force fallback is infeasible, so this alone is not a
   complete fix — see 2.)
2. Real fix: correct `_lexbfs` to the actual HMPV algorithm. The bug is the
   placement of x's own-bucket parts: after removing x, the buckets
   N(x)∩B and N(x)^c∩B must be APPENDED to the end of the bucket list (after
   all other buckets), not inserted at positions 1/2 in front of everything.
   The other buckets are already split in place correctly.
3. Do NOT try to "fix" `_try_repair` to find more local moves: its candidates
   are all verified, so it is sound; the failure is entirely in the unverified
   fallback. Adding more repair candidates without fixing `_lexbfs` will keep
   failing whenever the repair search space is exhausted.
4. Do not rely on `_is_lexbfs` as a substitute for a correct static algorithm
   at larger n — it is a checker, not a constructor.
