## FAILURE_DESCRIPTION

- Operation: `init` at `sequence_idx: 0` on a 3-vertex graph (graph_shape [3,3]).
- Expected (any valid LexBFS ordering): `[0, 1, 2]`.
- Actual returned: `[0, 2, 1]`.
- Verifier violation: (LB) 4-point property broken at positions a=0, b=2, c=1
  (pos_a=0, minD=1000000000 sentinel = no witness found).

The graph is the path 0-1-2 (edges {0-1, 1-2}, no edge 0-2). On that graph
`[0, 2, 1]` is invalid: at positions a=0 (vertex 0), b=1 (vertex 2),
c=2 (vertex 1): ac = 0-1 ∈ E, ab = 0-2 ∉ E, and there is no d < pos_a=0
to witness, so the (LB) property fails.

## ROOT_CAUSE

The bug is in the static generator `_lexbfs` (the label-based LexBFS).
The repair path is never reached at `init`, so the bug is in the initial
ordering computation.

The `_lexbfs` function implements the "pick the unplaced vertex with the
lexicographically smallest label" algorithm, where the label of vertex v
is the sequence of bits (v~order[0], v~order[1], ..., v~order[k-1]).
This algorithm is NOT equivalent to LexBFS.

Trace on the path 0-1-2 (adj[0]={1}, adj[1]={0,2}, adj[2]={1}):

- Step 1: all labels empty. best=0 (tie-break by id). out=[0].
  Extend: label[1]=[1] (1~0), label[2]=[0] (2⋯0).
- Step 2: unplaced {1,2}. labels: 1→[1], 2→[0].
  Lexicographic: [0] < [1]. Pick 2. out=[0,2].
  Extend: label[1]=[1,1] (1~0, 1~2).
- Step 3: pick 1. out=[0,2,1].

Result: [0,2,1]. But [0,2,1] violates (LB):
- i=0, j=1, k=2: order[0]=0, order[1]=2, order[2]=1.
  0~1? Yes. 0~2? No. Need d<0: none. → VIOLATION.

The correct LexBFS algorithm is BFS-based: at each step, pick the vertex
in the BFS frontier (unvisited vertices adjacent to visited vertices) with
the lexicographically smallest label. On the path 0-1-2:
- Start at 0. Frontier: {1}.
- Pick 1 (only choice). Frontier: {2}.
- Pick 2. Done.
- Result: [0,1,2]. ✓

The "pick the smallest label among all unvisited" algorithm is a different
algorithm that does not produce valid LexBFS orderings in general. The
HMPV partition-refinement algorithm (which IS equivalent to LexBFS)
maintains a partition of the unvisited vertices and refines it by
adjacency to the last visited vertex, then picks the first block in
lexicographic order. This is NOT the same as "pick the smallest label
among all unvisited."

The responsible code in `_lexbfs`:

```python
for v in range(n):
    if placed[v]:
        continue
    if best == -1 or labels[v] < best_label or (
        labels[v] == best_label and v < best
    ):
        best = v
        best_label = labels[v]
```

This picks the vertex with the smallest label among ALL unplaced vertices,
not just those in the BFS frontier. This is the bug.

## REPAIR_HINTS

1. Replace `_lexbfs` with a correct BFS-based LexBFS implementation:

```python
def _lexbfs(adj, n):
    visited = [False] * n
    order = []
    start = 0
    visited[start] = True
    order.append(start)
    frontier = set(adj[start])
    while frontier:
        best = None
        best_label = None
        for v in sorted(frontier):
            label = tuple(1 if x in adj[v] else 0 for x in order)
            if best is None or label < best_label:
                best = v
                best_label = label
        visited[best] = True
        order.append(best)
        frontier.discard(best)
        for w in adj[best]:
            if not visited[w]:
                frontier.add(w)
    for v in range(n):
        if not visited[v]:
            visited[v] = True
            order.append(v)
    return order
```

This picks the vertex in the BFS frontier with the lexicographically
smallest label, which is the correct LexBFS algorithm.
