# Reflection: gen003_c03

## FAILURE_DESCRIPTION

- Operation: `init` (sequence_idx 0, no prior updates).
- Graph: n = 3, undirected. The candidate returned `ordering = [0, 2, 1]`.
- Expected (per the harness): `[0, 1, 2]`.
- Reported violation: `a=0, b=2, c=1, pos_a=0, minD=1000000000`.

Interpreting the violation fields as **vertex ids** (a=0, b=2, c=1) with
`pos_a` = position of vertex a in the returned ordering (0), the violated
(LB) 4-point condition is:

- a = vertex 0 at position 0, b = vertex 2 at position 1, c = vertex 1 at
  position 2 (so pos_a < pos_b < pos_c).
- ac in E (0-1 is an edge), ab not in E (0-2 is not an edge).
- The witness set {d : d < a} is empty (a is at position 0), so no d exists
  with db in E and dc not in E. `minD=1000000000` is the harness's
  "no witness found" sentinel.

This is a genuine (LB) violation, and it is consistent with the graph being
the path 1-0-2 (edges {0-1, 0-2}, no edge 1-2). On that graph:
- `[0, 1, 2]` is a valid LexBFS (start 0, then 1, then 2; the 4-point
  property holds vacuously for the only non-edge pair 1-2).
- `[0, 2, 1]` is NOT a valid LexBFS: at position 0 vertex 0 is adjacent to
  vertex 1 (position 2) but not to vertex 2 (position 1), and there is no
  earlier vertex to witness it.

## ROOT_CAUSE

The failure is in `init` -> `_lexbfs(adj, n)`. The static label-based
LexBFS is wrong: it picks the unplaced vertex with the lexicographically
**smallest** label, but the label-based formulation of LexBFS requires
picking the lexicographically **largest** label (1 = adjacent to an already
placed vertex sorts before 0).

Responsible lines in `_lexbfs`:

```python
        best = -1
        best_label = None
        for v in range(n):
            if placed[v]:
                continue
            if best == -1 or labels[v] < best_label or (
                labels[v] == best_label and v < best
            ):
                best = v
                best_label = labels[v]
```

Trace on the path 1-0-2 (adj[0]={1,2}, adj[1]={0}, adj[2]={0}):

1. All labels empty; tie broken by vertex id -> place 0.
   Labels: label[1] = [1] (1 adjacent to 0), label[2] = [1].
2. Both unplaced labels are `[1]`; tie broken by vertex id -> place 1.
   label[2] becomes [1, 0] (2 not adjacent to 1).
3. Place 2. Result: `[0, 1, 2]`.

Wait — with the *current* (smallest) comparison and id tie-break this trace
actually yields `[0, 1, 2]`, not `[0, 2, 1]`. So the exact graph must be
different from the path 1-0-2. The only 3-vertex graphs on which the
smallest-label rule with id tie-break produces `[0, 2, 1]` while
`[0, 1, 2]` is the valid LexBFS are those where, after placing 0 first,
vertex 2's label is strictly smaller than vertex 1's label, i.e. 2 is
adjacent to 0 and 1 is not — but then 0-1 is not an edge and the reported
violation (ac = 0-1 in E) could not hold. Conversely, if 0-1 is an edge
and 0-2 is not, the smallest-label rule places 2 (label [0]) before 1
(label [1]) and returns `[0, 2, 1]`; but then the (LB) property is
satisfied by `[0, 2, 1]` (the non-edge is 0-1 with 1 at position 2, and
the witness d=2 works), so the harness would not flag it.

Conclusion: I cannot reconstruct the exact 3x3 matrix from the fields
given (the harness does not include the matrix in the failure record), and
the two hypotheses above are mutually exclusive with the reported
violation. What is certain, however, is the direction of the bug:

- The label-based LexBFS must select the lexicographically **largest**
  label at each step (equivalently, smallest label with 0/1 bits
  inverted). The candidate's `labels[v] < best_label` comparison is
  inverted relative to the standard formulation.
- The id tie-break (`v < best`) is a legal tie-break for LexBFS validity,
  so it is not the cause.
- `_is_lexbfs` itself is a correct implementation of the (LB) 4-point
  property (verified by hand on small cases), and it is not even called
  during `init`, so it cannot be the cause of this failure.

## REPAIR_HINTS

1. In `_lexbfs`, flip the comparison so the lexicographically **largest**
   label wins:

   ```python
   if best == -1 or labels[v] > best_label or (
       labels[v] == best_label and v < best
   ):
   ```

   Keep the id tie-break (any deterministic tie-break yields a valid
   LexBFS). This is the minimal change and restores correctness of `init`
   and of the full-recompute fallback in `insert_edge`/`delete_edge`.

2. Do NOT try to "fix" this by making `_try_repair` smarter or by adding
   more local-move candidates: the repair path is only reached after
   updates, and the failing case is `init`, which never calls
   `_try_repair`. The static routine must be correct on its own.

3. Do not rely on `_is_lexbfs` as a post-hoc filter in `init`: it is O(n^3)
   and, more importantly, if the static routine is wrong the filter would
   just reject the answer without producing a correct one. Fix the
   selection rule instead.

4. After fixing `_lexbfs`, add a self-check in `init` (assert
   `_is_lexbfs(order, adj, n)`) during development to catch any remaining
   tie-break/label bugs; the (LB) checker is correct and cheap enough for
   tests.

5. Note for the repair role: the dynamic part (local repair + fallback)
   is architecturally sound — the fallback recompute is correct once
   `_lexbfs` is fixed, and the repair is only accepted after a full (LB)
   verification. No changes to `insert_edge`/`delete_edge`/`_try_repair`
   are required for correctness.
