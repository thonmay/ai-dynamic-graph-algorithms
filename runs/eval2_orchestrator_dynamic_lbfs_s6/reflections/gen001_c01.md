## FAILURE_DESCRIPTION

Operation: `init` on a 3-vertex undirected graph (sequence_idx 0, so no prior updates).
- Result returned: `[0, 1, 2]`
- Expected (any valid LexBFS): `[0, 2, 1]`
- Verifier violation: a=0, b=1, c=2 (positions 0,1,2), with `minD = 10^9` (sentinel = no witness d found).

Reconstructing the graph from the violation and the expected ordering:
- The violated triple (a=0, b=1, c=2) requires: 0-1 NOT in E, 0-2 in E, and NO d < 0 (vacuous) — so the violation is real for `[0,1,2]`.
- Expected `[0,2,1]` must be valid. Checking its only non-edge triple (a=0, b=1, c=2 → vertices 0,1,2): 0-1 not in E, 0-2 in E, need d<0 — none exists, so this triple would ALSO violate... unless 0-1 IS in E. Indeed, if 0-1 in E then the (a=0,b=1,c=2) triple is not triggered (ab in E), and `[0,2,1]` is valid.
- So the graph is: edges {0-1, 0-2}, non-edge {1-2}. (Path 1-0-2.)

For this graph the valid LexBFS orderings are `[0,1,2]`... wait — check `[0,1,2]` again: a=0 (v0), b=1 (v1): 0-1 in E → not triggered. a=0, b=2 (v2): 0-2 in E → not triggered. a=1 (v1), b=2 (v2): 1-2 not in E; need c>2 — none. So `[0,1,2]` IS valid for edges {0-1,0-2}.

Therefore the actual graph must be different: the violation says for (a=0,b=1,c=2) in the returned order, 0-2 in E, 0-1 not in E, no witness. And `[0,2,1]` is valid. For `[0,2,1]` to be valid with 0-2 in E and 0-1 not in E: triple (a=0,b=1,c=2) = vertices (0,2,1): 0-2 in E → not triggered. Triple (a=0,b=2,c=1): vertices (0,1,2): 0-1 not in E, 0-2 in E, need d<0 — none → VIOLATION. So `[0,2,1]` is only valid if 1-2 in E as well? No — the triple (a=0,b=2,c=1) has ab = 0-1 not in E, ac = 0-2 in E, and no d<a. That violates regardless of 1-2.

Conclusion: the only consistent reading is that the graph is the path 2-0-1 (edges {0-2, 0-1}) OR the verifier's "expected" is just one valid ordering and the real graph is such that `[0,1,2]` violates and `[0,2,1]` satisfies. The exact graph is not fully pinned down by the report, but the key fact is: **`init` returned an ordering that fails the (LB) certificate**, i.e. `_lexbfs` itself produced an invalid ordering. The bug is in the static routine, not in the dynamic repair path.

## ROOT_CAUSE

`_lexbfs` (lines 20-46) is not a correct LexBFS. Two concrete defects:

1. **Wrong refinement semantics.** The code precomputes `labels[u] = {v : v < u and v~u}` (lines 26-29) and then, for each `v` in increasing order, splits every bucket by membership in `labels[v]` (lines 32-41). This is NOT the partition-refinement LexBFS of Habib–McConnell–Paul–Viennot. In the correct algorithm, when a vertex `v` is *selected* (removed from the front of the queue), only the buckets *after* v's position are refined by v's adjacency, and the refinement key is "is x adjacent to v" — not "is v in x's precomputed label set". Using `v in labels[x]` (i.e. x~v) is equivalent as a key, but applying it to **all** buckets (including those before v) and in a fixed vertex-index order (not selection order) destroys the LexBFS invariant.

2. **Refinement order is by vertex id, not by selection order.** The loop `for v in range(n)` (line 32) processes vertices in numeric order. LexBFS refinement must process vertices in the order they are *selected* from the queue. Since the buckets are being mutated during the loop, processing by id is simply wrong.

Consequence: for the failing 3-vertex graph the routine emits `[0,1,2]`, which violates the (LB) 4-point property at (a=0,b=1,c=2) — exactly the reported violation. Because `init` calls `_lexbfs` directly with no certificate check, the invalid ordering is returned as-is.

Note the candidate's own `_is_lexbfs` checker (lines 49-73) is correct; it is simply never called on the `init` output.

## REPAIR_HINTS

1. **Replace `_lexbfs` with a correct static LexBFS.** The simplest correct version (O(n^2) on a matrix, fine for correctness-first):
   - Maintain `labels[v]` = frozenset of already-selected neighbors of v (start empty).
   - Maintain an ordered list `unselected`.
   - Repeat n times: pick the unselected vertex with the lexicographically smallest label (any deterministic tie-break, e.g. smallest id); append to order; for each remaining unselected u, if the new vertex is adjacent to u, add it to `labels[u]`.
   - This is the standard label-based LexBFS and is trivially correct.

2. **Add a safety net in `init` (and in the update fallbacks):** after computing an ordering, run `_is_lexbfs`; if it fails, fall back to the label-based recompute. This guards against any residual bug in the refinement code.

3. **Do NOT try to patch the bucket-splitting loop in place** (e.g. by changing the loop order or the split key). The precomputed-labels + global-split design is structurally incompatible with LexBFS; a rewrite to the label/selection formulation is the minimal correct fix.

4. The `_local_repair` logic is downstream of this bug and cannot be assessed until `_lexbfs` is correct; leave it for a later iteration.
