## FAILURE_DESCRIPTION
Operation `init` on a 3-vertex undirected graph (0/1 adjacency matrix, 3x3).
The candidate returned ordering `[0, 1, 2]`, but the expected (valid) ordering
is `[0, 2, 1]`. The verifier reports a (LB) 4-point violation at positions
a=0, b=1, c=2 (pos_a=0, minD=1e9 meaning no witness d was found).

Concretely, for the returned ordering `[0, 1, 2]` the violated triple is:
- a=0 → va=0, b=1 → vb=1, c=2 → vc=2
- Condition: ac in E (edge 0-2 exists) AND ab not in E (edge 0-1 does NOT exist)
- Required: some d < a=0 with db in E and dc not in E. Since a=0, there is no
  d < 0, so the property is violated.

The graph must therefore have edges {0-2, 1-2} (path 0-2-1) and no edge 0-1.
The only valid LexBFS orderings are `[0, 2, 1]` or `[1, 2, 0]` (the middle
vertex 2 must come between its two neighbors).

## ROOT_CAUSE
The bug is in `_static_lexbfs`. The algorithm processes a bucket by iterating
`for v in B` where `B = buckets[bi]` was captured **before** the bucket was
emptied (`buckets[bi] = []`). During the loop, when vertex `v` is output and
other buckets are refined, the code appends new buckets to the `buckets` list
and enqueues them. However, the critical bug is:

**The refinement loop `for j in range(len(buckets))` iterates over ALL buckets
including ones that have already been consumed (emptied) and ones that are
currently being processed.** More importantly, the real bug is that when a
bucket is split, the `in_N` part stays in the same bucket index `j` and is
re-enqueued, while the `not_N` part gets a new index. But the outer loop
`for v in B` continues with the **original** list `B` that was captured at
the start. This is actually fine for the current bucket.

The actual bug: **the refinement of other buckets happens while iterating
`for j in range(len(buckets))`, but `len(buckets)` is evaluated once at the
start of the for-loop.** When a split appends a new bucket, the loop does NOT
visit the newly appended bucket in the same refinement pass. This means the
newly created `not_N` bucket is not refined by the current vertex `v`.

Wait — let me re-trace more carefully. `for j in range(len(buckets))` — in
Python, `range(len(buckets))` is evaluated once. So if `buckets` has length 3
at the start, the loop goes j=0,1,2. If during j=1 we split and append, the
new bucket at index 3 is NOT visited for this vertex v.

But actually, in the standard LexBFS algorithm, you only need to refine
buckets that are NOT the current one. The newly split bucket should be
refined by subsequent vertices, not the current one. Let me re-trace the
specific failing case.

Graph: 3 vertices, edges {0-2, 1-2}. Adjacency:
- adj[0] = [0, 0, 1]
- adj[1] = [0, 0, 1]
- adj[2] = [1, 1, 0]

Trace `_static_lexbfs(3, adj)`:
- buckets = [[0, 1, 2]], bucket_of = [0,0,0], q = deque([0])
- Pop bi=0. B = [0, 1, 2]. buckets[0] = [].
  - v=0: order=[0]. Refine other buckets. j ranges over range(1) → j=0 only.
    j==bi (0==0), skip. No refinement.
  - v=1: order=[0,1]. Refine other buckets. j ranges over range(1) → j=0 only.
    j==bi, skip. No refinement.
  - v=2: order=[0,1,2]. Refine other buckets. j ranges over range(1) → j=0 only.
    j==bi, skip. No refinement.
- q is empty. Return [0, 1, 2].

**The bug is clear**: all three vertices are in the single initial bucket.
When we pop that bucket and iterate through its vertices, there are NO other
non-empty buckets to refine (the only bucket is the one being consumed). So
no refinement ever happens, and the ordering is simply the initial order
[0, 1, 2].

The standard partition-refinement LexBFS requires that when you output a
vertex v from bucket B, you refine all OTHER buckets. But if all vertices
start in one bucket, the first vertex output gets no refinement (no other
buckets exist), and the remaining vertices in the same bucket are output
without any refinement either.

The correct algorithm should: after outputting v, split the REMAINDER of the
current bucket (not just other buckets) by N(v). Or equivalently, the
algorithm should process one vertex at a time from the front of the queue,
refining all other buckets including splitting the current bucket's remainder.

The standard HMPV algorithm works as follows:
- Maintain a queue of buckets.
- Pop the front bucket B.
- For each vertex v in B (in order):
  - Output v.
  - For each OTHER bucket C (not B, not empty): split C by N(v).
  - Also: the remaining vertices in B (after v) should be split by N(v)
    into B∩N(v) and B\N(v), and these become new buckets enqueued.

The candidate is missing the step of splitting the remainder of the current
bucket. Without it, all vertices in the initial bucket are output in their
original order with no refinement.

## REPAIR_HINTS
The fix is in `_static_lexbfs`. After outputting vertex `v` from bucket `B`,
the algorithm must also split the **remainder of B** (the vertices in B that
come after v) by N(v). Specifically:

1. When processing `v` from bucket `B`, after refining all other buckets,
   also partition the remaining vertices of `B` (those not yet output) into
   `B_rem ∩ N(v)` and `B_rem \ N(v)`.
2. If both parts are non-empty, replace the current bucket's remainder with
   two new buckets and enqueue them (the N(v) part first, to maintain the
   correct LexBFS order).

Concretely, restructure the inner loop:
```python
for idx, v in enumerate(B):
    order.append(v)
    # Refine all other non-empty buckets
    for j in range(len(buckets)):
        if j == bi or not buckets[j]:
            continue
        # ... existing split logic ...
    # ALSO: split the remainder of B (B[idx+1:]) by N(v)
    if idx + 1 < len(B):
        rem = B[idx+1:]
        in_N = [w for w in rem if adj[v][w]]
        not_N = [w for w in rem if not adj[v][w]]
        if in_N and not_N:
            # Replace the "virtual" remainder with two new buckets
            # Enqueue in_N first, then not_N
            buckets.append(in_N)
            buckets.append(not_N)
            q.append(len(buckets) - 2)
            q.append(len(buckets) - 1)
        # If only one part is non-empty, the remainder stays as-is
        # (no split needed)
```

Note: the current bucket `buckets[bi]` was already set to `[]`, so the
remainder is only tracked in the local variable `B`. The new sub-buckets
must be appended to `buckets` and enqueued.

**Approaches that will NOT work:**
- Simply reordering the initial bucket: the problem is structural (no
  refinement happens), not a tie-break issue.
- Adding a post-hoc validation + recompute in `init`: this would mask the
  bug but not fix the algorithm; the static LexBFS would still be wrong for
  any graph where the initial bucket has >1 vertex (i.e., all graphs).
- Only refining "other" buckets: this is what the code already does and it
  is insufficient. The remainder of the current bucket MUST be split.
