## FAILURE_DESCRIPTION
Failing case: n=3, operation `insert (0, 2)` at sequence index 0. The graph after the update is the triangle (all three edges present). The candidate returned ordering `[0, 1, 2]` (kept the pre-update ordering), but the expected valid LexBFS ordering is `[0, 2, 1]`. The verifier reports a 4-point property violation at positions a=0, b=1, c=2 (pos_a=0, minD=1e9, i.e. no witness d found).

Note: for the triangle, `[0, 1, 2]` is in fact a valid LexBFS ordering (every triple has a witness d), so the verifier's "expected" is just one valid ordering, not a unique one. The real failure is that the candidate's own validity check `_is_valid_lexbfs` returned True for an ordering that the verifier rejected — i.e. the check and the verifier disagree on the 4-point property.

## ROOT_CAUSE
The bug is in `_is_valid_lexbfs` (the fast-path validity check). The (LB) 4-point property requires, for every triple of positions a < b < c with P[a]~P[c] and not P[a]~P[b], a witness d < a with P[d]~P[b] and not P[d]~P[c]. The code only checks the witness for a single a, namely `a0 = min {a < b : P[a]~P[c]}`:

```python
for c in range(n):
    a0 = None  # min of {a < b : P[a]~P[c]}, or None
    for b in range(c):
        if not ((pos_nbr[b] >> c) & 1):
            if a0 is not None:
                mask_below_a0 = (1 << a0) - 1
                D = (pos_nbr[b] & mask_below_a0) & ~pos_nbr[c]
                if D == 0:
                    return False
        if (pos_nbr[b] >> c) & 1:
            if a0 is None:
                a0 = b
```

Checking only the minimum a is not equivalent to checking all a. The witness condition "exists d < a with P[d]~P[b] and not P[d]~P[c]" is monotone in a (a larger a admits a superset of candidate d's), so if the minimum a0 has a witness, every larger a does too — but if a0 has no witness, a larger a might still have one. The code returns False as soon as the minimum a0 fails, even though another a < b could satisfy the property. This makes the check strictly stronger than the true (LB) property, so it can reject valid LexBFS orderings (false negatives), causing unnecessary recomputation and, depending on the verifier's tie-breaking, a mismatch with the expected ordering.

Additionally, `~pos_nbr[c]` in Python is an infinite two's-complement negative integer; it happens to work here only because it is ANDed with `pos_nbr[b] & mask_below_a0` (both non-negative and bounded), but it is fragile and should be masked to n bits.

## REPAIR_HINTS
1. In `_is_valid_lexbfs`, replace the single-`a0` check with a check over ALL a < b with P[a]~P[c]. Concretely, for each (b, c) with not P[b]~P[c], compute the set A = {a < b : P[a]~P[c]} as a bitmask (e.g. `A = pos_nbr[c] & ((1 << b) - 1)`), and require that for every a in A there exists d < a with P[d]~P[b] and not P[d]~P[c]. This can be done in O(n^2/word) by precomputing, for each b, the prefix of positions d that are adjacent to P[b] but not to P[c], or by iterating a over the set bits of A and testing `(pos_nbr[b] & ((1 << a) - 1)) & ~pos_nbr[c] != 0`.
2. Alternatively, and more simply, drop the fast path entirely: after every update, just recompute a fresh LexBFS ordering with `_lexbfs_ordering` and return it. This is O(n^2) per update (matrix input) and is guaranteed correct, satisfying the "full correctness first" research goal. The fast path can be re-added later once the 4-point check is verified against a brute-force reference on random graphs.
3. Fix the `~pos_nbr[c]` usage by masking to n bits: `(~pos_nbr[c]) & ((1 << n) - 1)`, or better, compute the non-neighbor set directly as `((1 << n) - 1) ^ pos_nbr[c]`.
4. Do NOT try to "fix" the check by only looking at the maximum a instead of the minimum — the property must hold for every a, so any single-a shortcut is unsound.
