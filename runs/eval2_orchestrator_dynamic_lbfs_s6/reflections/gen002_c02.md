## FAILURE_DESCRIPTION

Failing case: n=3, operation `delete (0, 2)` at sequence_idx 1 (the second
operation of the sequence; the first operation is not reported, so the exact
pre-update graph is not pinned down by the report).

- Returned ordering: `[0, 1, 2, 1, 2]` (length 5)
- Expected: `[0, 1, 2]` (length 3)
- The returned 'ordering' is not even a permutation of the vertex set:
  vertices 1 and 2 appear twice and vertex 0 once.

The post-update graph (after deleting 0-2) must be the single edge {0-1}
(plus isolated vertex 2), because the expected ordering `[0,1,2]` is valid
for exactly that graph: the only triggered (LB) triple is (a=0, b=1, c=2)
with 0-1 in E, so it is not triggered; and `[0,1,2]` is a genuine LexBFS
ordering (0 first, then its neighbor 1, then the isolated 2).

## ROOT_CAUSE

The divergence is in `_static_lexbfs` (the fallback recompute), which is
called from `delete_edge` when `_try_local_repair` returns None. The
function can return a list that is not a permutation of the vertices:
vertices get emitted multiple times.

Mechanism, traced on the failing graph (edges {0-1} only, adj[0]=[0,1,0],
adj[1]=[1,0,0], adj[2]=[0,0,0]):

1. `buckets = [[0,1,2]]`, `q = deque([0])`. Pop bi=0, `B = [0,1,2]`,
   `buckets[0] = []`.
2. v=0: order=[0]. rem=[1,2]. No other non-empty buckets. Remainder split:
   in_N=[1], not_N=[2] → append bucket 1=[1], bucket 2=[2], enqueue both,
   `rem = []`.
3. v=1: order=[0,1]. rem=[2]. The "refine all other buckets" loop runs
   `for j in range(len(buckets))` and visits bucket 2=[2]:
   adj[1][2]=0, so in_N=[], not_N=[2] → no split (both-non-empty guard).
   Remainder rem=[2]: adj[1][2]=0 → in_N=[], not_N=[2] → no split.
4. v=2: order=[0,1,2]. Done with B.
5. Pop bi=1 (bucket [1]): B=[1], buckets[1]=[]. v=1: **order=[0,1,2,1]**.
   No other non-empty buckets (bucket 2=[2] is non-empty but... wait, it is
   visited: adj[1][2]=0 → in_N=[], not_N=[2] → no split).
6. Pop bi=2 (bucket [2]): v=2: **order=[0,1,2,1,2]**.

Result: `[0,1,2,1,2]` — exactly the reported result.

The responsible lines are the remainder-split block:

```python
buckets.append(in_N)
...
q.append(len(buckets) - 1)
buckets.append(not_N)
...
q.append(len(buckets) - 1)
rem = []
```

The remainder of the current bucket B is split into two new buckets that are
enqueued for full processing, but the outer loop `for idx, v in enumerate(B)`
keeps iterating over the ORIGINAL list `B` and emits every remaining vertex
again. The `rem = []` line only suppresses further remainder splits; it does
not stop the enumeration. So every vertex in a bucket whose remainder was
ever split is emitted twice (once from the original enumeration, once from
the enqueued sub-bucket).

Note the same defect pattern exists in the "refine other buckets" loop:
`buckets[j] = in_N; q.append(j)` re-enqueues the in_N part, and if that
bucket is later popped it re-emits those vertices — but that path only
double-emits when a bucket is refined while it is still pending, which is
less common. The remainder path is the one that fires on the failing case.

Also note: `_try_local_repair` returned None here (all six candidates fail
the (LB) check on the post-update graph, or the pre-update ordering was
already such that no candidate works), so the buggy fallback ran. The
`_is_valid_lexbfs` checker itself is a correct (LB) implementation, but it
is only used inside `_try_local_repair` — it is never applied to the output
of `_static_lexbfs`, so the malformed ordering is returned unchecked.

## REPAIR_HINTS

1. **Replace `_static_lexbfs` with the simple label-based LexBFS** (O(n^2)
   on the matrix, correctness-first). This eliminates the entire
   bucket/queue/remainder machinery and its double-emission bug:
   - `labels[v]` = tuple of already-selected neighbors of v (start empty).
   - Repeat n times: pick the unselected vertex with the lexicographically
     LARGEST label (tie-break: smallest id); append to order; for each
     remaining unselected u, if adj[v][u] then labels[u] += (v,).
   - This is trivially a permutation and is a valid LexBFS for any
     tie-break.

2. **Add a safety net in `init`, `insert_edge`, and `delete_edge`**: after
   computing any ordering (repair or recompute), assert
   `sorted(order) == list(range(n))` and `_is_valid_lexbfs(order, graph)`;
   if either fails, recompute with the label-based routine. This guards
   against any residual bug in the refinement code.

3. **Do NOT** try to patch the remainder-split block in place (e.g. by
   breaking out of the `enumerate(B)` loop after a split, or by tracking
   emitted vertices in a set). The bucket/remainder design conflates
   "vertices still to be emitted from B" with "buckets pending in the
   queue"; any local patch risks leaving the same conflation in the
   other-bucket refinement path. A rewrite to the label formulation is the
   minimal correct fix.

4. The `_try_local_repair` candidate set (original, swap, four moves) is
   sound in principle (it only returns an ordering certified by
   `_is_valid_lexbfs`), so it can be kept as the cheap path; the fallback
   just needs to be a correct recompute.

5. Approaches that will not work:
   - Keeping the partition-refinement code and only fixing the remainder
     double-emission: the other-bucket re-enqueue path has the same
     structural hazard, and the algorithm's correctness on general graphs
     has not been established by any trace in this lineage.
   - Relying on `_is_valid_lexbfs` to catch the malformed ordering: it
     would not even be a meaningful check on a non-permutation (it indexes
     by vertex id and would silently pass or misbehave); the permutation
     check must come first.
