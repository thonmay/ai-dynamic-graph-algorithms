## FAILURE_DESCRIPTION

n=3. Initial graph (before the update) is the path 0-1-2 (edges (0,1) and (1,2)); `init` produced the valid LexBFS ordering `[0, 1, 2]`. The failing operation is `insert (0, 2)` (sequence_idx 0), which makes the graph the triangle 0-1-2. The candidate returned `[0, 1, 2]`, but the verifier reports a (LB) violation at positions a=0, b=1, c=2 (vertices 0, 1, 2): ac=02 is an edge, ab=01 is an edge, and no d < a exists (minD = 1000000000 sentinel). Expected: any valid LexBFS ordering of the triangle, e.g. `[0, 2, 1]`.

## ROOT_CAUSE

The certificate `_is_valid_lexbfs` is wrong: it implements a different 4-point property than the one stated in the brief, so it accepts orderings that are not LexBFS.

The brief's property (the one the verifier checks) is: for all positions a < b < c with **ac in E and ab NOT in E**, there exists d < a with db in E and dc not in E.

The code instead checks (see `_is_valid_lexbfs`):

```python
for c in range(n):
    not_c = full ^ nbr[c]
    for b in range(c):
        if (nbr[b] >> c) & 1:
            continue  # bc in E: no constraint
        Aset = nbr[c] & ((1 << b) - 1)
        ...
        if ((nb & (low - 1)) & not_c) == 0:
            return False
```

i.e. it iterates over b < c with **bc NOT in E** and a < b with **ac in E**, and requires a d < a with db in E and dc not in E. The antecedent is "bc not in E" instead of "ab not in E". These are different properties.

Trace on the failing case (triangle, order [0,1,2], all pairs adjacent):
- c=2, b=1: bc = 1-2 is an edge, so the code `continue`s. The only a (a=0) is never examined.
- c=2, b=0: Aset = nbr[2] & 0 = 0, skipped.
- c=1, b=0: Aset = 0, skipped.
Result: `_is_valid_lexbfs` returns True for `[0,1,2]` on the triangle.

But the brief's property does fire: a=0, b=1, c=2 has ac=02 in E and ab=01 NOT in E (the verifier's check), and no d < 0 exists, so the ordering is invalid.

Consequence in `insert_edge`: the first guard `if _is_valid_lexbfs(graph, order): return state` passes on the stale ordering, so the function returns `[0,1,2]` unchanged. The local-repair and full-recompute fallbacks are never reached. (Note the fallback `_lexbfs_full` is also broken — it returns `[0,1,2]` on the triangle too, since it never splits the initial bucket — so even if the guard had failed, the fallback would not have fixed this case.)

## REPAIR_HINTS

1. Fix `_is_valid_lexbfs` to implement the brief's property exactly: iterate c outermost, then b < c, and for each a < b with **ac in E and ab NOT in E** (i.e. `a in nbr[c]` and `a not in nbr[b]`), require `(nbr[b] & ((1 << a) - 1)) & ~nbr[c] != 0`. Concretely, replace the `if (nbr[b] >> c) & 1: continue` / `Aset = nbr[c] & ((1 << b) - 1)` structure with: for each b < c, `Aset = nbr[c] & ~nbr[b] & ((1 << b) - 1)` and for each a in Aset check the d condition. This makes the certificate sound and complete (it characterizes LexBFS orderings), so the guard in `insert_edge`/`delete_edge` will correctly reject the stale ordering.

2. Fix `_lexbfs_full`: it never splits the initial bucket. The bug is that the split result is appended to `new_buckets` in the same relative order as the old buckets, so the "adjacent" part (which should come first, i.e. before the non-adjacent part of the same bucket) is not moved ahead of the other buckets. The standard HMPV algorithm keeps buckets in (label, insertion) order and, when splitting a bucket, inserts the adjacent part immediately before the non-adjacent part. Simplest robust fix: replace the body of `_lexbfs_full` with the label-based `_lexbfs_full2` (which is correct: it picks the lexicographically smallest label with smallest-id tie-break and appends the selected vertex to its unselected neighbors' labels — this is exactly LexBFS with a fixed tie-break, hence a valid LexBFS ordering).

3. Do NOT rely on `_try_local_repair` for correctness: its "move endpoint before earliest non-neighbor" heuristic is not guaranteed to find a valid ordering even when one exists, and its certification is only as good as `_is_valid_lexbfs`. Keep it as an optimization only after the certificate is fixed; the full-recompute fallback (with a correct static LexBFS) is what guarantees correctness.

4. Do not try to "fix" the failure by special-casing the triangle or by changing the expected output; the verifier's property is the brief's property, and the candidate's certificate must match it.
