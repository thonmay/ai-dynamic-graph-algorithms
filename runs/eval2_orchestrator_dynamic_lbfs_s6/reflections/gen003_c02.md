## FAILURE_DESCRIPTION
Operation: `init` (sequence_idx 0) on a 4-vertex undirected graph.
`init` returned ordering `[0, 1, 2, 3]`; the expected (valid) ordering is `[0, 1, 3, 2]`.
The verifier reports an (LB) 4-point violation at positions a=0, b=2, c=3 (pos_a=0, minD=1):
- va=order[0]=0, vb=order[2]=2, vc=order[3]=3
- ab not in E: 0-2 is a non-edge
- ac in E: 0-3 is an edge
- no d < a exists (a=0, so the d-range is empty)
So the certificate fails. The graph must be the 4-cycle 0-1-2-3-0 (edges {01,12,23,30}): on this graph the only valid LexBFS orderings are the two cyclic rotations of [0,1,2,3] with the two non-adjacent pairs (0,2) and (1,3) kept apart, e.g. [0,1,3,2].

## ROOT_CAUSE
The bug is in the static `_lexbfs` itself (used by `init` and by the fallback), not in the dynamic repair path. The label update appends the selected vertex in *selection order*:

```python
for u in unselected:
    if graph[best][u]:
        labels[u] = labels[u] + (best,)
```

and the selection rule is:

```python
if best is None or lab > best_label or (lab == best_label and v < best):
```

LexBFS labels are compared lexicographically with the **earlier-selected neighbor first** (the first differing entry decides; a shorter label that is a prefix of a longer one is smaller). Appending in selection order makes the *most recently* selected neighbor the last entry, so the comparison is effectively reversed: it prioritizes the most recent neighbor instead of the earliest one.

Trace on the 4-cycle (edges 01,12,23,30):
- Step 1: all labels `()`; tie-break smallest id -> select 0. Labels: 1=(0,), 3=(0,), 2=().
- Step 2: 1 and 3 tie at (0,) -> smallest id -> select 1. Labels: 2=(1,), 3=(0,1).
- Step 3: compare 2=(1,) vs 3=(0,1). Correct LexBFS: first entry 0 < 1, so 3 wins -> order [0,1,3,2] (valid). Buggy code: (1,) > (0,1) because 1 > 0 at the first entry -> selects 2 -> order [0,1,2,3] (invalid, the reported violation).

So the first divergence is at step 3 of `_lexbfs`; the returned ordering is not a LexBFS ordering, and `init` has no certificate check to catch it.

## REPAIR_HINTS
Smallest fix, in `_lexbfs`: make the lexicographic comparison use the earliest-selected neighbor as the most significant entry. Two equivalent options:
1. Prepend instead of append: `labels[u] = (best,) + labels[u]`. Then the existing `lab > best_label` comparison is correct (earliest neighbor first, prefix = smaller).
2. Keep appending, but compare reversed labels: `key = lab[::-1]` (or `tuple(reversed(lab))`) in the selection loop.

Either way, verify with the 4-cycle: step 3 must select 3 over 2, giving [0,1,3,2].

Additional hardening (recommended, cheap): after computing the order in `init` (and in the fallback recompute), assert `_is_lexbfs(graph, order, n)`; the certificate checker is already present and correct, so a failed assertion would have caught this immediately.

Approaches that will NOT work:
- Relying on `_local_repair` to fix the ordering: it is only called from `insert_edge`/`delete_edge`, never from `init`, and its windowed re-LexBFS calls the same buggy `_lexbfs`, so it inherits the same defect.
- Changing only the tie-break (smallest id): the tie-break is fine; the defect is in the label comparison direction, which matters even when labels differ (as in step 3 above).
