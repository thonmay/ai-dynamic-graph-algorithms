## FAILURE_DESCRIPTION

Failing case (sequence_idx 2, operation `delete (2, 1)` on a 4-vertex undirected graph):
- Result returned: `[0, 1, 3, 2]`
- Expected (one valid LexBFS): `[0, 1, 2, 3]`
- Violation reported by the checker: a=0, b=3, c=2, pos_a=0, minD=1.

Interpreting the violation in the (LB) 4-point property: in the returned
ordering, position a=0 holds vertex 0, position b=3 holds vertex 2, position
c=2 holds vertex 3. So the triple is (va, vb, vc) = (0, 2, 3) with
pos(0)=0 < pos(3)=2 < pos(2)=3. The property requires: if 0-2 is NOT an edge
and 0-3 IS an edge, then there must exist d < 0 (i.e. a vertex before
position 0) adjacent to 2 but not to 3. Since a=0 is the first position, no
such d exists, so the ordering is invalid.

Reconstructing the graph from the trace (see below): after the delete of
(2,1), the graph is
  E = {0-1, 0-2, 0-3, 1-3, 2-3}
  (i.e. K4 minus edge 1-2).
Valid LexBFS orderings include [0,1,2,3] and [0,1,3,2]... wait — actually
[0,1,3,2] is NOT valid on this graph, which is exactly the failure.

## ROOT_CAUSE

The bug is in `_static_lexbfs`: it selects the unselected vertex with the
lexicographically LARGEST label, but the label-based LexBFS formulation
requires selecting the vertex with the lexicographically SMALLEST label
(tie-break smallest id).

Responsible lines:
```python
        best = None
        for v in unselected:
            if best is None or labels[v] > labels[best] or (
                labels[v] == labels[best] and v < best
            ):
                best = v
```
The comparison `labels[v] > labels[best]` implements "largest label wins".

Trace on the post-delete graph E = {0-1, 0-2, 0-3, 1-3, 2-3}:
- Start: all labels = (). Tie-break smallest id -> pick 0.
  Labels of unselected: 1 -> (0,), 2 -> (0,), 3 -> (0,).
- All labels equal (0,). Tie-break smallest id -> pick 1.
  Update: 3 is a neighbor of 1 -> labels[3] = (0,1). 2 is not a neighbor of 1.
  Labels: 2 -> (0,), 3 -> (0,1).
- With LARGEST-label selection: (0,1) > (0,), so pick 3.
  Update: 2 is a neighbor of 3 -> labels[2] = (0,3).
- Pick 2.
- Result: [0, 1, 3, 2] — exactly the failing output.

With the correct SMALLEST-label selection, at step 3 (0,) < (0,1), so 2 is
picked, giving [0, 1, 2, 3] — the expected valid ordering.

Why the bug survived the safety net: `_ensure_valid` calls
`_is_valid_lexbfs`, which implements the (LB) 4-point property. The (LB)
property is a certificate for chordality, NOT a certificate that an ordering
is a LexBFS ordering. On the chordal graph K4 minus an edge, [0,1,3,2]
satisfies the 4-point property (the checker's violation is a property of the
expected-vs-actual comparison, and the checker's own 4-point check on
[0,1,3,2] for this graph: a=0 (v=0), b=3 (v=2), c=2 (v=3): 0-2 in E? Yes, so
the condition "ab not in E" is not triggered — actually the violation reported
uses a different reading). In any case, `_is_valid_lexbfs` does not detect
that [0,1,3,2] is not a LexBFS ordering, so `_ensure_valid` accepts the
wrong ordering from `_static_lexbfs` and never recomputes.

Two compounding defects:
1. `_static_lexbfs` uses the wrong comparison direction (largest instead of
   smallest label).
2. `_is_valid_lexbfs` / `_ensure_valid` is not a real LexBFS validity check
   (the 4-point property certifies chordality, not LexBFS-ness), so the
   safety net cannot catch the wrong ordering.

## REPAIR_HINTS

1. **Primary fix (code location: `_static_lexbfs`, the `best` selection loop):**
   Change the comparison from largest-label to smallest-label:
   ```python
   if best is None or labels[v] < labels[best] or (
       labels[v] == labels[best] and v < best
   ):
   ```
   This makes `_static_lexbfs` a correct static LexBFS (smallest label,
   tie-break smallest id). Since both the fallback in `insert_edge`/
   `delete_edge` and `init` call `_static_lexbfs`, fixing this one comparison
   fixes the static core.

2. **Do NOT rely on `_is_valid_lexbfs` (the 4-point check) as a LexBFS
   validity certificate.** The (LB) 4-point property characterizes chordal
   graphs, not LexBFS orderings. A permutation of a chordal graph can
   satisfy the 4-point property without being a LexBFS ordering. If a real
   validity check is needed, re-run the static LexBFS and compare, or
   implement the actual LexBFS certificate (e.g. verify the ordering is
   consistent with the label-refinement process). The simplest correct
   approach: after any update, just call the fixed `_static_lexbfs` and
   return its result (correctness first, per the research goal).

3. **Approaches that will not work:**
   - Keeping the largest-label selection and "fixing" the tie-break: the
     direction is fundamentally wrong; no tie-break change compensates.
   - Relying on `_ensure_valid` to catch bad orderings via the 4-point
     property: it cannot, because the property is not a LexBFS certificate.
   - The local-repair candidate set (swap / move-to-neighbor) is fine as an
     optimization but is irrelevant to this failure; the failure is in the
     static recompute path itself.
