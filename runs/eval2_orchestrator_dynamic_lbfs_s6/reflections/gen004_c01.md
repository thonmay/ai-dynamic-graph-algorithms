## FAILURE_DESCRIPTION

The candidate crashes at `init` (line 132) with `AssertionError: init produced invalid LexBFS order`. The static `_lexbfs` function produces an ordering that fails the `_is_lexbfs` (LB) 4-point certificate. The crash occurs on the very first call, before any dynamic update, so the bug is entirely in the static LexBFS implementation.

**Concrete failing example** (n=4, edges {0-1, 0-2, 1-3}):

The candidate's `_lexbfs` produces order `[0, 1, 3, 2]`. Checking the (LB) property:
- a=0 (v0), b=2 (v3): 0-3 not in E. c=3 (v2): 0-2 in E. Need d < 0 with d-3 in E and d-2 not in E. No d < 0 exists. **FAIL.**

A valid LexBFS ordering for this graph is `[0, 1, 2, 3]` (or `[0, 2, 1, 3]`, etc.).

## ROOT_CAUSE

The label-based LexBFS in `_lexbfs` uses the **wrong label convention**. The code does:

```python
labels[u] = (best,) + labels[u]   # PREPEND
```

and selects the vertex with the **lexicographically LARGEST** label:

```python
if best is None or lab > best_label or (lab == best_label and v < best):
```

This is the inverse of the correct LexBFS label convention. In standard label-based LexBFS (Habib-McConnell-Paul-Viennot), labels record the sequence of already-selected neighbors in **selection order** (earliest first), and at each step you pick the vertex with the **lexicographically SMALLEST** label. The correct update is:

```python
labels[u] = labels[u] + (best,)   # APPEND
```

with selection of the **smallest** label:

```python
if best is None or lab < best_label or (lab == best_label and v < best):
```

**Why the candidate's convention is wrong:** Prepending means the most-recently-selected neighbor appears first in the tuple. Comparing tuples lexicographically then prioritizes the most recent neighbor's identity over earlier ones. This inverts the intended priority: LexBFS should prefer vertices whose *earliest* selected neighbor is smallest (i.e., the vertex that was "discovered" earliest in the BFS sense). The candidate's "largest label wins" with prepend effectively prefers vertices whose most recent neighbor has the largest id, which is not a valid LexBFS tie-breaking rule.

**Trace on the failing example** (edges {0-1, 0-2, 1-3}):
1. All labels `()`. Pick 0 (smallest id). Labels: 1→(0,), 2→(0,).
2. Tie (0,)=(0,). Pick 1 (smallest id). Labels: 3→(1,) [prepend].
3. 2 has (0,), 3 has (1,). Candidate picks LARGEST → 3. **Wrong.** Correct would pick SMALLEST → 2.
4. Pick 2. Order = [0,1,3,2]. Invalid.

With the correct convention (append, smallest wins):
3. 2 has (0,), 3 has (1,). Pick SMALLEST → 2.
4. Pick 3. Order = [0,1,2,3]. Valid.
