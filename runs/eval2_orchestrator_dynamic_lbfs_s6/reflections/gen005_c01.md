# Reflection: gen005_c01

## FAILURE_DESCRIPTION

- **Case**: `graph_n = 4`, `sequence_idx = 0`, `operation = "crash"`.
- **Error**: `AssertionError` at line 133, i.e. the assertion inside `init()`:
  ```python
  def init(graph):
      n = len(graph)
      order = _lexbfs(graph, n)
      assert _is_lexbfs(graph, order, n)   # line 133 — FAILED
      return {'ordering': order, 'n': n}
  ```
- **Expected**: `init` returns a state whose `'ordering'` is a valid LexBFS
  ordering of the initial 4-vertex graph (passes the (LB) 4-point certificate).
- **Actual**: `_lexbfs(graph, 4)` produced an ordering that `_is_lexbfs`
  rejects, so the candidate crashes before any update is even processed.
  The failure is in the *static* core, not in the dynamic repair logic.

## ROOT_CAUSE

The static `_lexbfs` is not a correct LexBFS. Two independent defects:

1. **Wrong label semantics (the fatal one).** The docstring says
   "select the lexicographically LARGEST label (most already-selected
   neighbors)", but the code prepends the *most recently* selected neighbor:
   ```python
   for u in unselected:
       if graph[best][u]:
           labels[u] = (best,) + labels[u]   # newest neighbor first
   ```
   In LexBFS the label of a vertex must be the sequence of its already-selected
   neighbors **in the order they were selected** (oldest first), and the
   vertex with the lexicographically **smallest** such sequence is chosen next
   (equivalently: largest if you store newest-first, but then the comparison
   must be consistent with that storage). Here the storage is newest-first
   while the comparison `lab > best_label` treats the tuple as if it were
   oldest-first. The two conventions are mixed, so the selection rule no
   longer matches any valid LexBFS tie-breaking. On a 4-vertex graph this
   produces an ordering that violates the (LB) 4-point property, which the
   (correct) `_is_lexbfs` checker then catches.

2. **Wrong tie-break.** `tie-break smallest id` is applied to the *vertex id*,
   not to the position in the current ordering. LexBFS tie-breaking must be
   consistent with a fixed total order on vertices (e.g. smallest id is fine
   *as a vertex order*), but combined with defect 1 it compounds the error.
   Note: any fixed vertex-id tie-break is legal for "any valid LexBFS", so
   this alone is not fatal — defect 1 is.

The `_is_lexbfs` checker itself is a faithful implementation of the (LB)
4-point property and is not the problem; it correctly rejects the bad
ordering.

## REPAIR_HINTS

Smallest concrete fix, in `_lexbfs`:

1. **Make label storage and comparison consistent.** Pick ONE convention:
   - *Option A (recommended, matches the docstring's "oldest first" intent):*
     append the newly selected neighbor to the END of the label
     (`labels[u] = labels[u] + (best,)`) and select the lexicographically
     **SMALLEST** label (`lab < best_label`), tie-break smallest vertex id.
   - *Option B:* keep prepending (newest first) but select the
     lexicographically **LARGEST** label. This also works, but the docstring
     and comments must be updated to avoid future confusion.
   Either way, the storage order and the comparison direction must agree.

2. **Verify with the existing checker.** After the fix, `init`'s
   `assert _is_lexbfs(graph, order, n)` should pass on all 4-vertex graphs.
   Keep the assertion (or a debug-mode check) as a safety net.

3. **Do NOT** try to "fix" this by weakening `_is_lexbfs` or by skipping the
   assertion — the checker is correct and the static routine is what must
   change.

4. **Do NOT** attempt to patch the dynamic repair path (`_local_repair`)
   first: the crash happens in `init` before any update, so the repair logic
   is never reached. Fix the static core, then re-test the dynamic path.

5. Once `_lexbfs` is correct, the fallback in `insert_edge`/`delete_edge`
   (full recompute + assert) is already sound, so full correctness is
   restored. The local-repair heuristic can remain as an optimization, but
   it must still be gated by `_is_lexbfs` (which it already is).
