## FAILURE_DESCRIPTION

After `init` on a 4-vertex graph, the update `insert (1, 3)` is applied. The
candidate returned ordering `[0, 1, 2, 3]`, but the verifier reports it is not
a valid LexBFS ordering of the post-update graph. The reported violation is
`(a, b, c, pos_a, minD) = (0, 1, 2, 0, 3)`, i.e. in the returned order
`a=order[0]=0`, `b=order[1]=1`, `c=order[2]=2` with `a-c` an edge, `a-b` not
an edge, and no earlier `d` (there is none, `pos_a=0`) with `d-b` an edge and
`d-c` not an edge. The expected valid ordering for the same graph is
`[0, 2, 3, 1]`.

## ROOT_CAUSE

The bug is in `_lexbfs`: it is not a correct partition-refinement LexBFS.
The key for a vertex `v` in the current bucket is computed as

```python
keys.append(tuple(x for x in order if graph[x][v]))
```

i.e. the tuple of *already-ordered* neighbours of `v`. This is the wrong
refinement key. In partition-refinement LexBFS (Habib–McConnell–Paul–Viennot),
a bucket is refined by the adjacency of its members to the *most recently
processed* vertex (or, equivalently, the buckets are maintained so that
within a bucket all vertices have identical adjacency to every already
processed vertex, and each step splits the front bucket by adjacency to the
last selected vertex). Using the full tuple of earlier neighbours as a sort
key and then taking the *lexicographically smallest* tuple as the next vertex
does not reproduce LexBFS semantics: it is a different (non-LexBFS) ordering
scheme.

Concretely, on the failing case the hint order is the previous state's
ordering. `_lexbfs` with that hint produces `[0, 1, 2, 3]`. Then
`_is_valid_lexbfs` is supposed to catch the invalidity, but it does not:
the 4-point check as written is also buggy. In `_is_valid_lexbfs`, the
condition `if graph[a][b]: continue` skips the case where `a-b` IS an edge,
but the (LB) property requires the witness `d` for the case `a-b` NOT in E
and `a-c` in E — that part is handled. However the real problem is that the
check iterates `for l in range(i)` for `d`, which is correct, but the
candidate's `_lexbfs` output `[0,1,2,3]` apparently *passes* this check on
the post-update graph (otherwise `_find_valid_ordering` would have tried
other starts and found `[0,2,3,1]`). So either the check has a subtle bug
that lets an invalid order through, or the check is correct and the
algorithm's output is genuinely invalid but the check missed it.

Tracing the check on order `[0,1,2,3]` with the post-update graph (which
must contain edge `0-2` and not edge `0-1`, per the violation):
- `i=0, a=0`: `j=1, b=1`: `graph[0][1]=0` (not an edge, so not skipped).
  `k=2, c=2`: `graph[0][2]=1` (edge). Need `d` in `range(0)` — empty.
  `found=False` → should return `False`.

So `_is_valid_lexbfs` SHOULD have rejected `[0,1,2,3]`. The fact that the
final result is `[0,1,2,3]` means the check did NOT reject it, which implies
the graph passed to the check differs from what the verifier sees — i.e.
**the `graph` argument to `insert_edge` is the pre-update matrix** (the
update is applied by the harness *after* the call, or the candidate is
expected to apply it). If `insert_edge` receives the graph *before* the edge
is flipped, then `_lexbfs` and `_is_valid_lexbfs` run on the old graph,
where `[0,1,2,3]` may be valid, and the returned ordering is then checked by
the verifier against the *new* graph, where it is invalid.

This is the root cause: **the candidate does not apply the edge update to
the graph before recomputing.** The interface passes `graph` and `edge`;
the candidate assumes `graph` already reflects the update, but the failing
case shows the returned ordering is invalid on the post-update graph while
valid on the pre-update graph. The fix is to flip `graph[edge[0]][edge[1]]`
and `graph[edge[1]][edge[0]]` (set to 1 in `insert_edge`, 0 in
`delete_edge`) before running `_find_valid_ordering`.

## REPAIR_HINTS

1. In `insert_edge`, before calling `_find_valid_ordering`, set
   `graph[edge[0]][edge[1]] = 1` and `graph[edge[1]][edge[0]] = 1`.
   In `delete_edge`, set both to `0`. This ensures the recomputation and
   the validity check run on the post-update graph.
2. Alternatively, if the harness guarantees `graph` is already updated,
   then the bug is in `_lexbfs` itself (the refinement key is not
   partition-refinement LexBFS). In that case, replace `_lexbfs` with a
   correct partition-refinement LexBFS: maintain a queue of buckets; when
   processing a bucket, split it by adjacency to the *last selected*
   vertex only (not the full tuple of earlier neighbours), put the
   non-adjacent part at the front of the queue, and select the first
   vertex of the adjacent part. The current "sort by full neighbour
   tuple" approach is not LexBFS and will produce invalid orderings even
   when the graph is correct.
3. Do NOT rely on `_is_valid_lexbfs` as a safety net for a broken
   `_lexbfs`; fix the algorithm itself. The 4-point check is O(n^4) and
   the retry loop over start vertices is O(n) extra, making the whole
   thing O(n^5) per update — acceptable for correctness but not for
   performance.
4. The `order_hint` mechanism (using the previous ordering as tie-break)
   is fine for performance but does not affect correctness as long as
   `_lexbfs` is a valid LexBFS algorithm.
