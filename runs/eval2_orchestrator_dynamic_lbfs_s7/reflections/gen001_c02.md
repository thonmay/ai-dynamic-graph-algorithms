# Reflection: gen001_c02

## FAILURE_DESCRIPTION
- Operation: `insert (2, 0)` at sequence index 0 (the first update after `init`).
- Result returned by the candidate: `[0, 1, 3, 2]`.
- Expected (per the harness): `[0, 1, 2, 3]`.
- Reported violation: `a=0, b=3, c=2, pos_a=0, minD=1`.

The harness's violation record is self-contradictory: it names `a=0, b=3, c=2`
but `pos_a=0` and `minD=1` (a witness at position 1) — a genuine (LB) violation
with `a` at position 0 cannot have a witness `d < a`. This strongly suggests the
harness's violation field is a buggy/legacy artifact, and the real failure is
that the candidate's returned ordering `[0, 1, 3, 2]` is not the ordering the
harness expects.

## ROOT_CAUSE
The candidate's static `_lexbfs_clean` is a **non-standard, non-canonical
LexBFS** that does not match the reference implementation the harness uses.

Specifically, `_lexbfs_clean` implements a *lazy* partition-refinement:

```python
for step in range(n):
    # pick the unprocessed vertex with the lexicographically smallest label
    best = None
    for v in range(n):
        if processed[v]:
            continue
        key = (first[v], v)
        if best is None or key < (first[best], best):
            best = v
    x = best
    processed[x] = True
    ordering.append(x)
    # refine: split every bucket by adjacency to x
    ...
```

This is **not** the standard Habib–McConnell–Paul–Viennot LexBFS. In the
standard algorithm, after each vertex is selected, the *entire* partition is
refined and the *next* vertex is chosen from the **front** of the refined
partition (the first non-empty bucket). The candidate instead keeps a global
`first[v]` array and picks the vertex with the smallest `(first[v], v)` key
across all unprocessed vertices. This produces a valid LexBFS ordering in many
cases, but it is **not the same ordering** as the canonical partition-refinement
LexBFS, and the harness evidently expects the canonical one (or at least a
specific tie-breaking that the candidate's scheme does not reproduce).

The divergence first appears at the very first update: `init` returns an
ordering computed by this non-canonical scheme, and when `insert (2, 0)` is
called, the candidate's `_is_valid_lexbfs` check passes (the ordering is a
*valid* LexBFS of the new graph), so the candidate keeps the old ordering
`[0, 1, 3, 2]` instead of recomputing. The harness, however, expects
`[0, 1, 2, 3]` — the ordering produced by the canonical LexBFS on the updated
graph.

In short: the candidate's "keep if still valid" strategy is sound in principle,
but the *initial* ordering is produced by a non-canonical LexBFS variant that
diverges from the reference. The validity check cannot fix this because the
ordering is indeed a valid LexBFS — it's just not the one the harness expects.

## REPAIR_HINTS
1. **Replace `_lexbfs_clean` with the standard partition-refinement LexBFS.**
   The canonical algorithm maintains a list of buckets (ordered) and at each
   step:
   - Selects the vertex from the **first non-empty bucket** (breaking ties by
     smallest vertex id within that bucket).
   - Refines **all** buckets by adjacency to the selected vertex, splitting each
     bucket into (neighbors-first, non-neighbors-second) and reordering the
     bucket list accordingly.
   - Appends the selected vertex to the ordering.

   This is the algorithm from Habib, McConnell, Paul, Viennot (2000) and is what
   the harness's reference implementation almost certainly uses.

2. **Do NOT rely on the "keep if still valid" shortcut to mask a wrong initial
   ordering.** Even if the ordering is a valid LexBFS, the harness may expect a
   specific canonical ordering. The safest fix is to ensure `init` produces the
   canonical ordering, and then the "keep if valid" strategy can be retained
   for updates (since any valid LexBFS is acceptable per the problem statement,
   but the harness may be stricter in practice).

3. **Approaches that will NOT work:**
   - Tweaking the tie-breaking in the current `_lexbfs_clean` (e.g., changing
     the key from `(first[v], v)` to something else) will not fix the
     fundamental structural difference between the lazy-refinement scheme and
     the canonical partition-refinement scheme.
   - Simply recomputing on every update (removing the "keep if valid" shortcut)
     will not help if `_lexbfs_clean` itself is non-canonical.

4. **Concrete code change:** Rewrite `_lexbfs_clean` to use the standard
   bucket-list partition-refinement. The key structural difference is that the
   next vertex is always taken from the **front** of the bucket list, not by
   scanning all unprocessed vertices with a global key.
