## FAILURE_DESCRIPTION

- Graph: n=3, initial graph has no edge (0,1) and no edge (0,2) (only possible edge is (1,2) or none).
- Operation: insert (0,1) at sequence_idx=0.
- Final graph: only edge (0,1).
- Expected LexBFS: [0,1,2] (start 0, N(0)={1}, pick 1, then 2).
- Actual result: [0,2,1].
- Violation: (a=0@pos0, b=2@pos1, c=1@pos2): ac=(0,1)∈E, ab=(0,2)∉E, no d<pos0 exists → 4-point property violated.

## ROOT_CAUSE

The bitset masks in `_verify` and `_try_local_repair` conflate **positions in the ordering** with **vertex IDs**. The adjacency bitmask `adj[x]` has bit i set iff vertex i is a neighbor of x (indexed by vertex ID). But the masks are built from **position** indices:

In `_verify` (and identically in `_try_local_repair`):
```python
C = A & ~((1 << (pb + 1)) - 1)   # "neighbors of a at positions > pb"
W = adj[b] & ((1 << pa) - 1)     # "neighbors of b at positions < pa"
```

`~((1 << (pb+1)) - 1)` clears bits 0..pb, i.e., **vertex IDs** 0..pb. But we want to clear **positions** 0..pb, which correspond to vertices `order[0], order[1], ..., order[pb]`. These are the same only when the ordering is the identity permutation.

**Trace on the failing case** (order=[0,2,1], adj[0]=2 meaning vertex 1 is a neighbor of 0):
- pa=0, a=0, A=2 (bit 1 set = vertex 1 is neighbor).
- pb=1, b=order[1]=2. ab=(0,2) not in E.
- C should be {neighbors of 0 at positions > 1} = {vertex at pos 2 = vertex 1} = {1}.
- Code computes: C = 2 & ~((1<<2)-1) = 2 & ~3 = 2 & ...11111100 = **0**.
- Vertex 1 (bit 1) is masked out because bit 1 ≤ pb=1, but vertex 1 is at **position 2**, not position 1.
- C=0 → no constraint checked → `_verify` returns True for the invalid ordering [0,2,1].

The same bug affects `W = adj[b] & ((1 << pa) - 1)`: it selects neighbors with vertex ID < pa instead of neighbors at positions < pa.

This bug is invisible when the ordering is the identity permutation [0,1,...,n-1], which is why it didn't trigger on simpler test cases.

## REPAIR_HINTS

The fix requires building position-based masks from the ordering, not from raw position indices. Two approaches:

**Approach 1 (correct, moderate cost):** Precompute a position-to-vertex mapping and build masks explicitly. For each position p, the set of vertices at positions ≤ p is `{order[0], ..., order[p]}`. Build the bitmask by OR-ing `(1 << order[i])` for i in range(p+1). This is O(n) per mask, making `_verify` O(n^4) worst case — acceptable for a verifier but not for the hot repair loop.

**Approach 2 (correct, efficient):** Maintain a `pos` array (vertex → position) and, for each vertex x, precompute `prefix_mask[x]` = bitmask of all vertices at positions < pos[x]. Then:
- "neighbors of a at positions > pb" = `adj[a] & ~prefix_mask_at_pos[pb]` where `prefix_mask_at_pos[pb]` = bitmask of {order[0],...,order[pb]}.
- "neighbors of b at positions < pa" = `adj[b] & prefix_mask_at_pos[pa-1]`.

Build `prefix_mask_at_pos` as an array of length n: `prefix_mask_at_pos[p] = prefix_mask_at_pos[p-1] | (1 << order[p])`. This is O(n) to build, O(1) per query.

**Specific code locations to fix:**
1. `_verify`: lines computing `C` and `W` — replace position-index-based masks with ordering-based masks.
2. `_try_local_repair`: the same `C` and `W` computations in the violation-detection loop — same fix.
3. After any `order.remove(b); order.insert(pa, b)` in the repair loop, the `pos` array and any precomputed prefix masks must be updated.

**Approaches that will NOT work:**
- Simply swapping the mask to use vertex IDs consistently: the 4-point property is defined over positions, so the masks must be position-based.
- Using `(1 << (pb+1)) - 1` with a different shift: the fundamental issue is that bit position ≠ vertex ID when the ordering is not the identity. Any mask built from raw position indices without referencing `order[]` will be wrong for non-identity orderings.
- Relying on the fallback recompute: the fallback only triggers when `_verify` returns False, but `_verify` is the buggy component — it returns True for invalid orderings, so the fallback never fires.
