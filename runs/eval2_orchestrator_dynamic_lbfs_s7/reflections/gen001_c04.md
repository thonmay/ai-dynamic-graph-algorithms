# Reflection: gen001_c04 (dynamic_lbfs)

## FAILURE_DESCRIPTION

Failing case: `sequence_idx: 0`, operation `insert (0, 1)` on a 4-vertex graph.
After the update the candidate returned ordering `[0, 1, 2, 3]`; the expected
(valid) ordering is `[0, 1, 3, 2]`. The checker reports the (LB) 4-point
violation at positions `a=0, b=2, c=3` (vertices 0, 2, 3): edge (0,3) is in E,
edge (0,2) is not, and there is no `d < a` (a is position 0, so no d exists at
all) with `db in E and dc not in E`. `minD = 1000000000` is the sentinel for
"no witness found".

Reconstructed post-update graph (consistent with the violation and the
expected ordering): edges (0,1), (0,3), (1,2), (1,3). In this graph:
- `[0,1,3,2]` is a valid LexBFS ordering (start 0; labels after 0: 1->{0},
  3->{0}, 2->{}; after 1: 3->{0,1}, 2->{1}; order 0,1,3,2).
- `[0,1,2,3]` is NOT a LexBFS ordering: after 0 and 1, vertex 3 has label
  {0,1} and vertex 2 has label {1}, so 3 must precede 2.

## ROOT_CAUSE

The static `_lexbfs_from` is a correct partition-refinement LexBFS, but the
candidate's "safety net" `_try_all_starts` is broken, so an invalid ordering
from one start can be returned as the final answer.

The bug is in `_check_lb` (the (LB) 4-point checker):

```python
for a in range(n):
    va = ordering[a]
    for b in range(a + 1, n):
        vb = ordering[b]
        if graph[va][vb]:
            continue  # ab in E, skip
        for c in range(b + 1, n):
            vc = ordering[c]
            if not graph[va][vc]:
                continue  # ac not in E, skip
            # Need d < a with db in E and dc not in E
            found = False
            for d in range(a):
                ...
            if not found:
                return False
```

The inner `for d in range(a)` loop is EMPTY when `a == 0`, so `found` stays
`False` and the function returns `False` for ANY triple with `a == 0` where
`ab not in E` and `ac in E` — even when the (LB) property is actually
satisfied. The (LB) property is a universal statement: for a = 0 the
witness set `d < a` is empty, so the property is vacuously satisfied for
every triple with a = 0. The checker must treat `a == 0` as "no witness
needed" (i.e., `continue` / `found = True`), not as a failure.

Consequence on the failing case: for the invalid ordering `[0,1,2,3]` on the
post-update graph, the only genuine (LB) violation is at a=0 (b=2, c=3), and
`_check_lb` happens to flag it — but it flags it for the WRONG reason (empty
d-loop, not a real missing witness). More importantly, for the VALID ordering
`[0,1,3,2]` (start 0), `_check_lb` also returns `False`: take a=0, b=2
(vertex 3), c=3 (vertex 2): ab = (0,3) is in E, so that triple is skipped;
but a=0, b=1 (vertex 2), c=2 (vertex 3): ab = (0,2) not in E, ac = (0,3) in
E, d-loop empty -> `return False`. So `_check_lb` rejects the valid ordering
too.

Because `_check_lb` rejects every ordering that has any (a=0, b, c) triple
with ab not in E and ac in E, `_try_all_starts` finds NO start whose ordering
passes the check on this graph, and falls through to the fallback:

```python
    # Fallback: return the first one (should not happen for valid graphs)
    return _lexbfs_from(graph, 0)
```

which returns the raw (invalid) output of `_lexbfs_from(graph, 0)` =
`[0, 1, 2, 3]`. That is exactly the reported result.

Note: the fallback is only reached because the checker is unsound in the
`a == 0` case. If `_check_lb` were correct, `_try_all_starts` would accept
the valid ordering from start 0 (or another start) and never hit the
fallback.

## REPAIR_HINTS

1. Fix `_check_lb` to handle `a == 0` correctly: when `a == 0`, the (LB)
   property is vacuously satisfied for that triple, so `continue` (or set
   `found = True`) instead of falling into the empty `for d in range(a)`
   loop and returning `False`. Concretely, replace:

   ```python
   found = False
   for d in range(a):
       vd = ordering[d]
       if graph[vd][vb] and not graph[vd][vc]:
           found = True
           break
   if not found:
       return False
   ```

   with:

   ```python
   if a == 0:
       continue  # no d < 0 exists; (LB) is vacuously satisfied
   for d in range(a):
       vd = ordering[d]
       if graph[vd][vb] and not graph[vd][vc]:
           break
   else:
       return False
   ```

   (or equivalently `found = (a == 0)` before the loop).

2. After fixing the checker, `_try_all_starts` will accept a valid ordering
   for this graph (e.g., start 0 gives `[0,1,3,2]`), so the fallback will not
   be reached on this case.

3. Do NOT rely on the fallback `return _lexbfs_from(graph, 0)` as a
   correctness mechanism — it returns an unvalidated ordering. If a graph
   ever has no valid LexBFS ordering (impossible for simple undirected
   graphs, but the code should not silently return garbage), the fallback
   should at least assert or raise, not return an unchecked ordering.

4. Approaches that will NOT work:
   - Changing the tie-break or start order in `_lexbfs_from` does not fix
     the bug; the static algorithm is already correct, the checker is not.
   - Adding more starts to `_try_all_starts` does not help, because
     `_check_lb` rejects all of them on this graph.
   - Caching or incremental updates are irrelevant to this failure; the
     failure is purely in the validation/fallback path.
