## FAILURE_DESCRIPTION
4-vertex undirected graph. After `init` the state ordering was `[0, 1, 2, 3]` (valid for the pre-update graph). The update is `insert (1, 3)`. The candidate returned `[0, 1, 2, 3]` as the new ordering, but this is NOT a valid LexBFS ordering of the post-insertion graph. The verifier reports the 4-point (LB) violation at positions a=0, b=1, c=2 (pos_a=0, minD=3): in the ordering, a=0 is at position 0, b=1 at position 1, c=2 at position 2; edge (0,2) is present, edge (0,1) is absent, and no earlier vertex d (none exists, since a is at position 0) can witness the property. The expected valid ordering was `[0, 2, 3, 1]`.

## ROOT_CAUSE
The `_lexbfs` function is NOT a correct LexBFS implementation. It uses a single "last" vertex to refine only the front bucket, which is the wrong algorithm.

Correct LexBFS (Habib-McConnell-Paul-Viennot) maintains a partition of unprocessed vertices into buckets. When a vertex `v` is selected, **every** bucket in the partition must be refined by adjacency to `v`: each bucket is split into (adjacent-to-v part, non-adjacent-to-v part), with the adjacent part placed before the non-adjacent part. The candidate instead only refines the **front** bucket by adjacency to the single most recently selected vertex `last`, and leaves all other buckets untouched.

The responsible lines in `_lexbfs`:
```python
b = buckets.pop(0)
# Split b by adjacency to the most recently selected vertex.
...
nb = [v for v in b if graph[last][v]]
nnb = [v for v in b if not graph[last][v]]
```
Only the front bucket `b` is split, and only by `last`. The remaining buckets in `buckets` are never refined by `last` (or by any previously selected vertex). This means the partition does not reflect the full adjacency history required by LexBFS, so the resulting order can violate the 4-point property.

The `_is_valid_lexbfs` checker correctly detects the violation, but `_find_valid_ordering`'s fallback loop (trying each vertex as start) also calls the same broken `_lexbfs`, so no alternative start rescues it. The final fallback `_lexbfs(graph, n)` (natural order hint) is also broken.

## REPAIR_HINTS
1. **Fix `_lexbfs` to be a correct LexBFS implementation.** The correct algorithm maintains a list of buckets (partition of unprocessed vertices). When a vertex `v` is selected from the front bucket, **every** bucket in the partition must be refined by adjacency to `v`: each bucket is split into (adjacent-to-v part, non-adjacent-to-v part), with the adjacent part placed before the non-adjacent part. The front bucket's adjacent part becomes the new front. This is the Habib-McConnell-Paul-Viennot algorithm. The current code only refines the front bucket by `last`, which is incorrect.

2. **Do not rely on the checker to catch algorithmic errors.** The `_is_valid_lexbfs` checker is O(n^4) and is used as a fallback, but if the core algorithm is wrong, the checker may not catch all invalid orders (or the fallback loop may not find a valid one). Fix the algorithm first.

3. **The `order_hint` mechanism is fine** as a tie-break for bucket ordering, but it must be applied to a correct LexBFS refinement, not the broken single-vertex refinement.

4. **Approaches that will not work:** Simply trying different start vertices with the broken `_lexbfs` will not fix the issue, because the algorithm is wrong regardless of start vertex. The fallback to natural order is also broken.
