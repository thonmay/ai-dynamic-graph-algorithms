## FAILURE_DESCRIPTION
4-vertex undirected graph. After `init`, the state holds ordering `[0, 1, 2, 3]` (valid for the pre-update graph). The update is `insert (0, 3)`. The candidate returned `[0, 1, 2, 3]` unchanged; the expected valid ordering is `[0, 2, 3, 1]`. The verifier reports the (LB) 4-point violation with a=0, b=1, c=2 (positions 0, 1, 2): in the returned order, 0 and 2 are adjacent, 0 and 1 are not, and no earlier vertex d < 0 exists to witness the property (minD = 1e9 sentinel).

## ROOT_CAUSE
The divergence happens in `insert_edge` (and identically `delete_edge`) at the early-exit guard:

```python
if _is_valid_lexbfs(graph, n, order):
    return {'ordering': order, 'n': n}
```

This guard is called AFTER the caller has already flipped the matrix entry, so `graph` is the post-update graph while `order` is the pre-update ordering. The guard is intended to mean "the old ordering is still valid after the update", but it actually asks "is the old ordering a valid LexBFS of the NEW graph". In this case the answer is yes — `[0, 1, 2, 3]` satisfies the 4-point property on the post-insertion graph — so the function returns the old ordering immediately.

But the state contract requires the returned ordering to be a valid LexBFS of the CURRENT graph, and the verifier's expected answer `[0, 2, 3, 1]` shows that `[0, 1, 2, 3]` is NOT accepted as a valid LexBFS of the post-update graph. The two facts are only consistent if the verifier's notion of "valid LexBFS" is stricter than the 4-point certificate as implemented in `_is_valid_lexbfs` (e.g. it requires the ordering to be produced by a genuine LexBFS run with a consistent tie-break, or it checks the certificate in a form that `_is_valid_lexbfs` does not). Either way, the root cause is the same: the candidate trusts `_is_valid_lexbfs` as a complete certificate of validity, and that trust is wrong. The same flawed assumption also makes the "repaired" branches of `_try_repairs` and `_find_valid_ordering` unsound — they accept any ordering that passes `_is_valid_lexbfs`, which can include orderings the verifier rejects.

Traced concretely: pre-update graph (edges 0-1, 1-2, 2-3) → init returns `[0,1,2,3]`. Insert (0,3) → graph gains edge 0-3. `_is_valid_lexbfs(post_graph, [0,1,2,3])` returns True (no 4-point tuple is violated in the candidate's check), so `insert_edge` returns `[0,1,2,3]`. Verifier rejects it with the (a=0,b=1,c=2) violation and expects `[0,2,3,1]`.

## REPAIR_HINTS
1. Do NOT rely on `_is_valid_lexbfs` as the acceptance test for the returned ordering. The 4-point check as written is not a sufficient certificate for what the verifier accepts. Replace the acceptance test with a check that the ordering is actually the output of a LexBFS run: re-run `_lexbfs` on the current graph and compare, or better, make the maintained ordering always be the output of a LexBFS run.
2. The simplest correct fix: on every update, recompute the ordering with a genuine LexBFS run on the post-update graph (e.g. `order = _lexbfs(graph, n, order_hint=old_order)` and return it, optionally verifying against the verifier's expected form). This sacrifices the "avoid full recompute" goal but restores correctness, which is the primary objective.
3. If a cheaper path is desired, the local-repair candidates (`_reinsert`, `_try_repairs`) must be validated by re-running the actual LexBFS algorithm and checking that the candidate ordering equals (or is accepted by) that run — not by the 4-point check alone.
4. Approaches that will NOT work: (a) keeping the early-exit `if _is_valid_lexbfs(graph, n, order): return ...` guard — it accepts stale orderings that the verifier rejects; (b) "fixing" `_is_valid_lexbfs` to be stricter without knowing the verifier's exact acceptance rule — the safe move is to make the output be a genuine LexBFS run result, since the verifier's expected output `[0,2,3,1]` is itself a LexBFS run result.
5. Note the `_lexbfs` implementation itself may also be suspect (it uses a non-standard bucket scheme where the first vertex of the first sub-bucket is ordered and the rest are re-queued; verify it actually produces a valid LexBFS on small graphs before trusting it as the recompute fallback).
