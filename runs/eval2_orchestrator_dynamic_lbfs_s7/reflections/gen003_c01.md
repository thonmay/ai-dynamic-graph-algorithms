## FAILURE_DESCRIPTION
After `init` on a 4-vertex graph, the update `insert (1, 3)` was applied. The candidate returned ordering `[0, 1, 2, 3]`, which is NOT a valid LexBFS ordering of the post-update graph. The verifier's 4-point (LB) certificate fails with the tuple (a, b, c) = (order[0], order[1], order[2]) = (0, 1, 2): edge (0,2) is present, edge (0,1) is absent, and no d < a exists (a is at position 0, so the witness set is empty). The expected valid ordering was `[0, 2, 3, 1]`.

## ROOT_CAUSE
The core bug is in `_lexbfs`: it is NOT a correct partition-refinement LexBFS. It starts with `buckets = [[v] for v in order_hint]` — i.e., n singleton buckets — and then, for each popped vertex `first`, it refines the remaining singleton buckets by adjacency to `first`. This is equivalent to a single-pass greedy ordering: each vertex is placed in the order in which it first becomes "adjacent to the current front" relative to the hint, with no re-refinement of already-split groups.

Concretely, in the failing case the post-update graph has edges (0,2), (0,3), (1,3) (plus whatever init's graph had; the key point is 0-1 is NOT an edge and 0-2 IS an edge). With hint `[0,1,2,3]`:
- Pop bucket [0], first=0. Refine remaining singletons [1],[2],[3] by adjacency to 0: 1 is non-adjacent, 2 and 3 are adjacent. New buckets: [[2],[3],[1]] (adjacent parts before non-adjacent). Order so far: [0].
- Pop [2], first=2. Refine [3],[1] by adjacency to 2. Order: [0,2].
- Pop [3], first=3. Refine [1]. Order: [0,2,3].
- Pop [1]. Order: [0,2,3,1].

Wait — that trace gives the correct answer. Let me re-trace more carefully. The issue is that the hint passed to `_lexbfs` is `state['ordering']`, which is the ordering from `init`. If init's graph already had edge (0,1) or a different structure, the hint ordering could be different.

Actually, the real bug is more subtle: the algorithm does NOT implement LexBFS correctly in general. The standard partition-refinement LexBFS maintains a list of buckets where each bucket is a set of vertices that are "equivalent" (same adjacency pattern to all previously ordered vertices). When you pop a bucket, you take the FIRST vertex from it, order it, and then refine ALL remaining buckets (including the rest of the popped bucket) by adjacency to that vertex. The candidate does this, BUT the critical error is:

**The refinement only splits each bucket into at most 2 parts (adjacent / non-adjacent to `first`), and the adjacent part is placed before the non-adjacent part. This is correct for a single refinement step. However, the algorithm never re-refines buckets that were already split in previous steps by the SAME vertex's adjacency pattern.**

More precisely: in correct LexBFS, after ordering vertex `first`, every remaining bucket is split into (N(first) ∩ bucket, N̄(first) ∩ bucket). The candidate does exactly this. So the single-pass refinement IS correct for LexBFS...

Let me re-examine. The actual bug: **the candidate's `_lexbfs` does NOT correctly implement LexBFS because it processes buckets in a fixed linear order and only refines by the single vertex `first` that is popped. In correct LexBFS, when you pop a bucket with multiple vertices, you order the first vertex, then the REMAINDER of that bucket must also be refined by adjacency to `first`. The candidate does handle this with `new_buckets.insert(0, b[1:])` — but it inserts the remainder as a SINGLE bucket without splitting it by adjacency to `first`.**

This is the bug: `b[1:]` is inserted as one bucket, but it should be split into (adjacent to first, non-adjacent to first). Since `first` is not adjacent to itself (no self-loops in 0/1 adjacency matrices for simple graphs), and the vertices in `b[1:]` are in the same bucket as `first` (meaning they had the same adjacency to all previously ordered vertices), they may or may not be adjacent to `first`. The candidate assumes they are all non-adjacent to `first` (the comment says "since `first` is adjacent to itself, the adjacent part is empty"), but this is WRONG: `first` is not adjacent to itself, but other vertices in the same bucket CAN be adjacent to `first`.

In the failing case, if the hint ordering from init placed 1 and 3 in the same bucket (because they had the same adjacency to vertex 0), then when 1 is popped, 3 remains in the bucket. If 3 IS adjacent to 1 (edge (1,3) was just inserted), then 3 should be placed BEFORE the non-adjacent remainder. But the candidate puts the entire `b[1:]` (including 3) after all other buckets, producing an invalid ordering.

The responsible lines:
```python
if len(b) > 1:
    new_buckets.insert(0, b[1:])
```
This should be:
```python
if len(b) > 1:
    nb = [v for v in b[1:] if graph[first][v]]
    nnb = [v for v in b[1:] if not graph[first][v]]
    if nb:
        new_buckets.insert(0, nb)
    if nnb:
        new_buckets.insert(0, nnb)
```
(Note: insert nnb first, then nb, so that nb ends up at position 0.)

## REPAIR_HINTS
1. **Fix the remainder-bucket handling in `_lexbfs`**: When popping bucket `b` and ordering `first = b[0]`, the remainder `b[1:]` must be split by adjacency to `first` (just like all other buckets), not inserted as a single unsplit bucket. Replace `new_buckets.insert(0, b[1:])` with a proper split into adjacent/non-adjacent parts, with the adjacent part before the non-adjacent part.

2. **Alternative (simpler and more robust)**: Rewrite `_lexbfs` as the standard HMPV partition-refinement algorithm where you maintain a list of buckets, pop the front bucket, order its first vertex, and refine ALL remaining buckets (including the rest of the popped bucket) by adjacency to that vertex. The key invariant is that every bucket is always split into at most 2 parts per refinement step.

3. **Do NOT rely on the `_is_valid_lexbfs` checker + retry loop as a correctness mechanism**: The checker is O(n^4) and the retry loop tries at most n+1 orderings. If `_lexbfs` is fundamentally broken, the retry loop may still fail to find a valid ordering (as in this case, where all n+1 attempts produced invalid orderings). Fix the core algorithm first.

4. **The `order_hint` mechanism is fine** as a tie-break: using the previous ordering as the initial bucket order is a valid way to get a deterministic LexBFS. The bug is purely in the refinement logic, not in the hint.
