## FAILURE_DESCRIPTION

- n = 3, operation `insert (0, 2)` at sequence index 0 (first update after `init`).
- Resulting graph (undirected, 0/1 matrix): edges {0-1, 0-2} (a path 1-0-2; vertex 1 and 2 are non-adjacent).
- Returned ordering: `[0, 1, 2]`.
- Expected (any valid LexBFS): `[0, 2, 1]` (or `[1, 0, 2]` / `[2, 0, 1]`).
- Verifier violation: a=0, b=1, c=2 (positions), pos_a=0, minD=1000000000 (sentinel: no witness d found).

## ROOT_CAUSE

The (LB) 4-point property check `_check_lb` is wrong: it treats the case `a == 0` as vacuously satisfied, but the property is NOT vacuous there.

```python
if a == 0:
    continue  # vacuously satisfied
```

For the returned ordering `[0, 1, 2]` on the path 1-0-2:
- a=0 (vertex 0), b=1 (vertex 1), c=2 (vertex 2): ab = 0-1 is an edge, so this triple is skipped by the `if graph[va][vb]: continue` line — no problem.
- But the real failing triple is a=0 (vertex 0), b=1 (vertex 1), c=2 (vertex 2) with **ab NOT in E**... wait, 0-1 IS in E. Let me re-trace with the actual violation record: the verifier reports a=0, b=1, c=2 with minD=1e9, meaning the verifier found a triple (a=0, b=1, c=2) where ac in E, ab not in E, and no d < a exists.

Re-tracing: in ordering `[0, 1, 2]`, positions a=0→vertex 0, b=1→vertex 1, c=2→vertex 2. ac = 0-2 is in E (just inserted). ab = 0-1: for the violation to fire, ab must NOT be in E. So the actual graph must be edges {0-2, 1-2} (path 0-2-1), i.e. the pre-update graph was {1-2} and inserting (0,2) gives the path 0-2-1. Then:
- a=0 (vertex 0), b=1 (vertex 1), c=2 (vertex 2): ac = 0-2 in E, ab = 0-1 not in E. The property requires some d < a = 0 with db in E and dc not in E — impossible since a=0 has no earlier position. Hence the ordering is invalid, and the correct LexBFS is `[0, 2, 1]` (or `[1, 2, 0]` etc.).

Why did the candidate return an invalid ordering? The bug is in `_check_lb`:

```python
if a == 0:
    continue  # vacuously satisfied
```

This line makes `_check_lb` return True for `[0, 1, 2]` on the path 0-2-1, because the only violating triple has a=0 and is skipped. Consequently:
1. In `insert_edge`, the fast path `_check_lb(old_ordering, graph)` (old ordering `[0, 1, 2]` from init on graph {1-2}) incorrectly reports the old ordering as still valid after inserting (0,2), so the invalid ordering is returned unchanged.
2. Even the fallback `_try_all_starts` is corrupted: `_lexbfs_simple` itself is also wrong (it picks lexicographically **maximal** labels, i.e. it implements a reverse-LexBFS variant), so its output would also fail a correct check; but `_try_all_starts` uses the same broken `_check_lb`, so it would accept the first (invalid) output anyway.

The (LB) property is: for all a < b < c with ac in E and ab not in E, there exists d < a with db in E and dc not in E. When a = 0 the existential is over an empty set, so the property is satisfied only if no such triple (a=0, b, c) exists at all. The `continue` inverts the logic: it should `return False` when a == 0 and the triple (ac in E, ab not in E) is found.

## REPAIR_HINTS

1. **Fix `_check_lb` (the minimal, decisive change).** Replace
   ```python
   if a == 0:
       continue  # vacuously satisfied
   ```
   with
   ```python
   if a == 0:
       return False  # no d < 0 can witness; triple (0, b, c) with ac in E, ab not in E is a violation
   ```
   This alone makes the fast path in `insert_edge`/`delete_edge` reject the stale ordering and fall through to the recompute path.

2. **Fix `_lexbfs_simple` so the recompute fallback actually produces a valid LexBFS.** The current code picks the unvisited vertex with lexicographically **maximal** adjacency tuple to the prefix; standard LexBFS (Habib–McConnell–Paul–Viennot) picks the **minimal** tuple (equivalently, maximal in the "non-neighbor" sense). Change the comparison to `key < best_key` (ties by smallest id) so the produced ordering is a genuine LexBFS. After fixing `_check_lb`, `_try_all_starts` will then correctly validate and return it. (Alternatively, implement the standard bucket/partition-refinement LexBFS; the O(n^3) tuple version is fine for correctness.)

3. **Do not** try to "fix" this by adding more local-repair candidates in `_local_repair`: the repair path is only reached when `_check_lb` says the old ordering is invalid, and with the broken checker it is never reached in this case. The local-repair heuristic is also fundamentally unsound in general (a valid LexBFS after an update need not be a small perturbation of the old one), so it should be treated as an optional speed-up, never as a correctness mechanism — every candidate it returns is already validated by `_check_lb`, which is fine once `_check_lb` is correct.

4. Note the verifier's `minD: 1000000000` sentinel confirms the failure mode: it searched for a witness d < a and found none, exactly the a=0 case the checker skips.
