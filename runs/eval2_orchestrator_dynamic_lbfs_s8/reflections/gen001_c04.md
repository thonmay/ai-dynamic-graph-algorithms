## FAILURE_DESCRIPTION
Operation: `init` on a 3-vertex undirected graph (sequence_idx 0, no updates involved).
`init` returned ordering `[0, 1, 2]`, but the verifier reports it is NOT a valid LexBFS ordering:
violation with a=0 (pos 0), b=1 (pos 1), c=2 (pos 2), and `minD = 1000000000` (sentinel = no
witness d found). Expected (a valid) ordering: `[0, 2, 1]`.

The violated (LB) 4-point property: for all positions a < b < c with ac in E and ab not in E,
there must exist d < a with db in E and dc not in E. Here a=0 is at position 0, so the witness
set {d : pos[d] < pos[a]} is empty and the property fails.

For the reported violation (a=0, b=1, c=2) to fire, the graph must satisfy:
- ab = 0-1 is NOT an edge,
- ac = 0-2 IS an edge,
- 0 is first in the ordering (so no witness d can exist).
So the graph has 0-2 in E and 0-1 not in E (1-2 may be either).

## ROOT_CAUSE
The bug is in `_lexbfs_full`, the static partition-refinement LexBFS used directly by `init`
(and as the fallback in both update functions). The failing case is at `init`, so the
local-repair path is irrelevant here.

The algorithm degenerates to the trivial ordering [0, 1, 2, ..., n-1] because the
partition-refinement step is never triggered. Here is the exact trace on the graph with
edges {0-2} only (0-1 and 1-2 non-edges), which matches the reported violation:

- Initial: `buckets = [[0, 1, 2]]`.
- Iteration 1: `first_bucket_idx = 0`. `v = buckets[0].pop(0) = 0`. `buckets[0]` is now `[1, 2]`.
  Rebuild `new_buckets`:
  - `i=0`: `i == first_bucket_idx`, `b = [1, 2]` (non-empty), append `[1, 2]`.
  - No other buckets exist.
  - `new_buckets = [[1, 2]]`.
- Iteration 2: `first_bucket_idx = 0`. `v = buckets[0].pop(0) = 1`. `buckets[0]` is now `[2]`.
  Rebuild `new_buckets`:
  - `i=0`: `i == first_bucket_idx`, `b = [2]` (non-empty), append `[2]`.
  - No other buckets exist.
  - `new_buckets = [[2]]`.
- Iteration 3: `first_bucket_idx = 0`. `v = 2`. Result: `[0, 1, 2]`.

The splitting logic (lines 56-66) only applies to buckets at indices OTHER than
`first_bucket_idx`. But when there is only ONE bucket (the initial state, and often
subsequent states), there are no "other buckets" to split, so no partition refinement ever
occurs. The algorithm simply outputs vertices in id order: [0, 1, 2, ..., n-1].

On the graph with edges {0-2} only: [0,1,2] has a=0, b=1, c=2 with ac=0-2 in E, ab=0-1 not
in E, and no d < a (a is first) → violation. Exactly as reported.

The responsible code:
```python
# Split all other non-empty buckets
new_buckets = []
for i, b in enumerate(buckets):
    if i == first_bucket_idx:
        if b:
            new_buckets.append(b)   # <-- selected bucket's remainder, no split
        continue
    if not b:
        continue
    # Split b into neighbors and non-neighbors of v
    neighbors = [x for x in b if graph[v][x]]
    non_neighbors = [x for x in b if not graph[v][x]]
    if neighbors:
        new_buckets.append(neighbors)
    if non_neighbors:
        new_buckets.append(non_neighbors)
```

When `len(buckets) == 1`, the loop only executes the `i == first_bucket_idx` branch, which
just appends the remainder without splitting. No refinement happens. The algorithm is
structurally incapable of performing any partition refinement from the initial single-bucket
state.

## REPAIR_HINTS
1. Replace `_lexbfs_full` with the standard LABEL-BASED LexBFS, which is simpler and
   provably correct:
   ```python
   def _lexbfs_full(graph):
       n = len(graph)
       if n == 0:
           return []
       # Start vertex: 0 (any start is valid)
       s = 0
       # Label for each vertex: list of processed neighbors in processing order
       labels = {v: [] for v in range(n)}
       # All vertices start with the same label (empty), so tie-break by id
       unprocessed = set(range(n))
       order = []
       while unprocessed:
           # Pick the unprocessed vertex with lexicographically smallest label,
           # tie-break by smallest vertex id
           v = min(unprocessed, key=lambda x: (labels[x], x))
           order.append(v)
           unprocessed.remove(v)
           # Update labels: prepend v to labels of unprocessed neighbors
           for u in unprocessed:
               if graph[v][u]:
                   labels[u] = [v] + labels[u]
       return order
   ```
   This is O(n^3) with list labels (or O(n^2) with a more careful implementation) and is
   provably a valid LexBFS. It does not suffer from the single-bucket degeneracy.

2. Do NOT try to "fix" the current bucket code by just swapping the order of neighbors and
   non-neighbors in the append — the deeper issue is that no splitting happens when there's
   a single bucket. The bucket-based approach as written is structurally broken for the
   initial state.

3. After fixing `_lexbfs_full`, add a debug assertion `_is_valid_lexbfs(order, graph)` in
   `init` and in the fallback paths of `insert_edge`/`delete_edge` to catch regressions.

4. The local-repair path (`_try_local_repair`) is sound only if `_is_valid_lexbfs` is
   correct. Keep it, but ensure the fallback `_lexbfs_full` is the fixed version, since the
   fallback is the only guarantee of correctness when repair fails.

5. Performance note: `_is_valid_lexbfs` is O(n^4) and `_try_local_repair` calls it O(n^2)
   times, making updates O(n^6). Acceptable for correctness-first, but flag for the
   performance goal.
