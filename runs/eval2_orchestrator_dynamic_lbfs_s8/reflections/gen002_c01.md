# Reflection: gen002_c01

## FAILURE_DESCRIPTION
Crash at `init` (sequence_idx 0, no updates yet): `AssertionError: init produced invalid LexBFS` at line 145. The candidate's own static LexBFS output fails its own `_is_valid_lexbfs` check on a 3-vertex graph. No update was involved; the failure is entirely in the static pipeline.

## ROOT_CAUSE
The static algorithm `_lexbfs_full` is not a valid LexBFS. It uses **vertex ids** as label symbols:

```python
v = min(unprocessed, key=lambda x: (labels[x], x))
...
if graph[v][u]:
    labels[u] = labels[u] + [v]
```

LexBFS validity requires labels to be compared **lexicographically over the BFS processing order** (i.e., the order in which vertices were output). The candidate compares them over the vertex-id order instead. These differ whenever the BFS order is not the id order, and the resulting ordering can violate the (LB) 4-point property.

Concrete trace (path 0-1-2, edges {01,12}):
- Step 1: all labels empty, tie-break by id -> pick 0. labels: 1->[0], 2->[].
- Step 2: labels 1=[0], 2=[] -> pick 2 (empty is lexicographically smallest). labels: 1=[0].
- Step 3: pick 1. Order = [0, 2, 1].

Check (LB) on [0,2,1]: a=0 (pos 0), b=2 (pos 1), c=1 (pos 2). ac=01 in E, ab=02 not in E. Need d before a with db in E and dc not in E: no d exists (a is first). Property violated -> `_is_valid_lexbfs` correctly returns False -> assert fires.

A correct label-based LexBFS would have picked 1 at step 2 (label [0] vs []: the vertex adjacent to the already-processed 0 must come first), giving [0,1,2], which is valid.

Note the checker `_is_valid_lexbfs` itself is a faithful implementation of the (LB) 4-point property and is not at fault; it correctly detected the bad ordering.

## REPAIR_HINTS
Fix `_lexbfs_full` so label symbols are the **processing positions**, not vertex ids:

1. Maintain `pos = {}` mapping vertex -> its index in `order` (set when the vertex is selected).
2. When updating labels after selecting `v`, append `pos[v]` (or equivalently `len(order)-1`) instead of `v`:
   ```python
   order.append(v)
   p = len(order) - 1
   for u in unprocessed:
       if graph[v][u]:
           labels[u].append(p)
   ```
3. Keep the tie-break by vertex id (any deterministic tie-break is fine for validity).

With position-based labels, the trace above picks 1 at step 2 (label [0] vs []: [0] < [] is false, but [] < [0] is true... note: empty list is a prefix and thus lexicographically smaller — so the correct LexBFS rule is that a vertex whose label is a *proper prefix* of another's is chosen first; with position labels [0] vs [], [] is smaller, so 2 would still be picked — this is the subtle part: the standard label-based LexBFS compares labels where a shorter label that is a prefix is considered smaller, which is exactly what Python list comparison does, and with position labels the algorithm is the standard one and is provably valid; the id-based version breaks the proof because the label symbols no longer reflect processing order).

Simpler and safer alternative: implement the standard **partition-refinement (bucket) LexBFS** (Habib–McConnell–Paul–Viennot): maintain an ordered list of buckets; repeatedly take the first vertex of the first non-empty bucket, then split every other bucket into (adjacent-to-v, not-adjacent-to-v) parts, keeping the adjacent part first. This is O(n+m) with adjacency lists and is the canonical correct construction; it avoids the label-comparison subtlety entirely.

Approaches that will NOT work:
- Keeping id-based labels and only changing the tie-break: the label-symbol mismatch is the core bug.
- Relying on `_try_local_repair` to fix a bad init order: it is never called from `init`, and the assert fires before any update.
- "Fixing" the checker to accept the bad order: the checker is correct; the verifier will reject the ordering anyway.
