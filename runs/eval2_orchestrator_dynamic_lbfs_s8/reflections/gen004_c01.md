## FAILURE_DESCRIPTION
n=3. Initial graph: edge (0,1) only (adj: 0~1). `init` returns ordering [0, 1, 2] (valid for that graph). Then `insert_edge(graph, (0,2), state)` is called; the updated graph has edges (0,1) and (0,2) — a star centered at 0. The candidate returned [0, 1, 2], but the only valid LexBFS orderings of this graph are [0, 2, 1] and [0, 1, 2] is NOT valid: the verifier reports the (LB) 4-point violation at a=0, b=1, c=2 (pos_a=0, minD=1e9 sentinel meaning no witness d exists). Expected [0, 2, 1], actual [0, 1, 2].

## ROOT_CAUSE
The bug is in `_is_valid_lexbfs`: it implements the (LB) property with the polarity of the witness condition INVERTED.

The (LB) property (Corneil–Krueger) says: for all a < b < c with ac in E and ab not in E, there must EXIST d < a with db in E and dc not in E. So the ordering is INVALID exactly when such a triple exists with NO witness d.

The code instead does:
```python
union_adj = 0
bs = bset
while bs:
    lsb2 = bs & (-bs)
    vb = lsb2.bit_length() - 1
    bs ^= lsb2
    union_adj |= adj[vb]
if (union_adj & prefix[a] & ~adj[vc]):
    return False
```
`union_adj & prefix[a] & ~adj[vc]` is non-zero precisely when a witness d DOES exist (d < a, db in E, dc not in E). The code returns False (invalid) in exactly the case where the property is SATISFIED, and returns True (valid) when no witness exists — the exact opposite.

Trace on the failing case: ordering [0,1,2], adj[0]={1,2}, adj[1]={0}, adj[2]={0}. a=0 (va=0): cands = adj[0] & ~prefix[1] = {1,2} & ~{0} = {1,2}. Take vc=1 (pc=1): bset = prefix[1] & ~prefix[1] & nonadj = empty, skip. Take vc=2 (pc=2): bset = prefix[2] & ~prefix[1] & nonadj = {0,1} & ~{0} & {2} = {1}. union_adj = adj[1] = {0}. prefix[a] = prefix[0] = 0, so the test is 0 → no `return False` → function returns True, i.e. it certifies [0,1,2] as valid. But the correct check for this triple: no d < 0 exists, so the property is VIOLATED and the ordering is invalid. The inverted logic let the stale ordering pass the "validation" gate in `_update`, so `_update` returned the previous ordering instead of recomputing.

Note the witness test is also vacuous for a=0 (prefix[0]=0), which is exactly the case that fails here; the inversion is what turns that vacuity into a false "valid".

## REPAIR_HINTS
Smallest fix, in `_is_valid_lexbfs`: invert the witness test. The ordering is invalid iff there exists a triple (a,b,c) with ac in E, ab not in E, and NO d < a with db in E and dc not in E. Concretely, replace the per-b union with a per-b existence check and return False when no b has a witness:

```python
ok = False
bs = bset
while bs:
    lsb2 = bs & (-bs)
    vb = lsb2.bit_length() - 1
    bs ^= lsb2
    if (prefix[a] & adj[vb] & ~adj[vc]):
        ok = True
        break
if not ok:
    return False
```
(Keep the `if not bset: continue` — a triple with no non-adjacent b between a and c imposes no constraint.)

Do NOT try to "fix" this by making the static `_lexbfs_static` produce a different ordering — it is correct; the failure is purely the inverted validator letting a stale ordering survive. Also note the current O(n^3) worst case of the validator (per (a,c) pair, scan all b) is acceptable for correctness-first; the per-b early break above is a minor improvement.
