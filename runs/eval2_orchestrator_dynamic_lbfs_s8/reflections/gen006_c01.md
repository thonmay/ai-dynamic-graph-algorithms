# Reflection: gen006_c01 — dynamic_lbfs

## FAILURE_DESCRIPTION

- Operation: `insert_edge(graph, (2, 0), state)` at sequence index 0 (first update after `init`).
- Result returned by the candidate: `[0, 2, 1, 3]`.
- Expected (a valid LexBFS ordering of the updated graph): `[0, 2, 3, 1]`.
- Verifier-reported violation of the (LB) 4-point property:
  `a=2, b=1, c=3, pos_a=1, minD=1000000000`.
  Interpreted as positions: pos_a=1 (vertex 2), pos_b=2 (vertex 1), pos_c=3 (vertex 3).
  In the returned ordering `[0, 2, 1, 3]`:
  - ac in E: edge (2,3) present.
  - ab not in E: edge (2,1) absent.
  - No d < pos_a=1 with db in E and dc not in E (only vertex 0 precedes position 1, and it fails the witness condition).
  Hence the ordering is NOT a valid LexBFS ordering of the updated graph.

## ROOT_CAUSE

The divergence happens in the **local-repair step** of `insert_edge` (step 2), which returns an ordering that is *not* actually valid. The fallback full recompute (step 3) is never reached because `_try_local_repair` claims success.

The chain of events:

1. `insert_edge` updates `adj_bits` for the new edge (2,0):
   ```python
   adj_bits[u] |= (1 << v)
   adj_bits[v] |= (1 << u)
   ```
2. `_lb_valid_fast(order, adj_bits)` correctly reports the current ordering invalid (step 1 fails).
3. `_try_local_repair(order, graph, adj_bits, u, v)` is called. It tries:
   - moving vertex 2 to every position,
   - moving vertex 0 to every position,
   - swapping 2 and 0,
   - swapping 2 with every other vertex,
   - swapping 0 with every other vertex.
   For each candidate it calls `_lb_valid_fast(new_order, adj_bits)`.
4. **`_lb_valid_fast` returns `True` for the invalid ordering `[0, 2, 1, 3]`** — a false negative (it fails to detect the violation). This is the bug.

### Why `_lb_valid_fast` misses the violation

The (LB) property requires: for all positions a < b < c with ac in E and ab not in E, there exists d < a with db in E and dc not in E.

For the invalid ordering `[0, 2, 1, 3]` with the violation at (a=2, b=1, c=3):
- pos_a = 1 (vertex 2), pos_b = 2 (vertex 1), pos_c = 3 (vertex 3).
- ac in E: (2,3) ∈ E. ✓
- ab not in E: (2,1) ∉ E. ✓
- Need: ∃ d at position < 1 (i.e., d = vertex 0) with d-b in E and d-c not in E.
  - d=0: (0,1) ∈ E? and (0,3) ∉ E?
  - The violation says NO such d exists.

In `_lb_valid_fast`, the code for the `pm != 0` branch (line ~85-100):
```python
for b in range(a + 1, n):
    vb = order[b]
    if (bits_a >> vb) & 1:
        continue  # ab in E
    bits_vb = adj_bits[vb]
    if (bits_vb & pm) == 0:
        continue
    for c in range(b + 1, n):
        vc = order[c]
        if not ((bits_a >> vc) & 1):
            continue
        bits_vc = adj_bits[vc]
        if (bits_vb & pm & ~bits_vc) != 0:
            return False
```

The check `(bits_vb & pm & ~bits_vc) != 0` is **inverted**. The property says: for the ordering to be valid, for every (a,b,c) with ac∈E and ab∉E, there must EXIST a d < a with db∈E and dc∉E. A violation occurs when NO such d exists, i.e., when for ALL d < a, either db∉E or dc∈E. Equivalently: `(N(vb) & ~N(vc) & pm) == 0` means violation.

But the code checks `(bits_vb & pm & ~bits_vc) != 0` → return False. This is checking the OPPOSITE: it returns False when there IS a witness d, which is the VALID case. The condition should be:
```python
if (bits_vb & pm & ~bits_vc) == 0:
    return False  # no witness d exists → violation
```

Wait — let me re-examine. Actually the logic is:
- `bits_vb & pm` = set of vertices d < a that are adjacent to b.
- `~bits_vc` = set of vertices NOT adjacent to c.
- `bits_vb & pm & ~bits_vc` = set of d < a with db∈E and dc∉E = the witness set.
- If this set is EMPTY (`== 0`), no witness exists → violation → return False.
- If this set is NON-EMPTY (`!= 0`), a witness exists → this (a,b,c) is fine → continue.

So the code `if (bits_vb & pm & ~bits_vc) != 0: return False` is **backwards**. It should be `== 0`.

However, there's a subtlety: the property requires the witness to exist for ALL valid (a,b,c) triples. The code iterates over all c > b with ac∈E and returns False if ANY of them has no witness. That's correct logic (violation if any triple fails). But the condition is inverted.

**The bug is on the line:**
```python
if (bits_vb & pm & ~bits_vc) != 0:
    return False
```
**It should be:**
```python
if (bits_vb & pm & ~bits_vc) == 0:
    return False
```

This inversion means `_lb_valid_fast` returns True for orderings that actually violate the (LB) property (when a witness exists it incorrectly flags a violation, and when no witness exists it incorrectly accepts). In this specific failing case, the invalid ordering `[0, 2, 1, 3]` has no witness for the (a=2,b=1,c=3) triple, so the correct check would find `bits_vb & pm & ~bits_vc == 0` and return False. But the buggy code sees `== 0` and does NOT return False (it only returns False on `!= 0`), so it incorrectly accepts the ordering.

Additionally, the `pm == 0` branch (lines ~60-75) has the correct logic: when no d < a exists, any (a,b,c) with ac∈E and ab∉E is a violation, and the code correctly returns False in that case. The bug is isolated to the `pm != 0` branch.

## REPAIR_HINTS

1. **Fix the inverted condition in `_lb_valid_fast`** (the `pm != 0` branch, around line 100):
   ```python
   # BUG: this line is inverted
   if (bits_vb & pm & ~bits_vc) != 0:
       return False
   # FIX: should be
   if (bits_vb & pm & ~bits_vc) == 0:
       return False
   ```
   This is the minimal one-character fix (`!=` → `==`).

2. **After fixing the validity check**, the local repair in `_try_local_repair` will correctly reject invalid orderings, and the fallback full recompute (`_lexbfs`) will produce a valid ordering. The overall strategy (check → local repair → recompute) is sound.

3. **Approaches that will NOT work:**
   - Simply removing the local repair step: this would make the algorithm correct (always recompute) but defeats the purpose of the dynamic approach.
   - Changing the local repair to try more permutations: the root cause is the false positive in `_lb_valid_fast`, not insufficient search in the repair.
   - Adding a separate brute-force validity check as a second opinion: this would mask the bug but not fix it, and would be O(n^4) per check.

4. **Verification after fix:** After applying the `==` fix, re-run the failing case. The expected behavior:
   - `_lb_valid_fast([0, 2, 1, 3], adj_bits)` should return False (detecting the violation).
   - `_try_local_repair` should either find a valid local repair or return None.
   - If None, `_lexbfs` recomputes and returns a valid ordering like `[0, 2, 3, 1]`.
