
The refinement step iterates over `buckets` **after** `v` has been popped from `buckets[0]`. If `buckets[0]` still contains other vertices (i.e. the first bucket had size > 1), those remaining vertices are refined against `v` — fine. But the critical bug is: **the first bucket is never re-inserted as a whole after refinement in a way that preserves the correct LexBFS semantics.** More precisely, the standard LexBFS partition refinement requires that after selecting vertex `v` from the first bucket, the *remaining* vertices of that first bucket are split into N(v) and non-N(v), and the N(v) part goes to the FRONT of the bucket list (before the other buckets), while the non-N(v) part stays in the same relative position. The code does this correctly for the first bucket (it's processed first in the loop, and `nb` is appended before `non_nb`).

## REPAIR_HINTS
In `_lb_valid_fast`, the line:
```python
if (bits_vb & pm) == 0:
    continue
```
is incorrect. When `bits_vb & pm == 0`, vertex b has no neighbors among vertices before position a. If there exists any c > b with ac in E (and ab not in E, which we already know), then the (a,b,c) triple is a violation because no d < a can satisfy db in E.

Fix: replace the `continue` with a check for whether any c > b has ac in E. If so, return False. Concretely:

```python
if (bits_vb & pm) == 0:
    # b has no neighbors in prefix; if any c > b is adjacent to a, violation
    for c in range(b + 1, n):
        if (bits_a >> order[c]) & 1:
            return False
    continue
```

Or more efficiently, precompute for each a the set of vertices after a that are adjacent to a, and check intersection.

This bug causes `_lb_valid_fast` to return True (valid) for orderings that are actually invalid, which means:
1. In `insert_edge`/`delete_edge`, step 1 may keep an invalid ordering.
2. In `_try_local_repair`, an invalid repaired ordering may be accepted.

The full recompute fallback (`_lexbfs`) is likely correct, so the fix to `_lb_valid_fast` should resolve the issue.
