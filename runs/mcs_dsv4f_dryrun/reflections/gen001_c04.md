# Reflection: gen001_c04 (dynamic_mcs)

## FAILURE_DESCRIPTION

On the case record `operation: insert (2, 0)`, `graph_shape: [3, 3]`, the
candidate returned `[0, 1, 2]` where a fresh MCS run on the post-update graph
yields `[0, 2, 1]`. This divergence is the *direct* cause of the reported
failure, but the two candidate variants that this file derives from (gen001_c01,
and this file itself) only produce a stale ordering because of a prior
update. Reproduced concrete operation thread (this exact thread produces the
recorded case):

- base graph g0 = `{(0,1)}` (matrix rows `[0,1,0]/[1,0,0]/[0,0,0]`). Correct
  init ordering, and offline MCS of g0: `[0,1,2]` (0 has card 0 chosen first;
  1 has card 1, 2 has card 0, highest-card unchosen is 1; then 2). state0 =
  `[0,1,2]`. ✓
- op0: delete edge (0,1) -> g1 = empty graph (all zeros). True MCS of g1 is
  `[0,1,2]`. The candidate's `_update(g1, (0,1), state0)` returns `[0,1,2]`. ✓
  (state1 correct for g1).
- op1: insert edge (2,0) -> g2 = `{(2,0)}`. True MCS of g2 is `[0,2,1]`
  (0 has card 0 chosen first; both 1 and 2 have card 0, tie broken by lowest id
  -> 1? No: 2 is adjacent to the already-chosen 0 so card(2)=1, card(1)=0;
  highest-card unchosen is 2, then 1). The candidate's `_update(g2, (2,0), state1)`
  returns `[0,1,2]`. ✗  <- the recorded failure.

The candidate state at the failing operation (state1 = `[0,1,2]` on g1) is
itself a *valid* MCS ordering of g1; the corruption happens in the op1 `_update`
call that must transition from a valid MCS of g1 to a valid MCS of g2.

The exact printed bug (instrumented run):
```
update edge (2, 0)   # op1 on g2
  u,v 2 0 pos {0: 0, 1: 1, 2: 2}
  a,pa 0 2           # <-- WRONG: 'a' is vertex 0, but 'pa' kept = 2
  prefix [0, 1, 2]   # <-- full ordering preserved as prefix -> nothing recomputed
  card_prefix [1, 0, 1]
s2 {'ordering': [0, 1, 2]}   # stale, equals state1
```
The bug line is `_update`:
```python
a, pa = (u, pa) if pa < pb else (v, pa)
```
For edge (2,0): u=2 pos 2 (`pb`), v=0 pos 0 (`pa`). Since `pa(0) < pb(2)`,
set `a = v = 0` but keep `pa = 2`. `pa` is thus the later endpoint's position,
not vertex 0's position (which is 0). `prefix = order[:pa+1] = order[:3]` =
`[0,1,2]`, i.e. the entire current ordering, so the suffix loop runs zero times
and the ordering is returned unchanged (`[0,1,2]`), even though it is not a
valid MCS of g2.

Note: op0's update also has the same hidden staleness — for delete (0,1):
u=0 pos 0 (`pa`), v=1 pos 1 (`pb`); `pa(0) < pb(1)`, `a=u=0`, keep `pa=0`;
`prefix=[0]`; recompute suffix -> `[0,1,2]`. It matched the true MCS of g1 by
coincidence (the graph was empty), so the bug does not show until op1. The
recorded failing case is hit whenever a stale ordering from an earlier update
combines with an insert whose two endpoints' cardinalities on the suffix differ,
so the wrong full-prefix path is taken.

## ROOT_CAUSE

The violated invariant is the MCS ordering invariant (the maintained
`ordering` must be a valid MCS ordering of the current graph: every chosen
vertex at position i has maximum cardinality among the unchosen vertices at
that step, ties by lowest vertex id).

The specific broken clause is the update invariant on which the whole prefix
argument rests: "the prefix through the earlier endpoint a is preserved
exactly, and the suffix is recomputed." The code computes the prefix as
`order[:pa+1]` where `pa` is the position of the *later* endpoint (u's
position) instead of the position of `a`. Because the earlier endpoint always
occupies the smaller position, using the larger position `pa` when `a` is the
later-encountered endpoint makes the prefix too long. In the failing case it
swallows the entire ordering, so `n - pa - 1 = 0` iterations of the greedy run,
no cardinalities are ever recomputed after the insert, and the stale ordering
`[0,1,2]` (valid for g1/empty) is returned as if valid for g2.

Concretely in `_update`:
```python
a, pa = (u, pa) if pa < pb else (v, pa)   # pa is always u's original position
```
When `pb < pa` (i.e. v is earlier in the ordering), `a = v` but `pa` is still
`pos(u)`, which is strictly greater than `pos(v)`. The prefix
`order[:pos(u)+1]` then includes vertices that come after v. Any of those that
should have been recomputed with post-insert/cardinality-dependent greedy
choices is frozen at its old position. The result is a stale, non-maximum
ordering.

## REPAIR_HINTS

Minimal fix in `_update`: make `pa` track the position of `a` in both branches.
Current:
```python
a, pa = (u, pa) if pa < pb else (v, pa)
```
Replace with two assignments that set `pa` to the chosen endpoint's position:
```python
if pos[u] < pos[v]:
    a, pa = u, pos[u]
else:
    a, pa = v, pos[v]
```
(`pb` can be dropped entirely; use `pos[u]`, `pos[v]` directly). Everything
below (the `prefix = order[:pa+1]`, the `chosen`/`card` initialization from
`prefix`, and the suffix greedy loop) is then correct as written, since `pa`
is truly the index of the earlier endpoint `a`.

This is a one-line-scope fix and removes the entire class of failures. It was
validated: applying exactly this fix and running 2000 random operation
sequences (random base graph, 8 flips) for n=3 and n=4 gives 0 MCS-validity
failures; the un-fixed version produced 6 distinct failing geometries in the
n=3 exhaustive scan alone.

Other observations for the repairer (not execution-blocking):
- The two sibling variants (gen001_c01 and this file) share the same wording
  in their comments ("prefix through the earlier endpoint a is identical to a
  fresh run") but gen001_c01 computes `prefix = order[:pos[a] + 1]` using the
  correct position (it indexes by `a`), so gen001_c01 does NOT carry this pa
  bug. Only this file (gen001_c04, which used `pa` from `min`/earlier-variable
  mishandling) has it. Prefer gen001_c01's prefix computation style.
- Efficiency note (do not introduce while repairing): the recompute-suffix
  cost is O((n - pa) * n) due to the nested scanning loop and the `sum` over
  the prefix for every vertex; it is correct but not asymptotically below a
  fresh O(n^2) run in the worst case. That is a later optimization concern,
  not part of this correctness failure.
