## FAILURE_DESCRIPTION
Case: n=2, root 0. The case's "graph" field is the **post-update** graph
`[[0,1],[0,0]]` (edge 0→1 present). Operation: `insert (0, 1)`,
`sequence_idx: 0` — the first update in the sequence.
Expected after the update: `parent = {0: None, 1: 0}`, `distances = {0: 0, 1: 1}`.
Actual returned state: `parent = [None, None]`, `distances = [0, -1]` — vertex 1
left unreachable. This is exactly the state `init` produces on the **empty**
graph `[[0,0],[0,0]]`, i.e. the state as if `insert_edge`'s repair never ran.

## ROOT_CAUSE
The trace is **inconclusive** from the case data alone, and I want to be
explicit about that rather than assert a wrong cause.

Facts established by tracing the candidate code:
1. If `init` was called on the empty pre-update graph, `dist = [0, -1]`,
   `parent = [None, None]`. Then `insert_edge(graph, (0,1), state)` computes
   `du = dist[0] = 0`, so the `if du == -1: return state` guard does **not**
   fire. The repair queue `[(1, 1)]` runs: `nd=1 < dist[1]=-1` is false →
   `dist[1] = 1`, parent scan over `state['in'][1] = {0}` finds `dist[0] == 0
   == nd-1` → `parent[1] = 0`. The code as written **passes** this case.
2. The observed wrong state equals the post-init state on the empty graph, so
   in the failing run the repair was skipped entirely. The only skip path in
   `insert_edge` is `if du == -1: return state`. For that to fire with edge
   (0,1), `dist[0]` would have to be -1, which contradicts `dist[root] = 0`
   set in `_bfs_full` — **unless the state passed in was not produced by this
   candidate's `init`** (e.g. the harness seeded/seeded a different state, or
   `init` was called on a graph where the root row was not yet processed, or
   the state dict's `distances` list was replaced externally).

Hypotheses ruled out:
- The `du == -1` guard firing on a legitimately `init`-ed state: ruled out,
  because `dist[0]` is always 0 after `_bfs_full`.
- The repair loop miscomputing: ruled out by direct trace (step 1).
- `state['in'][1]` missing 0: ruled out — `insert_edge` adds it to
  `state['in'][v]` before the repair, and `init` on the empty graph gives an
  empty set that the add populates.

Remaining plausible root cause (not fully confirmed): the harness's state
handoff — the state arriving at `insert_edge` did not match what this
candidate's `init` would produce (e.g. `init` was called on a different
initial graph than the empty one, or the harness re-created/normalized the
state between `init` and the update). The candidate code itself is correct for
the stated case; the failure indicates a state-contract mismatch at the
harness boundary.

## REPAIR_HINTS
1. **Make `insert_edge` self-healing against a stale/foreign state.** The
   cheapest robust fix: at the top of `insert_edge`, after adding the edge to
   `out`/`in`, verify the invariant locally for the affected vertices. If
   `dist[v] == -1` but `v` has any in-neighbor `p` with `dist[p] >= 0`, the
   state is inconsistent — run a local BFS from the root restricted to the
   region reachable from the set of in-neighbors of `v` (or, as a correctness
   backstop, a full `_bfs_full` recompute) and rebuild `parent`/`distances`
   before doing the incremental repair. This makes the candidate correct
   regardless of how the state was seeded.
2. **Do not rely on `init` having been called on the exact pre-update graph.**
   The contract says `init(graph)` is called, but the failing run shows the
   state at update time was not the candidate's own init output. A defensive
   re-sync in `insert_edge` (and symmetrically in `delete_edge`: if
   `parent[v] != u` but `v` is unreachable while having reachable in-neighbors,
   recompute) closes this class of bug.
3. **Do not** "fix" this by assuming the harness is wrong and leaving the code
   as-is — the verifier will keep failing. **Do not** remove the `du == -1`
   guard entirely without the self-heal check, because an unreachable source
   genuinely cannot improve `v` via that edge; the guard is logically sound
   *given a consistent state*. The bug is the missing consistency guarantee,
   not the guard itself.
4. A full `_bfs_full` recompute on every update is a valid correctness
   backstop for reaching full correctness first (the research goal says
   correctness before work ratio), but prefer the local repair + conditional
   recompute to keep the work ratio low once correctness is established.
