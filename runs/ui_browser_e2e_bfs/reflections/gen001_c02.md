## FAILURE_DESCRIPTION
Graph (n=3, directed, root 0): edges 0→1, 1→2, 2→1 (adjacency rows: [0,1,0], [0,0,1], [0,1,0]).
Operation: `delete (0, 1)` (sequence_idx 3). The verifier reported a timeout — no result within 3 s, i.e. an infinite loop.

After `init`, the BFS tree is: parent = [None, 0, 1], distances = [0, 1, 2].
Deleting (0,1) makes 1 and 2 unreachable (the only remaining edge is 2→1, which is a cycle with no root connection). Expected final state: parent = [None, None, None], distances = [0, -1, -1]. Instead the candidate never returns.

## ROOT_CAUSE
The infinite loop is in the "detach" branch of `delete_edge` (the `else` after `best == -1`):

```python
q = deque([v])
while q:
    x = q.popleft()
    for y in range(n):
        if parent[y] == x:
            parent[y] = None
            dist[y] = -1
            q.append(y)
parent[v] = None
dist[v] = -1
```

The bug: `parent[v]` is only cleared **after** the loop, while the loop's termination relies on `parent[y] == x` becoming false for every child. Trace on the failing case:

1. `v = 1`. `in_edges[1] = {0, 2}`; after `discard(0)`, only `w = 2` remains, but `dist[2] = 2` is still stale (2 is a descendant of 1, so it is actually unreachable too). So `best = 2` — the code takes the **reparent** branch, not the detach branch.
2. `dist[1] = dist[2] + 1 = 3`, `parent[1] = 2`. Now the parent pointers form a **cycle**: 1→2→1 (parent[1]=2, parent[2]=1).
3. The descendant-propagation loop:
   ```python
   q = deque()
   for x in range(n):
       if parent[x] == v:      # parent[2] == 1 → enqueue 2
           q.append(x)
   while q:
       x = q.popleft()
       for y in range(n):
           if parent[y] == x:  # x=2: parent[1] == 2 → enqueue 1
               dist[y] = dist[x] + 1
               q.append(y)
   ```
   Enqueues 2, then 1, then 2, then 1, … forever. Distances grow unboundedly (dist[1], dist[2] keep increasing) but the loop never terminates.

Root cause in one line: the reparent step in `delete_edge` picks a "best" in-neighbor **without checking that the in-neighbor is not a descendant of v in the current BFS tree**. When the only remaining in-neighbor is a descendant (here 2, whose reachability depended on v itself), the code creates a parent cycle, and the subsequent tree-BFS over `parent` pointers loops forever. The stale `dist` values of v's descendants (still ≥ dist[v]) make the descendant look like a valid, even "better", candidate.

Note the detach branch itself is also subtly wrong (it would leave `parent[v]` pointing at v's old parent during the walk, and it never reattaches the detached subtree via other in-neighbors as the docstring promises), but on this failing case the hang is caused by the reparent-branch cycle, not the detach branch.

## REPAIR_HINTS
Smallest concrete fix, in `delete_edge`:

1. Before choosing `best`, exclude any in-neighbor `w` that is a descendant of `v` in the current tree (or, equivalently, any `w` whose reachability from the root goes through `v`). A cheap sufficient test: first mark v's subtree (walk `parent` pointers from v's children, as the detach branch does), and only consider in-neighbors `w` with `dist[w] != -1` that are **not** in that marked set. In the failing case, 2 is in v's subtree, so `best` becomes -1 and the detach branch runs.
2. Fix the detach branch so it cannot leave stale parent pointers and so it actually reattaches: (a) clear `parent[v]` **before** walking the subtree (or collect the subtree first, then clear), and (b) after detaching, for each detached vertex `x` (in increasing distance order), try to reattach it to a reachable in-neighbor `w` with `dist[w] != -1` and `w` not in the detached set, setting `parent[x] = w`, `dist[x] = dist[w] + 1`. Without (b), a vertex that lost its parent edge but still has another reachable in-neighbor would be wrongly reported unreachable.
3. As a defensive guard against any residual cycle bug, the descendant-propagation loops (in both `insert_edge` and `delete_edge`) should track visited vertices and stop if a vertex is about to be enqueued twice — this converts a potential infinite loop into a detectable error rather than a hang.

Approaches that will NOT work:
- Simply checking `dist[w] < dist[v]` when picking `best`: in the failing case dist[2]=2 < dist[1]=2 is false, but after other update orders the stale descendant distance can be smaller than v's, so the cycle would still form. The descendant-set exclusion is the robust condition.
- Recomputing a full BFS on every update: correct but defeats the purpose of the dynamic algorithm (the research goal is work below full recomputation); acceptable only as a last-resort fallback, not as the primary repair.
