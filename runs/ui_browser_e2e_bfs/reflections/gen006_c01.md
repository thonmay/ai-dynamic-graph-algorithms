## FAILURE_DESCRIPTION
3-vertex directed graph, root 0. Initial graph has only edge 0→1, so the state after `init` is `dist = [0, 1, -1]`, `parent = [None, 0, None]`.

Operation: `insert (0, 2)`. After the flip the graph has edges 0→1, 0→2, 1→2, so the correct BFS state is `dist = [0, 1, 1]`, `parent[2] = 0`.

The candidate's `insert_edge` left vertex 2 unreachable (`dist[2] = -1`, `parent[2] = None`). The subsequent update in the sequence (insert 1→2) also failed to reach vertex 2 for the same reason. The final maintained state therefore reported vertex 2 as unreachable, while the verifier's reference BFS on the final graph gives `distances [0, 1, 2]` / `parent[2] = 1` (the "wrong_vertices" entry in the report is the reference value, not the candidate's).

## ROOT_CAUSE
In `insert_edge`, the repair queue is seeded with `q = [(v, du + 1)]` and each popped entry is guarded by:

```python
if nd >= dist[x]:
    continue
```

When `v` was previously unreachable, `dist[v] == -1`. Since `nd` is a non-negative integer, `nd >= -1` is always True, so the vertex is skipped and its distance/parent are never updated. The `-1` sentinel ("unreachable") is not ordered below real distances in this comparison, so the guard that is meant to skip vertices whose distance did not improve also skips vertices that just became reachable.

Concretely, for the failing case: `du = dist[0] = 0`, `dist[2] = -1`, the entry condition `du + 1 < dist[v]` (i.e. `1 < -1`... actually the code checks `dist[v] == -1 or du + 1 < dist[v]`, which is True via the first disjunct) correctly enters the repair, but the queue guard then discards `(2, 1)` because `1 >= -1`.

## REPAIR_HINTS
In `insert_edge`, change the queue guard so that an unreachable vertex is always processed. The smallest fix:

```python
if dist[x] != -1 and nd >= dist[x]:
    continue
```

(or equivalently `if nd >= dist[x] and dist[x] != -1: continue`). This makes the guard mean "skip only if x is already reachable at a distance no worse than nd", which is the intended semantics.

Do NOT "fix" this by changing the entry condition `if du == -1 or not (dist[v] == -1 or du + 1 < dist[v])` — that condition is already correct; the bug is purely in the queue guard.

Also note the same `-1`-sentinel hazard pattern exists in the descendant propagation `if dist[y] > nd + 1: q.append((y, nd + 1))` — that one happens to be safe (an unreachable `y` with `dist[y] = -1` is not enqueued, but it can only be reached via a reachable parent's out-edge, and the parent's own processing will enqueue it through the fixed guard only if it is a direct improvement; verify after the fix that a vertex newly made reachable through a multi-hop cascade is still enqueued — with the guard fix, the first hop is enqueued by the parent's `dist[y] > nd + 1` check only if `dist[y]` is not -1, so consider also enqueuing when `dist[y] == -1` there, i.e. `if dist[y] == -1 or dist[y] > nd + 1`).
