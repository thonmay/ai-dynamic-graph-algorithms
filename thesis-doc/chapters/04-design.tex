\chapter{Solution Design}
\label{ch:design}

This chapter is the software design of the discovery platform, written to be
implementable: a reader who has not seen the code should be able to build the
system from it alone. It covers the user interface design, the data and
persistence design, and the core application logic, and states the rationale
behind each consequential choice. It is a design, not an implementation: the
mechanism level is given here, and the code-level walk-through is deferred to
Chapter~\ref{ch:implementation}. Where the design refines the registered topic,
the refinement is stated explicitly and traced to the requirements in
Chapter~\ref{ch:requirements}.

\section{Architectural drivers and overview}
\label{sec:design-architecture}

The architecture is driven by the three registered contributions and the
non-functional requirements in Chapter~\ref{ch:requirements}. C1 (the
interactive research tool) forces a separation between a control plane (the
engine) and an observation plane (the user interface) that does not import the
engine. C2 (the verification engine) forces a hard trust boundary enforced by the
operating system rather than by convention (\texttt{NFR-SEC-01}). C3
(cooperative agents with dynamic generation) forces a pluggable agent layer and
an event stream from which specialist state can be derived. Reliability (\texttt{NFR-REL-01}) forces checkpointing and a replayable event
log; reproducibility (\texttt{NFR-REPR-01}) forces the engine to own its
randomness and reseed it per generation; and the loopback-only deployment
(\texttt{NFR-SEC-03}, \texttt{NFR-PORT-01}) means the system is for one
researcher on one machine.

Figure~\ref{fig:components} gives the component view. Each box is a component
with a single responsibility; each arrow points from the component that
\emph{requires} an interface to the one that \emph{provides} it, and the label
names the interface. The dashed boundary is the trusted core, the pre-built
components no agent can read or modify: the engine, the verifier, the sandbox
runner, the event log and control files, and the checkpoint store. The untrusted
side is the agent layer (the agent backends and the coding-agent harness) and the
external LLM provider.

The interfaces in Figure~\ref{fig:components} are the load-bearing decisions.
REST + WebSocket is the only channel between the browser and the server. The
\texttt{events.jsonl} / \texttt{control.jsonl} pair is the interface between the
engine and everything else, and is a publish-subscribe boundary: the UI, the CLI,
and the specialist replay all observe the same run without importing the engine
(Section~\ref{sec:design-concurrency}). The remaining interfaces,
\texttt{Backend.run} and JSON over a pipe, are the agent and the sandbox
boundaries of Sections~\ref{sec:design-agents} and \ref{sec:design-sandbox}.

\section{Domain model and business rules}
\label{sec:design-domain}

The domain is described by one static model and two dynamic models, each
answering a different question: the class diagram (Figure~\ref{fig:class})
states which classes exist and how they are related; the candidate state
machine (Figure~\ref{fig:states}) states which transitions a candidate may
undergo; and the generation sequence diagram (Figure~\ref{fig:sequence}) states
the order in which the engine acts over one generation.

\subsection{Class model}

Figure~\ref{fig:class} is the class diagram of the core domain, drawn to match
the modules in \texttt{src/evoalgo} and notated in UML \citep{omg2017uml}; the
\emph{Orchestrator} is the composition root and each component has a lifetime
bound to the run. Two relationships are deliberate design decisions rather than
bookkeeping. The \emph{Population} \emph{aggregates} \emph{Candidate} (open
diamond) rather than composing it, because a candidate outlives culling: it is
written to the checkpoint and the event log before it is dropped from the live
population. And the two abstractions, \emph{ProblemDefinition} and
\emph{Backend}, are what keep this static structure unchanged when a problem or
a provider is added.

\subsection{Candidate state machine}

The candidate is a single state machine, used identically by the engine, the
checkpoint, the event log, and the UI. Figure~\ref{fig:states} shows it. A
candidate is written by an agent in state \texttt{NEW}; the verifier moves it to
\texttt{TESTING}; and it leaves \texttt{TESTING} to exactly one of three terminal
verdicts, \texttt{PASS}, \texttt{FAIL}, or \texttt{CRASH}. Selection may then
move any of the three to \texttt{DISCARDED}. Every transition not drawn raises
\texttt{TransitionError}, enforced by \texttt{Candidate.transition} against the
table in \texttt{candidate.py}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.5\textwidth]{figures/candidate-states.pdf}
  \caption{State machine of a candidate. A timeout maps to \texttt{FAIL} with a
  timeout flag; a runtime exception, a missing function, or a sandbox kill maps
  to \texttt{CRASH}. Any transition not shown is rejected.}
  \label{fig:states}
\end{figure}

The rule is unambiguous and is the one the code enforces: \textbf{a timeout is
\texttt{FAIL} with a timeout flag, and a crash is \texttt{CRASH}}.

\subsection{Business rules}

\textbf{Ranking and selection.} Candidates are ranked by the key
$(\texttt{not passing}\allowbreak, -\texttt{fitness}\allowbreak, \texttt{work\_ratio})$
in \texttt{population.py}: passing before failing, then higher fitness, then
lower work ratio; the same key is implemented independently in the UI
(\texttt{rank} in \texttt{ui/src/state.ts}) so the population table and the
engine agree. Parent selection is tournament selection over the viable
candidates (\texttt{PASS} or \texttt{FAIL}); elitism keeps the top-$k$ by rank
(default $k=2$) regardless of the cull. Selection is the engine's only
randomness, and it is reseeded per generation from
$(\texttt{selection\_seed}, \texttt{generation})$, so a resumed run draws the
same parent stream as an uninterrupted one (\texttt{NFR-REPR-01}). When the
population exceeds its size, the cull keeps the elite and then fills the
remaining slots with passing candidates and failing candidates deduplicated by
failure signature.

\textbf{Stop conditions and plateau.} A run stops when a candidate reaches
fitness $1.0$ within the bound (success), when the generation budget is
exhausted, when the model-call budget is exhausted, or after a configurable
number of consecutive all-failed generations. A plateau does not stop the run;
it is declared at a generation boundary when, over the last
\texttt{plateau\_window} generations, the population best improved neither its
fitness nor its work ratio by \texttt{plateau\_epsilon} (relative), and it only
triggers specialist generation (Section~\ref{sec:design-agents}).

\section{Verification engine design}
\label{sec:design-verifier}

The verification engine is the trusted core of contribution C2. It decides, for
a candidate algorithm, whether it maintains its problem's invariant after every
edge operation in a bounded test universe, and measures how much work it does
relative to recomputing from scratch. The test universe is defined once in
Chapter~\ref{ch:requirements}, Section~\ref{sec:universe}, and is not repeated
here.

\subsection{Correctness by certificate, not by equality}

Raw equality with the offline output cannot be used, because dynamic BFS and DFS
outputs are not unique: two correct algorithms with different tie-breaks produce
different trees. Refinement R1 resolves this: the offline oracle still defines
the semantics and is the efficiency baseline, but the checker accepts any valid
structure by verifying a \emph{certificate}, a property every correct output
satisfies and no incorrect output satisfies. Each problem owns its certificate
in a \texttt{ProblemDefinition} subclass. The certificates are:


\textbf{Dynamic BFS.} The output is a parent tree and a distance field; the
certificate is that the tree spans exactly the vertices reachable from the root,
each non-root vertex has at most one parent that is a graph neighbour, each
distance is one more than its parent's, and the reported distances equal the true
BFS distances.


\textbf{Dynamic DFS.} The output is a parent forest plus discovery and finish
times from one shared counter; the certificate is that the times are a valid
traversal of the parent tree and that the parent of a reachable vertex is a
reachable in-neighbour discovered before it. The checker also enforces
Lemma~1 of \citet{yang2019dynamic}: for an edge $u \to v$ with
$\text{discover}[u] < \text{discover}[v]$, the vertex $v$ must be a tree
descendant of $u$; a predicate that forbade all forward and cross edges would be
wrong, because a directed DFS forest legitimately admits forward edges.

\textbf{Dynamic LBFS.} Lexicographic BFS is defined on undirected graphs
(Refinement R2); the certificate is the (LB) four-point property of
\citet{corneil2008unified}, and the checker accepts any valid ordering with any
start vertex and tie-break. The offline oracle is the partition-refinement LexBFS
of \citet{habib2000lexbfs}.

\textbf{Dynamic SCC.} The output partitions the vertices into strongly connected
components; the certificate is internal reachability, disjointness, coverage,
and maximality, the last checked against the unique SCC partition from Tarjan's
algorithm \citep{tarjan1972dfs} rather than by pairwise merging.

\textbf{Reachability} and \textbf{dynamic MCS} are checked against the true
reachability set and the MCS definition respectively.

\subsection{The two-tier grade and the work ratio}

The engine grades a candidate on two tiers (Refinement R3). The \emph{search
grade} runs during the evolution on every candidate, on a small bound
(\texttt{search\_n\_max}, 4); it takes seconds per candidate. The \emph{final
grade} runs on the best passing candidates on the full bound ($n \le 5$); it
takes minutes. The two tiers cover different graphs and update sequences, so a
candidate that passes the search grade can still fail the final grade, the gap
the tiering exists to close. A result is reported as bounded exhaustive
verification, that is no counterexample within the stated bound, and is never
called a proof.

The efficiency metric is the \textbf{work ratio}, the candidate's measured time
divided by the offline baseline's measured time on the same operation, both
measured in the sandbox with the same clock and the same adaptive repeat
amplification, so the ratio cancels the environment. It is measured wall time,
not instrumented operation counting, because the candidate can patch an operation
counter but not the clock the runner binds before candidate code runs. An
efficiency improvement is declared only when the candidate is fully correct and
its work ratio is below $1$.

\subsection{Chunking, parallel merge, and hang localisation}

The test universe is split into chunks of base graphs, each executed in its own
sandbox subprocess with its own wall-clock timeout, so a correct candidate
finishes within the timeout while one that loops forever on a case fails fast.
The chunks are evaluated in parallel in a process pool and merged in chunk order,
so the parallel result is identical to the serial one; the process-versus-thread
choice is the concurrency decision in Section~\ref{sec:design-concurrency}. When
a chunk times out, the engine localises the hang by re-running it one base graph,
then one sequence, at a time, so the reflector receives a concrete failing case
rather than a bare timeout.

\section{Cooperative agents and the evolutionary loop}
\label{sec:design-agents}

The evolutionary loop is the core application logic of contribution C3. It is a
cooperative multi-agent search in which the agents propose and repair code and
the trusted verifier grades it, in the spirit of large-scale model search
\citep{funsearch2023,alphaevolve2025} applied to program repair
\citep{legoues2012genprog}. The loop is driven by the \texttt{Orchestrator} and
is shown, for one generation, in Figure~\ref{fig:sequence}; the code-level
realisation is in Chapter~\ref{ch:implementation}.

  \centering
  \includegraphics[width=\textwidth]{figures/generation-sequence.pdf}
  \caption{Sequence diagram of one generation: the orchestrator emits
  \texttt{gen\_start}, fills the offspring slots (checking the control channel,
  generating or repairing), verifies each candidate, reflects on failures, adds
  and culls the population, and emits \texttt{gen\_committed}; on a plateau it
  emits \texttt{agent\_spawned}.}
  \label{fig:sequence}
\end{figure}

\subsection{Roles, operators, and the reflection schema}

There are four roles, all implemented as calls to a \texttt{Backend} through the
\texttt{LLMProvider}: the \emph{generator} proposes a new candidate from a parent
(or blank) and the problem interface; the \emph{repairer} is the generator given
a failing candidate and its reflection; the \emph{reflector} writes a structured
reflection for a failing candidate; and the \emph{specialist} is a generator with
an extra focus section, spawned on a plateau. The orchestrator routes every
artifact between the agents, keeping the verifier out of their reach. The repair
prompt is the distinguishing feature of the system, because it converts a bounded
counterexample into a targeted edit rather than a blind rewrite. The operators,
the selection order, the cull, and the budgets are the business rules in
Section~\ref{sec:design-domain}.

The reflection is structured, not free text: the reflector writes a Markdown file
under \texttt{reflections/} with the failure description, the root cause, and the
repair hints. This is the verbal-reinforcement mechanism of \citet{reflexion2023}
applied to code, and it is the input the repairer receives.

\subsection{Dynamic agent generation}

Contribution C3's dynamic-agent variant adds specialists. On a plateau (the rule
in Section~\ref{sec:design-domain}), the system spawns a specialist: the
generator role with a focus written from the dominant signature of the window.
At most \texttt{agent\_budget} specialists are active at once, and the whole
specialist state is derived from the event log (the \texttt{agent\_spawned} and
\texttt{agent\_retired} events), so a resumed run continues with the same
specialists.

\section{Concurrency and synchronisation design}
\label{sec:design-concurrency}

The system is concurrent in three different ways, and each is chosen for a
specific reason. Figure~\ref{fig:processes} shows the runtime processes and the
paths between them.

\begin{figure}[H]
  \centering
  \includegraphics[width=\textwidth]{figures/processes.pdf}
  \caption{Runtime processes and their communication paths. The browser talks to
  the UI server over a WebSocket; the server reads the engine's
  \texttt{events.jsonl} and writes \texttt{control.jsonl}; the engine drives the
  verifier workers through a process pool and the LLM provider over HTTPS; each
  verifier worker spawns a jailed runner subprocess per chunk and reads its
  result over a pipe.}
  \label{fig:processes}
\end{figure}

\subsection{Process, thread, and task model}

The engine is a single Python process and is itself single-threaded. The verifier
fans out to a pool of worker \emph{processes} because the per-chunk work is
CPU-bound Python that the interpreter's global lock would serialise in threads
(Section~\ref{sec:impl-concurrency}). The sandbox runs one jailed
\emph{subprocess} per verifier chunk, so a candidate that loops or forks cannot
slow the engine or the other workers. The UI server is a single asynchronous
process that, for each connected WebSocket, runs a tail task and a command task.

\subsection{Shared resources and their synchronisation}

The shared resources are files, and each has a single-writer, multiple-reader
protocol, which makes the design safe without locks in most cases.
\texttt{events.jsonl} is the canonical instance: a \emph{readers-writers}
solution in which the single writer is the engine and the readers are the server
tail, the resume accounting, and the specialist replay. \texttt{control.jsonl}
is the reverse (written by the server and CLI, read by the engine). The two
resources that genuinely need a lock are the harness workspace and the model
token file, each guarded by an exclusive file lock.


The readers poll the file rather than waiting on a monitor or a condition
variable, and that is the right choice for this boundary. The writer and the
readers are separate processes that communicate only through files, so they share
no memory and there is no shared object a monitor could guard: a monitor
coordinates threads that share memory \citep{hoare1974monitors}, and a condition
variable would need a shared variable to signal on, which across a process
boundary is exactly the file. Polling the file by byte offset is therefore the
simplest correct mechanism, and its cost is a fixed poll interval, not a missed
wakeup. The bounded worker window of the parallel verifier is the one place a
reader can be starved: a worker that is never scheduled because the window is
always full of other chunks. That is starvation, not deadlock; the workers are
not holding a resource and waiting for one another, so Coffman's conditions do
not hold, and the ordered merge guarantees every chunk is eventually served in
turn.

\subsection{Producer-consumer chains and the pipe deadlock}

The three producer-consumer chains are shown in Figure~\ref{fig:processes}. The
last, the sandbox runner producing a result JSON on a pipe that a reader thread
consumes, is where a naive design deadlocks: if the parent writes the input while
also waiting for the child, and the child writes more than the pipe buffer holds,
the child blocks on a full pipe and the parent blocks on the child, and neither
proceeds. The design breaks this by draining the pipes concurrently with the
wait; all four of Coffman's conditions for deadlock \citep{coffman1971deadlock}
must hold for a deadlock to occur, and the concurrent draining breaks the
\emph{hold-and-wait} condition.

\subsection{Races designed out}

Several races are designed out rather than guarded: the \emph{first-connect}
race (the UI connects before the engine has created the run directory) is handled
by the server writing the run's configuration before it replies to a launch; the
\emph{duplicate command} race by the exactly-once rule above; the \emph{reconnect}
race by resuming from the last received sequence number; and the \emph{pause} is a
blocking pause. Each is handled in code in Chapter~\ref{ch:implementation}.

\section{Sandbox and isolation design}
\label{sec:design-sandbox}

The sandbox is the enforcement of the trust boundary. Its threat model is
untrusted generated code: a candidate is Python written by an LLM, and it must be
able to do nothing but compute on the adjacency matrices it is given. A restricted
\texttt{subprocess} environment is not a security boundary (the environment
mapping controls environment variables only), so the design uses an
operating-system isolation mechanism, and the boundary is enforced by the kernel.

\subsection{Isolation by processes and namespaces}

Each candidate chunk runs in its own process, placed in new Linux namespaces
\citep{manNamespaces,silberschatz2018os,tanenbaum2015modern}. The jail is built
with \texttt{unshare} using unprivileged user namespaces only (no root, no extra
packages): a new user namespace (mapped to root inside), a new network namespace
with the interface down, a new mount namespace, a new PID namespace, and a new
IPC namespace. A second user namespace is then created, mapped back to the real
user id. The process runs with an isolated interpreter and a scrubbed
environment.

\subsection{Filesystem view}

Inside the mount namespace the host tree is bound at a private root, and the
directories that hold user data, shared storage, temporary files, system logs,
and host daemon sockets are hidden behind empty read-only temporary filesystems;
only the interpreter's import paths are bound back, the whole tree is made
read-only, and the process pivots its root into it with a fresh private temporary
directory, the only writable location. The candidate source is sent in the input,
not as a path, so the run directory, verifier source, test graphs, and oracle are
absent from the candidate's filesystem.

\subsection{Resource limits}

The jail stops a candidate reading or writing the host; resource limits stop it
exhausting the host. These are set by the runner before candidate code runs, as
soft limits equal to hard limits, so the candidate cannot raise them. They bound
the address space, the CPU time, the per-file size, the open-file-descriptor
count, the core dump, and the process count (four tasks in the runner's user
namespace, so a fork bomb dies quickly and parallel runners do not share the
budget). The exact values and the \texttt{RLIMIT\_*} constants are in
Chapter~\ref{ch:implementation}.


The address-space limit is on virtual memory, not on the resident set, and the
distinction is why it is the right knob. \texttt{RLIMIT\_AS} bounds the virtual
address space a process may map, while the resident set is the subset of pages
that paging actually keeps in RAM; a process can map far more virtual memory than
it touches, and the mapped-but-untouched pages cost no RAM. Bounding the address
space therefore stops a candidate from reserving a terabyte of virtual memory and
then touching only a little of it, which a resident-memory limit would not catch
until the pages were faulted in \citep{silberschatz2018os}. The limit is generous
relative to what a real chunk uses: the measured peak resident set of a dynamic
DFS chunk is 618 MB (\texttt{campaign/chunk\_memory.log}), well under the four
gigabyte ceiling, so the limit bounds abuse without constraining a correct
candidate.

\subsection{Signals, process groups, and IPC}

The runner starts the candidate in its own process group, so when the timeout
fires or the output overflows, the parent kills the whole group, not just the
direct child; this is what stops a forked grandchild from keeping the pipes open
after the runner is killed. The CPU signal handler writes a marker to the error
stream and exits, so the parent can tell a CPU-limit kill from a wall-clock
timeout.

\section{Data and persistence design}
\label{sec:design-persistence}

All state is persisted to the local filesystem as files under a per-run
directory; there is no database. This is a deliberate choice for a
single-writer, single-host research tool, and it is what makes the run
human-inspectable and replayable.

\subsection{The run directory as the data model}

The run directory is the data model. A \emph{run} (named by a unique run id that
namespaces every file so parallel runs never collide) has one
\emph{configuration} and many \emph{generation snapshots}; a generation has many
\emph{candidates}; a candidate has zero or one \emph{reflection} and zero or more
\emph{prompt logs}; and a run has many \emph{events} and many \emph{commands}.
Candidate lineage is carried by the \texttt{parent\_ids} list.



\subsection{Formats, atomicity, and crash recovery}

The configuration is YAML, validated at launch. The generation snapshot is JSON
with a fixed schema version; its fields are the last row of
Table~\ref{tab:events}. The candidate code is a self-contained Python module
implementing the fixed interface; the reflection is Markdown; the event and
control logs are line-delimited JSON; and the results are a run summary JSON and
an efficiency report CSV. A generation is written to a
temporary file and then renamed over the target with an atomic replace, so a
crash mid-write leaves either the old complete file or the new complete file,
never a torn one. The \texttt{COMMITTED} marker names the last fully committed
generation; on resume the engine discards any incomplete file beyond it and
restores the specialist state by replaying the event log.

part of the design. Table~\ref{tab:events} lists every event type, when it is
emitted, and its key payload fields; the fields are the \texttt{RunEvent} union in
\texttt{ui/src/types.ts} together with the final-grade and run-end events emitted
by the orchestrator. Every event also carries \texttt{seq} (the monotonic
sequence number) and \texttt{ts} (the timestamp).

\subsection{Why files and no database}

The data model is small and hierarchical (runs to generations to candidates), so
there is no query benefit from a relational store, and a researcher needs to
inspect state by hand, which files are human-readable for. The single-writer rule
is what makes files safe here, and the append-only event log gives the durability
and replay that a database would otherwise provide (ADR-06 in
Appendix~\ref{app:decisions}).

\section{User interface design}
\label{sec:design-ui}

The user interface is the realisation of contribution C1: an interactive
platform that launches, monitors, replays, and steers a run. It is a single-page
web application that talks to the UI server over REST and a WebSocket, and it is
designed around the event stream, so the live view and the replay view are the
same code. It has three top-level screens, navigated by hash routes: the
\emph{Runs} screen (the landing page), the \emph{New Run} screen (a launch form),
and the \emph{Run} screen (the main view, with a live/replay toggle and the
monitoring and steering panels). Their layout is shown once, in
Chapter~\ref{ch:user-documentation} (Figures~\ref{fig:ud-runs} and
\ref{fig:ud-live}), and is not repeated here.

\subsection{The event-sourced state model}

The central UI decision is that the interface state is a pure reducer over the
event stream: one function, \texttt{applyEvents} in \texttt{ui/src/state.ts},
folds a list of events into the run state, and both the live view and the replay
view call it. This is what makes the registered replay completion signal honest:
replaying generation $k$ is the same reducer applied to fewer events, not a
second rendering path that could disagree with the live view. The run status is
derived, not stored, and the Steer panel offers a research hint and setters for
the model-call budget and the population size.

\subsection{Access control and accessibility}

The server binds to the loopback address by default, and every API request and
WebSocket requires the access token; non-local browser origins are refused, and
there are no roles, so a read-only review is a convention, not an enforced
permission. For accessibility, the controls are semantic with ARIA roles and
labels and keyboard focus is managed; full conformance requires manual testing
with assistive technology, which the automated suite does not assert
(\texttt{NFR-USAB-01}, \citep{wcag22}).


\section{Design decisions and trade-offs}
\label{sec:design-decisions}

The principal decisions are recorded as architecture decision records in
Appendix~\ref{app:decisions}. In one sentence each:
ADR-01 grades a candidate by a per-problem certificate rather than by raw
equality with one offline reference tree; ADR-02 builds the directed test
universe from nauty isomorphism classes and the undirected one from every
labelled graph; ADR-03 uses a two-tier grade, a cheap search bound during the run
and a full bound on the finalists; ADR-04 runs the verifier workers as processes
rather than threads; ADR-05 jails the sandbox with unprivileged Linux namespaces
rather than a restricted subprocess or a container; ADR-06 persists the run as
event-sourced files rather than a database; ADR-07 exposes the same verifier to
an external coding-agent harness as a baseline alongside the built-in agents;
ADR-08 renders the UI with one pure reducer shared by live and replay; and
ADR-09 spawns plateau-triggered specialist agents whose state is derived from the
event log. The next chapter walks through the implementation of each at the code
level, and the testing chapter reports the evidence that the design holds.
