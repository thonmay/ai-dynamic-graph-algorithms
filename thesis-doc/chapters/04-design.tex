This chapter gives the design at the level of mechanisms, detailed enough to

\section{Architectural drivers and overview}
\label{sec:design-architecture}

The architecture is driven by the three registered contributions and the
non-functional requirements in Chapter~\ref{ch:requirements}. C1 (the
interactive research tool) forces a separation between a control plane (the
engine) and an observation plane (the user interface) that does not import the
engine. C2 (the verification engine) forces a hard trust boundary enforced by the
operating system rather than by convention (\texttt{NFR-SEC-01}). C3
(cooperative agents with dynamic generation) forces a pluggable agent layer and
an event stream from which specialist state can be derived. Reliability and
reproducibility (\texttt{NFR-REL-01}, \texttt{NFR-REPR-01}) force checkpointing,
a replayable event log and engine-owned, per-generation-reseeded randomness.

\emph{requires} an interface to the one that \emph{provides} it, and the label

\subsection{Candidate state machine}

The candidate is one state machine shared by the engine, the checkpoint, the
event log and the UI (Figure~\ref{fig:states}): \texttt{NEW} when written,
\texttt{TESTING} under the verifier, then exactly one of \texttt{PASS},
\texttt{FAIL} or \texttt{CRASH}, and possibly \texttt{DISCARDED} by selection.
Any other transition raises \texttt{TransitionError} in
\texttt{Candidate.transition}.

\subsection{Business rules}

\textbf{Ranking and selection.} Candidates are ranked by the key
$(\texttt{not passing}\allowbreak, -\texttt{fitness}\allowbreak, \texttt{work\_ratio})$
in \texttt{population.py}: passing before failing, then higher fitness, then
lower work ratio; the same key is implemented independently in the UI
(\texttt{rank} in \texttt{ui/src/state.ts}) so the population table and the
engine agree. Parent selection is tournament selection \citep{goldberg1989genetic} over the viable
candidates (\texttt{PASS} or \texttt{FAIL}); elitism keeps the top-$k$ by rank
(default $k=2$) regardless of the cull, the elitist strategy of classical genetic
algorithms \citep{holland1975adaptation}. Selection is the engine's only
randomness, and it is reseeded per generation from
$(\texttt{selection\_seed}, \texttt{generation})$, so a resumed run draws the
same parent stream as an uninterrupted one (\texttt{NFR-REPR-01}). When the
population exceeds its size, the cull keeps the elite and then fills the
remaining slots with passing candidates and failing candidates deduplicated by
failure signature.

\textbf{Stop conditions and plateau.} A run stops on success, on the generation
or model-call budget, after consecutive all-failed generations, or at once when
no seed call produced a candidate (an unusable agent backend). A plateau,
declared when the best fitness and work ratio have not improved by
\texttt{plateau\_epsilon} over \texttt{plateau\_window} generations, does not
stop the run; it only triggers specialist generation.

\section{Verification engine design}
\label{sec:design-verifier}

The verification engine, the trusted core of C2, decides whether a candidate
maintains its problem's invariant after every operation of the universe of
Section~\ref{sec:universe}, and measures its work against recomputing.

\subsection{Correctness by certificate, not by equality}

Raw equality with the offline output cannot be used, because dynamic BFS and DFS
outputs are not unique: two correct algorithms with different tie-breaks produce
different trees. Refinement R1 resolves this: the offline oracle still defines
the semantics and is the efficiency baseline, but the checker accepts any valid
structure by verifying a \emph{certificate}, a property every correct output
satisfies and no incorrect output satisfies. Each problem owns its certificate
in a \texttt{ProblemDefinition} subclass. The certificates are:


\textbf{Dynamic BFS.} The output is a parent tree and a distance field; the
certificate is that the tree spans exactly the vertices reachable from the root,
each non-root vertex has at most one parent that is a graph neighbour, each
distance is one more than its parent's, and the reported distances equal the true
BFS distances.


\textbf{Dynamic DFS.} The output is a parent forest plus discovery and finish
times from one shared counter; the certificate is that the times are a valid
traversal of the parent tree and that the parent of a reachable vertex is a
reachable in-neighbour discovered before it. The checker also enforces
Lemma~1 of \citet{yang2019dynamic}: for an edge $u \to v$ with
$\text{discover}[u] < \text{discover}[v]$, the vertex $v$ must be a tree
descendant of $u$; a predicate that forbade all forward and cross edges would be
wrong, because a directed DFS forest legitimately admits forward edges.

\textbf{Dynamic LBFS.} Lexicographic BFS is defined on undirected graphs
(Refinement R2); the certificate is the (LB) four-point property of
\citet{corneil2008unified}, and the checker accepts any valid ordering with any
start vertex and tie-break. The offline oracle is the partition-refinement LexBFS
of \citet{habib2000lexbfs}.

\textbf{Dynamic SCC.} The output partitions the vertices into strongly connected
components; the certificate is internal reachability, disjointness, coverage,
and maximality, the last checked against the unique SCC partition from Tarjan's
algorithm \citep{tarjan1972dfs} rather than by pairwise merging.

\textbf{Reachability} and \textbf{dynamic MCS} are checked against the true
reachability set and the maximum cardinality search definition
\citep{tarjan1984mcs,rose1976algorithmic} respectively.

\subsection{The two-tier grade and the work ratio}

The search grade ($n \le 4$, seconds) runs on every candidate and the final grade
($n \le 5$, minutes) on the best ones (Refinement R3); a search-grade pass can
still fail the final grade, which is the gap the tiering closes. The efficiency metric is the \textbf{work ratio}, the candidate's measured time
divided by the offline baseline's measured time on the same operation, both
measured in the sandbox with the same clock and the same adaptive repeat
amplification, so the ratio cancels the environment. It is measured wall time,
not instrumented operation counting, because the candidate can patch an operation
counter but not the clock the runner binds before candidate code runs. An
efficiency improvement is declared only when the candidate is fully correct and
its work ratio is below $1$.

\subsection{Chunking, parallel merge, and hang localisation}

The universe is split into chunks, each run in its own sandbox subprocess with a
wall-clock timeout, evaluated in a process pool and merged in chunk order so the
parallel result equals the serial one. A timed-out chunk is re-run one graph and
one sequence at a time, so the reflector receives a concrete failing case.

\section{Cooperative agents and the evolutionary loop}
\label{sec:design-agents}

The evolutionary loop of C3 is a cooperative search in which agents propose and
repair code and the trusted verifier grades it, in the spirit of large-scale model
search \citep{funsearch2023,alphaevolve2025} applied to program repair
\citep{legoues2012genprog}. Figure~\ref{fig:sequence} shows one generation.

  \texttt{gen\_start}, fills the offspring slots (selecting a parent per slot, checking the control channel, generating or
  repairing), verifies every new candidate, then reflects on the failed ones
  through the \texttt{Reflector} (with a control point before each call), adds

  emits \texttt{agent\_spawned}.}
  \label{fig:sequence}

\subsection{Roles, operators, and the reflection schema}

There are four roles, all implemented as calls to a \texttt{Backend} through the
\texttt{LLMProvider}: the \emph{generator} proposes a new candidate from a parent
(or blank) and the problem interface; the \emph{repairer} is the generator given
a failing candidate and its reflection; the \emph{reflector} writes a structured
reflection for a failing candidate; and the \emph{specialist} is a generator with
an extra focus section, spawned on a plateau. The orchestrator routes every
artefact between the agents and keeps the verifier out of their reach. The
reflection is structured (failure description, root cause, repair hints), the
verbal-reinforcement mechanism of \citet{reflexion2023} applied to code, so the
repairer turns a bounded counterexample into a targeted edit rather than a blind
rewrite.

\subsection{Dynamic agent generation}

On a plateau the system spawns a specialist, the generator role with a focus
written from the dominant signature of the window; at most
\texttt{agent\_budget} are active, and their state is derived from the
\texttt{agent\_spawned} and \texttt{agent\_retired} events, so a resumed run
keeps them.

\section{Concurrency and synchronisation design}
\label{sec:design-concurrency}

The system is concurrent in three different ways, and each is chosen for a
specific reason. Figure~\ref{fig:processes} shows the runtime processes and the
paths between them.

\begin{figure}[H]
  \centering
  \includegraphics[width=\textwidth]{figures/processes.pdf}
  \caption{Runtime processes and their communication paths. The browser talks to
  the UI server over a WebSocket; the server reads the engine's
  \texttt{events.jsonl} and writes \texttt{control.jsonl}; the engine drives the
  verifier workers through a process pool and the LLM provider over HTTPS; each
  verifier worker spawns a jailed runner subprocess per chunk and reads its
  result over a pipe.}
  \label{fig:processes}
\end{figure}

\subsection{Process, thread, and task model}

The engine is a single Python process whose own logic runs on one thread; the
process pool adds a manager thread that moves work items and results between the
engine and the workers. The verifier
fans out to a pool of worker \emph{processes} because the per-chunk work is
CPU-bound Python that the interpreter's global lock would serialise in threads
(Section~\ref{sec:impl-concurrency}). The sandbox runs one jailed
\emph{subprocess} per verifier chunk, so a candidate that loops or forks cannot
slow the engine or the other workers. The UI server is a single asynchronous
process that, for each connected WebSocket, runs a tail task and a command task.

\subsection{Shared resources and their synchronisation}

The shared resources are files. Most have a single-writer, multiple-reader
protocol, which makes the design safe without locks in most cases.
\texttt{events.jsonl} is the canonical instance: a \emph{readers-writers}
solution in which the single writer is the engine and the readers are the server
tail, the resume accounting, and the specialist replay. \texttt{control.jsonl}
is the reverse: one reader (the engine) and several writers (the CLI and one
command task per open WebSocket). It needs no lock because every command is one
short line appended with \texttt{O\_APPEND} in a single \texttt{write}, which a
local file system applies atomically. The two
resources that genuinely need a lock are the harness workspace and the model
token file, each guarded by an exclusive file lock.


The readers poll the file rather than waiting on a monitor or a condition
variable, and that is the right choice for this boundary. The server tail and the CLI are separate processes from the writer and
communicate with it only through files, so they share no memory and there is no shared object a monitor could guard: a monitor
coordinates threads that share memory \citep{hoare1974monitors}, and a condition
variable would need a shared variable to signal on, which across a process
boundary is exactly the file. (The resume accounting and the specialist replay
read the log inside the writing engine, but only between generations, when it
is not being appended.) Polling the file by byte offset is therefore the
simplest correct mechanism, and its cost is a fixed poll interval, not a missed
wakeup. The bounded worker window of the parallel verifier is where starvation
could in principle arise (a chunk that is never scheduled while others keep
taking the free slots), but it cannot: chunks are submitted strictly in order,
so every chunk is scheduled after at most \texttt{workers} earlier ones. Nor can
the window deadlock: a worker holds no resource that another worker waits for,
so Coffman's conditions do not hold. The two hazards differ in kind \citep{herlihy2012art}: starvation
is a runnable task that is passed over indefinitely, while deadlock is a set of
tasks each blocked on another. The pipe case below is a deadlock, because the
parent and the runner both block, and neither stays runnable.

Communication between the processes is \emph{message passing}, never shared
memory, over three buffered channels: the runner returns one JSON result message
on its saved standard output, a pool worker returns its pickled partial result
through the executor, and the server and the engine exchange control commands and
events as JSON lines in files. None of them needs a shared object, which is why
the sandbox can give each candidate its own address space and IPC namespace.

\subsection{Producer-consumer chains and the pipe deadlock}

The three producer-consumer chains are shown in Figure~\ref{fig:processes}. The
last, the sandbox runner producing a result JSON on a pipe that a reader thread
consumes, is where a naive design deadlocks: if the parent writes the input while
also waiting for the child, and the child writes more than the pipe buffer holds,
the child blocks on a full pipe and the parent blocks on the child, and neither
proceeds. The design breaks this by draining the pipes concurrently with the
wait; all four of Coffman's conditions for deadlock \citep{coffman1971deadlock}
must hold for a deadlock to occur, and the concurrent draining breaks the
\emph{circular wait}: the parent no longer waits for the child while the child
waits for the parent to read.

\subsection{Races designed out}

The \emph{first-connect} race is designed out by writing the run's configuration
before the launch reply, the \emph{duplicate command} race by the exactly-once
acknowledgement in the event log, and the \emph{reconnect} race by resuming from
the last received sequence number.

\section{Sandbox and isolation design}
\label{sec:design-sandbox}

The sandbox enforces the trust boundary against untrusted generated code, which
must be able to do nothing but compute on the matrices it is given. A restricted
\texttt{subprocess} environment is not a security boundary, so the boundary is
enforced by the kernel.

\subsection{Isolation and filesystem view}

Each chunk runs in its own process in new Linux namespaces
\citep{manNamespaces,silberschatz2018os,tanenbaum2015modern}, built with
\texttt{unshare} from unprivileged user namespaces only: user (root inside),
network (interface down), mount, PID and IPC, then a second user namespace mapped
back to the real user, with an isolated interpreter and a scrubbed environment.
In the mount namespace the host tree is bound at a private root, user data,
shared storage, temporary files, logs and daemon sockets are hidden behind empty
read-only tmpfs mounts, only the interpreter's paths are bound back, the tree is
made read-only, and the process pivots into it with a private \texttt{/tmp}. The
candidate source arrives in the input, so the run directory, verifier, test graphs
and oracle are absent from its filesystem.

\subsection{Resource limits}

Resource limits stop a candidate exhausting the host: hard limits the runner sets
before candidate code runs, on address space, CPU time (hard one second above
soft, so the signal below arrives first), file size, descriptors, core dumps and
processes (Section~\ref{sec:impl-sandbox} gives the values). The address-space limit is on virtual memory, not on the resident set, and the
distinction is why it is the right knob. \texttt{RLIMIT\_AS} bounds the virtual
address space a process may map, while the resident set is the subset of pages
that paging actually keeps in RAM; a process can map far more virtual memory than
it touches, and the mapped-but-untouched pages cost no RAM. Bounding the address
space therefore stops a candidate from reserving a terabyte of virtual memory and
then touching only a little of it, which a resident-memory limit would not catch
until the pages were faulted in \citep{silberschatz2018os}. Demand paging is
also why the runner applies the limits only after importing NumPy: the import
maps much more virtual memory than it touches, so a limit set before it would
measure the library rather than the candidate. The limit is generous
relative to what a real chunk uses: the measured peak resident set of a dynamic
DFS chunk is 618 MB (\texttt{campaign/chunk\_memory.log}), well under the four
gigabyte ceiling, so the limit bounds abuse without constraining a correct
candidate.

\subsection{Signals, process groups, and IPC}

Inside the jail, the PID namespace and \texttt{unshare -{}-kill-child} end every
process the candidate forked when the runner dies, so no grandchild can keep the
pipes open. The runner is also started in its own process group, and the parent
kills the whole group on a timeout or an output overflow; that matters only
when the jail is disabled for debugging, where the group kill is what stops a
forked grandchild from holding the pipes. The CPU signal handler writes a marker to the error
stream and exits, so the parent can tell a CPU-limit kill from a wall-clock
timeout. The IPC namespace closes a quieter channel: System V shared-memory segments
are kernel objects that outlive the process that created them, so without it a
candidate's \texttt{shmget} would leave a segment in the host's namespace after
the run. In its own IPC namespace the segment disappears with the jail.

Operating-system errors are handled where they arise rather than turned into
generic failures: \texttt{ProcessLookupError} and \texttt{PermissionError} from
\texttt{killpg} mean the group is already gone, \texttt{BrokenPipeError} on the
feed means the runner died before reading its input, and inside the runner the
limits surface as \texttt{EAGAIN} on \texttt{fork}, \texttt{EFBIG} on a write
past the file limit and \texttt{MemoryError} past the address-space limit, each
reported in the candidate's verdict. Every acquired resource has a release path
that runs on all exits: file and pool handles are context managers, the
workspace lock is released in a \texttt{finally}, and the runner is killed,
reaped and its threads joined before \texttt{\_run\_capped} returns, which
\texttt{test\_sandbox\_leaves\_no\_temp\_files} checks.

\section{Data and persistence design}
\label{sec:design-persistence}

All state is files under a per-run directory, which keeps a run inspectable by
hand and replayable; ADR-06 (Appendix~\ref{app:decisions}) records why there is
no database. The run directory is the data model. A \emph{run} (named by a unique run id that
namespaces every file so parallel runs never collide) has one
\emph{configuration} and many \emph{generation snapshots}; a generation has many
\emph{candidates}; a candidate has zero or one \emph{reflection} and zero or more
\emph{prompt logs}; and a run has many \emph{events} and many \emph{commands}.
Candidate lineage is carried by the \texttt{parent\_ids} list. The configuration
is YAML, validated at launch; the generation snapshot is JSON with a fixed schema
version, its fields the last row of Table~\ref{tab:events}; the candidate code is
a self-contained Python module; the reflection is Markdown; the event and control
logs are line-delimited JSON; and the results are a run summary JSON and an
efficiency report CSV. A generation is written to a temporary file and then
renamed over the target with an atomic replace, so a crash mid-write leaves
either the old complete file or the new complete file, never a torn one. The
\texttt{COMMITTED} marker names the last fully committed generation; on resume the
engine discards any incomplete file beyond it and restores the specialist state by
replaying the event log.

The event vocabulary is part of the design: Table~\ref{tab:events}
(Appendix~\ref{app:tables}) lists each type, when it is emitted and its payload
(the \texttt{RunEvent} union of \texttt{ui/src/types.ts}); every event carries
a monotonic \texttt{seq} and a timestamp.

\section{User interface design}
\label{sec:design-ui}

The interface of C1 is a single-page application over REST and a WebSocket with
three hash-routed screens (Runs, New Run, Run), shown in
Chapter~\ref{ch:user-documentation} (Figures~\ref{fig:ud-runs} and
\ref{fig:ud-live}). The central UI decision is that the interface state is a pure reducer over the
event stream: one function, \texttt{applyEvents} in \texttt{ui/src/state.ts},
folds a list of events into the run state, and both the live view and the replay
view call it. This is what makes the registered replay completion signal honest:
replaying generation $k$ is the same reducer applied to fewer events, not a
second rendering path that could disagree with the live view. The run status is
derived, not stored, and the Steer panel offers a research hint and setters for
the model-call budget and the population size.

The server binds to the loopback address by default, and every API request and
WebSocket requires the access token; non-local browser origins are refused, and
there are no roles, so a read-only review is a convention, not an enforced
permission. For accessibility, the controls are semantic with ARIA roles and
labels and keyboard focus is managed; full conformance requires manual testing
with assistive technology, which the automated suite does not assert
(\texttt{NFR-USAB-01}, \citep{wcag22}).


\section{Design decisions and trade-offs}
\label{sec:design-decisions}

The nine principal decisions are recorded as architecture decision records in
Appendix~\ref{app:decisions}, each with its rejected alternative: certificates
rather than raw equality (ADR-01), nauty classes for directed and all labelled
graphs for undirected problems (ADR-02), the two-tier grade (ADR-03), worker
processes rather than threads (ADR-04), a namespace jail rather than a subprocess
or container (ADR-05), event-sourced files rather than a database (ADR-06), the
coding-agent harness beside the built-in agents (ADR-07), one pure UI reducer for
live and replay (ADR-08), and event-derived plateau specialists (ADR-09).
