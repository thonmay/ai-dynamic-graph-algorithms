This chapter explains how the design of Chapter~\ref{ch:design} is realised in
code. The design chapter states \emph{what} the system does and \emph{why};
here the unit is the module, the function, and the file on disk. Every claim
is made of the source at the current revision (commit \texttt{ebd6766}); where
a behavioural fact matters, the module is named. The implementation is a
Python package (\texttt{evoalgo}) with a command-line interface, a local web
user interface, and a harness mode, all sharing one verifier and one sandbox.
The sections follow the design: the technology stack and repository layout,
the verifier, the sandbox, the agents and the evolutionary loop, the event
log, control channel and user interface, the concurrency mechanisms taken
together, and the shortcomings that remain.

\section{Development environment and technology stack}
\label{sec:impl-stack}

The system is written in Python 3.11 or later \citep{python311} and a
React/TypeScript user interface. The interpreter floor is set by
\texttt{requires-python = ">=3.11"} in \texttt{pyproject.toml}; the code uses
3.11 typing and the \texttt{asyncio} task APIs. All dependency versions are
pinned exactly, not by range, so a build is reproducible from the manifest
alone. The Python pins, read from \texttt{pyproject.toml}, are
\texttt{numpy==2.4.6} and \texttt{pyyaml==6.0.3}; in the \texttt{api} extra,
\texttt{openai==3.35.1} and \texttt{httpx==0.28.1}; in the \texttt{ui} extra,
\texttt{fastapi==0.143.2}, \texttt{uvicorn==0.54.0} and
\texttt{websockets==15.0.1}; and in the \texttt{dev} extra,
\texttt{pytest==9.1.1}. The interface pins, read from
\texttt{ui/package.json}, are \texttt{react 19.3.1} and
\texttt{react-dom 19.3.1}, with \texttt{typescript 7.0.2}, \texttt{vite
8.3.4}, \texttt{vitest 5.0.5}, \texttt{@vitejs/plugin-react 6.1.2} and
\texttt{@types/react 19.3.0} in the development dependencies.

Each choice is made for a specific reason. \textbf{NumPy}
\citep{harris2020numpy} is used only where a dense adjacency matrix is the
natural representation: the offline oracles and the sandbox runner index a graph
as a \texttt{numpy} array, and the runner converts a candidate's returned array
back to plain Python with \texttt{ndarray.tolist} before it crosses the process
boundary. \textbf{PyYAML} serialises the run configuration and the problem-pack
manifests. \textbf{FastAPI} \citep{fastapi} and \textbf{Uvicorn} provide the
web server and its asynchronous runtime; FastAPI's \texttt{websocket} endpoint
lets the server stream events and accept commands over one connection
\citep{rfc6455}. \textbf{OpenAI} and \textbf{httpx} are the client for any
OpenAI-compatible chat endpoint. \textbf{Pytest} \citep{pytest} runs the Python
suite and \textbf{Vitest} \citep{vitest} the TypeScript reducer tests;
\textbf{Vite} \citep{vite} builds the interface into \texttt{ui\_dist}, and
\textbf{React} \citep{react} with \textbf{TypeScript} \citep{typescript}
implements it.

Two non-Python tools are part of the runtime environment. The graph universe
is not generated at run time: it is a set of committed \texttt{nauty} data
files, produced offline with the \texttt{nauty 2.7r4} binaries \texttt{geng}
and \texttt{directg} \citep{mckay2014nauty}; the provenance and the OEIS
class-count cross-checks are recorded in the \texttt{README.md} that ships
with the data files, so the \texttt{nauty} command line is not required at run
time. The sandbox jail is built with \texttt{unshare} from util-linux, which
creates the user, network, mount, pid and IPC namespaces the jail needs
(Section~\ref{sec:impl-sandbox}); the jail fails closed on a host without
unprivileged user namespaces.

Lean~4 appears in the code only as a research byproduct: the optional
\texttt{formalize} step (\texttt{formalize.py}) asks a prover agent to
formalise the best correct candidate, but it is experimental, never gates a
run, and is not a committed deliverable.

The engine is a flat package with the dependencies flowing in one direction:
the orchestrator imports the verifier, sandbox, population, event log,
checkpoint, provider and specialists, and none of those imports the orchestrator.
The agent layer is a subpackage; the problem definitions live in a single
module. The interface is a separate npm project under \texttt{ui/}; its build
output is committed under \texttt{src/evoalgo/ui\_dist} so the Python package
serves it without a Node toolchain at run time.

\paragraph{Version control.} The project is a single git repository on the
GitHub remote \texttt{ai-dynamic-graph-algorithms}; the thesis documents the
code at HEAD. The commits that shaped the final system, in order, are:
\texttt{c1fe044} (security: jail untrusted candidates, allow-list the agent
environment, add the UI access token), \texttt{8f7206c} (Yang et al.'s fully
dynamic DFS \citep{yang2019dynamic}, Algorithms 2 to 5, as a verifier
reference, plus seven one-line mutations of it), \texttt{e9fcf59} (dynamic
agent generation: specialists spawned on a plateau), \texttt{eaf77ee} (the
bug-hunt fixes: the DFS and SCC checker holes, sandbox and harness hardening,
the eight-seed eval2), and \texttt{7895107} (sandbox resource limits, the UI
failure-patterns panel, the LBFS fault corpus).

\paragraph{Review and debugging.} Non-trivial changes were reviewed by
independent review agents before merging: after the campaigns, five read-only
review agents and one security agent tried to break the tool, and the confirmed
findings are recorded in \texttt{campaign/analysis.md}
(Section~\ref{sec:impl-shortcomings} and the testing chapter's defect table);
each was fixed with a regression test, so the fixes are guarded by the suite.
Three debugging techniques recur. \emph{Hang localisation}: when a verifier
chunk times out, \texttt{\_locate\_hang} re-runs it one base graph at a time,
then one sequence at a time, with a short per-probe timeout, so the reflector gets a concrete failing
graph and operation rather than a bare ``timeout''.
\emph{Failing-case reports}: every failed candidate carries a structured
\texttt{failing\_case} (graph, operation, violated invariant clause) that the
reflector reads and the UI's failure-patterns panel aggregates.
\emph{Event-log replay}: because the whole run is recorded in
\texttt{events.jsonl}, a hang or a wrong verdict is reproduced by replaying the
log into the UI reducer or by re-running the verifier on the recorded candidate.

\paragraph{Manifests.} The Python dependencies are pinned in
\texttt{pyproject.toml} (Section~\ref{sec:impl-stack}); the interface
dependencies are pinned in \texttt{package.json} and locked by
\texttt{package-lock.json} under \texttt{ui/}. 

\section{Verifier implementation}
\label{sec:impl-verifier}

The verifier (Section~\ref{sec:design-verifier}) is three cooperating
modules: \texttt{graph\_generator.py} builds the test universe,
\texttt{verifier.py} drives the sandbox and merges the results, and
\texttt{problem\_definitions.py} supplies the per-problem invariant checker
and the offline oracle.

\paragraph{Graph generation.} \texttt{graph\_generator.py} decodes the
committed \texttt{nauty} files: \texttt{decode\_digraph6} reads the
\texttt{digraph6} format (an \texttt{\&} header, a \texttt{n+63} size byte, and
the full $n \times n$ adjacency matrix packed row by row into 6-bit groups) and
\texttt{decode\_graph6} does the same for the undirected files.
\texttt{generate\_test\_graphs} assembles the universe: for a directed problem
it loads the non-isomorphic representatives (the \texttt{directed} files, or
the \texttt{rooted} files when the problem fixes a source at vertex 0) and
appends \texttt{relabels\_per\_class} deterministic random relabelings of each
representative; for an undirected problem it enumerates every labelled graph up
to the bound. The operation sequences come from two generators:
\texttt{generate\_operation\_sequences} produces \texttt{seq\_count} seeded
random sequences of up to \texttt{seq\_len\_max} legal edge flips, and
\texttt{\_exhaustive\_flip\_sequences} (in \texttt{verifier.py}) appends one
length-1 sequence per possible edge, the ``every possible edge operation''
clause of the verification contract.

\paragraph{The problem interface.} Each problem is a subclass of
\texttt{ProblemDefinition}, an abstract base class with four abstract methods:
\texttt{extract\_result} reads the maintained result out of the candidate's
state, \texttt{check\_invariant} decides whether the state is valid for the
current graph, \texttt{offline\_compute} is the reference algorithm, and
\texttt{baseline\_work} estimates its cost. The \texttt{offline\_source}
property returns a self-contained string form of the oracle that the sandbox
runner \texttt{exec}s to time the baseline alongside the candidate. The six
subclasses, \texttt{DynamicBFS}, \texttt{DynamicDFS},
\texttt{DynamicMCS}, \texttt{DynamicSCC}, \texttt{Reachability} and
\texttt{DynamicLBFS}, are registered in the \texttt{PROBLEMS} dictionary and
looked up by \texttt{get\_problem}. The checkers are certificate-based
(Refinement R1 in the requirements chapter): for BFS the parent tree and the
distance field are certified against the oracle's distances; for DFS the
parent, discover and finish times are certified by laminarity and by the
absence of a forward-cross edge; for LBFS the ordering is certified by the
four-point property \citep{corneil2008unified}. Listing~\ref{lst:dfs-cert}
shows the DFS forward-cross-edge clause, the direct implementation of Yang et
al.'s Lemma 1 \citep{yang2019dynamic}: for an edge $u \to v$ whose discover
time is earlier than $v$'s, $v$ must be a tree descendant of $u$, otherwise
the times cannot be those of any DFS.

\begin{lstlisting}[language=Python, basicstyle=\ttfamily\scriptsize,
  caption={The DFS certificate's forward-cross-edge clause
  (\texttt{problem\_definitions.py}, \texttt{DynamicDFS.\_verify\_dfs\_certificate}).},
  label={lst:dfs-cert}]
        # Yang et al. Lemma 1: no forward-cross edge. For an edge u->v with
        # discover[u] < discover[v], v must be a tree descendant of u.
        for u in reachable:
            for v in reachable:
                if u != v and graph[u, v] == 1 and discover[u] < discover[v]:
                    if u not in ancestors[v]:
                        return False

        return True
\end{lstlisting}

\paragraph{Chunking and parallel evaluation.} \texttt{Verifier.verify} splits
the test universe into chunks of \texttt{chunk\_size} base graphs, each
executed in its own sandbox subprocess with its own wall-clock timeout. The chunk size is auto-tuned: 2000 for the serial path, 1000 when parallel,
so a correct candidate finishes a chunk well under the timeout while a candidate
that loops forever on one case hits the per-chunk timeout and fails fast. When
\texttt{workers > 1} the chunks are evaluated by a \texttt{ProcessPoolExecutor}
in a sliding window of at most \texttt{workers} in-flight chunks
(\texttt{\_merge\_parallel}); each worker rebuilds the problem and the sandbox
from a plain picklable context, runs the sandbox for its chunk, and returns a
compact partial result. The parent merges the partials \emph{in chunk order},
so the merged result is identical to the serial path. Processes rather than threads are used because the per-chunk
checking is CPU-bound Python (Section~\ref{sec:impl-concurrency}).

\paragraph{Adaptive timing.} The work ratio is candidate time over offline
time, measured by repeating each update and dividing. The repeat count is
adaptive: \texttt{verify} targets about 500{,}000 total timed calls (candidate
plus offline) and lowers \texttt{repeat} toward 1 as the universe grows, so
timing stays meaningful without dominating wall time. Each repeat gets its own
copy of the graph and its own deep copy of the state, made \emph{outside} the
timed region, so a candidate that caches by graph object cannot turn the
repeats into lookups.

\paragraph{Hang location.} \texttt{\_locate\_hang} runs after a chunk timeout:
it re-executes the chunk one base graph at a time with a 3-second probe
timeout, and for the first hanging graph one sequence at a time, giving up
after 400 graphs or 60 seconds. The result is a concrete \texttt{hang} record
(graph, sequence, operations) attached to the failing case, which is what the
reflector and the UI's failure panel show.

\paragraph{Self-test.} \texttt{src/evoalgo/selftest/} holds the acceptance
evidence for the verifier. \texttt{references.py} contains two honest
references per corpus problem: a \emph{validate-or-rebuild} dynamic algorithm
and an \emph{equivalent control} that differs only in its tie-break, so the
checker must accept a different valid output; the DFS reference is informed by
Yang et al.'s Lemma 1 for its keep/rebuild decision. \texttt{faults.py} is the
seeded-fault corpus: each fault is a one-line mutation of the reference,
expressed as an override of a single named code block, so each fault is a clean
diff against the known-good and carries a documented minimal counterexample at
$n \le 5$. The self-test drives the real verifier over the full $n \le 5$
universe and asserts that every reference and control is accepted and every
real fault is rejected, the zero-false-negatives completion signal (the testing
chapter reports the counts).

\section{Sandbox implementation}
\label{sec:impl-sandbox}

The sandbox (Section~\ref{sec:design-sandbox}) executes untrusted, LLM-written
candidate code. The design's trust boundary is realised in
\texttt{sandbox.py} as two layers: a Linux namespace jail that stops a
candidate reading or writing the host, and resource limits that stop it
exhausting the host. The candidate source travels in the JSON input, not as a file path, so the
run directory is never visible inside the jail.

\paragraph{The jail.} \texttt{\_jail\_argv} builds the command line
\texttt{unshare -rnmpfi --kill-child sh -c <script> ... exec unshare -U
--fork --kill-child python}. The first \texttt{unshare} creates five
namespaces at once \citep{manNamespaces}: a \emph{user} namespace mapped to
root inside (\texttt{-r}), a \emph{network} namespace with loopback down
(\texttt{-n}), a \emph{mount} namespace (\texttt{-m}), a \emph{pid} namespace
(\texttt{-p}), and an \emph{IPC} namespace (\texttt{-i}), the last so a SysV
shared-memory segment a candidate creates cannot outlive it on the host;
\texttt{--kill-child} makes \texttt{unshare} kill the child when it exits.
The mount script (\texttt{\_JAIL\_SCRIPT}) then bind-mounts the host tree at
\texttt{/mnt}; hides a fixed list of host directories (\texttt{HIDDEN\_DIRS}:
\texttt{/home}, \texttt{/proj}, \texttt{/var}, \texttt{/opt}, \texttt{/boot},
\texttt{/etc/ssh}, and others) behind empty 1 MB tmpfs mounts, so user data,
the shared NFS, system logs and daemon sockets are not readable; bind-mounts
back only the interpreter's own prefixes (the venv and base install, found by
\texttt{\_keep\_paths}) because the runner needs \texttt{numpy}; makes the whole
tree read-only; mounts a fresh 64 MB tmpfs over \texttt{/tmp} and a fresh
\texttt{/proc}; and \texttt{pivot\_root}s into the new tree
\citep{kerrisk2010tlpi}. The read-only remount is the one step
\texttt{mount -o ro,recursive} does not do reliably across submounts, so it is
done with the \texttt{mount\_setattr(2)} system call (number 442) and the
\texttt{AT\_RECURSIVE} flag, invoked through \texttt{ctypes} in the
\texttt{\_RDONLY\_SRC} snippet. A second \texttt{unshare -U} then maps the
candidate back to its real uid and gid, so it keeps no capabilities over its
mounts \citep{silberschatz2018os}; the candidate runs as pid 1's child, not
pid 1, because pid 1 ignores signals it has no handler for.

\paragraph{The runner template.} \texttt{\_RUNNER\_TEMPLATE} is a Python
program the sandbox \texttt{exec}s inside the jail. It binds the trusted
objects \emph{before} any candidate code runs, because the candidate shares
the interpreter and could otherwise patch them: it captures
\texttt{\_dumps = json.dumps}, \texttt{\_write = os.write}, and
\texttt{\_out = os.dup(1)}, the last a saved copy of the standard-output file
descriptor that becomes the result channel. It then applies the resource
limits (below), installs a \texttt{SIGXCPU} handler, redirects the candidate's
\texttt{sys.stdout} to \texttt{sys.stderr} (so the candidate's prints cannot
corrupt the result channel), and only then \texttt{exec}s the candidate source
and calls its \texttt{init}/\texttt{insert\_edge}/\texttt{delete\_edge}. The
result is written with the saved \texttt{\_dumps} and \texttt{\_write} to the
saved \texttt{\_out} descriptor; the candidate's prints go to stderr, which the
parent keeps only as a 64 KB tail.

\paragraph{Resource limits.} The limits are set by the runner before the
candidate code, with the soft limit equal to the hard limit so the candidate
cannot raise them (raising a hard limit needs \texttt{CAP\_SYS\_RESOURCE} in
the initial user namespace, which it does not have)
\citep{tanenbaum2015modern}. Listing~\ref{lst:limits} shows
\texttt{\_limits}: 4 GB of virtual address space (\texttt{RLIMIT\_AS}), CPU
time equal to the wall-clock timeout plus 5 seconds (\texttt{RLIMIT\_CPU}),
16 MB per file (\texttt{RLIMIT\_FSIZE}, which also bounds memory files such as
\texttt{memfd}), 64 open file descriptors (\texttt{RLIMIT\_NOFILE}), no core
dump (\texttt{RLIMIT\_CORE}), and, only when jailed, 4 processes
(\texttt{RLIMIT\_NPROC}). \texttt{RLIMIT\_AS} bounds the virtual address space,
which is larger than the resident set, so a candidate that maps far more virtual
memory than it touches is stopped. \texttt{RLIMIT\_NPROC} counts per user
namespace, and every runner has its own, so parallel verifier workers do not
share the budget.

\begin{lstlisting}[language=Python, basicstyle=\ttfamily\scriptsize,
  caption={The rlimits the runner applies to itself (\texttt{sandbox.py},
  \texttt{\_limits}).}, label={lst:limits}]
def _limits(timeout: float, jailed: bool) -> dict[str, int]:
    limits = {"RLIMIT_AS": MEMORY_LIMIT_MB << 20,
              "RLIMIT_CPU": int(timeout) + CPU_GRACE_SECONDS,
              "RLIMIT_FSIZE": MAX_FILE_MB << 20,
              "RLIMIT_NOFILE": MAX_OPEN_FILES,
              "RLIMIT_CORE": 0}
    if jailed:
        limits["RLIMIT_NPROC"] = MAX_PROCESSES
    return limits
\end{lstlisting}

The \texttt{SIGXCPU} handler writes a marker to a saved copy of stderr and
calls \texttt{os.\_exit(152)}; the CPU limit is set with the hard limit one
second above the soft, so the kernel sends \texttt{SIGXCPU} at the soft limit
and \texttt{SIGKILL} at the hard one, and a candidate that replaces the
handler is killed one second later and reported as killed.

\paragraph{Capped execution and the pipe deadlock.} The parent runs the runner
with \texttt{\_run\_capped}, a \texttt{subprocess.run} with bounded memory.
The subprocess is started in its own session
(\texttt{start\_new\_session=True}), so it leads a process group that the
parent can kill wholesale with \texttt{os.killpg(pid, SIGKILL)}; this matters
in the unjailed mode, where a forked child of the candidate would otherwise
keep the pipes open after the runner is killed \citep{herlihy2012art}. Three
daemon threads run concurrently with the parent's wait: a \emph{feed} thread
that writes the JSON input to the runner's stdin, and two \emph{drain} threads,
one per output pipe, that read with a cap. Listing~\ref{lst:run-capped} shows
the thread setup and the wait.

\begin{lstlisting}[language=Python, basicstyle=\ttfamily\scriptsize,
  caption={Concurrent feed and drain in \texttt{sandbox.py},
  \texttt{\_run\_capped}.}, label={lst:run-capped}]
    threads = [threading.Thread(target=feed, daemon=True),
               threading.Thread(target=_read_capped,
                                args=(proc.stdout, stdout_cap, False, out), daemon=True),
               threading.Thread(target=_read_capped,
                                args=(proc.stderr, stderr_cap, True, err), daemon=True)]
    for t in threads:
        t.start()
    timed_out = False
    try:
        proc.wait(timeout=timeout)
    except subprocess.TimeoutExpired:
        timed_out = True
    kill()  # whatever of the group is left (nothing, jailed: --kill-child)
    proc.wait()
    for t in threads:
        t.join()
\end{lstlisting}

The reason the drains are separate threads, rather than read after the wait,
is the classic pipe deadlock \citep{coffman1971deadlock}: a pipe has a finite
kernel buffer, so if the runner writes more than the buffer holds to stdout or
stderr and the parent is blocked in \texttt{wait} (or in writing stdin), the
runner blocks on the full pipe and the parent blocks on the runner, and neither
makes progress. Draining both pipes concurrently with the wait keeps the runner
from blocking on output. The stdout drain is capped at 256 MB and kills the
process group on overflow; the stderr drain keeps only the last 64 KB. After
the wait (or timeout) the parent kills whatever of the process group is left,
waits for the runner, and joins the three threads.

\paragraph{Result classification.} Each subprocess outcome is mapped by
\texttt{execute\_batch} to a \texttt{SandboxResult} of status \texttt{ok},
\texttt{crash} or \texttt{timeout}. A wall-clock timeout, a stdout overflow, the
CPU-limit marker
in the stderr tail, and a \texttt{SIGKILL} (which, through the namespace, shows
as a signal-death message) are each a timeout; a non-zero exit with no stdout,
and a result that is not valid JSON (including a deeply nested forged result),
are crashes. A crash or timeout is a failure of the candidate, never a pass,
and never aborts the run.

\section{Agents and the evolutionary loop}
\label{sec:impl-agents}

The agents and the loop (Section~\ref{sec:design-agents},
Section~\ref{sec:design-architecture}) are realised in the orchestrator, the
provider, and the agent backends. The orchestrator is the composition root: it
owns the run configuration, the problem, the sandbox, two verifiers (the
search grade and the final grade), the checkpoint, the provider, the reflector,
the population, the event log and the control channel, and drives the loop.

\paragraph{One generation.} \texttt{Orchestrator.step\_generation} executes one
generation and is the code that Figure~\ref{fig:sequence} in the design chapter
depicts. It reseeds parent selection (the engine's only randomness, reseeded
from \texttt{(selection\_seed, generation)} so a resumed run draws the same
stream), emits \texttt{gen\_start}, and fills the offspring slots: the population
size minus the passing candidates already present, split between \emph{repair}
(failed candidates that have a reflection) and \emph{fresh} (a tournament
parent, or none), plus one extra fresh candidate when diversity is low and, when
dynamic agents are enabled, one per active specialist. Each phase checks the
model-call budget and passes through the \texttt{\_before\_call} control point,
so a pause or stop waits for at most one agent call. The new candidates are then
verified, reflected on failure, added, culled, and the generation committed.

\paragraph{Selection and cull.} \texttt{Population} ranks candidates by the
key (passing before failing, then higher fitness, then lower work ratio), so a
timed-out failure that reports fitness 1.0 never outranks a real pass.
\texttt{select\_parents} is tournament selection over the viable candidates
(PASS or FAIL) with a tournament size of \texttt{min(3, viable)}, using a
private \texttt{random.Random} instance so selection does not depend on other
users of the global random. \texttt{cull} keeps the top-\texttt{elitism\_k} as
the elite, always keeps passing candidates (ranked by work ratio), and
deduplicates failing candidates by failure signature, so the population
explores distinct failure modes.

\paragraph{The provider and the backend protocol.} The orchestrator talks to
the model only through \texttt{LLMProvider}, which builds the problem prompt
(problem definition, pack brief, research goal, live hint) and dispatches each
role call to a backend. The backend is the \texttt{Backend} protocol in
\texttt{agents/base.py}, a single method \texttt{run(Task) -> CallResult}; a
\texttt{Task} carries the role, candidate id, problem prompt and role-specific
inputs, and a \texttt{CallResult} carries whether the output file was written,
the summary, any error, and the token usage. \texttt{make\_backend} builds the
backend named by \texttt{config.provider}: the \texttt{api} backend is the
built-in tool loop, the \texttt{enlcode} (and \texttt{claude}, \texttt{codex})
backends are harnesses, and the \texttt{mock} backend is scripted for tests.

\paragraph{The api backend tool loop.} \texttt{ApiBackend.run} is a bounded
loop over an OpenAI-compatible endpoint: it sends the system prompt and task
message with the \texttt{Toolbox} function-tool schemas and repeats, calling
the model, and if it returns tool calls, executing each through the
\texttt{Toolbox} and feeding the results back, until it returns no tool call.
The loop is bounded by \texttt{agent\_max\_steps} (model turns) and
\texttt{agent\_max\_seconds} (wall clock), and a reply that hits the output
length limit without a tool call is nudged once and then fails the call. The
\texttt{Toolbox} tools are \texttt{read\_file} (confined to the run's
\texttt{candidates/}, \texttt{reflections/} and the pack folder),
\texttt{write\_candidate} and \texttt{edit\_candidate} (only the single output
file of the call; \texttt{edit} requires the old text to occur exactly once),
\texttt{run\_examples} (the small public example set, never the hidden
verifier), and \texttt{write\_reflection} (for the reflect role). Every tool
result is clipped so a large file or failure dump cannot flood the context; a
failed call (network, auth, malformed response) is recorded as one failed call
and the loop continues.

\paragraph{The harness backends.} \texttt{HarnessBackend} is a template method:
\texttt{run} builds the same role prompt as the api backend plus the output path
and the rule that the agent may not run the project's verifier, then calls the
subclass's \texttt{command} to build the argv and \texttt{parse} to read the
result, running it with \texttt{subprocess.run} under a timeout and an
allow-listed environment (\texttt{harness\_env} keeps only a fixed set of
variables plus the harness's own model-access variables, so the user's
unrelated keys are not handed to the agent). The subclasses are
\texttt{EnlcodeBackend}, \texttt{ClaudeBackend} and \texttt{CodexBackend}; only
the enlcode path is exercised in this project.

\paragraph{Reflection.} 	exttt{Reflector.reflect} reads a failed candidate's source and its
	exttt{failing\_case}, calls the provider's reflect role, and stores the
agent's reflection under 	exttt{reflections/}, one markdown file per candidate
(writing the provider's summary if the agent did not write the file itself).
The reflection is what makes the candidate repairable in a later generation.

\paragraph{Dynamic agent generation.} \texttt{specialists.py} derives all
specialist state by replaying the event log, so a resumed run continues with the
same specialists. \texttt{specialists(events)} folds the
\texttt{agent\_spawned}, \texttt{agent\_retired}, specialist
\texttt{candidate\_generated} and \texttt{gen\_committed} events into the list
of specialists, tracking how many candidates each produced and when it last
improved the population best. \texttt{boundary\_actions} runs at the
\texttt{\_agent\_boundary} after each commit: it retires a specialist that has
used its generation budget or gone a full plateau window without gain, and, if
the population best has plateaued (neither fitness nor work ratio improved by
\texttt{plateau\_epsilon} over the window) and there is budget, it spawns a new
specialist whose focus is written from the window's signature (the dominant
failing update kind, or the best work ratio). In the next generation each active
specialist derives one candidate from the population best with its focus in the
task.

\paragraph{Budgets and stop conditions.} \texttt{\_check\_stop\_conditions}
sets the stop reason on a passing candidate (when early stop is on), the maximum
generation count, \texttt{max\_consecutive\_all\_failed} generations in a row,
or the model-call budget; the budget is \texttt{model\_calls}, updated from the
provider's call count after every agent call, and is the sum over the whole run,
not per generation.

\paragraph{Token refresh.} The EricAI token is short-lived and is refreshed
in \texttt{\textasciitilde/.ericai\_token\_env}. \texttt{refresh\_ericai\_token}
runs the \texttt{ericai} CLI to mint a fresh token and writes the file under an
exclusive \texttt{fcntl.flock} on a sidecar lock file, re-checking after waiting
so that parallel runs refresh only once between them; the file is written to an
\texttt{O\_EXCL} temporary and \texttt{os.replace}d into place with mode 600.
The api backend re-reads the token on every call and forces one
refresh-and-retry on a 401.

\section{Event log, control channel and the user interface}
\label{sec:impl-ui}

The engine and the interface never import each other; they are connected by
two append-only JSON-Lines files in the run directory
(Section~\ref{sec:design-persistence}, Section~\ref{sec:design-concurrency}).
\texttt{events.jsonl} is written by the engine and read by the interface;
\texttt{control.jsonl} is written by the interface (or the CLI) and read by
the engine at control points.

\paragraph{The event log.} \texttt{EventLog.emit} assigns each event a
monotonically increasing \texttt{seq} (rebuilt from the file on reopen, so a
resumed run continues the numbering) and appends it with
\texttt{\_append\_line}: the record is serialised to one line and written,
flushed, and \texttt{fsync}ed, so an event is durable before the engine moves
on. Readers take only complete, newline-terminated lines
(\texttt{\_read\_complete\_lines} stops at the last newline and skips malformed
lines), so a reader never sees a half-written record.

\paragraph{The control channel.} \texttt{ControlChannel} is the engine side of
\texttt{control.jsonl}. A command counts as handled once its id appears in a
\texttt{control\_ack} or \texttt{control\_reject} event, and the handled set
is rebuilt from the event log on construction, so a command is applied exactly
once even across a resume: a channel rebuilt after a crash sees the
acknowledgements already in the log and does not re-deliver the command.
\texttt{pending} returns the not-yet-acknowledged commands in the order they
were sent. The engine applies them at \texttt{\_control\_point}, called before
every agent call and at generation boundaries; while paused it loops, polling
the control file at the poll interval, until resumed or stopped.

\paragraph{The server.} \texttt{server.py} builds a FastAPI app
(\texttt{create\_app}). Every \texttt{/api} request and the websocket need the
access token, checked in constant time with \texttt{hmac.compare\_digest}
(from an HttpOnly cookie for the browser or a bearer header for scripts);
requests carrying a browser \texttt{Origin} from a non-local host are refused.
Launching a run (\texttt{POST /api/runs}) validates the request, writes the
run's \texttt{config.yaml} \emph{before} replying (so the UI's first websocket
connect does not race an absent run directory), and starts the engine with
\texttt{subprocess.Popen} in a new session, its stdout to a launch log. The
websocket endpoint (\texttt{/api/runs/{run\_id}/ws?from=N}) accepts, sends the
unacknowledged commands first, and runs two \texttt{asyncio} tasks:
\texttt{\_tail}, which polls \texttt{events.jsonl} by byte offset every 0.5
seconds, keeps a partial-line buffer, and sends events with \texttt{seq >= N}
(the backlog, then live) plus an engine-liveness message on each change; and
\texttt{\_commands}, which receives control messages, validates them, and
appends them to \texttt{control.jsonl}. The endpoint waits for the first of
the two tasks to finish and cancels the other, so a disconnect tears down both.

\paragraph{The interface.} The interface (Section~\ref{sec:design-ui}) is a
single-page React application whose state is a pure reducer.
\texttt{ui/src/state.ts} defines
\texttt{applyEvents}, which takes the current \texttt{RunState} and a batch of
events and returns a new one; it ignores any event with \texttt{seq <= lastSeq}
(so a duplicate or a replayed event is a no-op) and updates the candidates, the
generations, the log, the pending commands and the specialists.
\texttt{failurePatterns} aggregates the verified candidates up to the viewed
generation into counts by failure kind (init, insert, delete, crash, timeout)
and by the size of the first failing graph; \texttt{rank} mirrors the engine's
population ranking so the UI's ordering matches the checkpoint's; and
\texttt{deriveStatus} combines the events, the pending commands and the engine
liveness into the single status the user sees. Live monitoring and replay both
run through the same \texttt{applyEvents}.

The stream client, \texttt{ui/src/api.ts}, owns the websocket and the
reconnect. It connects with \texttt{?from=lastSeq+1}, so a reconnect resumes
from the last event received rather than replaying the whole log; on close it
reconnects with exponential backoff, $500 \cdot 2^{\text{retry}}$ milliseconds
capped at 10 seconds, resetting the retry count on a successful open.
Listing~\ref{lst:reconnect} shows the connect and the backoff.

\begin{lstlisting}[language=TypeScript, basicstyle=\ttfamily\scriptsize,
  caption={Reconnect with backoff and resume from the last sequence
  (\texttt{ui/src/api.ts}, \texttt{useRunStream}).},
  label={lst:reconnect}]
    const connect = () => {
      const url = new URL(
        `api/runs/${encodeURIComponent(runId)}/ws?from=${lastSeq.current + 1}`,
        location.href)
      const ws = new WebSocket(url)
      ws.onclose = () => {
        if (!closed) reconnect = window.setTimeout(
          connect, Math.min(10_000, 500 * 2 ** retry++))
      }
    }
\end{lstlisting}

The producer-consumer structure runs through the whole system. The engine is
the producer of events; \texttt{events.jsonl} is the queue; the server's
\texttt{\_tail} task is the consumer that forwards to the websocket; the UI
reducer is the final consumer. The control channel is the reverse: the UI
produces commands, \texttt{control.jsonl} is the queue, and the engine's
\texttt{\_control\_point} consumes them. Inside the sandbox, the runner is the
producer on the stdout pipe and the drain thread is the consumer, with the cap
acting as back-pressure that kills the producer rather than letting the buffer
grow.

\paragraph{Thread safety and the GIL.} The engine itself is single-threaded;
the only threads it creates are the three short-lived drain/feed threads in
\texttt{\_run\_capped}, which communicate with the parent only through the
subprocess pipes and two result dictionaries written by a single thread each.
The parallel verifier uses processes, not threads, and this is deliberate:
CPython's global interpreter lock means CPU-bound Python in threads does not
run in parallel, so threading the invariant checks would not speed them up and
would only add locking. \texttt{ProcessPoolExecutor} gives real parallelism
across the workers, and the ordered merge makes the parallel result identical
to the serial one without a lock on the running totals, because each worker
returns an immutable partial and only the parent mutates the accumulator, in a
fixed order. The two places that do need a lock are the two that have a real
race: the harness workspace, where two checks could run at once and both write
the run, is serialised by an exclusive \texttt{flock} held for the whole check;
and the EricAI token, where several engine processes could refresh at once, is
serialised by an exclusive \texttt{flock} with a re-check after waiting.
Deadlock is avoided by construction: the drain threads are daemon threads
joined only after the runner has been killed and reaped, so they cannot hold a
pipe open against the wait; and the pause loop polls the control file rather
than waiting on a lock the UI holds.

\section{Implementation shortcomings and technical debt}
\label{sec:impl-shortcomings}

The following are known shortcomings, each stated as it is in the code at HEAD.

\paragraph{Non-atomic \texttt{COMMITTED} marker and \texttt{config.yaml}.}
\texttt{Checkpoint.commit} writes the generation file atomically (temp file
plus \texttt{os.replace}) and then writes the \texttt{COMMITTED} marker with a
plain \texttt{write\_text}, which is not atomic; a crash between the two can
leave a complete generation file that the marker does not point at, and
\texttt{discard\_incomplete} would drop it. The run's \texttt{config.yaml} is
also written with a plain write, not the temp-plus-rename pattern, so a
steering \texttt{set} command that re-saves it mid-write could leave a partial
file. Both are low-probability (a crash in a narrow window) and neither
corrupts a committed generation, but they are not atomic in the way the
generation file is.

\paragraph{Timing integrity is best-effort.} The runner binds
\texttt{json}, \texttt{os.write} and the result descriptor before the candidate
runs, which closes the direct routes to faking the timing or the output. It
does not close the indirect ones: a candidate that walks its own frames or
patches \texttt{json} internals could still distort the measured time.
Correctness is not affected, because the verifier re-checks every state it
receives against the oracle; only the work ratio could be gamed, and the bug
hunt found no campaign candidate that attempted it.

\paragraph{\texttt{/etc} is readable in the jail.} The interpreter needs
\texttt{ld.so.cache}, locale and \texttt{passwd} lookups, so \texttt{/etc} is
not hidden; what remains there is world-readable host configuration. The bug
hunt hid the world-readable host data that could reach the LLM through the
result (\texttt{/var/log}, \texttt{/opt}, \texttt{/boot}, \texttt{/etc/ssh});
\texttt{/etc} itself stays, which is a residual, bounded exposure.

\paragraph{LLM sampling is not seeded.} The verifier universe and the parent
selection are deterministic (seeded), but the model's sampling is not, so two
runs with the same configuration do not produce identical fitness
trajectories. Reproducibility is claimed only for the verifier and the
selection, not for the model output; this is stated as a non-functional
requirement and is a property of the provider, not a bug.

\paragraph{No fault corpus for SCC, reachability and MCS.} The seeded-fault
corpus and the known-good references cover BFS, DFS and LBFS, the three
problems in the evaluation. \texttt{DynamicSCC}, \texttt{Reachability} and
\texttt{DynamicMCS} have checkers and are registered, but they have no
self-test references or fault corpus, so the zero-false-negatives claim does
not extend to them.

\paragraph{A lazy reverse dependency in the mock backend.}
\texttt{agents/mock.py} imports the candidate generators from
\texttt{evoalgo.cli} (lazily, inside \texttt{run}), so the agent layer has a
reverse dependency on the CLI. It is confined to the test-only mock backend and
is lazy so it does not load at import time, but it inverts the intended
dependency direction and would be removed if the mock were used outside tests.

\paragraph{No CI for the test suites.} The only GitHub Actions workflow is the
Lean one (\texttt{lean.yml}), for the Lean byproduct. The pytest and Vitest
suites are run by hand (the commands are in the repository notes); there is no
workflow that runs them on push. This is a maintenance gap, not a code defect:
the suites pass at HEAD, but they are not gated in CI.

\paragraph{UI accessibility is not fully validated.} The interface uses
semantic controls with ARIA roles and labels and keyboard-reachable state, but
full WCAG conformance requires manual testing with assistive technology, which
the automated suite does not perform; this is stated as a non-functional
requirement rather than asserted.

\paragraph{Future work.} The natural extensions, in order of proximity to the
current code: an atomic \texttt{COMMITTED} marker and \texttt{config.yaml}
write (temp-plus-rename, as the generation file already uses); fault corpora
and references for SCC, reachability and MCS to extend the zero-false-negatives
claim; a CI workflow for the pytest and Vitest suites; and a seeded or
fixed-temperature model path for fully reproducible runs. The Lean
formalisation step is the furthest out and remains experimental.
