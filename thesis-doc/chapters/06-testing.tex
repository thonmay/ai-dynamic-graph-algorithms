\chapter{Testing and Evaluation}
\label{ch:testing}

This chapter reports how the system was tested and how the experimental
evaluation was run and measured: the test strategy and evidence policy, a
requirement-based test case catalogue, the unit and functional tests, the
verifier self-test over the seeded fault corpus, user interface
testing, integration and end-to-end testing, reliability, security and
performance, the evaluation of the three registered contributions, and the
defects found. Every number is taken from a committed artefact: the campaign
files under \texttt{campaign/}, the suites under \texttt{tests/} and
\texttt{ui/src/}, or a recorded manual check. A median is over the ended runs
of the stated campaign.

\section{Strategy, environment and evidence policy}
\label{sec:test-strategy}

Four categories are used throughout, and every case in
Section~\ref{sec:test-cases} belongs to one or more: \textbf{unit} (one module,
dependencies faked: the state machine, population ranking, problem checkers,
event log, agent tool loop, sandbox jail); \textbf{integration} (two or more
real components at a real boundary: the orchestrator driving a mock provider,
the server streaming a real event log, the harness recording checks as a run,
the parallel verifier reproducing the serial one); \textbf{scenario} (a
user-facing sequence, the headless-Chrome run and the recorded manual UI
checks); and \textbf{regression} (a test written after a defect, that fails
without the fix; the sandbox-limit and DFS/SCC checker tests,
Section~\ref{sec:test-defects}).

All automated tests run on the development host (Linux, x86-64) in the project
virtual environment. The Python suites run with \texttt{.venv/bin/pytest}; the
slow corpus tests (the full $n \le 5$ self-test and the parallel-serial check)
carry the \texttt{slow} marker. The UI is TypeScript under \texttt{ui/}; its
reducer and form logic are unit-tested with Vitest, and \texttt{tsc -{}-noEmit}
is run clean in the build. The browser end-to-end check uses headless Chrome
against the real UI server. The evaluation ran on the EricAI model farm with
thinking off: Qwen3.8-27B-FP8 for the calibration and dynamic-agent campaigns,
Gemma-4-31B-it for the second-model check. The verifier and sandbox ran inside
the same jail for every candidate, so a reported number is always the number
under the enforced limits.

The evidence policy is that a claim is made only when a named artefact supports
it: a test function and its outcome, a CSV, JSON or log under
\texttt{campaign/}, or a screenshot under \texttt{campaign/ui\_check/}. The
suites were last run on 2026-10-25: the fast Python suite collected 193 tests,
of which 188 are not marked slow and all 188 passed in about 140 seconds, and
the 5 slow tests passed in 1140.5 seconds. The Vitest suite passed 14 tests
(4 in \texttt{newrun.test.ts}, 6 in \texttt{state.test.ts}, 4 in
\texttt{status.test.ts}) and \texttt{tsc -{}-noEmit} reported no errors. The
self-test \texttt{evoalgo verify -{}-problem dynamic\_dfs -{}-n-max 5} printed
\texttt{ALL PASS} (\texttt{selftest\_dfs\_n5.log}); the BFS and LBFS commands
printed \texttt{ALL PASS} (\texttt{selftest\_bfs\_n5.log},
\texttt{selftest\_lbfs\_n5.log}).

The verifier's test universe and the two-tier grade are defined in
Section~\ref{sec:universe} of Chapter~\ref{ch:requirements}: directed problems
(BFS, DFS) use the non-isomorphic rooted digraph classes, LBFS uses every
labelled undirected graph, correctness is judged by the problem's certificate
or invariant (refinement R1), and offline recomputation is the efficiency
baseline. This is bounded exhaustive verification, not a proof; the large-graph
benchmark (Section~\ref{sec:test-reliability}) extends passing candidates to
$n = 128$ to measure efficiency, not correctness, at those sizes.

\section{Unit and functional testing}
\label{sec:test-unit}

\subsection{Candidate state machine and population}

The candidate is a single state machine: \texttt{NEW} $\rightarrow$
\texttt{TESTING} $\rightarrow$ \{\texttt{PASS}, \texttt{FAIL},
\texttt{CRASH}\} $\rightarrow$ \texttt{DISCARDED}, a timeout mapping to
\texttt{FAIL} with a timeout flag (Figure~\ref{fig:states} in
Chapter~\ref{ch:design}); any other transition raises
\texttt{TransitionError} (\texttt{candidate.py}).
\texttt{test\_best\_is\_best\_pass\_so\_far} confirms the population ranking:
among equally correct candidates the faster one wins, a timed-out
\texttt{FAIL} (which can report fitness 1.0) never outranks a real
\texttt{PASS}, and the cull keeps the lowest work-ratio passers while
deduplicating only failures that break the same way.

\subsection{Problem checkers}

Each problem carries a certificate checker (\texttt{problem\_definitions.py});
the unit tests confirm the certificates are real, not permissive. The BFS
distance certificate (\texttt{test\_bfs\_distance\_field\_is\_certified})
rejects a valid parent tree with a corrupted distance field and accepts a
parent-only state. The DFS certificate: \texttt{test\_dfs\_requires\_finish}
shows that without finish times only a weak replay check exists;
\texttt{test\_dfs\_rejects\_parent\_that\_did\_not\_discover} rejects a parent
that did not discover its child even with valid times;
\texttt{test\_dfs\_checker\_rejects\_nan\_parent\_cycle\_without\_hanging}
rejects NaN times without hanging. Beyond these unit tests, an exhaustive
cross-check (\texttt{scripts/dfs\_certificate\_crosscheck.py}) enumerates, for
every labelled digraph with $n \le 4$, every certificate that some DFS from the
root can produce (all neighbour orders) together with all single-field
perturbations of them (one parent re-pointed, or two times swapped), and compares
the checker's verdict with the ground truth: 274{,}942 certificates, 0 wrong
verdicts (\texttt{campaign/dfs\_certificate\_crosscheck.log}).
The LBFS certificate, the (LB) 4-point property \citep{corneil2008unified}, is
checked in \texttt{test\_lbfs.py}: the oracle output passes on all labelled
undirected graphs $n \le 5$; the accepted permutations equal brute-force LexBFS
over all starts and tie-breaks (the checker and the reference agree over all
124{,}469 orderings of the labelled graphs $n \le 5$, per
\texttt{selftest/references.py}); the 4-cycle has exactly 8 accepted orderings;
and an MCS ordering that is not a LexBFS ordering is found and rejected. The
SCC checker (\texttt{test\_scc\_rejects\_split\_cycle\_through\_three\_components})
rejects a cycle split across three components, which pairwise merging misses.

\subsection{Event log and command exactly-once}

\texttt{test\_seq\_continues\_after\_reopen} confirms sequence numbers continue
after a reopen; \texttt{test\_partial\_and\_malformed\_lines\_are\_skipped}
confirms a partial and a non-JSON line are skipped, not fatal.
\texttt{test\_validate\_command} and \texttt{test\_send\_command\_rejects\_unknown}
confirm only allowed commands are accepted and an over-long hint or
out-of-range \texttt{set} is rejected.
\texttt{test\_commands\_are\_handled\_once\_across\_restarts} confirms the
exactly-once property: a command is acknowledged once and a channel rebuilt
from the log (as after a resume) does not re-deliver it.

\section{Verifier self-test on the seeded fault corpus}
\label{sec:test-selftest}

The completion signal of the verification contribution (C2) is that the engine
validates known-good algorithms and rejects known-bad mutations with zero false
negatives on $n \le 5$. The self-test drives the real verifier over every
isomorphism-class representative up to $n = 5$ (46,752 rooted base graphs for
BFS and DFS; every labelled graph for LBFS) for references, equivalent controls
and seeded faults, and asserts each verdict. Its result is precise and bounded:
all 48 seeded faults (14 BFS, 22 DFS, 12 LBFS) are rejected on the tested graph
representatives, relabellings and operation histories (all single-edge flips
plus the seeded sequences of Section~\ref{sec:universe}). It shows zero
\emph{observed} false negatives on this corpus; it does not show that every
unknown fault, internal state or arbitrarily long history would be caught.

For dynamic DFS, \texttt{selftest\_dfs\_n5.log} reports 46{,}752 test graphs
($n = 2$ to $5$, directed, nauty universe 4, 36, 752, 45{,}960). The same
self-test was repeated with two relabelled copies of every class
(\texttt{-{}-relabels 2}, the universe of the final grade: 140{,}252 base graphs)
with identical verdicts, all 22 faults rejected
(\texttt{selftest\_dfs\_n5\_relabels2.log}). The
validate-or-rebuild reference and Yang et al.'s fully dynamic DFS
\citep{yang2019dynamic} (Algorithms 2 to 5, in \texttt{selftest/references.py})
are both accepted; the equivalent control (a different tie-break) is accepted;
and all 22 real faults are rejected,
\texttt{Zero-false-negative (n<=5): 22/22}, \texttt{ALL PASS}. For dynamic LBFS,
\texttt{selftest\_lbfs\_n5.log} reports 1{,}098 test graphs (undirected 2, 8,
64, 1{,}024); the reference and control are accepted and all 12 seeded faults
rejected (\texttt{12/12}, \texttt{ALL PASS}). For dynamic BFS, which shares the
rooted universe, the known-good reference and the control are accepted and all 14
seeded faults are rejected (\texttt{14/14}, \texttt{ALL PASS},
\texttt{selftest\_bfs\_n5.log}).

The 15 seeded DFS faults (\texttt{faults.py}) span the realistic failure
modes: stale tree after a tree-edge delete (D1); missed update on insert (D2,
D8, D15); wrong predicate (D3); off-by-one timing (D4, D12, D14); stale
certificate (D5); invalid root (D6); ignores direction (D7); incomplete forest
(D10); invalid parent (D11); stale state (D13); and wrong tree with valid
times (D16, added after the bug hunt). The 7 one-line mutations of the Yang
implementation (Y1 to Y7) cover the same space from the other direction; Y7
(plain vertex order instead of old-discovery order) has no single-update
counterexample and is caught only through the multi-step sequences. The 12 LBFS
faults (L1 to L12) are: missed update (L1, L2); wrong, absent or partial
refinement (L3, L4, L5, L12); wrong pivot (L6, L7); wrong predicate (L8, L9);
stale state (L10); incomplete ordering (L11).

Every real fault carries a documented minimal counterexample with $n \le 5$,
and \texttt{test\_fault\_counterexamples\_trigger\_invariant} re-derives each
against the real \texttt{check\_invariant} without the sandbox: each fault's
counterexample violates the invariant, each control does not.
\texttt{test\_fault\_corpus\_metadata\_complete} confirms one equivalent
control per problem and $n \le 5$ counterexamples. The threat is the bound
itself: a fault that only manifests on a larger graph is not caught, which is
why the large-graph benchmark and a random-update check of the Yang reference
beyond the bound are reported as supporting evidence: 1.44 M seeded random
insertions and deletions on digraphs with $n = 6$ to $30$ at eight densities,
the DFS certificate checked after every update, no violation
(\texttt{scripts/yang\_random\_check.py}, \texttt{campaign/yang\_random\_check.log}).

\section{Integration and end-to-end testing}

\subsection{Server integration}

The web server is tested with a real event log (backfilled from a reference
run) and a FastAPI test client. TC-SRV-01 to TC-SRV-03 in

\subsection{Workspace, resume and parallel-verifier integration}

The harness exposes the same verifier to an external coding agent through
\texttt{evoalgo init/check}. TC-HAR-01 in Table~\ref{tab:test-cases} confirms
the workspace files and a live run; the same tests confirm each check records
a generation with lineage to the last passing check, the final grade outranks
the example grade and the run ends \texttt{done}, the CLI returns JSON with the
correct exit codes (0 pass, 3 fail), and an interrupted check closes its
generation as a crash. For resume, the tests confirm the budget is kept and
parent selection is reseeded identically (the per-generation reseeding fix).
The parallel-serial check (slow) confirms the parallel merge reproduces the
serial semantics exactly (identical state, fitness, test counts, failing case
and timeout for a known-good reference and two real faults, with a chunk size
that splits the $n \le 4$ universe into four chunks); this is the regression
guard for the \texttt{ProcessPoolExecutor} refactor.

\subsection{Mock-provider end-to-end runs}

TC-EVO-02 in Table~\ref{tab:test-cases} and the no-reflection ablation run the
full orchestrator with a mock provider that writes a known-good or known-bad
candidate. The first confirms the search grade on $n \le 2$ during the run and
the final grade on the full bound at the end, with the final grade trying the
next passing candidate when the best search candidate fails the full bound
(\texttt{test\_final\_grade\_tries\_next\_passing}); the second confirms the
no-reflection ablation removes the reflect and repair roles.

\section{Reliability, security and performance}
\label{sec:test-reliability}

\subsection{Sandbox negative tests}

Since the bug hunt, the runner limits itself before candidate code runs: 4 GB
of address space, CPU time equal to the timeout plus 5 seconds, 4 tasks in its
user namespace, 16 MB per file (memory files included) and 64 open files, its
own IPC namespace, 256 MB of result output and 64 KB of stderr
(\texttt{sandbox.py}). The negative tests are TC-SBX-01 to TC-SBX-05 in
Table~\ref{tab:test-cases}, plus three regression tests for a forked child
holding pipes, a CPU spinner, and a timing forgery.

\subsection{Chunk performance}

The measurement procedure: run the reference algorithm on a single final-grade
chunk (1000 graphs at $n = 5$) inside the sandbox with all limits in place, and
record the peak RSS and wall time (\texttt{scripts/chunk\_memory.py}, run on 2026-10-26;
output in \texttt{campaign/chunk\_memory.log}). The DFS reference peaked at 618 MB
of RSS and ran 129 s; BFS peaked at 469 MB and ran 86 s.
\texttt{test\_limits\_leave\_room\_for\_a\_final\_grade\_chunk} confirms a
correct candidate on a full final-grade-sized chunk stays within the memory,
process and output limits (measured peak near 620 MB, about 50 MB of output).

\subsection{Large-graph benchmark beyond the bound}

\texttt{eval1/bench.csv} runs each passing final candidate against the
recompute candidate (same list representation) on random graphs at
$n = 16, 64, 128$, 10 graphs by 200 balanced insert/delete updates, the
invariant checked on every 10th update, each cell in the sandbox jail with a
600 s budget. No invariant violation occurred on any graph beyond $n = 5$;
three LBFS cells timed out (slow, not wrong). Table~\ref{tab:bench} gives the
median speedup over recomputing at $n = 128$ (greater than 1 is faster).

\section{Experimental evaluation}
\label{sec:test-evaluation}

\subsection{Setup and metrics}

The evaluation used a tiered set of problems: dynamic BFS and DFS
(calibration tier) and dynamic LBFS (open tier), directed except LBFS. The
grade has two tiers: a search grade during a run (all non-isomorphic graphs up
to $n = 4$, every single update, three short sequences) and a final grade on
the best candidates ($n \le 5$, 4{,}187{,}856 test sequences for BFS/DFS,
21{,}630 for LBFS). Three modes were compared: the orchestrator (generator,
reflector and repairer agents, population 4, 8 generations, 64 model-call
budget); the same without the reflection role; and a single coding agent
(harness) running the edit-check loop itself. The metric is the work ratio (candidate time over offline baseline time on
the final-grade graphs), and ``vs recompute'' divides it by the
recompute-from-scratch candidate's ratio (\texttt{eval1/reference.json}), so
1.0 means no better than recomputing. Because the baseline runs on a numpy
array (about 2x slower than the same algorithm on lists), a
recompute-from-scratch candidate scores 0.479 (BFS), 0.847 (DFS) and 0.818
(LBFS) rather than 1.

evidence of a correctness effect. The cost is a median of 30 versus 28 model
calls (the same budget), with more tokens for dynamic agents.

final-grade PASS inside the run. The two asterisked harness cells completed the
search but not their own final grade: the
agent's own \texttt{check -{}-final} was killed by its shell's 2 to 5 minute
default timeout on BFS and DFS (the grade takes about 10 minutes), so the kept
candidates were re-graded (\texttt{eval3/final\_regrade.json}); both pass all
4{,}187{,}856 cases (BFS 0.211, DFS 0.1998). So all 9 cells end with a correct,
final-grade-passing candidate, but only 7 were graded inside an uninterrupted
session; the other 2 are post-run regrades of the retained candidates. Every
first search-grade PASS is in generation 1. The fix is that the skill and the
workspace brief now tell the agent to give the command at least 15 minutes
(eval1's Qwen sessions had set a 900 s timeout on their own). As a model
comparison, Gemma used about 22 times fewer tokens per orchestrator run than Qwen
(medians; 75 to 90 k versus 1.1 to 2.7 M per run) and finished in 1 to 16 minutes, with lower
raw work ratios on BFS and DFS. One seed per cell, so this is an indication,
not a measurement.

\subsection{Threats to validity}

The sample sizes are three seeds per cell in eval1, one in eval3, eight in
eval2; medians are reported throughout, and an exact paired test (Wilcoxon
signed-rank and sign test) is applied only to eval2, where the pairing is by
seed, so the eval1 and eval3 comparisons are descriptive. Two models come from
one provider (EricAI); there is no closed frontier model and no Claude Code or
Codex sessions (no keys). The calibration problems are solved quickly, so
differences between modes show in cost, not in whether a correct algorithm is
found. The work-ratio baseline is biased (the numpy reference is about 2x
slower than the same algorithm on lists); ``vs recompute'' corrects for it only
on the $n \le 5$ graphs, and large-graph speedups come from the separate
benchmark. LLM sampling is not seeded; only parent selection is.
