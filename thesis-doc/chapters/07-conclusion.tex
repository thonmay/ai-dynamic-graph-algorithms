\chapter{Conclusion}
\label{ch:conclusion}

\section{Results against commitments and success criteria}

I consider the project a success, and I judge it first by the three completion
signals registered in the topic form, because those are what I committed to.
All three were met (Chapter~\ref{ch:testing}).

\textbf{C1, the research tool user interface, is fulfilled.} The signal was that
the UI can launch, monitor, and replay a multi-generation run end to end. A
recorded headless-Chrome run against the real UI server launched a dynamic BFS
run from the New Run page, followed it live, steered it with a hint that the
engine acknowledged at generation 2, and replayed it with the generation
scrubber after it ended (Section~\ref{sec:test-ui}). The reducer and form logic
are covered by 14 Vitest tests, all passing.

\textbf{C2, the isomorphism-aware verification engine, is fulfilled.} The signal
was that the engine validates known-good algorithms and rejects known-bad
mutations with zero false negatives on $n \le 5$, measured on the seeded fault
corpus. The self-test drives the real verifier over every isomorphism-class
representative up to $n = 5$. All 22 DFS faults (15 seeded and 7 one-line
mutations of the Yang et al.\ reference), 14 BFS faults and 12 LBFS faults are
rejected, and both the validate-or-rebuild reference and the Yang et al.\ fully
dynamic DFS are accepted. Repeating the DFS self-test with two relabelled copies
of every class (140{,}252 base graphs) gives identical verdicts
(Section~\ref{sec:test-selftest}, Table~\ref{tab:selftest}).

\textbf{C3, cooperative agents with optional dynamic agent generation, is
fulfilled for the core signal and reported as a negative result for the
generation variant.} The signal was a correct dynamic BFS algorithm within a
bounded number of generations without human intervention. The orchestrator arm
reaches final-grade PASS in all nine cells, including 3 of 3 BFS seeds, and
every cell reaches a search-grade PASS by generation 3. Dynamic agent generation
works as designed but does not significantly improve the result at this scale
(medians 0.44 versus 0.45, exact Wilcoxon $p = 0.46$,
\citealp{wilcoxon1945}; Section~\ref{sec:test-evaluation}).

\section{Related outcome}

Alongside the thesis I worked on dynamic maximum cardinality search, which was
the first problem I tried the tool on. That work became a separate paper with my
supervisor on how stable MCS orderings are under edge updates, with the proofs
checked in Lean~4. It has been submitted to arXiv but is not public yet. The
paper is not a result of evoalgo and is not part of the evaluation here; I
mention it because working on it shaped my understanding of these problems.

\section{Deviations and refinements}

The four refinements of Section~\ref{sec:refinements} (certificates instead of
raw equality, undirected LBFS, two-tier bounded grading, and the harness as an
extra baseline) narrow or extend the registered wording; none removes a
registered contribution.

\section{Limitations}

The verification is bounded, not a proof: a fault that only manifests on a
graph larger than five vertices is not caught, which is why the large-graph
benchmark and a 1.44 M random-update check beyond the bound are reported as
supporting evidence. The zero-false-negative result holds only for the seeded
fault corpus, within the graph bound and for the tested operation histories.
The limits of the evaluation itself (small-graph efficiency as a weak proxy for
large graphs, few seeds, two models from one provider, unseeded sampling) are
discussed in the threats to validity of Section~\ref{sec:test-evaluation}.
Finally, the timing integrity is best-effort against adversarial
code; the sandbox blocks the direct routes to faking the clock or the output,
but a candidate that patches the interpreter internals could still distort the
measured time.

\section{Lessons learned}

The most interesting part for me was designing the agent orchestration:
deciding which roles the agents should have, what each one sees, and how a
failure is turned into a repair. I was also surprised how capable current models
are. They solved the calibration problems more often than not, usually in the
first generation.

Technically, the hardest part was the sandbox. Candidate code is written by a
model and runs on my machine, so it must not be able to read the API keys the
verifier holds, for example through \texttt{/proc/<ppid>/environ} or token files
in the home directory. Even the coding agents I used struggled with this part;
the final design came out of several rounds of trying ideas with them
(Section~\ref{sec:impl-sandbox}).

Two lessons came from the testing. The checker must be tested as hard as the
candidates: the DFS certificate checker once accepted a parent tree that no DFS
produces, and the fix is backed by an exhaustive $n \le 4$ cross-check over
274{,}942 certificates. And timing must never decide a functional test: a test
that depended on measured work ratios failed once in six reruns on a busy
machine.

\section{Future work}

With six more months, I would first improve the sandbox and the agent workflow,
and reduce token use. Tokens are the main cost of a run. The single agent used
similar or more tokens than the orchestrator, and Gemma used about 22 times
fewer tokens per orchestrator run than Qwen, so reaching the same result with
fewer tokens is clearly possible. After that, the most useful steps would be
fault corpora for SCC, reachability and MCS, so the zero-false-negative claim
extends beyond BFS, DFS and LBFS; more seeds and models, including a closed
frontier model; seeded LLM sampling where the provider allows it; continuous
integration for the test suites, which are currently run by hand; and a full
accessibility check of the user interface against WCAG.
